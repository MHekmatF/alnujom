Four questions, each answered from evidence gathered on the live project and the
code on `main` at `6f5891a`, not from the previous reviews. Where a claim could
be **proven** by running it, it was run — inside a transaction that was rolled
back, so nothing changed.

| Question | Short answer |
|---|---|
| Is anything a real-estate app needs missing? | **Yes, three things.** A publisher cannot mark a listing sold, rented or paused, cannot delete anything but a draft (and that delete silently fails), and a shared listing link points at a domain that does not exist. Plus: nobody is notified of a new chat message or a viewing request. |
| Is it secure? | **Mostly, with two real holes and one overstatement.** Either party in a chat can rewrite the other's messages (proven); a viewing requester can confirm their own viewing (proven); and photos of rejected listings are fetchable by URL with no login (proven) — the July audit said otherwise. |
| Is it fast? | **Yes at this size.** Cold start 1.98 s; a filtered search runs in 69 ms; every list is keyset-paginated. The one drag is images: cards download the full 1920-px photo. |
| Does it scale to big data? | **The code does; the plan does not.** Two unbounded queries (map, chat thread) and the audit log's growth need fixing, and the **Free plan's storage (1 GB) and egress (5 GB/month) are the real ceilings** — roughly 1,000 listings or a few hundred daily active users. |

**And one latent bug that will surface on day one of real use:** the
`notifications` table's CHECK constraint does not allow the type the saved-search
trigger inserts. The first time an admin approves a listing that matches anyone's
saved search, **the approval fails**. Proven below. Nobody has hit it only because
there are zero saved searches today.

## 1. Completeness — what a marketplace needs, and what is here

Sixty-five routes were inventoried from `app_router.dart` and mapped against
what a real-estate marketplace has to do. Present and working (most of it walked
on the device on 2026-09-03/04):

- **Listings:** create (three form modes), edit (direct while draft/rejected;
  stay-live revision once approved), renew, admin feature + verify, moderation
  history, expiry enforced at read time (no job needed).
- **Discovery:** home feed, search with 20 filters, map with clustering, saved
  searches with alerts, smart assistant, reels, similar listings, market
  insights, comparison, recently viewed.
- **Engagement:** favourites, chat, contact form (guest-capable, phone
  encrypted), viewings scheduler, reviews, reports, share.
- **Publisher:** dashboard, my listings, CRM (leads / notes / reminders),
  analytics, agency (create, members, verification, profile, listings).
- **Account:** register, sign in, change password, reset (SMTP-blocked),
  profile edit, self-serve deletion with 30-day purge.
- **Admin:** account approvals, listing review + revisions, reports, agencies,
  inquiries oversight, locations (3 levels), currencies + rate history, ads,
  settings, audit log, analytics, roles + assignment.
- **Platform:** push + in-app notifications, maintenance mode (fails open),
  update prompt, theme / language / currency / data-saver, about + privacy,
  Arabic-first RTL throughout.

### Missing

**M1 — A publisher cannot close a listing.** — **FIXED 2026-09-04 (A15).** The statuses `sold`, `rented` and
`paused` exist in the schema and render everywhere, but there is **no way to
reach them**: no RPC (`set_listing_status`, `mark_sold`, … — none exists among
the 118 public functions), no UI action, and the owner UPDATE policy
`listings_update_owner` only allows edits while the status is `draft` or
`rejected`. The only path to `paused` is an admin resolving a report. After
approval a listing can be revised, renewed, or left to expire — nothing else.
"Sold" is the single most common thing a publisher does after posting.

**M2 — "Delete draft" silently does nothing for a real publisher.** — **FIXED 2026-09-04 (A14 + A15).** `listings`
has one DELETE policy, `listings_delete_admin` (`listings.delete_any`). The
client's `deleteListing` is a bare `.delete().eq('id', …)` with no `.select()`,
so an RLS denial returns zero rows and no error; the bloc then resets the form as
if the draft were gone, and it reappears in My Listings. Both drafts in
production today belong to staff who hold `delete_any`, which is why nobody has
seen it. No publisher can delete anything.

**M3 — Shared links are dead links.** Sharing a listing sends
`https://alnujom.app/listings/<id>`. The domain does not resolve
(`curl: (6)`; NXDOMAIN), and `AndroidManifest.xml` has **no https intent
filter** — only `alnujom://auth/reset-password` — so even a registered domain
would not open the app. The code comment claiming the manifest "already declares
an https VIEW intent" is wrong (it is a `<queries>` entry, which is the
opposite: what the app may *open*). For an app distributed through Telegram,
sharing is the growth loop; today it produces a link nobody can open.

**M4 — Nobody is told about a new chat message or a viewing request.** The
`notifications.type` CHECK allows exactly six types: `account_approved`,
`account_rejected`, `listing_approved`, `listing_rejected`, `inquiry_received`,
`agency_invitation`. `bump_conversation_last_message` only updates a timestamp;
`request_viewing` and `update_viewing_status` enqueue nothing. A buyer's
message reaches the publisher only if the publisher happens to open the
Messages tab; a viewing request is invisible until the Viewings screen is
opened.

**M5 — Smaller gaps, for the record:** no "your listing expires in 3 days"
reminder; no terms of service (known); no block-user; phone verification
accepted as a constraint; the permission catalogue on the role editor is
English-only database text (2026-09-04 walk).

## 2. Security

> **Fixed 2026-09-04, hours after this was written.** Migrations
> `20260904120001_close_proven_write_holes.sql` and
> `20260904120002_throttle_guest_writers.sql` close S1, S2, S4 and the section-5
> bug, and are verified by re-running every proof below. What each section
> describes is the state **before** those migrations; it is kept in the past
> tense of its own writing so the evidence and the reasoning stay readable.
> Still open from this document: **S3** (public bucket — owner decision B14),
> **S5**, and sections 3 and 4. From section 1, **M1 and M2 were fixed the same
> day by A15**; M3, M4 and M5 remain.


The July audit's structure holds: RLS on all 43 tables, storage write policies
ownership-gated with UUID-path enforcement, the service-role key never in the
client, sessions in the encrypted keystore, HTTPS-only, enumeration-resistant
auth endpoints, admin actions behind server-checked permissions, all 15
anon-executable definer functions reviewed 2026-09-03. Re-run on 2026-09-04:
security advisor shows the same 6 definer views (by design), 15 anon + 88
authenticated definer functions (the latter is the normal shape of an RPC
surface), leaked-password (Pro-only), `pg_net` in public (cosmetic). Nothing new
from the advisor.

What the advisor cannot see, and what was found by reading policies and grants:

### S1 — Chat messages can be rewritten by the other party — **proven, FIXED same day**

`messages_update_member` is `USING (caller is buyer or publisher of the
conversation)` with **no WITH CHECK and no column restriction**, and
`authenticated` holds table-wide UPDATE on every column. Run as the buyer
through the normal API role, inside a rolled-back transaction:

```
update public.messages set body = 'TAMPERED by the buyer',
                           sender_user_id = <buyer> where id = <publisher's message>;
→ body = 'TAMPERED by the buyer', sender_is_now_buyer = true
```

A buyer can alter what a publisher said, and who said it, with one hand-crafted
request. The legitimate use of that policy is the read receipt (`read_at`).

### S2 — A viewing requester can confirm their own viewing — **proven, FIXED same day**

`update_viewing_status` correctly restricts `confirmed`/`declined` to the
publisher. But `viewings_update_member` lets either party UPDATE any column
directly, bypassing the RPC:

```
update public.viewings set status = 'confirmed' where id = <own request>;
→ status = 'confirmed'
```

`conversations` has the same shape (member UPDATE, no WITH CHECK); the client
never updates that table, so the grant is simply unnecessary.

### S3 — Photos of unapproved listings are public — **proven**; the July audit was wrong

`listing-images` is a **public bucket**. A public bucket's CDN path
(`/storage/v1/object/public/…`) is served with no auth and no RLS; the
`listing_images_anon_select_when_approved` policy governs only the
`storage.objects` *listing* through the API. Tested with a **rejected**
listing's photo, no key, no session:

```
GET /storage/v1/object/public/listing-images/7a43f8c0-…/6f3ed06f.jpg → 200, 94,071 bytes
GET /rest/v1/listing_media?listing_id=eq.7a43f8c0-…  (anon)          → []
```

The row is hidden; the file is not. This is a design choice more than a hole —
paths are unguessable UUIDs and these are photographs of property, not people —
and the purge job removes files after account deletion. But the audit's
"only serves approved public content" is not true, and the owner should decide
knowingly. `agency-documents` (ID papers) is private, correctly.

### S4 — Three write endpoints callable without login and without any throttle

`submit_inquiry`, `record_lead_event` and `record_ad_event` are intentionally
guest-callable and validate their inputs well, but nothing limits how often.
`submit_inquiry` also enqueues a push notification to the publisher — so one
script can flood a publisher's phone and fill `inquiries`, `lead_events` and
`ad_impressions` without bound. Supabase applies rate limits to Auth endpoints,
not to PostgREST RPC on the Free plan.

### S5 — Smaller

- `listings.phone` / `whatsapp` are readable by anon on approved rows directly,
  bypassing the "reveal" lead event. The number is public by design; only the
  analytics are dodged.
- `sync_auth_email_from_profile` sets `email_confirmed_at` on any email a user
  types, unverified. Not a takeover (auth emails are unique), but a typo sends
  that person's reset mail to a stranger.
- The `ILIKE '%' || p_query || '%'` search does not escape `%`/`_` — a wildcard
  in the query only widens results.
- The held coordinate revoke (plan item A5) remains the one medium item from
  July.

## 3. Speed

Measured, not assumed:

| Measure | Result |
|---|---|
| Cold start to first frame, Infinix X692, release `1.1.1+3` | **1.98 s** |
| `search_listings('شقة', purpose=sale)` — EXPLAIN ANALYZE | **69 ms**, 1,991 buffer hits, all cached |
| `search_map()` unfiltered | 51 ms for 16 markers |
| APK download | **31.7 MB** (was 37.8) |
| Top statement by total time in `pg_stat_statements` | Realtime's own WAL poll (90k calls) — the app's queries are all sub-25 ms |

Pagination is keyset (cursor) on the feed, search and reels, and offset/limit
on my-listings and notifications; every admin list is bounded. Lists render with
builders; only form and detail pages use eager `ListView(children:)`, which is
correct for bounded content.

**P1 — Images are the drag.** Uploads are resized to a 1920-px long edge, EXIF
stripped, JPEG q85 (average **156 KB**, max 396 KB in the bucket). Cards then
download that full file: a home feed of 20 cards is **~3 MB**. `memCacheWidth`
caps the *decode*, not the *download*; data-saver caps the disk cache, not the
transfer. There are no thumbnails for images (`thumbnail_path` is populated only
for videos), and Supabase image transforms are a Pro feature. On Syrian mobile
data this is the single biggest speed and cost item.

## 4. Scale

### The code

Indexes cover the hot paths (status + published_at, governorate/city/area,
publisher + status, GIN on `search_vector`, keyset-friendly composite indexes);
`search_vector` is a generated column so it can never go stale; views use
LATERAL `LIMIT 1` sub-selects that hit the partial unique indexes. Three things
do not scale:

**C1 — The map returns every listing.** `search_map` has **no LIMIT and no
bounding box**; `loadAll()` selects the whole `v_listings_map_public`. At 5,000
approved listings that is a ~1 MB payload and 5,000 markers parsed on every
map open (clustering is client-side, after download).

**C2 — A chat thread streams its entire history.** `watchMessages` is
`.stream().eq(conversation).order(created_at)` with no limit — the Realtime
stream's initial load is the whole thread, every time it opens.

**C3 — The audit log will fill the database.** 19 tables carry audit triggers,
including **three row-level triggers on `listing_media`** (one audit row per
photo insert / update / delete). Today: 1,359 rows, 1.5 MB → **~1.1 KB per row,
~50 rows per listing**. At 10,000 listings that is ~500 MB — the entire Free-plan
database — for a table nobody reads past the first page.

Also noted, lower: `notify_saved_search_matches` scans every saved search per
approval (fine to ~50k); the publisher dashboard subscribes to **all** changes on
`listings` and `inquiries` unfiltered, so every write fans out to every open
dashboard (Realtime messages, and an RLS check per subscriber per event); the
search `ILIKE` on `listing_details.description` is a sequential scan (known,
deferred; needs `pg_trgm`, not installed); `tile.openstreetmap.org` is used
directly, whose usage policy forbids being the default tile source of a
distributed app — expect blank maps if it ever gets popular.

### The plan — this is where it actually stops

| Free-plan limit | Today | When it bites |
|---|---|---|
| Database **500 MB** | 20 MB | Audit log at ~10k listings (C3) |
| File storage **1 GB** | 22 MB | **~1,000 listings** at ~1 MB each (6 photos × 156 KB). The first hard wall. |
| Egress **5 GB / month** | — | ~1,600 home-feed opens/month at 3 MB each; ~10k with thumbnails (P1) |
| Realtime **200 concurrent** | ~1 | A few hundred simultaneous open apps (each dashboard/chat holds a connection) |
| MAU 50k, Edge 500k/month | — | Not a concern |

Limits as published for the Free plan at the time of writing — confirm in the
dashboard. The next tier (Pro, ~$25/month: 8 GB DB, 100 GB storage, 250 GB
egress, 500 Realtime, daily backups, image transforms) removes all four walls at
once, and makes A6's hand-rolled backup and P1's thumbnails less urgent. **The
architecture is sound; the plan is the ceiling.** Budget for Pro at roughly the
1,000-listing mark.

## 5. The latent bug — approvals would have started failing — **proven, FIXED same day**

```
insert into public.notifications (recipient_user_id, type, params)
  values (<any user>, 'saved_search_match', '{}');
→ ERROR 23514: violates check constraint "notifications_type_check"
```

`trg_listings_saved_search_alert` is `AFTER UPDATE FOR EACH ROW` on `listings`
and runs `notify_saved_search_matches`, which inserts exactly that type. It fires
inside `approve_listing_internal`'s UPDATE. So: the first user saves a search →
an admin approves a listing that matches it → the trigger raises → **the
approval transaction rolls back** and the admin sees an error. Today
`saved_searches` has 0 rows, which is the only reason approvals work. The
migration that added the alert (`20260608130001`) never widened the constraint.

Fix is one `ALTER TABLE … DROP CONSTRAINT … ADD CONSTRAINT` listing the new
types — and while there, add the types M4 needs.
