## 2. Found today — not previously recorded anywhere

### 2.1 Orphaned files are 57% of storage — **re-checked**

`listing-images` holds 131 objects for 51 `listing_media` rows plus their
thumbnails; **29 files (3.4 MB) match no row**. `listing-videos` holds 2 files
(9 MB) and there are **0 video rows**. Together 12.5 MB of the 22 MB in use.

By cause, from the path prefixes:

| Files | Under | Most likely how |
|---|---|---|
| 20 | four listing ids that **no longer exist** (one carries 16 files) | hard-deleted listings from before A15; nothing removed their files |
| 9 | nine **approved** listings, one file each | a replaced photo whose original was never removed |
| 2 videos | two **existing** listings | the upload's last step (the media row) failed, or the row was removed and the file was not — the video path has never been walked on a device |

Two things follow. A15 turned publisher delete into a soft delete
(`status = 'deleted'`) so the purge job can find the files — **but the purge
only runs for account deletions**; a deleted listing on a living account keeps
its photos forever. And storage is the first Free-plan wall (review §4), so
this is a cost item, not tidiness. → **A25**.

### 2.2 Every public listing goes dark on 2026-10-06 — **re-checked**

All 16 approved listings carry `expires_at = 2026-10-06`, and every public read
policy hides a row once `expires_at` is past. **On that date the feed, the
search and the map empty at once**, unless the rows are renewed (`renew_listing`)
or replaced by real ones (A11 / B7). If launch happens with the demo data still
in, this is a dated risk. → **A26**, and B7 by then.

### 2.3 New listings never expire — **re-checked**

Nothing in `submit_listing`, `approve_listing_internal` or the relist path
writes `expires_at`; only `renew_listing` extends it and the deletion path sets
it to `now()`. So a listing approved after the demo data has `expires_at = NULL`,
which every policy treats as *never expires*. Review §1 M5 already noted "no
expiry reminder"; the finding here is that there is nothing to remind *about*.
A year in, the feed is old sold flats with no freshness signal. → **A26**.

### 2.4 The backup keeps nothing — **re-checked**

`db-backup.yml` dumps, verifies and restores correctly (A6), then **refuses to
upload without `BACKUP_PASSPHRASE`** because the repository is public. The
secret does not exist (`gh secret list`: `SUPABASE_ANON_KEY`, `SUPABASE_DB_URL`,
`SUPABASE_URL` only). The first scheduled run is tomorrow and will behave the
same way. One owner step (A6, B-list).

### 2.5 The live update manifest is a June placeholder — **re-checked**

`app-release/android/latest.json` says `1.1.0`, build `1`, download at
`https://t.me/alnujom` — written 2026-06-04, before any channel existed. Today
it is harmless (no build newer than the one on the founder's phone is posted),
but it means **no phone on 1.1.x will ever be prompted** until A10 rewrites it
with build `2005` and the real post URL (B5). A duplicate copy sits at
`app-release/app-release/android/latest.json` (backend sweep 2026-09-02, row 182).

## 5. Smaller things noticed, for the record

- The register screen has no password show/hide (login has one) — `REVIEW.md` §3.
- `publisher_approval_pending_page` is the only gate page with no sign-out.
- Rejected/suspended copy says "contact support" with no tap target.

  not a gap.

  is 31.7 MB because the release recipe splits per ABI. Not a gap, but the size
  depends on remembering the flag — `HANDOVER.md` §7 has it.

  it holds only the manifest.
- Deleting a user who was ever a CRM contact trips `crm_leads_identity`
  (July IMPLEMENTATION.md:98) — the A7 purge should be checked against it when
  it first runs for real.
