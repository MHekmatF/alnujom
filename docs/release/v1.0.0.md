## Operator prerequisites

These are not code. They must exist before a production build can be created or
distributed.

### 1. Crash-reporting endpoint + DSN — **DONE**

- Crash reports go to **GlitchTip** (Sentry-protocol compatible; chosen over
  Sentry Cloud for sanctions safety). The app code is provider-agnostic — only
  the DSN differs.
- Supplied at build time via `--dart-define-from-file=.env.json`
  (`"SENTRY_DSN": "<dsn>"`) — never committed (gitignored per ADR-0001).
- **Evidence**: a forced uncaught exception from a signed release build arrived
  in GlitchTip as issue `ALNUJOM-APP-1` on 2026-06-03 (full detail in "Crash
  reporting" below).

### 2. Release keystore — **DONE**

- Keystore lives **outside** the repository; `android/key.properties`
  (gitignored) points at it:

  ```
  storePassword=<password>
  keyPassword=<password>
  keyAlias=<alias>
  storeFile=<absolute-path-to-keystore>
  ```

- `android/app/build.gradle.kts` reads this file and **fails closed** — a
  release build with no `key.properties` fails at Gradle configuration; there is
  no debug-signed fallback.
- **Evidence**: `apksigner` on the 2026-06-03 release APK reports
  `V2 Signer certificate: CN=Hekmat Fanari, OU=AlNujom, O=AlNujom, L=Syria, ST=Aleppo, C=Sy`
  — a real release key, not `CN=Android Debug`.
- ⚠️ **Back up the keystore and its passwords.** Losing them means you can never
  ship an update to the same app again — not on Telegram (Android refuses to
  install an update signed by a different key) and not on Google Play. Keep two
  copies in two places.

### 3. Version manifest on Supabase Storage — **DONE for 1.0.0**

- `latest.json` lives at the `android/` prefix inside the **public**
  `app-release` Storage bucket (exact path the app reads:
  `app-release/android/latest.json`, hardcoded in
  `lib/features/app_update/data/datasources/supabase_manifest_datasource.dart`).
- Schema: `docs/release/version-manifest.example.json`.
- Currently published: `1.0.0` / build `1`. **Must be re-uploaded** with
  `1.1.0` / `2` and the real `telegram_url` when 1.1.0+2 ships.

### 4. Telegram channel — **OPEN (the one outstanding item)**

Create the channel, post the signed APK as a file attachment, copy the post URL
into `latest.json` → `download.telegram_url`.

### 5. Google Play — **SEPARATE TRACK, NOT STARTED**

Previously written here as "Play Store internal testing track". It is now
tracked properly in [`docs/release/google-play-readiness.md`](google-play-readiness.md),
which lists everything Play requires (signing, privacy-policy URL, Data Safety
form, account deletion, target API level, content rating). Note the standing
concern that a Google Play Console account may be difficult or impossible to
obtain from Syria — see that document.

## Build & signing

**Build the distribution APK with:**

```bash
flutter build apk --release \
  --split-per-abi \
  --obfuscate --split-debug-info=build/symbols \
  --dart-define-from-file=.env.json
```

- `--dart-define-from-file=.env.json` is **mandatory** — without it Supabase is
  never initialised and the app red-screens on first use.
- `--split-per-abi` is what makes the download small (see below).
- `--obfuscate --split-debug-info=build/symbols` makes the app harder to
  reverse-engineer. **Keep `build/symbols` out of git** (already gitignored via
  `app.*.symbols`) but **do keep it** — without the symbol files a crash report
  from an obfuscated build is unreadable.

**Fail-closed signing check** (repeat after any Gradle change):

```bash
# Temporarily rename android/key.properties, then:
flutter build apk --release
# Expect: Gradle error "Release signing: 'storeFile' not found in android/key.properties".
# Restore key.properties afterwards.
```

### Download size

| Build | Size | Note |
|---|---|---|
| Fat APK (all ABIs) | ~90 MB | The 2026-07-17 measurement. The 1.0.0 artifact was smaller before later feature growth — though the original notes recorded it inconsistently as both 70.8 MB and 75.6 MB on the same day, so treat the 1.0.0 figure as approximate. |
| `--split-per-abi` → **arm64-v8a** | **37.8 MB** | Verified 2026-07-17. This is the one to post — it covers essentially every phone in use. |
| `--split-per-abi` → armeabi-v7a | 36.0 MB | Very old 32-bit devices only |
| `--split-per-abi` → x86_64 | 39.1 MB | Emulators |

A **58% smaller download** for no code change — which matters a great deal on
Syrian mobile data. R8 minification was tested and deliberately left **off**: on
a Flutter APK it saved ~0.5 MB (the bulk is native `.so`, which R8 does not
touch) for release-only runtime risk. The config is left ready to enable in
`android/app/build.gradle.kts` if wanted later.

> If you post only the arm64 APK, a user on an ancient 32-bit phone cannot
> install it. Either post arm64 only (recommended — simplest, and matches
> virtually all real devices) or post arm64 + armeabi-v7a clearly labelled.

## Crash reporting

Crash reporting uses the Sentry SDK pointed at a self-controlled,
Sentry-compatible endpoint (**GlitchTip**). It is active only in release/profile
builds **when `SENTRY_DSN` is non-empty**; in debug builds, or with no DSN, the
`NoopCrashReporter` is bound — no network, no init.

| Check | Result |
|---|---|
| Forced uncaught exception reaches the dashboard | **PASS** (2026-06-03, signed release on AVD) — `StateError: SENTRY_TEST_CRASH` arrived as `ALNUJOM-APP-1` with stack trace, device (`sdk_gphone16k_x86_64`, Android 17), release `com.alnujom.app@1.0.0+1`, environment `release`, and a breadcrumb trail |
| Payload carries no PII | **PASS** — no phone / email / password / JWT / Vault material. The only identity is a Sentry-generated **random per-install UUID**, which is not the user's account ID |
| App survives an unreachable DSN | **PASS (by demonstration)** — the app kept running through the forced uncaught exception, proving the handlers are non-blocking |
| Empty DSN → `NoopCrashReporter`, app fine | **PASS** — every other build in that session ran with an empty DSN and worked normally |

Hardening confirmed in the July security pass: `sendDefaultPii = false`,
`tracesSampleRate = 0`, a fail-closed `beforeSend`, and a shared redactor
(`lib/core/logging/log_redaction.dart`) that strips JWTs, bearer tokens, emails
and phone numbers from every log line in debug **and** release.

**Secret hygiene**: `SUPABASE_SERVICE_ROLE_KEY` lives in a gitignored,
build-excluded `.env.admin.json` — never in `.env.json`, never in a build.

## July 2026 QA + security pass (branch `qa/e2e-2026-07-16`, PR #95)

A full end-to-end QA sweep plus a security review of session storage, logging,
secrets, and the whole Supabase backend. Full reports:
[`docs/qa/e2e-2026-07-16/SECURITY_AUDIT.md`](../qa/e2e-2026-07-16/SECURITY_AUDIT.md)
and [`IMPLEMENTATION.md`](../qa/e2e-2026-07-16/IMPLEMENTATION.md).

### Fixed

| Fix | What it does |
|---|---|
| **Encrypted session storage** (was the one real weakness) | The login session — including the long-lived refresh token — was being written to **plaintext** SharedPreferences, liftable from a rooted or forensically-imaged phone to sign in as that user. It now lives in the Android encrypted keystore (`flutter_secure_storage`); existing sessions migrate in and the plaintext copy is wiped, with no forced logout. **Verified on the Pixel 8 Pro AVD**: after login → force-stop → relaunch the session persists, and on disk it is Tink AES-SIV ciphertext with an empty plaintext prefs file. |
| **HTTPS-only network config** | `network_security_config.xml` + `usesCleartextTraffic=false` pin the app to HTTPS and reject user-installed certificates (anti-MITM), independent of the Android version default. |
| **Log redaction** | A shared redactor strips JWTs, bearer tokens, emails and phones from every log line, in debug as well as release. |
| **Trimmed API surface** | Revoked needless direct-call grants on four internal trigger functions and the inbox-count function. |
| **Anonymous coordinate leak closed** | Anonymous clients could read every approved listing's **exact** map pin over the raw API, defeating the approximate-location privacy for 100% of listings. `anon` SELECT on `listings.latitude/longitude` is revoked; the detail page now sources its marker from the gated `v_listings_map_public` view. |
| **RLS performance** | `auth.uid()` wrapped as `(select auth.uid())` across every public table — semantically identical, far fewer per-row re-evaluations. |
| **Home feed virtualization** | The feed is a `SliverList.builder` instead of a `Column`, so it no longer keeps every paged card and image alive. AVD-verified against the Blue Crown layout. |
| Plus ~20 smaller functional fixes | Price-filter currency leak, chat optimistic send, favourites photo, create-form exit guard, permission-prompt timing, image decode sizing, FK indexes, dead-font prune. |

### Verified already secure (no change needed)

Row-level security on **every** table; six gated views each correctly filtered;
storage buckets locked down with UUID-path enforcement; admin Edge Functions
require a verified admin JWT; the contact form encrypts the inquirer's phone
number; the publish gate is enforced in the **database**, not just the UI;
enumeration-resistant sign-in and password reset; no hardcoded secrets anywhere;
`allowBackup=false`; hardened manifest.

|---|---|---|

## APK binary secret-scan (1.0.0+1)

Performed 2026-06-03 on the signed `app-release.apk` (recorded as 70.8 MB in the
scan note and 75.6 MB in the distribution note — the discrepancy was never
reconciled): unzip, grep the
contents including `libapp.so`, extract every embedded JWT and base64-decode its
payload to inspect the role claim. **Result: CLEAN.**

- No Sentry/GlitchTip DSN host in the binary (no DSN was set for that scan).
- No keystore password or alias.
- Exactly **one** embedded JWT, decoded role = `anon` — **no** `service_role`,
  no `sb_secret_`.
- No FCM service-account JSON (`"type":"service_account"`, `private_key`).
- Expected and correct: the Supabase URL and the public **anon** key are
  present. Those are designed to ship in a client; RLS is what protects the
  data, not the secrecy of that key.

**A 1.1.0+2 rescan has NOT been done.** Repeat it before distributing, since the
app has gained Firebase, video upload and chat since.

## No-email account recovery

AlNujom authenticates by phone number. Most accounts use a synthetic email
(`<E.164>@alnujom.local`) that cannot receive mail, so the emailed reset link
only works for the small number of accounts with a real email on file. If a user
is locked out:

1. The user contacts support (Telegram channel or in-app inquiry).
2. A super-admin finds the account by phone in Supabase → **Authentication →
   Users** (or `SELECT id, phone FROM auth.users WHERE phone = '<phone>';`).
3. The super-admin sets a temporary password using the **Change password** field
   in the user editor. ("Send password recovery" does nothing useful for a
   synthetic email.)
4. The user signs in with the temporary password and changes it in the app.

This requires super-admin credentials and is intentionally not self-serve.
