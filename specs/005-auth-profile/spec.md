# Feature Specification: Auth & Profile

**Feature Branch**: `005-auth-profile`
**Created**: 2026-05-10
**Status**: Draft
**Input**: User description: "Phase 5 — Auth & profile. Phone+password registration with synthetic email, login, account-approval workflow gating publishing. New `account_approval_requests` table auto-populated on profile creation, Vault-backed columns for `legal_name`, `national_id`, `private_contact_methods` per ADR-0001, an interim `is_admin` boolean on `profiles` (replaced when Phase 6 ships). Frontend `lib/features/auth/`, `lib/features/profile/`, `lib/features/onboarding/`, plus a phone-number value object in `lib/shared/domain/` with E.164 normalization."

## Clarifications

### Session 2026-05-10

- Q: Which Vault storage mechanism does Phase 5 use for `legal_name`, `national_id`, and `private_contact_methods`? → A: Per-user secrets in `vault.secrets`, one row per user-per-field, keyed by a deterministic name like `pii.<user_id>.<field_name>`. Read paths layer on top of Phase 4's `app_vault_secret(name)` helper: a self-decrypting helper `app_vault_secret_for_self(field_name)` resolves `auth.uid()` and reads `pii.<auth.uid()>.<field_name>`; an admin-gated sibling helper `app_vault_secret_for_user(user_id, field_name)` checks the admin predicate and reads `pii.<user_id>.<field_name>`. No encrypted columns are added to `profiles`; no sibling table is added. Writes happen through a `SECURITY DEFINER` SQL function (or Edge Function) that calls `vault.create_secret()` / `vault.update_secret()` so the Vault key never leaves the server.
- Q: What is the content shape of the `private_contact_methods` Vault secret? → A: Structured JSON — a JSON object whose keys are drawn from a server-validated allowlist of channel keys (`whatsapp`, `telegram`, `signal`, `private_email`, `secondary_phone`) and whose values are the corresponding handle/number/address. Validated at the write boundary against the allowlist; unknown keys are rejected. The single Vault secret named `pii.<user_id>.private_contact_methods` stores the JSON-serialized object; the `legal_name` and `national_id` secrets remain plain TEXT. Downstream consumers (Phase 16 inquiries' "show inquirer my contact", Phase 19 agency contact) consume the typed JSON, not free-form text.
- Q: What is the password policy at registration and password-change time? → A: Minimum 8 characters, no complexity requirements (no mandatory letter/digit/symbol mix), no maximum length cap below Supabase Auth's platform limit. Aligned with NIST SP 800-63B's length-over-complexity guidance, more usable for the Syrian market's non-tech users than complexity rules, and a stricter baseline than Supabase Auth's default 6-character minimum. The Supabase project's `auth.minimum_password_length` setting is configured to `8` to match. The localized validator message is "Password must be at least 8 characters" (Arabic + English). The same policy applies to password reset and password change flows.
- Q: What is the scope of admin actions on the Phase 5 admin queue page? → A: Pending-only — the queue lists `account_approval_requests` rows where status = `pending`, newest first, and the admin's only actions are **approve** or **reject** (with typed reason). Suspending an already-approved user, lifting a suspension, and re-opening a rejection are explicitly DEFERRED to Phase 7's super-admin UI. This matches the implementation plan's Phase 5 deliverables exactly (which list "approve / reject" but not "suspend / unsuspend") and keeps Phase 5's surface area minimal. The previous draft of US 4 mentioned "suspend" as a third action — that mention is removed; `account_status='suspended'` is reachable in v1 only via privileged SQL (Supabase MCP `execute_sql`) until Phase 7 ships the surface.
- Q: After the first authenticated sign-in (FR-018), which side wins for `locale` on subsequent sign-ins? → A: **Server wins post-first-sign-in.** On every authenticated sign-in after the first, `user_preferences.locale` is the source of truth and overwrites the device-side `flutter_secure_storage` value. The in-app locale picker (Phase 3's `LocaleCubit` once authenticated) writes through to BOTH `user_preferences` (durable, server-side) and `flutter_secure_storage` (offline cache so signed-out / cold-start screens render without a server round-trip). The first-sign-in-on-this-device exception in FR-018 still applies: the very first authenticated sign-in seeds `user_preferences.locale` from the device's chosen locale (so a user who picked Arabic on the onboarding screen does not get switched to a server-default value on their first authenticated session). Multi-device users have one consistent locale across devices; the local cache only matters for the signed-out / pre-authenticated UX.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Register with phone and password, then wait for admin approval before publishing (Priority: P1)

A first-time visitor opens the app on their phone, walks through onboarding (Arabic-first, RTL), taps "Create account", and enters a phone number (with country code, defaulting to `+963` for Syria), a password, and — optionally — a real email address for password recovery later. They submit. Behind the scenes the app constructs a synthetic email from the normalized E.164 phone number (`+963XXXXXXXXX@alnujom.local`) and signs up with Supabase Auth using that synthetic email plus the password. Supabase creates the `auth.users` row; the auto-provision trigger from Phase 4 creates the matching `profiles` row (`account_status = pending`, `publisher_status = pending`) and the matching `user_preferences` row atomically; this phase's new trigger additionally inserts an `account_approval_requests` row keyed to the new profile. The user is signed in but lands on a localized "Account pending approval" screen — they cannot reach home, cannot publish, cannot view restricted content. They close the app. An admin (via an interim flag explained in Story 4) flips `account_status = approved`. Next time the user opens the app, they sign in with phone + password (the app re-derives the synthetic email under the hood), and this time they land on home.

**Why this priority**: This is the entire critical path of the platform. Until users can register and be admitted by an admin, no later phase has actors to test against — Phase 6 (roles) needs admins, Phase 8+ (locations, currencies, listings, etc.) needs approved publishers, Phase 16 (inquiries) needs both an inquirer and a publisher. Constitution Principle VIII (Approval Workflow & Publisher Identity) is the binding rule: nothing publishable goes live without admin approval, and the approval gate IS this phase. The phone-first / synthetic-email design is itself a non-trivial product decision (see implementation-plan §6.6 and the migration journal in §11): most Syrian users don't have or know an email, SMS-OTP is unreliable in the region, and admin approval is the phone-verification gate. This story is the MVP slice — it ships register + login + the four account-status screens (pending, rejected, suspended, approved-redirects-home) and nothing else, but on its own it already lets the project stand up its first real user.

**Independent Test**: From a fresh app install on the reference Android device against the remote Supabase project: complete onboarding, register with phone `+963991234567` + a chosen password + optional real email. Confirm the app lands on the "Account pending approval" screen. Inspect the remote project via Supabase MCP `execute_sql`: `profiles` has one row for the new `auth.users.id` with `account_status = 'pending'`, `publisher_status = 'pending'`, the entered phone normalized to E.164, and the optional real email if supplied; `user_preferences` has the matching row from the Phase 4 auto-provision trigger; `account_approval_requests` has exactly one row pointing at the new profile. Force-close and re-open the app, attempt to log in with the same phone + password. Confirm sign-in succeeds and the app returns to the pending screen — `pending` is sticky until an admin acts. Then, via Supabase MCP `execute_sql` running as a privileged session, set `account_status = 'approved'` for that user. Sign in again from the device. Confirm the app lands on home (or, if Phase-8+ home is not yet ready, on the post-approval landing slot Phase 5 owns).

**Acceptance Scenarios**:

1. **Given** a new visitor on the onboarding screen, **When** they enter phone `+963991234567`, a valid password, and submit, **Then** the app calls `supabase.auth.signUp` with the synthetic email `+963991234567@alnujom.local`, an `auth.users` row appears, the Phase-4 auto-provision trigger produces one `profiles` row (`account_status='pending'`, `publisher_status='pending'`, `phone='+963991234567'`) and one `user_preferences` row, this phase's trigger produces one `account_approval_requests` row, and the user lands on the localized "Account pending approval" screen.
2. **Given** a registered user whose `account_status='pending'`, **When** they sign in with their phone + password, **Then** sign-in succeeds (Supabase Auth issues a session) and the app routes them to the pending screen — not home, not any publishable surface.
3. **Given** the same user after an admin sets `account_status='approved'`, **When** they sign in with their phone + password, **Then** the app reads the updated status and routes them to home.
4. **Given** a registered user whose `account_status='rejected'`, **When** they sign in, **Then** the app routes them to a rejection screen that displays the reviewer-supplied reason from `account_approval_requests`.
5. **Given** a registered user whose `account_status='suspended'`, **When** they sign in, **Then** the app routes them to a suspension screen. (In Phase 5, `account_status='suspended'` is reachable only via privileged SQL — Supabase MCP `execute_sql` running as `postgres` — per the Session 2026-05-10 queue-scope clarification; the in-app affordance for an admin to suspend an approved user lands with Phase 7's super-admin UI. The sign-in branch must still handle the state correctly when reached out-of-band.)
6. **Given** any incorrect phone or password combination, **When** sign-in is attempted, **Then** the app shows a single localized error message ("Invalid phone or password") that does NOT distinguish "phone not found" from "password wrong" (avoiding account enumeration).
7. **Given** a user with `account_status='pending'`, **When** they attempt to publish or perform any publisher-gated action, **Then** the action is refused — the app surfaces a message explaining that approval is required, and (when later phases ship publisher-gated UI) the affordance is hidden or disabled outright.
8. **Given** a user signs out from any app surface, **When** they re-open the app, **Then** they land on onboarding (or, if onboarding has been seen before, the login screen), and any previously-cached session is gone.

### User Story 2 - View and edit my own profile (Priority: P1)

After approval, a user opens their profile page from the home navigation. They see their full name, username, phone (E.164 formatted, read-only — the platform-of-record value), optional real email, and avatar. They tap edit, change their full name, choose a username (which must be unique across the platform), optionally update the real email, and save. The change persists to the `profiles` row, the audit-trigger from Phase 4 emits an `audit_logs` row capturing the diff for any admin-relevant field, and the next time they reload the profile page the new values are present. The user CANNOT change their `account_status`, `publisher_status`, or the Vault-backed admin-only fields (`legal_name`, `national_id`, `private_contact_methods`) from the user-facing edit page — those are separate surfaces with separate gating (status fields are admin-only; Vault-backed fields belong to the user but are written through a privileged path and decrypted only for the user themselves and admins).

**Why this priority**: Profile read/edit is the second half of the auth/profile story — without it, an approved user has nothing to do in the app. Constitution III (RLS) requires the profile-edit path to be self-only at the database level, not just at the UI level. Constitution IX (Future Backend Portability) requires the profile feature to live behind a domain repository so swapping Supabase out later does not touch UI or use cases. This is also the first phase that adds a real Flutter feature folder on top of the Phase 1 shell — so the feature-folder shape (`data/`, `domain/`, `presentation/`) for `lib/features/auth/` and `lib/features/profile/` is established here for every later feature to follow.

**Independent Test**: As an approved user on the device, open the profile page; confirm the displayed values match the `profiles` row read via Supabase MCP `execute_sql`. Tap edit, change the full name and pick a new username, save. Confirm the page reloads with the new values; confirm `profiles.full_name` and `profiles.username` updated on the remote; confirm an `audit_logs` row was appended for the change (per Phase 4's audit trigger contract). Try to set the username to a value already taken by another user — confirm the save fails with a localized "username taken" error and the row is unchanged. From a *second* approved user's session, attempt to read or update the first user's profile — RLS suppresses both. Open the profile page in Arabic and English; confirm RTL/LTR mirroring and that all user-visible strings come from the localization runtime (Phase 3) — no literal strings.

**Acceptance Scenarios**:

1. **Given** an approved user on the profile page, **When** the page loads, **Then** it displays their `full_name`, `username` (or "set a username" placeholder if NULL), phone (read-only, E.164), optional `email`, `avatar_url` (or a default avatar), and their `account_status`/`publisher_status` (read-only, badge or label).
2. **Given** the profile edit form, **When** the user changes their full name to a non-empty value and saves, **Then** the `profiles` row updates, the page refreshes, and the new value is present on subsequent reads.
3. **Given** the profile edit form, **When** the user picks a username that no other profile holds, **Then** the save succeeds and `profiles.username` updates.
4. **Given** the profile edit form, **When** the user picks a username that another profile already holds, **Then** the save is rejected with a localized "username taken" message and `profiles.username` is unchanged.
5. **Given** the profile edit form, **When** the user attempts to change `account_status` or `publisher_status` (e.g., via a crafted client request bypassing the UI), **Then** the database refuses the update — the column-level admin-enforcement trigger from Phase 4 raises `42501 insufficient_privilege`.
6. **Given** an authenticated user A and another authenticated user B, **When** user B issues a `SELECT` or `UPDATE` against user A's `profiles` row, **Then** RLS suppresses the read (zero rows) and rejects the write (zero rows affected) — Phase 4's self-only RLS posture is preserved exactly.
7. **Given** the profile page, **When** the device locale is Arabic, **Then** the layout mirrors RTL, the body font is the Arabic font from Phase 2's bilingual stack, and every visible string resolves through Phase 3's `AppLocalizations` — no Dart literal user-visible string ships in the file.

### User Story 3 - Reset password when a real email is on file (Priority: P2)

A user who registered with an optional real email address forgets their password. From the login screen they tap "Forgot password?", enter their phone, and the app — having looked up the user's `profiles.email` — calls Supabase Auth's password-reset flow against the **real** email (NOT the synthetic email, which is just an internal join key). Supabase emails the user a reset link. The user clicks it, sets a new password, and signs back in with phone + new password. A user who registered without a real email sees a different message: "We don't have an email on file for this account. Please contact support." Phase 5 does not yet ship a self-service flow for those users — admin-issued temporary passwords are deferred to the super-admin UI in Phase 7.

**Why this priority**: P2 because it is not on the critical path for the first user — registration and approval (Story 1) work whether or not the user remembers their password later. But it is the only user-visible self-recovery path the platform has in v1 (Constitution VIII gates approvals on admins, not on automated phone-OTP), and shipping it later means a real user lockout in the meantime. Bundling it into Phase 5 is cheap because Supabase Auth already exposes `resetPasswordForEmail` — Phase 5 only adds the UI and the lookup-by-phone-then-route-to-real-email step.

**Independent Test**: As a user who registered with a real email on file, tap "Forgot password?", enter the phone. Confirm the reset email arrives at the real email (not the synthetic one). Click the link, set a new password, sign in with phone + new password — confirm sign-in succeeds. As a user who registered without a real email, tap "Forgot password?", enter the phone. Confirm the app shows the "no email on file — contact support" message and does NOT silently call the reset flow against the synthetic email (the synthetic-email mailbox does not exist; sending mail to it is wasted at best and a security signal at worst).

**Acceptance Scenarios**:

1. **Given** a user with `profiles.email` set to a real address, **When** they enter their phone on the reset-password screen and submit, **Then** the app calls `supabase.auth.resetPasswordForEmail` against `profiles.email` (the real address), and a reset link arrives there.
2. **Given** the user receives the reset link and clicks it, **When** they choose a new password and confirm, **Then** Supabase Auth updates the password and the user can sign in with phone + new password.
3. **Given** a user with `profiles.email IS NULL`, **When** they enter their phone on the reset-password screen and submit, **Then** the app shows the localized "no email on file — contact support" message and makes NO call to `resetPasswordForEmail`.
4. **Given** a phone the platform does not recognize, **When** entered on the reset-password screen, **Then** the app shows the SAME generic "if an account exists for this phone, a reset link has been sent" message it shows for the success path (avoiding account enumeration), and makes no reset call.

### User Story 4 - Admin reviews and acts on pending account-approval requests (Priority: P1)

An admin signs in (an admin in Phase 5 is a user whose `profiles.is_admin = true` — the interim boolean Phase 6 will replace with the role/permission system). They open an admin queue page that lists every `account_approval_requests` row in `pending` state, newest first. For each request the admin sees the registrant's phone, the optional real email, the registrant's stated full name (if supplied during registration), and the timestamps. The admin chooses one of two actions per pending request: **approve** (sets `account_approval_requests.status = approved` and `profiles.account_status = approved`) or **reject** with a typed reason (sets `status = rejected`, stores the reason, and sets `profiles.account_status = rejected`). Every action emits one `audit_logs` row per affected table via the Phase 4 reusable trigger. A non-admin who attempts to reach the admin queue page is bounced — both by route guards in the app and by RLS at the database (the policy that grants read on the admin queue is gated by the admin predicate). Suspending an already-approved user, lifting a suspension, and re-opening a rejection are explicitly out of scope for Phase 5 and ship in Phase 7's super-admin UI; reaching `account_status = 'suspended'` in v1 happens only via privileged SQL (per the Session 2026-05-10 clarification).

**Why this priority**: This is the other half of Story 1's critical path — registration without an admin to approve is a dead end. Constitution VIII requires admin approval as the publishing gate, and Constitution VII requires every admin action to be audit-logged with actor + before/after state. The feature itself is small (a pending list, two buttons, a reason field), but the wiring it establishes — admin-gated routing, admin-gated RLS via the `current_user_is_admin()` helper, audit-trigger reuse from Phase 4 — is the template Phases 6, 7, 11, 16, 19, 21 all follow. P1 because Story 1 is unverifiable end-to-end without an admin path.

**Independent Test**: Pick one user from the existing test set and set `profiles.is_admin = true` via Supabase MCP `execute_sql` (this is the only way to bootstrap the first admin in Phase 5; Phase 7 ships the super-admin UI for managing admins). Sign in on the device as that admin. Confirm the admin queue route is reachable from the home navigation (or wherever the admin tile lives in this phase) and lists every pending account-approval request. As a non-admin user, confirm the same route is NOT reachable from the navigation and that direct URL navigation is bounced. As the admin, approve one pending user — confirm `profiles.account_status` flips to `approved`, `account_approval_requests.status` flips to `approved`, and exactly one `audit_logs` row is appended for each (per Phase 4's audit-trigger contract). Reject another pending user with a typed reason — confirm the reason is stored and surfaces on that user's "rejected" screen on their next login.

**Acceptance Scenarios**:

1. **Given** an authenticated user whose `profiles.is_admin = true`, **When** they open the admin queue page, **Then** the page lists every `account_approval_requests` row whose status is `pending`, newest first, with phone + optional email + timestamps. Approved, rejected, and suspended users are NOT in this list — the queue is pending-only in Phase 5.
2. **Given** the admin queue page, **When** the admin taps "approve" on a row, **Then** `account_approval_requests.status` updates to `approved`, `profiles.account_status` updates to `approved`, and exactly one `audit_logs` row is appended per affected table (actor = the admin, before/after JSON populated).
3. **Given** the admin queue page, **When** the admin taps "reject" and types a reason and confirms, **Then** `account_approval_requests.status` updates to `rejected`, the reason is stored on the request row, `profiles.account_status` updates to `rejected`, and an `audit_logs` row is appended per affected table.
4. **Given** an authenticated user whose `profiles.is_admin` is `false` (or `NULL`), **When** they attempt to reach the admin queue page, **Then** the route guard refuses navigation AND the database RLS on `account_approval_requests` returns zero rows for cross-user reads.
5. **Given** the admin acts on a request, **When** the affected user signs in next, **Then** they see the post-action screen for their new status — approved → home, rejected → rejection screen with the stored reason. (Suspension is unreachable from the queue in Phase 5; if a privileged SQL action sets `suspended`, the user lands on the suspension screen on next sign-in per US 1.)
6. **Given** the `current_user_is_admin()` placeholder helper from Phase 4 (returns `false` for everyone), **When** Phase 5 ships, **Then** the helper is rewritten to return `COALESCE((SELECT is_admin FROM profiles WHERE user_id = auth.uid()), FALSE)` — wrapped in `COALESCE` so the function returns a non-NULL boolean even when no profile row matches `auth.uid()` (e.g., during the brief auto-provision window before the row exists, or for a service-role caller without an `auth.uid()`) — and every Phase 4 policy that referenced the placeholder picks up the new behavior without that policy file being edited (the central-helper invariant from Phase 4 is preserved).

### User Story 5 - Private identity fields are stored in Vault, not as plaintext (Priority: P2)

When a user fills in or updates their `legal_name`, `national_id`, or `private_contact_methods` (the admin-only PII fields from Constitution VIII / ADR-0001), the values are written through a privileged path that stores them in Supabase Vault, not as plaintext columns. A normal user can read their OWN values back through a decrypting view (the user is allowed to see their own PII). A different authenticated user receives nothing — RLS blocks the row, and even if RLS were bypassed, the columns would be encrypted ciphertext. A `pg_dump` of the database does not contain the plaintext values. An admin (via the interim `is_admin` flag) can read every user's decrypted PII through an admin-gated decrypting view.

**Why this priority**: P2 because the user-visible flow does not depend on it being feature-rich in v1 — most users will not enter `national_id` or `legal_name` until prompted by a future feature (e.g., agency verification in Phase 19, or a high-trust seller badge). But Constitution III sets the bar for a real-estate marketplace handling national-ID-level data, ADR-0001 commits the project to Vault for admin-only PII, and ADR-0001's verification clause specifically requires Phase 5 to "store via Vault" the three named fields. Shipping the columns now — even with no UI surface yet — also locks in the encryption-at-rest invariant before any production data lands. The first migration that adds a Vault-backed column is the one that proves the Phase-4 scaffolding works end-to-end.

**Independent Test**: As a signed-in user on the device, navigate to the (this-phase) profile page's "private identity" section, enter a `legal_name` and a `national_id`, and save. Inspect via Supabase MCP `execute_sql`: `profiles` has no plaintext column for these fields; `vault.secrets` has two new rows whose names are `pii.<this-user-uuid>.legal_name` and `pii.<this-user-uuid>.national_id` and whose `secret` column is ciphertext. Call `app_vault_secret_for_self('legal_name')` from the user's own JWT-claims-simulated session — get the plaintext back. Switch to a second authenticated user and call the same helper for `'legal_name'` — get the SECOND user's value (or NULL if they have not set one), never the first user's. Call `app_vault_secret_for_user(<first-user-uuid>, 'legal_name')` from a non-admin session — get NULL. Switch to an admin (interim `is_admin = true`) and call the same helper — get the first user's plaintext. Run `pg_dump` (or its MCP-exposed equivalent) and confirm the plaintext does not appear; only the encrypted bytes in `vault.secrets` are present.

**Acceptance Scenarios**:

1. **Given** the user's profile-edit page exposes the private identity fields, **When** the user saves a value for `legal_name`, `national_id`, or `private_contact_methods`, **Then** the value is stored as a row in `vault.secrets` with name `pii.<user_id>.<field_name>` — no plaintext column on `profiles` holds it and the write goes through a `SECURITY DEFINER` server-side function (the client never sees the raw key).
2. **Given** the user signs in and reads their own profile, **When** `app_vault_secret_for_self(field_name)` is called for each PII field, **Then** the user sees their own decrypted values.
3. **Given** authenticated user B calls `app_vault_secret_for_self('legal_name')`, **When** the helper resolves `auth.uid()`, **Then** it reads `pii.<user_B>.legal_name` — never user A's secret. There is no path through which `app_vault_secret_for_self` returns another user's value.
4. **Given** an admin (interim `is_admin = true`), **When** they call `app_vault_secret_for_user(<any-user-uuid>, field_name)`, **Then** the helper passes the admin-predicate check and returns the decrypted value for that user.
5. **Given** a non-admin authenticated user, **When** they call `app_vault_secret_for_user(<other-user-uuid>, field_name)`, **Then** the helper fails the admin-predicate check and returns NULL — it does NOT leak the ciphertext or raise an error that distinguishes "you're not admin" from "secret doesn't exist".
6. **Given** a database dump or any whole-table SELECT, **When** the rows are inspected, **Then** the private identity values appear only as ciphertext in `vault.secrets`; no plaintext copy exists anywhere in the schema.

### Edge Cases

- **Phone normalization**: A user who types `0991234567`, `0991-234-567`, or `+963 99 123 4567` MUST end up with the same E.164 form `+963991234567` in `profiles.phone`. The phone-number value object in `lib/shared/domain/` performs this normalization once, at the boundary; downstream code only sees the canonical form. Two users MUST NOT be able to register the same phone in different formats.
- **Synthetic email collision**: Two users MUST NOT share a synthetic email. Because the synthetic email is derived deterministically from the canonical E.164 phone, the collision check reduces to "phone is unique on `profiles`" — Phase 4's `UNIQUE(phone)` constraint enforces this, and the registration flow surfaces the collision as a localized "phone already registered" error.
- **Username uniqueness on edit**: When a user edits their username, the new value MUST be rejected if any *other* profile holds it. The profile's own current username must NOT be treated as a collision against itself.
- **Auto-provision trigger absorbs the auth-side insert**: When `supabase.auth.signUp` succeeds, the Phase 4 auto-provision trigger creates the `profiles` row before any client-side code runs. Phase 5 MUST NOT also try to insert a profile from the client — the only remaining work is updating the profile with the registration-form fields (full name, phone in E.164, optional real email).
- **Mid-session status change detection (covers pending lockout AND out-of-band suspension)**: A user's `profiles.account_status` can change while their session is live — either from `pending` → `approved | rejected` via the admin queue (US4) or from `approved` → `suspended` via privileged out-of-band SQL (Phase 5 has no in-app suspend; per the Session 2026-05-10 queue-scope clarification, the in-app surface ships in Phase 7). The `AuthBloc` MUST detect the change at three observation points: (a) the auth-state listener stream (Phase 4 FR-016), (b) `WidgetsBindingObserver.didChangeAppLifecycleState(resumed)` triggering a profile re-read (research R-21), and (c) the next database action (RLS independently enforces gating where later phases tie policies to `account_status`). Route guards alone are not sufficient — the user MUST NOT be able to bypass the pending / rejected / suspended screen by manipulating the client.
- **Rejected user re-registers**: A user rejected once tries to register again with the same phone. The platform behavior in v1 is to refuse — `profiles.phone` is unique, so the second `signUp` fails on the synthetic-email collision via the existing phone uniqueness, and the surface message is "phone already registered". A re-application path is deferred (admins can re-open a rejection by changing the user's status; a true "delete account" flow is post-v1).
- **Anonymous client sees nothing**: An unauthenticated client MUST NOT be able to read `profiles`, `account_approval_requests`, or any other Phase 5 table. Phase 4's anon-blocked baseline is preserved; Phase 5 adds no public-read tables.
- **Admin-only fields stay admin-only**: A regular user editing their profile MUST NOT be able to change `account_status`, `publisher_status`, or `is_admin` even via crafted client requests. The Phase 4 column-level enforcement trigger (`enforce_profile_status_admin_only()`) raises `42501 insufficient_privilege`; Phase 5 extends the same trigger or adds a sibling check to also block `is_admin` mutations from non-privileged callers.
- **Vault-backed fields are write-through**: A user updating their own `legal_name`, `national_id`, or `private_contact_methods` writes through a server-side path (Edge Function or `SECURITY DEFINER` SQL function) — the client cannot store ciphertext directly because the Vault key never leaves the server. Reads come back through a decrypting view that respects RLS.
- **Real-email recovery is the only self-serve recovery in v1**: A user without `profiles.email` set MUST see the "contact support" message on the reset-password screen and MUST NOT receive a reset email at the synthetic mailbox (the mailbox does not exist; sending email there is wasted at best and an information leak at worst). The admin-issued-temporary-password path lands in Phase 7's super-admin UI.
- **Account enumeration resistance**: Both the login path and the reset-password path MUST surface the same generic message for "phone known, action accepted" and "phone unknown, action ignored" — the user-facing copy MUST NOT distinguish "no such phone" from "wrong password" or "no email on file but phone exists" from "phone doesn't exist".
- **Audit emission on status flip**: Phase 4's audit trigger fires on any change to `account_status` / `publisher_status`. Phase 5 MUST NOT bypass it — every admin action that changes status goes through a normal `UPDATE` so the trigger fires; nothing pre-empts the trigger or writes `audit_logs` directly from the client.
- **Real-time admin queue is out of scope**: The admin queue page reflects the database state at fetch time. A new pending request appearing while the admin is on the page does NOT auto-update — the admin pulls to refresh. Realtime subscriptions land later (Phase 22+); this phase is explicit pull.
- **Onboarding shown once**: Onboarding screens (welcome / value props / language picker if not picked) MUST NOT replay on every launch. A persisted flag (in `flutter_secure_storage` per Phase 1's secure-storage pattern, or in `user_preferences` once an account exists) records the "onboarding seen" state.
- **Locale handoff from secure storage to user_preferences**: Phase 3 stores the chosen locale in `flutter_secure_storage`. The first time a user signs in to an authenticated session in Phase 5, the device-side locale MUST be reconciled with `user_preferences.locale` — if `user_preferences.locale` was created with the Phase 4 default `'ar'` and the device-side locale is something else, the device-side value wins on first sign-in (the user's explicit choice carries forward) and is written through to `user_preferences.locale`. Subsequent reads come from `user_preferences`.
- **Phone-number value object rejects malformed input at the boundary**: The value object's constructor MUST reject input that cannot be normalized to E.164 (e.g., letters, fewer than the minimum digits, a clearly-foreign country code with an invalid length) and surface a localized "invalid phone" error in the UI. The database does NOT see invalid phones — the boundary catches them.
- **Idempotent migrations**: Every Phase 5 migration MUST be safe to re-apply against the remote Supabase project. Supabase's migration tracker handles the normal flow; migration bodies SHOULD also use idempotent constructs (`CREATE … IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`, `DROP TRIGGER IF EXISTS … CREATE TRIGGER …`, `DO $$ … EXCEPTION WHEN duplicate_object THEN NULL; END $$`) so a forced re-apply does not error.
- **Domain layer stays Supabase-free**: The new `lib/features/auth/`, `lib/features/profile/`, and `lib/features/onboarding/` folders MUST follow Constitution IX — `domain/` imports nothing from `package:supabase_flutter`; the `data/` layer is the only place Supabase types appear.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST support user registration via phone number + password + optional real email. The phone number is captured via the country-code-aware UI (defaulting to `+963`) and normalized to E.164 by a phone-number value object in `lib/shared/domain/value_objects/`. The synthetic email passed to Supabase Auth is `<E.164 phone>@alnujom.local`. The password MUST be at least 8 characters with no complexity requirements (no mandatory letter/digit/symbol mix); the same minimum applies to password change and password reset (per the Session 2026-05-10 clarification on the password-policy question). The Supabase project's `auth.minimum_password_length` setting is configured to `8` to match the app-side validator. Validator errors surface localized strings ("Password must be at least 8 characters" in Arabic + English).
- **FR-002**: On successful `auth.signUp`, the Phase 4 auto-provision trigger creates one `profiles` row (defaults `account_status='pending'`, `publisher_status='pending'`) and one `user_preferences` row. Phase 5's registration flow MUST NOT also insert into either table from the client. The remaining client work is updating the new profile with the form's `full_name`, `phone` (in E.164), and optional `email`.
- **FR-003**: System MUST add a new `account_approval_requests` table with at minimum: `id` (UUID PK), `user_id` (FK to `auth.users.id`, unique), `status` (enum: `pending`, `approved`, `rejected`), `rejection_reason` (TEXT, nullable), `reviewed_by` (UUID, FK to `auth.users.id`, nullable), `reviewed_at` (TIMESTAMPTZ, nullable), `created_at` (TIMESTAMPTZ, default `now()`), `updated_at` (TIMESTAMPTZ, maintained by `set_updated_at()`). RLS is enabled by default; policies (per FR-008) allow self-read and admin-read-and-write only.
- **FR-004**: System MUST add a database trigger that auto-inserts an `account_approval_requests` row whenever a new `profiles` row is inserted (i.e., whenever the Phase 4 auto-provision trigger fires for a new `auth.users`). The trigger MUST be idempotent (`ON CONFLICT (user_id) DO NOTHING`) to absorb the signup-race edge case end-to-end.
- **FR-005**: System MUST store `legal_name`, `national_id`, and `private_contact_methods` per ADR-0001 as per-user secrets in `vault.secrets` — one row per user-per-field, keyed by the deterministic name `pii.<user_id>.<field_name>` (e.g., `pii.<uuid>.legal_name`). The `legal_name` and `national_id` secrets hold plain TEXT values. The `private_contact_methods` secret holds a JSON-serialized object whose keys are drawn from a server-side allowlist (`whatsapp`, `telegram`, `signal`, `private_email`, `secondary_phone`) and whose values are the corresponding handle/number/address (per the Session 2026-05-10 clarification on the contact-shape question). No plaintext column for these three fields is added to `profiles`; no sibling encrypted-columns table is added either. Writes go through a `SECURITY DEFINER` SQL function that calls `vault.create_secret()` / `vault.update_secret()` — the Vault key never leaves the server, and the client never sees ciphertext or the raw key. (The plan-time research locked this to SQL functions only; an Edge Function alternative was considered and rejected in research R-13.) The write path for `private_contact_methods` rejects unknown keys at the boundary; phone-typed values (`secondary_phone`) are normalized to E.164 by the same value object used for `profiles.phone` before serialization. The migration that installs the helpers is `20260510120004_profiles_vault_pii_helpers.sql` per the timestamp filename convention locked in Phase 4 R-02 (the implementation-plan hint `0008_profiles_vault_columns.sql` is historical and superseded — see research R-01).
- **FR-006**: System MUST expose two read paths for the Vault-backed fields, both layered on top of Phase 4's `app_vault_secret(name)` helper: (a) a self-decrypting helper `app_vault_secret_for_self(field_name TEXT) RETURNS TEXT` that resolves `auth.uid()` internally and reads `pii.<auth.uid()>.<field_name>` via `app_vault_secret`; (b) an admin-gated sibling `app_vault_secret_for_user(user_id UUID, field_name TEXT) RETURNS TEXT` that checks the admin predicate (`current_user_is_admin()`, the central helper Phase 5 swaps the body of per FR-007) and reads `pii.<user_id>.<field_name>`. Both helpers MUST return `NULL` (not raise) when the secret does not exist — the same shape Phase 4's `app_vault_secret` already guarantees. Cross-user reads via (a) are impossible by construction (the user_id is `auth.uid()`); non-admin reads via (b) MUST return `NULL` instead of leaking the secret.
- **FR-007**: System MUST add the column `profiles.is_admin` (BOOLEAN NOT NULL DEFAULT FALSE) — the interim admin flag explicitly called out by the implementation plan as a Phase 5 stopgap that Phase 6 replaces. The Phase 4 `current_user_is_admin()` helper MUST be replaced (one definition swap, not policy-file edits) to return `(SELECT is_admin FROM profiles WHERE user_id = auth.uid())`. Bootstrap of the first admin happens via privileged-session SQL only (Supabase MCP `execute_sql`); there is no in-app affordance to flip `is_admin` in Phase 5.
- **FR-008**: System MUST add RLS policies for `account_approval_requests`: self-read (a user can see their own request), admin-read-all (the admin predicate gates the all-rows read), admin-write (the admin predicate gates the status/reason update); no client INSERT (the trigger on FR-004 is the only writer); no client DELETE (rejected/approved requests are retained for audit). The admin-write policy is the path through which the Phase 4 audit trigger fires for status changes.
- **FR-009**: System MUST extend Phase 4's column-level enforcement (`enforce_profile_status_admin_only()` or sibling) to also block client-initiated mutations of `profiles.is_admin`. A non-privileged session that attempts to update its own (or anyone's) `is_admin` MUST receive `42501 insufficient_privilege`. The privileged-role list (per Phase 4's R-12 decision) bypass continues to apply for Supabase MCP `execute_sql` running as `postgres`.
- **FR-010**: System MUST attach an audit trigger to `account_approval_requests` for changes to `status`, `rejection_reason`, `reviewed_by`, and `reviewed_at` — reusing the Phase 4 `log_audit()` function unchanged (per Phase 4 FR-009's reusability invariant). The trigger's third `TG_ARGV` is `'user_id'` so the audit-log target id matches the affected user.
- **FR-011**: System MUST ship a `lib/features/auth/` feature folder with `data/`, `domain/`, and `presentation/` subfolders following Clean Architecture (Constitution IV). Specifically: `data/datasources/supabase_auth_datasource.dart` (synthetic-email construction + Supabase Auth calls; the only file in this feature that imports `package:supabase_flutter`), `data/repositories/auth_repository_impl.dart`, `domain/entities/{credentials,phone_number,session}.dart`, `domain/repositories/auth_repository.dart`, `domain/usecases/{register,login,logout,reset_password}.dart`, `presentation/bloc/auth_bloc.dart`, and `presentation/pages/{login_page,register_page,pending_approval_page,rejected_page,suspended_page}.dart`.
- **FR-012**: System MUST ship a `lib/features/profile/` feature folder with profile-view and profile-edit pages, a Cubit (or BLoC), a domain repository interface, a data-layer Supabase implementation, and a use case for username-uniqueness validation that maps the Postgres unique-constraint violation into a domain-layer "username taken" error. The domain layer MUST NOT import `package:supabase_flutter`.
- **FR-013**: System MUST ship a `lib/features/onboarding/` feature folder with a splash screen and onboarding screens (Arabic-first; bilingual; uses Phase 2 design tokens and Phase 3 localization). An "onboarding seen" flag is persisted in `flutter_secure_storage` (the Phase 1 wrapper) so subsequent launches skip onboarding.
- **FR-014**: System MUST ship a phone-number value object in `lib/shared/domain/value_objects/phone_number.dart` that normalizes input to E.164 and rejects malformed input at the boundary. The same value object is used by the registration flow, the login flow, the reset-password flow, and the profile-edit flow. The value object MUST NOT depend on `package:supabase_flutter`.
- **FR-015**: System MUST construct the synthetic email deterministically from the E.164 phone in exactly one helper (`syntheticEmailFor(phoneNumber)`) so that registration, login, and any future internal lookup share one definition. The format is `<E.164 phone>@alnujom.local`.
- **FR-016**: System MUST gate every publisher-relevant action behind `account_status = 'approved'`. In Phase 5 specifically that means the pending/rejected/suspended screens replace home for non-approved users, and any client-side affordance the rest of the app (Phases 8+) ships will read the same gate. The database independently enforces this for every later phase via RLS policies tied to the user's status. **Scope of Phase 5's enforcement**: Phase 5's only gate is the screen-routing redirect (the `AuthBloc` + `go_router` redirect helper sends non-approved users to `/pending` | `/rejected` | `/suspended` instead of `/home`). Distinguishing "phone unknown" from "password wrong" or "no email on file but phone exists" from "phone doesn't exist" is forbidden in the user-facing copy.

### Key Entities

- **PhoneNumber (value object)**: A normalized E.164 phone number. Constructed from raw user input plus a default country code; rejects malformed input at the boundary. Equality is by canonical string. The single source of truth for phone format across the app.
- **Credentials**: A pair of (phone, password) used for registration and login. Crosses the domain boundary into the auth use cases; the synthetic-email derivation happens at the data-layer boundary, not in the domain.
- **Session**: The provider-agnostic auth-state record exposed by the auth repository. Wraps the Supabase session token's existence/absence + the linked user id + the user's `account_status` snapshot. The presentation layer reads `Session` through the repository; nothing in `presentation/` ever imports a Supabase type.
- **AccountApprovalRequest**: One row per user. Tracks the lifecycle of admin approval (`pending` → `approved` | `rejected`). Stores who acted (`reviewed_by`), when (`reviewed_at`), and — on rejection — the reviewer-supplied reason. Auto-created by trigger on profile insert; never client-inserted; never client-deleted; admin-mutable.
- **AdminPredicate (Phase 5 form)**: The `current_user_is_admin()` SQL function whose body Phase 5 swaps to `(SELECT is_admin FROM profiles WHERE user_id = auth.uid())`. The single helper definition every admin-gated policy across the project depends on; Phase 6 swaps the body again to `current_user_has_permission('admin')` without touching policy files.
- **VaultBackedProfileFields**: The conceptual entity for `legal_name`, `national_id`, and `private_contact_methods` — stored as per-user secrets in `vault.secrets` keyed by `pii.<user_id>.<field_name>` (per the Session 2026-05-10 clarification). `legal_name` and `national_id` are plain TEXT secrets; `private_contact_methods` is a JSON-serialized object with allowlisted typed keys (`whatsapp`, `telegram`, `signal`, `private_email`, `secondary_phone`). Read through `app_vault_secret_for_self(field_name)` and `app_vault_secret_for_user(user_id, field_name)` per FR-006. Not present as plaintext columns on `profiles`, and not present as encrypted columns either — Phase 5's storage choice is the secrets-store pattern, not column-level encryption.
- **OnboardingState (presentation)**: The "has the user seen onboarding before?" flag. Persisted in `flutter_secure_storage` (per Phase 1's wrapper) so onboarding shows exactly once per device install. Independent of authentication state.
