# Feature Specification: Listing Creation & Submit-for-Review

**Feature Branch**: `010-listing-creation`
**Created**: 2026-05-18
**Status**: Draft (awaiting clarifications)
**Input**: User description: "Phase 10 — Listing creation. Goal: Approved publishers can create draft listings with all v1 fields; submit changes status to `pending_review`. Backend: migrations `0016_create_listings.sql`, `0017_create_listing_details.sql`, `0018_create_listing_prices.sql`, `0019_create_listing_visibility.sql`, `0020_create_listing_status_history.sql`; status-transition trigger that writes `listing_status_history` rows; Edge Function `submit_listing` (validates required fields, sets status, writes history); policies — owner draft/edit, public approved-read, admin edit_any. Frontend: `lib/features/listing_form/` — multi-step form (basics → location → details → prices → visibility settings → media placeholder → review); `lib/features/publisher_dashboard/` — `MyListingsPage`, status filters; validators in `lib/core/validators/` for area, price, phone. Acceptance: an approved publisher creates a draft, fills all required fields, submits → status becomes `pending_review`; a non-approved user cannot reach the form; a rejected listing is editable and resubmittable; status history shows the transition chain. Authored per docs/IMPLEMENTATION_PLAN.md §Phase 10."

> **Scope note**: Phase 10 introduces the *publisher's authoring surface* and the listing-status engine. It does NOT introduce the admin approval workflow (Phase 12 owns `approve_listing` / `reject_listing` and the moderation queue), media upload + watermark (Phase 11), public browsing of approved listings (Phase 13), search and filters (Phase 14), or map view (Phase 15). Phase 10 ships listings whose public surface is **draft-only-visible-to-owner-and-admins**; the public-read-when-approved RLS policy is included in this phase's migrations so Phase 12's approval flip is a status change, not a policy change. The `listing_media` table itself is forward-stated to Phase 11 — Phase 10's "media placeholder" step is a no-op UI stub with the Phase 11 hook point. The `listings.agency_id` column ships in Phase 10's migration with the column declared but **not yet FK-constrained** — the FK to `public.agencies(id)` is added by Phase 19 (per IMPLEMENTATION_PLAN §Phase 19 deliverables).

## Clarifications

### Session 2026-05-18

The three questions below MUST be answered before `/speckit-plan` runs. They shape the `submit_listing` validation contract, the Phase 10 vs Phase 15 boundary, and the multi-currency-price form UX. Answers are folded back into this spec under "Functional Requirements" before planning.

- **Q1 — Required-field set for `draft → pending_review` submission**: Which fields are required by `submit_listing` before a draft may transition to `pending_review`? → **B: Full set.** The `submit_listing` server-side validation requires every one of the following to be non-null / non-empty: `title`, `purpose`, `property_type`, `governorate_id`, `city_id`, `area_id`, `address_text`, `area_size`, AND at least one `listing_prices` row with `is_primary=true`, AND at least one of `phone` OR `whatsapp` (the contact channel). For residential `property_type` values (`apartment`, `villa`), `rooms` AND `bathrooms` are ALSO required; for non-residential types (`land`, `shop`, `office`, `farm`, `warehouse`, `other`), `rooms` and `bathrooms` are optional. `description`, `year_built`, `furnished`, `parking`, `floor`, `location_visibility` (defaults to `approximate`), `contact_name_visibility` (defaults to `public`), `hide_until`, `latitude`, `longitude` (per Q2 resolution), and `agency_id` remain optional. The client-side form mirrors the same rule and blocks the Submit button on the Review step until all required fields are filled; the server-side `submit_listing` re-runs the check as the authoritative gate. The chosen set raises publisher friction but lowers admin moderation cost, reducing the likelihood of "submitted but incomplete" listings clogging the Phase 12 queue.
- **Q2 — Latitude/longitude entry mode in Phase 10**: How does the publisher set `listings.latitude` / `listings.longitude` in Phase 10, before Phase 15 introduces the `flutter_map` + OSM dependency? → **A: Area-centroid auto-fill.** When the publisher picks an `area_id` in the location step, the form auto-populates `listings.latitude` / `listings.longitude` from the area's centroid coordinates. The publisher cannot override the value in Phase 10 — there is no map widget, no manual numeric input, and no "use my GPS" affordance. Phase 15 (Map view) will add a pin-drop edit affordance as a separate post-Phase-10 capability. **Data-source caveat**: Phase 8 explicitly deferred lat/lng columns on `public.areas` per its Clarifications Session 2026-05-16 Q1 + research R-10, and pre-stated that Phase 10 was expected to carry its own coordinates. To deliver Q2's auto-fill behavior, the Phase 10 plan-time research file MUST select ONE of these three data-source paths and lock the decision before `/speckit-implement` runs: (i) **Phase 10 ALTER TABLE migration** adding `centroid_lat NUMERIC(9,6)` + `centroid_lng NUMERIC(9,6)` columns to `public.areas` AND seeding them via a static fixture (~10 governorates × 5–10 areas ≈ 50–100 centroids researched manually from OpenStreetMap), with a `NOT NULL` constraint enforced only after the seed completes; (ii) **Flutter-side static map** in `lib/features/locations/data/area_centroids.dart` keyed by `area_id` — no schema change to Phase 8, but the form must be re-deployed when new areas are added; (iii) **Governorate-fallback** — Phase 10 ALTER TABLEs `public.governorates` (only 14 rows, smaller seed surface) with centroid columns and uses the governorate centroid as the listing's coordinates regardless of which area is picked. **Recommended path for plan-time**: (i) area-level centroids seeded server-side, because it lines up with FR-019a-style "Phase 8 row carries its own canonical data" pattern from prior phases and avoids client-redeploy-when-areas-change. Phase 10 spec FR-013 / FR-019 are updated to reflect Q2's UX resolution; the data-source choice is deferred to research.
- **Q3 — Multi-currency price entry UX**: Does the Phase 10 prices step let the publisher add multiple `listing_prices` rows (USD + SYP) in one form pass, or single-currency-only at first submit with edit-to-add later? → **A: Single-currency-only across every Phase 10 surface.** The Phase 10 listing form's prices step shows exactly ONE currency picker + ONE amount field; there is NO "Add another currency" affordance, NO multi-row entry, and NO multi-currency edit sub-page in Phase 10. Every Phase 10 listing has exactly one `listing_prices` row with `is_primary=true`. The Phase 9 forward-stated schema support (`UNIQUE(listing_id, currency_code)`, the FR-019a row-selection rule's "fall back to primary when no matching currency row exists" branch) remains intact in Phase 10 migrations, so a future spec can layer multi-currency entry on top without re-architecting either Phase 9 or Phase 10. For Phase 10's RLS write policy, owner UPDATEs on `listing_prices` are still permitted on the single existing row (publisher can correct the amount or change the currency while the parent listing is in `draft` or `rejected`); the policy does NOT need to know whether multiple rows exist. The "multi-currency listing" use case Phase 9 anticipated remains exercisable in production only by direct admin SQL until the future-spec UX lands; the Phase 9 FR-019a row-selection rule's primary branch handles every Phase 10 listing correctly.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Approved publisher creates a draft listing through the multi-step form (Priority: P1)

A signed-in user whose `profiles.publisher_status='approved'` (set by an admin during Phase 5's account-approval flow; carried forward unchanged in Phase 6/7) opens the publisher dashboard, taps the "Create listing" call-to-action, and walks through the seven-step listing form: **basics** (title, listing purpose `sale | rent | daily_rent | investment`, property type `apartment | villa | land | shop | office | farm | warehouse | other`), **location** (governorate → city → area cascading dropdown via the Phase 8 `LocationPicker`, plus an `address_text` free-text field, plus latitude/longitude per Q2's resolution), **details** (description, amenities multi-select, `year_built`, `furnished` boolean, `parking` boolean, `area_size` in square meters, `rooms`, `bathrooms`, `floor`), **prices** (one or more `listing_prices` rows per Q3's resolution, with currency picked from the Phase 9 `currencies` catalog and exactly one row flagged `is_primary=true`), **visibility settings** (location-visibility `hidden | approximate | exact | admin_only`, contact-name-visibility `public | admin_only`, optional `hide_until` deferral timestamp), **media placeholder** (a no-op step in Phase 10 — a banner indicating "media upload arrives in Phase 11"), and **review** (a full preview rendering plus a Submit action). Tapping Submit calls `submit_listing` which validates the required fields per Q1, transitions the listing's status from `draft` to `pending_review`, writes a `listing_status_history` row, and returns success. The dashboard re-renders showing the listing under the "Pending review" status filter.

**Why this priority**: P1 because the entire phase exists to ship this flow. Constitution VIII (Approval Workflow & Publisher Identity) requires that publishing is gated by approval status; this story exercises the publisher-side leg of that workflow. Without US1, no listing ever enters the system and Phases 11–17 have nothing to render.

**Independent Test**: Apply Phase 10 migrations to the remote Supabase project via Supabase MCP `apply_migration`. **Acceptance Scenarios**:

1. **Given** an approved-publisher session and a clean draft, **When** the publisher completes all seven steps with the required-field set per Q1 and taps Submit, **Then** `submit_listing` returns success, the listing's `status` flips from `draft` to `pending_review`, exactly one row is appended to `listing_status_history` with `previous_status='draft'` / `new_status='pending_review'` / `changed_by=auth.uid()`, and the publisher dashboard re-renders the listing under the "Pending review" filter.
2. **Given** an approved-publisher session, **When** the publisher partially fills the form and leaves the screen (back button, app close, lifecycle suspend), **Then** the in-progress data is persisted as a `status='draft'` row with whatever fields have been filled so far; returning later re-opens the form pre-populated at the step they left.
3. **Given** the publisher reaches the Review step with one or more required fields missing, **When** they tap Submit, **Then** `submit_listing` rejects with a localized error listing the missing fields by display label; the listing remains in `draft` status; no `listing_status_history` row is appended.
4. **Given** any successful insert into `public.listings`, **When** the row commits, **Then** an INSERT-side `listing_status_history` trigger writes a row capturing `previous_status=NULL` / `new_status='draft'` / `changed_by=auth.uid()`, so the history table reflects the listing's full status lineage from inception.
5. **Given** the publisher edits a `draft` listing and re-submits, **When** the same `submit_listing` call commits, **Then** the listing's status flips from `draft` to `pending_review` via the same trigger path (no special-case code). The audit-side guarantees from US6 also apply.
6. **Given** the listing-form widget tree, **When** an automated grep is run against `lib/features/listing_form/`, **Then** no `package:supabase_flutter` imports appear inside the widget tree (Constitution IX-clean — datasource isolated under `data/`).

### User Story 2 — Non-approved users cannot reach the listing form or write listings (Priority: P1)

A signed-in user whose `profiles.publisher_status` is `pending`, `rejected`, or `suspended` — or whose `account_status` is `pending`, `rejected`, or `suspended` — does NOT see the "Create listing" affordance on their dashboard. The Phase 5 pending/rejected/suspended screens already block these users from reaching most app surfaces; Phase 10 extends the gate by hiding the create affordance, by adding a router guard on `/publisher/listings/create` that refuses navigation, and by enforcing write-side RLS on `public.listings` that requires `auth.uid() = publisher_user_id` AND `publisher_user_id IN (SELECT user_id FROM public.profiles WHERE publisher_status='approved' AND account_status='approved')`. Anonymous (not-signed-in) users cannot reach the form at all because the router guard requires authentication. Three-layer enforcement matches Constitution III; the RLS policy is the final safety net even if the UX layer or router guard is bypassed.

**Why this priority**: P1 because without this gate, any signed-in user could publish listings, defeating the Phase 5 approval workflow and Constitution VIII (Approval Workflow & Publisher Identity). The Phase 5 / Phase 6 precedent established UX-hide + route-guard + RLS as the standard three-layer pattern.

**Independent Test**: Sign in as a `publisher_status='pending'` user on the reference device. Confirm the publisher dashboard does NOT render a "Create listing" affordance — instead, the existing Phase 5 "Pending approval" guidance message renders. Hand-type `/publisher/listings/create` into a deep link; confirm the route guard refuses and redirects per the established admin-route unauthorized pattern. From a desktop with this user's JWT, attempt `INSERT INTO public.listings (publisher_user_id, purpose, property_type, title, governorate_id, status) VALUES (<this user's id>, 'sale', 'apartment', 'test', <some governorate>, 'draft')` via Supabase MCP `execute_sql` — confirm the INSERT returns 0 rows affected (RLS deny). Repeat for `publisher_status='rejected'` and `publisher_status='suspended'`. Repeat for an anonymous (not-signed-in) Supabase client — confirm both the route guard and RLS deny.

**Acceptance Scenarios**:

1. **Given** a signed-in user whose `publisher_status='pending'`, **When** the publisher dashboard renders, **Then** the "Create listing" affordance is hidden (not dimmed); the existing Phase 5 pending-approval messaging is shown instead.
2. **Given** any non-approved publisher session (`pending` / `rejected` / `suspended`), **When** the user deep-links to `/publisher/listings/create` or `/publisher/listings/<id>/edit`, **Then** the router guard refuses the navigation and redirects per the admin-route unauthorized pattern established in Phase 5.
3. **Given** any non-approved publisher session, **When** the user crafts a direct INSERT / UPDATE / DELETE against `public.listings` (or any child table `listing_details` / `listing_prices` / `listing_visibility`), **Then** the write-side RLS policy rejects the write (0 rows affected). For inserts, the policy requires `auth.uid() = publisher_user_id` AND `publisher_user_id IN (approved-publishers)`.
4. **Given** an approved publisher whose `account_status` later becomes `suspended` (account suspension while still publisher-approved), **When** they attempt to create or edit a listing, **Then** the same gate applies — both `account_status='approved'` AND `publisher_status='approved'` are required by RLS.
5. **Given** an anonymous (not-signed-in) Supabase client, **When** it attempts to SELECT a `draft` or `pending_review` listing's row, **Then** the public-read RLS returns 0 rows — only `status='approved'` listings within the publish window are publicly readable per the FR-005 policy (the policy itself ships in Phase 10; Phase 12 flips listings into the public surface by transitioning them to `approved`).

### User Story 3 — Rejected listing is editable and resubmittable (Priority: P1)

A publisher whose listing was rejected by an admin in Phase 12 (returning `status='rejected'` with a rejection reason text on the most recent `listing_status_history` row) sees the listing on their `MyListingsPage` under the "Rejected" filter, with the rejection reason rendered inline plus a "Resubmit" CTA. Tapping the CTA opens the same multi-step form pre-populated with the existing values; the publisher addresses the rejection reason and taps Submit. `submit_listing` validates per Q1, transitions the listing from `rejected` to `pending_review`, writes a new `listing_status_history` row, and returns success. The full transition chain (`NULL → draft → pending_review → rejected → pending_review`) is preserved in the history table for admin / audit visibility. Phase 10 also permits editing while the listing is in `draft` status (the in-progress authoring window — covered by US1 acceptance scenario 2). Editing while the listing is `approved` is **NOT** in scope for Phase 10 — Phase 12 owns the post-approval edit policy (the implementation plan implies "publisher must request edit" but the exact mechanism is deferred to a later spec).

**Why this priority**: P1 because the implementation plan's third headline acceptance criterion ("A rejected listing is editable and resubmittable; status history shows the transition chain") is realized here. Without the resubmit loop, publishers whose first attempt was rejected have no path forward.

**Independent Test**: Sign in as an approved publisher who has one listing in `status='rejected'` (the rejection was inserted by a prior Phase 12 admin action — for Phase 10's manual test, the rejection can be inserted directly via Supabase MCP `execute_sql` since Phase 12's `reject_listing` Edge Function does not yet exist). Open the publisher dashboard, switch to the "Rejected" filter. Confirm the listing card renders with the rejection reason prominently visible (Arabic in `ar` locale, English in `en`). Tap the "Resubmit" CTA. Confirm the multi-step form opens at step 1 with all fields pre-populated. Fix the issue that caused rejection (e.g., revise the description) and tap through to the Review step. Submit. Confirm success. Query `SELECT previous_status, new_status, changed_by, changed_at, reason FROM public.listing_status_history WHERE listing_id=<this id> ORDER BY changed_at ASC` — confirm the chain shows four rows: `(NULL→draft)`, `(draft→pending_review)`, `(pending_review→rejected, reason=<admin's reason>)`, `(rejected→pending_review)`.

**Acceptance Scenarios**:

1. **Given** an approved-publisher session and a listing in `status='rejected'`, **When** the publisher dashboard renders the "Rejected" filter, **Then** the listing card displays the rejection reason from the most recent `listing_status_history` row and a "Resubmit" CTA.
2. **Given** the publisher taps "Resubmit", **When** the form opens, **Then** every field is pre-populated from the existing `listings` / `listing_details` / `listing_prices` / `listing_visibility` rows; the publisher may edit any field; the listing remains in `status='rejected'` until they tap Submit.
3. **Given** the publisher submits a previously-rejected listing, **When** `submit_listing` commits, **Then** the status flips from `rejected` to `pending_review` and a new `listing_status_history` row is appended; the full status chain is preserved.
4. **Given** a publisher attempts to edit a listing whose `status='approved'`, **When** the form would normally open, **Then** the form refuses to open with a localized "approved listings can not be edited in v1; contact support to request a change" message — this is the Phase 10 stub for the deferred post-approval edit policy.
5. **Given** the status-transition trigger that auto-writes `listing_status_history`, **When** any caller (Edge Function, RLS-permitted direct UPDATE, admin script) flips `listings.status`, **Then** exactly one history row is appended per transition. Concurrent transitions on different rows do not interfere; concurrent transitions on the same row are serialized by row-level locking.

### User Story 5 — Publisher enters a single primary price via the prices step (Priority: P2)

In the prices step of the multi-step form, the publisher selects exactly ONE currency from the Phase 9 `currencies` catalog (SYP or USD by default, plus any admin-added currencies) and enters one amount per Q3's single-currency-only resolution. The row is auto-flagged `is_primary=true` on save. There is NO "Add another currency" affordance, NO multi-row entry, and NO multi-row delete in Phase 10's form — the prices step is intentionally narrowed. The publisher MAY change either the currency or the amount on the single row at any time while the parent listing is in `draft` or `rejected` status (the same edit window as the rest of the form). Amounts must be positive; `MoneyFormatter` (Phase 9) shows the formatted amount inline as the publisher types. The currency dropdown lists only `is_active=true` rows from `public.currencies`, ordered by `sort_order`. The Phase 9 forward-stated schema support — `UNIQUE(listing_id, currency_code)`, the FR-019a row-selection rule's primary-fallback branch — remains intact so a future spec can add multi-row entry without altering Phase 9 or Phase 10's schema layer, but Phase 10's UI surface never exercises the multi-row branch.

**Why this priority**: P2 because the single-currency form is the entire publisher-facing pricing surface in Phase 10. The Phase 9 FR-019a row-selection rule's primary-fallback branch handles every Phase 10 listing correctly (single row → that row is always selected). Multi-currency entry is deferred to a future spec per Q3.

Phase 10 leaves no migration debt.

### User Story 6 — Status-transition trigger auto-writes `listing_status_history` on every status change (Priority: P2)

Phase 10 attaches a trigger on `public.listings` that, on every INSERT (to capture the initial `NULL → draft` lineage) and every UPDATE that changes the `status` column, appends a row to `public.listing_status_history` carrying `(listing_id, previous_status, new_status, changed_by, changed_at, reason)`. The trigger captures `changed_by` from `auth.uid()` when called inside an RLS-authenticated session, or `NULL` when called from a system context (e.g., the seeded test data in a future fixture migration, or the Phase 12 system-driven auto-expiry trigger). The `reason` column carries the human-meaningful explanation when the transition has one (e.g., admin's rejection text from Phase 12's `reject_listing`); it is `NULL` for self-explanatory transitions like `draft → pending_review`. The same trigger fires for every status transition originating from any source — `submit_listing` (Phase 10), `approve_listing` / `reject_listing` (Phase 12), system-driven `expired` flips (Phase 13+ scheduled job, deferred), publisher-side `paused` toggles (Phase 13+ self-service), and any admin-direct UPDATE via Supabase MCP `execute_sql`. The history table is **append-only** by RLS — UPDATE and DELETE policies do not exist; historical rows are immutable. This mirrors Phase 9's `exchange_rates` append-only invariant.

**Why this priority**: P2 because the trigger is a foundational invariant that other phases rely on (Phase 12's approve/reject queue reads the history; Phase 20's admin dashboard could surface "average time-to-approval" by diff'ing pending→approved timestamps). It ships in Phase 10 but is consumed elsewhere.

Attempt `UPDATE public.listing_status_history SET previous_status='draft' WHERE id=<any>` — confirm 0 rows affected (append-only RLS). Attempt `DELETE FROM public.listing_status_history WHERE id=<any>` — confirm 0 rows affected.

**Acceptance Scenarios**:

1. **Given** any INSERT into `public.listings`, **When** the row commits, **Then** the trigger appends exactly one `listing_status_history` row with `previous_status=NULL` / `new_status=NEW.status` / `changed_by=auth.uid()` (or NULL for system context).
2. **Given** any UPDATE that changes `listings.status`, **When** the row commits, **Then** the trigger appends exactly one row with `previous_status=OLD.status` / `new_status=NEW.status` / `changed_by=auth.uid()`.
3. **Given** an UPDATE that does NOT change `listings.status` (e.g., re-saving a draft's title or description), **When** the row commits, **Then** the trigger does NOT append a history row.
4. **Given** the `listing_status_history` table, **When** any caller attempts UPDATE or DELETE on a historical row, **Then** the RLS policies reject the operation (0 rows affected) — the table is append-only.
5. **Given** the audit-log infrastructure (Phase 4's `log_audit()`), **When** a status transition fires, **Then** the trigger ALSO emits a `listing.<verb>` audit row via `log_audit()` (e.g., `listing.submitted`, `listing.approved`, `listing.rejected`) per FR-007. The `listing_status_history` row and the `audit_logs` row coexist — the former is the operational record (queryable cheaply by admins and publishers), the latter is the compliance trail (admin-only via `audit_logs.view`).

### User Story 7 — Validators for area, price, and phone (Priority: P2)

The implementation plan calls out three validators that live in `lib/core/validators/` and are consumed by the listing form: `AreaSizeValidator` (positive numeric, sane upper bound to catch typos like 999999), `PriceValidator` (positive numeric, up to `NUMERIC(14, 2)` per Assumption 5), and `PhoneValidator` (E.164 normalization with Syrian-prefix recognition — the same logic as Phase 5's phone-number value object, lifted into a reusable validator for the listing form's `phone` and `whatsapp` fields). Each validator returns a localized error message via the active `AppLocalizations` instance. Validation runs at the field-blur level (immediate feedback) and again at the step-transition level (block forward navigation if any step's fields fail). The Edge Function's server-side validation re-runs the same rules in PL/pgSQL or via the function's input contract; on conflict between client and server validation, the server is authoritative.

**Why this priority**: P2 because validation correctness is the difference between admin queue full of typos and admin queue full of reviewable listings. It is independently shippable from the form chrome itself.

**Independent Test**: Sign in as an approved publisher. Open the form, reach the details step. Enter `area_size = -5`; confirm a localized "area must be positive" error appears at field blur. Enter `area_size = 999999`; confirm a localized "area seems too large; please verify" warning appears. Enter `area_size = 180`; confirm no error. Reach the prices step. Enter `amount = 0`; confirm a localized "price must be positive" error. Enter `amount = 0.001`; confirm whatever sub-cent / sub-SYP rule applies (Q1 includes the decimals contract). Reach the visibility settings step. Enter `phone = '0991234567'`; confirm the validator auto-normalizes to `+963991234567` and accepts. Enter `phone = '123'`; confirm a localized "phone number is too short" error.

**Acceptance Scenarios**:

1. **Given** the form's details step renders, **When** the publisher enters a non-positive `area_size`, **Then** the `AreaSizeValidator` rejects with a localized error.
2. **Given** the form's prices step, **When** the publisher enters a non-positive `amount`, **Then** the `PriceValidator` rejects with a localized error.
3. **Given** the form's visibility step (which contains the `phone` and `whatsapp` fields per Assumption 4), **When** the publisher enters a Syrian local phone number without country code, **Then** the `PhoneValidator` auto-normalizes to E.164 form and accepts; the stored value is the normalized form.
4. **Given** any validator's output, **When** the locale is `ar`, **Then** the error string is the Arabic ARB key; when `en`, the English; when neither has an entry, the validator name is used as the fallback (per Phase 3 conventions).
5. **Given** the Edge Function `submit_listing`, **When** the client-side validation has been bypassed (e.g., a malicious caller posting JSON directly to the function), **Then** the function re-runs the same validation rules server-side and rejects on any violation with HTTP 400 + localized error code.

### Edge Cases

- **Publisher creates a draft, then has their `publisher_status` revoked while the draft is in progress**: The draft row already exists in `public.listings`. The publisher can no longer edit it (RLS denies UPDATE because the policy requires `publisher_status='approved'`). The draft sits orphaned in the table. Phase 10 does NOT auto-cascade-delete the draft; admins can clean up via a future settings page or via direct SQL. The publisher cannot resubmit. The orphaned draft does NOT appear on any public surface because its status is `draft`.
- **Approved publisher's draft has empty / null `governorate_id`**: The draft can be saved (in-progress saves don't enforce required-field validation). But `submit_listing` will reject the submit with a localized "location is required" error per Q1. The publisher returns to the form, fills the location step, re-submits.
- **Two concurrent `submit_listing` calls for the same draft**: The Edge Function (or RPC) wraps validation + status flip + history insert in a single transaction; the row-level lock on `public.listings` ensures only one call commits the transition. The second call sees the listing's status is no longer `draft` and returns success (idempotency) or a localized "already submitted" message — the plan-time decision picks one.
- **Publisher tries to submit a draft that has 0 `listing_prices` rows**: Per Q1, at least one `listing_prices` row with `is_primary=true` is required; submit is rejected with a localized error. The "no-price" affordance ("price on request") is NOT supported in Phase 10 v1 — a listing without a price cannot be approved. Forward-stated phases may revisit.
- **Multi-currency uniqueness conflict via direct SQL only**: Per Q3, Phase 10's UI surface emits exactly ONE `listing_prices` row per listing and provides no path to insert a second. Any duplicate `(listing_id, currency_code)` row attempt must therefore originate from direct admin SQL (a future-spec UI may also exercise this path once multi-row entry ships); the database `UNIQUE(listing_id, currency_code)` constraint (Phase 9 Q4 forward-stated) raises `23505 unique_violation` server-side, defense-in-depth. The `submit_listing` server-side validation re-confirms each Phase 10 listing has exactly one row and surfaces a structured error if a future-spec path or admin SQL inadvertently created a multi-row state for a listing whose status is still `draft` or `rejected`.
- **Publisher edits a `rejected` listing, fixes the reason, but submits with a different validation failure**: `submit_listing` rejects with the new validation errors; the listing's status remains `rejected` (it does NOT regress to `draft`). The rejection-reason rendering on `MyListingsPage` continues to show the original admin's rejection text (the rejection reason is captured in `listing_status_history`, not in the listing row itself).
- **System-driven status transitions (e.g., a scheduled job that flips approved listings to `expired` after `expires_at` passes)**: When such a transition fires, the trigger captures `changed_by=NULL` because there is no `auth.uid()` in the system context. Phase 10 ships the trigger; Phase 13+ owns the scheduler. Until the scheduler exists, no `expired` transitions occur — admins can manually expire via direct UPDATE.
- **Trigger-before-seed audit ordering**: Following Phase 8 / Phase 9's precedent (R-08 in Phase 9 research), the migration MUST attach the `listing_status_history` INSERT trigger AND any `log_audit` triggers on `public.listings` BEFORE any system-seeded listing rows are inserted. Phase 10 does NOT seed any sample listing rows (the seed inventory is empty); this invariant is reaffirmed defensively in case a future spec adds fixture data.
- **Anonymous SELECT during `pending_review`**: An anonymous client SELECTing a `pending_review` listing's row returns 0 rows. Only `status='approved'` listings (AND within the publish window — `published_at <= now() < expires_at`) are anonymously readable. The Phase 10 RLS policy on `public.listings` codifies this in advance of Phase 12's approval flip, so Phase 12 only needs to set `status='approved'` to make the listing public.
- **`listings.agency_id` column with no FK constraint in Phase 10**: The column is declared `agency_id UUID NULL` with NO FK constraint. Phase 19 will add the FK to `public.agencies(id)` (per IMPLEMENTATION_PLAN §Phase 19 deliverables). Phase 10 listings created by an `agency_admin` user MAY populate `agency_id`, but the value is unenforced at the DB level until Phase 19; the form UX in Phase 10 leaves the field hidden and always populates `NULL` (the "Publish under agency" switch from Phase 19's form extension is not in scope here).
- **Constitution III RLS on every child table**: Each of the five new tables (`listings`, `listing_details`, `listing_prices`, `listing_visibility`, `listing_status_history`) ships with RLS enabled and explicit policies. None opts out. The policies on child tables join through `listings` to derive the owning publisher; e.g., `listing_prices` SELECT is allowed when the parent listing is publicly approved (anonymous read) OR when `auth.uid() = parent.publisher_user_id` (owner read) OR when the caller has `listings.view_all` (admin read). Owner UPDATE on child tables is gated by both `auth.uid() = parent.publisher_user_id` AND `parent.status IN ('draft', 'rejected')` (only edit windows allow child mutations).

- **FR-005**: System MUST gate write access to `listings` and its child tables behind a composite check: (a) `auth.uid() = listings.publisher_user_id` for owner-side writes, AND (b) `publisher_user_id IN (SELECT user_id FROM public.profiles WHERE publisher_status='approved' AND account_status='approved')` so that revoked publishers cannot write. #### Submission RPC / Edge Function

- **FR-010**: System MUST provide a `submit_listing` server-side mutation, exposed either as an Edge Function (`supabase/functions/submit_listing/`) OR as a SECURITY DEFINER PL/pgSQL RPC (`public.submit_listing(listing_id uuid) RETURNS jsonb`). Plan-time decision per Assumption 7 (Phase 7 / Phase 9 carry-forward toward RPC). The function MUST: (a) authenticate the caller's JWT, (b) verify `auth.uid() = listings.publisher_user_id` AND the publisher's `profiles.publisher_status='approved'` AND `account_status='approved'`, (c) verify the listing's current status is `draft` or `rejected`, (d) re-run server-side validation of the Q1 Full required-field set per FR-010a, (e) atomically `UPDATE public.listings SET status='pending_review' WHERE id=<listing_id>` (the trigger from FR-004 captures the history row as a side-effect), (f) return HTTP 200 with the updated row's JSON. On any validation failure: HTTP 400 with a localized error code per FR-021 + a structured payload listing each failing field by name. On any permission failure: HTTP 403. On any database failure: HTTP 500.
- **FR-010a**: System MUST enforce the following Q1-resolved required-field set at `submit_listing` time. **Always required** (every `property_type`): `listings.title` (non-empty after trim), `listings.purpose`, `listings.property_type`, `listings.governorate_id`, `listings.city_id`, `listings.area_id`, `listings.address_text` (non-empty after trim), `listings.area_size` (positive, per FR-018 validator bounds), AND at least one `listing_prices` row with `is_primary=true` AND `amount > 0`, AND at least one of `listings.phone` OR `listings.whatsapp` (both validated by `PhoneValidator` per FR-018). **Conditionally required**: when `listings.property_type IN ('apartment', 'villa')` (residential types), BOTH `listings.rooms` AND `listings.bathrooms` are also required (non-null, non-negative SMALLINT). **Always optional**: `description`, `year_built`, `furnished`, `parking`, `floor`, `latitude`, `longitude` (per Q2), `hide_until`, `agency_id`, `expires_at`, `published_at`. `location_visibility` defaults to `approximate` if unset; `contact_name_visibility` defaults to `public` if unset — neither is treated as missing. The client-side form blocks the Submit button on the Review step until all required fields are filled; the server-side `submit_listing` re-runs the same check as the authoritative gate. The server's structured error payload returns the missing-field list under the key `missing_fields` (an array of dot-notated field paths like `["listings.city_id", "listings.area_size", "listings.rooms"]`) so the client can re-open the form at the earliest step containing a missing field.

### Key Entities *(include if feature involves data)*

- **Listing**: The canonical row representing one published (or to-be-published) real-estate asset. Carries the full v1 field inventory from IMPLEMENTATION_PLAN §6.2; owned by `publisher_user_id` (always set; optionally also `agency_id` once Phase 19 ships). Status drives visibility: `draft` and `pending_review` are private to owner+admins; `approved` becomes publicly readable; `rejected` returns to private with a rejection reason visible to the owner; `paused`/`sold`/`rented`/`expired` are post-approval states that remain visible to owner+admins but exit the public surface.
- **ListingDetails**: A 1:1 extension carrying the long-form `description` plus amenity / year-built / furnished / parking flags. Split from the parent `listings` table to keep the parent row small for list-view queries and the details row large for detail-view queries. Joined when needed; cascade-deleted with the parent.
- **ListingPrice**: One row per currency the publisher chose to expose. Each carries `currency_code` (FK to Phase 9 `currencies`), `amount` (positive numeric), and `is_primary` (exactly one per listing). Phase 9 forward-stated `UNIQUE(listing_id, currency_code)` constrains uniqueness; the partial unique index `WHERE is_primary=true` enforces the single-primary invariant. Rows are mutable while the parent listing is in `draft` / `rejected`; effectively frozen post-approval.
- **ListingVisibility**: A 1:1 envelope carrying the visibility knobs that Phase 15 (map) and Phase 13 (public surface) consume: `location_visibility` (`hidden | approximate | exact | admin_only`), `contact_visibility` (`public | admin_only`), and `hide_until` (deferred visibility). The same `location_visibility` value also appears on the parent `listings` row for query-locality; the two are kept in sync by Phase 10's form (the parent column is authoritative; the child row exists for the Phase 15 map view's narrow projection per IMPLEMENTATION_PLAN §Phase 15).
- **ListingStatusHistory**: An append-only log of every status transition the listing has gone through. Auto-written by the FR-004 trigger on every INSERT and every UPDATE of `status`. Carries `previous_status` (NULL for the initial draft insert), `new_status`, `changed_by` (`auth.uid()` or NULL for system context), `changed_at`, and `reason` (the admin's free-text rejection note in Phase 12; NULL for self-explanatory transitions).

## Assumptions

- **Phase 5 publisher-status gate semantics**: The `profiles.publisher_status` column exists from Phase 5; values are `pending` / `approved` / `rejected` / `suspended` / `deleted` per IMPLEMENTATION_PLAN §6.3. Phase 10 reads `publisher_status='approved'` to gate the form, in conjunction with `account_status='approved'` (both must be true). The gate is mirrored in RLS, the router guard, and the UX tile.
- **Forward-stated `agency_id` FK constraint**: Phase 10 declares `listings.agency_id UUID NULL` with NO foreign-key constraint. Phase 19's migration adds `ALTER TABLE public.listings ADD CONSTRAINT listings_agency_id_fkey FOREIGN KEY (agency_id) REFERENCES public.agencies(id) ON DELETE SET NULL`. Phase 10 listings populate `agency_id=NULL` always; the "Publish under agency" affordance ships in Phase 19's form-extension scope.
- **Media-step placeholder**: The form's sixth step (media) is a no-op UI banner in Phase 10. Phase 11 wires the actual `MediaPicker` widget + `listing_media` table + storage policies. Phase 10's form contract is "include the step in the navigation so users see the full path; the step's continue button is always enabled and proceeds to the Review step without writing any media row."
- **`submit_listing` implementation surface** *(plan-time deviation, Phase 7 / Phase 9 carry-forward)*: The IMPLEMENTATION_PLAN literal text says "Edge Function `submit_listing`", but the plan-time research file MAY select a SECURITY DEFINER PL/pgSQL RPC instead, mirroring the Phase 7 / Phase 9 R-06 decision. The functional contract (permission check, atomic status flip + history-insert side-effect, HTTP error mapping) is identical; the only difference is whether it lives under `supabase/functions/submit_listing/` (TypeScript) or as `public.submit_listing(uuid) RETURNS jsonb` (PL/pgSQL). The Flutter client adapter is symmetric across both implementations.
- **Listing decimals**: `listing_prices.amount NUMERIC(14, 2)` — 12 integer digits, 2 fractional digits — accommodates SYP-scale prices up to 999,999,999,999.99 (about 10^12) which covers any realistic real-estate price in the Syrian market. Display-time rounding follows the row's `currency_code.display_decimals` from Phase 9 (SYP=0, USD=2), but the stored amount precision is always 2 decimals at the schema level to avoid information loss on multi-currency listings.
- **No new automated tests — manual UI verification only**: Per `feedback_no_new_tests.md`, Phase 10 does NOT introduce new automated unit tests for the validators despite the IMPLEMENTATION_PLAN's reference to "Unit tests for validators." Instead, the validator golden cases are codified in `quickstart.md` as a manual-verification checklist. The schema-level invariants (FR-004 trigger, FR-007 append-only, FR-008 permission gating) are verified via direct-SQL probes through Supabase MCP `execute_sql`. The "Skip new tests until MVP" directive applies for the seventh time across Phases 5–10.
- **Trigger-before-seed audit ordering**: Phase 10 does NOT seed any sample listing rows. The IMPLEMENTATION_PLAN §Phase 10 verification list does not call for fixture data. The trigger-attach-before-seed invariant (Phase 8 R-08) is preserved defensively for any future spec that may add sample listings — triggers are attached at the end of the table-creation migration, before any rare seed `INSERT` would run.
- **Public-read-when-approved RLS shipped in Phase 10**: The public-read policy `USING (status='approved' AND (published_at IS NULL OR published_at <= now()) AND (expires_at IS NULL OR expires_at > now()))` is part of Phase 10's policy file. Phase 12's approval workflow only flips the listing's `status` to `approved`; no Phase 12 policy edit is needed. The forward-stated Phase 13 (public home), Phase 14 (search), and Phase 15 (map view) all consume this policy unchanged.
- **`listing_visibility` parent-column duplication**: The IMPLEMENTATION_PLAN §6.2 lists `location_visibility` on BOTH `listings` (for query-locality on map and search) AND `listing_visibility` (the 1:1 envelope). Phase 10 ships both columns; the form keeps them in sync via a single source of truth — the form writes to the parent's column, and a trigger maintains the child row. Forward-stated phases that read from the child row see the same value.
- **Phase 8 LocationPicker reuse**: The location step reuses Phase 8's `LocationPicker` widget unchanged. Phase 10 does NOT introduce a new cascading-dropdown widget under `lib/features/listing_form/`. If the LocationPicker's API needs minor extension (e.g., an `onChange` callback shape), the extension lives in `lib/features/locations/` not in `lib/features/listing_form/`.
- **Phase 9 MoneyFormatter reuse**: The prices step's inline amount preview uses Phase 9's `MoneyFormatter` unchanged. The formatter is called with the publisher's entered amount + the picked currency_code + the active locale; no rate parameter (per Phase 9 Q1).
- **Plan-override is bounded to Phase 10 only**: The Q1 / Q2 / Q3 resolutions of this spec apply ONLY to Phase 10. They do not preclude later phases from refining the field set (Phase 12 may add admin-side required-field-overrides per a future spec), from adding a map picker (Phase 15 will), or from adding more multi-currency UX (a future spec may extend).
- **Constitution XI (Android-First MVP)**: Every manual acceptance test runs on the Infinix Note 8 (Helio G80, 6 GB RAM, Android 10/11). No iOS / web / desktop target is in scope. The seven-step form is evaluated for one-handed reach and step-transition friction on a 6.78" portrait screen.

The plan-time research file will codify exact filenames (e.g., `20260518120001_create_listings.sql`).
- **`log_audit` reusability invariant**: Phase 10 attaches new audit triggers to `public.listings` using Phase 4's `log_audit()` function unchanged. The R-05 reusability invariant — `log_audit` unchanged — is preserved for a SEVENTH time across Phases 4/5/6/7/8/9/10.
