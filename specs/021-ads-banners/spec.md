# Feature Specification: Ads & Banners Admin Module

**Feature Branch**: `021-ads-banners`
**Created**: 2026-06-01
**Status**: Draft
**Input**: Phase 21 — Ads & banners admin module, from `docs/IMPLEMENTATION_PLAN.md` (§ "Phase 21 — Ads & banners admin module", plus the schema in §6.2, RLS posture in §6.4, storage in §6.5, permission catalog in §9.1, and audit triggers in §9.4)

> **Scope note**: Phase 21 introduces the **first-party banner-ads module** — the ability for staff who hold the `ads.manage` permission to author promotional banners, schedule when they run, choose where they appear and in what priority, point each at a destination (an external web link OR an in-app deep link), and have the app surface those banners to ordinary users in the right places at the right time, recording a click whenever a user taps one. It is the **first and only consumer** of the `ads.manage` permission (seeded onto `admin` + `super_admin` in Phase 6, unused until now) and the **first owner** of the three ads tables the plan reserved (`ads`, `ad_placements`, `ad_impressions`), the public-read `ads` storage bucket, and the `record_ad_event` SECURITY DEFINER RPC (the controlled click-recording write path — realized as an RPC mirroring Phase 16's `record_lead_event`, not a Deno Edge Function; see plan research R-167). Phase 21 also **wires the Ads section that Phase 20 left as a disabled "coming soon" tile** on the admin dashboard (`dashboardTileAds`, gated by `PermissionKeys.adsManage`, currently `DashboardSectionState.comingSoon` with no route) — flipping it to a navigable tile that routes to the new ads admin surface behind an `ads.manage` route guard (`requireAdsManageRedirect`, mirroring the existing single-key `requireAuditLogsViewRedirect`), exactly as Phase 20 designed for (the later phase "only wires the destination route without restructuring the dashboard"). Phase 21 ships exactly: (a) an **admin ads surface** under `lib/features/ads/admin/` — create / edit / activate-deactivate / soft-delete (archive) a banner ad, upload its image to the `ads` bucket, optionally add a bilingual (ar/en) **caption/CTA** (image-only is allowed), set its schedule (start / end window), assign it to one or more **placements** with a **priority**, and choose its **link target**; (b) a **link-target picker** so each ad points at EITHER an external web URL OR an in-app deep link to a listing / a filtered search / a category / an agency profile (the user-resolved "both" decision — see Clarifications); (c) a placement-aware **`AdSlot` widget** under `lib/features/ads/widgets/` rendered on the public browsing surfaces — **home** (`home_top_banner`, `home_middle_banner`), **search results** (`search_results_banner`), and **listing details** (`listing_details_banner`) — that shows only the **eligible** ads for that placement (active AND inside their schedule window AND assigned to the placement), with the eligibility filter enforced **server-side** so non-eligible ads never reach the client; (d) **rotating-carousel** rendering when more than one eligible ad shares a placement, ordered by the placement-assignment **priority** (the user-resolved "carousel by priority" decision — see Clarifications); (e) **tap-through** behavior — tapping a banner opens its link target (launches the external URL via the existing launcher, or navigates the in-app deep link via the existing `go_router` surface) AND records a **click** event through the controlled `record_ad_event` write path; (f) **clicks-only tracking** — this phase logs taps ONLY and does NOT log impression / view events (the user-resolved "clicks only" decision — see Clarifications), which narrows the reserved `ad_impressions` table and the `record_ad_event` function to the `click` kind in v1; (g) **automatic scheduling** — an ad outside its window (not yet started, or already ended) or toggled inactive disappears from every placement with no further admin action, because the server-side eligibility filter is evaluated against the current time on every read; (h) **audit logging** — ad creation and deletion write `audit_logs` rows (Principle VII, plan §9.4), reusing the Phase 4 `log_audit()` infrastructure; (i) **checks at both ends** — every authoring action is gated by `ads.manage` at BOTH the UI (the Phase 6 `PermissionChecker` hides the surface) AND the backend (RLS on the ads tables / the `ads` bucket write policy / the write RPCs' server-side `ads.manage` re-check), public ad reads are restricted server-side to the eligible window, and `ad_impressions` is admin-read-only and written ONLY by the `record_ad_event` RPC; (j) the **localization layer** gains the ads strings (admin form labels, placement names, link-type picker, schedule pickers, status chips, list/empty/error states, and any AdSlot affordance) flowing through `AppLocalizations` with `ar` + `en` entries per Phase 3, rendering correctly in all four (light / dark) × (Arabic RTL / English LTR) combinations using Phase 2 design tokens. Phase 21 honors Principle III (RLS on all three new tables + the storage bucket; the moderation/serving path gated server-side; no client write to `ad_impressions`), Principle VII (the `ads.manage` permission gates the surface data-drivenly — never a hardcoded role branch — and ad creation / deletion are audit-logged), Principle V (all new strings localized `ar` / `en`), Principle VI (themed via Phase 2 tokens, four-combination correct), Principle XI (Android-only; no new non-Android plugin), and Principle I (this spec precedes any implementation). Phase 21 does **NOT** introduce any third-party ad network (Google AdMob or otherwise — first-party banners only; per ADR-0001, external-network API keys would be Vault secrets read by an Edge Function only when an explicitly-approved later spec opens them); does **NOT** add a paid / self-serve advertiser flow (ads are admin-authored only); does **NOT** introduce a new pubspec package, Postgres extension, or Android manifest change (external launch, deep links, image upload, image display, and carousel all reuse already-present infrastructure); does **NOT** log impressions / view-through metrics (clicks only); does **NOT** change the `ads.manage` seed, the §9.1 permission catalog, or any existing business table; and does **NOT** build a category landing surface (the `category_banner` placement is defined in the schema but has no host page wired in this phase — see Assumptions).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — An admin authors, schedules, places, and manages a banner ad (Priority: P1)

A staff member who holds the `ads.manage` permission opens the Ads section from the admin dashboard. They create a new banner: they give it an internal title, upload a banner image, choose where it should appear (one or more placements) and in what priority within each placement, set its schedule (when it starts and when it ends), choose its destination (an external web URL or an in-app deep link), and mark it active. The ad is saved and appears in the admin's list of ads with a clear status (active / scheduled / expired / inactive) and its placements. The admin can later edit any field, toggle it active or inactive, or delete it. Creating and deleting an ad is recorded in the audit log.

**Why this priority**: P1 because the authoring surface IS the module's foundation — the IMPLEMENTATION_PLAN's Phase 21 goal is "Admins create banner ads with placement, schedule, and link target," and its frontend deliverable centers on `lib/features/ads/admin/` (CRUD, placement mapping, schedule pickers). Nothing can be served to users (US2) before an admin can author it. This story is the minimum viable slice: a staff member can manage the banner inventory end-to-end.

**Independent Test**: Sign in as an admin holding `ads.manage`; open the admin dashboard and confirm the Ads tile is now navigable (no longer "coming soon"); create a banner with a title, an uploaded image, a placement + priority, a schedule, a link target, and active = true; confirm it persists and appears in the ads list with the correct status and placement; edit the title and toggle it inactive; confirm the changes persist; delete it; confirm an `audit_logs` row was written for the creation and for the deletion. Sign in as a user WITHOUT `ads.manage`; confirm the Ads tile is absent and the ads admin route is not reachable.

**Acceptance Scenarios**:

1. **Given** a signed-in admin holding `ads.manage`, **When** they open the admin dashboard, **Then** the Ads tile is present and navigable (the Phase 20 "coming soon" state is replaced by a route to the ads admin surface), and tapping it opens the ads admin surface.
2. **Given** the ads admin surface, **When** the admin creates a banner with a title, an uploaded image, at least one placement + priority, a schedule (start / end), and a link target, and saves, **Then** the ad is persisted and appears in the ads list with a status reflecting its schedule/active state and the placement(s) it is assigned to.
3. **Given** an existing ad, **When** the admin edits any field (title, image, placement, priority, schedule, link target) and saves, **Then** the changes persist and are reflected in the ads list and (where eligible) in the live placement.
4. **Given** an existing ad, **When** the admin toggles it inactive, **Then** it is immediately ineligible for serving (it stops appearing in its placements) without being deleted, and the admin can re-activate it later.
5. **Given** an existing ad, **When** the admin deletes it, **Then** the ad is **archived** (soft-deleted) — hidden from every placement and from the default ads list, while its row and recorded click history are **retained** — and an `audit_logs` row records the deletion.
6. **Given** an ad is created or deleted, **When** the action completes, **Then** an `audit_logs` row is written (actor, action, target) reusing the existing audit infrastructure (Principle VII, plan §9.4).
7. **Given** a signed-in user WITHOUT `ads.manage`, **When** they view the admin dashboard or attempt the ads admin route, **Then** the Ads tile is absent and the route is denied at the guard (redirected) — the authoring surface is unreachable.

### User Story 2 — Users see the right ads, in the right place, at the right time (Priority: P1)

An ordinary app user — anonymous or signed-in — browses the home screen, runs a search, or opens a listing's details. Where the layout has an ad placement, they see the banner(s) an admin scheduled for that spot: only banners that are currently active and inside their scheduled window appear, and only in the placement they were assigned to. When more than one eligible banner is assigned to the same placement, the placement shows them as a rotating carousel ordered by the admin-set priority. When a banner's end date passes (or an admin deactivates it), it stops appearing automatically — no admin action is needed to take it down. When a placement has no eligible banner, the slot simply shows nothing and the surrounding layout is unaffected.

**Why this priority**: P1 because serving banners to users is the whole point of the module and is the subject of the plan's first two acceptance criteria ("Active ad in `home_top_banner` appears at the top of home for non-admin users" and "Schedule end-date hides the ad automatically"). The plan's `AdSlot` widget (home, search results, listing details) and `ad_placements.priority` (the carousel order) are exactly this story. It builds on the inventory authored in US1.

**Independent Test**: With an active, in-window banner assigned to `home_top_banner` (from US1), open the app as an ordinary user and confirm the banner appears at the top of home. Assign a second active in-window banner to the same placement with a different priority; confirm both rotate in a carousel ordered by priority. Set the first banner's end date to the past (or toggle it inactive); refresh home and confirm it no longer appears. Create a banner scheduled to start in the future; confirm it does NOT appear until its start time. Open a placement with no eligible banner; confirm the slot renders nothing and the layout is not disrupted. Repeat the "appears" check on the search-results and listing-details placements.

**Acceptance Scenarios**:

1. **Given** an active banner whose schedule window includes now, assigned to `home_top_banner`, **When** an ordinary user opens home, **Then** the banner appears in the home top placement.
2. **Given** two or more active in-window banners assigned to the same placement, **When** the placement renders, **Then** the banners are shown as a rotating carousel ordered by their placement-assignment priority, auto-advancing on a timer and manually swipeable (looping).
3. **Given** a banner whose end date has passed, OR a banner toggled inactive, **When** the placement renders (on the next read / refresh), **Then** the banner no longer appears — automatically, with no admin takedown action.
4. **Given** a banner whose start date is in the future, **When** the placement renders, **Then** the banner does NOT appear until its start time is reached.
5. **Given** a placement with no eligible banner, **When** the surface renders, **Then** the ad slot shows nothing (it collapses) and does not introduce an empty box, placeholder, or layout reflow.
6. **Given** the search-results and listing-details surfaces, **When** they render with an eligible banner for `search_results_banner` / `listing_details_banner` respectively, **Then** the banner appears in that placement following the same eligibility + carousel rules as home.

### User Story 3 — Tapping a banner opens its destination and records a click (Priority: P2)

A user sees a banner and taps it. If the banner points at an external web URL, the app opens that URL in the appropriate handler; if it points at an in-app destination (a specific listing, a filtered search, a category, or an agency profile), the app navigates there in-app. Either way, the tap is recorded as a click so the team can later see how many times each banner was tapped. Recording the click never gets in the way of opening the destination: if the click can't be recorded, the destination still opens.

**Why this priority**: P2 because tap-through + click tracking is the engagement layer the plan calls for ("Tap on banner records click + opens link"; verification counts `ad_impressions ... kind = 'click'`) and the user-resolved decisions pin (link target = both external URL and in-app deep link; tracking = clicks only). It is essential to the module's value but sits on top of the P1 authoring + serving slices — banners can be shown (US2) before taps are wired.

**Independent Test**: Create a banner with an external URL target and confirm tapping it opens that URL; create a banner with an in-app deep-link target (e.g., a specific listing) and confirm tapping it navigates to that listing in-app; for each, confirm a `click` event is recorded for the correct ad and placement (verify via the admin/data path). Simulate a click-recording failure (e.g., offline) and confirm the destination still opens (recording is best-effort, non-blocking). Confirm NO impression/view events are recorded when a banner is merely displayed (clicks only).

**Acceptance Scenarios**:

1. **Given** a banner whose link target is an external web URL, **When** the user taps it, **Then** the app opens that URL using the existing external-launch mechanism.
2. **Given** a banner whose link target is an in-app deep link (listing / filtered search / category / agency profile), **When** the user taps it, **Then** the app navigates to that in-app destination.
3. **Given** any banner tap, **When** the user taps, **Then** a `click` event is recorded through the controlled write path (the `record_ad_event` SECURITY DEFINER RPC), capturing the ad, the placement, and the user (when signed in; anonymous otherwise).
4. **Given** click recording fails (network/server error), **When** the user taps a banner, **Then** the destination still opens — recording is best-effort and MUST NOT block, delay, or cancel the navigation/launch.
5. **Given** a banner is displayed but not tapped, **When** it renders, **Then** NO impression/view event is recorded — this phase tracks clicks only (the `impression` kind is not produced in v1).

### User Story 4 — Ad management and serving are enforced at the data layer, not just hidden in the UI (Priority: P2)

The product MUST guarantee that the `ads.manage` gate on authoring is backed by a real backend check, and that the public ad feed never leaks ads users shouldn't see. A user without `ads.manage` cannot create, edit, or delete an ad even by calling the backend directly; the public read path returns only eligible (active, in-window) ads and never exposes drafts, inactive, expired, or admin-only fields; banner images can be written to the `ads` bucket only by an `ads.manage` holder; and the click-event table can be written only through the controlled function, never directly by a client. All gating is data-driven — changing which permissions a role carries re-shapes who can manage ads on the next session refresh, with no hardcoded role branch.

**Why this priority**: P2 because Constitution Principle III ("checks at both ends") and Principle VII (data-driven permissions, no hardcoded role checks) make a UI-only gate insufficient, and the §6.4 RLS matrix mandates this exact posture (`ads`/`ad_placements`: public read of the active window, `ads.manage` write; `ad_impressions`: admin read, system write). It is a hard correctness/security requirement layered over the P1 authoring + serving behavior.

**Independent Test**: From a session WITHOUT `ads.manage`, attempt to insert/update/delete an `ads` row and to write to the `ads` bucket at the wire level; confirm each is denied. From an anonymous session, read the public ad feed and confirm it returns only active in-window ads (no drafts/inactive/expired, no admin-only fields). Attempt to insert an `ad_impressions` row directly from a client session; confirm it is denied (writes go only through the `record_ad_event` RPC). Grant `ads.manage` to a role, refresh the session, and confirm that user can now reach the ads admin surface — with no code change.

**Acceptance Scenarios**:

1. **Given** a session lacking `ads.manage`, **When** it attempts to create, edit, or delete an ad / placement at the wire level, **Then** the write is denied by RLS — the UI hide is backed by a backend check ("checks at both ends").
2. **Given** any client (anonymous or authenticated), **When** it reads ads at the wire level, **Then** only active, in-window ads (and their public placement/serving fields) are returned — drafts, inactive, expired ads, and any admin-only field are NOT exposed.
3. **Given** the `ads` storage bucket, **When** a non-`ads.manage` session attempts to upload/replace/delete a banner image, **Then** the write is denied; banner imagery is publicly readable but write-gated to `ads.manage`.
4. **Given** the `ad_impressions` table, **When** a client attempts to write a row directly, **Then** it is denied — click events are written ONLY through the `record_ad_event` SECURITY DEFINER RPC, and the table is admin-read-only.
5. **Given** all ad gating, **When** evaluated, **Then** it is data-driven via the `ads.manage` permission key (no hardcoded role branch); granting/revoking `ads.manage` on a role re-shapes ads-management access on the next permission-state refresh with no code change (Principle VII).

### User Story 5 — The ads admin surface and banners are fully localized and themed in every combination (Priority: P3)

Every admin managing ads — and every user seeing them — gets a correct, readable experience whether the app is in Arabic (RTL) or English (LTR), in light or dark theme: localized form labels, placement names, the link-type picker, schedule pickers, status chips, list/empty/error states, and any banner affordance, with direction-aware layout and design-token styling throughout.

**Why this priority**: P3 because localization and theming are cross-cutting quality gates the plan calls out for every phase (Principles V and VI); they refine the experience delivered by the P1/P2 stories rather than being a standalone capability.

**Independent Test**: Open the ads admin surface and a host surface with an active banner and cycle the four combinations — (light, ar), (dark, ar), (light, en), (dark, en) — on the reference Infinix Note 8 and a 412 dp emulator profile; confirm every string is localized (no raw literals), forms/pickers/list/carousel lay out correctly RTL and LTR, and colors/typography/spacing come from Phase 2 tokens (no clipped text, no mirrored-wrong icons, no inline hex).

**Acceptance Scenarios**:

1. **Given** the app locale is Arabic, **When** the ads admin surface and a banner render, **Then** all strings appear in Arabic and the layout is RTL-correct (form fields, pickers, status chips, the carousel, and any directional icons mirror appropriately).
2. **Given** the app locale is English, **When** the same surfaces render, **Then** all strings appear in English and the layout is LTR-correct.
3. **Given** light and dark themes, **When** the surfaces render in each, **Then** all colors, typography, spacing, and elevation come from the Phase 2 design tokens with no inline hex / raw font size / ad-hoc padding, in both themes.
4. **Given** any ads state (form, list, empty inventory, load/save error, a placement with no eligible ad, a single-ad slot, a multi-ad carousel), **When** it renders, **Then** every user-visible string is sourced from `AppLocalizations` with both `ar` and `en` entries.

### Edge Cases

- **A placement has no eligible ad**: the `AdSlot` renders nothing and collapses — no empty frame, no placeholder, no layout reflow on the host surface (home/search/details look identical to today when no ad is scheduled).
- **A placement has exactly one eligible ad**: the slot shows that single banner statically (no carousel rotation, no rotation controls / indicators) — carousel behavior only engages with two or more eligible ads.
- **Many eligible ads share one placement**: all eligible ads rotate in the carousel ordered by priority; ties on priority resolve by a deterministic secondary order (e.g., most-recently-created) so rotation is stable and not random.
- **An ad's window opens/closes while the surface is on screen**: eligibility is evaluated server-side at read time, so an ad that expires mid-session disappears on the next read/refresh; the phase does not require live mid-screen removal (consistent with the polling/refresh posture of the rest of v1).
- **Open-ended schedule**: an ad may have no end date (runs until deactivated) and/or no start date (eligible immediately); the eligibility rule treats a missing bound as "unbounded on that side."
- **Start date after end date**: the admin form MUST reject a schedule whose start is not before its end (a validation error), so an ad can never be saved with an impossible window.
- **An ad with no placement assignment**: it is saved but never served (it appears in no placement); the admin list MUST make this state legible (e.g., "no placement") so it isn't mistaken for a bug.
- **A deep-link target that no longer resolves** (e.g., the linked listing was deleted or is no longer public): tapping it MUST fail gracefully (a localized "content unavailable" message or a safe fallback) rather than crashing or opening a broken screen; the click is still recorded.
- **An external URL that fails to open** (no handler / malformed): the app MUST fail gracefully with a localized message rather than crashing; the admin form SHOULD validate the URL shape on save.
- **An ad is deleted while a user is mid-tap**: the destination open is best-effort; a deleted/now-ineligible ad MUST NOT crash the client, and the public feed converges to exclude it on the next read.
- **The `category_banner` placement**: it is defined in the schema (per §6.2) but has no host surface wired in this phase (no category landing page exists yet); admins MAY still assign ads to it, but those ads will not render until a future phase wires the host. This is recorded in Assumptions per Principle XII; the admin UI SHOULD signal that the placement is not yet live, or omit it from the picker, to avoid silently-invisible assignments.
- **Click recording failure**: recording is best-effort and non-blocking — a failed `record_ad_event` call MUST NOT prevent, delay, or cancel opening the destination.
- **Admins viewing the app**: ads render on the public browsing surfaces for whoever is viewing them; an admin browsing home sees the same eligible banners a regular user would (the plan's "for non-admin users" wording denotes the verification audience — confirming ads are public-facing — not a rule hiding ads from admins). Recorded in Assumptions.
- **Very large ad inventory**: the public serving read MUST be bounded (filtered to the eligible set, scoped per placement) — the client MUST NOT fetch the entire ads table to filter client-side.
- **Permission changes mid-session**: if an admin's role loses `ads.manage`, the Ads tile and admin surface become unreachable on the next permission-state refresh (per the Phase 6 permission-cache model); no hardcoded role branch caches stale access.

## Requirements *(mandatory)*

### Functional Requirements

#### Ad authoring & management (admin CRUD)

- **FR-001**: A user holding `ads.manage` MUST be able to create a banner ad with: an internal title/label, a banner image, a link target, a schedule (start and/or end), an active flag, and one or more placement assignments — each placement assignment carrying a priority that orders the ad within that placement.
- **FR-002**: The banner image MUST be uploaded to the public-read `ads` storage bucket and displayed from there; image selection/upload MUST reuse the project's existing image-handling discipline (pick, downscale/compress to control storage cost, display via the existing cached image loader) — no new image dependency is introduced. Each ad MAY ALSO carry an **OPTIONAL caption/call-to-action text** shown with the image; the admin chooses per ad to publish **image-only OR image + caption**. When a caption is used it MUST be authored by the admin in **BOTH Arabic and English**, and the `AdSlot` MUST render the caption matching the viewer's active locale (this is admin-authored bilingual content — like a listing title — distinct from the app's `AppLocalizations` UI strings in FR-023).
- **FR-003**: Each ad MUST carry exactly one link target, chosen by the admin via a link-type picker as EITHER (a) an external web URL OR (b) an in-app deep link to one of: a specific listing, a filtered search, a category, or an agency profile. (User-resolved "both" decision — see Clarifications.)
- **FR-004**: The admin MUST be able to assign an ad to one or more of the defined placements — **`home_top_banner`**, **`home_middle_banner`**, **`search_results_banner`**, **`listing_details_banner`**, **`category_banner`** — and set a **priority** for the ad within each placement (priority orders the carousel in US2/FR-010).
- **FR-005**: Each ad MUST carry a schedule (a start and/or end timestamp) and an active flag; together these determine the ad's eligibility for serving (FR-009). The admin form MUST reject a schedule whose start is not strictly before its end.
- **FR-006**: A user holding `ads.manage` MUST be able to edit any field of an existing ad, toggle it active/inactive, and **delete (soft-delete / archive)** it; and MUST be able to view a list of all ads showing each ad's derived status (active / scheduled / expired / inactive / **archived**) and its assigned placement(s). Deletion MUST be a **soft-delete**: the archived ad is hidden from every placement and excluded from the default ads list, but its row and recorded click history are **retained** (historical click counts survive). The admin surface MUST allow viewing archived ads distinctly from active inventory (e.g., an archived filter/state).
- **FR-007**: Ad **creation** and **deletion** MUST each write an `audit_logs` row (actor, action, target type/id) reusing the Phase 4 `log_audit()` infrastructure (Principle VII, plan §9.4). (Activation/deactivation and schedule edits SHOULD also be audited; create + delete are the minimum mandated by the plan — see Assumptions.)
- **FR-008**: The ads admin surface MUST be reachable from the Phase 20 admin dashboard by replacing the existing disabled "coming soon" Ads tile (`dashboardTileAds`, gated by `PermissionKeys.adsManage`) with a **navigable** tile routing to the ads admin surface — without restructuring the dashboard. The `/admin/ads*` route(s) MUST be guarded by an `ads.manage` redirect (`requireAdsManageRedirect`, mirroring the single-key `requireAuditLogsViewRedirect` — a one-line `PermissionChecker.has('ads.manage')` check, since `ads.manage` is a single key, not the multi-key `.any()` form used by `requireAgenciesManageRedirect`), and a denied caller MUST be redirected (consistent with the existing `/admin?denied=<section>` behavior).

#### Ad serving (public read + carousel)

- **FR-009**: The app MUST render a placement-aware `AdSlot` on the public browsing surfaces — **home** (`home_top_banner` at the top, and `home_middle_banner` as a **single mid-feed slot inserted once after the first page/batch of listings** — not repeated as the user scrolls), **search results** (`search_results_banner`), and **listing details** (`listing_details_banner`) — showing only ads that are **eligible** for that placement: `active = true` AND the current time is within the ad's schedule window AND the ad is assigned to that placement.
- **FR-010**: When two or more eligible ads share a placement, the `AdSlot` MUST present them as a **rotating carousel ordered by the placement-assignment priority** — the carousel MUST **auto-advance on a timed interval AND be manually swipeable, looping** (a lightweight client-side UI timer, NOT a network/Realtime subscription, so it respects the home performance posture); with exactly one eligible ad it MUST render that ad statically (no rotation UI and no timer); priority ties MUST resolve by a deterministic secondary order so rotation is stable. (User-resolved "carousel by priority" + "auto-advance + swipe" decisions — see Clarifications.)
- **FR-011**: Eligibility (active + in-window + placement match) MUST be enforced **server-side** so that ineligible ads (draft/inactive/expired/not-yet-started/**archived**/other placement) and any admin-only field NEVER reach the client. An ad that leaves its window, is deactivated, or is archived MUST disappear from its placement automatically on the next read/refresh, with no admin takedown action.
- **FR-012**: When a placement has no eligible ad, the `AdSlot` MUST render nothing and collapse — no empty frame, placeholder, or layout reflow on the host surface (the surface MUST look identical to a no-ad-scheduled state).
- **FR-013**: The public serving read MUST be bounded and scoped per placement — the client MUST NOT fetch the full ads table to filter client-side; serving MUST remain bounded as the ad inventory grows.
- **FR-014**: The **`category_banner`** placement is defined in the schema but has no host surface wired in this phase; `AdSlot`s are rendered only on home, search results, and listing details. The admin placement picker MUST make this explicit (signal "not yet live" or omit the option) so an assignment to `category_banner` is not silently invisible. (Recorded in Assumptions.)

#### Engagement (tap-through + click tracking)

- **FR-015**: Tapping a banner MUST open its link target — launch the external web URL via the project's existing external-launch mechanism, or navigate the in-app deep link (listing / filtered search / category / agency profile) via the existing in-app routing surface.
- **FR-016**: Each banner tap MUST record a **click** event through the controlled write path (the `record_ad_event` SECURITY DEFINER RPC — mirroring Phase 16's `record_lead_event`, not a Deno Edge Function; see research R-167), capturing the ad, the placement, and the user identity when signed in (anonymous/null otherwise). This phase records **clicks only** — it MUST NOT log impression/view events; the `impression` kind is not produced in v1. (User-resolved "clicks only" decision — see Clarifications.)
- **FR-017**: Click recording MUST be best-effort and non-blocking — a failed event write MUST NOT prevent, delay, or cancel opening the link target.
- **FR-018**: A link target that no longer resolves (deleted/non-public listing, broken external URL, unavailable handler) MUST fail gracefully with a localized message or safe fallback — it MUST NOT crash the client; the click MAY still be recorded.

#### Security & permission enforcement (checks at both ends)

- **FR-019**: All ad authoring (create / edit / delete / activate-deactivate / placement / schedule / image upload) MUST be gated by `ads.manage` at BOTH the UI (the Phase 6 `PermissionChecker` hides the surface and the dashboard tile) AND the backend (RLS on `ads` + `ad_placements`, the `ads` bucket write policy, and the write RPCs' server-side `ads.manage` re-check), so a non-holder cannot mutate ads even at the wire level (Principle III).
- **FR-020**: Public read of ads MUST be restricted **server-side** to the eligible (active, in-window) set, exposing only the fields needed to render and tap a banner (image, optional locale-matched caption, link target, placement, priority) — drafts, inactive, expired, archived ads, and any admin-only field MUST NOT be exposed to clients (mirrors the §6.4 "public read of the active window" posture).
- **FR-021**: The `ads` storage bucket MUST be **public-read** (so banner images load for everyone) but **write-gated to `ads.manage`**; the `ad_impressions` table MUST be **admin-read-only** and written ONLY by the `record_ad_event` SECURITY DEFINER RPC — clients MUST NOT be able to write `ad_impressions` directly.
- **FR-022**: All ad gating MUST be **data-driven** via the `ads.manage` permission key — the feature MUST NOT contain any hardcoded role branch (e.g., `if role == 'admin'`). Granting or revoking `ads.manage` on a role MUST re-shape ads-management access on the next permission-state refresh (per Phase 6), with no code change (Principle VII).

#### Localization, theming & dependency constraints

- **FR-023**: Every user-visible string introduced by Phase 21 — the ads admin form labels, placement names, the link-type picker, the schedule pickers, status chips, the ads list and its empty/error states, and any `AdSlot` affordance/fallback message — MUST flow through `AppLocalizations` with both `ar` and `en` entries (Principle V). (An ad's optional **caption/CTA** per FR-002 is the exception: it is admin-authored bilingual *content* entered in ar + en and shown per the viewer's locale — NOT an `AppLocalizations` key; this requirement governs the surrounding UI chrome, and the form MUST capture both the ar and en caption when a caption is used.)
- **FR-024**: The ads admin surface and the `AdSlot` (single banner, carousel, empty/collapsed, and error/fallback states) MUST render correctly in all four combinations of (light / dark theme) × (Arabic RTL / English LTR), using logical/direction-aware insets and Phase 2 design tokens — no inline hex literals, no raw font sizes, no ad-hoc paddings (Principle VI).
- **FR-025**: The PR MUST NOT add any new third-party dependency, Postgres extension, or Android manifest change — banner rendering, the carousel, external-URL launch, in-app deep-link navigation, and image pick/compress/display all reuse infrastructure already present in the app. The new backend surface is exactly the plan's set: the three ads tables, the `ads` storage bucket, the `record_ad_event` RPC (plus the admin write RPCs), and their policies/audit triggers.
- **FR-026**: Phase 21 MUST NOT introduce any third-party ad network (e.g., Google AdMob) or any external-network API key, MUST NOT add a paid/self-serve advertiser flow, and MUST NOT alter the `ads.manage` seed, the §9.1 permission catalog, or any existing business-data table. First-party admin-authored banners only.

### Key Entities

- **Ad (banner)**: A promotional banner authored by an `ads.manage` holder. Attributes: internal title/label, banner image (in the `ads` bucket), an OPTIONAL admin-authored bilingual (ar/en) caption/CTA, link target (external URL or in-app deep link), schedule (start and/or end), active flag, archived/deleted marker, creator, timestamps. Its derived status (active / scheduled / expired / inactive / archived) is computed from the schedule + active flag + archived marker relative to now. Deletion is a **soft-delete (archive)** that retains the row and its click history. Corresponds to the plan's `ads` table.
- **Placement Assignment**: The mapping of one ad to one placement, with a priority that orders the ad within that placement's carousel. An ad may be assigned to several placements (each with its own priority); a placement may hold several ads. Corresponds to the plan's `ad_placements` table. Defined placements: `home_top_banner`, `home_middle_banner`, `search_results_banner`, `listing_details_banner`, `category_banner`.
- **Link Target**: The destination a banner tap opens — exactly one per ad, of type external-URL OR in-app-deep-link (listing / filtered search / category / agency profile). Drives both the tap-through navigation and the link-type picker in the admin form.
- **Ad Slot**: The placement-aware UI region on a host surface (home top/mid, search results, listing details) that resolves the eligible ad(s) for its placement and renders a single static banner, a rotating priority-ordered carousel, or nothing (collapsed).
- **Click Event**: A record of a user tapping a banner — ad, placement, optional user, time. Written only by the `record_ad_event` SECURITY DEFINER RPC; admin-read-only. Corresponds to the plan's `ad_impressions` table, narrowed in this phase to the `click` kind (no impressions). Click rows are **retained when the parent ad is archived/soft-deleted**, so historical counts survive.
- **Ads Admin Surface**: The `ads.manage`-gated screens for authoring and managing the ad inventory, reached from the Phase 20 admin dashboard's (now navigable) Ads tile.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An `ads.manage` holder can create a banner — title, uploaded image, ≥ 1 placement + priority, schedule, link target, active — and see it persisted with the correct derived status and placement(s), in under 3 minutes on the reference Infinix Note 8; a user without `ads.manage` sees no Ads tile and cannot reach the ads admin route (verified from a non-admin session, including at the wire level).
- **SC-002**: An active, in-window banner assigned to `home_top_banner` appears at the top of home for an ordinary user within 2 seconds of the home surface loading — verified on the reference Infinix Note 8; the same holds for the search-results and listing-details placements.
- **SC-003**: When ≥ 2 eligible banners share a placement, they rotate in a carousel ordered by priority (highest-priority first) — auto-advancing on a timer and also manually swipeable (looping) — and a single eligible banner renders statically (no rotation/timer) — verified by seeding two banners with distinct priorities and observing the order + auto-advance + swipe, then deactivating one and observing the static render.
- **SC-004**: A banner whose end date has passed (or that is toggled inactive) disappears from its placement on the next refresh with NO admin takedown action, and a banner scheduled to start in the future does not appear until its start — both verified on-device against seeded schedules.
- **SC-005**: Tapping a banner opens its destination — an external URL launches in the appropriate handler; an in-app deep link navigates to the listing/search/category/agency in-app — verified for one ad of each link type.
- **SC-006**: Each banner tap records exactly one `click` event for the correct ad + placement (verified via `SELECT COUNT(*) FROM ad_impressions WHERE ad_id = '…' AND kind = 'click'` matching the number of taps), and NO impression/view rows are written when a banner is merely displayed (clicks only).
- **SC-007**: Click recording is non-blocking — with click recording forced to fail (e.g., offline), tapping a banner still opens its destination — verified on-device.
- **SC-008**: From a session lacking `ads.manage`, a direct wire-level attempt to insert/update/delete an `ads`/`ad_placements` row, to write the `ads` bucket, or to insert an `ad_impressions` row is DENIED; and an anonymous wire-level read of ads returns only active in-window ads (no drafts/inactive/expired, no admin-only fields) — all four checks pass.
- **SC-009**: A placement with no eligible ad renders nothing and causes no layout change on its host surface — verified by comparing the surface with and without an eligible ad (no empty box, no reflow).
- **SC-010**: The ads admin surface and the `AdSlot` (single, carousel, empty, error/fallback states) render correctly in all four (light/dark) × (Arabic RTL / English LTR) combinations on the reference Infinix Note 8 (≈480 dp) and a 412 dp emulator profile — all strings localized, layout direction-correct, styling from Phase 2 tokens.
- **SC-011**: Ad creation and deletion each write an `audit_logs` row — verified by `SELECT * FROM audit_logs WHERE target_type = 'ads' ORDER BY created_at DESC` showing the `ad.created` and `ad.deleted` actions with the acting admin (`target_type` is the table name `ads` via `log_audit`'s `TG_TABLE_NAME`).
- **SC-012**: Granting `ads.manage` to a previously-unprivileged role and refreshing the session makes the Ads tile + admin surface reachable for that user with NO code change; revoking it makes them unreachable on the next refresh (Principle VII) — verified by toggling the permission on a test role.
- **SC-013**: A repository-wide check confirms Phase 21 adds ZERO new pubspec packages, ZERO new Postgres extensions, ZERO Android manifest changes, ZERO new permission keys, ZERO hardcoded role/permission branches in the ads feature code, and introduces NO third-party ad network — the new backend surface is exactly the three ads tables, the `ads` bucket, the `v_ads_serving` view, the `record_ad_event` RPC plus the four admin write RPCs (`create_ad` / `update_ad` / `set_ad_active` / `archive_ad`), and their policies/audit triggers.

## Assumptions

- **Phase 21 is the Ads & banners module** (`specs/021-ads-banners/`), distinct from Phase 20 (Admin dashboard) and Phase 22 (Notifications + Realtime). This spec covers only the first-party banner-ads module.
- **Three product decisions were pre-resolved by the user on 2026-06-01** (folded in here, not re-asked — see Clarifications): (1) link target = **both** an external URL or an in-app deep link, admin-chosen per ad; (2) multiple eligible ads in one placement = a **rotating carousel ordered by priority**; (3) tracking = **clicks only**, no impression/view logging in this phase.
- **Four further decisions were clarified on 2026-06-01** (see Clarifications): (4) **banner content = image + OPTIONAL bilingual caption/CTA**, admin's choice per ad to publish image-only or image + caption (captions are admin-authored ar/en content shown per the viewer's locale, NOT `AppLocalizations` keys; rejected: image-only-always as too limiting, and a single non-localized caption as breaking Arabic-first parity); (5) **deletion = soft-delete / archive** — the ad is hidden everywhere and dropped from the default list but its row + click history are retained so historical click counts survive (this adds a small archived/deleted marker to the `ads` schema; rejected: hard-delete-cascade which loses click history, and hard-delete-detach which needs orphan handling); (6) the **carousel auto-advances on a lightweight client-side UI timer and is also swipeable, looping** (a single eligible ad is static) — the timer is pure UI rotation, NOT a network/Realtime subscription, so it does not violate the "no eager Realtime on home" performance posture; (7) **`home_middle_banner` is a single slot inserted once after the first page/batch** of home listings, not repeated every-N as the user scrolls (keeps the feed uncluttered and the serving read bounded; repeating insertion is a possible later refinement).
- **First-party banners only.** No third-party ad network (AdMob, etc.) and no advertiser self-serve/checkout flow in v1. Per ADR-0001, if a later explicitly-approved spec opens an external ad network, its API keys are Supabase Vault secrets read by an Edge Function — never committed and never shipped to the client. Phase 21 introduces no such key.
- **The `ads.manage` permission already exists** (`PermissionKeys.adsManage = 'ads.manage'`), seeded onto `admin` + `super_admin` in Phase 6 and unused until now; Phase 21 is its first consumer and adds no new permission key and no seed change.
- **The Ads dashboard tile already exists as "coming soon"** (Phase 20 placed `dashboardTileAds`, gated by `PermissionKeys.adsManage`, as `DashboardSectionState.comingSoon` with no route, explicitly so this phase "only wires the destination route without restructuring the dashboard"). Phase 21 flips it to a navigable tile pointing at the new ads admin surface and adds a matching `ads.manage` route guard (`requireAdsManageRedirect`) mirroring the existing `requireReportsManageRedirect` / `requireAgenciesManageRedirect`.
- **Host surfaces wired this phase are home, search results, and listing details** (the plan's `AdSlot` deliverable). Placements: `home_top_banner` (home, top) + `home_middle_banner` (home — a single mid-feed slot inserted once after the first page/batch of listings), `search_results_banner` (search results), `listing_details_banner` (listing details).
- **The `category_banner` placement has no host surface in this phase.** It is defined in the schema (§6.2) but no category landing page exists yet; ads assigned to it will not render until a future phase wires the host. The admin picker signals this (or omits the option) so assignments are not silently invisible. Recorded per Principle XII.
- **In-app deep-link `link_value` encoding per `link_kind`** (resolved — research R-179): `listing`/`agency` carry the target UUID; `category` carries a **property-type key** (apartment/villa/land/shop/office/farm/warehouse/other) opening the search surface filtered to that type; `search` carries a **free-text query string** opening the search surface pre-filled with it; `external` carries an absolute URL. Complex multi-facet filter serialization for `search` is **deferred to a future phase** (v1 = a single text query); the rejected alternative was encoding a full filter set into `link_value`. The admin form validates `link_value` per kind.
- **The ads image column is `image_path`, not `image_url`** (resolved — research R-180): a Storage object path in the `ads` bucket, with the display URL derived at read time (`getPublicUrl`), matching the project's `storage_path`/`logo_path` idiom — a naming alignment with no behavior change vs the plan's §6.2 `image_url`.
- **Ads are public-facing on the host surfaces.** They render for whoever is viewing (anonymous or authenticated, including admins). The plan's acceptance wording "for non-admin users" denotes the verification audience (confirming ads are not gated behind admin), not a rule that hides ads from admins.
- **Eligibility is evaluated server-side at read time** against the current time; the phase uses the project's established read/refresh posture (no eager Realtime, no mid-screen live takedown). An expired/deactivated ad disappears on the next read/refresh. Realtime-driven liveness is out of scope (Phase 22 owns Realtime).
- **Schedule bounds may be open-ended**: a missing start = eligible immediately; a missing end = runs until deactivated. The form forbids start ≥ end when both are set.
- **Click events reuse the reserved `ad_impressions` table, narrowed to `kind = 'click'`.** Because impressions are not logged, the plan's "sampling allowed for cost reasons" note is moot for this phase — clicks are low-volume and recorded unsampled. Whether the `impression` kind/value is even created in v1 is left to the data-model step (it is not produced).
- **Audit scope**: the plan (§9.4) names ad **creation/deletion** as the audited events; this spec mandates those two and treats auditing of activation/deactivation and schedule edits as a recommended additive (decided at the data-model/plan step), consistent with the project's audit posture.
- **Image handling reuses Phase 11 infrastructure** (pick → downscale/compress → upload → cached display) and the established storage discipline; no new image dependency. Recommended per-placement aspect ratios are a design/plan-step detail, not a spec-level product decision; the form may guide/crop accordingly.
- **No new automated tests** are added, per the project's MVP manual-verification convention; verification is by manual on-device walks plus direct wire-level/SQL inspection against fixtures, recorded against the Success Criteria.
- **Backend backed by Supabase** with RLS on all three new tables and the `ads` bucket; the click-recording path is a SECURITY DEFINER RPC mirroring the Phase 16 `record_lead_event` RPC (the plan's §6.7 labels `record_lead_event` an "Edge Function," but it shipped as an RPC; `record_ad_event` follows the real precedent — research R-167). The repository remains the source of truth (migrations, policies, functions, bucket SQL all checked in — Principle II).

## Clarifications

### Session 2026-06-01

- Q: When a banner has a link, what can it point at — an external web URL, an in-app destination, or both? → A: **Both** — each ad points at EITHER an external web URL OR an in-app deep link (listing / filtered search / category / agency profile), chosen per-ad via a link-type picker (FR-003).
- Q: When more than one active ad is eligible for the same placement, how are they shown? → A: A **rotating carousel ordered by the `ad_placements.priority`** field; a single eligible ad renders statically (FR-010).
- Q: What engagement does this phase track — impressions, clicks, or both? → A: **Clicks only.** Taps are recorded via `record_ad_event`; impression/view events are NOT logged in this phase, narrowing the `ad_impressions` table to the `click` kind (FR-016).
- Q: Does a banner show only the uploaded image, or image plus app-rendered text? → A: **Image with an OPTIONAL bilingual (ar/en) caption/CTA, admin's choice per ad** — each ad is published image-only OR image + caption; when a caption is used the admin authors it in both Arabic and English and the slot shows the one matching the viewer's locale (admin-authored content, not `AppLocalizations` keys) (FR-002, Key Entities, FR-023).
- Q: When an admin deletes an ad, what happens to the ad row and its click history? → A: **Soft-delete / archive** — the ad is hidden from every placement and excluded from the default admin list, but its row + click history are retained (click counts survive); deletion adds an archived/deleted marker rather than removing the row (FR-006, FR-011, FR-020).
- Q: How does the priority-ordered carousel advance when multiple ads share a placement? → A: **Auto-advances on a lightweight UI timer AND is manually swipeable, looping**; a single eligible ad renders statically (FR-010).
- Q: How does `home_middle_banner` appear in the paginated home feed? → A: **A single mid-feed slot inserted once, after the first page/batch of listings** (not repeated per-N as the user scrolls) (FR-009).
