# Feature Specification: Locations Catalog (Governorates, Cities, Areas)

**Feature Branch**: `008-locations`
**Created**: 2026-05-16
**Status**: Draft
**Input**: User description: "Phase 8 — Locations. Goal: Structured Syrian governorates / cities / areas managed by admins; selectable in listing form. Backend: migrations `0011_create_governorates.sql`, `0012_create_cities.sql`, `0013_create_areas.sql`; seed all 14 Syrian governorates + major cities (Damascus, Aleppo, Homs, Latakia, Tartus, Hama, etc.) + a starter set of areas; policies — public read, `locations.manage` write. ## Clarifications

### Session 2026-05-16

- Q: Should Phase 8 introduce `latitude`/`longitude` columns on `cities`/`areas` now (forward-stated for Phase 15 map view), or defer entirely? → A: Defer entirely. Phase 8 ships without lat/lng columns; Phase 15 adds them via a follow-up migration if its map view actually needs them. Listings (Phase 10) are expected to carry their own coordinates, which Phase 15 will likely use directly for pin placement.
- Q: Should the internal hierarchy FKs (`cities.governorate_id`, `areas.city_id`) be `ON DELETE CASCADE` or `ON DELETE RESTRICT`? → A: CASCADE on both. Deleting a custom (admin-added, non-protected) governorate cascades to remove its cities and their areas in the same transaction; deleting a custom city cascades to remove its areas. The pre-delete confirmation dialog enumerates the count of dependent rows that will vanish, so the admin enters the action with full awareness. Phase 10's `listings.city_id` remains `ON DELETE RESTRICT` per the forward-stated assumption — cascade can therefore never silently delete listing rows. The 14 seeded governorates and seat cities are admin-protected (FR-015), so this cascade only ever fires on a path the admin explicitly authored.
- Q: Which mechanism implements the seeded-row protection (FR-015, SC-017)? → A: `is_system BOOLEAN NOT NULL DEFAULT false` columns on `governorates` and `cities`, plus DB-side immutability triggers (`enforce_governorate_system_immutability`, `enforce_city_system_immutability`) that refuse `DELETE` and refuse `UPDATE` on the `key` column when `is_system=true`. The 14 seeded governorate rows and the seeded seat-city rows are inserted with `is_system=true`; all admin-created rows default to `is_system=false`. `areas` does NOT carry an `is_system` column (per FR-015, areas have no protected seed). The pattern mirrors Phase 6's `roles.is_system` plus its `enforce_role_system_immutability` trigger — defense-in-depth: even a direct SQL DELETE through Supabase MCP `execute_sql` with an admin JWT is refused.
- Q: What is the target city-coverage scope for the Phase 8 seed? → A: Major cities — the 14 seat cities (one per governorate) PLUS the second-tier known cities of each governorate, totalling roughly 30–40 city rows. The exact inventory is codified at plan time in `research.md` and the seed migration; example second-tier additions include Manbij (Aleppo), Salamiya (Hama), Qamishli (Hasakah), Douma (Rif Dimashq), Albu Kamal (Deir ez-Zor). All seeded city rows carry `is_system=true` (per Q3). Smaller cities and towns are NOT in the initial seed — admins add them via the in-app form (US4) as real listings surface them.
- Q: Should the initial seed produce audit rows, or should the audit log start "empty" for the locations tables from day one? → A: Trigger BEFORE seed. The audit triggers (FR-007) are attached as the FIRST step of the table-creation migration, before any seed `INSERT` runs. Every seeded row therefore produces exactly one `governorate.created` / `city.created` / `area.created` audit row with `actor_user_id=NULL` (the seed migration executes as `postgres`, which carries no `auth.uid()`). This preserves the project-wide invariant "every mutation on an audit-tracked table produces exactly one audit row" without an initial-seed carve-out. The ~80-row audit burst from the seed is the legitimate starting point of the change record; audit-log queries that want admin activity only filter `WHERE actor_user_id IS NOT NULL`.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Public clients see the seeded location catalog on first launch (Priority: P1)

A first-time visitor to the AlNujom app — including anonymous (not-yet-signed-in) clients on the public home, the search screen, and the listing-details screen — reads the locations catalog at launch. The catalog presents all 14 Syrian governorates plus the major cities seeded for each (at minimum Damascus, Aleppo, Homs, Latakia, Tartus, Hama, with the remaining eight governorates each carrying at least their seat city), plus a starter set of areas for the most populous cities. Names are returned in the active locale (Arabic by default per Constitution V, English when the user toggles); the data set is identical for every reader because the rows are publicly readable. A signed-in regular user, moderator, and admin see exactly the same data — locations are global reference data, not per-user. The first read is fast enough to populate downstream consumers (the cascading `LocationPicker` widget used by the Phase 10 listing form, the Phase 13 public listing details "location" line, the Phase 14 search filter chips) without a perceptible blocking gap on the device.

**Why this priority**: P1 because every later location-aware feature — listing creation (Phase 10), public listing details (Phase 13), search and filters (Phase 14), map view (Phase 15) — depends on this catalog existing and being readable by the consumers those phases ship. Constitution VII (Dynamic Roles & Permissions) requires that even reference data not be hardcoded into client builds; Phase 8 is the first phase that introduces an admin-curated, app-readable catalog of geographic data. If Phase 8 ships only the admin write surface (US3-US5) without a working public read path, every later phase that depends on the catalog is also blocked. The story is also the simplest independently testable slice — the seed migrations plus the public-read RLS plus a smoke-test rendering screen are sufficient to demonstrate the value.

**Independent Test**: Apply the Phase 8 migrations to the remote Supabase project via Supabase MCP `apply_migration`. Without signing in (anonymous Supabase JWT), query `SELECT count(*) FROM public.governorates` via Supabase MCP `execute_sql` — confirm the result is 14. Query `SELECT count(*) FROM public.cities` — confirm the count matches the seeded inventory (≥14, one or more per governorate). Query `SELECT count(*) FROM public.areas` — confirm the starter areas are present (≥1, scoped to the largest cities). Run the Flutter app on the reference Infinix Note 8 device with no signed-in session; navigate to whatever public surface Phase 8 ships as a smoke test (an admin-list-as-public-read page works, or a dedicated dev-only browse screen). Confirm all 14 governorate names render in Arabic by default. Toggle the device locale to English; confirm the same governorate rows re-render with their English names; confirm the alphabetical/positional ordering is preserved across locales (ordering is locale-independent).

**Acceptance Scenarios**:

1. **Given** the Phase 8 migrations have applied and the seed has run, **When** an anonymous (not-yet-signed-in) Supabase client queries `public.governorates`, **Then** all 14 rows are returned (RLS allows the anonymous role to SELECT).
2. **Given** the same anonymous client, **When** it queries `public.cities`, **Then** every city row is returned (the seeded set spans at least the six named governorates: Damascus, Aleppo, Homs, Latakia, Tartus, Hama, plus the eight others' seat cities).
3. **Given** the same anonymous client, **When** it queries `public.areas`, **Then** the seeded starter areas are returned (no row is empty-`display_name`).
4. **Given** a signed-in regular `user`-role client, **When** it queries the same three tables, **Then** the same rows are returned — the SELECT policy is identical for anon and authenticated roles (locations are global reference data).
5. **Given** the device locale is Arabic, **When** the smoke-test surface renders, **Then** every governorate / city / area name shown is the Arabic value from the JSONB `display_name`; switching to English re-renders the same rows in their English names; the row order is locale-independent.
6. **Given** a row's `display_name` for the active locale is empty or missing, **When** the smoke-test surface renders that row, **Then** the widget falls back first to the other locale's value, then to the row's `key` slug as the last-resort label (no row ever renders blank).

### User Story 2 — Admin entry tile and route guard are permission-gated (Priority: P1)

After Phase 8 ships, a signed-in user holding the `locations.manage` permission key (the seven Phase 6 system roles include this on `admin` and `super_admin`; future custom roles may include it via Phase 7's `RoleEditorPage`) sees a new "Locations" entry tile on the admin home page (the Phase 6 `AdminHomePage`, alongside the existing Phase 5 account-approvals tile and the Phase 7 super-admin tile). Tapping the tile opens the locations admin section, whose three top-level pages are `LocationsListPage` (the governorate index — US3), the in-list `GovernorateDetailPage` (cities for a governorate — US4), and `CityDetailPage` (areas for a city — US5). A signed-in user who does NOT hold `locations.manage` (a regular `user`, `owner`, `agent`, `agency_admin`, `moderator`, or a custom role that does not include the key) does NOT see the Locations tile; if they hand-craft a deep link to `/admin/locations/*`, the route guard refuses the navigation. Even if a non-permission-holder defeats both layers, the write-side RLS policies introduced in this phase reject every INSERT / UPDATE / DELETE on `governorates`, `cities`, and `areas`. The read path is unaffected — non-admins (including anonymous clients) continue to see the seed via the public-read RLS (US1).

**Why this priority**: P1 because every later Phase 8 story (US3-US5) depends on the entry gate working. Constitution III (Security-First Supabase) requires three-layer enforcement on every admin surface — UX hide via the Phase 6 `PermissionChecker`, route guard at the Flutter router, RLS+write policy at the backend — and this story exercises all three. Constitution VII (Dynamic Roles & Permissions) is preserved: the gate resolves to `permissions.key='locations.manage'`, the same key the Phase 6 seed mapping introduced, with no hardcoded role identity check anywhere in the gate.

**Independent Test**: After applying the Phase 8 migrations, open the project on the reference Infinix Note 8 device. Sign in as a Phase 5 regular `user`-only account — confirm the Locations tile is absent from the admin home (the user's session has no admin home at all in this case, which is correct). Sign out, sign in as the Phase 5 admin (holding the `admin` role from the Phase 6 backfill, which includes `locations.manage` per Phase 6 §9.1) — confirm the admin home renders with the existing Phase 5 account-approvals tile, the Phase 7 super-admin tile (only if this admin also holds `super_admin`; the bootstrap setup matters here), AND the new Phase 8 Locations tile. Tap "Locations"; confirm `LocationsListPage` opens. Sign out, sign in as a moderator account (the Phase 6 moderator role does NOT include `locations.manage` per §9.1) — confirm the admin home renders with only those tiles whose permission keys the moderator holds, and the Locations tile is absent. From the moderator session, hand-type `/admin/locations` into a deep link (or whatever mechanism the Flutter router exposes); confirm the route guard refuses navigation with the same "not authorized" treatment used by other admin routes. From a desktop, run an INSERT against `public.governorates` using a JWT for the moderator session via Supabase MCP `execute_sql` — confirm the write returns 0 rows affected (write-side RLS deny).

**Acceptance Scenarios**:

1. **Given** a signed-in session for a user holding no admin-tier permissions, **When** the admin home page would normally render, **Then** the user is not on the admin home at all (their navigation does not surface it) — Phase 6 behavior preserved.
2. **Given** a signed-in session for a user holding `locations.manage` (via `admin`, `super_admin`, or a custom role), **When** the admin home renders, **Then** the "Locations" tile is present.
3. **Given** a signed-in session for a user holding some admin-tier permissions BUT NOT `locations.manage` (e.g., `moderator` whose mapping covers `listings.*` and `reports.*` but not locations), **When** the admin home renders, **Then** the Locations tile is absent (`PermissionChecker.has('locations.manage')` returns false; the tile widget is hidden, not dimmed).
4. **Given** the same non-permission-holder session, **When** they navigate directly via the deep link `/admin/locations` or `/admin/locations/<governorate-id>`, **Then** the route guard refuses the navigation and redirects per the established admin-route unauthorized pattern.
5. **Given** the same non-permission-holder session, **When** they craft a direct INSERT / UPDATE / DELETE against `public.governorates`, `public.cities`, or `public.areas`, **Then** the write-side RLS policy rejects the write (no rows affected) — defense in depth behind the UI gate and the route guard.
6. **Given** the Phase 6 `PermissionChecker` cache refresh observation points (FR-015 from Phase 6: cold start, sign-in, lifecycle resume), **When** an admin is granted `locations.manage` via `RoleEditorPage` (Phase 7 US3) mid-session, **Then** the Locations tile appears on next lifecycle observation (foreground resume or token refresh) without a sign-out — Phase 6 FR-015 propagation invariant carries forward unchanged.

### User Story 3 — Admin creates, renames, and deletes governorates (Priority: P1)

A signed-in user holding `locations.manage` taps the Locations tile, opening `LocationsListPage`. The page lists all 14 governorates plus any custom governorates the admin has added. Each row shows the governorate's localized `display_name` (Arabic by default, English when toggled, falling back to the other locale and finally to the `key` slug), a count of how many cities the governorate carries (e.g., "8 cities" via a rolled-up read), and a status badge if `is_active=false`. The list is ordered by an editorial position field (Damascus first, then by descending population by convention), falling back to alphabetical-by-`key` for rows with no editorial position. The page exposes "Add governorate", per-row "Edit", and per-row "Delete" affordances; the delete affordance is restricted on the 14 originally-seeded governorates (analogous to Phase 6 `is_system=true` system rows — the seeded set is a closed catalog and cannot be deleted via the in-app surface, only edited or deactivated). The form for add/edit requires a unique lowercase `key` slug, a `display_name` JSONB with at least the Arabic value populated (English is encouraged but optional, matching Constitution V's Arabic-first stance), an optional `description` JSONB, an optional editorial `position INTEGER`, and an `is_active BOOLEAN` (default `true`). On save, the row is upserted in a single transaction; on edit of `display_name`, every consumer surface — the LocationPicker, every signed-in user's home page, every listing details screen that references this governorate — reflects the new name on its next render.

**Why this priority**: P1 because governorates are the top of the location hierarchy; without governorate CRUD, the cascading picker has no first level to populate. The plan's acceptance criterion "Renaming a governorate updates everywhere" tests this story end-to-end. Constitution V (Arabic-First Localization) requires every user-visible label to flow through `AppLocalizations` for app-chrome strings AND through JSONB `display_name` for data labels; this story is where the JSONB pattern from Phase 6 (`roles.display_name`) extends to a second admin-curated catalog.

**Independent Test**: Sign in as the Phase 5 admin (or any user holding `locations.manage`) on the device. Open the admin home → "Locations". Confirm `LocationsListPage` renders with 14 governorate rows. Tap "Add governorate". Fill in `key=ar-raqqah-test`, `display_name={"ar": "الرقة (اختبار)", "en": "Ar-Raqqah (test)"}`, leave description blank, set position to 99, leave `is_active=true`. Tap Save. Confirm the new row appears in the list (at position 99 — i.e., at the bottom). Tap the row, then tap "Edit". Change the English display_name to "Raqqah". Save. Confirm the row label updates in the list immediately. From a desktop, query via Supabase MCP `execute_sql`: `SELECT key, display_name->>'ar' AS ar, display_name->>'en' AS en, is_active FROM public.governorates WHERE key='ar-raqqah-test'` — confirm the row reflects the saved state. Open a second device (or a second incognito session on the desktop emulator) signed in as a regular `user` and navigate to a smoke-test public surface that lists governorates — confirm the renamed row appears with the new English label on next render (no sign-out, no app restart). Return to the admin device, tap "Delete" on the custom row, confirm the dialog ("are you sure?"), tap Confirm. Confirm the row disappears from the list. Verify via SQL the row is gone. Confirm — on the same row of any of the 14 originally-seeded governorates — no "Delete" affordance appears (only "Edit" and a soft-deactivate via `is_active=false`).

**Acceptance Scenarios**:

1. **Given** the Phase 8 deploy has just completed, **When** `LocationsListPage` renders for a `locations.manage` holder, **Then** all 14 originally-seeded governorates appear, each labeled with its active-locale `display_name`.
2. **Given** the same page, **When** the admin taps "Add governorate" and submits a valid form with a unique `key`, **Then** the row is inserted with `is_active=true` by default and appears in the list immediately on return.
3. **Given** the admin enters a `key` that collides with an existing governorate, **When** they tap Save, **Then** the form refuses to save and shows a localized "this key is already used" error (the `UNIQUE(governorates.key)` constraint would also reject server-side).
4. **Given** the admin enters a `display_name` whose `ar` value is empty (English populated, Arabic blank), **When** they tap Save, **Then** the form refuses to save and shows a localized "Arabic name is required" error (Constitution V Arabic-first).
5. **Given** the admin edits an existing governorate's `display_name`, **When** they Save, **Then** every consumer of the row — the LocationPicker, the smoke-test surface, every signed-in user's location-aware page — reflects the new label on its next render. No client-side cache delays the rename beyond the time the next paint takes.
6. **Given** the admin deactivates an existing governorate (`is_active=false`) via the form, **When** they Save, **Then** the row remains in the admin list with a "Hidden" badge, but the public LocationPicker no longer offers it as a selectable option on next render.
7. **Given** one of the 14 originally-seeded governorates, **When** the admin opens its contextual menu, **Then** no "Delete" affordance is present (the seeded catalog is protected — admins may rename, deactivate, or reposition, but not delete). If a non-seed governorate the admin previously created has been deleted via the in-app surface and the row had no cities, the delete succeeds in a single transaction.
8. **Given** a custom (non-seeded) governorate that already has cities, **When** the admin attempts to delete it, **Then** the confirmation dialog first displays the count of dependent rows that will be removed (e.g., "this governorate has 3 cities and 7 areas — they will also be deleted"); on Confirm, the FK `cities.governorate_id ON DELETE CASCADE` removes the cities and their areas in the same transaction with the governorate (Clarifications Session 2026-05-16 Q2). If any of those dependent cities are referenced by a Phase 10 `listings` row, the Phase 10 `listings.city_id ON DELETE RESTRICT` foreign key aborts the entire transaction with a `23503 foreign_key_violation`, which the UI maps back to a localized "this governorate has cities with active listings; remove the listings first" error.

### User Story 4 — Admin manages cities scoped to a governorate (Priority: P1)

The admin taps a governorate on `LocationsListPage`, opening `GovernorateDetailPage` for that governorate. The page shows the governorate's localized name as a header, plus a list of every city in `public.cities` whose `governorate_id` matches. Each row shows the city's localized `display_name`, a count of how many areas the city carries, the `is_active` badge if hidden, and the editorial position. The page exposes "Add city", per-row "Edit", and per-row "Delete" affordances. The add/edit form requires a unique-within-this-governorate lowercase `key` slug, a `display_name` JSONB with at least the Arabic value, an optional `description` JSONB, an optional editorial `position INTEGER`, and an `is_active BOOLEAN`. Saving inserts or updates one row in `public.cities` with `governorate_id` bound to the page's governorate. The originally-seeded cities (the major cities listed in the plan — Damascus, Aleppo, Homs, Latakia, Tartus, Hama, and the seat city of each remaining governorate) are protected from in-app deletion exactly like the seeded governorates are; custom (admin-added) cities can be deleted subject to the same FK protection on dependent areas (and, once Phase 10 ships, on dependent listings).

**Why this priority**: P1 because the LocationPicker needs both governorate and city to be selectable; without cities, the picker has nothing to populate level 2 with. Constitution VII is reinforced: the city catalog is data-driven and admin-editable, not a hardcoded enum compiled into the app.

**Independent Test**: From the admin device, open `LocationsListPage`, tap "Damascus" (or its Arabic label "دمشق"). Confirm `GovernorateDetailPage` renders with the city header in the active locale and a list of seeded Damascus cities. (For Damascus governorate, the seeded city is typically Damascus itself plus possibly Douma, Daraya — whatever the plan-time seed inventory decides.) Tap "Add city". Fill in `key=jaramana`, `display_name={"ar": "جرمانا", "en": "Jaramana"}`, position 5, `is_active=true`. Save. Confirm the row appears in the list. Open `LocationPicker` (US6) from a smoke-test screen; pick Damascus governorate; confirm Jaramana appears in the city dropdown. Edit the row's display_name English to "Jaramana City"; Save; confirm the picker updates on next open. Delete the custom row; confirm it disappears from the admin list and from the picker. Confirm the seeded "Damascus" city row has no Delete affordance.

**Acceptance Scenarios**:

1. **Given** `GovernorateDetailPage` opens for any governorate, **When** the page renders, **Then** every row in `public.cities WHERE governorate_id=<this id>` is listed with its active-locale `display_name`.
2. **Given** the page, **When** the admin taps "Add city" and submits a valid form, **Then** the row is inserted with `governorate_id` correctly bound to the page's governorate and `is_active=true` by default.
3. **Given** the admin enters a `key` that collides with an existing city within the same governorate, **When** they Save, **Then** the form refuses to save (the `UNIQUE(governorate_id, key)` composite constraint would also reject server-side).
4. **Given** the admin enters a `key` that exists in a different governorate but not this one (e.g., two governorates each have a city slug `markaz`), **When** they Save, **Then** the row inserts successfully — uniqueness is scoped per-governorate, not global.
5. **Given** the admin deactivates a city (`is_active=false`), **When** Save completes, **Then** the LocationPicker no longer offers it for picking, but the admin list still shows it with a "Hidden" badge.
6. **Given** an originally-seeded city, **When** the admin opens its contextual menu, **Then** no "Delete" affordance is present (the seeded catalog is protected). The Edit affordance remains.
7. **Given** a custom city the admin earlier added, with zero areas referencing it, **When** they tap Delete and confirm, **Then** the city row is removed from `public.cities` and the admin list updates.

### User Story 5 — Admin manages areas scoped to a city (Priority: P2)

The admin taps a city on `GovernorateDetailPage`, opening `CityDetailPage` for that city. The page shows the governorate → city breadcrumb (e.g., "Damascus → Jaramana") plus a list of every area in `public.areas` whose `city_id` matches. Each row shows the area's localized `display_name`, the `is_active` badge if hidden, and the editorial position. The page exposes "Add area", per-row "Edit", and per-row "Delete" affordances. The add/edit form requires a unique-within-this-city lowercase `key` slug, a `display_name` JSONB with at least the Arabic value, an optional `description` JSONB, an optional editorial `position INTEGER`, and an `is_active BOOLEAN`. Saving inserts or updates one row in `public.areas` with `city_id` bound to the page's city. Unlike governorates and cities, areas have no protected seed — the plan describes only "a starter set of areas" rather than an exhaustive list, so every seeded area is treated as editorial scaffolding the admin may delete, rename, or replace freely. Any area, seeded or not, can be deleted.

**Why this priority**: P2 because while the LocationPicker is more useful with areas, a city-only picker still satisfies every Phase 8 acceptance criterion (the plan's listing form acceptance only requires "selectable in listing form" — picking just to the city level is sufficient for a v1 listing). Areas can ship in a v1.0 with a small starter seed and be filled in incrementally; the schema and CRUD surface for areas can therefore be exercised independently of US3 and US4. The plan's acceptance criterion "Admin with `locations.manage` can add a new area; it appears in the picker" directly tests this story plus US6.

**Independent Test**: From the admin device, open `LocationsListPage` → Damascus → Jaramana. Confirm `CityDetailPage` renders with the breadcrumb and a list of seeded areas (could be empty for some cities — that is acceptable). Tap "Add area". Edit the row's display_name; confirm the picker reflects the rename. Delete the row; confirm it disappears from both surfaces.

**Acceptance Scenarios**:

1. **Given** `CityDetailPage` opens for any city, **When** the page renders, **Then** every row in `public.areas WHERE city_id=<this id>` is listed with its active-locale `display_name`.
2. **Given** the page, **When** the admin taps "Add area" and submits a valid form, **Then** the row is inserted with `city_id` correctly bound to the page's city.
3. **Given** the admin enters a `key` that collides with an existing area in the same city, **When** they Save, **Then** the form refuses to save (the `UNIQUE(city_id, key)` composite constraint enforces this server-side).
4. **Given** any area row (seeded or custom), **When** the admin taps Delete and confirms, **Then** the row is removed from `public.areas` and disappears from both the admin list and the LocationPicker on next render.
5. **Given** the admin deactivates an area (`is_active=false`), **When** Save completes, **Then** the LocationPicker no longer offers it, but the admin list still shows it with a "Hidden" badge.
6. **Given** a city has zero areas in `public.areas`, **When** the LocationPicker advances to the area-selection step for that city, **Then** the picker presents a localized "no areas yet — proceed without area" affordance rather than blocking the user; the listing form (Phase 10) treats `area_id` as optional.

### User Story 6 — Cascading LocationPicker widget renders the catalog for downstream consumers (Priority: P1)

A reusable `LocationPicker` widget — defined under `lib/features/locations/presentation/widgets/` and exported as a public component of the locations feature — renders three dependent dropdown (or modal-list) controls: governorate, city, area. The widget reads the catalog via the same `locations` repository the admin pages use, filters out `is_active=false` rows for the consumer-facing path (admins editing the catalog see hidden rows in their own pages; consumers do not), and renders every label in the active locale with the same fallback chain (active locale → other locale → `key`). Selecting a governorate populates the city control with that governorate's cities (zero or more); selecting a city populates the area control with that city's areas (zero or more). Selecting an area is OPTIONAL — the widget supports a "city-only" outcome where the user chooses a city and submits without picking an area. The widget exposes a single result object — `{governorateId, cityId, areaId?}` — and emits a change event whenever any level changes. The widget is the integration seam Phase 10's listing form (and later Phase 13 listing details, Phase 14 search filters, Phase 15 map view) consumes; Phase 8 ships the widget with a smoke-test screen demonstrating it works end-to-end with the seeded data.

**Why this priority**: P1 because the plan's acceptance criterion "selectable in listing form" depends on this widget existing and being consumed downstream; without it, Phase 10's listing form cannot wire up the location section. Constitution IV (Clean Architecture Flutter) is enforced: the widget consumes the domain entities (Governorate, City, Area) and use cases (LoadGovernorates, LoadCitiesForGovernorate, LoadAreasForCity) — no Supabase client call from within the widget tree. Constitution VI is enforced: all visual treatment flows through the Phase 2 design tokens.

**Independent Test**: From the device, open the Phase 8 smoke-test screen (or the Phase 10 listing form once it ships). Mount the LocationPicker. Confirm the governorate dropdown lists all 14 governorates in their active-locale names in the editorially-ordered sequence. Tap Damascus; confirm the city dropdown populates with Damascus's cities (≥1). Tap Damascus city; confirm the area dropdown populates with Damascus city's areas (≥0). Pick any area; confirm the widget emits `{governorateId: <damascus uuid>, cityId: <damascus-city uuid>, areaId: <picked area uuid>}`. Reset; pick Aleppo; confirm the city dropdown re-populates with Aleppo's cities (Damascus's cities are gone). Pick an Aleppo city with zero seeded areas; confirm the widget allows the user to leave area blank and submit a `{governorateId, cityId, areaId: null}` result. Toggle locale ar↔en; confirm every label re-renders in the toggled locale without losing the user's selection state.

**Acceptance Scenarios**:

1. **Given** the LocationPicker is mounted with no prior selection, **When** it renders, **Then** the governorate control is populated, the city control is disabled / empty, and the area control is disabled / empty.
2. **Given** the user picks a governorate, **When** the picker re-renders, **Then** the city control is populated with that governorate's `is_active=true` cities and the area control is reset.
3. **Given** the user picks a city, **When** the picker re-renders, **Then** the area control is populated with that city's `is_active=true` areas; if zero, the area control is rendered with a "no areas yet — leave blank" affordance that submits `areaId=null`.
4. **Given** the user picks an area, **When** the picker emits its result, **Then** the result is `{governorateId, cityId, areaId}` — all three populated.
5. **Given** the user has picked governorate + city but no area, **When** the picker is committed (submit button or external onChange), **Then** the result is `{governorateId, cityId, areaId: null}` (area is optional).
6. **Given** the user toggles the device locale mid-selection, **When** the picker re-renders, **Then** every label flips to the new locale; the user's selection state is preserved (the picked IDs do not change).
7. **Given** an admin deactivates a city via the admin pages (US4), **When** any signed-in user opens the LocationPicker on next render, **Then** the deactivated city is absent from the city dropdown (the widget reads `is_active=true` rows only).
8. **Given** an admin renames a governorate (US3), **When** any signed-in user opens the LocationPicker on next render, **Then** the renamed label appears immediately — there is no stale client-side cache that defers the rename beyond the next render of the widget.

### User Story 7 — Every locations mutation emits an audit-log row (Priority: P2)

Phase 7 established the precedent of attaching audit triggers to every new admin-curated catalog table (Phase 7 attached triggers to `roles`, `role_permissions`, `permissions`). Phase 8 extends the precedent: three INSERT / UPDATE / DELETE trigger pairs attach to `public.governorates`, `public.cities`, and `public.areas` via Phase 4's reusable `log_audit()` function (the Phase 4 R-05 reusability invariant — `log_audit` is unchanged a fourth time). The action keys are `governorate.created` / `governorate.updated` / `governorate.deleted`, `city.created` / `city.updated` / `city.deleted`, and `area.created` / `area.updated` / `area.deleted`. The audit row's `actor_user_id` carries `auth.uid()` for in-app mutations (the admin performing the action) and NULL for system mutations (the initial seed migration runs as `postgres`, so seed rows produce `actor_user_id=NULL` audit rows or — if the trigger is attached after the seed inserts — produce no audit row for the initial seed at all; either is acceptable and the plan-time decision is codified in research.md).

**Why this priority**: P2 because the audit coverage is a compliance + observability concern, not a feature-correctness concern; the plan's three acceptance criteria do not strictly require it. But Constitution III (Security-First Supabase) makes audit-trail completeness for admin mutations a project-wide expectation, and the Phase 7 precedent (Phase 7 US6) established the pattern. Shipping Phase 8 without audit coverage would be the first phase since Phase 4 to break the pattern — a recurring deviation that compounds. The story is also independently testable — the triggers can be installed and exercised via direct-SQL mutations before any of the UI stories ship.

**Independent Test**: After applying the Phase 8 migrations, run via Supabase MCP `execute_sql` (running as `postgres` or as a `locations.manage`-holding JWT):
- INSERT a row into `public.governorates` (`key=test-gov`). Verify a `governorate.created` row appears in `public.audit_logs` with the inserted row in `after_state` and `target_id = <new governorate id>`.
- UPDATE the same row's `display_name`. Verify a `governorate.updated` row appears with `before_state` carrying the prior display_name and `after_state` carrying the new one.
- INSERT a city under the new governorate. Verify a `city.created` row appears with `target_id = <new city id>`.
- INSERT an area under the new city. Verify an `area.created` row appears.
- DELETE the area, the city, the governorate (in that order to avoid FK violations). Verify three `*.deleted` rows appear in turn.
- Confirm the existing Phase 6 / Phase 7 audit triggers on `user_roles` / `roles` / `role_permissions` / `permissions` remain present and functional — Phase 8 migrations do not modify or rewrite them.

**Acceptance Scenarios**:

1. **Given** an INSERT into `public.governorates` from any caller (in-app admin or direct SQL), **When** the row is committed, **Then** ONE `audit_logs` row is emitted with `action = 'governorate.created'`, `before_state = null::jsonb`, `after_state` carrying the inserted row's JSON, and `target_id` set to `NEW.id`.
2. **Given** an UPDATE on `public.governorates`, **When** the row is committed, **Then** ONE `audit_logs` row is emitted with `action = 'governorate.updated'`, `before_state` carrying `OLD` and `after_state` carrying `NEW`.
3. **Given** a DELETE on `public.governorates` (only legal when no cities reference it, or under ON DELETE CASCADE per the plan-time schema decision), **When** the row is committed, **Then** ONE `audit_logs` row is emitted with `action = 'governorate.deleted'` and `before_state` carrying the deleted row's JSON.
4. **Given** the same three trigger pairs on `public.cities` and `public.areas`, **When** any mutation hits those tables, **Then** the corresponding `city.*` and `area.*` actions are emitted following the same shape.
5. **Given** the Phase 4 `log_audit` function, **When** Phase 8 migrations attach the new triggers, **Then** `log_audit` is NOT modified — the trigger declarations pass the action name as `TG_ARGV[0]` exactly as Phase 5, Phase 6, and Phase 7 already do.
6. **Given** the initial seed migration runs as `postgres` and the audit triggers are attached BEFORE the seed `INSERT` statements (Clarifications Session 2026-05-16 Q5), **When** the migration inserts the 14 governorates, ~30–40 cities, and the starter areas, **Then** exactly one `*.created` audit row is emitted per inserted row, every such row carries `actor_user_id=NULL`, and the `audit_logs` row count after the migration completes is the sum of the three seed sizes (approximately 80 rows total, exact count determined by the plan-time seed inventory).

### Edge Cases

- **Empty branches**: A governorate may have zero cities in its initial seed (unlikely in practice but possible during plan-time inventory work); a city may have zero areas (very likely for smaller cities). The LocationPicker MUST handle both gracefully — empty city control offers a "no cities yet" affordance and prevents progression; empty area control offers a "no areas yet — leave blank" affordance and allows progression with `areaId=null`.
- **Anonymous read on app launch**: Constitution III's RLS-by-default posture means every table must have an explicit SELECT policy. The Phase 8 spec deliberately enables `anon` and `authenticated` SELECT on all three locations tables — locations are global reference data with no privacy concern, and Phase 13 (Public listing details) and Phase 14 (Search) both serve anonymous clients. This is a Phase 8 carve-out from the "authenticated-only" default that Phase 4 / Phase 5 / Phase 6 used; it is intentional and limited to the three locations tables.
- **Cascading delete on the internal hierarchy**: Per Clarifications Session 2026-05-16 Q2, both internal FKs (`cities.governorate_id`, `areas.city_id`) use `ON DELETE CASCADE`. Deleting a custom governorate cascades to remove its cities and their areas in the same transaction; the confirmation dialog enumerates the dependent count before committing. Phase 10's `listings.city_id` remains `ON DELETE RESTRICT`, so cascade can never silently remove listing rows.
- **Phase 10 listings FK behavior**: When Phase 10 ships `listings.city_id` and `listings.area_id`, those FKs MUST be `ON DELETE RESTRICT` (or `ON DELETE SET NULL` on `area_id` since area is optional) — never `CASCADE`, because deleting a city or area would otherwise silently nuke listing rows. The Phase 8 spec calls this out so Phase 10's plan honors it. Phase 8 itself does not introduce the listings table; that constraint is forward-stated.
- **Rename consistency for the 14 originally-seeded governorates**: Constitution V's Arabic-first rule means the 14 seeded `display_name->>ar` values MUST be the canonical Arabic names used in Syrian public discourse (e.g., "دمشق" not "الشام"; "ريف دمشق" rather than another form for Damascus Countryside). The seed migration codifies the canonical strings; admins may rename via US3 if a project owner later disagrees, with the audit trail recording the rename.
- **Locale fallback chain**: For every label rendered from `display_name` JSONB, the fallback is (1) active locale's value, (2) the other locale's value, (3) the row's `key` slug as a last-resort label. This matches Phase 6's exact pattern on `roles.display_name`. No label ever renders as an empty string.
- **Editorial position ties**: If two rows share the same `position INTEGER` value, the tie is broken by alphabetical `key` (locale-independent). Plan-time decision MAY introduce a separate tie-break (e.g., `created_at`); the spec leaves this open.
- **Concurrent rename by two admins**: Two admins simultaneously editing the same governorate's display_name is a low-probability event but not impossible. Phase 8 does NOT introduce optimistic locking for locations (unlike Phase 7's `mutate_role` which uses `roles.updated_at` per Q4) — the locations catalog is a low-write, infrequently-edited surface where last-write-wins is acceptable, and the audit trail (US7) records both writes so the older edit is recoverable. If a later spec finds this is too loose, optimistic locking can be retrofitted using `updated_at` (already present per FR-006).

## Requirements *(mandatory)*

### Functional Requirements

#### Schema and seed

- **FR-001**: System MUST introduce three new tables in the `public` schema — `governorates`, `cities`, `areas` — each with a UUID primary key, a stable lowercase TEXT `key` slug, a non-null JSONB `display_name` (with at least the `ar` entry required at write time), an optional JSONB `description`, an optional INTEGER `position` for editorial ordering, a non-null BOOLEAN `is_active` defaulting to `true`, and TIMESTAMPTZ `created_at` / `updated_at` columns maintained by the Phase 4 `set_updated_at` trigger. `governorates` and `cities` additionally carry a non-null BOOLEAN `is_system` column defaulting to `false` (the seeded 14 governorates and seeded seat cities are inserted with `is_system=true`); `areas` does NOT carry `is_system`.
- **FR-002**: `cities` MUST carry a `governorate_id UUID NOT NULL REFERENCES public.governorates(id) ON DELETE CASCADE` foreign key. `areas` MUST carry a `city_id UUID NOT NULL REFERENCES public.cities(id) ON DELETE CASCADE` foreign key. Deleting a custom (non-protected) governorate or city therefore cascades to remove its dependents in the same transaction; the admin sees the dependent count in the confirmation dialog before committing (FR-017). Phase 10's later `listings.city_id` MUST remain `ON DELETE RESTRICT` so the cascade never silently removes listing rows.
- **FR-003**: `governorates.key` MUST be globally unique. `cities.key` MUST be unique within each governorate (composite `UNIQUE(governorate_id, key)`). `areas.key` MUST be unique within each city (composite `UNIQUE(city_id, key)`).
- **FR-004**: System MUST seed exactly 14 rows into `public.governorates` representing the 14 Syrian governorates, with canonical Arabic `display_name->>ar` values and English `display_name->>en` values. The seed is idempotent — re-running the migration does not duplicate rows.
- **FR-005**: System MUST seed approximately 30–40 city rows covering (a) the 14 seat cities (one per governorate, with the six named in the plan — Damascus, Aleppo, Homs, Latakia, Tartus, Hama — carrying their full canonical names in both locales) AND (b) the second-tier known cities of each governorate (e.g., Manbij in Aleppo, Salamiya in Hama, Qamishli in Hasakah, Douma in Rif Dimashq, Albu Kamal in Deir ez-Zor). All seeded city rows are inserted with `is_system=true`. The exact 30–40 city inventory is codified at plan time in `research.md` and the seed migration; smaller cities and towns are NOT in the initial seed and are added by admins via the in-app form (US4).
- **FR-006**: System MUST seed a starter set of areas (at least one area for the most populous cities; smaller cities MAY have zero seeded areas). The exact starter inventory is decided at plan time.
- **FR-007**: System MUST attach INSERT / UPDATE / DELETE audit triggers to `public.governorates`, `public.cities`, `public.areas` using Phase 4's `log_audit()` function unchanged, emitting actions `governorate.*`, `city.*`, `area.*` respectively. Per Clarifications Session 2026-05-16 Q5, the triggers MUST be attached BEFORE the seed `INSERT` statements run in the table-creation migration, so every seeded row produces exactly one `*.created` audit row with `actor_user_id=NULL` (system provenance).
- **FR-007a**: System MUST attach immutability triggers `enforce_governorate_system_immutability` (on `public.governorates`) and `enforce_city_system_immutability` (on `public.cities`) that refuse any `DELETE` on a row where `is_system=true` AND refuse any `UPDATE` that changes the `key` column on a row where `is_system=true`. The triggers raise `SQLSTATE 42501` with a structured error message; mirrors Phase 6's `enforce_role_system_immutability` precedent. Admins MAY still `UPDATE` `display_name`, `description`, `position`, and `is_active` on a `is_system=true` row.

#### Permissions and policies

- **FR-008**: System MUST gate write access to `governorates`, `cities`, `areas` behind the `permissions.key='locations.manage'` key. The write-side RLS policies MUST check `current_user_has_permission('locations.manage')` (the Phase 6 helper).
- **FR-009**: System MUST allow public SELECT on all three tables for both `anon` and `authenticated` roles — locations are global reference data per the Edge Case note.
- **FR-010**: System MUST NOT introduce a new permission key — `locations.manage` already exists in the Phase 6 catalog and is already mapped to the `admin` and `super_admin` roles.
- **FR-011**: System MUST honor the Phase 6 PermissionChecker cache-refresh invariants (FR-015 from Phase 6) — when a user is granted `locations.manage` mid-session via Phase 7's RoleEditorPage, the Locations tile appears on the next lifecycle observation point without a sign-out.

#### Admin UI

- **FR-012**: System MUST add a "Locations" tile to the Phase 6 `AdminHomePage`, gated by `PermissionChecker.has('locations.manage')`. The tile is hidden, not dimmed, for non-permission-holders.
- **FR-013**: System MUST add a router guard on `/admin/locations/*` routes that refuses navigation for users without `locations.manage`, redirecting per the established admin-route unauthorized pattern.
- **FR-014**: System MUST provide three pages under `lib/features/locations/presentation/pages/` — `LocationsListPage` (governorate index), `GovernorateDetailPage` (cities for a governorate), `CityDetailPage` (areas for a city) — wired up via the BLoC / cubit pattern from Constitution IV. No Supabase client call lives inside the widget tree.
- **FR-015**: System MUST provide add / edit / delete affordances on each admin page. The seeded 14 governorates and the seeded seat cities (`is_system=true` rows, per FR-001 and FR-007a) MUST NOT expose a Delete affordance, and MUST NOT expose a `key`-rename affordance — these are enforced server-side by `enforce_governorate_system_immutability` / `enforce_city_system_immutability` and mirrored client-side so the admin never sees an affordance that would error. Edit (on `display_name`, `description`, `position`, `is_active`) remains available on every row including the seeded ones. Areas have no `is_system` column and no protected seed; every area row (seeded or custom) exposes Delete and `key`-rename.
- **FR-016**: System MUST validate every form: `key` is required and unique within scope (server-side `UNIQUE` constraint, client-side preflight check), `display_name->>ar` is required and non-empty (Constitution V), `display_name->>en` is optional, `position` is an integer when present, `is_active` defaults to true.
- **FR-017**: System MUST show a confirmation dialog before any destructive action (Delete on a custom row, Deactivate on a previously-active row).

#### LocationPicker widget

- **FR-018**: System MUST provide a `LocationPicker` widget exported from `lib/features/locations/presentation/widgets/`, consumable by every later feature that needs a location selection (Phase 10 listing form, Phase 14 search filters, Phase 15 map view).
- **FR-019**: The widget MUST render three cascading controls — governorate (always populated), city (populated after governorate), area (populated after city, optional). It MUST surface a clear "no areas yet" affordance when a city has zero `is_active=true` areas, permitting an `areaId=null` outcome.
- **FR-020**: The widget MUST filter out `is_active=false` rows from its public-facing output. The admin pages (FR-014) still show hidden rows with a "Hidden" badge.
- **FR-021**: The widget MUST render every label in the active locale with the same fallback chain (active locale → other locale → `key`), matching the Phase 6 `roles.display_name` rendering convention.
- **FR-022**: The widget MUST emit a structured result `{governorateId, cityId, areaId?}` and a change event on every level transition. The result type MUST be a domain entity, not a raw map, per Constitution IV.

#### Localization, design tokens, audit

- **FR-023**: System MUST add ARB keys to `lib/l10n/app_ar.arb` and `lib/l10n/app_en.arb` for every new user-visible string introduced by the locations admin pages (page titles, button labels, form labels, dialog copy, error messages). Data labels — governorate names, city names, area names — come from the JSONB `display_name`, not from ARB.
- **FR-024**: Every new widget in `lib/features/locations/presentation/` MUST consume the Phase 2 design tokens for spacing, color, typography. No inline magic numbers.
- **FR-025**: Every mutation through any in-app surface OR via direct SQL MUST emit exactly one `audit_logs` row per row-mutation, action-keyed per FR-007. Bulk mutations (e.g., a single migration inserting multiple rows) emit one audit row per inserted row.

### Key Entities *(include if feature involves data)*

- **Governorate**: A Syrian first-level administrative division. Identified by a stable lowercase `key` slug (e.g., `damascus`, `aleppo`, `rif-dimashq`); displayed via the bilingual `display_name` JSONB (e.g., `{"ar": "دمشق", "en": "Damascus"}`); ordered editorially via `position INTEGER` (Damascus first by convention, with the rest by descending population or alphabetical-by-`key` as fallback). Owns zero-or-more cities. The 14 seeded rows are marked `is_system=true` and are protected from in-app deletion AND from `key`-rename via `enforce_governorate_system_immutability`; admin-created rows default to `is_system=false`.
- **City**: A second-level administrative division within a governorate. Identified by a stable lowercase `key` slug scoped to its governorate (uniqueness is `(governorate_id, key)`); displayed via the bilingual `display_name` JSONB; ordered editorially via `position INTEGER` within its governorate. Owns zero-or-more areas. Holds a `governorate_id` foreign key with `ON DELETE CASCADE`. Seeded seat cities are marked `is_system=true` and protected from in-app deletion AND from `key`-rename via `enforce_city_system_immutability`; admin-added cities default to `is_system=false` and carry full CRUD affordances.
- **Area**: A third-level administrative division within a city — a neighborhood, district, or named locality. Identified by a stable lowercase `key` slug scoped to its city (uniqueness is `(city_id, key)`); displayed via the bilingual `display_name` JSONB; ordered editorially via `position INTEGER` within its city. Holds a `city_id` foreign key with `ON DELETE CASCADE`. Has no `is_system` column and no protected seed — every area row, seeded or custom, can be edited, deactivated, or deleted.
- **LocationPicker selection** *(transient, not persisted by Phase 8)*: A `{governorateId: UUID, cityId: UUID, areaId: UUID?}` triple emitted by the LocationPicker widget. `areaId` is optional (null when the chosen city has no areas, or when the user chooses to skip area selection). Consumed by downstream features (Phase 10 listing form binds it onto the new listing row; Phase 14 search filters bind it onto the query parameter; Phase 15 map view binds it onto the map bounds).

## Assumptions

- **Bilingual `display_name` JSONB pattern carries forward from Phase 6**: Phase 6 introduced `roles.display_name JSONB` with at-least-`ar`-required semantics and the (active → other → key) fallback chain. Phase 8 mirrors that contract exactly on `governorates.display_name`, `cities.display_name`, `areas.display_name`. No new schema concept is introduced.
- **`locations.manage` is the only permission key**: Phase 6 §9.1 already mapped `locations.manage` to `admin` and `super_admin`. Phase 8 does NOT split read vs. write into separate keys, does NOT introduce a per-governorate scoping key, and does NOT introduce a moderator-can-read-but-not-write key. The Phase 6 mapping is sufficient.
- **Public read is anon-allowed**: Constitution III defaults RLS to authenticated-only, but Phase 13 (public listing details) and Phase 14 (search) explicitly serve anonymous clients. Phase 8 enables `anon` SELECT on the three locations tables to support those forward-stated phases. This is the second carve-out in the project (the first being whatever Phase 13 lays down for `listings` rows in `status='approved'`).
- **Editorial position with alphabetical fallback**: Locations benefit from editorial ordering (Damascus first as the capital; Aleppo second by population) more than they benefit from a purely deterministic alphabetical sort. Phase 8 introduces a `position INTEGER` column for editorial control; rows without a position fall back to alphabetical-by-`key` (locale-independent, matching Phase 6 RolesListPage). Plan-time decision MAY refine the tie-break rule.
- **The seeded 14 governorates and seat cities are protected like Phase 6 system roles** (Clarifications Session 2026-05-16 Q3): Phase 6 introduced `is_system BOOLEAN` on `roles` plus an `enforce_role_system_immutability` trigger; Phase 8 takes the same posture for `governorates` and `cities` via the analogous `is_system` column (FR-001) plus the analogous `enforce_governorate_system_immutability` / `enforce_city_system_immutability` triggers (FR-007a). The 14 seeded governorates and the seeded seat cities are inserted with `is_system=true`; the protection is enforced server-side (DELETE refused; `key` UPDATE refused) AND mirrored client-side (the in-app surface omits the Delete and rename-key affordances on those rows). Defense-in-depth: even a direct SQL DELETE through Supabase MCP `execute_sql` with an admin JWT is refused.
- **Areas have no protected seed**: The plan describes only "a starter set of areas" — an editorial scaffold, not an authoritative inventory. Every area row is fully editable, deactivatable, and deletable by an admin holding `locations.manage`, regardless of whether it was seeded.
- **Audit trigger pattern carries forward from Phase 7**: Phase 7 (US6) established that every new admin-curated catalog table gets attached audit triggers via Phase 4's unchanged `log_audit()`. Phase 8 follows the same pattern with the same action-key shape (`<entity>.<verb>`) and the same TG_ARGV[0] convention.
- **No optimistic locking on locations writes**: Unlike Phase 7's `mutate_role` (which uses `roles.updated_at` for concurrent-edit safety), Phase 8 does NOT introduce optimistic locking. The locations catalog is low-write, infrequently-edited, and the cost of last-write-wins is bounded by the audit trail (US7).
- **The first super_admin / first admin already exists**: Phase 8 is admin-facing only on the write path. The Phase 6 backfill migration already promoted the existing Phase 5 admin to the `admin` role with `locations.manage`. The Phase 7 first-super_admin bootstrap is independent of Phase 8 and not required for Phase 8 to ship.
- **Future listings-table FKs will be RESTRICT, not CASCADE**: When Phase 10 introduces `listings.city_id` and `listings.area_id`, those FKs MUST be `ON DELETE RESTRICT` (with `ON DELETE SET NULL` acceptable for `area_id` since area is optional). This is forward-stated in Phase 8 so Phase 10's plan honors it; Phase 8 itself does NOT create the listings table.
- **No geographic coordinates in Phase 8** (Clarifications Session 2026-05-16 Q1): The Phase 8 schema does NOT introduce `latitude` / `longitude` / `bbox` columns on `governorates`, `cities`, or `areas`. Phase 15 (Map view) is expected to use per-listing coordinates carried by the Phase 10 `listings` table; if Phase 15 later needs a "city center" pin for a browse-by-city affordance, it adds the columns via a non-breaking follow-up migration. This keeps the Phase 8 seed authoring scope bounded to bilingual `display_name` plus `key` plus `position` — no unsourced coordinate lookup work.
