# Feature Specification: Currencies & Exchange Rates

**Feature Branch**: `009-currencies`
**Created**: 2026-05-17
**Status**: Draft (clarifications closed)
**Input**: User description: "Phase 9 — Currencies & exchange rates. Goal: Multi-currency price storage + admin-managed exchange rates + user-preferred display currency. Backend: migrations `0014_create_currencies.sql`, `0015_create_exchange_rates.sql`; seed USD + SYP rows; Edge Function `update_exchange_rate` (insert-only, audit-logged); policies. Frontend: `lib/features/currencies/` admin pages (currency list, exchange-rate history, set new rate); `lib/shared/domain/value_objects/money.dart` + `MoneyFormatter` utility; profile/settings page extended with display-currency toggle. Acceptance: admin sets USD → SYP rate, subsequent listing prices are convertible; a USD listing displays its SYP equivalent when display currency = SYP, but the stored row never changes; old rates are visible in history. Authored per docs/IMPLEMENTATION_PLAN.md §Phase 9."

> **Plan override note**: The user's Session 2026-05-17 clarifications (Q1) explicitly reject display-time currency conversion. Phase 9 therefore deliberately deviates from the implementation plan's third headline acceptance criterion ("A USD listing displays its SYP equivalent when display currency = SYP"). Per the resolved Q1, listings instead render in whichever currency the publisher entered; the viewer's `user_preferences.display_currency` is used only to pick among multiple `listing_prices` rows when a publisher entered prices in more than one currency. Exchange rates remain stored and admin-managed for record-keeping, regulatory tracking, and possible future re-introduction of conversion — but no UI surface in Phase 9 performs an FX multiplication.

## Clarifications

### Session 2026-05-17

- **Q1 — Display-time conversion vs publisher-entered currency**: When a viewer's `display_currency = SYP` but a listing only has a USD `listing_prices` row, what does the viewer see? → **A: No conversion ever.** Listings always render in the currency the publisher entered. Exchange rates are stored for admin record-keeping only and never applied to user-facing displays. When a listing has multiple `listing_prices` rows (e.g., one USD + one SYP), the viewer's `display_currency` preference picks the matching row; when no matching row exists, the listing's primary row is rendered unchanged in its native currency. This overrides the implementation plan's third headline acceptance criterion. The implication for `MoneyFormatter` is significant: it formats amounts (digit grouping, RTL Arabic-Indic digits, currency symbol placement) but never multiplies by an exchange rate.
- **Q2 — Inverse rate storage**: When an admin sets `USD → SYP = 15000` via `update_exchange_rate`, how is the inverse (`SYP → USD`) represented in `public.exchange_rates`? → **C: Auto-derive inverse server-side.** The Edge Function atomically INSERTs two rows: the admin-authored row and a derived row with `rate = 1 / admin_rate` (rounded to `NUMERIC(18, 6)`) marked `source = 'auto-derived from <admin row uuid>'`. The history page (US6) lists both with the derived one visually tagged. One admin action produces two queryable rows, the derived precision is documented in `source`, and the audit log captures both INSERTs as separate `exchange_rate.updated` events. Note: because Q1 chose "no conversion ever", the auto-derived inverse is not used to drive any user-facing display in Phase 9; it exists for completeness of the historical record and for any later phase that may introduce conversion semantics.
- **Q3 — Conversion locus (no longer applicable)**: The original spec posed a question about whether Phase 9 should ship a backend view / RPC that pre-computes converted amounts, or whether conversion is strictly client-side. The Q1 resolution makes Q3 vacuous — no conversion is performed anywhere in Phase 9, so there is no locus to choose. Phase 14 (Search & filters) will own any future cross-currency filtering UX; the implementation plan's forward-statement that Phase 14 may add such filtering remains intact and unaffected by Phase 9's no-conversion stance.
- **Q4 — `listing_prices` uniqueness per currency**: Should Phase 10's `listing_prices` table enforce `UNIQUE(listing_id, currency_code)` so a listing has at most one price row per currency? → **A: Yes, enforce uniqueness.** This is a forward-stated Phase 10 contract that Phase 9's FR-019a row-selection rule relies on. With the constraint in place, FR-019a is fully deterministic: "find the row where `currency_code = viewer's preference`; if no match, fall back to the row where `is_primary=true`." No tiebreaker is needed because no two rows can share `(listing_id, currency_code)`. The "asking price vs. minimum acceptable" use case — if it ever surfaces — is handled by a separate column on `listings` or `listing_details` (e.g., `negotiable BOOLEAN`, `minimum_price NUMERIC`), not by duplicate `listing_prices` rows.
- **Q5 — Backdating bounds for `effective_at`**: How far back can an admin backdate an exchange rate via `update_exchange_rate`? → **B: Symmetric 24-hour confirmation gate.** Any submission whose `effective_at` is more than 24 hours in the past (relative to `now()` at submit time) triggers the same confirmation dialog already required by FR-017 for future-dating more than 24 hours ahead. Backdating remains permitted (to support legitimate "correcting yesterday's late entry" cases), but accidental year-old typos are caught by the gate. The Edge Function does NOT hard-refuse backdated submissions; the gate is client-side UX plus the audit-log row's `actor_user_id` + `effective_at` discrepancy provides traceability. There is no project-epoch hard cap.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Public clients read the seeded currencies catalog on first launch (Priority: P1)

A first-time visitor to the AlNujom app — including anonymous (not-yet-signed-in) clients on the public home, the search screen, and the listing-details screen — reads the currencies catalog at launch. The catalog presents both `USD` (US Dollar) and `SYP` (Syrian Pound) as the v1 seed; each row carries a stable 3-letter `code`, a bilingual `name_ar` / `name_en`, a `symbol` (e.g., `$`, `ل.س`), a `display_decimals` rule (SYP = 0, USD = 2), an `is_active` flag (defaulting to `true`), and a `sort_order` editorial position (SYP first as the local currency, USD second). Reading the catalog is fast enough to populate downstream consumers — the Phase 10 listing-form currency dropdown (publisher picks which currencies to enter prices in), the Phase 13 public listing-details price block (renders all entered prices), the Phase 14 search filter's currency selector (filter by currency when comparing prices), the profile/settings display-currency toggle (US4) — without a perceptible blocking gap. A signed-in regular user, moderator, and admin see exactly the same rows because currencies are global reference data, not per-user.

**Why this priority**: P1 because every later price-aware feature — listing creation (Phase 10's `listing_prices` rows, which require a `currency_code` FK to this table), public listing details (Phase 13 price block), search filters (Phase 14 currency selector), the user-preferred display-currency toggle (US4 of this phase) — depends on the catalog existing and being readable by anonymous + authenticated clients. Constitution III's RLS-by-default posture requires an explicit anon SELECT carve-out for global reference data; this story exercises that carve-out for the new `currencies` table (analogous to the carve-out Phase 8 introduced for `governorates` / `cities` / `areas`). Without this story, every later price-aware story is blocked.

**Independent Test**: Apply the Phase 9 migrations to the remote Supabase project via Supabase MCP `apply_migration`. Query `SELECT code, name_ar, name_en, symbol, display_decimals, is_active, sort_order, is_system FROM public.currencies ORDER BY sort_order ASC` — confirm row 1 is `SYP` (`name_ar='ليرة سورية'`, `name_en='Syrian Pound'`, `symbol='ل.س'`, `display_decimals=0`, `is_system=true`, `is_active=true`) and row 2 is `USD` (`name_ar='دولار أمريكي'`, `name_en='US Dollar'`, `symbol='$'`, `display_decimals=2`, `is_system=true`, `is_active=true`). 5. **Given** a row's locale-specific name column for the active locale is empty or missing (unlikely for the v1 seed but defensive for future admin-added codes), **When** the smoke-test surface renders that row, **Then** the widget falls back first to the other locale's value, then to the `code` itself as the last-resort label (no row ever renders blank).

### User Story 3 — Admin sets a new USD → SYP exchange rate via Edge Function with auto-derived inverse (Priority: P1)

A signed-in user holding `currencies.manage` taps the Currencies tile, opening `CurrenciesListPage`. The page lists both seeded currencies plus any custom currencies an admin has added later (e.g., EUR, TRY). Each row shows the currency's `code`, its active-locale `name`, its `symbol`, its `is_active` badge if deactivated, and the *latest* effective rate against every other active currency (a compact "1 USD = 15,000 SYP" line per currency pair) — these rates are displayed for **admin awareness only**; they do not drive any listing-price conversion (per Q1). The page exposes a "Set new rate" affordance that opens `SetExchangeRatePage`. The form requires `base_currency` (dropdown of active currencies), `target_currency` (dropdown of active currencies, must differ from base), `rate` (positive numeric, up to 6 decimal places of precision per Assumption 4), `effective_at` (defaults to `now()` but admins may post-date or future-date), and an optional `source` text field for a human note (e.g., "Central Bank rate, 2026-05-17"). On submit, the form calls the `update_exchange_rate` Edge Function with those parameters; the Edge Function (a) checks `currencies.manage`, (b) validates the inputs, (c) atomically INSERTs **two** rows into `public.exchange_rates`: the admin-authored row with `set_by = auth.uid()` and `source` carrying the admin's note, AND a derived row with `rate = 1 / admin_rate` rounded to `NUMERIC(18, 6)`, `set_by = auth.uid()`, and `source = 'auto-derived from <admin row uuid>'` (per Q2). The Edge Function NEVER updates an existing `exchange_rates` row — history is immutable, and the latest rate for each pair is "the most-recently-effective row" computed at query time. After submission, the admin returns to `CurrenciesListPage`; the displayed "1 USD = … SYP" line AND its inverse "1 SYP = … USD" both reflect the new rate.

**Why this priority**: P1 because the implementation plan's first headline acceptance criterion — "Admin sets USD → SYP rate" — is realized by this story; the Edge Function pattern (permission check + audit log + insert-only with auto-derive) is also the precedent for every later admin-mutation surface that needs strong write-side guarantees, so getting it right here de-risks Phases 12 (listing approval) and 21 (ads). Even with the Q1 decision that ratings are not user-facing, the admin record-keeping requirement remains material: when admins (or a future regulator-facing report) need to know "what was the exchange rate on date X", the history must exist and be queryable.

**Independent Test**: Sign in as the Phase 5 admin on the reference device. Open the admin home → "Currencies" → "Set new rate". Pick `base_currency = USD`, `target_currency = SYP`, `rate = 15000`, leave `effective_at` at default, leave `source` blank. Tap Submit. Confirm the form returns success and navigates back to `CurrenciesListPage`. Confirm the USD row's "1 USD = … SYP" line now displays "1 USD = 15,000 SYP" in the active-locale numerals AND the SYP row's "1 SYP = … USD" line displays the rounded auto-derived inverse "1 SYP = 0.000067 USD". From a desktop, query via Supabase MCP `execute_sql`: `SELECT id, base_currency, target_currency, rate, effective_at, set_by, source FROM public.exchange_rates WHERE (base_currency='USD' AND target_currency='SYP') OR (base_currency='SYP' AND target_currency='USD') ORDER BY effective_at DESC, source ASC` — confirm exactly **two** rows exist; one is the admin-authored row (`source` IS NULL or the admin's note), the other is the derived row with `source LIKE 'auto-derived from %'`; both share the same `set_by` and approximately-same `effective_at` (within microseconds since the Edge Function INSERT is atomic). Query `SELECT * FROM public.audit_logs WHERE action='exchange_rate.updated' ORDER BY created_at DESC LIMIT 2` — confirm two audit rows exist, one per INSERT. Set a second rate, this time USD → SYP = 15500, effective_at = now()+1 hour. Confirm `SELECT count(*) FROM public.exchange_rates WHERE base_currency='USD' AND target_currency='SYP'` returns 2 (history preserved for USD → SYP) and `count(*)` for SYP → USD also returns 2 (history preserved for the derived inverse).

**Acceptance Scenarios**:

1. **Given** an admin session holding `currencies.manage`, **When** they submit a valid `update_exchange_rate` request via the form, **Then** the Edge Function INSERTs exactly **two** new rows into `public.exchange_rates` atomically — the admin-authored row and the auto-derived inverse — and returns success. The admin UI navigates back to the currency list with the new rate visible on both the base and target currency rows.
2. **Given** any submission to `update_exchange_rate`, **When** the Edge Function commits the two rows, **Then** exactly **two** `audit_logs` rows are emitted (one per INSERT), both with `action='exchange_rate.updated'`, both with `actor_user_id=auth.uid()`, and `after_state` carrying each inserted row's JSON.
3. **Given** any submission where `base_currency = target_currency`, **When** the Edge Function validates inputs, **Then** the request is rejected with HTTP 400 and a localized "base and target currency must differ" error; no row is inserted.
4. **Given** any submission where `base_currency` or `target_currency` is not present in `public.currencies` (i.e., the admin somehow targeted a code the system does not know), **When** the Edge Function validates inputs, **Then** the request is rejected with HTTP 400 and a localized "unknown currency code" error; no row is inserted. The foreign-key constraint on `exchange_rates.base_currency` and `exchange_rates.target_currency` would also reject this server-side.
5. **Given** any submission where `rate <= 0`, **When** the Edge Function validates inputs, **Then** the request is rejected with HTTP 400 and a localized "rate must be positive" error; no row is inserted. The `CHECK (rate > 0)` constraint on `exchange_rates.rate` would also reject this server-side.
6. **Given** a session NOT holding `currencies.manage`, **When** it attempts to call `update_exchange_rate`, **Then** the Edge Function returns HTTP 403 and no row is inserted; the RLS policy on direct INSERT against `public.exchange_rates` would also deny.
7. **Given** the admin has already set a USD → SYP rate of 15000 yesterday, **When** they set a new USD → SYP rate of 15500 today, **Then** the prior rows are NOT updated or deleted — two new rows are INSERTed (admin-authored + derived inverse) and the historical rows remain visible in `ExchangeRateHistoryPage` (US6). The "latest rate" computation is "the row with the largest `effective_at` value that is ≤ `now()` for the given (base, target) pair."
8. **Given** the admin-set rate is `15000.000000` (exact NUMERIC(18,6)), **When** the Edge Function computes the inverse, **Then** the derived rate is `0.000067` (i.e., `1 / 15000` rounded half-to-even to 6 decimal places per Assumption 4); the precision-loss tradeoff is documented in the derived row's `source` text and visually flagged on the history page (US6 acceptance scenario 4).

### User Story 4 — User picks their preferred display currency (used to pick among publisher's prices) (Priority: P1)

A signed-in user — `user`, `owner`, `agent`, `agency_admin`, `moderator`, admin, or any role — opens their profile/settings page (the existing Phase 5 surface, extended in this phase). The page exposes a new "Preferred currency" toggle (a labeled segmented control or dropdown), seeded with the active `currencies` rows: SYP and USD by default, plus any custom-added currencies. The currently-selected value reflects the user's `user_preferences.display_currency` column (defaulting to `'SYP'` per the Phase 4 migration). Tapping a different option updates `user_preferences.display_currency` to the new code. This preference is consumed by every listing-price rendering surface (Phase 13 cards, Phase 14 search results, Phase 15 map popovers) to **pick which `listing_prices` row to display** when a publisher has entered prices in more than one currency: if a row exists whose `currency_code` matches the viewer's preference, that row's amount is rendered in its native currency; if no matching row exists, the listing's `is_primary=true` row is rendered unchanged in its publisher-entered currency. There is **no exchange-rate conversion at any point** (per Q1) — the preference only routes among existing publisher-entered prices. Switching the toggle never alters any `listing_prices` row — publisher-entered prices are immutable across the read path per the cross-cutting "Multi-currency confusion" risk mitigation in the implementation plan §17.

**Why this priority**: P1 because without this preference, the system has no way to disambiguate when a publisher has entered both USD and SYP prices for the same listing — every reader would see the primary row regardless of personal preference. Constitution V's Arabic-first stance suggests the default is `'SYP'`, which the Phase 4 migration already encodes.

**Acceptance Scenarios**:

1. **Given** the user's profile/settings page renders, **When** the page mounts, **Then** the "Preferred currency" toggle is visible with one option per `is_active=true` row in `public.currencies`, ordered by `sort_order ASC`, and the currently-selected option matches the user's `user_preferences.display_currency` column.
2. **Given** the toggle is on `'SYP'`, **When** the user taps `'USD'`, **Then** `user_preferences.display_currency` is updated to `'USD'` via an authenticated UPDATE that satisfies the existing self-only RLS policy on `user_preferences`, and the next render of any listing-card surface reflects the new preference per the row-selection rule.
3. **Given** the user toggles their preferred currency, **When** the UPDATE commits, **Then** no `listing_prices` row is mutated (verifiable: `SELECT count(*) FROM public.listing_prices` is unchanged before and after the toggle).
4. **Given** the user's previously-selected preferred currency has been deactivated by an admin (`currencies.is_active=false`) while the user was offline, **When** the user signs in and the profile page renders, **Then** the toggle gracefully falls back to the first active currency by `sort_order ASC` (typically SYP) and the displayed surfaces re-render against that fallback per the row-selection rule. The deactivated currency is NOT offered as a selectable option.
5. **Given** a user has not yet visited the profile page since the Phase 4 row was auto-provisioned with the default `'SYP'`, **When** they first see any listing-card surface, **Then** listings whose `listing_prices` includes a SYP row render that SYP row; listings whose `listing_prices` only includes other currencies render the primary row in its publisher-entered currency (the Phase 4 default `'SYP'` carries through end-to-end with no upgrade migration needed).

### User Story 5 — Listing prices render in the publisher's entered currency (no conversion) (Priority: P1)

When any user — anonymous or signed-in — views any surface that renders listing prices (the home listings grid, the listing-details price block, the listing-form preview, the favorites list, the search results), each listed price is rendered in the **currency the publisher entered**. For a listing whose `listing_prices` rows are `[{amount: 50000, currency: 'USD', is_primary: true}]`, every viewer sees `$50,000` (or `٥٠٬٠٠٠ $` in Arabic locale) regardless of their `user_preferences.display_currency` preference. For a listing whose `listing_prices` rows are `[{amount: 50000, currency: 'USD', is_primary: true}, {amount: 750000000, currency: 'SYP', is_primary: false}]`, the displayed row is chosen by the viewer's preference per US4's row-selection rule: a SYP-preferring viewer sees `750,000,000 ل.س`; a USD-preferring viewer sees `$50,000`; an anonymous viewer with no preference uses the device fallback per Assumption 9. The listing's `listing_prices` rows are **never** mutated by any rendering surface — publisher-entered prices are immutable across the read path. There is no FX multiplication anywhere — `MoneyFormatter` formats the picked row's amount in the picked row's currency, applying the currency's `display_decimals` rule and the active locale's digit form, thousands separator, and symbol position.

**Why this priority**: P1 because this is the user-visible payoff of the entire phase: viewers see prices in real, publisher-entered currencies — not in a model-computed approximation. The user's Q1 decision makes this story the manifestation of the project's posture toward currency: respect what publishers actually enter; do not silently translate. Constitution VII (Dynamic Roles & Permissions) is preserved indirectly: even though Phase 9 does no conversion, the `currencies` catalog and `exchange_rates` history remain data-driven and admin-editable, not hardcoded.

**Independent Test**: Once Phase 10 lands (the listing form ships `listing_prices` rows), or via a temporary smoke-test screen for Phase 9 that emulates a listing-price card, render a card whose primary price is `{amount: 50000, currency: 'USD'}`. Set the user's preferred currency to `'USD'` via US4. Confirm the card shows `$50,000` (English locale) or `٥٠٬٠٠٠ $` (Arabic locale). Toggle to `'SYP'`. Confirm the card **still** shows `$50,000` in its native USD currency — there is no conversion. Now create a second test listing with both `{amount: 50000, currency: 'USD'}` AND `{amount: 750000000, currency: 'SYP'}`. With the user's preference at `'SYP'`, confirm the card now shows `750,000,000 ل.س` (the SYP row was picked). Toggle to `'USD'`. Confirm the card shows `$50,000` (the USD row was picked). From a desktop, run `SELECT id, amount, currency_code FROM public.listing_prices WHERE listing_id IN (<two test listing ids>) ORDER BY listing_id` — confirm all rows are present with their original amounts and currencies; nothing was mutated by the toggle.

**Acceptance Scenarios**:

1. **Given** a listing's `listing_prices` carries exactly one row `{amount: 50000, currency_code: 'USD', is_primary: true}`, **When** any viewer (regardless of their `display_currency` preference) opens any listing-card surface, **Then** the card displays `$50,000` (English locale) or `٥٠٬٠٠٠ $` (Arabic locale) — the USD row is rendered unchanged in its native currency. No conversion is applied because no other currency-row exists.

### User Story 7 — MoneyFormatter renders RTL Arabic digits, currency symbols, and locale-appropriate grouping (Priority: P1)

The shared utility `MoneyFormatter` (defined under `lib/shared/domain/value_objects/money.dart` plus a presentation-layer formatter — the exact split between value object and formatter is a Phase 9 plan-time decision) renders monetary amounts in the active locale. **The formatter never performs FX conversion** (per Q1) — it takes an amount in a specific currency and renders that amount in that currency, full stop. Concretely: in Arabic locale (`ar`), the formatter produces strings like `٧٥٠٬٠٠٠٬٠٠٠ ل.س` — RTL Arabic-Indic digits (`٠١٢٣٤٥٦٧٨٩`), Arabic thousands separator (`٬`, U+066C), suffix-position currency symbol (`ل.س` for SYP, `$` for USD when used by an Arabic speaker who hasn't switched to English), and right-to-left text direction. In English locale (`en`), the formatter produces strings like `$750,000,000` — Latin digits, ASCII comma separator (`,`), prefix-position currency symbol for USD, suffix-position for SYP (rendered as the ASCII code `SYP` when the symbol `ل.س` is inappropriate for an English UI context per Assumption 7). Negative amounts (only used in administrative contexts — listing prices are never negative) render with the minus sign in the locale-appropriate position. Zero amounts render as the locale's zero with the currency symbol — never blank. The formatter takes a single `Money` value object input (`{amount: Decimal, currency: Currency}`) and a display-context tuple (`{locale: Locale}`); the value object guarantees the amount is non-null and the currency code is one the system knows. Internally, formatting uses Dart's `intl` `NumberFormat.currency` with a custom symbol override (because the Arabic SYP symbol `ل.س` is not in ICU's default symbol set for `ar_SY` for the v1 ICU bundle), and rounding to the currency's `display_decimals` (Assumption 5) using banker's rounding (half-to-even).

**Why this priority**: P1 because every price-rendering surface across the entire app — Phase 10 listing form preview, Phase 13 public listings grid, Phase 13 listing details, Phase 14 search results, Phase 15 map popovers, Phase 16 inquiry forms, the admin currency list itself — flows through this formatter. A broken formatter produces broken UI across half the app; a correct formatter is a quiet, invisible foundation. Constitution V (Arabic-first localization) requires the Arabic numeral and symbol treatment, which is not standard ICU behavior and must be explicit.

**Independent Test**: Open the device on the reference Infinix Note 8 with locale set to Arabic. Open the admin currency list (US3 sub-flow). Confirm the rate line for the USD row reads "1 دولار أمريكي = ١٥٬٠٠٠ ليرة سورية" (or per the plan-time exact wording template). Confirm the digits are Arabic-Indic, the separator is `٬`, the symbol position is suffix, and the text direction is RTL. Switch the locale to English. Confirm the same line re-renders as "1 US Dollar = 15,000 Syrian Pound" with Latin digits, ASCII comma separator, suffix position for the SYP descriptor, LTR direction. Now exercise the plan-time-locked golden-case inputs by manually opening a smoke-test screen that renders each input — verify each output string matches the locked expected output captured at plan time (see Assumption 13 for the manual-verification path that substitutes for automated golden tests per the user's project-wide directive).

**Acceptance Scenarios**:

1. **Given** an Arabic locale (`ar`) and an input `{amount: 750_000_000, currency: SYP}`, **When** the formatter produces the output, **Then** the string is `٧٥٠٬٠٠٠٬٠٠٠ ل.س` — Arabic-Indic digits, Arabic thousands separator, suffix-position symbol, RTL direction.
2. **Given** an English locale (`en`) and the same input, **When** the formatter produces the output, **Then** the string is `750,000,000 SYP` — Latin digits, ASCII comma separator, suffix-position symbol (SYP has no widely-recognized prefix glyph in English context per Assumption 7).
3. **Given** an input `{amount: 50_000, currency: USD}`, locale `en`, **When** the formatter renders, **Then** the output is `$50,000` — Latin digits, ASCII comma, prefix-position `$`.
4. **Given** the same USD input with locale `ar`, **When** the formatter renders, **Then** the output is `٥٠٬٠٠٠ $` — Arabic-Indic digits, Arabic thousands separator, suffix-position `$` (per the Arabic typographic convention that even Latin currency symbols are placed after the amount when surrounded by Arabic text per Assumption 7).
5. **Given** an input whose amount has more fractional digits than the currency's `display_decimals` rule (e.g., `{amount: 49_999.997, currency: USD}` with `display_decimals=2`), **When** the formatter renders, **Then** the displayed amount is rounded half-to-even to the currency's `display_decimals` (`$50,000.00` in this case). The underlying `Money` value object is unchanged.
6. **Given** a zero amount input `{amount: 0, currency: SYP}`, **When** the formatter renders, **Then** the output is `٠ ل.س` (Arabic) or `0 SYP` (English) — never blank.
7. **Given** the same value object passed to the formatter twice with identical locale, **When** both calls render, **Then** both outputs are byte-identical (the formatter is deterministic; no implicit time, no random, no global state).
8. **Given** an attempted call to the formatter with a `rate` parameter or any other FX-related argument (a contract-violation attempt), **When** the call is made, **Then** the formatter's public signature does not accept such a parameter — the API surface is intentionally narrowed to "format an amount in its own currency for a given locale" per Q1. Any later attempt to re-introduce conversion belongs to a future spec, not Phase 9.

### User Story 8 — Every currency and exchange-rate mutation emits an audit-log row (Priority: P2)

Phase 7 (US6) and Phase 8 (US7) established the precedent of attaching audit triggers to every new admin-curated catalog table. Phase 9 extends the precedent: INSERT / UPDATE / DELETE trigger pairs attach to `public.currencies` (the catalog table) via Phase 4's reusable `log_audit()` function (the R-05 reusability invariant — `log_audit` is unchanged for a *sixth* time, across Phases 4, 5, 6, 7, 8, and now 9). The action keys are `currency.created` / `currency.updated` / `currency.deleted`. For `public.exchange_rates`, the table is **insert-only by RLS** (FR-008): rows are never UPDATEd or DELETEd through the in-app surface; therefore only an INSERT trigger attaches, emitting `exchange_rate.updated` (matching the implementation-plan §9.4 wording — the verb is "updated" because the user-perceived intent is "the rate has been updated", even though the table mechanically appends a new row). Because the `update_exchange_rate` Edge Function performs **two** INSERTs per admin submission per Q2 (the admin-authored row + the auto-derived inverse), **two** `exchange_rate.updated` audit rows are emitted per admin action. Each audit row carries `actor_user_id` for in-app mutations (set by the Edge Function as `auth.uid()`, applied to both INSERTs) and NULL for system mutations.

**Why this priority**: P2 because audit coverage is a compliance + observability concern, not a feature-correctness concern. But Constitution III (Security-First Supabase) makes audit-trail completeness for admin mutations a project-wide expectation, and the Phase 7 / Phase 8 precedent established the pattern. The Q2 auto-derive inverse adds a small wrinkle: an admin who sets one rate produces two audit rows; an auditor querying "what did the admin do" sees both rows and the `source` field distinguishes the authored from the derived.

**Independent Test**: After applying the Phase 9 migrations, run via Supabase MCP `execute_sql`:

### Edge Cases

- **Anonymous read on app launch**: Constitution III's RLS-by-default posture means every table must have an explicit SELECT policy. The Phase 9 spec deliberately enables `anon` and `authenticated` SELECT on both `currencies` and `exchange_rates` — they are global reference data. Anonymous viewers don't actively read exchange rates in any user-facing surface (per Q1), but Phase 13 (Public listing details) MAY query `currencies` to resolve symbol/name for the publisher's price-row currency. This is the third project-wide carve-out from the "authenticated-only" default — Phase 8 introduced two (governorates / cities / areas as one group); Phase 9 adds the currencies tables.
- **Insert-only history on `exchange_rates`**: Per FR-008, the table is insert-only by RLS — UPDATE and DELETE policies do not exist (or exist only as `WITH CHECK (false)` deny-all). Historical rows are immutable. The "latest rate" for any (base, target) pair is computed at query time as the row with the largest `effective_at` value ≤ `now()` — this is used by the admin currency list's "1 USD = X SYP" awareness display (US3) but NOT by any user-facing rendering (per Q1). The contrast with `governorates` / `cities` / `areas` / `currencies` (which all support UPDATE) is deliberate, because rate corrections via UPDATE would silently rewrite history.
- **Multi-currency listing-price-row selection** (US4 + US5): When a listing has multiple `listing_prices` rows in different currencies, the row to display is picked by the viewer's `display_currency` preference: match-by-currency-code if a matching row exists, else the row with `is_primary=true` in its native currency. No conversion is ever applied. The publisher controls which currencies they want to expose; the viewer controls which (among those) they prefer to see. Phase 10 will own the listing-form UX of letting publishers enter multi-currency prices; Phase 9 ensures the row-selection rule is in place.
- **Missing display-currency match**: When a viewer's `display_currency='SYP'` but a listing's `listing_prices` rows include only USD, the viewer sees the USD primary row unchanged in USD. There is no fallback to conversion (per Q1). The "rate not available" hint that the original spec contemplated is REMOVED — no hint is needed because no conversion is being attempted.
- **Currency deactivation while listings reference it**: An admin who deactivates a currency (`is_active=false`) via the form does NOT break any listing whose primary price is in that currency — the listing's price-rendering surface continues to display the native amount; only the user-facing toggle (US4) removes the currency from selection, and the listing form (Phase 10) removes it from publisher selection for new prices. If admins later want to remove a currency entirely (DELETE), the FK from Phase 10's `listing_prices.currency_code` (forward-stated as `ON DELETE RESTRICT` per Assumption 10) AND the FK from `exchange_rates` history (FR-006) block the DELETE — admins must deactivate instead.
- **Seed protection (`is_system=true`)**: Following the Phase 6 / Phase 8 precedent, the seeded `USD` and `SYP` rows are inserted with `is_system=true`, and an `enforce_currency_system_immutability` trigger refuses any `DELETE` on `is_system=true` rows AND refuses any `UPDATE` to the `code` column on `is_system=true` rows. Admins MAY still UPDATE `name_ar`, `name_en`, `symbol`, `sort_order`, `is_active`, and `display_decimals` on a `is_system=true` row. Defense-in-depth: even a direct SQL DELETE via Supabase MCP `execute_sql` with an admin JWT is refused. This pattern mirrors Phase 6's `enforce_role_system_immutability` and Phase 8's two location triggers.
- **Concurrent rate-set by two admins**: Two admins simultaneously calling `update_exchange_rate` for the same pair is rare but possible. The `exchange_rates` table is append-only, so both INSERTs succeed with sequential `effective_at` values; the "latest rate" computation returns whichever has the larger `effective_at`. Both admins' submissions each produce two rows (admin + auto-derived inverse), so four rows total enter the table from two concurrent calls. No optimistic locking is required because there is no shared mutable state — each admin's rate is a fresh pair of rows. The audit log captures all four writes per US8.
- **Rate precision and rounding**: `exchange_rates.rate` is stored as `NUMERIC(18, 6)` per Assumption 4 — 12 integer digits, 6 fractional digits. This handles SYP-scale rates (15000+) and USD-scale derived inverses (0.000067 ≈ 1/15000) without overflow. The Q2 auto-derive multiplies-and-rounds at function execution time and persists the derived rate with full precision; the precision-loss tradeoff is documented in the derived row's `source` text (US3 acceptance scenario 8) so an admin querying history can see exactly which row is canonical (admin-authored) versus computed.
- **`profiles.preferred_currency` does not exist in the actual schema**: The implementation plan §6.2 references `profiles.preferred_currency`, but the Phase 5 profile schema never created such a column — the source of truth is `user_preferences.display_currency` per the Phase 4 contract `004-supabase-foundation/contracts/user-preferences-entity.md`. Phase 9 does NOT introduce `profiles.preferred_currency`; the toggle (US4) updates `user_preferences.display_currency` only. No backfill is needed.
- **Custom currencies post-v1**: The schema accepts arbitrary additional codes (EUR, TRY, GBP, etc.) via the in-app admin form; adding a new currency is a single-row INSERT into `public.currencies` and any number of `exchange_rates` rows (each generating its auto-derived inverse). No destructive migration is ever required. The v1 seed is exactly USD + SYP per the implementation plan §8.

## Requirements *(mandatory)*

### Functional Requirements

#### Schema and seed

- **FR-001**: System MUST introduce two new tables in the `public` schema — `currencies` (catalog) and `exchange_rates` (history). Both have RLS enabled with explicit policies per FR-008 and FR-009.
- **FR-002**: `currencies` MUST carry a primary key column `code TEXT PRIMARY KEY` (e.g., `'USD'`, `'SYP'`, `'EUR'`) with a CHECK constraint enforcing exactly 3 uppercase ASCII letters (`code ~ '^[A-Z]{3}$'`), plus columns: `name_ar TEXT NOT NULL`, `name_en TEXT NOT NULL`, `symbol TEXT NOT NULL`, `is_active BOOLEAN NOT NULL DEFAULT true`, `sort_order INTEGER NOT NULL DEFAULT 100`, `is_system BOOLEAN NOT NULL DEFAULT false`, `display_decimals SMALLINT NOT NULL DEFAULT 2` (per Assumption 5), `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`. The `updated_at` column is maintained by Phase 4's reusable `set_updated_at` trigger.
- **FR-003**: `exchange_rates` MUST carry columns: `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`, `base_currency TEXT NOT NULL REFERENCES public.currencies(code) ON DELETE RESTRICT`, `target_currency TEXT NOT NULL REFERENCES public.currencies(code) ON DELETE RESTRICT`, `rate NUMERIC(18, 6) NOT NULL CHECK (rate > 0)`, `effective_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `set_by UUID REFERENCES auth.users(id) ON DELETE SET NULL`, `source TEXT`, `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`. The table also carries a `CHECK (base_currency <> target_currency)` constraint and a composite index on `(base_currency, target_currency, effective_at DESC)` for the latest-rate-lookup query path (used by the admin "1 USD = X SYP" awareness display in `CurrenciesListPage`).
- **FR-004**: System MUST seed exactly two rows into `public.currencies`: `SYP` (`name_ar='ليرة سورية'`, `name_en='Syrian Pound'`, `symbol='ل.س'`, `sort_order=10`, `is_system=true`, `display_decimals=0` per Assumption 5) and `USD` (`name_ar='دولار أمريكي'`, `name_en='US Dollar'`, `symbol='$'`, `sort_order=20`, `is_system=true`, `display_decimals=2`). The seed is idempotent — re-running the migration does not duplicate rows.
- **FR-005**: System MAY seed a starter `USD → SYP` rate pair into `public.exchange_rates` for development convenience (decided at plan time). If seeded, the row pair carries `set_by=NULL`, `effective_at` matching the migration timestamp, `source='seed'` for the admin-direction row, and `source='auto-derived from seed (USD→SYP)'` for the inverse row per Q2. The system MAY skip the seeded rate entirely and require the first admin to set it via US3 — both options are acceptable per the plan, particularly given Q1's no-conversion stance (the seeded rate doesn't drive any user-facing display).
- **FR-006**: `currencies.code` MUST be enforced as the foreign-key target of `exchange_rates.base_currency`, `exchange_rates.target_currency`, the Phase-4-existing `user_preferences.display_currency` (added as a new FK constraint in Phase 9's migration — see FR-019), and the Phase-10-forward `listing_prices.currency_code`. The two `exchange_rates` FKs use `ON DELETE RESTRICT`; `user_preferences.display_currency` uses `ON DELETE SET NULL` per Assumption 6; `listing_prices.currency_code` MUST use `ON DELETE RESTRICT` (forward-stated to Phase 10 per Assumption 10).
- **FR-007**: System MUST attach INSERT / UPDATE / DELETE audit triggers to `public.currencies` using Phase 4's `log_audit()` function unchanged, emitting actions `currency.created` / `currency.updated` / `currency.deleted`. System MUST attach an INSERT-only audit trigger to `public.exchange_rates`, emitting action `exchange_rate.updated`. The triggers MUST be attached BEFORE the seed INSERT statements run in the table-creation migration, so every seeded row produces exactly one `*.created` (or `exchange_rate.updated`) audit row with `actor_user_id=NULL` — mirroring Phase 8 Clarifications Session 2026-05-16 Q5.
- **FR-007a**: System MUST attach an immutability trigger `enforce_currency_system_immutability` on `public.currencies` that refuses any `DELETE` on a row where `is_system=true` AND refuses any `UPDATE` that changes the `code` column on a row where `is_system=true`. The trigger raises `SQLSTATE 42501` with a structured error message; mirrors Phase 6's `enforce_role_system_immutability` and Phase 8's two location triggers. Admins MAY still `UPDATE` `name_ar`, `name_en`, `symbol`, `sort_order`, `is_active`, and `display_decimals` on a `is_system=true` row.

#### Permissions and policies

- **FR-008**: System MUST gate write access to `currencies` and `exchange_rates` behind the `permissions.key='currencies.manage'` key. The write-side RLS policies MUST check `current_user_has_permission('currencies.manage')` (the Phase 6 helper). For `exchange_rates`, ONLY an INSERT policy exists; UPDATE and DELETE policies do not exist (or exist as `USING (false)` deny-all), making the table append-only by design.
- **FR-009**: System MUST allow public SELECT on both tables for both `anon` and `authenticated` roles — currencies and historical rates are global reference data per the Edge Case note.
- **FR-010**: System MUST NOT introduce a new permission key — `currencies.manage` already exists in the Phase 6 catalog and is already mapped to the `admin` and `super_admin` roles per §9.1. Phase 7's `RoleEditorPage` permits attaching `currencies.manage` to any custom role (such as the documented `finance` role).

#### Edge Function

- **FR-012**: System MUST provide an Edge Function `update_exchange_rate` deployed via Supabase MCP `deploy_edge_function`. The function MUST: (a) authenticate the caller's JWT, (b) check `current_user_has_permission('currencies.manage')`, (c) validate inputs (`base_currency` and `target_currency` are 3-letter codes present in `public.currencies`; `base_currency <> target_currency`; `rate > 0`; `effective_at` is a valid ISO 8601 timestamp; `source` is text ≤ 500 chars or null), (d) atomically INSERT **two** new rows into `public.exchange_rates` in a single transaction — the admin-authored row with `(base_currency, target_currency, rate, effective_at, set_by=auth.uid(), source=admin_note)` AND a derived row with `(base_currency=target_currency, target_currency=base_currency, rate=1/admin_rate rounded half-to-even to NUMERIC(18,6), effective_at=admin_effective_at, set_by=auth.uid(), source='auto-derived from <admin_row_uuid>')` per Q2, (e) return HTTP 200 with both inserted rows' JSON. The function MUST NEVER UPDATE or DELETE an existing row in `public.exchange_rates`. On any validation failure, the function MUST return HTTP 400 with a localized error code; on permission failure, HTTP 403; on database failure, HTTP 500. The audit trigger from FR-007 emits the audit rows as a side-effect of the INSERTs — the Edge Function does NOT call `log_audit` directly.

### Key Entities *(include if feature involves data)*

- **Currency**: A monetary unit with a stable 3-letter ISO-style `code` (e.g., `USD`, `SYP`, `EUR`). Displayed via the bilingual `name_ar` / `name_en` columns plus a `symbol` (e.g., `$`, `ل.س`, `€`); ordered editorially via `sort_order INTEGER` (SYP first per local market). `display_decimals SMALLINT` defines how many fractional digits the currency uses at display time (SYP = 0, USD = 2, EUR = 2). `is_active BOOLEAN` toggles whether the currency is offered for user selection (preference toggle and Phase-10 publisher selection). The two seeded rows (`USD`, `SYP`) carry `is_system=true` and are protected from in-app deletion AND from `code`-rename via `enforce_currency_system_immutability`; admin-created rows default to `is_system=false`.
- **ExchangeRate**: A historical record of "1 unit of `base_currency` equals `rate` units of `target_currency`, effective from `effective_at`". UUID primary key, foreign keys to `currencies(code)` for both base and target (both `ON DELETE RESTRICT`); `rate NUMERIC(18, 6)` constrained `> 0`; `effective_at` defaults to `now()` but may be past or future; `set_by` references the admin user (or `NULL` for seeded rows); `source` is an optional human note OR the auto-derive marker `'auto-derived from <uuid>'` per Q2. The table is append-only — historical rows are immutable per FR-008. Each admin call to `update_exchange_rate` produces exactly two rows: the admin-authored row and its auto-derived inverse. Per Q1, the rate is NOT used for any user-facing display in Phase 9; it exists for admin record-keeping.
- **Money** *(domain value object, not persisted as a row in Phase 9 — Phase 10 owns `listing_prices` row persistence)*: An immutable `{amount: Decimal, currency: Currency}` pair flowing through the domain layer. Consumed by every price-rendering surface; produced by Phase 10's listing form and any system path that emits a price. The `Decimal` type is the high-precision arbitrary-decimal type from `package:decimal` to avoid floating-point rounding errors on multi-million SYP amounts. **No `rate` field** — Phase 9 does not convert.
- **UserPreferences.display_currency** *(extended in Phase 9 — not a new entity)*: The existing Phase 4 column on `public.user_preferences` is narrowed in this phase by adding a foreign-key constraint to `public.currencies(code)` with `ON DELETE SET NULL`. The default value remains `'SYP'` per Phase 4 FR-019. The column's semantic name is preserved at the schema level (`display_currency`) for backward compatibility with the Phase 4 migration; the UI label says "Preferred currency" (FR-018) to reflect the actual Q1 semantics.

## Assumptions

- **Bilingual data-label pattern carries forward from Phases 6 and 8**: Phase 6 (`roles.display_name JSONB`) and Phase 8 (`governorates.display_name JSONB` / `cities.display_name` / `areas.display_name`) used a JSONB column with at-least-`ar`-required semantics. Phase 9 takes a slightly different shape — `currencies` uses two TEXT columns (`name_ar`, `name_en`) instead of one JSONB — because the implementation-plan schema (§6.2) prescribes that exact shape, and currencies are a smaller, fixed catalog where the relational-column form is no less expressive than JSONB. The active-locale-fallback rendering convention is preserved (active → other → `code` slug).
- **`currencies.manage` is the only permission key**: Phase 6 §9.1 already mapped `currencies.manage` to `admin` and `super_admin`. Phase 9 does NOT split read vs. write into separate keys, does NOT introduce a per-currency scoping key (e.g., `currencies.usd.edit`), and does NOT introduce a separate `exchange_rates.set` key. The Phase 6 mapping is sufficient. Phase 7's `RoleEditorPage` already supports attaching the key to a custom role (such as the documented `finance` role from §11.3).
- **Public read is anon-allowed**: Constitution III defaults RLS to authenticated-only, but Phase 13 (public listing details) and Phase 14 (search) explicitly serve anonymous clients who need currency-symbol context for rendering `listing_prices` rows. Phase 9 enables `anon` SELECT on `currencies` and `exchange_rates` to support those forward-stated phases. This is the third project-wide carve-out — Phase 8 introduced two (governorates / cities / areas as one carve-out, treated as one decision since they share the rationale); Phase 9 adds the currencies tables.
- **Rate precision**: `exchange_rates.rate` is stored as `NUMERIC(18, 6)` — 12 integer digits, 6 fractional digits. This handles SYP-scale rates (up to ~999,999,999,999) and USD-scale derived inverses (down to ~0.000001 per unit) without overflow. The Q2 auto-derive applies banker's rounding (half-to-even) at this precision; the rounding error is visible in the derived row's `rate` value and documented via the `source` text.
- **`currencies.display_decimals` controls display rounding**: SYP rounds to 0 decimal places (whole SYP only); USD rounds to 2 decimal places (cents); EUR will round to 2; TRY will round to 2. The `display_decimals SMALLINT` column carries the rule per-currency; `MoneyFormatter` reads it. Banker's rounding (half-to-even) is the default rounding mode per the Dart `Decimal` package's `ScaleRoundingMode.halfEven`.
- **`user_preferences.display_currency` FK uses `ON DELETE SET NULL`**: Per FR-019, the FK on `user_preferences.display_currency` is `SET NULL` (not `RESTRICT`) so that an admin's deletion of a custom currency (theoretically — system rows are protected per Assumption Phase 6 / 8 pattern) does not leave orphaned references but also does not cascade-overwrite a user's stored preference with another value. The app-layer fallback (US4 acceptance scenario 4) handles NULL by displaying the first active currency by `sort_order ASC`. In practice, this scenario rarely fires because the seeded USD / SYP rows cannot be deleted.
- **Currency symbol position is locale-driven, not currency-driven**: In Arabic typography, ALL currency symbols (whether Latin like `$` or Arabic like `ل.س`) are placed AFTER the amount because Arabic is right-to-left and the typographic convention treats currency symbols as trailing units. In English, USD's `$` is conventionally placed BEFORE the amount; SYP has no widely-recognized English-context glyph, so it is rendered as the suffix code `SYP`. Phase 9 codifies this in `MoneyFormatter`'s locale-driven symbol-position rule; future currencies (EUR, TRY) follow the same locale rule.
- **Editorial position with `code` fallback**: Currencies benefit from editorial ordering (SYP first as the local market currency, USD second, future EUR/TRY/GBP added in admin's preferred order). Phase 9 introduces `sort_order INTEGER NOT NULL DEFAULT 100`; rows with the same `sort_order` are tie-broken by alphabetical `code` (locale-independent), matching Phase 8's editorial-position convention.
- **Anonymous-viewer currency-preference fallback**: An anonymous (not-signed-in) viewer has no `user_preferences` row and therefore no `display_currency` preference. For US4's row-selection rule, anonymous viewers fall back to the listing's `is_primary=true` row in its native currency — i.e., they see whatever the publisher set as primary. There is no device-level cached fallback in Phase 9; if a future phase wants to remember an anonymous viewer's last-seen currency via `flutter_secure_storage`, it can layer that on without altering the schema.
- **Phase 10 listing-prices FK behavior, uniqueness, and multi-row support**: When Phase 10 ships `listing_prices.currency_code`, the FK MUST be `ON DELETE RESTRICT` — never `CASCADE` and never `SET NULL`. Phase 10 MUST also support 1+ rows per listing with exactly one `is_primary=true` (per implementation plan §8); per Q4, Phase 10 MUST enforce `UNIQUE(listing_id, currency_code)` so each listing has at most one price row per currency, making FR-019a's row-selection rule fully deterministic. The Phase 10 listing form MUST present a multi-currency price entry UI so publishers can choose to enter prices in multiple currencies (e.g., USD + SYP for a high-value sale), with one slot per currency. "Asking vs. minimum acceptable" use cases, if they emerge, MUST be implemented as separate columns on `listings` or `listing_details` (e.g., `negotiable BOOLEAN`, `minimum_price NUMERIC`), NOT as duplicate `listing_prices` rows. These constraints are forward-stated to Phase 10 so its plan honors them.
- **Edge Function deployment**: The `update_exchange_rate` Edge Function deploys via Supabase MCP `deploy_edge_function`. The function lives in `supabase/functions/update_exchange_rate/` per the project layout; its environment variables (`SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`) come from the Supabase platform's automatic injection, NOT from `.env.json` (Supabase Edge Functions and Flutter dart-defines are separate environments).
- **Migration naming follows project convention**: The IMPLEMENTATION_PLAN.md references migration filenames as `0014_create_currencies.sql` / `0015_create_exchange_rates.sql` (descriptive integers), but the actual project uses date-prefixed names (e.g., `20260517120001_create_currencies.sql`) per Phase 8 R-01's carry-forward decision. The plan-time research file will codify exact filenames.
- **No new automated tests — manual UI verification only**: Per the project-wide directive in user memory `feedback_no_new_tests.md`, Phase 9 does NOT introduce new automated unit tests for `MoneyFormatter` despite the implementation plan's reference to "Unit test: MoneyFormatter golden cases (10 fixed inputs → expected strings) in ar + en." Instead, the 10 golden cases are codified in `quickstart.md` as a manual-verification checklist; an engineer renders each input on the smoke-test surface and compares the displayed string against the locked expected output. This deferral is the same posture taken by Phases 5-8 and will revisit after MVP feature-completion. The schema-level invariants (FR-007, FR-008, immutability triggers) are still verified via direct-SQL probes through Supabase MCP `execute_sql`.
- **`profiles.preferred_currency` does not exist**: Per the Phase 4 user-preferences-entity contract, `Profile` does NOT carry locale or currency; `user_preferences.display_currency` is the single source of truth. The implementation plan §6.2's listing of `profiles.preferred_currency` is historical drift in that document and is NOT enacted in the actual schema. Phase 9 does NOT introduce `profiles.preferred_currency`; the profile/settings toggle (US4) writes to `user_preferences.display_currency` only.
- **Plan-override is bounded to Phase 9 only**: The Q1 decision to skip display-time conversion overrides only the implementation plan's third headline acceptance criterion for Phase 9. It does NOT preclude a future phase (e.g., a hypothetical Phase 26 "user-facing FX conversion") from introducing conversion later — `exchange_rates` data is preserved exactly so such a phase can build on the existing record-keeping foundation without backfilling missing rates. The Q2 auto-derive ensures that whenever conversion is later introduced, the inverse direction is already available.
- **Constitution XI (Android-First MVP) constrains the device target**: Every manual acceptance test runs on the Infinix Note 8 (Helio G80, 6 GB RAM, Android 10/11). No iOS / web / desktop target is in scope. The profile-page toggle, the admin pages, and the `MoneyFormatter` output are all evaluated against a 6.78" portrait Android screen with one-handed reach. RTL Arabic rendering is verified by toggling the device locale to Arabic and confirming the digit form, separator glyph, symbol position, and overall text direction match the FR-021 specification.
- **Audit-trigger pattern carries forward**: Phases 7 and 8 each attached new INSERT/UPDATE/DELETE triggers via Phase 4's unchanged `log_audit()`. Phase 9 follows the same pattern with the same action-key shape (`<entity>.<verb>`), the same `TG_ARGV[0]` convention, and the same trigger-before-seed ordering invariant (Phase 8 Clarifications Session 2026-05-16 Q5). The R-05 reusability invariant — `log_audit` unchanged — is preserved for a sixth time.
