# Implementation Plan: Currencies & Exchange Rates

**Branch**: `009-currencies` | **Date**: 2026-05-17 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/009-currencies/spec.md`

## Summary

Phase 9 introduces the project's first monetary catalog: two new tables (`public.currencies`, `public.exchange_rates`) with public-read RLS, `currencies.manage`-gated write RLS, Phase 6-style `is_system` immutability triggers on `currencies`, an insert-only invariant on `exchange_rates`, and Phase 4-style audit-trigger groups on both tables — every artifact applied via Supabase MCP `apply_migration` to the remote Supabase project. The atomic two-row INSERT (admin-authored row + auto-derived inverse per Q2) is implemented as a **SECURITY DEFINER PL/pgSQL RPC** `public.update_exchange_rate(...)`, NOT as a TypeScript Edge Function — the same deviation from the implementation plan's literal wording that Phase 7 made for `mutate_role` (research R-06 carry-forward; the spec's "Edge Function" language is preserved at the FR level for narrative clarity but is implemented as an RPC, per Constitution XII Assumption now also surfaced in `spec.md` Assumptions). The Flutter side adds a new feature folder `lib/features/currencies/` containing three admin pages (`CurrenciesListPage` → `SetExchangeRatePage` → `ExchangeRateHistoryPage`) plus the `Money` domain value object + `MoneyFormatter` utility at `lib/shared/`, and extends the existing Phase 5 profile/settings page with a "Preferred currency" toggle. The Phase 6 `AdminHomePage` gains one new tile "Currencies" gated by `PermissionChecker.has('currencies.manage')`. The seed migration inserts 2 currency rows (USD, SYP — both `is_system=true`) and optionally a starter USD → SYP rate pair (admin row + auto-derived inverse). Verification is manual SQL inspection via Supabase MCP `execute_sql` + `get_advisors` after each migration plus end-to-end manual UI verification on the reference Infinix Note 8 device, all walked by `quickstart.md`.

**Technical approach**: Five Session 2026-05-17 clarifications closed the design space — Q1 (no display-time conversion ever; listings render in publisher-entered currency), Q2 (server-side auto-derive of inverse rates with `source='auto-derived from <uuid>'`), Q3 (conversion locus question vacated by Q1), Q4 (forward-stated `UNIQUE(listing_id, currency_code)` constraint on Phase 10's `listing_prices`), Q5 (symmetric 24-hour client-side confirmation gate for backdated rates mirroring the existing future-dating gate). The Phase 9 backend deliverables collapse into **five new migration files** (parallel to Phase 8's R-01 date-prefix naming), **two new policy files** (`currencies_phase9.sql`, `exchange_rates_phase9.sql` per Phase 6 R-02 inline-bundle-plus-parallel-file pattern), **one new SECURITY DEFINER RPC** `update_exchange_rate` (replaces the literal "Edge Function" of the implementation plan per R-06), **one new feature folder** under `lib/features/currencies/`, **two new shared files** under `lib/shared/` (`money.dart` value object + `money_formatter.dart` presentation utility), **one new tile** on `AdminHomePage`, **three new `go_router` routes** under `/admin/currencies/...`, **one updated profile page** with the preferred-currency toggle, **one new ARB-key cluster** (~25 page/dialog/form/error/badge keys), and **zero new packages in `pubspec.yaml`** (the `decimal` package required by the `Money` value object's `Decimal` field type is added as the single new runtime dependency — see Technical Context Primary Dependencies). Phase 4 R-05 / Phase 6 R-05 / Phase 7 R-05 / Phase 8 R-05 central-helper invariant is preserved a **sixth** time: `current_user_has_permission()` is unchanged; `log_audit()` is invoked unchanged for the two new audit-trigger groups (Phase 4 R-05 reusability invariant preserved across Phases 4/5/6/7/8/9). The Flutter side adds `lib/features/currencies/{data,domain,presentation}/` strictly per Constitution IV; the `domain/` of the new feature is Supabase-free per Constitution IX. **No new automated tests** per the durable session feedback rule (`feedback_no_new_tests.md`); verification is manual SQL via Supabase MCP `execute_sql` + `get_advisors` + manual device walk on the reference Infinix Note 8 against the remote Supabase project.

## Technical Context

**Language/Version**: Dart 3.x on Flutter (latest stable channel) for the app additions; PostgreSQL (Supabase remote, Postgres 15+) for the SQL migrations and the new RPC. **No Edge Function in Phase 9** per Research R-06 — the deviation from the implementation plan's literal "Edge Function `update_exchange_rate`" wording is recorded in spec Assumptions ("Edge Function vs RPC implementation surface") and in research R-06, exactly as Phase 7 did for `mutate_role`. The `update_exchange_rate` mutation lives as a SECURITY DEFINER PL/pgSQL function callable from the Flutter client via `supabase.rpc('update_exchange_rate', params)`.

**Primary Dependencies**: `supabase_flutter` (already in `pubspec.yaml`), `flutter_bloc` (already in), `equatable` (already in), `get_it` + `injectable` (already in — used for DI registration of the new BLoCs, use cases, data sources via codegen), `go_router` (already in — the new `/admin/currencies/...` route guards read from `PermissionChecker.has('currencies.manage')`), `intl` (already in — used by `MoneyFormatter` for `NumberFormat.currency`). **One new runtime package**: `decimal: ^3.0.0` (or the latest 3.x compatible with Dart 3.x) — required by the `Money` value object's high-precision `Decimal amount` field per FR-020 / Assumption 4. The `intl` package's default Arabic locale data covers Arabic-Indic digit rendering (`٠١٢٣٤٥٦٧٨٩`) and the U+066C Arabic thousands separator; the SYP `ل.س` symbol is supplied by `MoneyFormatter` as a custom symbol override (per spec's FR-021 Assumption 7) because ICU's default `ar_SY` locale data does not include it. **Tooling**: Supabase MCP server (`apply_migration`, `execute_sql`, `list_tables`, `list_migrations`, `get_advisors`) is the canonical migration-apply / inspection mechanism — same as Phases 4, 5, 6, 7, 8.

**Storage**: Remote Supabase Postgres project. Phase 9 adds:

- **Two new tables**: `public.currencies` (the catalog) and `public.exchange_rates` (the history).
  - `public.currencies`: `code TEXT PRIMARY KEY CHECK (code ~ '^[A-Z]{3}$')`, `name_ar TEXT NOT NULL`, `name_en TEXT NOT NULL`, `symbol TEXT NOT NULL`, `is_active BOOLEAN NOT NULL DEFAULT true`, `sort_order INTEGER NOT NULL DEFAULT 100`, `is_system BOOLEAN NOT NULL DEFAULT false`, `display_decimals SMALLINT NOT NULL DEFAULT 2 CHECK (display_decimals BETWEEN 0 AND 8)`, `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`. (FR-001, FR-002.)
  - `public.exchange_rates`: `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`, `base_currency TEXT NOT NULL REFERENCES public.currencies(code) ON DELETE RESTRICT`, `target_currency TEXT NOT NULL REFERENCES public.currencies(code) ON DELETE RESTRICT`, `rate NUMERIC(18, 6) NOT NULL CHECK (rate > 0)`, `effective_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `set_by UUID REFERENCES auth.users(id) ON DELETE SET NULL`, `source TEXT CHECK (source IS NULL OR length(source) <= 500)`, `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`. Plus `CHECK (base_currency <> target_currency)`. Plus composite index `(base_currency, target_currency, effective_at DESC)` for the latest-rate lookup. (FR-003.)
- **Two new audit-trigger groups**: triggers on `public.currencies` (INSERT/UPDATE/DELETE → `currency.created` / `currency.updated` / `currency.deleted` — FR-007); on `public.exchange_rates` (INSERT-only → `exchange_rate.updated`). All attached via Phase 4's `log_audit()` reusable trigger function (unchanged for a sixth time across Phases 4/5/6/7/8/9). The triggers are attached BEFORE the seed `INSERT`s in the same migration so the seed produces 2 `currency.created` audit rows (and, optionally, 2 `exchange_rate.updated` rows if FR-005 starter rate is seeded) with `actor_user_id=NULL` (US8 acceptance scenario 6 / Phase 8 Clarifications Q5 carry-forward).
- **One immutability trigger**: `enforce_currency_system_immutability` on `public.currencies` (refuses `DELETE` and refuses `UPDATE` on `code` when `is_system=true`). `exchange_rates` has no `is_system` column and is append-only by RLS, so no immutability trigger is needed there. Pattern mirrors Phase 6's `enforce_role_system_immutability` and Phase 8's `enforce_governorate_system_immutability` / `enforce_city_system_immutability` (FR-007a).
- **One new SECURITY DEFINER RPC**: `public.update_exchange_rate(p_base_currency TEXT, p_target_currency TEXT, p_rate NUMERIC, p_effective_at TIMESTAMPTZ, p_source TEXT) RETURNS JSONB` — performs (a) `current_user_has_permission('currencies.manage')` check (raises `42501` on fail), (b) input validation (raises `22023` on `base = target` or `rate <= 0` or unknown codes — the FK + CHECK constraints would also reject), (c) computes `derived_rate := round(1.0 / p_rate, 6)` using PL/pgSQL `numeric_round_mode = 'banker'` semantics (Postgres NUMERIC half-to-even is the default for `round()`), (d) `INSERT` admin-authored row with `set_by = auth.uid()`, captures the new UUID into `v_admin_row_id`, (e) `INSERT` derived row with `source = format('auto-derived from %s', v_admin_row_id)`, (f) returns a JSONB with both inserted rows. The function's transactional scope is automatic — both INSERTs happen in the single function-call transaction, so the audit-trigger-emitted rows for both INSERTs commit together (Q2 atomicity). Function declared `LANGUAGE plpgsql VOLATILE SECURITY DEFINER SET search_path=public,auth`. (FR-012, Q2.)
- **Two new RLS policy files**: `currencies_phase9.sql` and `exchange_rates_phase9.sql`. Each policy file declares (a) one SELECT policy admitting `anon` AND `authenticated` (currencies and historical rates are global reference data — see Edge Case "Anonymous read on app launch" and forward-statement to Phase 13/14); (b) INSERT/UPDATE/DELETE policies on `currencies` gated by `current_user_has_permission('currencies.manage')`; (c) INSERT-only policy on `exchange_rates` gated by `current_user_has_permission('currencies.manage')` — NO UPDATE policy, NO DELETE policy (the table is append-only per FR-008). (FR-008, FR-009.)
- **One altered existing table**: `public.user_preferences.display_currency` gains a FK constraint `REFERENCES public.currencies(code) ON DELETE SET NULL`, applied AFTER the `currencies` seed runs so the existing default value `'SYP'` already satisfies the FK. The migration MUST NOT modify any existing `user_preferences` row's `display_currency` value during the FK addition. (FR-019.)
- **No new helper functions**. The Phase 6 `current_user_has_permission(TEXT)` helper is reused unchanged. The Phase 4 `log_audit()` and `set_updated_at()` triggers are reused unchanged.

**Testing**: **Manual SQL inspection against the remote Supabase project via Supabase MCP `execute_sql` + `get_advisors` after each migration + manual UI verification on the reference Infinix Note 8 device.** Per the durable session feedback (`feedback_no_new_tests.md`) and the spec's assumptions, this phase introduces NO new automated tests of any kind — including for `MoneyFormatter` despite the implementation plan's literal reference to "Unit test: MoneyFormatter golden cases". The 10 plan-time-locked golden cases are codified in `quickstart.md` as a manual-verification checklist; an engineer renders each input on the smoke-test surface and compares the displayed string against the locked expected output. Build-time validation is preserved: Supabase's static SQL parser at `apply_migration` time catches syntax errors; Flutter's analyzer + the existing Phase 3 localization lint guard validate the new Dart files. Existing Phase 1/2/3/4/5/6/7/8 tests remain in source unchanged.

**Target Platform**: Android 7.0+ (API 24+) for the Flutter side (Constitution XI); Supabase remote Postgres for the backend side. iOS, Web, desktop NOT a target.

**Project Type**: Mobile app + backend. Phase 9 introduces the third new feature-folder top-level since Phase 5/6 (Phase 7's `lib/features/super_admin/`, Phase 8's `lib/features/locations/`, and now Phase 9's `lib/features/currencies/`). It also adds a single new tile to the Phase 6 `AdminHomePage`, adds a preferred-currency toggle to the Phase 5 profile/settings page, introduces two new shared files (`lib/shared/domain/value_objects/money.dart` + `lib/shared/presentation/money_formatter.dart`), and adds ~25 ARB keys to both `app_ar.arb` and `app_en.arb`.

**Performance Goals**:

- `CurrenciesListPage` initial render: under 1 second on the reference Infinix Note 8 (one read of `SELECT * FROM currencies ORDER BY sort_order ASC, code ASC` — ~2-10 rows — plus a roll-up read of `(base_currency, target_currency, rate)` from the latest-effective `exchange_rates` rows for each pair via the composite index).
- `SetExchangeRatePage` initial render: under 500ms (one read of active currencies for the dropdowns).
- `ExchangeRateHistoryPage` initial render: under 1 second (cursor-paginated read of 50 rows for the chosen base currency, ordered `effective_at DESC` using the composite index).
- `update_exchange_rate` RPC end-to-end latency: under 200ms server-side + one round-trip from the device against the remote project; under 1 second total observed on the reference Infinix Note 8 on a typical mobile connection.
- Profile/settings "Preferred currency" toggle UPDATE: under 500ms server-side (a single UPDATE on the self-only `user_preferences` row).
- `MoneyFormatter.format(money, locale)`: under 10ms per call (no I/O; pure-Dart formatting via `intl.NumberFormat`).
- Listing-card paint after `display_currency` toggle (the FR-019a row-selection rule kicks in): under 1 second for the next paint (SC-012).
- Migration apply (five migrations) against the remote project: under 60 seconds total.

**Constraints**:
