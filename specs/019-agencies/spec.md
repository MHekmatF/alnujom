# Feature Specification: Agencies

**Feature Branch**: `019-agencies`
**Created**: 2026-05-30
**Status**: Draft
**Input**: Phase 19 — Agencies, from `docs/IMPLEMENTATION_PLAN.md` (§ "Phase 19 — Agencies")

> **Scope note**: Phase 19 introduces **agencies as multi-user publishing entities** — a real-estate office or brokerage that has its own public profile, a roster of member users with roles, an admin-reviewed verification status, and listings published under its banner. It is the first phase to consume the three `agencies.*` permission keys (`agencies.view`, `agencies.approve`, `agencies.suspend`) that Phase 6 seeded onto the `admin` and `super_admin` roles (`supabase/migrations/20260515120002_create_permissions.sql` lines 43–45; `…120003_create_role_permissions.sql` admin block), and the first to give the `listings.agency_id` column (added unenforced in Phase 10, `supabase/migrations/20260519120002_create_listings.sql:7`, "R-17 agency_id has no FK in Phase 10") a real foreign key. Phase 19 ships exactly: (a) three new tables — `public.agencies` (a brokerage entity owned by one approved publisher, with a lifecycle status `pending`/`approved`/`rejected`/`suspended`), `public.agency_members` (the roster — which users belong to which agency, with a per-agency `member_role` of `admin` or `agent` and a membership `status` lifecycle), and `public.agency_verification_requests` (the admin-review request that drives an agency from `pending` to `approved`/`rejected`, structurally mirroring the Phase 5 `public.account_approval_requests` table at `supabase/migrations/20260510120001_create_account_approval_requests.sql`); (b) a new `agency_status` enum (`pending`/`approved`/`rejected`/`suspended`) created in Phase 19 — it is NOT in `supabase/migrations/20260506120001_init_enums.sql` and is distinct from `account_approval_status` (which has no `suspended` value); (c) agency creation — a SECURITY DEFINER RPC that lets an **approved publisher** (`publisher_status = 'approved'` AND `account_status = 'approved'`) create exactly **one** agency (UNIQUE on `owner_user_id`, per Q3=A), binding `owner_user_id = auth.uid()` so it cannot be forged, seeding the agency at `status = 'pending'` and the owner as the first `agency_members` row (`member_role = 'admin'`, `status = 'active'`); (d) agency verification — the owner/agency-admin submits the agency for verification (an `agency_verification_requests` row with private identity material — the owner/registration ID-document number — stored via **Supabase Vault per ADR-0001**, never as a plaintext column and never in any client-readable view, plus verification document FILES in a private storage bucket with owner+admin-only access), and an admin holding `agencies.approve` reviews a verification queue and approves (→ `approved`, agency becomes public + verified) or rejects (→ `rejected`, with a reviewer reason surfaced to the owner) — via a privileged path mirroring the Phase 12 `approve_listing` / `reject_listing` Edge Function + service-role-only `*_internal` RPC pattern (`supabase/functions/approve_listing/index.ts` + `supabase/migrations/20260523120005_approve_reject_atomic_wrappers.sql`), NOT a phantom account-approval RPC (account approval is in fact a status-column + audit-trigger flow, so the only reusable approval template is Phase 12's); (e) agency lifecycle moderation — an admin holding `agencies.suspend` may suspend an `approved` agency (→ `suspended`) or reinstate it (→ `approved`), via the same dual-layer privileged path; (f) membership via **invite + in-app accept** (Q2=B) — an agency admin (a member whose `member_role = 'admin'` for THAT agency) invites a user **by phone**; the invite resolves to an **already-registered** account (no match → a structured "user not found" error), creating an `agency_members` row at `status = 'pending'`; the invitee sees the pending invitation in-app and explicitly **accepts** (→ `active`) or **declines** (→ removed), with NO dependency on push notifications (Phase 22); (g) publishing under an agency (Q1=A, **soft gate**) — the Phase 10 listing form gains a "Publish under agency" control that appears only when the signed-in publisher is an `active` member of ≥ 1 agency (whose status ∈ {`pending`, `approved`}), letting them attribute the listing to that agency by setting `listings.agency_id`; the publish path validates that `agency_id` references an agency the publisher actively belongs to, but **publishing authorization otherwise reuses the EXISTING per-user gate** (`publisher_status = 'approved' AND account_status = 'approved'`, keyed to `auth.uid() = publisher_user_id`, per `supabase/migrations/20260519120002_create_listings.sql` insert/update RLS) — agency approval is NOT a second publish gate; (h) the verified-agency badge — when a listing's `agency_id` is set AND that agency is `approved`, listing cards and the Phase 13 listing details page render a verified-agency badge (name + logo) linking to the agency's public profile (the `Listing` entity already carries `agencyId` per `lib/features/listing_form/domain/entities/listing.dart:244` and the details datasource already selects `agency_id`, but NO UI renders it today); (i) the agency frontend at `lib/features/agency/` (Clean-Architecture shape mirroring `lib/features/admin/listing_review/` and the `lib/features/locations/` admin-CRUD precedent) — `AgencyProfilePage` (public view of an approved agency + owner/admin edit), `AgencyMembersPage` (invite by phone, set member role, remove; shows pending invites), `AgencyListingsPage` (the agency's listings), `AgencyAnalyticsPage` (simple counters), and an `AgencyVerificationFlow` (submit + status) — plus a "My Agency" tile on the Phase 5 Profile page (`lib/features/profile/presentation/pages/profile_page.dart`, after the "My Reports" tile) and an admin verification surface at `lib/features/admin/agencies/`; (j) routing — new `/agency*` self-service routes (gated by active agency membership) and an `/admin/agencies` verification queue (gated by `agencies.view`/`agencies.approve`/`agencies.suspend` through a `requireAgenciesManageRedirect` mirroring `requireReportsManageRedirect` in `lib/core/routing/auth_redirect.dart`); (k) the localization layer gains the agency strings (create-agency, profile/edit, verification flow + status, member management + invite/accept/decline, publish-under-agency control, verified badge, admin queue + approve/reject/suspend copy, Profile tile, analytics labels, all errors) flowing through `AppLocalizations` with `ar` and `en` entries per Phase 3. Phase 19 does NOT introduce a paid/promoted agency tier; does NOT introduce automatic agency-identity verification (admin review only); does NOT mass-mutate an agency's listings when the agency is suspended (suspension blocks NEW agency publishing + hides the public profile/badge, but existing listings keep their status — Q5 default); does NOT add ownership transfer between users, multiple agencies per owner, or reporting of agencies (agency reporting is a separate future spec); does NOT notify members or owners of any event via push (Phase 22); and does NOT add any new third-party dependency. Phase 19 honors Principle VIII (agency verification + publisher-identity privacy — agency owner ID material is admin-only via Vault), Principle III (RLS on all three new tables, owner/member/admin read tiers, the agency-moderation mutation gated server-side at BOTH the Edge-Function permission check AND the service-role-only RPC, "checks at both ends"), Principle VII (the admin surface is gated by the data-driven `agencies.*` permissions and member management is gated by the per-agency `member_role` row — never a hardcoded role check), Principle IV (the new `lib/features/agency/` feature is layered data/domain/presentation with Supabase types confined to `data/`), and Principle I (this spec precedes any implementation).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — An approved publisher creates an agency and submits it for verification (Priority: P1)

An approved publisher who runs a real-estate office wants their business to have a presence on the marketplace. From their Profile they open "My Agency," create an agency (name, description, contact details, logo), and land on the agency's management surface. The agency starts in a `pending` state — not yet publicly visible and not yet carrying a verified badge. To become public and verified, the owner submits the agency for verification: they provide the agency's identity material (a registration / ID-document number and supporting document files) and submit. The submission enters an admin verification queue. The owner can see the agency's current verification status (pending / approved / rejected) and, if rejected, the reviewer's reason, and may re-submit.

**Why this priority**: P1 because the agency entity IS the foundation of the feature — without a created agency there is nothing to verify, no roster to manage, and no banner to publish under. Agency creation + the verification submission are the entry point the rest of the phase builds on.

**Independent Test**: Apply the Phase 19 migrations. Sign in as an approved publisher (`publisher_status='approved'`). Open Profile → "My Agency"; create an agency with a name + contact + logo. Confirm (a) exactly one `public.agencies` row exists with `owner_user_id = auth.uid()`, `status = 'pending'`, the entered fields; (b) an `agency_members` row exists for the owner with `member_role = 'admin'`, `status = 'active'`; (c) attempting to create a SECOND agency as the same user is rejected (UNIQUE owner). Submit the agency for verification with an ID-document number + a document file; confirm an `agency_verification_requests` row exists with `decision = 'pending'`, the document path captured, AND the ID-document number is NOT present as a plaintext column / is not returned by the agency read view (it is Vault-stored). Confirm a user who is NOT an approved publisher cannot create an agency.

**Acceptance Scenarios**:

1. **Given** a signed-in approved publisher with no agency, **When** they create an agency, **Then** exactly one `public.agencies` row is inserted with `owner_user_id = auth.uid()`, `status = 'pending'`, and the entered profile fields, AND the owner is auto-added to `agency_members` as `member_role = 'admin'`, `status = 'active'`.
2. **Given** a user who already owns an agency, **When** they attempt to create a second, **Then** the creation is rejected (one agency per owner, UNIQUE `owner_user_id`) with a localized message.
3. **Given** a signed-in user who is NOT an approved publisher (`publisher_status ≠ 'approved'`), **When** they attempt to create an agency, **Then** the attempt is rejected with a localized "approval required" message.
4. **Given** an agency owner on the agency management surface, **When** they submit the agency for verification with an ID-document number and supporting files, **Then** an `agency_verification_requests` row is created with `decision = 'pending'`, the document storage paths captured, AND the ID-document number is stored via Vault (never a plaintext column, never in a client-readable agency view).
5. **Given** an agency whose verification was rejected with a reason, **When** the owner opens the agency surface, **Then** the rejection reason is shown AND the owner may re-submit a fresh verification request.
6. **Given** a verification submission that fails (network / server error), **When** the write fails, **Then** a localized retryable error surfaces AND no partial verification-request row is committed.

### User Story 2 — An admin reviews and decides agency verification, and can suspend an agency (Priority: P1)

A user holding `agencies.approve` opens the agency verification queue from the admin home. They see agencies awaiting verification, each showing the agency profile and the submitted identity material (with the private ID-document number visible only to authorized admins). They open one, review it, and approve it (the agency becomes public and verified) or reject it with a reason (surfaced to the owner). Separately, a user holding `agencies.suspend` can suspend an already-approved agency (taking down its public profile and verified badge and blocking new publishing under it) or reinstate it. Every decision is audit-logged.

**Why this priority**: P1 because an agency that can never be approved is a dead end — the entire trust value of agencies (Principle VIII) is that an authorized human verifies the business before it is publicly badged. This story delivers the admin half of the loop plus the lifecycle controls and the audit trail the IMPLEMENTATION_PLAN requires.

**Independent Test**: Seed ≥ 2 agencies with `pending` verification requests. Sign in as a user holding `agencies.approve`; confirm the agency-verification tile is visible on the admin home and a user WITHOUT the permission does NOT see it. Open the queue; confirm pending requests list with the agency profile + the (Vault-decrypted, admin-only) ID-document number. Approve one; verify (a) the agency `status` becomes `approved`, (b) the verification request `decision` becomes `approved` with `reviewed_by`/`reviewed_at`, (c) an `audit_logs` row records the decision, (d) the agency's public profile is now reachable and approved listings under it show the verified badge. Reject the other with a reason; verify `status = 'rejected'`, the reason is stored and visible to the owner, and an `audit_logs` row exists. Sign in as a user holding `agencies.suspend`; suspend the approved agency; verify `status = 'suspended'`, the public profile + badge disappear, an `audit_logs` row exists, AND the agency's existing listings keep their prior status (no mass de-listing). Reinstate; verify `status = 'approved'` again.

**Acceptance Scenarios**:

1. **Given** a user holding `agencies.approve`, **When** they open the admin home, **Then** an agency-verification entry is visible and routes to the verification queue; **And given** a user WITHOUT `agencies.view`/`agencies.approve`/`agencies.suspend`, **Then** no agency entry is shown (frontend hide) AND the queue data is denied at the RLS layer (backend gate).
2. **Given** the verification queue is open, **When** it loads, **Then** pending verification requests are listed (paginated, newest first), each showing the agency profile and — for an authorized admin only — the Vault-decrypted ID-document number.
3. **Given** an admin opens a pending request and approves it, **When** the decision commits, **Then** in a single transaction the agency `status` becomes `approved`, the request `decision` becomes `approved` with `reviewed_by`/`reviewed_at`, and an `audit_logs` row is written — via the Edge-Function-plus-`*_internal`-RPC privileged path.
4. **Given** an admin rejects a pending request with a reason, **When** it commits, **Then** the agency `status` becomes `rejected`, the request `decision` becomes `rejected` with the reviewer reason recorded, the reason surfaces to the owner, and an `audit_logs` row is written.
5. **Given** a user holding `agencies.suspend` opens an `approved` agency, **When** they suspend it (with the destructive-action confirmation), **Then** the agency `status` becomes `suspended`, its public profile + verified badge are removed, new publishing under it is blocked, the agency's existing listings keep their current status, and an `audit_logs` row is written.
6. **Given** a `suspended` agency, **When** an admin reinstates it, **Then** the agency `status` becomes `approved` again and an `audit_logs` row is written.
7. **Given** any agency status decision by an authorized admin, **When** it commits, **Then** the decision is gated at BOTH the Edge-Function permission check AND the service-role-only `*_internal` RPC (which is not client-callable), and an unauthorized caller is rejected at both ends.

### User Story 3 — Agency members: invite, accept, and publish under the agency (Priority: P1)

An agency admin (a member whose role in that agency is `admin`) opens the agency's Members surface and invites a colleague by phone. The colleague — who already has an account — sees a pending invitation in-app and accepts it, becoming an active member. The agency admin can set a member's role (`admin` or `agent`) and remove members. Once a publisher is an active member of an agency, the Phase 10 listing form offers a "Publish under agency" control: when they create a listing, they can attribute it to the agency, which sets `agency_id` on the listing. Publishing still requires the individual to be an approved publisher — agency membership adds attribution, not a bypass.

**Why this priority**: P1 because "multi-user publishing entity" is the defining capability of an agency — without membership and publish-under-agency, an agency is just a profile page. This story delivers the roster + the publishing attribution that the IMPLEMENTATION_PLAN's acceptance criteria require ("agency admin invites a member; member can publish under the agency").

**Independent Test**: As an agency admin, invite an existing approved-publisher account by phone; confirm an `agency_members` row exists at `status = 'pending'`. Confirm inviting a phone with no matching account returns a localized "user not found" error and writes no row. Sign in as the invitee; confirm the pending invitation is visible in-app; accept it; confirm the row moves to `status = 'active'`. As that now-active member, open the listing form; confirm a "Publish under agency" control appears offering the agency; create a listing attributed to the agency; confirm the resulting listing has `agency_id` = the agency. Confirm a publisher who is NOT a member of the agency cannot set `agency_id` to it (the publish path rejects a foreign agency). Confirm a user who belongs to NO agency sees no "Publish under agency" control and their listings have `agency_id = NULL`.

**Acceptance Scenarios**:

1. **Given** an agency admin on the Members surface, **When** they invite an existing registered account by phone, **Then** an `agency_members` row is created at `status = 'pending'`, `member_role` as chosen (default `agent`), `invited_by` = the admin.
2. **Given** an agency admin invites a phone with NO matching registered account, **When** the invite is submitted, **Then** a localized "user not found" error surfaces AND no `agency_members` row is created.
3. **Given** an invited user with a pending invitation, **When** they open the app's agency/invitations surface, **Then** the pending invitation is visible AND they may accept (→ `status = 'active'`) or decline (→ removed); no push notification is required to discover it.
4. **Given** an agency admin, **When** they change a member's `member_role` or remove a member of their own agency, **Then** the change persists; **And** the owner is an `admin` member who cannot be removed.
5. **Given** a member operation, **When** it is attempted by a non-admin member or by an admin of a DIFFERENT agency, **Then** it is rejected (member management is authorized by `member_role = 'admin'` for THAT agency, not a global role).
6. **Given** an active member who is an approved publisher, **When** they open the listing form, **Then** a "Publish under agency" control appears offering the agency(ies) they actively belong to (whose status ∈ {`pending`, `approved`}); selecting one sets `listings.agency_id` on the created listing.
7. **Given** a publisher who is NOT an active member of an agency, **When** they (or a crafted request) attempt to publish a listing with that `agency_id`, **Then** the publish path rejects it; **And** a publisher with no agency membership sees no control and publishes with `agency_id = NULL`.
8. **Given** an active member publishing under an agency, **When** they submit, **Then** publishing authorization still requires their own `publisher_status = 'approved' AND account_status = 'approved'` (the existing per-user gate) — agency membership does not bypass individual approval.

### User Story 4 — Agencies, members, and verification data are protected by RLS (Priority: P1)

Agency rosters and verification material are sensitive (a member list reveals staff; a verification request carries an owner's national-ID-level identity). The product MUST guarantee that the public can read only `approved` agencies' public profile fields, that an agency's members can read their own agency at any status, that the private ID material is admin-decrypt-only, that only `agencies.view`/`approve`/`suspend` holders can read the verification queue and decide on agencies, and that no anonymous client can read members or verification data or write anything.

**Why this priority**: P1 because Constitution Principle III + VIII + ADR-0001 make an unprotected agency-verification table (with plaintext ID numbers) a breach, and exposing a competitor's member roster or letting a non-admin approve an agency would undermine the trust model. The owner/member/admin read tiers, the Vault-backed admin-only PII, and the dual-layer moderation gate are load-bearing.

**Independent Test**: Seed agency-A (owned by user-A, `pending`) and agency-B (owned by user-B, `approved`), each with members and a verification request. From an anonymous client, confirm ONLY agency-B's public profile + approved listings return — never agency-A (pending), never any member row, never any verification row. From user-A's session, confirm they can read their own agency-A (even though pending) and its members, but NOT agency-B's member roster or verification request, and NOT any ID-document number. From a `agencies.view` admin session, confirm the full agency directory + member rosters + verification queue are readable AND the ID-document number decrypts (admin-only). Attempt to create an `agencies` row with a forged `owner_user_id` from user-A; confirm rejected. Attempt to insert/update `agency_members` directly (not via the RPCs) as a non-admin; confirm rejected. Attempt to approve an agency as a non-`agencies.approve` caller (Edge Function AND, if bypassed, the `*_internal` RPC); confirm rejected at both ends.

**Acceptance Scenarios**:

1. **Given** an anonymous client, **When** it queries agencies, **Then** ONLY `approved` agencies' public profile fields return — never a `pending`/`rejected`/`suspended` agency, never a member row, never a verification request.
2. **Given** an agency's owner or active member, **When** they query their own agency, **Then** it returns at ANY status (including `pending`), as do its member rows — but no other agency's roster or verification data returns.
3. **Given** a user holding `agencies.view`, **When** they query the directory, rosters, and verification queue, **Then** all agencies (any status), all rosters, and all verification requests are readable (the moderation view).
4. **Given** any caller, **When** the agency read path is exercised, **Then** the private ID-document number is NEVER returned in a client-readable view; it is decryptable ONLY by an authorized admin via the dedicated Vault helper.
5. **Given** user-A is signed in, **When** they attempt to create an `agencies` row whose `owner_user_id` is not their `auth.uid()`, **Then** the write is rejected (creation binds `owner_user_id = auth.uid()` via the SECURITY DEFINER RPC; no client INSERT bypass).
6. **Given** a non-admin member or an admin of a different agency, **When** they attempt to write `agency_members` directly or via an unauthorized RPC call, **Then** it is rejected (member writes go only through the privileged RPCs with the per-agency `member_role = 'admin'` check; the invitee-only accept/decline binds `auth.uid()`).
7. **Given** an unauthorized caller (anonymous, or authenticated without the relevant `agencies.*` permission), **When** they attempt to approve/reject/suspend an agency, **Then** it is rejected at the Edge-Function permission check AND, if bypassed, by the service-role-only `*_internal` RPC grant — no agency-status mutation occurs.
8. **Given** any agency status change or member add/remove/role change, **When** it commits, **Then** an `audit_logs` row records the actor, action, target, and before/after state (per the §6.4 matrix), reusing the Phase 4 `log_audit()` machinery.

### User Story 5 — Public users browse an approved agency and see the verified badge (Priority: P2)

An anonymous or signed-in browser viewing the marketplace encounters a listing published under an agency. The listing card and the listing details page show a verified-agency badge with the agency's name and logo; tapping it opens the agency's public profile — name, description, contact, logo, and the agency's currently-approved listings. The badge and public profile appear only for `approved` agencies; a listing under a `pending`, `rejected`, or `suspended` agency shows no badge and the agency profile is not publicly browsable.

**Why this priority**: P2 because the public-facing payoff (the verified badge + browsable agency profile) is the visible value of agency verification, but it sits on top of the P1 create → verify → publish loop and the approval gate rather than being a prerequisite for them.

**Independent Test**: Approve an agency and publish (and approve) a listing under it. As an anonymous user, open the home feed / the listing's details; confirm a verified-agency badge (name + logo) renders and links to the agency's public profile, which lists the agency's approved listings. Suspend the agency (as admin); reload the public surfaces; confirm the badge and the public profile disappear without any code change. Confirm a listing under a `pending` agency shows no badge.

**Acceptance Scenarios**:

1. **Given** a listing whose `agency_id` references an `approved` agency, **When** it renders on a card or the details page, **Then** a localized verified-agency badge (agency name + logo) appears and links to the agency's public profile.
2. **Given** a listing whose `agency_id` references a `pending`/`rejected`/`suspended` agency, or whose `agency_id` is NULL, **When** it renders, **Then** NO agency badge appears AND the surrounding layout is unchanged (surgical addition, no reflow).
3. **Given** an anonymous user, **When** they open an `approved` agency's public profile, **Then** they see the agency's name, description, contact, logo, and its currently-approved listings — and never its member roster or verification material.
4. **Given** an approved agency that is later suspended, **When** the public surfaces are reloaded, **Then** the badge and the public profile are gone with no code change (driven by the agency status read gate).

### User Story 6 — An agency admin sees simple analytics for their agency (Priority: P3)

An agency admin opens an Analytics view for their agency and sees at-a-glance counters: number of members, number of listings under the agency broken down by status (e.g., approved / pending / paused), and total active listings. The counters are scoped to their own agency only.

**Why this priority**: P3 because counters are a convenience that refines the agency-admin experience; they sit on top of the membership + publishing data delivered by P1 stories and the admin dashboard (Phase 20) is the broader home for cross-cutting counters.

**Independent Test**: As an agency admin of an agency with a known set of members and listings, open the Analytics view; confirm the member count and the listing-by-status counts match the seeded fixture, and that the queries are bounded (no unbounded scan) and reveal no other agency's data.

**Acceptance Scenarios**:

1. **Given** an agency admin, **When** they open the agency Analytics view, **Then** they see the member count and the listing counts by status for THEIR agency, matching the underlying data.
2. **Given** the Analytics view, **When** it loads, **Then** its queries are bounded and scoped to the caller's agency only — no other agency's counters are exposed.

### Edge Cases

- **A non-approved user (or non-publisher) attempts to create an agency**: Rejected with a localized "approval required" message (Q3=A — eligibility is `publisher_status = 'approved'`). No agency row is written.
- **A user who already owns an agency tries to create a second**: Rejected (one agency per owner, UNIQUE `owner_user_id`, per Q3=A). A user MAY still be an active member of other agencies — ownership is one-per-user, membership is not.
- **An agency admin invites a phone with no matching registered account**: Rejected with a localized "user not found" error; no `agency_members` row is created (Q2=B — invite resolves to an existing account; pre-staging non-registered phones is out of scope).
- **An agency admin invites a user who is already a member or already invited**: The invite is idempotent / surfaces a localized "already a member / already invited" acknowledgement rather than creating a duplicate roster row (PK `(agency_id, user_id)` enforces one membership row per user per agency).
- **An invited user declines, or never accepts**: A declined/pending invitation does not grant any membership capability; only `status = 'active'` confers member abilities (publishing under the agency, reading the roster). A declined invite leaves no active membership.
- **A member publishes under an agency, then is removed from the agency**: Already-published listings keep their `agency_id` (and badge, if the agency is approved) — removing a member does not retroactively strip attribution from listings already filed; the removed member simply loses the ability to publish NEW listings under the agency. (Plan-time: whether removal nulls future drafts is an Assumption.)
- **A publisher belongs to multiple agencies**: The "Publish under agency" control offers a choice among all agencies the user is an active member of (whose status ∈ {`pending`, `approved`}), plus "personal" (no agency). With exactly one membership it is a simple toggle; with several it is a selector.
- **An agency is suspended while it has live listings**: Suspension blocks NEW publishing under the agency and removes the public profile + verified badge, but does NOT mass-mutate the agency's existing listings — they keep their current status (Q5 default). Bulk handling of a suspended agency's listings is noted as possible future admin-dashboard work (Phase 20), not Phase 19.
- **A listing references an agency that is later suspended/rejected**: The listing remains valid and keeps its `agency_id`; the verified badge simply stops rendering (the badge is gated on the agency being `approved`).
- **The `listings.agency_id` FK is enforced over existing data**: All pre-Phase-19 listings have `agency_id = NULL` (the column was added nullable with no FK in Phase 10), so enforcing the FK does not break any existing row; the FK rejects only a NEW `agency_id` that does not reference a real agency.
- **An owner's account is later deleted**: The agency's `owner_user_id` FK delete behavior is plan-time; the spec mandates no orphaned agency identity and no dangling FK (cascade the agency, or block deletion, consistent with the favorites/lead-events precedents).
- **A verification request references private ID material**: The ID-document number is Vault-stored (ADR-0001) and never appears in a plaintext column or any client-readable view; only an authorized admin can decrypt it via the dedicated helper. Verification document files live in a private storage bucket readable only by the agency owner/admins and platform admins, never public.
- **A SECURITY INVOKER view would hide a member's own pending agency**: Per the Phase 18 invoker-view gotcha (`supabase/migrations/20260530120010_fix_v_reports_definer_scoping.sql`), the public agencies read view is implemented as SECURITY DEFINER with an explicit `WHERE (status = 'approved' OR owner/active-member OR agencies.view)` so a member's own non-`approved` agency remains visible to them while staying hidden from the public.
- **Network failure during agency creation, verification submission, invite/accept, or a moderation decision**: A localized retryable error surfaces AND the database has no partial state (no half-created agency, no member row without its lifecycle, no agency-status change without its audit entry).

## Requirements *(mandatory)*

### Functional Requirements

#### Agency creation & profile

- **FR-001**: System MUST let a signed-in **approved publisher** (`publisher_status = 'approved'` AND `account_status = 'approved'`) create exactly **one** agency (Q3=A), through a privileged server-side path (a SECURITY DEFINER RPC) that binds `owner_user_id = auth.uid()` (un-forgeable), seeds the new agency at `status = 'pending'`, and creates the owner's `agency_members` row at `member_role = 'admin'`, `status = 'active'` in the same transaction. A UNIQUE constraint on `owner_user_id` MUST enforce one-agency-per-owner; a non-approved or already-owning user MUST be rejected with a structured/localized error.
- **FR-002**: An agency MUST carry at minimum a name, description, public contact fields (phone, whatsapp, address), and logo/cover image references. The owner and the agency's `admin` members MUST be able to edit these fields while the agency is `pending` or `approved` (own-agency only); no client may edit another agency's profile.
- **FR-003**: System MUST provide a public agency profile surface (route `/agency/:id`) that, for an `approved` agency, shows its public profile fields and its currently-`approved` listings, and that is NOT publicly browsable for a `pending`/`rejected`/`suspended` agency (only the owner/active members and `agencies.view` admins may view a non-approved agency).

#### Verification submission (owner) & Vault-stored identity

- **FR-004**: The agency owner / an `admin` member MUST be able to submit the agency for verification, creating a `public.agency_verification_requests` row (`decision = 'pending'`) that captures the supporting document storage paths and the agency's private identity material; at most one OPEN (`pending`) verification request exists per agency at a time, and a fresh request MAY follow a `rejected` decision.
- **FR-005**: The agency's private identity material — at minimum the registration / ID-document number — MUST be stored via **Supabase Vault per ADR-0001**, never as a plaintext column and never returned in any client-readable agency/verification view; it MUST be decryptable ONLY by an authorized admin via a dedicated agency-scoped Vault helper mirroring the Phase 5 `app_vault_secret_for_user` pattern (`supabase/migrations/20260510120004_profiles_vault_pii_helpers.sql`).
- **FR-006**: Verification document FILES MUST live in a private storage bucket readable only by the agency owner/admins and platform admins (never public), distinct from the public agency-logo bucket.

#### Admin verification & lifecycle moderation

- **FR-007**: System MUST ship an admin agency-verification surface reachable from the Phase 6 admin home via an entry gated on `agencies.view`/`agencies.approve` (frontend `PermissionChecker`), denied at the RLS layer for callers without an `agencies.*` permission (Principle "checks at both ends"). It MUST list verification requests (paginated, newest first), each showing the agency profile and — for an authorized admin only — the Vault-decrypted ID-document number.
- **FR-008**: Deciding an agency's verification (approve / reject) MUST go through a privileged path mirroring the Phase 12 `approve_listing` / `reject_listing` pattern: an Edge Function that (a) extracts the caller's JWT, (b) gates on `agencies.approve` (via `current_user_has_permission`), and (c) invokes a SECURITY DEFINER `*_internal` RPC granted to `service_role` only, which in a SINGLE transaction sets the agency `status` (`approved` / `rejected`), sets the verification request `decision` + `reviewed_by` + `reviewed_at` (+ reason on reject), and writes the audit entry. The `*_internal` RPC MUST NOT be client-callable.
- **FR-009**: A rejection MUST carry a reviewer-supplied reason that surfaces to the agency owner (Principle VIII), and the owner MUST be able to re-submit.
- **FR-010**: Suspending or reinstating an `approved` agency MUST go through the same dual-layer privileged path, gated on `agencies.suspend`, transitioning `approved → suspended` (suspend) or `suspended → approved` (reinstate), each audit-logged. Destructive lifecycle actions (suspend) MUST require an explicit confirmation step in the admin UI (matching the Phase 7/12/18 destructive-action convention).
- **FR-011**: Suspension MUST block NEW publishing under the agency and remove its public profile + verified badge, but MUST NOT mass-mutate the agency's existing listings — their status is unchanged (Q5 default). Mass handling of a suspended agency's listings is out of Phase 19 scope.
- **FR-012**: Every agency status change (approve / reject / suspend / reinstate) and every membership add / remove / role-change MUST write an `audit_logs` row capturing actor, action, target, and before/after state, reusing the Phase 4 `log_audit()` machinery (`supabase/migrations/20260506120004_create_audit_logs.sql`) — no parallel audit mechanism (§6.4).

#### Membership (invite + in-app accept)

- **FR-013**: An agency `admin` member MUST be able to invite a colleague **by phone** (Q2=B); the invite MUST resolve to an **already-registered** account, and a phone with no matching account MUST be rejected with a structured/localized "user not found" error (no row written). Inviting a user who is already a member or already invited MUST be idempotent (one `agency_members` row per `(agency_id, user_id)`), surfacing a localized acknowledgement.
- **FR-014**: An invite MUST create an `agency_members` row at `status = 'pending'` (`member_role` as chosen by the inviter, default `agent`, `invited_by` = the inviting admin). The invited user MUST be able to discover the pending invitation IN-APP (no push-notification dependency — Phase 22) and explicitly **accept** (→ `status = 'active'`) or **decline** (→ removed); accept/decline MUST be performable ONLY by the invitee (RPC binds `auth.uid()`).
- **FR-015**: `agency_members` MUST carry a `member_role` ∈ {`admin`, `agent`} and a membership `status` lifecycle (`pending` → `active` → removed). An agency `admin` member MUST be able to set/change another member's `member_role` and remove members of their OWN agency; the owner MUST be an `admin` member and MUST NOT be removable (ownership transfer is out of scope for v1).
- **FR-016**: Member management (invite / accept-handling / remove / role-change) MUST be authorized by the per-agency `member_role = 'admin'` row for THAT agency (row-scoped), NOT by a global permission key or the seeded global `agency_admin` role; an `admin` of one agency MUST NOT be able to manage another agency.
- **FR-017**: All `agency_members` writes MUST go through privileged RPCs (no direct client INSERT/UPDATE/DELETE grant): invite/remove/role-change require the caller be an `admin` member of that agency; accept/decline require the caller be the invitee.

#### Publishing under an agency

- **FR-018**: System MUST enforce the `listings.agency_id` foreign key to `public.agencies(id)` in Phase 19 (the column exists nullable with no FK from Phase 10). The FK delete behavior MUST guarantee no dangling reference and no orphaned attribution (plan-time choice consistent with the existing listing FKs). Enforcing the FK MUST NOT break existing listings (all have `agency_id = NULL`).
- **FR-019**: The Phase 10 listing form MUST gain a "Publish under agency" control that appears ONLY when the signed-in publisher is an `active` member of ≥ 1 agency (whose `status` ∈ {`pending`, `approved`}); it MUST offer "personal" (no agency) plus each such agency, and selecting one MUST set `listings.agency_id`. For a publisher with no active agency membership the control MUST be absent and the listing's `agency_id` MUST remain NULL; the addition MUST NOT reflow the unrelated form steps.
- **FR-020**: The publish path MUST validate, when `agency_id` is set, that the publisher is an `active` member of that agency AND the agency `status` ∈ {`pending`, `approved`} — otherwise reject. Publishing authorization otherwise MUST reuse the EXISTING per-user gate (`publisher_status = 'approved' AND account_status = 'approved'`, keyed to `auth.uid() = publisher_user_id`); agency approval MUST NOT be introduced as a second publish gate (Q1=A, soft gate).
- **FR-021**: Agency attribution (`agency_id`) MUST be settable/changeable in the same listing states as other listing fields (draft / rejected, via the listing form), subject to the FR-020 membership validation; it MUST NOT be silently mutable by a client outside that validated path.

#### Verified badge & public surfaces

- **FR-022**: When a listing's `agency_id` references an `approved` agency, the listing card and the Phase 13 listing details page MUST render a localized verified-agency badge (agency name + logo) linking to the agency's public profile. When `agency_id` is NULL or references a non-`approved` agency, NO badge MUST render. The query shape that supplies the agency name/logo to the card/details surface is plan-time (join vs. secondary fetch).
- **FR-023**: The badge addition MUST be surgical — it MUST NOT reflow the existing Phase 13 listing card / details layout when no badge applies, and MUST NOT alter unrelated Phase 13/17/18 surfaces (Favorite toggle, Share stub, Report CTA).

#### Tables, enums, indices

- **FR-024**: System MUST create a new `agency_status` enum (or equivalent CHECK) with values `pending` / `approved` / `rejected` / `suspended` — it is NOT pre-declared in `init_enums.sql` and is distinct from `account_approval_status` (which lacks `suspended`). No new value is added to the listings status enum or any other existing enum.
- **FR-025**: System MUST create `public.agencies` with at minimum: `id` (UUID PK), `owner_user_id` (UUID NOT NULL, UNIQUE, FK to `auth.users(id)`), `name`, `description`, `phone`, `whatsapp`, `address`, `logo_url`, `cover_url` (nullable), `status` (`agency_status`, NOT NULL, DEFAULT `pending`), `created_at`, `updated_at`. RLS MUST be enabled.
- **FR-026**: System MUST create `public.agency_members` with at minimum: `agency_id` (FK to `public.agencies(id)`), `user_id` (FK to `auth.users(id)`), `member_role` (CHECK {`admin`, `agent`}), `status` (CHECK {`pending`, `active`, `removed`}), `invited_by` (FK to `auth.users(id)`, nullable), `joined_at`, with PK `(agency_id, user_id)`. RLS MUST be enabled.
- **FR-027**: System MUST create `public.agency_verification_requests` with at minimum: `id` (UUID PK), `agency_id` (FK to `public.agencies(id)`), `submitted_at`, `reviewed_by` (FK to `auth.users(id)`, nullable), `reviewed_at` (nullable), `decision` (CHECK {`pending`, `approved`, `rejected`}, DEFAULT `pending`), `decision_reason` (nullable), `evidence_urls` (document storage paths) — and the private ID-document number stored via Vault (FR-005), NOT as a plaintext column. RLS MUST be enabled.
- **FR-028**: System MUST create indices supporting the primary access patterns: the admin verification queue (verification requests by `decision`, `submitted_at`), the roster lookup (`agency_members` by `agency_id`), the "my agencies / my invitations" lookup (`agency_members` by `user_id`, `status`), the public directory (`agencies` by `status`), and the one-open-verification-request-per-agency dedup.

#### Privacy / RLS / storage

- **FR-029**: System MUST enable RLS on `public.agencies` with a read posture matching §6.4: readable when `status = 'approved'` (public) OR by the owner / an `active` member OR by an `agencies.view` holder — implemented via a SECURITY DEFINER read view with an explicit `WHERE` (proactively applying the Phase 18 invoker-view gotcha, `…120010_fix_v_reports_definer_scoping.sql`) so a member's own non-`approved` agency stays visible to them. Profile-field writes MUST be limited to the owner/`admin` members of that agency; `status` changes MUST occur only via the privileged admin path (FR-008/FR-010); creation MUST occur only via the SECURITY DEFINER create RPC (FR-001).
- **FR-030**: System MUST enable RLS on `public.agency_members` so that an agency's `active` members + `agencies.view` admins can read the roster, and an invited user can read their OWN pending invitation; all writes go only through the privileged RPCs (FR-017). No anonymous read.
- **FR-031**: System MUST enable RLS on `public.agency_verification_requests` so it is readable by the agency's owner/`admin` members + `agencies.view`/`agencies.approve` admins only; the Vault-stored ID material MUST never appear in any client-readable view (admin-decrypt-only RPC); submission is by the owner/admin via RPC and the decision is by an admin via the Edge Function (FR-008).
- **FR-032**: Anonymous clients MUST be able to read ONLY `approved` agencies' public profile fields + their approved listings (public marketplace browsing); anonymous clients MUST NOT read member rosters, verification requests, or any non-`approved` agency, and MUST NOT write to any of the three new tables.
- **FR-033**: System MUST provide the storage buckets the feature needs — a public bucket for approved-agency logos/cover imagery (public read, agency-`admin` write) and a private bucket for verification documents (owner/admin read only, never public) — following the Phase 11 listing-media storage-policy path-shape pattern (`supabase/migrations/20260522120003_create_listing_media_storage_policies.sql`).

#### Analytics

- **FR-034**: The agency Analytics surface MUST present simple, bounded counters scoped to the caller's own agency only — at minimum member count and listing counts by status — with no cross-agency leakage and no unbounded query.

#### Localization, theming, accessibility

- **FR-035**: Every user-visible string introduced by Phase 19 — create-agency, agency profile/edit, verification flow + status + rejection reason, member management (invite, role labels, accept/decline, remove), the publish-under-agency control, the verified-agency badge, the admin verification queue + approve/reject/suspend copy + confirmations, the Profile "My Agency" tile, the analytics labels, and every error/empty-state — MUST flow through `AppLocalizations` with both `ar` and `en` entries (Principle V).
- **FR-036**: All new surfaces (create/edit agency, verification flow, members + invitations, publish-under-agency control, verified badge, public agency profile, admin verification queue + decision dialogs, analytics, Profile tile, empty/error states) MUST render correctly in all four combinations of (light/dark theme) × (Arabic RTL / English LTR), using logical insets and Phase 2 design tokens (no inline hex literals, no raw font sizes, no ad-hoc paddings) (Principle VI).

#### Constitutional & dependency constraints

- **FR-037**: The PR MUST NOT add any new third-party dependency — agencies are implemented with the existing Flutter / BLoC / `go_router` / `supabase_flutter` stack, in-house Postgres tables, Supabase Vault + Storage, and Edge Function(s) consistent with the Phase 12 runtime. No new pubspec package, no new Postgres extension, no Android manifest change.
- **FR-038**: The PR MUST NOT introduce any hardcoded role/permission branch — the admin agency surface is gated by the data-driven `agencies.view`/`agencies.approve`/`agencies.suspend` permissions via `PermissionChecker` (frontend) and `current_user_has_permission`/RLS (backend); agency self-service (member management, profile edit, publish-under-agency) is gated by the per-agency `member_role`/membership row, never by a hardcoded role string (Principle VII).
- **FR-039**: The PR MUST honor Principle III and the "checks at both ends" rule — RLS enabled on all three new tables, agency moderation (approve/reject/suspend/reinstate) gated at BOTH the Edge-Function permission check AND the service-role-only `*_internal` RPC, no service-role key on the client, and agency creation / member operations / verification submission performed through SECURITY DEFINER RPCs binding `auth.uid()`.
- **FR-040**: The PR MUST NOT add a new value to the listings status enum, MUST NOT alter the Phase 16 `lead_events` schema, and MUST NOT modify the Phase 13/17/18 `PerListingActionBlock` CTAs; enforcing the `listings.agency_id` FK MUST NOT break existing listings (all existing rows have `agency_id = NULL`).
- **FR-041**: The PR MUST reuse the established cross-cutting machinery rather than introducing parallels — the Phase 4 `audit_logs` + `log_audit()` for all agency audit; the Phase 12 Edge-Function-plus-`*_internal`-RPC pattern for agency moderation; the ADR-0001 Vault helper pattern for agency identity PII; and the Phase 5 `account_approval_requests` table shape as the structural template for `agency_verification_requests`.

### Key Entities

- **Agency**: A brokerage entity owned by exactly one approved publisher, carrying a public profile (name, description, contact, logo/cover) and a lifecycle `status` (`pending` → `approved`/`rejected`; `approved` ↔ `suspended`). Publicly readable only when `approved`; readable by its owner/active members at any status; fully readable by `agencies.view` admins. One agency per owner (UNIQUE `owner_user_id`).
- **Agency Member**: A row linking a user to an agency with a per-agency `member_role` (`admin` or `agent`) and a membership `status` (`pending` invited → `active` → removed). `admin` members manage the roster + profile + verification of their own agency; `active` members of any role may publish listings under the agency. The owner is an un-removable `admin` member.
- **Agency Verification Request**: An admin-review request that drives an agency from `pending` to `approved`/`rejected`, carrying supporting document references and Vault-stored private identity material (ID-document number, admin-decrypt-only). Structurally mirrors the Phase 5 `account_approval_requests` table. At most one open (`pending`) request per agency.
- **Agency Membership Invitation**: The user-facing pending invitation an invited (already-registered) user sees in-app and accepts/declines (Q2=B). Discoverable without push notifications; accept/decline is invitee-only.
- **Publish-Under-Agency Attribution**: The act of attributing a listing to an agency by setting `listings.agency_id` via the listing form's "Publish under agency" control — available to `active` members of agencies with status ∈ {`pending`, `approved`}, validated server-side at publish, and orthogonal to the unchanged per-user publish-authorization gate.
- **Verified-Agency Badge**: The public-facing badge (agency name + logo) rendered on listing cards/details for listings under an `approved` agency, linking to the agency's public profile; absent for NULL/non-`approved` `agency_id`.
- **Agency Verification Queue**: The `agencies.view`/`agencies.approve`-gated, paginated admin list of pending verification requests, from which each is opened, reviewed (with admin-only decrypted ID material), and approved/rejected.
- **Agency Analytics**: The own-agency, bounded counters (member count, listing counts by status) shown to an agency admin.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An approved publisher can create an agency from Profile → "My Agency" in under 60 seconds, and exactly one `public.agencies` row (`status = 'pending'`, correct owner/fields) plus the owner's `active`/`admin` `agency_members` row exist within 2 seconds — verified on the reference Infinix Note 8 against a fixture; a non-approved user and a second-agency attempt are both rejected.
- **SC-002**: An agency owner can submit the agency for verification with an ID-document number + document file, producing one `agency_verification_requests` row (`decision = 'pending'`) with the document path captured AND the ID-document number absent from every client-readable view / plaintext column — verified by direct inspection + a `pg_dump | grep`-style check that the ID number does not appear in plaintext (per ADR-0001 §Verification).
- **SC-003**: A user holding `agencies.approve` sees the agency-verification entry on the admin home and opens a paginated queue listing pending requests with the admin-only decrypted ID number; a user WITHOUT any `agencies.*` permission sees no entry AND cannot read the queue at the wire level — verified across an admin session and a non-admin session.
- **SC-004**: Approving a pending verification sets the agency to `approved` and the request to `approved` (with reviewer/timestamp); rejecting sets the agency to `rejected` with a reviewer reason visible to the owner — and in every case exactly one `audit_logs` row is written, all verified by direct table inspection.
- **SC-005**: Suspending an `approved` agency sets it to `suspended`, removes its public profile + verified badge within one refresh, and blocks new publishing under it — while the agency's existing listings keep their prior status (no mass de-listing); reinstating returns it to `approved` — all verified by inspection + reloading the public surfaces with no code change, plus an `audit_logs` row per transition.
- **SC-006**: An agency admin can invite an existing account by phone (row at `status = 'pending'`), an unregistered phone is rejected with "user not found" and writes no row, and the invitee can accept in-app (→ `status = 'active'`) — all verified by direct `agency_members` inspection across the inviter and invitee sessions.
- **SC-007**: An `active` member who is an approved publisher sees the "Publish under agency" control and can publish a listing with `agency_id` = the agency; a publisher who is NOT a member of that agency (or a crafted request) is rejected by the publish path; a publisher with no membership sees no control and publishes `agency_id = NULL` — all verified at the wire level.
- **SC-008**: A listing under an `approved` agency renders the verified-agency badge (name + logo) linking to the agency's public profile on both the card and the details page; a listing under a `pending`/`rejected`/`suspended` agency (or with NULL `agency_id`) renders NO badge and no layout reflow — verified on the reference device.
- **SC-009**: An anonymous client reading agencies receives ONLY `approved` agencies' public profile fields + approved listings and ZERO member/verification rows; an agency's owner/member can read their own agency at any status but not another agency's roster/verification; a non-`agencies.view` authenticated session cannot read the full directory/rosters/verification — all verified at the wire level, not merely in the UI.
- **SC-010**: The private ID-document number is decryptable ONLY by an authorized admin via the dedicated Vault helper and is returned by NO client-readable view to the owner, members, or anonymous callers — verified by a wire-level read attempt from each unauthorized session returning no plaintext ID.
- **SC-011**: An unauthorized caller (anonymous, or authenticated without the relevant `agencies.*` permission) attempting to approve/reject/suspend an agency is rejected at the Edge-Function permission check AND, if bypassed, by the service-role-only `*_internal` RPC grant — verified by a wire-level attempt producing no agency-status change and no audit row.
- **SC-012**: A forged agency creation (`owner_user_id ≠ auth.uid()`) and a direct (non-RPC) `agency_members` write by a non-admin are both rejected — verified at the wire level (creation binds `owner_user_id = auth.uid()`; member writes go only through the privileged RPCs with the per-agency `admin` check).
- **SC-013**: The agency surfaces (create/edit, verification flow, members + invitations, publish-under-agency control, verified badge, public profile, admin verification queue + decision dialogs, analytics, Profile tile, empty/error states) render correctly in all four combinations of (light/dark) × (Arabic RTL / English LTR) on the reference Infinix Note 8 (480 dp) AND a 412 dp emulator profile — all strings localized and directionally correct.
- **SC-014**: A repository-wide check returns zero new third-party packages introduced by Phase 19, zero hardcoded role/permission branches in the agency feature code (admin gated by `agencies.*` via `PermissionChecker`+RLS; self-service gated by the membership row), AND no new value added to the listings status enum or `lead_events.event_type` — verified by grep gates.
- **SC-015**: The admin verification queue, the agency roster, the public directory, and the agency Analytics view all issue bounded (paginated/limited) queries — verified by inspecting each query for a `LIMIT`/cursor and confirming no unbounded full-table scan on a large-agencies fixture.

## Assumptions

- **Agency verification is a SOFT gate on publishing** (Q1=A): publishing a listing under an agency reuses the EXISTING per-user authorization (`publisher_status = 'approved' AND account_status = 'approved'`, the listings insert/update RLS at `supabase/migrations/20260519120002_create_listings.sql`); the agency's `approved` status gates only its public profile visibility + the verified badge, NOT the ability to publish. A member may publish under a `pending` agency immediately. A hard publish gate (no publishing until the agency is approved) was rejected as making a brand-new agency inert and requiring a new agency-status branch in the publish path; a dual-approval hybrid was rejected as the heaviest option. Recorded per Principle XII.
- **Membership is invite + in-app accept** (Q2=B): an agency `admin` invites an ALREADY-REGISTERED user by phone (no match → "user not found"); the invitee gets a `pending` `agency_members` row and explicitly accepts (→ `active`) or declines in-app. Pre-staging unregistered phones (auto-link at signup) was rejected because it needs signup-time phone linking and a notify channel that does not exist until Phase 22; immediate-active invite (no accept step) was rejected as adding people to an agency without their consent. The in-app pending-invitation surface is the discovery channel; push notification of invites is deferred to Phase 22.
- **Eligibility & cardinality: one agency per approved publisher** (Q3=A): a user with `publisher_status = 'approved'` may create exactly one agency (UNIQUE `owner_user_id`). Reuses the existing publisher-approval signal, avoids introducing role-grant UX for the inert seeded `owner`/`agent` roles, and sidesteps multi-agency-per-owner ambiguity. A user MAY be an `active` member of multiple agencies (a freelance agent working with several offices) but may OWN only one. Allowing any approved account (non-publisher) to create one, and allowing multiple agencies per owner, were both rejected for v1 simplicity.
- **Member-management authorization is the per-agency membership row, not a global role** (reconciling the plan's "when the user has an agency-admin role" wording with §6.4's "Agency admin (own agency)"): authorization for invite/remove/role-change/profile-edit/verification-submit is `agency_members.member_role = 'admin'` for THAT specific agency. The seeded global `agency_admin` system role (`supabase/migrations/20260515120001_create_roles.sql:63`, permission-less) is NOT used as the gate and remains reserved/inert; no global `agencies.manage`/`agencies.manage_members` permission key is introduced. This is cleaner than minting a global key and correctly scopes authority to one agency. Recorded per Principle XII.
- **Agency moderation reuses the Phase 12 Edge-Function-plus-`*_internal`-RPC pattern**, NOT a phantom account-approval RPC. Investigation confirmed there is NO `approve_account_approval_request` RPC — Phase 5 account approval is a status-column + audit-trigger flow. The only reusable permission-gated-mutation template is Phase 12's `approve_listing` / `reject_listing` (`supabase/functions/approve_listing/index.ts` + `supabase/migrations/20260523120005_approve_reject_atomic_wrappers.sql`, with `set_config('app.current_user_id', …)` GUC + same-transaction UPDATE + service-role-only grant). Agency approve/reject/suspend/reinstate mirror that. The exact decomposition (one `moderate_agency` Edge Function with an action parameter vs. separate functions) is plan-time; the spec mandates the dual-layer gate.
- **Agency suspension does not mass-mutate listings** (Q5 default): suspending an agency blocks new agency publishing + removes its public profile/badge but leaves its existing listings' status untouched. Mass-pausing a suspended agency's listings was rejected as a bulk-transition feature beyond Phase 19; it is noted as possible Phase 20 admin-dashboard work.
- **Agency attribution is set in the listing form, validated at publish, and not silently reassignable** (Q5-related): `agency_id` is chosen in the "Publish under agency" control and is editable in the same listing states as other fields (draft/rejected), always subject to the FR-020 membership + agency-status validation. Removing a member does NOT retroactively strip `agency_id` from listings already filed under the agency (the badge simply stops if the agency loses `approved` status). Ownership transfer and arbitrary post-publish reassignment are out of scope for v1.
- **Public read scope via a SECURITY DEFINER view** (Q4 default): the agency read path is a SECURITY DEFINER view with an explicit `WHERE (status = 'approved' OR owner/active-member OR current_user_has_permission('agencies.view'))`, proactively applying the Phase 18 invoker-view gotcha (`supabase/migrations/20260530120010_fix_v_reports_definer_scoping.sql`) so a member's own `pending` agency stays visible to them while remaining hidden from the public. `auth.uid()` still resolves to the caller inside a definer view.
- **Vault-stored fields & document files** (ADR-0001): at minimum the registration/ID-document number is Vault-stored and admin-decrypt-only; the full list of Vault-backed agency-identity fields (e.g., a commercial-registration number) is finalized at plan time, but the spec mandates that no private identity number is ever a plaintext column or in a client-readable view. Verification document FILES live in a private storage bucket (owner/admin only); agency logos/cover live in a public bucket gated to `approved` agencies.
- **Frontend page scope**: Phase 19 ships `AgencyProfilePage` (public view + owner/admin edit), `AgencyMembersPage` (invite/accept/decline/role/remove + pending invitations), `AgencyListingsPage`, `AgencyVerificationFlow`, and a minimal `AgencyAnalyticsPage` (counters only). Rich agency analytics beyond simple counters is deferred (the Phase 20 admin dashboard owns cross-cutting counters). The "My Agency" Profile tile is placed after the Phase 18 "My Reports" tile (`lib/features/profile/presentation/pages/profile_page.dart`).
- **Routing**: new `/agency*` self-service routes (gated by active agency membership, mirroring the Phase 17 `/favorites` + Phase 18 `/reports` authenticated entries) and an `/admin/agencies` verification surface under the `/admin/...` namespace (gated by a `requireAgenciesManageRedirect` mirroring `requireReportsManageRedirect` / `requireListingReviewRedirect` in `lib/core/routing/auth_redirect.dart`) are added to the Phase 1 `go_router` surface (`lib/core/routing/app_router.dart`).
- **The `agencies.view`/`agencies.approve`/`agencies.suspend` permissions already exist** (seeded in Phase 6: `supabase/migrations/20260515120002_create_permissions.sql:43-45`, mapped to `admin` + `super_admin` in `…120003`; frontend constants `PermissionKeys.agenciesView/agenciesApprove/agenciesSuspend` at `lib/core/security/permission_keys.dart:34-36`). Phase 19 is their FIRST consumer and introduces NO new permission key.

- **No agency reporting, no promoted/paid agency tier, no ownership transfer, no agency-to-agency relationships, and no push notifications** are introduced in Phase 19 — each is a separate future spec. Publishers/owners/members are not notified of any agency event via push (Phase 22's concern); discovery is in-app.

## Clarifications

### Resolved — Session 2026-05-30

Three product-shaping decisions resolved during `/speckit-specify` before validation. Answers are folded into the Functional Requirements (FR-001, FR-013, FR-014, FR-019, FR-020), User Stories (US1, US2, US3), Edge Cases, Key Entities, and Assumptions.

- **Q1 — Agency verification as a publish gate**: Must an agency be admin-approved/verified before its members can publish listings under it (the acceptance criteria are ambiguous, and the existing listings RLS already gates publishing on the individual's approval)? → **A: Soft gate (badge only).** Members publish under a new agency immediately — the existing per-user `account_status`/`publisher_status` gate still applies; agency `approved` status unlocks only the public profile + verified badge. Zero new publish-blocking logic. A hard gate (block publishing until the agency is approved) was rejected as making a brand-new agency inert and requiring an agency-status branch in the publish path; a dual-approval hybrid was rejected as heaviest. See FR-020, FR-022, and US3/US5.
- **Q2 — Membership & invite model**: How do people become agency members (the plan says "invite by phone", which could mean existing users or pre-staged non-users)? → **B: Invite + in-app accept.** An agency `admin` invites an already-registered user by phone (no match → "user not found"); the invitee gets a `pending` membership and explicitly accepts (→ `active`) or declines in-app, discovered without push notifications. Immediate-active invite (no consent step) and pre-staging unregistered phones (auto-link at signup, needs Phase 22) were both rejected. This fixes the `agency_members.status` lifecycle at `pending` → `active` → removed. See FR-013, FR-014, and US3.
- **Q3 — Creation eligibility & cardinality**: Who can create an agency, and how many? → **A: Approved publishers, one each.** A user with `publisher_status = 'approved'` may create exactly one agency (UNIQUE `owner_user_id`). Reuses the existing publisher signal, avoids role-grant UX for the inert `owner`/`agent` roles, and sidesteps multi-agency ambiguity; a user may still be an `active` member of multiple agencies but own only one. Any-approved-account and multiple-agencies-per-owner were rejected for v1 simplicity. See FR-001 and US1.
