# Feature Specification: Admin Dashboard

**Feature Branch**: `020-admin-dashboard`
**Created**: 2026-06-01
**Status**: Draft
**Input**: Phase 20 — Admin dashboard, from `docs/IMPLEMENTATION_PLAN.md` (§ "Phase 20 — Admin dashboard")

> **Scope note**: Phase 20 introduces the **unified admin home** — a single, permission-gated landing surface that consolidates the admin tools built across Phases 5–19 into one place, surfaces at-a-glance operational counters (how much work is waiting), and offers quick navigation into each admin queue. It is a *consolidation + navigation + dashboard* feature, not a new business domain: it adds **no new business-data table**, introduces **no new permission key**, and re-uses the admin surfaces that already exist rather than re-implementing them. Phase 20 **upgrades the admin home that already exists** — `lib/features/admin/presentation/pages/admin_home_page.dart` (`AdminHomePage` at `/admin`), which since Phase 6 has accreted a permission-gated `ListView` of eight section tiles (account approvals, pending listing review, super-admin roles, admin inquiries, locations, currencies, reports, agencies — each wrapped in a `PermissionChecker.has/any` guard) plus an empty-state for a user with no tiles — into the unified dashboard the plan calls for, at the SAME `/admin` entry point and behind the **existing** `/admin` admin-access route guard (`authRedirect` already redirects any caller lacking every `PermissionKeys.adminCategoryKeys` key away from `/admin*`). The genuinely-new work is the operational counters, the counter→queue quick actions, the grid presentation, the not-yet-present section tiles, and a minimal read-only **audit-log viewer** (the Audit-logs section's destination, which no prior phase owns even though the `audit_logs` table + `audit_logs.view` permission already exist). Phase 20 ships exactly: (a) a **permission-gated tile grid** — one tile per admin section, where each tile renders ONLY if the signed-in user holds the section's gating permission (via the Phase 6 frontend `PermissionChecker.has/any`), and tapping a tile routes to that section's existing admin surface; the canonical section set is the plan's ten — **Users, Listings, Locations, Currencies, Reports, Ads, Roles, Permissions, Settings, Audit logs** — plus **Agencies** and **Inquiries**, the two `*.view`/`*.view_all`-gated admin surfaces already present on the admin home that the plan's (earlier-written) section list omits; note **Roles** and **Permissions** are surfaced as a SINGLE combined "super-admin" tile (gated by the `roles.*` + `permissions.manage` `superAdminCategoryKeys`) and remain combined in Phase 20 (resolved in Clarifications); (b) **operational counters** — the five counts named in the plan's Phase 20 backend deliverable: **pending users**, **pending listings**, **open reports**, **new inquiries (last 24h)**, and **active listings**, each computed by a single bounded aggregate path (`admin_dashboard_counts()`), each gated to the same permission as its section so a counter is never returned to a caller who may not see that section; (c) **quick actions** — each counter/tile deep-links into the most relevant filtered queue (pending listings → the Phase 12 listing-review pending queue; open reports → the Phase 18 reports queue filtered to open; pending users → the Phase 5/6 account-approval queue; etc.), so the dashboard is a launchpad, not a dead-end; (d) **refresh** — counters refresh on screen entry and on explicit pull-to-refresh, with Phase 20 limited to **polling / manual refresh ONLY**; the plan explicitly defers Realtime-driven auto-refresh to Phase 22, so the dashboard is structured so a later phase can subscribe to Realtime signals without redesign; (e) **backend permission enforcement** — the counts aggregate enforces the caller's permissions server-side (via the Phase 6 `current_user_has_permission(...)` helper / RLS) so the count posture matches the tile posture at BOTH ends (frontend hide AND backend deny), never leaking a count for a section the caller cannot access; (f) **graceful states** — localized loading, empty/zero, and error states, with tiles remaining navigable even when counts fail to load (navigation is independent of the counters); (g) the **localization layer** gains the dashboard strings (the admin-home title, every tile label, every counter label, the coming-soon label, and the loading/empty/error states) flowing through `AppLocalizations` with `ar` and `en` entries per Phase 3, rendering correctly in all four (light/dark) × (Arabic RTL / English LTR) combinations using Phase 2 design tokens. Sections whose dedicated admin surface is **not yet built** at Phase 20 — namely **Ads** (Phase 21) and **Settings** (Phase 23) — render as a **disabled "coming soon" tile** that is STILL permission-gated, so the later phase only wires the destination route without restructuring the dashboard (resolved in Clarifications). The **Audit-logs** section is the exception: it has the `audit_logs` table + `audit_logs.view` permission but no owner phase, so Phase 20 builds a minimal read-only audit-log viewer for it (resolved in Clarifications). Phase 20 does NOT add Realtime (Phase 22); does NOT build the Ads or Settings surfaces themselves (Phases 21/23); does NOT modify any gated admin surface, the permission catalog (§9.1), any role-permission seed, or any existing business table; does NOT introduce cross-publisher data exposure beyond the already-permissioned counts; and does NOT add any new third-party dependency. Phase 20 honors Principle VII (every tile and every counter is gated by a data-driven permission key — never a hardcoded role branch — so a role-permission change re-shapes the dashboard on the next session refresh with no code change), Principle V (all new strings localized `ar`/`en`), Principle VI (themed via Phase 2 tokens, four-combination correct), and Principle I (this spec precedes any implementation).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — An admin opens one home that shows only the tools they are allowed to use (Priority: P1)

A staff member who holds one or more admin permissions opens the app and navigates to the admin area. Their admin home — already a permission-gated list of tiles since Phase 6 — is now a unified dashboard: a grid of section tiles (Users, Listings, Locations, Currencies, Reports, Agencies, Inquiries, Roles & Permissions, Audit logs, Ads, Settings) that also carries live operational counters. Crucially, they see ONLY the tiles for the sections their permissions grant: a moderator (who can review listings and reports but not manage currencies or roles) sees the Listings, Reports, and Users tiles but not the Currencies, Roles, Permissions, or Settings tiles, while a super admin sees them all. Tapping a tile takes them straight to that section's existing admin surface.

**Why this priority**: P1 because the permission-gated tile hub IS the feature's foundation — it is the consolidated admin home the IMPLEMENTATION_PLAN's Phase 20 goal ("a unified admin home consolidating counters, queues, and quick actions") centers on, and the plan's first acceptance criterion ("An admin sees only the tiles they have permissions for") is exactly this story. Counters and refresh build on top of this grid.

**Independent Test**: Sign in as an admin whose role grants a known subset of admin permissions (e.g., a moderator with `listings.approve` + `reports.manage` + `users.view`). Open the admin home; confirm (a) tiles for the granted sections render and tiles for non-granted sections (e.g., Currencies, Roles, Permissions, Settings) do NOT, (b) tapping a rendered tile routes to that section's existing admin surface (Listings → listing-review queue, Reports → reports queue, Users → account-approval queue). Sign in as a super admin; confirm all sections render. Sign in as a user with NO admin permission; confirm the admin home is not reachable (redirected).

**Acceptance Scenarios**:

1. **Given** a signed-in user holding ≥ 1 admin permission, **When** they open the admin area, **Then** the unified admin home renders a grid of section tiles, and ONLY the tiles whose gating permission(s) the user holds are shown (each other tile is absent, not greyed).
2. **Given** two admins with different permission sets (e.g., a moderator vs. a super admin), **When** each opens the admin home, **Then** the visible tile set differs and matches each user's permissions exactly.
3. **Given** an admin viewing a tile, **When** they tap it, **Then** the app routes to that section's existing admin surface (e.g., Listings → the Phase 12 listing-review queue, Reports → the Phase 18 reports queue, Agencies → the Phase 19 agency-verification queue).
4. **Given** a signed-in user with NO admin permission, **When** they attempt to reach the admin home route, **Then** access is denied at the route guard and they are redirected (the admin home is not rendered).
5. **Given** a section whose dedicated admin surface is not yet implemented (e.g., Ads, Settings), **When** a permitted admin views the dashboard, **Then** that section renders as a disabled "coming soon" tile (still permission-gated to its key) that does not navigate, rather than being silently omitted or routing to a missing page.

### User Story 2 — An admin sees how much work is waiting, at a glance (Priority: P1)

An admin opening the dashboard immediately sees operational counters telling them what needs attention: how many users are pending approval, how many listings are pending review, how many reports are open, how many new inquiries arrived in the last 24 hours, and how many listings are currently active. Each counter sits with (or on) its section's tile, and — like the tiles — a counter only appears for an admin who is permitted to see that section: an admin without report-moderation permission sees no open-reports count at all.

**Why this priority**: P1 because the counters are half of the plan's Phase 20 goal ("consolidating **counters**, queues, and quick actions") and the entire reason for a dashboard over a plain menu — they turn the admin home from a navigation list into an operations overview. Without them the admin must open each queue to learn whether work is waiting.

**Independent Test**: Seed a fixture with a known number of pending account-approval requests, pending-review listings, open reports, inquiries created within 24h, and active (approved, in-window) listings. Sign in as a super admin; open the dashboard; confirm each of the five counters matches the seeded counts. Sign in as an admin lacking `reports.manage`; confirm the open-reports counter is absent (not shown as zero). Sign in as an admin lacking `inquiries.view_all`; confirm the new-inquiries counter is absent.

**Acceptance Scenarios**:

1. **Given** a permitted admin opens the dashboard, **When** it loads, **Then** the operational counters render — **pending users**, **pending listings**, **open reports**, **new inquiries (last 24h)**, **active listings** — each showing a count drawn from the underlying data.
2. **Given** an admin who does NOT hold a section's gating permission, **When** the dashboard loads, **Then** that section's counter is absent (it is not computed for nor returned to that caller), consistent with that section's tile being absent.
3. **Given** seeded fixture data with known counts, **When** the dashboard loads, **Then** each visible counter equals the corresponding count in the fixture.
4. **Given** the "new inquiries" counter, **When** it renders, **Then** it counts only inquiries created within the last 24 hours (a rolling window), not the all-time total.
5. **Given** the counts are still loading or fail to load, **When** the dashboard renders, **Then** a localized loading state (then, on failure, a localized error/retry state) is shown for the counters — never a blank tile, a crash, or a misleading zero — AND the tiles remain navigable.

### User Story 3 — Dashboard counters and tiles are enforced at the data layer, not just hidden in the UI (Priority: P1)

The dashboard aggregates counts over sensitive tables (accounts awaiting approval, reported listings, inquiries). The product MUST guarantee that hiding a tile or a counter in the UI is backed by a real backend check: a caller who lacks a section's permission cannot retrieve that section's count by calling the aggregate directly, and a user with no admin permission cannot reach the dashboard data at all. Permission gating is data-driven — changing which permissions a role carries re-shapes the dashboard on the next session refresh, with no code change and no hardcoded role branch.

**Why this priority**: P1 because Constitution Principle VII (dynamic, data-driven permissions, no hardcoded role checks) and the "checks at both ends" discipline make a UI-only gate insufficient — a frontend that merely hides a counter while the backend would still return it to anyone is a leak. The counts aggregate over RLS-protected tables, so the aggregate path itself must enforce permission, and the route guard must deny non-admins.

**Independent Test**: From a session lacking `reports.manage`, invoke the counts aggregate directly (at the wire level, bypassing the UI); confirm the open-reports count is NOT returned. From a session with no admin permission at all, confirm the counts aggregate returns nothing/denies and the dashboard route redirects. From a `reports.manage` + `listings.approve` session, confirm exactly those counts return and unrelated counts (e.g., requiring `settings.manage`) do not. Grant `reports.manage` to that user's role, refresh the session, and confirm the Reports tile + open-reports counter now appear — with no code change.

**Acceptance Scenarios**:

1. **Given** an authenticated caller lacking a section's gating permission, **When** they invoke the counts aggregate directly, **Then** that section's count is not returned (the aggregate enforces the permission server-side, matching the UI hide — "checks at both ends").
2. **Given** a user with no admin permission, **When** they attempt to load the dashboard or its counts at the wire level, **Then** the request is denied / returns nothing AND the dashboard route redirects them away.
3. **Given** the counts aggregate, **When** it computes a section's count, **Then** it MUST respect the source table's RLS/permission rules and expose only the permitted aggregate count — never row-level data.
4. **Given** an admin's role gains or loses a permission, **When** the admin's permission state is refreshed (next session / cache refresh per Phase 6), **Then** the corresponding tile and counter appear or disappear accordingly — driven entirely by the data-driven permission keys, with no hardcoded role branch in the dashboard.

### User Story 4 — Counters stay current and act as shortcuts into the work queues (Priority: P2)

An admin keeps the dashboard open while working. They pull-to-refresh (or re-enter the screen) and the counters update to reflect newly submitted listings, fresh reports, and new inquiries. When a counter shows work waiting, the admin taps it and is taken straight into the relevant queue, already filtered to the work that needs attention (e.g., tapping "pending listings" opens the listing-review queue showing the pending items; tapping "open reports" opens the reports queue filtered to open reports).

**Why this priority**: P2 because keeping the numbers fresh and making them actionable ("quick actions") is the third part of the plan's goal and the plan's second acceptance criterion ("Counters refresh on pull-to-refresh ... Phase 20 uses polling"), but it sits on top of the P1 tiles + counters rather than being a prerequisite. Realtime auto-refresh is explicitly deferred to Phase 22.

**Independent Test**: Open the dashboard and note a counter (e.g., pending listings = N). From another session, submit a new listing for review (N should become N+1). Back on the dashboard, pull-to-refresh (or leave and re-enter); confirm the counter updates to N+1. Tap the pending-listings counter/tile; confirm it opens the listing-review queue showing the pending items. Confirm Phase 20 does NOT auto-update the counter without a refresh (Realtime is deferred to Phase 22).

**Acceptance Scenarios**:

1. **Given** the dashboard is open and underlying data changes, **When** the admin pull-to-refreshes or re-enters the dashboard, **Then** the affected counters update to the new values.
2. **Given** a counter showing work waiting, **When** the admin taps it (or its tile's primary action), **Then** the app deep-links into the relevant queue filtered to that work (pending listings → pending listing-review queue; open reports → open reports queue; pending users → account-approval queue; etc.).
3. **Given** Phase 20's refresh model, **When** underlying data changes while the dashboard is open and the admin does NOT refresh, **Then** the counter does NOT auto-update (Realtime-driven live updates are deferred to Phase 22) — and the dashboard is structured so Phase 22 can add a Realtime subscription without redesigning it.
4. **Given** the counts aggregate is queried, **When** it executes, **Then** it is a single bounded call (no unbounded per-tile full-table scans), so a refresh does not degrade with data volume.

### User Story 5 — The dashboard is fully localized and themed in every combination (Priority: P3)

Every admin — whether using the app in Arabic (RTL) or English (LTR), in light or dark theme — sees a correct, readable dashboard: localized title, tile labels, counter labels, the "coming soon" label, and the loading/empty/error states, with correct direction-aware layout and design-token styling.

**Why this priority**: P3 because localization and theming are cross-cutting quality gates the IMPLEMENTATION_PLAN calls out for Phase 20 (Principles V and VI), but they refine the experience delivered by the P1/P2 stories rather than being a standalone capability.

**Independent Test**: Open the dashboard and cycle the four combinations — (light, ar), (dark, ar), (light, en), (dark, en) — on the reference Infinix Note 8 and a 412 dp emulator profile; confirm every string is localized (no raw literals), the grid and tiles lay out correctly RTL and LTR, and colors/typography/spacing come from Phase 2 tokens (no clipped text, no mirrored-wrong icons, no inline hex).

**Acceptance Scenarios**:

1. **Given** the app locale is Arabic, **When** the dashboard renders, **Then** all strings appear in Arabic and the layout is RTL-correct (tiles, counters, and any directional icons mirror appropriately).
2. **Given** the app locale is English, **When** the dashboard renders, **Then** all strings appear in English and the layout is LTR-correct.
3. **Given** light and dark themes, **When** the dashboard renders in each, **Then** all colors, typography, spacing, and elevation come from the Phase 2 design tokens with no inline hex / raw font size / ad-hoc padding, in both themes.
4. **Given** any dashboard state (loaded, loading, empty/zero counts, error), **When** it renders, **Then** every user-visible string is sourced from `AppLocalizations` with both `ar` and `en` entries.

### Edge Cases

- **An admin holds exactly one admin permission**: The dashboard renders the single matching tile (and its counter, if that section has one) and nothing else; it MUST NOT render an empty grid or other sections' tiles. The dashboard is still reachable (≥ 1 admin permission qualifies).
- **A signed-in user holds NO admin permission**: The admin home route is guarded — the user is redirected (e.g., to the public home), and the counts aggregate returns nothing for them. There is no "empty admin home" shown to non-admins.
- **An anonymous (signed-out) visitor navigates to the admin route**: Treated as unauthenticated — redirected to sign-in / public home; never shown the dashboard shell or any count.
- **A counter's source surface is not yet built** (Ads → Phase 21, Settings → Phase 23): the section renders as a disabled "coming soon" tile with no live counter; the five plan-named counters (pending users / pending listings / open reports / new inquiries 24h / active listings) all map to surfaces that already exist by Phase 19, so no counter depends on an unbuilt surface.
- **Agencies tile**: Agencies (Phase 19) is NOT in the plan's literal Phase-20 section list but ships a `agencies.view`/`approve`/`suspend`-gated admin verification surface that belongs on the dashboard; it is included as an 11th section (recorded in Assumptions per Principle XII). An admin without any `agencies.*` permission does not see it.
- **A count is zero**: A permitted section with zero pending items shows its counter as `0` (a meaningful "nothing waiting" signal), distinct from the section being absent because the admin lacks permission — the two states (absent tile vs. zero counter) MUST be visually distinguishable.
- **The counts aggregate fails or times out** (network/server error): The tiles still render and remain navigable; the counters show a localized error/retry affordance rather than stale, blank, or misleading values — navigation never depends on the counters succeeding.
- **A very large data set** (tens of thousands of listings/reports): The counts come from a single bounded aggregate call; the dashboard MUST NOT issue an unbounded per-tile scan or fetch rows to count them client-side.
- **Permission changes mid-session**: If an admin's role loses a permission, the corresponding tile/counter disappears on the next permission-state refresh (per the Phase 6 permission-cache refresh model); the dashboard does not cache a stale tile set indefinitely. (The deeper Realtime-driven permission refresh is a Phase 22 concern — see `project_phase22_perm_cache_revisit`.)
- **Stale counts vs. the queue**: Because Phase 20 uses polling, a counter may briefly lag the actual queue (e.g., another admin just cleared an item). Tapping through always shows the live queue; the counter is a hint, not a source of truth, and converges on the next refresh. Realtime convergence is Phase 22.
- **Two sections share overlapping permissions**: Where a section is gated by any-of several permission keys (e.g., Listings via `listings.view_all` OR `listings.approve`), holding any one of them is sufficient to show the tile, matching how the underlying surface gates itself.

## Requirements *(mandatory)*

### Functional Requirements

#### Admin home & permission-gated tiles

- **FR-001**: System MUST upgrade the EXISTING admin home (`AdminHomePage` at `/admin`, today a permission-gated `ListView` of section tiles) into the unified dashboard at the same `/admin` entry point, presenting the section tiles as a counter-bearing grid. The dashboard MUST remain reachable by any signed-in user holding ≥ 1 admin permission and blocked for users with no admin permission and for anonymous visitors — REUSING the existing `/admin` admin-access route guard (`authRedirect` over `PermissionKeys.adminCategoryKeys`) and the existing per-section sub-route redirects (`requireListingReviewRedirect`, `requireReportsManageRedirect`, `requireAgenciesManageRedirect`, etc.); Phase 20 MUST NOT weaken, duplicate, or replace those guards.
- **FR-002**: Each section tile MUST be gated by the section's data-driven permission key(s) via the Phase 6 frontend `PermissionChecker` (`has` / `any`) — a tile MUST render ONLY when the signed-in user holds the required permission(s), and MUST be absent (not merely disabled or greyed) otherwise. Tapping an enabled tile MUST route to that section's existing admin surface.
- **FR-003**: The dashboard MUST define the canonical admin section set and each section's gating permission(s): **Users** (`users.view`/`users.approve`), **Listings** (`listings.view_all`/`listings.approve`/`listings.reject`/`listings.edit_any`), **Locations** (`locations.manage`), **Currencies** (`currencies.manage`), **Reports** (`reports.manage`), **Agencies** (`agencies.view`/`agencies.approve`/`agencies.suspend`), **Inquiries** (`inquiries.view_all`, routing to the existing `/admin/inquiries` oversight surface), **Roles & Permissions** (`roles.view`/`roles.create`/`roles.update`/`roles.delete` + `permissions.manage` — a single combined "super-admin" tile, kept combined in Phase 20), **Audit logs** (`audit_logs.view`), **Ads** (`ads.manage`), and **Settings** (`settings.manage`). Gating is "any-of" where a section's surface accepts any of several keys. Sections already present on the admin home (Users, Listings, Reports, Agencies, Inquiries, Locations, Currencies, Roles/Permissions) MUST keep their existing routes; only their presentation (grid + counter) changes.
- **FR-004**: Sections whose dedicated admin surface is NOT yet implemented at Phase 20 (notably **Ads** — Phase 21 — and **Settings** — Phase 23) MUST render as a **disabled "coming soon" tile** that is STILL permission-gated to its key and does NOT navigate, so the owning later phase only wires the destination route without restructuring the dashboard. (Resolved 2026-06-01 — see Clarifications; the rejected alternative was to omit such tiles until built.)
- **FR-005**: The dashboard MUST NOT re-implement any gated surface — each enabled tile MUST navigate to the EXISTING admin surface for that section (account approvals, listing review, locations CRUD, currencies, reports queue, agency verification, admin inquiry oversight, super-admin roles/permissions). The dashboard is a hub, not a duplicate; the ONLY admin surface Phase 20 itself builds is the minimal audit-log viewer (FR-021), because no prior phase owns it.
- **FR-021**: System MUST ship a minimal **read-only audit-log viewer** as the destination of the Audit-logs tile — the one net-new admin surface Phase 20 builds. It MUST present `audit_logs` entries (actor, action, target type/id, timestamp, and before/after state) ordered newest-first, MUST paginate (no unbounded scan), and MUST be strictly read-only (no create/edit/delete). It MUST be gated by `audit_logs.view` at BOTH the tile (`PermissionChecker`) AND the data layer — for which Phase 20 **swaps the existing `audit_logs_select_admin` RLS policy's predicate** from the role-based `current_user_is_admin()` (the §6.4 gate as shipped) to the data-driven `current_user_has_permission('audit_logs.view')`, so the read gate matches the tile gate ("checks at both ends") and obeys Principle VII; net access is unchanged today (only `admin`/`super_admin` hold `audit_logs.view`). The viewer MUST render localized and themed across the four (light/dark) × (Arabic RTL / English LTR) combinations. Optional filters (by action / target / actor / date range) are plan-time and not required for this phase.

#### Operational counters

- **FR-006**: The dashboard MUST display the operational counters named in the plan's Phase 20 backend deliverable: **pending users**, **pending listings**, **open reports**, **new inquiries (last 24 hours)**, and **active listings** — each associated with its section, sourced from the underlying data.
- **FR-007**: Each counter MUST be gated to the SAME permission as its section: **pending users** → `users.view`/`users.approve`; **pending listings** & **active listings** → `listings.view_all`/`listings.approve`; **open reports** → `reports.manage`; **new inquiries (24h)** → `inquiries.view_all`. A counter MUST NOT be computed for, returned to, or rendered for a caller who lacks the relevant permission.
- **FR-008**: The counters MUST be produced by a SINGLE bounded aggregate path (`admin_dashboard_counts()` per the plan) — the dashboard MUST NOT issue an unbounded per-tile full-table scan nor fetch rows to count them client-side; counting MUST remain bounded as data volume grows.
- **FR-009**: Each counter (and/or its tile's primary action) MUST deep-link to the relevant filtered queue as the "quick action": **pending listings** → the Phase 12 listing-review pending queue (`/admin/listing-review/pending`); **open reports** → the Phase 18 reports queue (`/admin/reports`) filtered to open; **pending users** → the Phase 5/6 account-approval queue (`/admin/approvals`); **new inquiries (24h)** → the existing admin inquiry oversight surface (`/admin/inquiries`); and equivalently for any other counter where a filtered queue exists.
- **FR-010**: A counter for a permitted section with no waiting items MUST render `0` (a meaningful "nothing waiting" state), VISUALLY DISTINCT from a section being absent because the admin lacks permission.

#### Refresh & freshness

- **FR-011**: Counters MUST refresh on dashboard entry and on explicit pull-to-refresh, and MUST NOT use a periodic auto-poll timer (no fixed-interval background refetch). Phase 20 MUST be limited to this on-entry + manual-refresh model; Realtime-driven auto-refresh MUST be explicitly deferred to Phase 22 — and the dashboard MUST be structured so Phase 22 can add a Realtime subscription (re-fetching counts on relevant change events) WITHOUT redesigning the surface.
- **FR-012**: While counts are loading the dashboard MUST show a localized loading state; on counts failure it MUST show a localized error/retry state — never a blank tile, a crash, or a misleading value. Tiles MUST remain navigable regardless of counter load state (navigation MUST NOT depend on the counts succeeding).

#### Security & permission enforcement (checks at both ends)

- **FR-013**: The counts aggregate MUST enforce the caller's permissions SERVER-SIDE (via the Phase 6 `current_user_has_permission(...)` helper and/or RLS), so the count posture matches the tile posture at BOTH the UI (PermissionChecker hide) AND the backend (deny). A caller lacking a section's permission MUST NOT be able to obtain that section's count by calling the aggregate directly.
- **FR-014**: The counts aggregate MUST respect each source table's RLS/permission rules and expose ONLY permitted aggregate counts — never row-level data. A user with no admin permission MUST receive no counts and MUST be denied the dashboard data path.
- **FR-015**: All gating MUST be data-driven — the dashboard MUST NOT contain any hardcoded role branch (e.g., `if role == 'admin'`). Adding or removing a permission from a role MUST re-shape the visible tiles and counters on the next permission-state refresh (per Phase 6), with no code change (Principle VII).

#### Localization, theming, accessibility

- **FR-016**: Every user-visible string introduced by Phase 20 — the admin-home title, every section tile label, every counter label, the "coming soon" label, and the loading / empty-zero / error states — MUST flow through `AppLocalizations` with both `ar` and `en` entries (Principle V).
- **FR-017**: The dashboard (tile grid, counters, coming-soon tiles, and all loading/empty/error states) MUST render correctly in all four combinations of (light/dark theme) × (Arabic RTL / English LTR), using logical/direction-aware insets and Phase 2 design tokens — no inline hex literals, no raw font sizes, no ad-hoc paddings (Principle VI).

#### Constitutional & dependency constraints

- **FR-018**: The PR MUST NOT add any new third-party dependency — the dashboard is implemented with the existing Flutter / BLoC / `go_router` / `supabase_flutter` stack, the Phase 6 `PermissionChecker`, and a single Supabase aggregate (view or RPC) for the counts. No new pubspec package, no new Postgres extension, no Android manifest change.
- **FR-019**: The PR MUST NOT introduce a new permission key, MUST NOT alter the §9.1 permission catalog or any role-permission seed, and MUST NOT modify any existing admin surface or business-data table. The only backend changes are read-only and additive-or-aligning: the counts aggregate (a view/RPC) the plan authorizes, and a one-statement swap of the existing `audit_logs_select_admin` RLS policy's predicate to `current_user_has_permission('audit_logs.view')` (FR-021); no new business table is created, no table schema is mutated, and no existing admin feature is changed.
- **FR-020**: The PR MUST NOT introduce Supabase Realtime in Phase 20 (deferred to Phase 22) and MUST NOT add eager Realtime subscriptions — refresh is polling / pull-to-refresh only, consistent with the plan and the project performance posture.

### Key Entities

- **Admin Dashboard**: The unified, permission-gated admin home at `/admin` that consolidates the admin section tiles, the operational counters, and the quick-action deep links into one surface. Reachable by any holder of ≥ 1 admin permission; replaces the Phase 6 placeholder admin home.
- **Section Tile**: A navigable entry for one admin section, carrying a localized label, an icon, the gating permission key(s), and either a destination route (when the section's surface exists) or a disabled "coming soon" state (when it does not). Rendered only when the signed-in user holds the gating permission. Canonical sections: Users, Listings, Locations, Currencies, Reports, Agencies, Inquiries, Roles & Permissions (today one combined "super-admin" tile), Audit logs, Ads, Settings.
- **Operational Counter**: A single named count surfaced on the dashboard (pending users, pending listings, open reports, new inquiries-24h, active listings), gated to its section's permission, sourced from the counts aggregate, and deep-linking to the relevant filtered queue. A `0` value is a meaningful "nothing waiting" state.
- **Admin Dashboard Counts**: The bounded aggregate snapshot (the `admin_dashboard_counts()` view/RPC) that computes the operational counters in one call, enforcing the caller's permissions server-side and returning only the counts that caller is permitted to see.
- **Quick Action**: The deep-link behavior attached to a counter/tile that opens the relevant admin queue pre-filtered to the work it represents (e.g., open reports → reports queue filtered to open).

## Success Criteria *(mandatory)*

- **SC-005**: After underlying data changes (e.g., a new listing submitted for review), a pull-to-refresh (or screen re-entry) updates the affected counter to the new value within one refresh; with no refresh, the counter does NOT auto-update (Realtime deferred to Phase 22) — both verified on the reference device.
- **SC-006**: Tapping a counter / its tile opens the corresponding filtered queue (pending listings → listing-review pending queue; open reports → open reports queue; pending users → account-approval queue) — verified for each counter that has a filtered queue.

## Assumptions

- **Phase 20 is the Admin dashboard, not Ads.** The IMPLEMENTATION_PLAN numbers Phase 20 = "Admin dashboard" (`specs/020-admin-dashboard/`) and Phase 21 = "Ads & banners admin module" (`specs/021-ads-banners/`). This spec covers the Admin dashboard; the ads work is a separate, later spec.
- **The dashboard upgrades the EXISTING admin home in place** (not a new surface): `AdminHomePage` at `/admin` already renders a permission-gated `ListView` of eight tiles (account approvals, pending listing review, super-admin roles, admin inquiries, locations, currencies, reports, agencies), each gated by `PermissionChecker.has/any`, plus an `_EmptyState`. Phase 20 upgrades this same page to the grid-plus-counters dashboard at the same route — it does NOT build a new admin home and does NOT leave a second surface behind. The genuinely-new work is the counters, the quick-action deep links, the grid presentation, the not-yet-present tiles (Ads/Settings as disabled coming-soon), and the minimal read-only audit-log viewer (FR-021).
- **The `/admin` route guard already exists and is reused** (not rebuilt): the global `authRedirect` already blocks any caller lacking every `PermissionKeys.adminCategoryKeys` key from `/admin` and `/admin/*`, and each sensitive sub-route has its own redirect (`requireListingReviewRedirect`, `requireSuperAdminRedirect`, `requireReportsManageRedirect`, `requireAgenciesManageRedirect`, `requireLocationsManageRedirect`, `requireCurrenciesManageRedirect`, and the inline `inquiries.view_all` guard on `/admin/inquiries`). Denials route to `/admin?denied=<section>`. Phase 20 reuses these; the route-guard requirements in this spec (FR-001, US1) describe the existing behavior the dashboard relies on, not new guards to build.
- **Inquiries is already an admin section** (`inquiries.view_all` → `/admin/inquiries`, the Phase 16 US7 admin inquiry-oversight page) and is therefore both a dashboard tile AND the deep-link target for the "new inquiries (last 24h)" counter — even though the plan's (earlier) Phase-20 section list names neither Inquiries nor Agencies. Both are included per Principle XII.
- **Roles and Permissions are currently one combined tile**: the live admin home exposes a single "super-admin" tile gated by `superAdminCategoryKeys` (`roles.*` + `permissions.manage`) routing to `/admin/super-admin/roles`, rather than two separate Roles and Permissions tiles as the plan's section list implies. Phase 20 keeps them combined (resolved in Clarifications). (`permissions.manage` is seeded but is described in the catalog as "post-v1 if ever," so a separate Permissions surface may never materialize.)
- **Coming-soon tiles for not-yet-built sections** (resolved 2026-06-01, see Clarifications): the sections whose dedicated surface is not yet built — Ads (Phase 21) and Settings (Phase 23) — render as disabled, permission-gated "coming soon" tiles so the later phase only wires the route. The rejected alternative was to OMIT such tiles until their phase ships; "coming soon" was chosen because the plan explicitly enumerates Ads and Settings in the dashboard's section list, so showing them (disabled, gated) honors the plan and signals the roadmap, while omission would silently drop two plan-named sections. **Audit logs is the exception** — its table + permission exist but no phase owns a viewer, so Phase 20 builds a minimal read-only viewer for it (FR-021), rather than a coming-soon tile. Recorded per Principle XII.
- **Agencies is included as an 11th section** even though the plan's literal Phase-20 section list (written before the agency work) names ten (Users, Listings, Locations, Currencies, Reports, Ads, Roles, Permissions, Settings, Audit logs): Phase 19 shipped a `agencies.*`-gated admin verification surface that logically belongs on the admin home, so the dashboard includes an Agencies tile gated by `agencies.view`/`approve`/`suspend`. Recorded per Principle XII (no hidden product decisions).
- **The five operational counters are exactly the plan's named set** — pending users, pending listings, open reports, new inquiries (last 24h), active listings — each mapping to a surface that already exists by Phase 19. Additional counters (e.g., agencies pending verification) are out of scope for Phase 20 and may be added by a later refinement; the plan names only these five.
- **Counter semantics**: "pending users" = accounts/approval-requests awaiting an approval decision; "pending listings" = listings in `pending_review`; "open reports" = reports in a non-terminal status (`new`/`reviewing`); "new inquiries (last 24h)" = inquiries created within a rolling 24-hour window; "active listings" = listings currently `approved` and within their publish window. The exact predicates reuse the existing Phase 5/10/12/16/18 status definitions; no new status is introduced.
- **Counter permission mapping** follows the §6.4 RLS matrix and §9.1 catalog: pending-users → `users.view`/`approve`; pending/active-listings → `listings.view_all`/`approve`; open-reports → `reports.manage`; new-inquiries → `inquiries.view_all`. Where a section's surface accepts any of several keys, holding any one suffices to show that tile/counter.
- **The counts aggregate is a permission-aware read path** (a SECURITY DEFINER view or RPC, e.g., `admin_dashboard_counts()`), mirroring the project's established pattern of permission-gated server-side reads — it returns only the counts the caller is permitted to see and never exposes row-level data. Whether it is implemented as a view or an RPC is a plan-time detail (the plan says "Materialized view or RPC"); a non-materialized definer function is the likely default to avoid staleness, but the spec mandates only the behavior (bounded, permission-aware), not the mechanism.
- **Refresh is polling / pull-to-refresh only in Phase 20**; Realtime-driven live counters are deferred to Phase 22, which will subscribe to `listings`/`reports` change signals and re-fetch counts. The dashboard is built to accept that subscription later without redesign. (Phase 22 must also revisit the Phase 6 permission-cache refresh — see `project_phase22_perm_cache_revisit`.)
- **Permission-state freshness reuses the Phase 6 model** — the dashboard reflects the user's current permission set as maintained by the Phase 6 `PermissionChecker` cache (refreshed on login / session refresh / the established refresh points); Phase 20 does not add a new permission-refresh mechanism.
- **No new automated tests** are added, per the project's MVP manual-verification convention; verification is by manual on-device walks and direct wire-level/SQL inspection against fixtures, recorded against the Success Criteria.
- **No notifications, no cross-publisher row exposure, no settings/ads business logic** — the dashboard surfaces only already-permissioned aggregate counts and navigation; it adds no new data exposure beyond the counts and builds none of the Ads (Phase 21), Settings (Phase 23), or Realtime/notifications (Phase 22) functionality those phases own.
