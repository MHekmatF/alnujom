> **Scope note**: Phase 11 introduces the *media authoring surface and storage layer* that Phase 10's no-op `step_media_placeholder.dart` was forward-stating. It does NOT change the listing-status engine (Phase 10 owns `submit_listing` / the status-transition trigger / the public-read-when-approved RLS — Phase 11 only amends `submit_listing` per Q1=A's `images_below_minimum` check), it does NOT introduce admin approval (Phase 12 owns `approve_listing` / `reject_listing`), it does NOT render the gallery on the public listing-details surface (Phase 13 owns the consumer side via the same `listing_media` rows), and it does NOT add server-side watermark re-application (deferred per IMPLEMENTATION_PLAN §6.5 — "Watermark applied client-side before upload (v1); server-side later"). Per Q2=D, the external-video-link UI is deferred to a future spec — the `kind` enum retains the `'external_link'` value for forward-compat but no Phase 11 UI exercises that path.

## Clarifications

### Session 2026-05-22

The three questions below were resolved in-session before `/speckit-plan`. They shape `submit_listing`'s media required-field contract (Phase 11 strengthens Phase 10's FR-010a per Q1), the external-video-link moderation surface (deferred to a future spec per Q2), and the image-replace UX on the rejected-resubmit path (Q3). Answers are folded into the "Functional Requirements", "Success Criteria", and "Assumptions" sections below.

- **Q1 — Minimum-media required-field strengthening of `submit_listing`**: Does Phase 11 strengthen Phase 10's `submit_listing` required-field set (FR-010a) to include a minimum image count? → **A: Require ≥1 image.** Phase 11 strengthens Phase 10's FR-010a to require at least one `listing_media` row with `kind='image'` AND `watermarked=true` before `submit_listing` accepts the `draft → pending_review` (or `rejected → pending_review`) transition. The `submit_listing` RPC's `missing_fields[]` payload gains a new key `listing_media.images_below_minimum` (with `min=1` carried in the DETAIL payload for future-spec extensibility). The client-side form's Review-step Submit button mirrors the same check, disabling Submit when the listing has zero `kind='image'` rows. This matches industry-standard real-estate marketplaces (Aqarmap, Bayut, Zillow, Realtor.com); the publisher friction is one extra picker step at the cost of keeping the Phase 12 admin queue free of zero-photo submissions. Resubmit-after-rejection inherits the same check — a publisher who deletes all their images on the Q3=A edit-in-place path and tries to resubmit hits the same rejection.
- **Q2 — External-video URL allowlist for `kind='external_link'` rows**: When a publisher pastes an external video link in the MediaPicker, which hosts does the form accept? → **D: Disable `external_link` kind in Phase 11.** The Phase 11 MediaPicker exposes ONLY "Add images" (capped at 10 per FR-005) and "Add video" (direct MP4 file upload, capped at 2 per FR-005); there is NO "Add external link" CTA, NO URL text field, NO host badge rendering, and NO external-video-URL validator. The schema's `kind` enum retains the `'external_link'` value per Phase 9 / Phase 10 forward-stated forward-compat precedent (matches IMPLEMENTATION_PLAN §6.2's stated enum), but the Phase 11 UI has zero affordance to insert a `kind='external_link'` row. Any direct-SQL INSERT of an `external_link` row by an admin succeeds at the schema layer (the CHECK constraints in FR-002 still validate mutual exclusivity between `storage_path` and `external_url`), but Phase 11's UI never exercises the path. The 2-video cap from FR-005 retains its combined `kind IN ('video', 'external_link')` predicate as defense-in-depth so a future-spec UI can layer external-link entry on top without re-doing the trigger. The "external video link" use case Phase 11 anticipates remains exercisable in production only by direct admin SQL until the future-spec UX lands; a future-spec extension will introduce the validator, the URL field, and the host-badge rendering.
- **Q3 — Image-replace UX on the resubmit-after-rejection path**: When a publisher opens the MediaPicker on a `rejected` listing whose existing images already live in the `listing-images` bucket (watermarked at first upload), what does the picker surface? → **A: Edit-in-place + Add more.** The MediaPicker renders every existing `listing_media` row for the listing as a thumbnail in the picker grid on entry, with the watermark preserved, the `ordering` honored, the `is_main` badge floating on the main row, and per-thumbnail actions (set-main, delete, drag-reorder) wired identically to the first-upload flow. Appending new images uploads + watermarks them and inserts new `listing_media` rows; no bucket objects are removed at media-step entry. This is the "edit-in-place" path and matches Phase 10's research R-14 invariant ("draft mutated in place across resubmits — stable UUID preserves audit lineage") — every existing row's UUID `id` is preserved across the resubmit, so audit-log lineage and the `created_at` timestamp survive intact. Per-image "Replace" (Q3=C) and "Clear-and-re-upload" (Q3=B) are not in Phase 11 scope; a publisher who wants to replace a specific image deletes the old row (which removes the bucket object) and then uploads the new one.
- **Q4 — Image format support: source-accept set vs bucket-store set**: Should the picker accept formats beyond JPEG (e.g., iPhone HEIC/HEIF, PNG, WebP) and normalize them before upload, or reject anything that isn't JPEG at the file-pick step? → **A (with explicit source-format normalization): JPEG-only at the bucket, but the picker accepts a broader source set and converts.** The `listing-images` bucket's `allowed_mime_types` is narrowed to `['image/jpeg']` ONLY — every stored object is a JPEG (matches FR-014 step (e)'s always-JPEG re-encode). At the file-pick layer, the picker accepts the following source formats and normalizes each to JPEG inside the FR-014 pipeline before upload: **JPEG** (`image/jpeg`, treated as native input — still goes through the EXIF-strip + downscale + watermark steps; no decode-and-re-encode round-trip if the source is already a valid baseline JPEG at ≤ 1920 px long edge, in which case only EXIF-strip + watermark composite are applied), **PNG** (`image/png`, converted to JPEG; transparency is composited against a white background before watermark — this is acceptable since real-estate photos rarely carry meaningful transparency), **HEIC / HEIF** (`image/heic`, `image/heif`, the iPhone default since iOS 11 — common in WhatsApp / Telegram cross-platform shares to Android publishers' phones; decoded and converted to JPEG), and **WebP** (`image/webp`, increasingly common in Telegram stickers / browser saves; decoded and converted to JPEG). Formats outside this accept set (BMP, TIFF, GIF, SVG, RAW camera files, exotic codecs) are rejected at the file-pick step with a localized "this image format cannot be read — please pick a JPEG, PNG, HEIC, or WebP" message. The chosen Dart image library MUST be able to decode all four accepted formats; the plan-time research file picks the library — note that the pure-Dart `image` package historically had no HEIC support, so a native plugin or hybrid pipeline (e.g., `flutter_image_compress`, `image_picker`'s built-in HEIC→JPEG conversion on iOS, or a dedicated `heif_converter` plugin) may be required for HEIC decode on Android. This decision intentionally favors publisher experience (don't block on file format — convert silently) over server simplicity.
- **Q5 — Android image-picker manifest permissions**: Which permissions does the AndroidManifest.xml declare for the MediaPicker to access the device gallery across the Android-version range that APK-distributed publishers may install on? → **A: Both permission sets, version-aware runtime requests via `image_picker` plugin.** The AndroidManifest.xml declares BOTH the legacy `READ_EXTERNAL_STORAGE` (for Android ≤ 12 / API ≤ 32) AND the granular Android-13+ permissions `READ_MEDIA_IMAGES` and `READ_MEDIA_VIDEO` (for Android ≥ 13 / API ≥ 33). The `image_picker` Flutter plugin (the planned-time picker per the updated Assumptions image-library bullet) handles version-aware runtime requests internally — on Android 13+ it requests the granular media permissions; on Android ≤ 12 it requests the legacy storage permission. The runtime permission flow is invoked the first time the publisher taps "Add images" or "Add video"; if the publisher denies, the picker surfaces a localized "gallery access is required to upload photos" message with a "Open settings" affordance that deep-links to the app's Android settings page (`android.settings.APPLICATION_DETAILS_SETTINGS` intent). Camera access (for in-app capture) is NOT in Phase 11 scope — the picker only reads from the existing gallery; an in-app camera capture path is forward-stated to a future spec. The reference QA device (Infinix Note 8, Android 10/11 per `user_test_device.md`) exercises only the legacy permission code path; the granular Android-13+ path is exercised on a secondary test device or emulator (Pixel 8 Pro emulator running Android 14, available per `project_android_emulator_window_offscreen.md`).
- **Q6 — Hard cap on source image resolution before decode**: Does the pipeline cap source image dimensions BEFORE the full-decode step, to prevent OOM on the 6 GB Helio G80 ceiling? → **B: Cap at 8000×8000 px (~64 MP) via header-only metadata read.** Before step (b) of the FR-014 pipeline (the full pixel decode), the picker reads ONLY the source file's header metadata (JPEG SOF0 marker, PNG IHDR chunk, HEIC `ispe` box, WebP VP8X chunk) to extract pixel dimensions without decoding raw pixels — a constant-cost operation regardless of source file size. If either `width > 8000` OR `height > 8000`, the picker rejects the file with a localized "this image is too large — please pick a smaller photo (max 8000×8000 pixels)" message AND no `listing_media` row is inserted AND no decode-then-OOM cycle runs. The 8000×8000 cap accommodates every realistic phone-camera shot in production (12 MP iPhone = 4032×3024; 50 MP Samsung S25 = 8160×6120; 48 MP Infinix Note 8 main camera = 8000×6000) while stopping pathological inputs (16K × 9K test patterns, 200 MP modes that flagship cameras can produce). Combined with the existing OOM-catch in US4 scenario 2 (decode failure surfaces as per-thumbnail error state with Retry), the publisher path against malformed or unusually large sources is graceful: header-cap rejects clean cases before decode; OOM-catch handles the remaining corner cases. This decision favors a deterministic file-pick UX over premium-camera permissiveness; a future spec MAY raise the cap if the device floor shifts upward.
- **Q7 — Per-image processing timeout in the FR-014 pipeline**: How long does the picker wait on a single image's full decode + downscale + watermark + upload (including retries) before surfacing a timeout error? → **B: 60-second hard timeout per image.** The MediaPicker enforces a 60-second per-image timeout that starts when the file is picked AND covers the full FR-014 pipeline (header-read, decode, EXIF-strip, downscale, watermark composite, JPEG re-encode, upload, plus the existing US4 / edge-case 2-retry exponential-backoff window of 1s + 4s = 5s of retry budget). If the pipeline has not committed the `listing_media` row within 60 seconds, the in-flight isolate / HTTP request is cancelled, any partial bucket object is removed via Storage DELETE (defense-in-depth — though a partial Supabase Storage upload typically does not produce a visible object), the picker thumbnail switches to an error state with a localized "this upload took too long — please try again" message AND a Retry action. The 60-second budget is generous enough to cover a 5 MB JPEG over a slow Syrian mobile data link (~700 kbps sustained, common on 3G fallback) AND tight enough to surface a stuck pipeline before the publisher abandons the form. The timeout is per-image — the 8-image batch from US4 has a combined budget of 8 × 60s = 480 s worst case, but the US4 happy-path target (45 s for 8 images) is well inside that. The timeout is enforced from the BLoC layer (`Future.timeout(Duration(seconds: 60))` or equivalent), not at the Supabase SDK layer — the SDK's own default timeout is internal and not overridden. This decision favors deterministic UX recovery over premium-network-speed optimism.
- **Q8 — Supabase Storage bucket access mode (public + RLS vs private + signed URLs)**: How does the public-read-when-approved policy from FR-006 / FR-007 translate to a Supabase Storage bucket configuration — `public: true` with RLS as the access filter, or `public: false` with every read requiring a short-lived signed URL? → **A: Public bucket + RLS on `storage.objects`.** Both buckets (`listing-images` and `listing-videos`) are configured with `public: true` in the Supabase Storage bucket-create migration. RLS policies on `storage.objects` are the authoritative access filter — they enforce the same `parent.status='approved'` AND publish-window predicate that FR-006 enforces on the parent `listings` row. Public callers fetch images via stable URLs from `supabase.storage.from(bucket).getPublicUrl(path)` — no token, no expiry, no rotation on each render. Phase 13's gallery widget and Phase 14's search-result thumbnails consume these stable URLs and may cache them indefinitely (via `cached_network_image` already in Phase 1's pubspec) since the URL never changes for a given path. The RLS policies are the single point of access enforcement; a mis-edited policy is the only failure mode. The constitutional review on every RLS policy (Constitution III) plus SC-008 / SC-025 verification cover that risk. Private buckets + signed URLs were rejected because (a) every Phase 13 render would have to mint a signed URL via an RPC call (multiplicative SDK churn on a paginated home feed), (b) cached signed URLs would expire mid-session and the gallery would need URL refresh logic, (c) URL-expiry creates an additional axis of debug surface for Phase 13. The mixed-mode (private videos + public images) was rejected because asymmetry between the two buckets complicates the Phase 13 gallery's media-loader. A future spec MAY reconsider for the video bucket specifically if storage egress costs warrant the strictness — Phase 11 ships uniform public-bucket + RLS for both.

### User Story 1 — Approved publisher uploads images on a draft listing, sees watermark applied, reorders, marks one as main, submits (Priority: P1)

A signed-in user whose `profiles.publisher_status='approved'` AND `account_status='approved'` opens the Phase 10 multi-step listing form, walks through the basics → location → details → prices → visibility-settings steps as usual, and arrives at step 6 — which in Phase 11 is no longer the no-op banner but the real **MediaPicker** widget. The publisher taps "Add images", picks 4 images from their device gallery, and the form processes each image through a client-side pipeline: (a) decode + EXIF-orientation correction + EXIF-block strip, (b) downscale so the long edge ≤ 1920 px, (c) composite the AlNujom logo as a semi-transparent overlay at the FR-014 default position (bottom-end corner, 15% opacity, 18% of image long edge), (d) re-encode as JPEG (quality 85), (e) upload the watermarked bytes to `listing-images` bucket at a deterministic storage path `<listing_id>/<ordering>_<rand>.jpg`, (f) insert one `public.listing_media` row carrying `(listing_id, kind='image', storage_path, ordering, is_main, watermarked=true)`. The picker grid renders each uploaded image as a thumbnail with overlaid badges: a "main" badge on the row marked `is_main=true`, an order number, and per-thumbnail actions (set-main, delete, drag-to-reorder). The publisher drags the third image to the front position to make it the lead photo. The publisher long-presses the second image to "Set as main" — the picker UPDATEs `is_main` to true on that row and false on the row that was previously main (the schema's partial unique index enforces this server-side as defense-in-depth). The publisher taps "Continue", advances to step 7 (Review). The review step renders a horizontal carousel preview of the four watermarked thumbnails in the publisher's chosen order, with the main image highlighted. The publisher taps Submit. Phase 10's `submit_listing` runs with the Q1=A media-count check folded into FR-022 (≥1 `kind='image'` row required), the status flips `draft → pending_review`, and the dashboard re-renders.

**Why this priority**: P1 because the entire phase exists to ship this flow. Without US1, listings reach the Phase 12 admin queue without photos and the marketplace cannot launch (Constitution XI Android-First MVP requires a feature-complete v1, and a real-estate marketplace without listing photos is not a v1). The MediaPicker also unlocks Phase 13's gallery widget on the public listing-details surface.

### User Story 2 — 10-image / 2-video cap enforced at client AND server (Priority: P1)

The MediaPicker counts existing `listing_media` rows for the active listing and disables the "Add images" CTA once the count reaches 10 (`kind='image'`). It similarly disables the "Add video" CTA at 2 (`kind IN ('video', 'external_link')` combined). Attempting to upload an 11th image via any client-side path (e.g., a malicious caller bypassing the disabled button) is rejected by a `BEFORE INSERT` trigger on `public.listing_media` that raises a SQLSTATE-coded error. Two-layer enforcement matches Constitution III (security-first Supabase) — the UX disable is convenience; the DB trigger is the enforcement. Anonymous (not-signed-in) callers, non-owner publishers, and non-approved publishers cannot insert media rows at all (the RLS policy denies INSERT outside the owner-during-draft-or-rejected window AND outside the admin `listings.edit_any` permission).

**Why this priority**: P1 because uncapped media uploads are a denial-of-service vector against Supabase Storage (egress + storage cost grows unbounded). The IMPLEMENTATION_PLAN §Phase 11 acceptance line "Uploading an 11th image is rejected client-side and server-side" explicitly demands both layers.

**Independent Test**: Sign in as an approved publisher. Create a draft and reach the media step. Upload 10 images successfully — confirm the "Add images" CTA is disabled after the 10th. Attempt to upload an 11th by manually invoking the picker entry (or by directly INSERTing a `listing_media` row via Supabase MCP `execute_sql` against the listing-owner's JWT session) — confirm the BEFORE INSERT trigger raises a SQLSTATE-coded error with a localizable error key (e.g., SQLSTATE `23514` `check_violation` paired with the trigger's RAISE EXCEPTION message). Repeat for videos: upload 2 videos (one direct upload, one external link), confirm the "Add video" CTA disables after the second. Attempt a third — confirm the same trigger fires. Attempt from an anonymous Supabase client to INSERT a row for another publisher's listing — confirm RLS denies (0 rows affected).

**Acceptance Scenarios**:

1. **Given** an approved-publisher session and a draft listing with exactly 10 `kind='image'` rows in `listing_media`, **When** the publisher attempts to add an 11th image via the MediaPicker, **Then** the picker's "Add images" CTA is disabled with a localized "10-image limit reached" message; if the publisher bypasses the UX (e.g., direct SQL INSERT), the `BEFORE INSERT` trigger raises an error with SQLSTATE and a structured payload.
2. **Given** an approved-publisher session and a draft listing with 2 `kind IN ('video','external_link')` rows combined, **When** the publisher attempts to add a third, **Then** the "Add video" CTA disables with a localized "2-video limit reached" message and the BEFORE INSERT trigger denies any bypass attempt.
3. **Given** a publisher whose `publisher_status='pending'` (or `rejected` / `suspended`) attempts to INSERT a media row directly via SQL against their own user JWT, **When** the INSERT runs, **Then** RLS denies (0 rows affected) — the policy requires the same composite (`auth.uid()=parent.publisher_user_id` AND `publisher_status='approved'` AND `account_status='approved'`) as Phase 10's listings-write policy.
4. **Given** an admin holding `listings.edit_any`, **When** the admin INSERTs / UPDATEs / DELETEs `listing_media` rows for any listing in any status, **Then** the policy permits the write; the 10-image / 2-video cap trigger STILL fires (admins cannot exceed the cap either — the cap is structural, not policy).
5. **Given** an anonymous (not-signed-in) Supabase client, **When** it attempts INSERT / UPDATE / DELETE on `listing_media`, **Then** RLS denies; for SELECT, only rows whose parent listing is publicly readable (status='approved' AND publish window open) are visible.

### User Story 3 — Resubmit-after-rejection preserves existing media (edit-in-place per Q3=A) (Priority: P1)

A publisher whose listing was rejected by an admin in Phase 12 opens the listing from `MyListingsPage`'s Rejected filter (Phase 10 US3), reaches the media step, and per Q3=A's resolution sees all existing watermarked images as thumbnails in the picker grid, with their `ordering` honored, the `is_main` badge floating on the main row, and per-thumbnail actions (set-main, delete, drag-reorder) wired identically to the first-upload flow. An "Add more" affordance appears alongside the thumbnails (subject to the 10-image cap from FR-005). The publisher may delete any image (which removes both the row AND the bucket object), reorder freely, change the main image, and append new images — all in place, with stable row UUIDs. The publisher advances to Review, taps Submit, and the listing transitions back to `pending_review` per the Phase 10 US3 contract. The full transition chain (`NULL → draft → pending_review → rejected → pending_review`) is preserved in `listing_status_history`; the existing `listing_media` rows carry forward unchanged, with their UUIDs preserved across the resubmit — matching the Phase 10 research R-14 invariant "draft mutated in place across resubmits — stable UUID preserves audit lineage."

**Why this priority**: P1 because rejected listings are the publisher's most-common path to retry the moderation queue; preserving prior watermarked work avoids re-upload friction on Syrian mobile data plans (which can be slow and metered).

**Independent Test**: Sign in as an approved publisher with one listing in `status='rejected'` AND ≥ 3 existing `listing_media` rows in the `listing-images` bucket. Open MyListingsPage's Rejected filter; confirm the rejection-reason card renders (Phase 10 US3 path). Tap "Resubmit"; confirm the form opens at step 1, pre-populated. Advance to step 6 (media). Confirm all 3 existing thumbnails render in the picker grid with their `ordering` preserved and the existing `is_main` badge. Query `SELECT id, ordering, is_main FROM public.listing_media WHERE listing_id=<this id> ORDER BY ordering ASC` BEFORE and AFTER entering the media step; confirm the row UUIDs are identical (no DELETE+INSERT churn). Delete one image via the picker; confirm the row AND the bucket object are removed (count drops to 2). Add one new image; confirm the new row is inserted with a fresh UUID and a higher `ordering` value. Advance to Review → Submit; confirm the listing flips to `pending_review` and the post-edit `listing_media` set is what `submit_listing`'s Q1=A check evaluates.

**Acceptance Scenarios**:

1. **Given** a `rejected` listing with N existing `listing_media` rows, **When** the publisher reaches the media step on resubmit, **Then** the picker renders all N existing thumbnails with their `ordering`, `is_main`, and watermark preserved; an "Add more" affordance appears (disabled at the 10-image cap).
2. **Given** the picker loads existing rows on resubmit, **When** any thumbnail commits to the grid, **Then** every existing row's UUID `id` is preserved across the resubmit — no DELETE+INSERT churn — preserving audit-log lineage and the `created_at` timestamp (Phase 10 R-14 invariant).
3. **Given** the publisher deletes an existing image during resubmit edit, **When** the delete action commits, **Then** the `listing_media` row is removed AND the bucket object is removed via the storage SDK; the FR-005 audit trigger emits a `listing_media.deleted` row.
4. **Given** the publisher submits after editing media on a rejected listing, **When** `submit_listing` commits, **Then** the Q1=A minimum-media check runs against the post-edit state — a publisher who deleted all images during resubmit is rejected with `missing_fields=["listing_media.images_below_minimum"]` per FR-022.
5. **Given** the publisher abandons the resubmit mid-edit (back button, app suspend), **When** they return later, **Then** the picker reflects the in-place media state — partial edits (an image deleted, a new image added) persist across launches as long as the listing remains in `status='rejected'`.

### User Story 4 — Image downscale + watermark composite runs on a background isolate without blocking the UI (Priority: P1)

When the publisher picks multiple high-resolution images at once (e.g., 8 images from a 12-megapixel camera at 4000×3000 px each), the watermark + downscale pipeline runs on a background Dart isolate so the picker grid remains scrollable and the rest of the app remains responsive. Each image is processed sequentially (one isolate, sequential queue) to avoid OOM on the Helio G80's 6 GB RAM constraint. The picker grid shows a per-thumbnail progress indicator (spinning ring) until processing+upload completes; if processing fails for any image (corrupt source, unsupported format, OOM, network error during upload), that thumbnail switches to an error state with a "Retry" action and a localized error message. Successfully processed images insert their `listing_media` row only after the bucket upload completes — atomic-from-the-publisher-perspective (no dangling rows pointing to missing bucket objects).

**Why this priority**: P1 because Constitution XI (Android-First MVP) targets devices like the Infinix Note 8 (Helio G80, 6 GB RAM) where on-thread image processing of 8 high-res photos would jank the UI for 10+ seconds and risk an Android "App Not Responding" dialog. The background-isolate pipeline is a quality-of-life requirement, not a nice-to-have.

**Independent Test**: On the reference Infinix Note 8 device, prepare a gallery folder with 8 images each at ≥ 4000×3000 px (~5 MB JPEG each). ### User Story 6 — Storage-bucket RLS: public sees only approved listings' media (Priority: P2)

The `listing-images` and `listing-videos` Supabase Storage buckets carry RLS policies on the `storage.objects` table that mirror the Phase 10 `public.listings` public-read-when-approved policy. ### Edge Cases

- **Publisher denies the gallery permission** (per Q5): The picker surfaces a localized "gallery access is required to upload photos" message with an "Open settings" affordance that fires the `ACTION_APPLICATION_DETAILS_SETTINGS` intent. No `listing_media` row is inserted. If the permission is revoked mid-session (the publisher backgrounded the app and toggled the permission off in Settings), the next picker invocation surfaces the same message — `image_picker` re-requests on each invocation. The publisher may continue to use the rest of the listing form; only the media step is blocked.
- **Publisher picks an image in HEIC / HEIF / PNG / WebP** (per Q4): The pipeline accepts the source, decodes it via the chosen library (HEIC may require a native plugin), and normalizes the output to JPEG per FR-014 — the publisher is NOT blocked at the file-pick step. Reject only formats outside the Q4 accept set (BMP, TIFF, GIF, SVG, RAW camera files, exotic codecs) with a localized "this image format cannot be read — please pick a JPEG, PNG, HEIC, or WebP" message; the publisher can replace the picked file. No row is inserted; no bucket object is created.
- **Publisher picks an image whose source dimensions exceed 8000×8000 pixels** (per Q6): The picker reads the source header metadata BEFORE decode and rejects with a localized "this image is too large — max 8000×8000 pixels" message. No decode is attempted; no `listing_media` row is inserted; no bucket object is created. The publisher can re-pick a smaller image or resize externally.
- **Publisher picks an image within the 8000×8000 cap but whose decoded byte count exceeds the device's available memory** (residual corner case): The decoder throws OOM inside the isolate; the picker catches the failure and surfaces an error thumbnail with a Retry action. The publisher can retry with a smaller image or different photo. The pipeline never crashes the app.
- **Picker is invoked on a listing whose status is `pending_review` (post-Phase-10-submit, pre-Phase-12-approval)**: The picker refuses to enter edit mode — `kind='listing_media'` writes are gated by parent listing status `IN ('draft', 'rejected')` per the RLS write policy. The picker shows a read-only carousel of existing thumbnails. The "Add" CTAs are hidden.
- **Picker is invoked on a listing whose status is `approved` / `paused` / `sold` / `rented` / `expired`**: Same as pending_review — read-only carousel, no add/edit/delete. Phase 10's post-approval edit policy (deferred per spec 010 DEFERRED.md) covers this entire surface; Phase 11 inherits the same restriction.
- **Publisher uploads an image, then the listing's owning publisher_status is revoked while the draft sits**: The picker becomes inaccessible (Phase 10 form's RLS gate). The existing `listing_media` rows remain in the DB and bucket objects remain in storage. They are not orphaned in the strict sense (the parent `listings` row still exists), but they are unreachable to the publisher. Admins may clean up via direct SQL.
- **Bucket object exists in storage but `listing_media` row was rolled back (DB transaction failed after upload)**: Defense-in-depth: every successful upload is followed by the row INSERT in the same datasource call; if the INSERT fails, the datasource issues a Storage DELETE to remove the orphaned object before surfacing the error to the picker. A background reconciliation job is forward-stated to Phase 23 (admin settings) — not in Phase 11 scope.
- **`listing_media` row exists but bucket object was deleted out-of-band (admin used Studio to delete)**: The picker's thumbnail renders a broken-image placeholder. The Phase 13 public gallery shows the same placeholder. Phase 11 does NOT auto-clean these rows; an admin can delete via the picker (which itself DELETEs the row even if the bucket DELETE 404s) or via direct SQL.
- **Network drops mid-upload of a large image**: The pipeline retries the upload twice with exponential backoff (1s, 4s); on third failure, the thumbnail switches to error state with a Retry action. No partial bucket objects remain (Supabase Storage's resumable-upload protocol handles partial bytes server-side, but for v1, the client uses a non-resumable upload and a partial failure is treated as a complete failure). The 1s + 4s retry budget sits inside the Q7-resolved 60-second per-image timeout.
- **Per-image timeout exhausted** (per Q7): If the full FR-014 pipeline does not commit a `listing_media` row within 60 seconds for a single image, the in-flight work is cancelled, any partial bucket object is removed (defense-in-depth), and the thumbnail switches to a timeout-error state with a localized "this upload took too long — please try again" message + Retry action. The other images in the batch continue processing unaffected. Repeated timeout failures on the same image suggest a slow-network or device-CPU condition; the publisher may retry, wait for a better network, or pick a different photo.
- **Two concurrent picker sessions on the same draft from two devices**: Phase 11 does not lock the picker. Both sessions can add rows; the `ordering` re-sequence transaction uses optimistic concurrency — last writer wins. The `is_main` partial unique index serializes set-main operations server-side. The 10-image cap is enforced by the BEFORE INSERT trigger — both sessions adding their 6th image simultaneously will see one INSERT succeed and the other fail with a cap-violation SQLSTATE.
- **Watermark logo asset is missing from the Flutter assets bundle**: The pipeline cannot composite the watermark. The picker surfaces a developer-facing crash (Flutter assertion) at debug time and a fail-soft "watermark could not be applied — please re-upload" message at release time. The pipeline DOES NOT upload an un-watermarked image — failing closed (Constitution III). The watermark asset is bundled via `pubspec.yaml`'s `flutter.assets` declaration and a pre-deploy smoke test exercises a one-image upload to confirm the asset is present.
- **Image's EXIF orientation header is non-trivial (e.g., camera shot in portrait but stored as landscape with rotation=6)**: The decoder applies the EXIF rotation BEFORE downscale and watermark composite, so the uploaded JPEG is right-side-up and the watermark sits in the publisher-expected corner. The uploaded JPEG strips the EXIF block (privacy: prevents location-leaking GPS EXIF on user photos).
- **Video file exceeds 30 MB**: The picker rejects client-side with a localized "video must be ≤ 30 MB" message; if the publisher bypasses the UX, the BEFORE INSERT trigger AND the storage policy reject (the bucket policy enforces a max-bytes limit via the Supabase Storage `bucket.file_size_limit` config).
- **Trigger-before-seed audit ordering**: Following Phase 8/9/10 R-08, the migration MUST attach the `listing_media` audit and cap triggers BEFORE any seeded fixture rows (Phase 11 seeds zero rows — defensive invariant for any future spec).
- **Constitution III RLS on the new table**: `public.listing_media` ships with RLS enabled and explicit policies. The policies join through `public.listings` to derive the parent's publisher and status. Anonymous SELECT is allowed only when the parent's `status='approved'` AND publish window is open (mirrors Phase 10's listings policy).

#### Watermark + downscale + upload pipeline

- **FR-014**: System MUST process every picked image through a deterministic client-side pipeline before upload, accepting the Q4-resolved source-format set (JPEG, PNG, HEIC/HEIF, WebP) and normalizing every output to JPEG: (a) detect source format from MIME + magic bytes; reject formats outside the accept set at this point with a localized error per FR-019; **(a-pre) per Q6, read the source file's header metadata (JPEG SOF0 marker, PNG IHDR chunk, HEIC `ispe` box, WebP VP8X chunk) to extract pixel dimensions WITHOUT decoding raw pixels; reject the file at this step with a localized "this image is too large — max 8000×8000 pixels" message if either `width > 8000` OR `height > 8000`**; (b) decode the file into raw pixels (PNG transparency is composited against a white background at decode time; HEIC may require a native plugin per the Q4-resolved Assumption block); (c) apply EXIF-orientation rotation AND strip the EXIF block (privacy — no GPS leakage); (d) downscale so the long edge ≤ 1920 px (if the source is already ≤ 1920, skip downscale — preserve native resolution); (e) composite the AlNujom logo as a semi-transparent overlay at the default position (bottom-end corner, 15% opacity, 18% of image long edge); (f) re-encode as JPEG with quality 85 — every output is JPEG regardless of source format; (g) upload to `listing-images` bucket at path `<listing_id>/<ordering>_<rand>.jpg`. The exact opacity / position numbers are codified in the plan-time research file; the spec captures only the default visual outcome. Every step runs on a background Dart isolate via Flutter's `compute()` or a dedicated isolate worker — UI thread is never blocked. As an optional fast-path optimization, a source JPEG that is already ≤ 1920 px long edge MAY skip the decode + re-encode round-trip and apply only the EXIF-strip + watermark-composite operations (research-time decision); the resulting object is still a JPEG at quality ≥ 85.
- **FR-015**: System MUST treat the pipeline as atomic from the publisher's perspective — only after the bucket upload succeeds does the datasource insert the `listing_media` row. On upload failure, NO row is inserted; the publisher sees a per-thumbnail error state. On row-insert failure (rare — e.g., the 10-image cap trigger fires due to a concurrent upload from another device), the datasource issues a Storage DELETE to remove the just-uploaded object, then surfaces the cap-violation error to the picker. Per Q7, the picker MUST enforce a 60-second per-image timeout covering the entire FR-014 pipeline (header-read through upload + retries); on timeout expiry, the in-flight isolate / HTTP request is cancelled, any partial bucket object is removed via Storage DELETE (defense-in-depth), and the thumbnail switches to an error state with a localized "this upload took too long — please try again" message + Retry action.
- **FR-016**: System MUST set `listing_media.watermarked=true` for every Phase 11 client-uploaded image (the client always watermarks; failed-watermark uploads do not happen — fail closed). The column exists as defense-in-depth for future server-side watermark re-application — a Phase 23+ background job could re-watermark images flagged `watermarked=false`. Phase 11 sets the flag at INSERT time; no Phase 11 reader queries it.

### Key Entities *(include if feature involves data)*

- **ListingMedia**: One row per media artifact attached to a listing. Two kinds are insertable through the Phase 11 UI: `image` (a JPEG bucket object in `listing-images`, client-side watermarked, downscaled to 1920 px long edge) and `video` (an MP4 bucket object in `listing-videos`, ≤ 30 MB, NOT watermarked in v1). The schema's `kind` enum also retains `'external_link'` (an external URL with `storage_path=NULL` and `external_url` populated) for future-spec forward-compat per Q2=D — no Phase 11 UI path inserts such rows. Each row carries an `ordering` integer (publisher-controlled via drag-reorder), an `is_main` boolean (exactly one per listing for `kind='image'`; never true for video or external_link per FR-002 CHECK), and a `watermarked` boolean (true for every Phase 11 client-uploaded image; defense-in-depth for future server-side re-watermark). Cascade-deleted with the parent listing.
- **StorageObject (listing-images / listing-videos)**: A Supabase Storage object at path `<listing_id>/<filename>`. Bucket policies on `storage.objects` mirror the `listing_media` RLS — public read only when parent listing's status='approved' AND publish window open. Owner read for any status. Bucket `file_size_limit` enforces the 10 MB / 30 MB caps as defense-in-depth alongside the BEFORE INSERT trigger on `listing_media`.

No new gate is introduced.
- **`log_audit()` reusability invariant**: Phase 11 attaches new audit triggers to `public.listing_media` using Phase 4's `log_audit()` function unchanged. The R-05 reusability invariant is preserved for an EIGHTH time across Phases 4/5/6/7/8/9/10/11.
- **Migration naming follows project convention**: The IMPLEMENTATION_PLAN references migration filename `0021_create_listing_media.sql` (descriptive integer), but the actual project uses date-prefixed names per Phase 8 R-01's carry-forward decision. The plan-time research file will codify exact filenames (e.g., `20260522120001_create_listing_media.sql`, `20260522120002_create_listing_media_storage_buckets.sql`, `20260522120003_create_listing_media_storage_policies.sql`).
- **No new automated tests — manual UI verification only**: Per `feedback_no_new_tests.md`, Phase 11 does NOT introduce new automated unit / widget tests despite the IMPLEMENTATION_PLAN's reference to verification cases. The watermark / downscale / cap-enforcement / storage-RLS scenarios are codified in `quickstart.md` as a manual-verification checklist exercised against the remote Supabase project + the reference Infinix Note 8 device. The "Skip new tests until MVP" directive applies for the eighth time across Phases 5–11.
- **Constitution XI (Android-First MVP)**: Every manual acceptance test runs on the Infinix Note 8 (Helio G80, 6 GB RAM, Android 10/11). No iOS / web / desktop target is in scope. The MediaPicker's grid layout, drag-reorder gestures, long-press action sheets, and isolate-based image pipeline are evaluated specifically against the Helio G80's CPU and 6 GB RAM ceiling.
- **Android-version coverage gap for Q5 permissions** *(test plan supplement)*: The reference Infinix Note 8 device (Android 10/11) exercises only the legacy `READ_EXTERNAL_STORAGE` code path declared by FR-023. The Q5-resolved granular `READ_MEDIA_IMAGES` / `READ_MEDIA_VIDEO` path that triggers on Android 13+ MUST be exercised on a secondary test surface — the Pixel 8 Pro emulator running Android 14 (set up per `project_android_emulator_window_offscreen.md`) covers this. Phase 11's `quickstart.md` includes manual-verification steps for both Android-version codepaths.
- **Watermark asset path**: The AlNujom logo lives at `assets/images/watermark/logo_watermark.png` (or `.webp` if smaller — research-time decision). It is bundled via `pubspec.yaml`'s `flutter.assets` declaration. The asset is a PNG with alpha channel (transparency) so the composite operation reads the alpha mask correctly. The asset's source SVG is checked into `docs/design/assets/watermark/` for re-export at higher DPI if needed.
- **Image library choice** *(updated per Q4)*: The pipeline accepts JPEG, PNG, HEIC/HEIF, and WebP source formats and normalizes every output to JPEG per FR-014. The chosen library set MUST be able to decode all four. Notable constraints: (a) the pure-Dart `image` package historically had NO HEIC decode support — a native plugin (`flutter_image_compress`, `heif_converter`, or `image_picker` with its built-in HEIC→JPEG conversion on the picker layer) will likely be required to handle iPhone-shot HEICs landing on Android via WhatsApp / Telegram. (b) `image_picker` (or equivalent) is required for the gallery picker affordance. (c) Watermark composite + downscale + JPEG re-encode can stay in pure Dart via the `image` package. The plan-time research file picks the exact package set, weighing pubspec.lock additions against device-RAM / runtime cost; one native plugin for HEIC decode is accepted, more than one is grounds for re-evaluation. No iOS-target native code is added (Constitution XI).
- **EXIF stripping for privacy**: Every uploaded JPEG has its EXIF block stripped before upload to prevent GPS / camera-make / camera-model leakage. This is a privacy-preservation default; the publisher is not informed (no UX surface, no opt-out). Phase 11 does not surface "remove EXIF?" as a publisher choice — the strip is mandatory.
- **Original-resolution preservation**: Phase 11 does NOT keep the publisher's original (pre-downscale, pre-watermark) image anywhere. Only the watermarked + downscaled JPEG is stored. A future spec MAY introduce an "original" sibling bucket (admin-only) if higher-resolution review is needed for moderation; that is not Phase 11 scope.
- **Video watermarking**: Phase 11 does NOT watermark uploaded videos. Watermarking video would require client-side re-encoding, which is expensive on the Helio G80. Videos are uploaded as-is (with a 30 MB cap and MP4 mime). External-link videos cannot be watermarked.
- **Storage cleanup on listing deletion**: When a listing is set to `status='deleted'` (admin action — Phase 12+ scope), the `listing_media` rows cascade-delete with the parent via `ON DELETE CASCADE` only if the parent row itself is DELETEd (not just status-flipped to 'deleted'). Phase 11 does NOT add a bucket-object cleanup trigger when status='deleted'; that is deferred to a future admin-tooling spec. Bucket objects whose parent listing is `status='deleted'` (but the row persists) are unreachable to anonymous viewers (RLS denies) but persist in storage indefinitely. A reconciliation job is forward-stated to Phase 23.
- **Resumable uploads**: Phase 11 uses non-resumable uploads (single `supabase.storage.from(bucket).upload()` call per image). A partial upload (network drop mid-stream) is treated as a complete failure — the client retries from scratch. Resumable uploads (Supabase's TUS protocol or equivalent) are out of v1 scope.
- **Phase 13 gallery consumer**: Phase 13 (public home & listing details) will render the `listing_media` rows as a horizontal carousel gallery on the listing-details page. Phase 11 does NOT ship the gallery widget — only the picker + storage + RLS. The Phase 13 spec reads `listing_media` ordered by `ordering ASC` with `is_main=true` first; Phase 11's schema fully supports this consumption pattern. Per Q8, Phase 13's gallery consumes stable public URLs from `supabase.storage.from(bucket).getPublicUrl(path)` — no per-render signed-URL minting — and caches via `cached_network_image`.
- **Phase 12 admin preview**: Phase 12 (listing approval) will render the same `listing_media` carousel on the admin preview surface for moderation. Phase 11 does NOT ship the admin preview; Phase 12 reads the same rows under its `listings.view_all` permission.
- **Constitution III RLS on the new table + storage objects**: Both `public.listing_media` AND the relevant `storage.objects` rows (filtered by `bucket_id IN ('listing-images', 'listing-videos')`) ship with RLS enabled and explicit policies. None opts out. The policies join through `public.listings` to derive the parent's publisher and status.
- **Forward-stated `public.listing_media` partial unique index**: Already documented in FR-003. Future-spec extensions that allow multi-main (e.g., a "secondary main" for tile-vs-detail rendering) would require an explicit migration that drops this index — Phase 11 does not anticipate such extensions.
- **Plan-time deviation between Edge Function vs RPC vs client-side cap**: The IMPLEMENTATION_PLAN says "Trigger enforcing the 10-image / 2-video caps server-side." Phase 11 ships exactly that (a `BEFORE INSERT` trigger, FR-004). No Edge Function is added in Phase 11 — the cap and the audit log are sufficient at the DB layer. The Phase 12 `approve_listing` and Phase 10's `submit_listing` continue to be the only RPCs touching the listings tree.
- **Forward-stated `external_link` UX deferral**: Per Q2=D, no `kind='external_link'` rows are insertable through the Phase 11 UI; the schema enum retains the value for future-spec forward-compat. The future-spec extension that introduces external-link entry will need to: (a) add an "Add external link" CTA to the picker, (b) add a URL text field, (c) introduce `lib/core/validators/external_video_url_validator.dart` with a host allowlist (the allowlist choice — YouTube / Vimeo / Telegram / Aparat / etc. — is that spec's clarification surface), (d) optionally add a server-side CHECK constraint or trigger enforcing the same allowlist, and (e) ensure the FR-005 2-video cap predicate continues to combine `kind IN ('video', 'external_link')` (Phase 11 already keeps this combined form). No Phase 11 schema migration is needed at the time the future-spec ships.
- **Plan-override is bounded to Phase 11 only**: The Q1 / Q2 / Q3 resolutions of this spec apply ONLY to Phase 11. They do not preclude later phases from refining the media required-field set (a future spec may require ≥ 3 images per listing-quality push), from layering external-link entry on top per the prior bullet, or from changing the resubmit UX (a future spec may add per-image revision history).
