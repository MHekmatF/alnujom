# Feature Specification: Favorites

**Feature Branch**: `017-favorites`
**Created**: 2026-05-29
**Status**: Draft
**Input**: Phase 17 — Favorites, from `docs/IMPLEMENTATION_PLAN.md` (§ "Phase 17 — Favorites")

> **Scope note**: Phase 17 introduces the *private saved-listings capability* — the working implementation of the Favorite heart that Phase 13 ships as a Coming-soon stub (the leftmost CTA in `PerListingActionBlock` per `lib/features/listing_details/presentation/widgets/per_listing_action_block.dart`, and the heart-overlay slot already wired but inert on `PropertyCard` per `lib/core/widgets/property_card.dart` lines 165–176), plus a dedicated FavoritesPage where the signed-in user reviews everything they have saved, plus the `favorite_added` lead-event emission that Phase 16 reserved in the `lead_events` enum but shipped no write path for. It does NOT introduce any sharing-between-users, public "popularity"/save-count display, or "users who saved this also saved" recommendation surface (favorites are strictly private per Principle III and the IMPLEMENTATION_PLAN's "favorites are private" goal); it does NOT introduce collections/folders/tags for organizing saved listings (a flat per-user list in v1); it does NOT introduce a "saved searches" or "notify me when price drops" capability (a future spec — Phase 22's notifications may revisit); it does NOT introduce favoriting of anything other than approved listings (no favoriting of publishers, agencies, areas, or searches in v1); it does NOT modify Phase 13's Share or Report stubs in `PerListingActionBlock` (those remain Coming-soon until a future share-wiring phase and Phase 18 Reports respectively); it does NOT introduce a `favorite_removed` lead event (the `lead_events` enum has no such value and Phase 17 adds none — removal is silent); it does NOT add any new third-party dependency (favorites are in-house Postgres + the existing Flutter/BLoC/`go_router`/`supabase_flutter` stack). The Phase 17 PR ships exactly: (a) one new table — `public.favorites` keyed on `(user_id, listing_id)` so the same user cannot double-save a listing, with a self-only RLS posture (a row is readable, insertable, and deletable ONLY by the user whose `auth.uid()` equals the row's `user_id` — no publisher, no admin, no anonymous, no cross-user reader path exists, because a person's saved listings are their own private behavioral data); (b) a privileged server-side write path — an `add_favorite(listing_id)` SECURITY DEFINER RPC that validates the target listing exists and is `status='approved'`, idempotently inserts the favorite row, and atomically emits a single `favorite_added` lead event **only the first time** the signed-in user has ever favorited that listing (deduplicated against the `lead_events` history per Q3=B — re-favoriting a previously-removed listing does NOT emit a second event), while un-favoriting hard-deletes the favorite row through a self-only DELETE RLS policy (the client deletes its own row directly, no RPC, per Q5=A) and emits NO lead event; (c) a single shared `FavoriteHeartButton` widget embedded into the four surfaces that render listings — the `PerListingActionBlock` Favorite CTA on the Phase 13 listing details page and the bespoke card widgets `HomeListingCardTile` (Phase 13 home feed), `SearchResultCard` (Phase 14 search results), and `MarkerPreviewPopover` (Phase 15 map marker preview) — wired to the real toggle, with optimistic UI and a shared session-level favorited-id set so a listing favorited in one surface reflects as favorited in every other surface without a round-trip (the live feeds use bespoke cards, not the Phase 2 `PropertyCard`, whose heart slot is debug-gallery-only); (d) a new feature folder at `lib/features/favorites/` containing the `FavoritesPage` (the signed-in user's chronological list of saved listings, newest-first, reusing the Phase 13 listing-card composition), its BLoC, repository, data source, and domain entities; (e) a "My Favorites" tile added to the Phase 5 Profile page (per Q1=A) that navigates to the new `/favorites` route — the entry point is auth-gated because the Profile page already requires a signed-in session; (f) the anonymous-visitor path per Q2=A — the heart renders for everyone (so anonymous browsers discover the feature) but tapping it while signed-out routes to the login flow with a localized "Sign in to save favorites" prompt rather than silently failing or hiding the control; (g) the localization layer gains the favorites strings — the heart's accessibility label, the sign-in prompt, the FavoritesPage title and empty-state, the "no longer available" indicator for favorites whose listing has since left `approved` status, and the Profile tile label — all flowing through `AppLocalizations` with `ar` and `en` entries per Phase 3. Phase 17 makes the Phase 13 Favorite stub real, gives the user a home for their saved listings, and emits the first `favorite_added` lead events into the Phase 16 substrate. It honors Principle III (self-only RLS, no service-role key on the client, the lead-event write goes through a SECURITY DEFINER RPC because `lead_events` grants no client INSERT) and Principle I (this spec precedes any implementation). Authentication is required to *hold* a favorite (the `favorites.user_id` foreign-keys `auth.users`); anonymous users may *see* the heart but must sign in to use it.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Signed-in visitor saves and un-saves a listing from anywhere a card or details page appears (Priority: P1)

A signed-in visitor browsing the home feed (or search results, or a map marker preview, or a listing's full details page) sees a heart control on each listing. They tap the heart on a listing they like; it fills in immediately (optimistic) and the listing is saved to their private favorites. They tap it again; it empties and the listing is removed from their favorites. The same listing's heart reflects the saved state consistently across every surface — if they saved it from the home feed and then open its details page, the details-page heart is already filled.

**Why this priority**: P1 because the toggle IS the feature — without a working save/un-save action there is nothing to list on the FavoritesPage and no `favorite_added` event to emit. The Phase 13 Coming-soon stub (a snackbar on tap) is the placeholder this story replaces. The cross-surface consistency is part of P1 because a heart that shows "saved" on the details page but "not saved" on the card the user just came from reads as broken.

**Independent Test**: Apply the Phase 17 migrations. Sign in as a test user with ≥ 0 prior favorites. From the home feed, tap the heart on an approved listing's card; confirm (a) the heart fills immediately, (b) a `public.favorites` row exists with `user_id` = the signed-in user, `listing_id` = the listing, `created_at` within the last 5 seconds, (c) navigating into that listing's details page shows the Favorite CTA already in the filled/saved state. Tap the heart again on the details page; confirm the `favorites` row is deleted and the home-feed card's heart (on return) is empty. Re-tap to favorite again; confirm a new `favorites` row is inserted. Repeat the favorite/un-favorite toggle rapidly several times; confirm the final database state matches the final UI state (saved ⇒ exactly one row; not-saved ⇒ zero rows) with no duplicate rows and no orphaned rows.

**Acceptance Scenarios**:

1. **Given** a signed-in visitor viewing an approved listing's card (home feed, search results, or map preview), **When** they tap the empty heart, **Then** the heart fills optimistically AND exactly one `public.favorites` row is inserted with `user_id = auth.uid()`, `listing_id` = the listing, and a server-generated `created_at`.
2. **Given** a signed-in visitor viewing an approved listing whose heart is already filled (saved), **When** they tap the filled heart, **Then** the heart empties optimistically AND the corresponding `public.favorites` row is hard-deleted.
3. **Given** a signed-in visitor has saved a listing from the home feed, **When** they open that listing's Phase 13 details page, **Then** the `PerListingActionBlock` Favorite CTA renders in the saved (filled) state without requiring a manual refresh.
4. **Given** the favorite toggle issues a server write, **When** the write fails (network drop, RPC error), **Then** the optimistic heart state reverts to its prior value AND a localized error message surfaces AND the database contains no partial state (no row inserted on a failed add; the row preserved on a failed remove).
5. **Given** a signed-in visitor taps the heart twice in rapid succession (add then immediate remove, or two adds), **When** the writes settle, **Then** the final `favorites` table state for that `(user_id, listing_id)` pair is consistent with the final UI state — at most one row exists for the pair (the `(user_id, listing_id)` uniqueness constraint prevents duplicates) AND the displayed heart matches the row's existence.
6. **Given** a signed-in visitor favorites a listing, then the listing later leaves `approved` status (sold / rented / rejected / paused / expired / deleted), **When** the visitor re-visits any card or details surface for that listing, **Then** the favorite is preserved (the row is not auto-removed) AND the un-favorite action still works on the FavoritesPage per US2.

### User Story 2 — Signed-in user reviews every listing they have saved on the FavoritesPage (Priority: P1)

A signed-in user opens the "My Favorites" tile in their Profile page. They land on a FavoritesPage showing every listing they have saved, newest-saved first, each rendered as a familiar listing card (image, title, price, location) with a filled heart they can tap to un-save directly from this page. Tapping a card opens the listing's Phase 13 details page. If a saved listing is no longer available (its listing left `approved` status), the card still appears but is visibly marked "no longer available" so the user understands why tapping it may lead to an unavailable listing. If the user has saved nothing, a localized empty-state explains how favorites work.

**Why this priority**: P1 because without the page the favorites accumulate invisibly — the user can save listings but has no consolidated place to find them again, which is the entire point of saving. The "no longer available" affordance is part of P1 because a marketplace where saved listings silently vanish (or silently 404 on tap) erodes trust in the save action.

**Independent Test**: Sign in as a user with ≥ 3 saved approved listings and ≥ 1 saved listing whose status has since changed away from `approved`. Open Profile → "My Favorites." Confirm (a) the page lists all saved listings newest-saved first, (b) each available listing renders as a card with title/price/location/image and a filled heart, (c) the listing whose status changed renders with a localized "no longer available" indicator and is visually distinguished, (d) tapping an available card navigates to its Phase 13 details page, (e) tapping the filled heart on a card removes it from the list immediately and deletes the `favorites` row. Un-save every favorite; confirm the page transitions to the localized empty-state. Confirm the page paginates (does not issue an unbounded query) when the user has many favorites.

**Acceptance Scenarios**:

1. **Given** a signed-in user with ≥ 1 saved listing, **When** they open the FavoritesPage, **Then** every listing they have saved appears, ordered by `favorites.created_at DESC` (most-recently-saved first), AND no listing they have not saved appears.
2. **Given** the FavoritesPage is open, **When** each saved listing renders, **Then** it uses the Phase 13 listing-card composition (image, title, price formatted per Phase 9 locale rules, location) with the same shared heart control (FR-002) in the filled state.
3. **Given** a saved listing whose underlying listing is no longer `approved` (sold / rented / rejected / paused / expired / deleted), **When** the FavoritesPage renders, **Then** the card still appears AND carries a localized "no longer available" indicator AND remains un-saveable via its heart so the user can clean it up.
4. **Given** a signed-in user with zero saved listings, **When** they open the FavoritesPage, **Then** a localized empty-state message renders (not a crash, not a blank screen) explaining that they have not saved any listings yet.
5. **Given** the FavoritesPage is open, **When** the user taps the filled heart on a card, **Then** the card is removed from the list immediately AND the `favorites` row is deleted AND the change persists across app restart.
6. **Given** the FavoritesPage is open and the user has many saved listings, **When** the list renders, **Then** it paginates (cursor- or page-based, matching the Phase 13 home-feed pattern) rather than issuing an unbounded query.
7. **Given** a signed-in user taps any saved card on the FavoritesPage (available OR no-longer-available, per Q4=A), **When** the navigation resolves, **Then** the Phase 13 listing details page for that listing opens — which itself renders the appropriate read-only / `_NotFoundView` state for terminal or deleted listings; the FavoritesPage applies no special-case tap handling.

### User Story 3 — Favorites are strictly private (cross-user RLS isolation) (Priority: P1)

A user's set of saved listings is private behavioral data — what someone is shopping for can reveal their budget, their relocation plans, their financial situation. The product MUST guarantee that no other user (including the listing's publisher and platform admins), and no anonymous client, can read, enumerate, or infer another user's favorites. The RLS posture enforces strict self-only access: a `favorites` row is readable, insertable, and deletable IF AND ONLY IF the requesting session's `auth.uid()` equals the row's `user_id`.

**Why this priority**: P1 because Constitution Principle III (Security-First Supabase) makes a single unprotected table a breach, and the IMPLEMENTATION_PLAN's explicit acceptance criterion is "User A cannot see User B's favorites." Unlike Phase 16's inquiries (which have a deliberate three-tier visibility because a publisher legitimately needs to see inquiries on their listings), favorites have NO legitimate cross-user reader — not even the publisher whose listing was favorited, and not even an admin (no `favorites.view_all` permission exists or is introduced).

**Independent Test**: Seed two users (user-A, user-B) each with ≥ 1 saved listing, including at least one listing saved by BOTH. Capture the wire-level response when user-A queries the favorites surface. Confirm (a) the response contains ONLY rows whose `user_id` equals user-A — none of user-B's, even for the listing both saved (the row returned is user-A's own row, never user-B's), (b) the same query executed from user-B's session returns ONLY user-B's rows, (c) the same query executed from an anonymous client returns zero rows AND/OR is rejected by RLS, (d) a direct SQL `SELECT * FROM public.favorites WHERE user_id = '<user-B-id>'` issued from user-A's session returns zero rows (the SELECT policy filters by `auth.uid()` regardless of the WHERE predicate the client supplies), (e) an admin session (any role, including super-admin) querying the favorites table sees only their own rows — there is no admin override permission. Attempt to INSERT a favorite row with `user_id` set to user-B's id from user-A's session; confirm the INSERT is rejected (the WITH CHECK ties `user_id` to `auth.uid()`). Attempt to DELETE user-B's favorite row from user-A's session; confirm zero rows are deleted.

**Acceptance Scenarios**:

1. **Given** user-A is signed in, **When** they query the favorites surface, **Then** the response contains every row whose `user_id` equals user-A's `auth.uid()` AND zero rows belonging to any other user.
2. **Given** user-B is signed in and has saved listings, **When** user-A queries the favorites table by any path (RPC, REST, direct SQL with a forged `WHERE user_id = '<user-B>'`), **Then** zero of user-B's rows appear — they are absent from the wire-level payload, not merely hidden in the UI.
3. **Given** an anonymous client, **When** it queries the favorites table, **Then** RLS denies the read AND no rows are returned regardless of the client's query parameters.
4. **Given** an admin or super-admin session, **When** they query the favorites table, **Then** they see ONLY their own favorites — Phase 17 introduces NO `favorites.view_all` (or equivalent) permission, so there is no admin cross-user reader path.
5. **Given** user-A is signed in, **When** they attempt to INSERT a `favorites` row whose `user_id` is NOT their own `auth.uid()`, **Then** the INSERT is rejected by the policy's WITH CHECK (a user can only create their own favorites).
6. **Given** user-A is signed in, **When** they attempt to DELETE a `favorites` row belonging to user-B, **Then** zero rows are deleted (the DELETE policy filters by `auth.uid()`).
7. **Given** the listing's publisher is signed in, **When** they query favorites, **Then** they see ONLY listings THEY have saved — they cannot see who favorited their own listings (no save-count, no saver identities; favorite counts are out of scope per the Scope note).

### User Story 4 — Favorites persist across sessions and devices (Priority: P2)

A signed-in user who saves listings on one device finds the same favorites when they sign in on another device, and finds them unchanged after closing and reopening the app, after a fresh install and re-login, and after a server-side refresh. Favorites are durable server-side state keyed to the user's account, not local device cache.

**Why this priority**: P2 because durable, account-bound persistence is the expectation a "save" action sets — but it is a property of the P1 storage design (server-side `favorites` table) rather than a separable surface. It is called out as its own story because the persistence guarantee is a distinct, independently-verifiable acceptance criterion ("Adding/removing a favorite persists across sessions" per the IMPLEMENTATION_PLAN).

**Independent Test**: Sign in as a test user on device-1 (the reference Infinix Note 8). Save 3 listings. Sign out. Sign in as the same user on device-2 (Pixel 8 Pro AVD). Confirm all 3 favorites appear on the FavoritesPage and the corresponding cards show filled hearts. Un-save 1 listing on device-2. Return to device-1, pull-to-refresh / re-open the FavoritesPage, and confirm the un-saved listing is gone (2 remain). Force-stop and relaunch the app on device-1; confirm the 2 favorites persist. Uninstall and reinstall the app on device-1, sign in again; confirm the 2 favorites are still present (they live server-side, not in local storage).

**Acceptance Scenarios**:

1. **Given** a signed-in user has saved listings on one device, **When** they sign in with the same account on a different device, **Then** the same set of favorites appears.
2. **Given** a signed-in user has saved listings, **When** they force-stop and relaunch the app, **Then** the favorites persist unchanged.
3. **Given** a signed-in user has saved listings, **When** they uninstall, reinstall, and sign in again, **Then** the favorites persist (they are server-side state, not local cache).
4. **Given** a user un-saves a listing on device-A, **When** they refresh the FavoritesPage on device-B, **Then** the un-saved listing is absent on device-B (last-write-wins server state; no client-side stale cache survives a refresh).

### User Story 5 — A favorite_added lead event is recorded the first time a user saves a listing (Priority: P2)

The first time a signed-in user ever favorites a given listing, the system records one `favorite_added` lead event (the event type Phase 16 reserved in the `lead_events` enum) tagged with the listing, the user, and a server timestamp — feeding the same engagement substrate that the future analytics surfaces (Phase 19 agency analytics, Phase 20 admin dashboard) will read. Per Q3=B, the event is deduplicated: re-favoriting a listing the user previously saved and then removed does NOT emit a second `favorite_added` event, and un-favoriting emits no event at all (there is no `favorite_removed` type).

**Why this priority**: P2 because, like Phase 16's lead events, the data substrate must be captured from day one so the eventual analytics surface has a meaningful historical record — but Phase 17 ships no favorites-analytics dashboard, so the capture is invisible to users in v1. Deduplication (once per user+listing ever) keeps "interest in this listing" honest: a user toggling the heart on and off repeatedly is one interested party, not N engagement signals.

**Independent Test**: Sign in as a test user with no prior favorites. Favorite listing-X. Query `lead_events`; confirm exactly one row with `event_type = 'favorite_added'`, `listing_id` = X, `user_id` = the test user, `created_at` recent. Un-favorite listing-X (confirm NO new `lead_events` row — no `favorite_removed`). Re-favorite listing-X; query `lead_events` again and confirm STILL exactly one `favorite_added` row for (this user, X) — the re-add did not emit a duplicate. Favorite a different listing-Y; confirm a second `favorite_added` row now exists for (this user, Y). Sign in as a different user and favorite listing-X; confirm a `favorite_added` row exists for (the second user, X) — dedup is per (user, listing), not global per listing.

**Acceptance Scenarios**:

1. **Given** a signed-in user who has never favorited listing-X, **When** they favorite listing-X for the first time, **Then** exactly one `lead_events` row is inserted with `event_type = 'favorite_added'`, `listing_id` = X, `user_id` = the user, and a server-generated `created_at`.
2. **Given** a user who has previously favorited and then un-favorited listing-X (a `favorite_added` event already exists for that user+listing), **When** they favorite listing-X again, **Then** NO new `favorite_added` lead event is inserted (deduplicated per Q3=B) AND the `favorites` row is still re-created (the favorite itself is restored; only the event is suppressed).
3. **Given** a user un-favorites any listing, **When** the removal is processed, **Then** NO lead event is inserted (there is no `favorite_removed` event type and Phase 17 introduces none).
4. **Given** the favorite-add write path runs, **When** it inserts the `favorites` row AND (conditionally) the `favorite_added` lead event, **Then** both are written in a single atomic transaction — there MUST NEVER be a `favorite_added` event without its corresponding favorite having been created in the same call, nor a partially-committed state.
5. **Given** the favorite-add write path is invoked by the client, **When** the request is processed, **Then** the `favorite_added` lead event is written through a privileged server-side path (a SECURITY DEFINER RPC) — NO direct client INSERT permission on `lead_events` is granted (consistent with the Phase 16 posture).
6. **Given** the `lead_events` enum already includes `favorite_added` from the Phase 16 migration, **When** Phase 17 writes the event, **Then** NO schema migration to `lead_events` is required (Phase 17 adds the write path only).

### User Story 6 — Anonymous visitor is invited to sign in when they tap the heart (Priority: P3)

An anonymous (signed-out) visitor browsing listings sees the same heart control that signed-in users see — favorites are advertised to everyone so the feature is discoverable. When the anonymous visitor taps the heart, instead of silently failing, the app surfaces a localized "Sign in to save favorites" prompt and routes them into the existing login flow. After signing in, they can save listings normally.

**Why this priority**: P3 because anonymous browsing is a first-class path in this marketplace (per Phases 13–15 all being anonymous-accessible), but the conversion nudge ("sign in to save") is a refinement on top of the core authenticated favorite flow rather than a prerequisite for it. The simplest correct behavior — show the control, prompt on tap — is also the highest-converting per Aqarmap/Bayut convention.

**Independent Test**: Without signing in (anonymous session), browse the home feed and open a listing's details page. Confirm the heart control renders (it is NOT hidden). Tap the heart; confirm (a) NO `favorites` row is inserted, (b) NO `favorite_added` lead event is recorded, (c) a localized "Sign in to save favorites" prompt appears and routing into the login page occurs (or a sign-in sheet). Complete sign-in; confirm the user can now favorite normally and the listing they attempted to save is NOT auto-saved (the tap that triggered the prompt does not silently persist after login — the user re-taps to save, an explicit action).

**Acceptance Scenarios**:

1. **Given** an anonymous visitor on any card or details surface, **When** the surface renders, **Then** the heart control is visible (not hidden, not greyed-out) in the empty/un-saved state.
2. **Given** an anonymous visitor taps the heart, **When** the tap is handled, **Then** NO `favorites` row and NO `favorite_added` lead event are written AND a localized "Sign in to save favorites" prompt surfaces AND the app routes into the existing Phase 5 login flow.
3. **Given** an anonymous visitor who tapped the heart and signed in, **When** sign-in completes, **Then** the listing they attempted to save is NOT auto-favorited — the user makes an explicit re-tap to save (no hidden side-effect from the pre-auth tap).
4. **Given** an anonymous visitor declines to sign in (dismisses the prompt / backs out of login), **When** they return to browsing, **Then** the heart remains in the empty state AND no favorite was created.

### Edge Cases

- **Anonymous user taps the heart**: Per US6 / Q2=A — the heart renders for everyone; the tap routes to the sign-in flow with a localized prompt; no row, no event. The pre-auth tap does not silently persist after login.
- **A signed-in user favorites a listing that is later soft-deleted or transitions to a terminal status (sold / rented / rejected / paused / expired / deleted)**: The `favorites` row is preserved (the `listing_id` FK uses `ON DELETE RESTRICT` per the Phase 16 Q4=C precedent, and listings soft-delete via `status='deleted'` rather than hard-deleting). The FavoritesPage still shows the card with a localized "no longer available" indicator (US2 AS-3). The user can still un-favorite it to clean up their list.
- **A user favorites, un-favorites, and re-favorites the same listing**: Each add re-creates the `favorites` row (hard-delete on removal means the row is gone in between); the `favorite_added` lead event is emitted ONLY on the first-ever add (deduped against `lead_events` history per Q3=B). The toggle is idempotent — the `(user_id, listing_id)` uniqueness constraint guarantees at most one live favorite row per pair.
- **Two devices/sessions of the same user toggle the same listing's favorite concurrently** (device-1 adds while device-2 removes within the same second): Last-write-wins on the row's existence — the later write determines whether the row exists. Because the add is idempotent (insert-if-absent) and the remove is delete-if-present, the final state is deterministic given write order; no optimistic concurrency control or lock is introduced (consistent with Phase 16 Q8=A's data-class reasoning — favorites are personal, low-stakes data).
- **A user attempts to favorite a non-approved listing directly via the RPC** (e.g., a crafted request targeting a `pending_review` or `rejected` listing's id): The `add_favorite` RPC validates `status='approved'` (mirroring `record_lead_event`) and rejects with a structured error — favorites can only be created for listings the user could legitimately see.
- **A user attempts to favorite a listing id that does not exist**: The RPC rejects with a `listing_not_found` structured error; no row is created.
- **The `favorites` write succeeds but the optimistic UI already advanced, then the user backgrounds the app**: The server state is authoritative; on next FavoritesPage load / refresh the UI reconciles to the server truth. A failed write reverts the optimistic heart (US1 AS-4).
- **A user has a very large number of favorites (e.g., 500+)**: The FavoritesPage paginates (no unbounded query per Constitution performance baseline); the card-level favorited-state lookups for the home/search/map surfaces use a bounded session-scoped favorited-id set rather than per-card round-trips.
- **A signed-in user's account is later deleted**: The `favorites.user_id` FK uses `ON DELETE CASCADE` (matching the `user_preferences` precedent) so the user's favorites are removed with their account — a deleted user leaves no orphaned favorites.
- **The same listing is favorited by many different users**: Each user's favorite is an independent row; there is NO aggregate save-count surfaced anywhere (no popularity display in v1 per the Scope note); the per-user RLS gate keeps every row private to its owner.
- **A favorite's listing leaves `approved` while the user is mid-scroll on the FavoritesPage**: The page renders from the data it fetched; on the next refresh the "no longer available" indicator appears. No real-time downgrade mid-scroll (Realtime is Phase 22's concern).
- **Network failure during a favorite toggle**: The optimistic state reverts AND a localized retryable error surfaces AND the database has no partial state (US1 AS-4).

## Requirements *(mandatory)*

### Functional Requirements

#### Favorite toggle (cards + details)

- **FR-001**: System MUST replace the Phase 13 `PerListingActionBlock` Favorite CTA's Coming-soon snackbar handler (per `lib/features/listing_details/presentation/widgets/per_listing_action_block.dart`) with a working favorite toggle. Only the Favorite CTA's handler and its filled/empty visual state MUST change; the Share and Report CTAs in the same block MUST remain Phase 13 Coming-soon stubs, and the surrounding widget tree (layout, icons, ordering, button styles) MUST NOT be reflowed.
- **FR-002**: System MUST surface a heart control on every listing-card surface — at minimum the Phase 13 home feed, the Phase 14 search results, and the Phase 15 map marker preview — wired to the real favorite toggle. Because these live surfaces render bespoke card widgets (`HomeListingCardTile`, `SearchResultCard`, `MarkerPreviewPopover`) rather than the Phase 2 `PropertyCard` (whose `favorite`/`onFavoritePressed` heart slot is used only in the debug gallery), the heart MUST be a single shared widget embedded into each bespoke card so one toggle behavior governs every card surface.
- **FR-003**: Tapping the heart on a listing the signed-in user has NOT saved MUST optimistically render the filled state AND insert exactly one `public.favorites` row for `(auth.uid(), listing_id)` via the privileged write path (FR-010).
- **FR-004**: Tapping the heart on a listing the signed-in user HAS saved MUST optimistically render the empty state AND hard-delete the corresponding `public.favorites` row via the write path (FR-011).
- **FR-005**: The favorited state of a listing MUST be consistent across every surface within a session — a listing saved on one card surface MUST render as saved on its details page and on any other card surface without requiring a manual refresh. The app MUST maintain a session-scoped set of the signed-in user's favorited listing ids to drive this consistency without per-card server round-trips.
- **FR-006**: When a favorite write fails (network or server error), the system MUST revert the optimistic heart to its prior state AND surface a localized, retryable error AND leave the database in a consistent state (no row on a failed add; the existing row preserved on a failed remove).
- **FR-007**: The favorite toggle MUST be idempotent at the data layer — a `(user_id, listing_id)` uniqueness constraint MUST prevent a second live favorite row for the same pair, so a double-add cannot create duplicates and a double-remove cannot error the user out.

#### Anonymous behavior

- **FR-008**: The heart control MUST render for anonymous (signed-out) visitors in the empty state on every card and details surface — it MUST NOT be hidden or greyed-out (per Q2=A).
- **FR-009**: When an anonymous visitor taps the heart, the system MUST NOT write any `favorites` row or `favorite_added` lead event AND MUST surface a localized "Sign in to save favorites" prompt AND route into the existing Phase 5 login flow. The pre-authentication tap MUST NOT auto-save the listing after the user signs in — saving requires an explicit post-login tap.

#### Table, indices, and the server-side write path

- **FR-010**: System MUST create a new `public.favorites` table with at minimum: `user_id` (UUID, NOT NULL, foreign key to `auth.users(id)` with `ON DELETE CASCADE`), `listing_id` (UUID, NOT NULL, foreign key to `public.listings(id)` with `ON DELETE RESTRICT` per the Phase 16 Q4=C precedent), and `created_at` (TIMESTAMPTZ, NOT NULL, server default `now()`), with a uniqueness constraint on `(user_id, listing_id)` (e.g., a composite primary key) so a user cannot double-save a listing.
- **FR-011**: Adding a favorite from the client MUST go through a privileged server-side write path — an `add_favorite(listing_id)` SECURITY DEFINER RPC — that (a) requires an authenticated session (rejects anonymous callers), (b) validates the target listing exists and is `status='approved'` (mirroring `record_lead_event`), (c) idempotently inserts the `favorites` row for `(auth.uid(), listing_id)`, and (d) atomically emits the `favorite_added` lead event per FR-014. No direct client INSERT permission on `public.favorites` is required for the add path, because the lead-event emission MUST be co-transactional and `lead_events` grants no client INSERT.
- **FR-012**: Removing a favorite MUST hard-delete the `(auth.uid(), listing_id)` row via a **self-only DELETE RLS policy** on `public.favorites` (the client DELETEs its own row directly, gated by `auth.uid() = user_id`) per Q5=A. A dedicated `remove_favorite` RPC MUST NOT be introduced — removal emits no lead event and needs no co-transactional work, so the direct RLS-gated DELETE is the idiomatic posture. Removal MUST NOT emit any lead event.
- **FR-013**: System MUST create an index supporting the FavoritesPage primary access pattern — at minimum an index on `favorites(user_id, created_at DESC)` for per-user newest-first reads.

#### Lead event

- **FR-014**: The first time a signed-in user ever favorites a given listing, the `add_favorite` write path MUST insert exactly one `lead_events` row with `event_type = 'favorite_added'`, `listing_id` = the listing, `user_id` = `auth.uid()`, and a server-generated `created_at` — in the SAME transaction as the `favorites` row insert. The metadata-capture posture (IP / user-agent per Phase 16 FR-014a) MAY be reused if available to the RPC; it is not required for favorites and is plan-time.
- **FR-015**: The `favorite_added` lead event MUST be deduplicated per `(user_id, listing_id)` across all time (per Q3=B) — if a `favorite_added` event already exists for the calling user and target listing, the `add_favorite` write path MUST NOT insert a second one (the `favorites` row is still (re-)created; only the event is suppressed). The dedup check MUST be performed server-side within the write path (e.g., against the `lead_events` history), not in client code.
- **FR-016**: Removing a favorite MUST NOT emit any lead event — there is NO `favorite_removed` event type and Phase 17 MUST NOT add one. The `lead_events.event_type` CHECK constraint MUST NOT be modified by Phase 17 (the `favorite_added` value already exists from the Phase 16 migration).

#### Privacy / RLS

- **FR-017**: System MUST enable Row Level Security on `public.favorites` with a strict self-only posture: a row MUST be SELECT-able and DELETE-able IF AND ONLY IF the requesting session's `auth.uid()` equals the row's `user_id` (per Q5=A the DELETE policy is the client's direct removal path). Row creation MUST go exclusively through the `add_favorite` SECURITY DEFINER RPC (FR-011), which sets `user_id = auth.uid()`; the spec MUST NOT grant a direct client INSERT on `public.favorites`, so a client cannot create a favorite that bypasses the co-transactional `favorite_added` event. (Defense-in-depth: if a guarded INSERT policy is added, its WITH CHECK MUST tie `user_id` to `auth.uid()`.)
- **FR-018**: Anonymous reads and writes on `public.favorites` MUST be denied entirely (no `anon` policy).
- **FR-019**: Phase 17 MUST NOT introduce any cross-user reader path for favorites — NO publisher-visibility of who saved their listings, NO admin `favorites.view_all`-style permission, NO aggregate save-count exposed to any client. The listing's publisher and platform admins MUST see ONLY their own favorites, identical to any other user.

#### Favorites page

- **FR-020**: System MUST ship a new feature folder at `lib/features/favorites/` containing the `FavoritesPage`, its BLoC, repository, and data source, following the Clean Architecture layering (Principle IV) — Supabase types confined to `data/`, domain entities and repository interface in `domain/`.
- **FR-021**: The FavoritesPage MUST list every listing the signed-in user has saved, ordered by `favorites.created_at DESC` (most-recently-saved first), each rendered with the Phase 13 listing-card composition (image, title, price formatted per Phase 9 locale rules, location) and the same shared heart control (FR-002) in the filled, tappable state.
- **FR-022**: The FavoritesPage MUST be reachable via a "My Favorites" tile on the Phase 5 Profile page (per Q1=A) that navigates to a new `/favorites` route. The entry point inherits the Profile page's authenticated-only access (anonymous users do not reach the Profile page), so the FavoritesPage itself assumes a signed-in session.
- **FR-023**: Tapping a saved listing's card on the FavoritesPage MUST navigate to that listing's Phase 13 details page (`/listings/:id`) — for BOTH available and no-longer-available favorites (per Q4=A). The Phase 13 details page already handles terminal states (sold/rented render the page read-only; deleted renders the existing `_NotFoundView`), so the FavoritesPage adds no bespoke tap handling for unavailable cards; every card body is tappable and routes to details.
- **FR-024**: Tapping the filled heart on a card within the FavoritesPage MUST remove the listing from the list immediately AND delete the `favorites` row (the same toggle path as FR-004).
- **FR-025**: A saved listing whose underlying listing is no longer `approved` (sold / rented / rejected / paused / expired / deleted) MUST still render on the FavoritesPage with a localized "no longer available" indicator AND remain un-saveable via its heart. The page MUST NOT silently drop such favorites and MUST NOT crash when a favorited listing is unavailable.
- **FR-026**: When the signed-in user has zero saved listings, the FavoritesPage MUST render a localized empty-state message (not a crash, not a blank screen).
- **FR-027**: The FavoritesPage MUST paginate (cursor- or page-based, matching the Phase 13 home-feed pattern) rather than issuing an unbounded query (Constitution performance baseline).

#### Localization, theming, accessibility

- **FR-028**: Every user-visible string introduced by Phase 17 — the heart's accessibility label, the "Sign in to save favorites" prompt, the FavoritesPage title and empty-state, the "no longer available" indicator, the Profile "My Favorites" tile label, and any toggle-failure error message — MUST flow through `AppLocalizations` with both `ar` and `en` entries.
- **FR-029**: The FavoritesPage, the heart control, the sign-in prompt, and the empty-state MUST render correctly in all four combinations of (light/dark theme) × (Arabic RTL / English LTR), using logical insets and Phase 2 design tokens (no inline hex literals, no raw font sizes, no ad-hoc paddings).

#### Constitutional and dependency constraints

- **FR-030**: The PR MUST NOT add any new third-party dependency — favorites are implemented with the existing Flutter / BLoC / `go_router` / `supabase_flutter` stack and an in-house Postgres table. No analytics, telemetry, or "favorites/wishlist" package is introduced.
- **FR-031**: The PR MUST honor Principle III — RLS enabled on `public.favorites`, self-only policies, no service-role key on the client, and the lead-event write through a SECURITY DEFINER RPC because `lead_events` grants no client INSERT.
- **FR-032**: The PR MUST NOT introduce any hardcoded role/permission branch for favorites (there is no admin override; favorites are self-only by RLS, not by an application-layer check).
- **FR-033**: The PR MUST NOT modify the Phase 13 Share or Report CTAs in `PerListingActionBlock`, and MUST NOT alter the Phase 16 `lead_events` table schema (it consumes the reserved `favorite_added` enum value as-is).

### Key Entities

- **Favorite**: A private, per-user record that a signed-in user has saved a specific approved listing. Keyed on `(user_id, listing_id)` (a user cannot double-save the same listing); carries the save timestamp. Owned exclusively by the user — readable, insertable, and deletable only by them. Hard-deleted on un-save (no soft-delete, no history retained in the favorites table itself).
- **Favorite Toggle**: The user-facing action of saving (heart fill) or un-saving (heart empty) a listing, available wherever a listing card or details page appears. Optimistic in the UI, durable server-side, idempotent at the data layer, and consistent across all surfaces within a session via a shared favorited-id set.
- **Favorites Page**: The signed-in user's private, paginated, newest-first list of saved listings, reached from a "My Favorites" Profile tile. Renders available listings as standard cards and unavailable (no-longer-`approved`) favorites with a "no longer available" indicator.
- **`favorite_added` Lead Event**: The engagement signal recorded the first time (and only the first time) a user ever favorites a given listing — the Phase 16-reserved `lead_events` enum value, now written by Phase 17's `add_favorite` path, deduplicated per `(user_id, listing_id)`. There is no companion removal event. Private to the listing's analytics substrate; no user-facing favorites analytics ship in Phase 17.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A signed-in user tapping the empty heart on an approved listing sees it fill within 300 ms (optimistic) AND exactly one `public.favorites` row for `(their user_id, that listing_id)` exists within 2 seconds — verified on the reference Infinix Note 8 against a fixture data set.
- **SC-002**: A signed-in user tapping the filled heart on a saved listing sees it empty within 300 ms AND the corresponding `public.favorites` row is deleted within 2 seconds.
- **SC-003**: A listing favorited on one surface (e.g., the home feed) shows as favorited (filled heart) on every other surface within the same session — its details page, search results, map preview, and the FavoritesPage — with no manual refresh, verified by saving on one surface and navigating to each other surface.
- **SC-004**: A signed-in user opening the FavoritesPage sees every listing they have saved (newest-saved first) AND zero listings they have not saved — verified against a fixture where the same user has a known saved set and other users have different saved sets.
- **SC-005**: User-A querying the favorites surface (via RPC, REST, or direct SQL with a forged `WHERE user_id = '<user-B>'`) receives ONLY user-A's own rows and ZERO of user-B's rows at the wire level — repeated across an anonymous session (zero rows) and an admin/super-admin session (only their own rows, no cross-user override).
- **SC-006**: A direct SQL `INSERT INTO public.favorites (user_id, listing_id) VALUES ('<user-B-id>', ...)` issued from user-A's session is rejected by the INSERT policy's WITH CHECK, and a `DELETE` targeting user-B's row from user-A's session deletes zero rows — cross-user write isolation matches cross-user read isolation.
- **SC-007**: The first-ever favorite of a listing by a user inserts exactly one `favorite_added` `lead_events` row; un-favoriting inserts none; re-favoriting the same listing inserts NO additional `favorite_added` row (deduped per `(user_id, listing_id)`); a different listing or a different user does produce its own first-time event — all four verified by direct `lead_events` inspection.
- **SC-008**: The `favorites` row insert and its (conditional) `favorite_added` event are atomic by construction — both inserts share a single PL/pgSQL function body, so Postgres transaction semantics guarantee "both or neither" with no intermediate commit. Verified by inspecting the `add_favorite` function body (one transaction) plus a SQL smoke check confirming zero partial states (never an event without the favorite, never a half-committed row). No new automated test is added, per the project's manual-verification convention.
- **SC-009**: Favorites persist across app restart, across a fresh reinstall + re-login, and across a different device signed in with the same account — verified by saving on device-1 and reading on device-2, and by force-stop/relaunch and uninstall/reinstall on device-1.
- **SC-010**: An anonymous visitor sees the heart control rendered (not hidden, not greyed) AND tapping it writes zero rows / zero events AND surfaces the localized "Sign in to save favorites" prompt routing into the login flow — verified on the reference device in an anonymous session.
- **SC-011**: A favorited listing that has left `approved` status still appears on the FavoritesPage with a localized "no longer available" indicator and is un-saveable; the page does not crash or silently drop it — verified by favoriting an approved listing, flipping its status server-side, and reloading the page.
- **SC-012**: A signed-in user with zero saved listings sees a localized empty-state on the FavoritesPage (not a crash, not a blank) — verified on a fresh account.
- **SC-013**: The favorites surfaces (heart control, FavoritesPage, sign-in prompt, empty-state, "no longer available" indicator) render correctly in all four combinations of (light/dark) × (Arabic RTL / English LTR) on the reference Infinix Note 8 (480 dp) AND a 412 dp emulator profile — all strings localized and directionally correct.
- **SC-014**: A repository-wide check of the dependency manifest returns zero new third-party packages introduced by Phase 17 (favorites use the existing stack) AND zero hardcoded role/permission branches in the favorites feature code (favorites are self-only by RLS).
- **SC-015**: The FavoritesPage issues a bounded (paginated) query — verified by inspecting the query for a `LIMIT` / cursor and confirming no unbounded full-table scan of a user's favorites on a large-favorites fixture.

## Assumptions

- Favorites are an **authenticated-only capability**: holding a favorite requires a Supabase Auth session because `favorites.user_id` foreign-keys `auth.users(id)`. Anonymous users see the heart and are prompted to sign in (Q2=A). This matches the Phase 13 stub's documented intent ("Favorites: dedicated phase wires favorite mutation + auth-required").
- The Phase 13 `PerListingActionBlock` already renders a Favorite CTA wired to a Coming-soon snackbar. The live home/search/map feeds render bespoke card widgets (`HomeListingCardTile`, `SearchResultCard`, `MarkerPreviewPopover`), NOT the Phase 2 `PropertyCard` — whose `favorite`/`onFavoritePressed` heart slot is used only in `lib/debug/theme_gallery_page.dart`. Phase 17 therefore introduces ONE shared `FavoriteHeartButton` widget and embeds it into each bespoke card plus the `PerListingActionBlock` Favorite CTA (rather than routing favorites through `PropertyCard`); the surrounding Phase 13 widget trees and the Share/Report stubs are not touched (per Phase 16 FR-035's forward statement that Phase 17 takes over the Favorite stub). The shared widget keeps the toggle behavior, anonymous-prompt branch, and token styling in one place.
- The Phase 16 `public.lead_events` table and its `event_type` CHECK constraint already include `favorite_added` (per `supabase/migrations/20260527120002_create_lead_events_table.sql`). Phase 17 adds only the write path; no `lead_events` schema migration is needed. The Phase 16 `record_lead_event` RPC explicitly rejects `favorite_added`, so Phase 17 uses a dedicated `add_favorite` SECURITY DEFINER RPC for the co-transactional favorite-row + lead-event write.
- The dedup rule "emit `favorite_added` once per `(user_id, listing_id)` ever" (Q3=B) is implemented by checking the `lead_events` history for an existing `favorite_added` row for the calling user + target listing before inserting — the `lead_events` table serves as the prior-favorite memory, so no separate history/`is_active` column is needed on `favorites` (the favorites table stays a simple hard-delete toggle). Because favorites are authenticated-only, `user_id` is never null and the dedup key is always well-defined.
- The `favorites.listing_id` FK uses `ON DELETE RESTRICT` (Phase 16 Q4=C precedent) and the `user_id` FK uses `ON DELETE CASCADE` (the `user_preferences` precedent in `supabase/migrations/20260506120003_create_user_preferences.sql`). Listings soft-delete via `status='deleted'`, so the RESTRICT FK is never exercised in normal operation; it defends against accidental hard-deletes and preserves the "no longer available" FavoritesPage affordance.
- The FavoritesPage renders favorited listings using the existing public listing projection (`v_listings_public`, per `supabase/migrations/20260525120002_create_v_listings_public.sql`) for available listings, and a fallback path for favorites whose listing has left `approved` (so the "no longer available" indicator can render). The exact read shape — a dedicated `v_favorites` view joining favorites to the listing base data, versus a two-step read (favorite ids, then a listing lookup) — is plan-time; the spec mandates the behavior (newest-first, available + unavailable both shown), not the view shape.
- The new `/favorites` route is added to the Phase 1 `go_router` surface alongside the existing routes (`AppRoutes`/`AppRouteNames` in `lib/core/routing/app_router.dart`); it does not require a route guard beyond the Profile-page entry point being authenticated-only, but a redirect-to-login on a deep-link cold-launch to `/favorites` while signed-out is a reasonable plan-time hardening.
- The session-scoped favorited-id set (FR-005) is held in a favorites BLoC/cubit and hydrated on sign-in (one read of the user's favorite ids); card surfaces consult this set for their heart state rather than issuing per-card server reads. On sign-out the set is cleared. This mirrors the Phase 16 `InquiriesUnreadCubit` shared-singleton pattern.
- No save-count, "saved by N people," or popularity ranking is introduced — favorites are strictly private behavioral data per Principle III and the IMPLEMENTATION_PLAN goal. Any future popularity/recommendation surface is a separate spec with its own privacy review.
- Concurrent toggles from two sessions of the same user follow last-write-wins on row existence (no optimistic concurrency control), consistent with the Phase 16 Q8=A reasoning for personal CRM-class data. The idempotent insert-if-absent / delete-if-present semantics make the converged state deterministic given write order.
- The "My Favorites" Profile tile (Q1=A) was chosen over a home app-bar heart action and a bottom-navigation tab: the Profile page is already the authenticated-only home for personal/account surfaces (matching the "saved items live under the account" convention), and a bottom nav would introduce a new global navigation paradigm beyond Phase 17's scope. The trade-off (one extra tap, lower discoverability than an always-visible app-bar heart) is accepted because the heart on every card/details surface is itself the primary, highly-discoverable entry into the favoriting behavior; the Profile tile is the review surface, not the save surface.

### Resolved — Session 2026-05-29

Three product-shaping decisions resolved during `/speckit-specify` before validation. Answers are folded into the Functional Requirements (FR-008, FR-009, FR-014, FR-015, FR-022), User Stories (US2, US5, US6), Edge Cases, Key Entities, and Assumptions.

- **Q1 — FavoritesPage entry point**: Where should the FavoritesPage be reachable from in the app's navigation — a Profile-page tile, a home app-bar heart action, or a dedicated bottom-navigation tab? → **A: Profile-page "My Favorites" tile.** The FavoritesPage is reached via a tile on the existing authenticated-only Phase 5 Profile page, navigating to a new `/favorites` route. The Profile page is the conventional home for personal/account surfaces and is already auth-gated (favorites are auth-only). A home app-bar heart was rejected as redundant with the per-card hearts that are the primary save affordance; a bottom-navigation tab was rejected as introducing a new global navigation paradigm beyond Phase 17's scope. See FR-022 and US2.
- **Q2 — Anonymous heart tap**: When a signed-out visitor taps the heart, should the app prompt them to sign in, hide the heart entirely for anonymous users, or render it disabled/greyed? → **A: Show the heart for everyone; prompt sign-in on tap.** The heart renders in the empty state for anonymous visitors (so the feature is discoverable) and tapping it surfaces a localized "Sign in to save favorites" prompt that routes into the existing login flow — no row, no event, and no silent auto-save after login. Hiding the control was rejected (anonymous users never discover favorites exist); greying it out was rejected (offers no path to use the feature from the tap). Matches Aqarmap/Bayut convention. See FR-008, FR-009, and US6.
- **Q3 — Un-favorite persistence + lead-event semantics**: On un-favorite, should the row be hard-deleted or soft-deleted, and how often should `favorite_added` fire? → **B: Hard delete on un-favorite; `favorite_added` fires once per `(user_id, listing_id)` ever (deduplicated).** Un-favoriting hard-deletes the `favorites` row. The `favorite_added` lead event is emitted only the first time a user ever favorites a given listing, deduplicated against the `lead_events` history; re-favoriting a previously-removed listing re-creates the favorite row but emits no second event, and un-favoriting emits nothing (there is no `favorite_removed` type). The "event on each add, no dedup" option was rejected because repeated toggle-on/off by one interested party would inflate "interest in this listing" with noise; a soft-delete (`is_active` flag) was rejected as unnecessary schema/RLS complexity since the `lead_events` history already provides the prior-favorite memory the dedup needs. See FR-014, FR-015, FR-016, and US5.
