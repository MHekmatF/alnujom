> **Scope note**: Phase 13 introduces the *public read surface* — the home feed of approved listings + the public listing-details page — that Phase 12's `approve_listing` Edge Function feeds. It does NOT ship search or filter logic (Phase 14 owns search + facet filters + `tsvector` infrastructure); it does NOT ship the map view (Phase 15 owns `flutter_map` + OSM tiles); it does NOT ship working contact wiring — call / WhatsApp / inquiry-form (Phase 16 owns `inquiries` + `lead_events` + the inquiry pipeline); it does NOT ship favorites persistence (a later phase owns the `favorites` table mutators per §6.2); it does NOT ship the moderation reports pipeline beyond a UI stub (a later phase owns the `reports` mutators); it does NOT ship push notifications or Realtime subscriptions (Phase 22 owns push + Realtime); it does NOT ship payments / promotion (post-v1); it does NOT ship analytics dashboards (post-v1). Phase 13 ships exactly: (a) one new index migration `0022_listings_indexes.sql` introducing three composite indexes on `public.listings` for home-feed read patterns; (b) the public `HomePage` at `lib/features/home/presentation/pages/home_page.dart` composing a hero search-bar surface + a horizontal property-type-shortcut row + a paginated latest-listings card feed; (c) the public `ListingDetailsPage` at `lib/features/listing_details/presentation/pages/listing_details_page.dart` composing Phase 12's Q8=A five shared display widgets (`ListingGallery`, `ListingPriceBlock`, `ListingLocationBlock`, `ListingAmenitiesBlock`, `ListingDescriptionBlock`) with the addition of a Contact block (call / WhatsApp / inquiry-form CTAs — scope per Q2) and a per-listing-action block (favorite / share / report — scope per Q2); (d) a new `ListingDetailsBloc` independent of Phase 12's preview BLoC per Phase 12 R-53; (e) `cached_network_image`-backed image loading on top of Phase 11's `getPublicUrl()` URL pattern (Phase 1's `cached_network_image` dependency becomes actively consumed at a public surface for the first time in Phase 13); (f) replacement of Phase 1's `ShellHomePage` as the `/` route (Phase 1 router contract explicitly forward-stated this); (g) a `go_router` route for `/listings/:id` that deep-links to a specific listing's details; (h) cursor-based pagination on the home feed using the `(published_at DESC, id DESC)` ordering pair with a page size of 20; (i) pull-to-refresh + infinite-scroll affordances on the home feed; (j) anonymous browsing (no auth gate) for both the home and the details page; (k) the Q1 / Q2 / Q3-resolved stub treatments for the surfaces that later phases (14, 16, 17, 22) will wire.

### Session 2026-05-23

Six questions resolved in session before `/speckit-plan`. The first three (Q1-Q3) were resolved during `/speckit-specify` and pin (Q1) the visual + behavioral treatment of the hero search bar + property-type shortcuts as uniformly-stubbed Phase-14 placeholders, (Q2) the scope of the listing-details contact + per-listing-action CTAs as uniformly-stubbed for v1 (all six CTAs route to a "Coming soon" snackbar — call / WhatsApp / inquiry-form / favorite / share / report — with the wiring deferred to later phases), and (Q3) the anonymous-tap pattern for auth-required CTAs as a forward-state convention (when a later phase wires any auth-required CTA, an anonymous tap shows a "Please sign in" snackbar with a "Sign in" action that routes to login). All six answers are folded into the "Functional Requirements", "Success Criteria", "Edge Cases", and "Assumptions" sections below.

- **Q1 — Hero search + property-type shortcut stub behavior in Phase 13**: The IMPLEMENTATION_PLAN names both surfaces as Phase 13 deliverables but Phase 14 owns search + facet filters + sort. What does the user see + experience when they tap the hero search bar or any property-type shortcut chip? → **A: Both surfaces visible + tappable; each shows a localized "Coming soon — search will land in a future release" snackbar.** The hero search bar AND the eight property-type shortcut chips render at Phase 2-token-styled affordances on the HomePage. The hero search bar is a single tappable surface (NOT a focusable `TextField` — tapping focus would summon the keyboard for nothing useful in v1); tapping it dismisses the keyboard if open AND surfaces a localized snackbar message keyed `home_search_coming_soon` ("Search is coming soon — for now, browse the latest listings below"). Each property-type chip surfaces the same snackbar via a shared key `home_property_shortcut_coming_soon` ("{type} listings filter is coming soon — browse the full feed below") — the message is localized to embed the tapped property-type label (e.g., "Apartment listings filter is coming soon"; "Villa listings filter is coming soon"; etc.). No new routes are introduced for these stubs; tapping does NOT navigate. Phase 14's hero-search replacement swaps the tap handler from "show snackbar" to "navigate to `/search` (or push a search overlay) AND route into the Phase 14 search-results surface". The property-type chip tap handler swaps from "show snackbar" to "navigate to `/search?property_type=<key>` (or equivalent)". Phase 13's stub is the minimum-viable placeholder — it tells the user the surface exists AND is intentionally deferred (NOT broken or styled-but-unimplemented). The disabled-styled alternative (Option B) was rejected because it gives no information about when the feature lands; the placeholder-route alternative (Option C) was rejected because it adds one navigation hop for zero v1 value; the immediate-filter alternative (Option D) was rejected because it blurs the Phase 13 / 14 boundary AND ships hidden product behavior (filtered-feed mode) outside the IMPLEMENTATION_PLAN's stated Phase 13 scope.
- **Q2 — Contact / favorite / share / report CTA scope on listing details in Phase 13**: The IMPLEMENTATION_PLAN names "contact-CTA stubs (Phase 16 wires them), favorite + share + report stubs" but doesn't specify which surfaces are fully functional now vs which are pure stubs. → **A: ALL six CTAs are localized "Coming soon" snackbar stubs in Phase 13.** The three Contact-block CTAs (Call / WhatsApp / Send inquiry) AND the three per-listing-action-block CTAs (Favorite / Share / Report) render as Phase 2-token-styled buttons on the ListingDetailsPage. Tapping any of the six surfaces a localized snackbar keyed per CTA: `contact_call_coming_soon`, `contact_whatsapp_coming_soon`, `contact_inquiry_coming_soon`, `action_favorite_coming_soon`, `action_share_coming_soon`, `action_report_coming_soon` (or a single shared `coming_soon` key with per-CTA arguments — plan-time research codifies whether to use six keys or one parameterized key). The Phase 13 PR introduces NO functional contact wiring: no `url_launcher.launch('tel:...')` call, no `url_launcher.launch('https://wa.me/...')` call, no `share_plus.share(...)` call. The dependency surface for Phase 13 narrows accordingly — `url_launcher` IS still introduced per FR-027 for the video-tap launch (which is a Phase 11 deferred item resolved in Phase 13, NOT a Q2 contact-CTA), but `share_plus` (and any equivalent share plugin) is DEFERRED to whichever later phase actually wires share. The choice deliberately accepts the v1 launch with no working contact method on the details page; the rationale is (a) Phase 16 ships immediately after Phase 13 (and Phase 14 + 15) per the IMPLEMENTATION_PLAN's stated order, so the "no working contact" window is short, (b) the Phase 13 PR's scope is constrained to the public read-side; mixing in contact wiring would expand the test surface, (c) launching the Call CTA via `tel:` looks deceptively functional — the call goes through the OS phone app — but the underlying `lead_events` analytics + Phase 16 inquiry pipeline are NOT recorded, which would create silent attribution gaps in Phase 16's debut analytics that Phase 16 would then need to back-fill. Uniform "Coming soon" until Phase 16 ships is the cleaner v1 boundary. Phase 16 will replace each tap handler (Call / WhatsApp / Inquiry-form) with the wired surface AND introduce the `lead_events`-emitting `record_lead_event` Edge Function call site. The Favorite / Share / Report CTAs follow the same pattern — their wiring lands in whichever later phase introduces the `favorites` / share / `reports` mutators respectively.
- **Q3 — Anonymous-user tap on an auth-required CTA**: For any CTA that requires a signed-in user (most concretely "favorite" under Q2's resolved scope; secondarily the inquiry-form under Q2-A/B; possibly report depending on the project's policy), what does the app do when an anonymous user taps it? → **A: Show a localized "Please sign in to use this feature" snackbar with a "Sign in" action button that routes to the login page.** Under Q2=A, the six CTAs on the listing-details page are uniformly "Coming soon" snackbar stubs for both anonymous AND authenticated users — so Q3=A has NO Phase-13 user-visible behavior. Q3=A is captured as a FORWARD-STATE CONVENTION for later phases: when Phase 16 (or any subsequent spec) wires an auth-required CTA (Favorite, Send inquiry, Report), the wired CTA MUST check the auth state via Phase 5's `AuthBloc` AND on an anonymous tap surface a localized snackbar keyed `auth_required_please_sign_in` ("Please sign in to use this feature") with a "Sign in" action button that routes to the existing Phase 5 login page (`AppRoutes.login` or the established Phase 5 route name). After successful sign-in, the user lands back on the listing-details page in authenticated mode; whether the previously-tapped CTA auto-completes (intent-replay) or requires a second tap is left to the wiring phase's plan-time research (Option B's auto-redirect-with-intent-replay variant is acknowledged as a possible future refinement but is NOT mandated by Q3=A — the v1 convention is "snackbar with Sign-in CTA"). The DISABLED-CTA alternative (Option C) was rejected because it hides the feature's existence from anonymous users; the LOCAL-STORAGE-FAVORITES alternative (Option D) was rejected because the device-loss / sync-complexity tradeoff is not warranted for v1 AND the `favorites` table mutator ship date is not yet decided. The Q3=A convention applies UNIFORMLY to every later-phase auth-required CTA across every feature, NOT just the listing-details surface — it is a project-wide UX convention codified by this spec's resolution.
- **Q4 — `ListingDetailsPage` back-arrow behavior when the user landed via deep-link** *(added during `/speckit-clarify` 2026-05-23)*: FR-010 introduces `/listings/:id` as a deep-linkable surface (paste a share URL, future Phase 22 deep-link receive, future Phase 15 map popover, future Phase 14 search-result tap). FR-021 specifies the `AppBar` has a back arrow. When the user opened the page directly via deep-link AND the in-app back-stack has zero entries, what does tapping back do? → **D: Conditional behavior — `if (Navigator.canPop()) Navigator.pop(); else context.go(AppRoutes.home)`.** The `ListingDetailsPage`'s `AppBar` back arrow checks the navigator's `canPop()` predicate at tap time. If the back-stack has entries (the in-app navigation case: user came from HomePage card tap, or from a future Phase 14 search-result tap, or from any other in-app surface that pushed onto the navigator), the back arrow performs a normal `Navigator.pop()` returning the user to whichever page pushed them onto the details page. If the back-stack is empty (the deep-link entry case: user opened `/listings/<id>` directly from a browser / Phase 22 push notification / Phase 15 map popover that used `context.go` rather than `context.push`), the back arrow performs `context.go(AppRoutes.home)` routing the user to the HomePage. The behavior is implemented in the `ListingDetailsPage` widget's back-arrow IconButton's `onPressed` handler — NO router-level shell-route restructuring is required (rejected alternative Option C); NO unconditional always-home routing (rejected alternative Option B which would lose in-app navigation history when future Phase 14 search results push details onto the stack); NO always-pop behavior (rejected alternative Option A which exits the app on deep-link entry — poor UX for shared-link consumers). The `Navigator.canPop()` predicate is the standard Flutter navigator API; no go_router-specific abstraction is required. The system back gesture (Android hardware back button) is handled identically via Flutter's `WillPopScope` (or `PopScope` on newer Flutter) wrapping the page body — same conditional logic. This pattern is the FORWARD-STATE CONVENTION for every later-phase page that may be entered via deep-link (Phase 14 search-result detail page if it has its own URL, Phase 22 push-notification deep-link targets, etc.) — each such page's back affordance MUST follow Q4=D. The pattern is codified in `research.md` as a reusable widget mixin (`DeepLinkAwareBackButton`) OR as an inlined helper (plan-time research codifies whether to abstract).
- **Q5 — Steady-state interaction latency budget for HomePage feed pagination** *(added during `/speckit-clarify` 2026-05-23)*: SC-001 sets cold-launch to ≤ 3 sec; SC-004 sets card-tap → details navigation to ≤ 1 sec; no budget defined for infinite-scroll next-page load NOR for pull-to-refresh first-page reload. → **A: ≤ 2 sec p95 for both infinite-scroll page-load AND pull-to-refresh, measured at the device on Syrian-realistic network conditions.** The budget aligns with Phase 12 Q6=A's `approve_listing` / `reject_listing` Edge Function latency budget — the same Supabase backend + same network leg justifies the same number even though Phase 13's reads are simpler (no Edge Function cold start, no JWT verification, no audit log, no service-role swap; just a PostgREST query against `public.listings` + embedded selects → JSON response → BLoC state update + widget rebuild). The budget covers the full client-to-client round-trip: user scroll triggers ScrollController threshold → `HomeFeedNextPageRequested` event fires → BLoC state transitions to `loadingMore` → datasource issues the Supabase client query (with cursor filter, `LIMIT 20`, ordered by `(published_at DESC, id DESC)`) → PostgREST returns rows → BLoC parses + appends to `state.listings` → ListView.builder renders the new cards (text placeholders first; images progressively fill via `cached_network_image`). The 2-second budget excludes the image-byte fill time (which is bound by `cached_network_image` defaults + Supabase Storage egress + Syrian network — uncontrollable in Phase 13). Pull-to-refresh follows the same shape but starts with a `HomeFeedRefreshRequested` event AND the BLoC clears the existing cursor before issuing the first-page query. The budget is verifiable from (a) the Supabase Edge Function logs' `duration_ms` field — though Phase 13 makes no Edge Function call so this is N/A for the PostgREST path; (b) Supabase database query logs (PostgREST request duration tracked separately); (c) a manual stopwatch session on the Infinix Note 8 over Syrian-realistic 4G with the device-side timer starting at the user gesture (scroll-threshold crossing OR pull-release) AND stopping when the new cards' text content first appears (NOT when images finish loading). Tighter targets (Option B, ≤ 1 sec p95) were rejected as risking flaky verification on bad-network days where p95 naturally exceeds 1 sec; looser targets (Option C, ≤ 3 sec p95) were rejected as degrading the perceived snappiness of a public-browse marketplace surface; "no budget" (Option D) was rejected as removing the verification gate entirely and pushing the question to Phase 24 observability, which is a poor v1 launch posture. If the budget is breached repeatedly in production, plan-time research SHOULD evaluate (i) thinning the home-feed SELECT projection (drop embedded selects from `listing_prices` + `listing_media` and lazy-load on card render), (ii) adding a materialized view `mv_listings_home_feed` refreshed on a schedule (Phase 23 admin settings area might own the refresh cadence), (iii) migrating to a dedicated Supabase tier — none are in Phase 13 scope. Phase 22 (push + Realtime) MAY revisit this budget if Realtime fan-out adds overhead. Phase 24 (observability) MAY introduce structured telemetry for these latencies for production monitoring.
- **Q6 — HomePage state freshness on background→foreground resume** *(added during `/speckit-clarify` 2026-05-23)*: When the user opens the app, browses the HomePage feed, then backgrounds the app (presses Home / switches to WhatsApp / takes a phone call) and returns — minutes, hours, or days later — does the feed auto-refresh OR preserve the prior state? → **A: No auto-refresh on resume; user pulls-to-refresh manually. The cached `HomeBloc` state (cursor + loaded card list + scroll position) is preserved across background/foreground transitions.** No `AppLifecycleState` observer is registered in `HomeBloc`. No "if backgrounded > N minutes auto-refresh" threshold logic ships. No "Updated X ago" passive freshness badge ships. The resume behavior is the Flutter framework's natural default: the widget tree is re-rendered from the preserved BLoC state; the `ListView.builder` rebuilds its visible window from the cached card list; the scroll position is restored by Flutter's `PageStorage` (or the `ScrollController` if the controller is preserved across the widget rebuild — plan-time research codifies whether explicit `PageStorageKey` is needed). `cached_network_image` continues to serve images from its disk cache (cache stale-ness is not a concern: edited listings produce new `storage_path` UUIDs per Phase 11 R-14, which produce new URLs, which naturally cache-miss and re-fetch). The choice is consistent with the existing "Folded default — Realtime subscription" which already commits Phase 13 to a pull-based freshness model — adding background-resume auto-refresh would contradict that. It also conserves bandwidth on Syrian 4G networks where users frequently switch back-and-forth from WhatsApp (auto-refresh on every quick switch is wasteful). Rejected alternatives: Option B (threshold-based auto-refresh) adds `AppLifecycleState` observer complexity that Phase 22 (Realtime + push) will replace anyway; Option C (always auto-refresh) is bandwidth-wasteful; Option D (passive "Updated X ago" badge) adds UI complexity for minimal product value. Phase 22 (Realtime + push) is the natural attachment point for true live freshness — when Realtime ships on `public.listings.status='approved'`, the home feed updates live without manual gesture. The Q6=A resume behavior is the explicit baseline UNTIL Phase 22 swaps it. The Q6=A convention applies to the HomePage ONLY (the ListingDetailsPage's separate question — "what happens on resume if the listing was un-approved while the user was backgrounded" — is already addressed in the Edge Cases section as "page does NOT auto-redirect; pull-to-refresh on the home feed surfaces the change").

> **Folded default — Routing replaces Phase 1's `ShellHomePage`**: Phase 1's `app_router.dart` (contract `specs/001-project-foundation/contracts/app-router.md` lines 10 + 46) explicitly forward-stated "Phase 13 replaces the shell home with the real home". Phase 13 changes `AppRoutes.shellHome = '/'` builder from `const ShellHomePage()` to `const HomePage()` AND removes the `lib/shell/shell_home_page.dart` file (Phase 1 explicitly captured this as Phase 13 follow-up; `lib/shell/` directory is deleted in the same commit). The route NAME (`AppRouteNames.shellHome` → `'shell-home'`) MAY be renamed to `AppRouteNames.home` → `'home'` AND the path constant `AppRoutes.shellHome` to `AppRoutes.home` (still bound to `/`); every consumer of the old name updates the import in the same Phase 13 PR. (If the rename surface is too broad for one PR, an interim back-compat alias `AppRoutes.shellHome = AppRoutes.home` MAY be left in place; this is a Phase 13 plan-time decision codified in `research.md`.)

> **Folded default — Deep-link route shape**: The listing-details route is `/listings/:id` with `id` bound to the `public.listings.id` UUID. The route NAME is `AppRouteNames.listingDetails` → `'listing-details'`. Deep-linking from another surface (Phase 14 search result; Phase 15 map marker popover; Phase 12 publisher dashboard rejection banner; a hypothetical share URL pasted into a browser) lands on the same page. The path-parameter `id` is parsed as a UUID; invalid UUIDs route to a localized "Listing not found" error page (Phase 1's `errorBuilder` is amended to handle this case — alternatively, the page itself renders the not-found state when the BLoC's `LoadListing` returns a `Failure`). Plan-time research codifies which approach lands.

> **Folded default — Pagination shape**: Cursor pagination using `(published_at DESC, id DESC)` as the ordering pair, page size 20, cursor encoded as the tuple of the last row's `published_at` ISO-8601 timestamp + `id` UUID. The `WHERE` clause for the next page is `(published_at, id) < (<last_published_at>, <last_id>)` (lexicographic compare). Why `published_at` not `created_at`: the IMPLEMENTATION_PLAN §Phase 13 says "latest listings", which in the real-estate market context means "most-recently-published-to-public" — `created_at` would order by draft-creation time which is publisher-visible only and includes draft / pending / rejected timestamps that anonymous users cannot observe. Phase 12's `approve_listing` sets `published_at = now()` per Q2=A; the column is non-NULL for every anonymous-visible row. Pull-to-refresh discards the cursor and re-issues the first page; infinite-scroll appends pages until the server returns < 20 rows (sentinel for "no more"). Note: the IMPLEMENTATION_PLAN's literal text named `(created_at, id)` as the tiebreaker; Phase 13's research file overrides to `(published_at, id)` for the user-facing read pattern AND keeps `created_at` available as a secondary index for admin / publisher surfaces — both indexes ship per FR-001.

> **Folded default — Empty-state UX**: When the home feed has zero approved listings (e.g., fresh deploy before any Phase 12 approval; admin in dev environment with no seed data), the HomePage renders a localized "No listings yet — be the first to publish!" empty-state with an icon and (for signed-in publishers holding a non-`pending` `publisher_status`) a CTA button routing to the Phase 10 listing form. For unauthenticated visitors, the CTA is replaced with "Sign in to publish" routing to the login page.

> **Folded default — Image loading + caching**: The `ListingGallery` widget (consumed verbatim from `lib/shared/presentation/widgets/listing_display/listing_gallery.dart` per Phase 12 Q8=A) uses `cached_network_image` (Phase 1 dependency, becomes actively consumed at a public surface for the first time in Phase 13) against public URLs returned by Phase 11's `getPublicUrl()` pattern. The cache uses the default `CachedNetworkImage` disk-cache configuration (no custom cache key, no custom max-age, no custom max-cache-size); a future spec MAY tighten cache configuration if cold-launch image counts become a bandwidth concern. Placeholder while loading: a 16:9 shimmer skeleton (a new Phase 2-token-styled `ShimmerBox` widget — added if not already present in Phase 2's component library; otherwise a `CircularProgressIndicator` centered in the gallery card). Error fallback: a localized "Image unavailable" tile rendered in place of the failing image.

> **Folded default — Video tap behavior (resolves Phase 11 deferred item)**: Phase 11 explicitly deferred external-player launch to Phase 13. The `ListingGallery` widget surfaces video media items with a play-button overlay (Phase 12 Q8=A widget contract); Phase 13 wires the tap-handler to launch the video URL via the `url_launcher` package (a new dependency — Phase 13 introduces it; alternative low-risk launcher plugin if `url_launcher` poses a sanctions / packaging concern). Internal video player is OUT of scope; the OS handles playback via the registered MIME-type intent (Android: VLC / MX Player / Chrome). External-link media (Phase 11 schema enum `'external_link'`) follows the same external-launch pattern; the schema reserves this enum value but Phase 11 deferred all `external_link` UI to a future spec — Phase 13 inherits that deferral except for the gallery rendering of a video-style play-button overlay (no URL launch since there's no `external_link` UI surface to author from yet).

> **Folded default — Anonymous-only auth-state observation**: The `HomePage` and `ListingDetailsPage` observe the auth state (Phase 5's `AuthBloc`) to decide whether to surface auth-required CTAs (per Q3) and to gate empty-state CTA routing (per FR-019). Phase 13 does NOT show a separate "My listings" view — Phase 10's `MyListingsPage` is unchanged; the home feed shows public-approved listings only, identical for anonymous and authenticated users. Sign-in / sign-out events trigger an `AuthChanged` event in `ListingDetailsBloc` so the page re-renders auth-dependent CTAs without requiring a manual refresh.

> **Folded default — Realtime subscription**: NOT introduced in Phase 13 per Constitution alignment with the plan's Phase 22 boundary. The home feed and details page are pull-based; pull-to-refresh is the user's only way to see newly-approved listings or status changes (e.g., a listing approved while the user is browsing won't appear until they pull-to-refresh). Phase 22 may add a Realtime subscription on `public.listings` filtered by `status='approved'` to keep the feed live.

> **Folded default — Sort options on the home feed**: Phase 13 ships ONE sort order (newest-published-first per the folded pagination default). Phase 14 owns the sort-options UI (newest / price low→high / price high→low) on its search-results page. The Phase 13 home is the marketing/discovery surface, not a power-user filter surface — the single sort order matches Aqarmap-style marketplace conventions for the home shelf.

> **Folded default — Cross-currency display on cards**: The home-feed card consumes Phase 9's `MoneyFormatter` via a lightweight version of Phase 12's `ListingPriceBlock` (or directly via `MoneyFormatter` if the price block widget's full surface is over-engineered for the card). The displayed currency follows the user's `user_preferences.display_currency` (Phase 9). For anonymous users without a preference row, the default display currency is the listing's stored primary currency (no conversion attempted client-side). The home-feed card does NOT show the "originally X" secondary line that `ListingPriceBlock` shows on the details page — the card surface is compact.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Anonymous visitor opens the app, browses the public home feed, scrolls to load more listings, pulls to refresh (Priority: P1)

A user with no prior sign-in opens AlNujom (tapping the launcher icon on Android or re-entering a backgrounded app). The app initializes Supabase (Phase 1), wires the router (Phase 1, updated by Phase 13 to land on `HomePage` at `/`), reads the persisted locale (Phase 3) + theme (Phase 2), and renders the new `HomePage`. The page shows: (a) a top app bar with the AlNujom brand mark on the start side + a sign-in entry point on the end side (icon button or text link, localized); (b) a **hero search bar** rendered as a tappable surface styled per Phase 2 tokens — tap behavior governed by Q1; (c) a **property-type shortcut row** rendered as a horizontal scroll of 8 chips (apartment / villa / land / shop / office / farm / warehouse / other), each with a Phase 2 icon and localized label, each chip's tap governed by Q1; (d) a **section header** localized "Latest listings"; (e) a **paginated feed** of listing cards, 20 per page, each card composed of the listing's main image (consumed from `public.listing_media` where `is_main=true AND kind='image'`, rendered via `cached_network_image` on the Phase 11 `getPublicUrl()` URL), a 2-line title, the property-type + purpose badge, the location (governorate / city — area omitted on the card for space), the primary price formatted via Phase 9's `MoneyFormatter` in the user's `display_currency`, and the time-since-publish ("3 hours ago" / "2 days ago", Phase 3 localized). The feed renders in a single vertical column on Infinix Note 8 portrait; the card aspect on a 2024+ flagship may render as a 2-column grid (a Phase 2 responsive-design decision codified in design tokens). The user scrolls; when they reach the bottom of the first 20 cards, the BLoC issues the next-page cursor query and appends 20 more cards. The user pulls down at the top of the list; the BLoC discards the cursor and re-issues the first page, replacing the feed. The user never signs in; nothing on the home requires auth (modulo Q1's resolution).

**Why this priority**: P1 because Phase 13 is the first surface where Phase 12's `approve_listing` produces user-visible value. Without a public home feed, the entire admin approval pipeline (Phases 10 + 11 + 12) has no consumer — the marketplace cannot launch. Constitution XI (Android-First MVP) implies the home feed is the primary entry point for Syrian users discovering the app for the first time.

**Independent Test**: Apply Phase 13 migration via Supabase MCP `apply_migration`. Have ≥ 25 `status='approved'` listings in the database with staggered `published_at` timestamps (seeded via Phase 10 + Phase 11 + Phase 12 happy paths in prior sessions; or seeded via direct SQL bypassing the Edge Functions for test setup). Launch the app on an Infinix Note 8 over WiFi AND signed out (clear app data to remove any persisted Supabase session). Confirm the app opens directly to the new `HomePage` (NOT to `ShellHomePage`, NOT to the login page). Confirm the page renders within 3 seconds of cold launch (text + image placeholders, then images filling in). Confirm exactly 20 listing cards appear; scroll to the bottom; confirm the next 5 cards load via infinite scroll (cursor pagination — the 21st-through-25th cards render with no duplicate of the 20th card). ### User Story 5 — Cursor pagination correctness across concurrent writes; no duplicate / skipped rows (Priority: P2)

A user is browsing the home feed; the user has scrolled past the first 20 cards (cursor advanced to position 20). Meanwhile, a Phase 12 admin approves a new listing AND the admin's approval sets `published_at = now()` — so the newly-approved listing's `published_at` is LATER than every card the user has already seen. The user scrolls further; the next-page query uses the cursor `(<last_published_at>, <last_id>)` AND the `WHERE` predicate `(published_at, id) < (<last_published_at>, <last_id>)` — the newly-approved listing's `published_at` is GREATER than the cursor, so the newly-approved listing is NOT included in the next page. The user does NOT see a duplicate of the 20th row (the cursor's strict `<` predicate skips the 20th row) AND does NOT see the newly-approved listing on subsequent pages (it's a "first-page" candidate now; the user must pull-to-refresh to see it). The user pulls-to-refresh; the cursor is discarded; the first page is re-fetched; the newly-approved listing appears at position 0 of the refreshed feed. Plan-time research codifies the exact pagination shape AND the rationale for the strict `<` predicate AND the explicit choice of `(published_at, id)` over `(created_at, id)`.

**Why this priority**: P2 because pagination correctness is a foundational concern but the production fault-rate is low under normal Phase 12 admin throughput (1-10 approvals per day expected in v1, not 1000s per minute). A duplicate or skip is annoying but not launch-blocking; the user pulls-to-refresh and the state resolves.

**Independent Test**: From the seeded ≥ 25 listings, scroll past the first 20 cards. ### Edge Cases

- **Listing approved after the user loaded the feed but before they scrolled to the bottom**: Per US5, the new listing does NOT appear on the user's current pagination cycle; it appears after pull-to-refresh.
- **Listing un-approved (status flipped out of `approved`) while the user is on its details page**: The page does NOT auto-redirect (no Realtime in v1). If the user pulls-to-refresh on the home feed, the listing disappears from the feed; if they navigate away and back to the details page, the page renders "Listing not found".
- **User scrolls extremely fast through a long feed (Infinix Note 8 + 100+ cards loaded)**: Per Phase 2 design-token decisions, the feed uses `ListView.builder` with lazy off-screen disposal AND `cached_network_image` to control memory. Plan-time research codifies the maximum loaded card count + the off-screen disposal threshold.
- **Cold-launch image fetch on slow Syrian 4G**: The `cached_network_image` shimmer placeholder renders for as long as the network takes; no hard timeout in v1 (the OS / network stack manages the eventual fail-state). A future spec MAY add a per-image timeout + Retry affordance.
- **User has zero `user_preferences` row (anonymous or never-set)**: Per the folded default, the display currency falls back to the listing's stored primary currency; no conversion is attempted.
- **User has `display_currency='USD'` but the latest `exchange_rates` row is missing (Phase 9 admin hasn't seeded a rate yet)**: The price block renders the listing's original-currency price WITHOUT conversion AND surfaces a localized "(rate unavailable)" footnote (or a similar Phase 9 fallback — plan-time research codifies Phase 9's existing behavior).
- **A listing's main image fails to load (storage 404, network error, corrupt image)**: The gallery's image-error fallback renders the localized "Image unavailable" tile per the folded default; the gallery's other images continue to render normally.
- **A listing has only video media items (no image)**: The card on the home feed renders a localized "Video listing" placeholder (a Phase 11 schema invariant says `is_main` must be `kind='image'`, so this case may be impossible if Phase 11's CHECK constraint holds — plan-time research codifies the defensive UI).
- **A listing's title is extremely long (200+ chars)**: The card on the home feed truncates at 2 lines via Phase 2 typography token (ellipsis at the end); the full title renders on the details page (no truncation).
- **A listing's description is empty**: The `ListingDescriptionBlock` renders a localized "No description provided" placeholder (or hides the entire block — plan-time research codifies Phase 12 Q8=A widget behavior).
- **A listing's amenities `jsonb` is empty or `{}`**: The `ListingAmenitiesBlock` renders nothing (the widget hides itself when there are zero truthy keys) — plan-time research confirms with Phase 12 Q8=A.
- **Network failure on the home feed first-page fetch**: The HomePage shows a localized error state ("Could not load listings") with a Retry button.
- **Network failure on a details page fetch**: The page shows a localized error state with a Retry button.
- **Network failure mid-image-load**: The image tile shows the error fallback; the user can pull-to-refresh to retry all images.
- **User navigates to details, navigates back, then forward again** (back-stack rebalancing): The cached BLoC state allows the details page to render the cached listing data + media without re-fetching (a Phase 13 plan-time decision; alternative is re-fetch on every navigation — plan-time research codifies).
- **User backgrounds the app while on the HomePage, returns minutes/hours later** *(per Q6=A)*: The cached `HomeBloc` state (cursor + loaded card list + scroll position) is preserved; the widget tree re-renders from the cached state with NO auto-refresh. The user pulls-to-refresh manually to see newly-approved listings. `cached_network_image` continues to serve images from disk cache. Verified by SC-035.
- **A listing's `published_at` is NULL** (impossible in v1 under normal flow — Phase 12's `approve_listing` Edge Function unconditionally sets `published_at = now()` per Q2=A AND the public-read RLS predicate `status='approved' AND publish-window-open` filters out NULL-`published_at` rows from the anonymous query result altogether): No defensive UI shipped in Phase 13. If a future data-import path bypasses Phase 12 and produces NULL `published_at` rows that the RLS predicate admits, that path's spec MUST define the rendering behavior. The Phase 13 card renderer MAY assume `card.publishedAt != null` after RLS filtering.
- **Deep-link with a tracking parameter or fragment** (e.g., `/listings/<id>?utm_source=facebook`): The router ignores unknown query parameters; the page renders normally.
- **Deep-link without an `id` parameter** (e.g., `/listings/`): The router treats this as a malformed route AND falls back to the `errorBuilder` (or routes to the HomePage — plan-time research codifies).
- **Deep-link entry with empty in-app back-stack** *(per Q4=D)*: When the user opens `/listings/<id>` directly (paste in browser, future Phase 22 push deep-link, future shared-URL receive) AND the navigator stack has only the ListingDetailsPage entry, tapping the AppBar back arrow OR the Android system back gesture routes to the HomePage via `context.go(AppRoutes.home)` — NOT exits the app. Verified by SC-033.
- **A listing's purpose is `investment`** (less common but valid per §6.3 enum): The card's purpose badge renders the localized "Investment" label; the details page renders normally.
- **A listing's contact phone is identical to the publisher's profile phone**: The contact block renders normally; no special UX for self-contact (the publisher is unlikely to be viewing their own listing's details from a different account — but if they do, the call CTA fires the `tel:` intent normally per Q2).
