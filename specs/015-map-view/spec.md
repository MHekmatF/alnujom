# Feature Specification: Map View

**Feature Branch**: `015-map-view`
**Created**: 2026-05-24
**Status**: Draft
**Input**: Phase 15 — Map view with marker pins for approved listings, location-visibility honored, from `docs/IMPLEMENTATION_PLAN.md`

> **Scope note**: Phase 15 introduces the *public geospatial discovery surface* — a full-screen map page that renders approved listings as marker pins on top of OpenStreetMap tiles. It does NOT introduce new persistent state about listings (no schema additions to `public.listings`), no new contact CTAs (Phase 16 owns the contact pipeline), no new search/filter primitives (Phase 14 owns text + facet search — Phase 15 only *consumes* that filter shape when the map is entered from search), no publisher-side map editor (the Phase 10 pin-drop deferral remains open — a future spec owns the publisher's manual coordinate edit affordance), no offline tile caching beyond whatever the tile layer's default in-memory cache provides, no driving-directions / "navigate to" integration with the device's native maps app, no map-side write actions of any kind (favoriting, reporting, contacting from a marker preview are all out of scope and routed through the existing Phase 13 listing-details page). The Phase 15 PR ships exactly: (a) one new public read-only data source exposing the map's marker dataset, with server-side enforcement that `hidden` and `admin_only` listings never leave the database, and with server-side coordinate jitter applied to `approximate` listings so client-side code never sees the publisher's true coordinates for that visibility tier; the data source accepts the same filter shape as the Phase 14 search RPC so a search→map transition can carry active filters forward (per Q2=A); (b) a new `lib/features/map/` feature implemented as a single full-screen page composing `flutter_map` over OpenStreetMap raster tiles, with marker clustering, a tile-attribution widget, a "center on my location" affordance gated by Android runtime geolocation permission (per Q3=A), a filter-active alert dialog with a "Reset filters" action shown on entry from a filtered search (per Q2=A), and a tap-to-preview popover that links into the existing Phase 13 `/listings/:id` route; (c) entry-point wiring from THREE surfaces per Q1=A, Q2=A, and Q8=B: a prominent map tile/card embedded in the existing home page near the hero search bar (NOT a bottom-nav tab — no bottom-nav shell is added), a "View on map" affordance added to the Phase 13 `ListingDetailsPage`, and a "Show on map" affordance added to the Phase 14 `SearchPage` results that carries the active filters forward; (d) five new packages introduced into `pubspec.yaml` for the first time: `flutter_map` (the OSM-compatible map renderer), `latlong2` (its required coordinate-pair peer), `flutter_map_marker_cluster` (the cluster layer for FR-013), `geolocator` (the Android-API-backed geolocation plugin for FR-015b — no Google Play Services hard dependency per R-88), and `permission_handler` (the Android runtime permission prompt for FR-015b) — explicitly avoiding any Google Maps or Mapbox dependency per the constitution's Syria-sanctions risk locked decision. Phase 15 is anonymous-accessible (no auth gate on map viewing). It honors the Phase 13 / Phase 14 `DeepLinkAwareBackButton` convention (Q4=D from Phase 13) for back-navigation when the map is entered via deep-link.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Anonymous visitor opens the map from the home shell and sees approved listings as pins (Priority: P1)

A visitor (anonymous or signed-in) taps the prominent map tile on the home page (positioned near the hero search bar, per Q8=B) and lands on a full-screen map surface. The map opens fitted to a Syria-wide bounding box that includes all 14 governorates (per Q3=A). OpenStreetMap base tiles render across the country, with attribution to OpenStreetMap visible on the map at all times. A marker pin renders for each approved listing whose location-visibility permits public display. A "center on my location" affordance is visible somewhere on the map chrome; tapping it requests Android runtime geolocation permission (if not yet granted) and, on grant, pans and zooms the map to the device's location so the user can see nearby listings without manual panning.

**Why this priority**: P1 because geospatial discovery is the third primary discovery mode the marketplace ships (alongside the Phase 13 home feed and the Phase 14 keyword/facet search). Real-estate buyers regularly think in terms of "what's near this neighborhood" rather than in terms of keywords — without a map, that intent has no path through the product. The map is also the only surface where a buyer can compare the spatial distribution of multiple candidate listings at a glance.

**Independent Test**: Apply the Phase 15 migration. With ≥ 20 approved listings spread across multiple governorates (Damascus, Aleppo, Latakia at minimum), launch the app on the reference Infinix Note 8 (anonymous, no sign-in). Tap the prominent map tile on the home page (visible without scrolling, near the hero search bar). Confirm: (a) the map opens fitted to a Syria-wide bounding box covering all 14 governorates, (b) OpenStreetMap raster tiles render, (c) attribution text crediting OpenStreetMap is visible somewhere on the map view, (d) one marker pin appears for each approved listing whose visibility permits display, (e) `hidden` and `admin_only` listings produce no marker, (f) `approximate` listings show at a coordinate within (but not necessarily at the centroid of) their area's region — repeated reloads of the same listing produce a marker in roughly the same general spot rather than the publisher's exact coordinates. Tap the "center on my location" affordance; confirm the Android runtime permission prompt appears on first tap; grant permission; confirm the map pans/zooms to the device's location. Tap the same affordance again from a different region; confirm no permission prompt re-appears (the grant is persisted) and the map re-pans to the device's location.

**Acceptance Scenarios**:

1. **Given** Phase 15 is deployed AND ≥ 20 approved listings exist with varied `location_visibility` values AND the user is anonymous, **When** the user taps the prominent map tile on the home page (positioned near the hero search bar per Q8=B), **Then** the map opens fitted to a Syria-wide bounding box AND the OpenStreetMap base tiles render AND a marker pin renders for every approved listing whose visibility is `exact` or `approximate`, AND no marker renders for any listing whose visibility is `hidden` or `admin_only` regardless of approval status.
2. **Given** the map is rendered, **When** the user inspects the visible map area, **Then** an attribution label crediting OpenStreetMap is visible on the map.
3. **Given** an approved listing with `location_visibility = 'exact'`, **When** its marker renders on the map, **Then** the marker sits at the listing's stored coordinates.
4. **Given** an approved listing with `location_visibility = 'approximate'`, **When** its marker renders on the map, **Then** the marker sits at a jittered position within the listing's area region — not at the publisher's true stored coordinates — AND the jitter is computed server-side so the true coordinates never travel over the wire to the client.
5. **Given** the map is rendered AND the user has not yet granted geolocation permission, **When** the user taps the "center on my location" affordance, **Then** the Android runtime permission prompt appears; if the user grants permission, the map pans and zooms to the device's location at a neighborhood-level zoom.
6. **Given** the user has previously granted geolocation permission, **When** they re-tap the "center on my location" affordance, **Then** the permission prompt does NOT re-appear AND the map re-pans to the device's current location.
7. **Given** the user denies geolocation permission (one-time or "don't ask again"), **When** the user taps "center on my location," **Then** a localized message explains that location access is unavailable AND the map remains at the Syria-wide overview; the rest of the map's functionality is unaffected.
8. **Given** an admin flips a listing's visibility from `exact` to `hidden`, **When** the user reloads the map, **Then** the marker disappears for that listing without any client-side code change.

### User Story 2 — Visitor taps a marker to preview the listing, then opens its full details (Priority: P1)

A visitor scans the map, identifies an area of interest, taps a marker pin and sees a compact preview popover anchored to that pin. The popover shows enough information to decide whether the listing is worth a deeper look: a main image, the title, the primary price (formatted via the user's display currency), and the property type / purpose. Tapping the popover (or a clearly-marked "View details" affordance on it) navigates to the existing Phase 13 `/listings/:id` page for that listing, where the user can see the full gallery, description, amenities, and contact CTAs.

**Why this priority**: P1 because a map of unlabeled pins is unusable — the user cannot tell which pin is worth opening without a preview, and forcing a full-page navigation on every tap (which then requires a back button to return to the map and re-find their spot) destroys the spatial-browsing flow. The preview-then-detail pattern is the standard marketplace map UX.

**Independent Test**: From the same setup as US1, tap any visible marker. Confirm a preview popover appears anchored to the marker showing image + title + price + type/purpose badge. Tap the popover. Confirm navigation to the corresponding `/listings/:id` page (Phase 13's `ListingDetailsPage`) rendering the listing's full content. Tap the back arrow. Confirm return to the map at the same zoom/pan position with no re-load of the marker dataset (no flicker of pins disappearing and reappearing).

**Acceptance Scenarios**:

1. **Given** a marker is visible on the map, **When** the user taps it, **Then** a preview popover appears anchored to that marker showing the listing's main image, title, primary price in the user's display currency (per Phase 9 conventions), and a property-type / purpose badge.
2. **Given** a preview popover is open, **When** the user taps the popover (or its explicit "View details" affordance), **Then** the app navigates to `/listings/:id` for that listing — the Phase 13 `ListingDetailsPage` renders unchanged.
3. **Given** a preview popover is open, **When** the user taps anywhere else on the map (a different marker, a tile, the close affordance), **Then** the preview popover dismisses; tapping a different marker dismisses the current popover and opens the new one in a single tap.
4. **Given** the user navigates from the map preview into the listing details page and then presses Back, **When** the navigation returns, **Then** the map is restored at the prior zoom and pan position — the user does not have to re-pan or re-zoom to find the markers they were inspecting.
5. **Given** the preview popover renders for a listing whose primary image is missing or fails to load, **When** the popover renders, **Then** a localized image placeholder is shown in the popover and the rest of the preview content (title, price, badges) renders normally.

### User Story 3 — Location-visibility is honored end-to-end with no client-side leak (Priority: P1)

The product allows a publisher to mark a listing's location as `hidden` (no public coordinates at all), `approximate` (a fuzzy region rather than a precise pin), `exact` (the publisher's real coordinates are public), or `admin_only` (visible only inside the admin tooling). The map MUST honor each tier strictly. For `hidden` and `admin_only` listings, no marker, no preview, and no server response containing those listings' coordinates ever reaches the public client. For `approximate` listings, only a server-jittered coordinate ever reaches the client — a network-capture of the map's data fetch must NEVER reveal the publisher's true stored coordinates. For `exact` listings, the real coordinates render as the marker's position. The same source-of-truth (the visibility tier on the database row) governs the rendering — no application-layer post-filter is permitted; the public read gate is enforced at the data layer per Constitution Principle III.

**Why this priority**: P1 because publisher trust is the entire product's foundation. A publisher who marks their listing's location as `approximate` because their address is sensitive (a single mother, a celebrity, a high-net-worth household, a politically exposed person — Syria has many) must be able to trust that the marketplace will not silently expose the true coordinates through the map surface. A single high-profile leak destroys publisher trust permanently. Constitution Principles III and VIII directly require this gate.

**Independent Test**: Seed one approved listing per visibility tier (`hidden`, `approximate`, `exact`, `admin_only`) with non-trivially-different stored coordinates (so any "true coordinate leaked into approximate marker position" defect would be immediately visible). On an anonymous client, capture the network response for the map's marker dataset. Confirm: (a) the `hidden` and `admin_only` listings produce no rows in the response — they are absent from the response payload entirely, not merely hidden in the UI, (b) the `approximate` listing produces one row whose coordinates differ from the listing's stored coordinates AND fall within the listing's area, (c) the `exact` listing produces one row whose coordinates match the stored coordinates, (d) repeating the network capture on a fresh session shows the same set of rows (the visibility filtering is deterministic, not random).

**Acceptance Scenarios**:

1. **Given** an approved listing with `location_visibility = 'hidden'`, **When** the public map dataset is fetched, **Then** no row for that listing appears in the response — the listing is absent from the wire-level payload, not merely filtered out client-side.
2. **Given** an approved listing with `location_visibility = 'admin_only'`, **When** the public map dataset is fetched, **Then** no row for that listing appears in the response — same wire-level absence as `hidden`.
3. **Given** an approved listing with `location_visibility = 'approximate'` and stored coordinates `(lat₀, lng₀)` within area A, **When** the public map dataset is fetched, **Then** the response row for that listing carries coordinates `(lat', lng')` such that `(lat', lng') ≠ (lat₀, lng₀)` AND `(lat', lng')` falls within area A's region.
4. **Given** the same `approximate` listing, **When** the public map dataset is fetched multiple times across multiple sessions, **Then** no fetch ever returns the publisher's true stored coordinates for that listing — only jittered coordinates.
5. **Given** an approved listing with `location_visibility = 'exact'`, **When** the public map dataset is fetched, **Then** the response row carries the listing's true stored coordinates.
6. **Given** a non-approved listing (`draft`, `pending_review`, `rejected`, `paused`, `sold`, `rented`, `expired`, `deleted`), **When** the public map dataset is fetched, **Then** the listing produces no row regardless of its `location_visibility` value — the public approval gate composes with the visibility gate, and both must pass for the listing to appear on the map.

### User Story 4 — Marker clustering keeps the map readable when many listings are nearby (Priority: P2)

When many listings sit in a small geographic area at the current zoom level (e.g., 50 apartment listings within central Damascus when the map is zoomed out to show the whole governorate), individual marker pins overlap into an unreadable mass. The map clusters nearby markers into a single cluster marker labelled with the count of listings inside it. Tapping a cluster auto-zooms the map in (re-centered on the cluster) when the map is below its maximum supported zoom level — split clusters reveal the individual markers beneath; when the map is already at maximum zoom (so further zoom-in cannot split the cluster — e.g., multiple listings at identical coordinates), the contained markers spiderfy out around the tap point so each is independently tappable. As the user zooms in, clusters automatically split; as they zoom out, individual markers re-cluster.

**Why this priority**: P2 because a map of 50+ overlapping pins is functionally unusable, but the cost of shipping the map without clustering is degraded UX in dense areas rather than a complete blocker — sparse areas remain readable without clustering. Clustering ships with the map as a single PR to avoid a "v1 map is broken in cities" regression, but it is conceptually severable from US1–US3.

**Independent Test**: Seed ≥ 30 approved listings within a 2km radius of central Damascus. Reach the map zoomed out to show all of Syria. Confirm the Damascus area shows one or more cluster markers (with numeric count badges) rather than 30 overlapping pins. Tap a cluster while below max zoom; confirm the map auto-zooms in (re-centered on the cluster) and the cluster splits into individual markers (or smaller child clusters). Zoom the map to its maximum zoom level, then tap a cluster that contains co-located markers; confirm the contained markers spiderfy out around the tap point so each is independently tappable. Zoom in manually; confirm clusters split into individual markers as the zoom level increases past the clustering threshold.

**Acceptance Scenarios**:

1. **Given** the map is zoomed out enough that ≥ 5 markers would overlap visually, **When** the map renders, **Then** the overlapping markers are replaced by a single cluster marker labelled with the count of listings inside it.
2. **Given** a cluster marker is visible AND the map is NOT at the maximum supported zoom level, **When** the user taps it, **Then** the map auto-zooms in (re-centering on the cluster) by enough levels to split the cluster into its constituent markers (or into a child cluster the user can tap again).
2a. **Given** a cluster marker is visible AND the map IS at the maximum supported zoom level (e.g., multiple listings at identical coordinates), **When** the user taps it, **Then** the contained markers spiderfy out around the tap point so each is independently tappable.
3. **Given** the user zooms in manually past the clustering threshold, **When** the map redraws, **Then** clusters split into individual markers automatically.
4. **Given** the user zooms out across the clustering threshold, **When** the map redraws, **Then** individual markers re-cluster automatically.

### User Story 5 — Visitor enters the map from a listing details page centered on that listing (Priority: P2)

A visitor on a listing details page (Phase 13's `ListingDetailsPage`) wants to see where this property sits in relation to surrounding markets. They tap a "View on map" affordance on the details page (added in Phase 15 per Q1=A). The map opens centered on the listing's marker, at a zoom level where neighboring listings are also visible — so the visitor can immediately compare this listing's location to nearby alternatives without re-orienting the map. Pressing Back returns them to the listing details page.

**Why this priority**: P2 because the entry-from-details path is a high-leverage cross-link that lifts the map from "yet another tab" into "the spatial context for whatever I'm currently looking at." It is severable from US1 (which covers map-as-discovery-entry), but its absence makes the map feel disconnected from the rest of the product.

**Independent Test**: From a `/listings/:id` page (for any approved listing whose visibility permits map display), tap the "View on map" affordance. Confirm the map opens centered on that listing's marker (with the marker visibly emphasized or pre-selected), at a zoom level that shows neighboring markers. Confirm the back arrow returns to the listing details page (not to an earlier surface in the stack).

**Acceptance Scenarios**:

1. **Given** the user is on the listing details page for an approved listing whose visibility is `exact` or `approximate`, **When** they tap the "View on map" affordance, **Then** the map opens centered on the listing's marker at a zoom level that also shows neighboring markers.
2. **Given** the user opened the map via the "View on map" affordance, **When** they press the back arrow, **Then** they return to the listing details page they came from.
3. **Given** the user is on the listing details page for a listing whose visibility is `hidden` or `admin_only`, **When** the page renders, **Then** the "View on map" affordance is hidden (since the listing has no public map presence) — tapping it is impossible because it does not exist.

### User Story 6 — Visitor enters the map from a filtered search and the active filters carry over with a Reset alert (Priority: P2)

A visitor on the Phase 14 search-results screen has applied filters (e.g., purpose = sale, type = apartment, governorate = Damascus, price range $50k–$200k) and wants to see those matching listings on a map. They tap a "Show on map" affordance on the search results. The map opens with markers restricted to listings matching those filters (per Q2=A). Because the filtered view can be confusing ("why are there only 3 markers in Aleppo?"), the map immediately surfaces a non-blocking alert dialog naming the active filters (a compact summary, not a verbatim re-render of the search filter sheet) with a "Reset filters" action. Tapping "Reset filters" clears all carried-over filters and reloads the map to show all approved listings; tapping "Keep filters" (or dismissing the dialog) leaves the filtered view in place.

**Why this priority**: P2 because the search→map transition is a high-value cross-link for users who have already invested effort in narrowing their candidate set — they want to keep that investment when switching to the spatial view. The alert dialog prevents the surprising "why are so few markers visible" reaction without forcing the user to navigate back to the search screen to clear filters.

**Independent Test**: On the Phase 14 search screen, apply at least two filters (e.g., property type = apartment AND governorate = Damascus) that meaningfully narrow the result set. Tap the "Show on map" affordance on the search results. Confirm: (a) the map opens showing only markers matching the applied filters (not all approved listings), (b) an alert dialog immediately appears summarizing the active filters with two actions — "Reset filters" and "Keep filters" (or equivalent localized labels). Tap "Reset filters." Confirm the alert dismisses, the map reloads, and the marker count grows to the full unfiltered approved set. Re-enter the same flow; tap "Keep filters" instead. Confirm the alert dismisses and the map remains filtered.

**Acceptance Scenarios**:

1. **Given** the user is on the Phase 14 search-results screen with at least one filter active, **When** they tap the "Show on map" affordance, **Then** the map opens AND the marker dataset is restricted to listings matching the active filters (purpose, type, governorate/city/area, price range with currency, rooms, bathrooms, area size — the same filter shape the Phase 14 search RPC accepts) AND an alert dialog appears summarizing the active filters with a "Reset filters" and a "Keep filters" action.
2. **Given** the filter-active alert is open, **When** the user taps "Reset filters," **Then** the dialog dismisses AND the filters are cleared AND the map reloads to show all approved listings whose visibility permits display.
3. **Given** the filter-active alert is open, **When** the user taps "Keep filters" (or dismisses the dialog by tapping outside it), **Then** the dialog dismisses AND the map remains filtered AND the alert does NOT re-surface unless the user re-enters the map from a new filtered search.
4. **Given** the user enters the map from the Phase 14 search screen with NO filters active (e.g., a fresh search with no facets applied), **When** the map opens, **Then** no filter-active alert appears AND the map shows the full unfiltered approved set (identical to a home-shell entry per US1).
5. **Given** the user entered the map from a filtered search and chose "Keep filters," **When** they later navigate back to the search screen (via Back) and clear the filters on the search side, **Then** the next "Show on map" tap opens the map with no filter alert and shows the full approved set.

### Edge Cases

- **All listings cluster on top of each other at the maximum zoom level (e.g., two listings at literally the same coordinates due to two publishers sharing a building)**: The cluster expansion at maximum zoom level uses a spiderfy pattern so each individual marker is still tappable; if spiderfy is not feasible, the preview popover for the cluster shows a list of the contained listings with one tap-target per listing.
- **The map is opened with zero approved listings in the country (fresh deploy, no Phase 12 approvals yet)**: The map renders with no markers; a localized empty-state hint is displayed near the attribution credit explaining that no listings are available yet without obscuring the map itself.
- **Network failure while loading the marker dataset (Syrian connectivity drops, server returns 5xx)**: The map renders the base tiles (which the tile layer fetches independently) plus a localized error banner inviting the user to retry — the failure does not crash the page or leave it blank.
- **Network failure while loading tiles (e.g., Syrian government blocks the OpenStreetMap tile CDN at certain hours)**: The map renders the marker dataset on a grey/empty tile background plus a localized notice that map tiles are unavailable — the markers remain spatially accurate even if the underlying basemap fails to render.
- **User opens the map on a very narrow viewport (Infinix Note 8 portrait at 480 dp width)**: The marker preview popover sizes itself to the viewport width with appropriate inset margins; the popover does NOT push off-screen.
- **User toggles the app language while the map is open**: The map tiles, marker positions, and clustering remain unchanged; only localized UI chrome (attribution wording, empty-state text, error banners, preview-popover labels) re-renders in the new language.
- **User toggles the app theme (light ↔ dark) while the map is open**: The map base tiles render in whichever single tile-source the spec ships (Phase 15 ships one OpenStreetMap raster tile source; a separate dark-mode tile source is out of scope and follows the same forward-stated path as Phase 22 Realtime — a future spec may add a dedicated dark-mode tile source if needed); the marker and popover chrome respect the active theme tokens.
- **User taps a marker on the boundary of a cluster's tap area**: The tap is resolved to the topmost marker (the marker drawn last); if two markers are exactly co-located, the cluster spiderfy pattern from US4 kicks in.
- **An admin flips an `approximate` listing's `location_visibility` to `hidden` while the user has the map open**: The change is not reflected until the user next refreshes the map dataset (no Realtime in v1 per the constitution's Phase 22 boundary). The user's stale view does not leak any data because the previously-fetched coordinates for the listing were already jittered.
- **User denies the Android runtime geolocation permission (one-time deny, or "don't ask again")**: The "center on my location" affordance shows a localized message explaining that location access is unavailable; the map remains at whatever region it was at and continues to function normally for all marker-driven flows. The affordance is NOT hidden — a future re-tap can re-trigger the permission prompt (for one-time deny) or open the OS settings deep-link (for "don't ask again"); the exact recovery path is a plan-time UX decision.
- **Device geolocation fix is unavailable or times out (e.g., indoors with no GPS, low-power mode disabling location services)**: After permission is granted but a location fix can't be obtained within 10 seconds (pinned in research.md R-88 / contracts/phase15-geolocation-envelope.md as the `Geolocator.getCurrentPosition` `timeLimit`), a localized message explains that the device's location is unavailable and invites the user to try again later. The map remains at its current region.
- **User enters the map from a search with filters AND the filter set yields zero matching listings**: The map shows zero markers, the filter-active alert dialog still appears with the "Reset filters" action, AND a localized empty-state hint reinforces that the active filters match no listings; tapping "Reset filters" clears the filters and re-renders the full marker set.
- **User enters the map from a search with filters that include a currency-converted price range AND the latest exchange rate data is missing**: The map's filter dataset honors the same Phase 14 currency-conversion behavior — the price-range filter is applied with whatever conversion data is available; if the conversion fails entirely, the filter dialog explains and offers "Reset filters" as the recovery path.
- **Filter-active alert is mid-render when the user taps Back**: The Back gesture dismisses the alert first; a second Back gesture exits the map. The alert never blocks Back navigation entirely.

## Requirements *(mandatory)*

### Functional Requirements

#### Public read surface

- **FR-001**: System MUST expose a public read-only data source (named `v_listings_map` per the IMPLEMENTATION_PLAN — implementation may extend the bare view with a thin RPC wrapper for the filter shape required by FR-007a) that projects exactly the columns needed to render a marker pin and a preview popover for each eligible listing: the listing's identifier (so a marker tap can navigate to `/listings/:id`), the coordinates to render the marker at, the listing's title, primary price (with the price's stored currency code), property type, purpose, and main image reference. The source MUST NOT project any field beyond what the map and its preview popover render — publisher contact details, descriptions, full media galleries, amenities, addresses, and any other field are out of scope for the map dataset.
- **FR-001a**: The public read surface MUST return every approved+visible listing in the country in a single fetch — no viewport bounding-box parameter, no hard count cap, no zoom-threshold-based scoping. At v1 scale (hundreds to low thousands of listings) the marker clustering layer (FR-013) handles render performance; the API contract stays a single flat list. If the marketplace catalog grows past the point where a single fetch becomes too large, a future spec extends the read surface with bbox or pagination — Phase 15 does NOT pre-bake that complexity.
- **FR-002**: The public read surface MUST return a row for a listing if AND ONLY IF the listing's `status` is `approved` AND its `location_visibility` is one of `exact` or `approximate`. Listings whose visibility is `hidden` or `admin_only` MUST NOT appear in the response, regardless of approval status. Listings whose status is not `approved` MUST NOT appear in the response, regardless of visibility.
- **FR-003**: For each listing whose visibility is `approximate`, the public read surface MUST return jittered coordinates computed server-side as a deterministic function of the listing's identifier plus a server-side salt — the same approximate listing MUST return the SAME jittered coordinates on every fetch, for every user, in every session. The publisher's true stored coordinates MUST NEVER appear in the response for an `approximate` listing. The jittered coordinates MUST fall within the listing's area region so the rendered marker remains spatially honest about which neighborhood the listing belongs to. The deterministic-per-listing strategy (rather than random-per-fetch) is required so that an attacker capturing multiple fetches cannot average them to triangulate the true centroid, AND so that a user re-visiting the map sees the marker in the same spot they noticed earlier.
- **FR-003a**: For every listing whose visibility is `approximate`, the map MUST render a visual indicator distinguishing the marker from `exact` markers (e.g., a different pin shape/color, a halo, or a dashed accent — exact visual treatment is plan-time UX detail), AND the preview popover for the marker MUST include a localized textual indicator (e.g., "Approximate location") explaining that the displayed position is not the listing's exact coordinates. The indicator MUST appear in both Arabic and English layouts and MUST flow through the localization layer.
- **FR-004**: For each listing whose visibility is `exact`, the public read surface MUST return the listing's true stored coordinates unmodified.
- **FR-005**: The visibility-and-status filtering specified in FR-002 / FR-003 / FR-004 MUST be enforced at the data layer — no application-layer post-filter is permitted, and an automated check at PR review time MUST confirm that no client-side code applies a `location_visibility != 'hidden'` or `status = 'approved'` filter (the filtering is the responsibility of the public read surface).
- **FR-006**: The public read surface MUST be accessible to anonymous (not-signed-in) users without a login prompt — the map is a public discovery surface and does not require an account.

#### Map page composition

- **FR-007**: System MUST provide a full-screen map page reachable from THREE entry points per Q1=A, Q2=A, and Q8=B: (a) a prominent map tile/card on the home page positioned near the existing hero search bar / property-type chip row — NOT a bottom-navigation tab (no bottom-nav shell is added in Phase 15) and NOT an app-bar icon; the tile is visible on the home page without scrolling and is styled per the existing Phase 2 design tokens; (b) a "View on map" affordance added to the Phase 13 `ListingDetailsPage` shown only for listings whose visibility is `exact` or `approximate`; (c) a "Show on map" affordance added to the Phase 14 `SearchPage` results that carries the active filter set forward per FR-007a. The page MUST render an OpenStreetMap-tile basemap.
- **FR-007a**: When the map is entered from the Phase 14 search-results "Show on map" affordance, the public read surface MUST accept the same filter shape as the Phase 14 search RPC (purpose, property type, governorate, city, area, price range with currency, rooms with exact/at-least mode, bathrooms with exact/at-least mode, area size) AND return only listings matching the active filters. The keyword search input from Phase 14 also propagates as a filter. When at least one filter is active on entry, the map page MUST immediately surface a non-blocking alert dialog summarizing the active filters with two actions: a "Reset filters" action that clears all carried-over filters and reloads the map to show all approved listings, and a "Keep filters" (or dismiss) action that leaves the filtered view in place. The alert does NOT re-surface after the user dismisses it within a session.
- **FR-008**: The map page MUST render a visible attribution credit for OpenStreetMap at all times — the credit MUST NOT be obscured by markers, popovers, or other overlays.
- **FR-009**: The map page MUST render one marker pin per listing returned by the public read surface, positioned at the coordinates returned for that listing.
- **FR-010**: When the user taps a marker, the map MUST display a preview popover anchored to the tapped marker showing the listing's main image (with a localized placeholder if the image fails to load), title, primary price formatted via the user's display currency (consistent with Phase 9 conventions), and a property-type / purpose badge.
- **FR-011**: When the user taps the preview popover (or an explicit "View details" affordance on it), the app MUST navigate to the listing's details page (`/listings/:id`).
- **FR-012**: When the user taps elsewhere on the map (a different marker, the base tiles, the popover close affordance), the preview popover MUST dismiss; tapping a different marker MUST open the new marker's popover in a single tap.
- **FR-013**: The map page MUST cluster overlapping markers into a single cluster marker labelled with the count of listings inside it. Tapping a cluster MUST follow this conditional rule: (a) if the map is NOT at the maximum supported zoom level (zoom 18 — the OpenStreetMap raster tile limit, pinned in research.md R-93), the cluster tap MUST auto-zoom the map in (re-centering on the cluster's centroid) by enough levels to split the cluster into its constituent markers (or, for very dense clusters, to a child cluster the user can tap again); (b) if the map IS at zoom 18 (so further zoom-in cannot split the cluster — e.g., multiple listings at identical coordinates), the cluster tap MUST spiderfy the contained markers around the tap point so each individual marker is independently tappable. This single conditional rule replaces the earlier ambiguous "either-or" wording and is what the acceptance test verifies.
- **FR-014**: When the user navigates from the map into a listing details page and presses Back, the map MUST be restored at the prior zoom and pan position without re-loading or re-flickering the marker dataset.
- **FR-014a**: The marker dataset MUST be fetched on first map open and cached within the session for as long as the map page remains alive (including pan, zoom, marker tap, return-from-details). The dataset MUST NOT auto-refresh on a timer, and MUST NOT auto-refresh on app foreground-resume — matching the Phase 13 home-feed freshness model (Phase 13 Q6=A). The user MUST have an explicit way to refresh the dataset; the affordance is plan-time decided between (a) a pull-to-refresh gesture from the map page's edge (if it doesn't conflict with map-pan gestures) and (b) an explicit refresh button on the map chrome. Re-fetching MUST replace the cached dataset; markers re-render in their new positions and clusters re-form per the new data.
- **FR-015**: When the map is entered via deep-link (a future deep-link URL, or a return path with no in-app navigation stack), the back affordance MUST follow the project-wide `Navigator.canPop() ? pop : go(home)` convention established in Phase 13 Q4=D. No new back-navigation pattern is introduced.

#### Initial view and geolocation

- **FR-015a**: When the map is entered from the home shell (US1) or from any non-listing entry point with no active filters, it MUST open fitted to a Syria-wide bounding box that includes all 14 governorates per Q3=A. When entered from the Phase 13 `ListingDetailsPage` "View on map" affordance (US5), it MUST open centered on that listing's marker at a zoom level that also shows neighboring markers. When entered from a filtered Phase 14 search (US6), it MUST open fitted to a bounding box that includes all matching markers (or remain at Syria-wide overview if matching markers are spread across the whole country).
- **FR-015b**: The map page MUST surface a "center on my location" affordance per Q3=A. Tapping the affordance the first time MUST trigger the Android runtime geolocation permission prompt; on grant, the map MUST pan and zoom to the device's location at a neighborhood-level zoom (zoom 15 — pinned in research.md R-88 / contracts/phase15-map-page-composition.md). On subsequent taps after grant, the map MUST re-pan to the device's current location without re-prompting. On user denial (one-time or "don't ask again"), the map MUST surface a localized message explaining that location is unavailable AND remain functional for all marker-driven flows. The affordance is NOT removed on denial — re-tap behavior on denied permission is a plan-time UX decision (re-prompt vs OS-settings deep-link).
- **FR-015c**: The "center on my location" affordance MUST work for both anonymous and authenticated users — geolocation does not require sign-in. The device's location MUST NOT be persisted server-side or logged in audit trails by Phase 15; it is used only for the client-side pan/zoom and is discarded when the map page disposes.

#### Localization, theming, and accessibility

- **FR-017**: The map page MUST render correctly in both Arabic (RTL) and English (LTR) layouts. RTL rendering MUST mirror back arrows and any directional chrome on the map page; the map tile orientation itself is direction-agnostic (north is up in both layouts).
- **FR-018**: The map page MUST consume the existing design tokens (colors, typography, spacing, radii, elevation) for its chrome — no inline hex literals, no raw pixel constants, no untokenized typography. ### Key Entities

- **Map Marker**: A single point on the map representing one approved listing whose visibility permits public display. Each marker carries the listing identifier (for tap-to-navigate), the coordinates (true for `exact` listings, jittered for `approximate` listings), and the minimal preview payload (image reference, title, primary price + currency, property type, purpose).
- **Marker Cluster**: A composite marker rendered in place of multiple nearby map markers at low zoom levels, labelled with the count of listings inside it. Clusters split into individual markers as the user zooms in past a threshold, and re-cluster as the user zooms out.
- **Preview Popover**: A compact UI surface anchored to a tapped marker showing the listing's image, title, price, and type/purpose badge. The popover is the link between a marker tap and the full listing details page.
- **Public Map Dataset**: The complete set of marker rows returned by the public read surface for a given fetch. The dataset is gated by approval status (`approved` only) and by visibility (`exact` and `approximate` only) — `hidden`, `admin_only`, and non-approved listings are absent from the dataset at the wire level, not merely hidden in the UI.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An anonymous visitor reaching the map sees the OpenStreetMap basemap render within 3 seconds on the reference Infinix Note 8 over a standard Syrian 4G connection; marker pins appear within an additional 2 seconds.
- **SC-002**: For every approved listing whose `location_visibility` is `exact`, the marker on the map sits at the listing's stored coordinates; for every approved listing whose visibility is `approximate`, the marker sits at coordinates that differ from the publisher's stored coordinates and that fall within the listing's area region. Verified against a known fixture data set.
- **SC-003**: An automated wire-level inspection of the public map dataset shows zero rows for any listing whose `location_visibility` is `hidden` or `admin_only`, and zero rows for any listing whose `status` is not `approved`. The same inspection across multiple fetches NEVER returns the publisher's true coordinates for an `approximate` listing.
- **SC-004**: Tapping a marker opens a preview popover within 500 milliseconds; tapping the preview popover navigates to the corresponding `/listings/:id` page within an additional 1 second.
- **SC-005**: Pressing Back from the listing details page (when reached via the map) returns the user to the map at the same zoom and pan position as before the marker tap — no re-load of the marker dataset is required.
- **SC-006**: At a zoom level where 5 or more markers would visually overlap, the overlapping markers are replaced by a single cluster marker labelled with the count; zooming in past the clustering threshold splits the cluster into individual markers.
- **SC-007**: An attribution credit to OpenStreetMap is visible on the map page in every layout (light, dark, Arabic, English) and is never obscured by markers, clusters, or preview popovers.
- **SC-008**: The map page renders correctly in all four combinations of (light/dark theme) × (Arabic/English locale) on the Infinix Note 8 (480 dp width) and on a 412 dp emulator profile.
- **SC-009**: A repository-wide check of the project's dependency manifest returns zero matches for any Google Maps, Mapbox, Apple Maps, or other commercial-map dependency.
- **SC-010**: An admin flipping a listing's `location_visibility` from `exact` to `hidden` via direct database update causes the listing's marker to disappear from the map on the next user-initiated refresh, without any code change in the Phase 15 PR.
- **SC-011**: A signed-in user and an anonymous user reaching the map see identical marker datasets — auth state does not unlock additional listings or hide any listings on the public map.
- **SC-012**: Entering the map from the Phase 14 search-results "Show on map" affordance with at least one active filter produces a marker dataset restricted to listings matching every active filter; tapping "Reset filters" in the alert dialog re-loads the map to the full unfiltered approved set within 2 seconds.
- **SC-013**: The filter-active alert dialog appears within 500 milliseconds of map render when entered from a filtered search; it does NOT appear at all when entered from the search with zero active filters or from any non-search entry point.
- **SC-014**: First tap on "center on my location" triggers the Android runtime geolocation permission prompt; on grant, the map pans and zooms to the device's location within 3 seconds (assuming a successful location fix). Subsequent taps do not re-prompt and re-pan within 1 second.

## Assumptions

- The Phase 8 / Phase 10 location data (governorates, cities, areas with centroid coordinates) is already in place and is read by the public map read surface to compute the jittered coordinates for `approximate` listings. Phase 15 does not modify the location tables.
- The Phase 10 listing schema's `latitude`, `longitude`, and `location_visibility` columns are the authoritative source for marker positions and visibility tier. Phase 15 does not add new columns to the listings table.
- The Phase 12 approval workflow is the only writer of `status = 'approved'` rows; Phase 15's marker dataset is empty until Phase 12 has merged and at least one approval has succeeded. The same admin tools used in Phase 12 are used to test visibility-tier changes in Phase 15.
- The Phase 13 `/listings/:id` route is the unmodified destination for any "view full listing" tap from the map (preview popover, cluster-expansion list). Phase 15 does not modify the Phase 13 details page beyond the optional addition of a "View on map" affordance per the Clarifications section.
- The default region/zoom on first map open is a Syria-wide overview that includes all 14 governorates per Q3=A. The map ALSO ships a "center on my location" affordance that requests Android runtime geolocation permission on first tap and pans/zooms to the device's location on grant per Q3=A. The geolocation usage is scoped to client-side pan/zoom only — the device location is NOT persisted server-side, NOT included in any audit log, and NOT used to filter the marker dataset (the dataset is the same for every user regardless of their device location). The user can use the map without ever tapping the geolocation affordance; denying the permission does not degrade the rest of the map's functionality.
- The geolocation plugin choice is plan-time decided. The chosen plugin MUST work on Syrian Android devices distributed via direct-APK (the primary distribution channel per the constitution); a plugin that depends exclusively on Google Play Services would fail on devices where Play Services is missing or stale. A pure Android-API-backed plugin is preferred; a hybrid Play-Services-with-fallback plugin is acceptable.
- The default tile source is the OpenStreetMap public tile servers. Tile usage volume is assumed to remain within the OSM Foundation's tile usage policy for v1's scale. If usage grows large enough to warrant moving off the OSM public tile servers, a future spec ships a self-hosted or paid tile mirror (still OSM-licensed, so still no commercial-map provider).
- The jitter algorithm for `approximate` listings is **deterministic per listing** (per Q4=A) — a function of the listing identifier plus a server-side salt — so the same approximate listing returns the same jittered coordinates on every fetch and for every user. This protects against multi-fetch averaging attacks AND keeps the marker stable across user re-visits. The salt is plan-time decided (database-stored constant vs Vault-stored secret); rotating the salt re-jitters every approximate listing's marker, which is acceptable since the marker was always approximate. Approximate markers are visually differentiated on the map AND in the preview popover per FR-003a so viewers can tell at a glance that the displayed position is not the listing's exact coordinates.
- Map tile caching uses the tile layer's default in-memory cache only. Aggressive disk caching for offline use is not a v1 requirement and is deferred to a future spec.
- Driving directions and any integration with the device's native maps application (Google Maps, Waze, OsmAnd) is OUT of scope. The map is read-only for spatial discovery; it does not act as a navigation surface.
- The map page is anonymous-accessible (no login required), consistent with the Phase 13 home feed and the Phase 14 search surface.
