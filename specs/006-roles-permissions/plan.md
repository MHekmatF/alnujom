# Implementation Plan: Roles & Permissions

**Branch**: `006-roles-permissions` | **Date**: 2026-05-15 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `specs/006-roles-permissions/spec.md`

## Summary

Replace the interim `profiles.is_admin` BOOLEAN flag (Phase 5 stopgap) with a real data-driven role / permission system: four new tables (`roles`, `permissions`, `role_permissions`, `user_roles`), the seeded §9.1 permission catalog + default role-permission mappings, one new helper SQL function `current_user_has_permission(perm_key)`, the body-swap of Phase 5's `current_user_is_admin()` (now resolving to "user holds `admin` or `super_admin` role" — no policy file edited), a backfill migration that converts every prior `is_admin=true` user to an `admin` role assignment and seeds the implicit `user` role for every existing profile, an auto-`user`-role trigger on every new profile insert, the system-role-immutability trigger, one new cross-user `profiles` read policy gated on `users.view`, audit-trigger attachment to `user_roles` only (the other three new tables get audit triggers in Phase 7 alongside their mutation UI), and a small Flutter surface: `lib/core/security/permission_checker.dart` (a session-scoped singleton with the three Phase-5-R-21-style observation points), `lib/core/security/permission_keys.dart` (the Dart mirror of the 24 §9.1 keys), `lib/features/admin/` skeleton (admin home tile-list, with the Phase 5 admin queue rehosted under the new home), and an extension of `lib/features/profile/` to render a read-only "Roles" section on the profile page. Apply every migration to the **remote** Supabase project via Supabase MCP `apply_migration` (inherited from Phase 4 R-01 — there is no local Supabase setup). Verification is manual SQL inspection via Supabase MCP `execute_sql` + Supabase MCP `get_advisors` after each migration + end-to-end manual UI verification on the reference Infinix Note 8 device, all walked by `quickstart.md`.

**Technical approach**: Three Session 2026-05-15 clarifications closed the design space — (Q1) first super_admin is bootstrapped post-Phase-6 via privileged SQL, mirroring Phase 5 R-19; (Q2) the PermissionChecker cache refreshes via three observation points exactly (no periodic timer, no Realtime — Phase 22 spec is tagged to revisit Realtime); (Q3) the Phase 5 PII cross-user read predicate keeps `current_user_is_admin()` (admins decrypt others' PII; moderators do not), with the gate being future-mutable by Phase 7's super-admin UI editing role-permission mappings. The four migrations + the seed + the one helper + the body swap + the backfill + the auto-`user`-role trigger + the system-role-immutability trigger + the audit-trigger attachment + the new cross-user `profiles` read policy + the policy files for the four new tables collapse into **eight new migration files** plus **five new policy files** plus **four new doc files** plus three updated doc files — every SQL artifact is a checked-in `.sql` under `supabase/migrations/` or `supabase/policies/` per Constitution II. The Phase 4 R-05 central-helper invariant (preserved by Phase 5) holds again: no Phase 4 or Phase 5 policy file is edited — only `current_user_is_admin()`'s body is swapped (one `CREATE OR REPLACE FUNCTION` call). The Flutter side adds two `lib/core/security/` files, extends the existing `lib/features/admin/` skeleton Phase 5 introduced (rehosting the Phase 5 account-approval-queue page under a new `AdminHomePage` tile listing), extends `lib/features/profile/presentation/pages/profile_page.dart` to render the new Roles section, and wires the `PermissionChecker` lifecycle into the existing `AuthBloc` from Phase 5 (the same `WidgetsBindingObserver.didChangeAppLifecycleState(resumed)` that already refreshes `account_status` per Phase 5 R-21 — extended to also call `PermissionChecker.refresh()`). No new packages in `pubspec.yaml`. **No new automated tests** per the durable session feedback rule (`feedback_no_new_tests.md` carried forward from Phase 3–5); verification is manual SQL via Supabase MCP `execute_sql` + Supabase MCP `get_advisors` + manual device walk on the reference Infinix Note 8 against the remote Supabase project.

## Technical Context

**Language/Version**: Dart 3.x on Flutter (latest stable channel) for the app additions; PostgreSQL (Supabase remote, Postgres 15+) for the SQL migrations. **No Edge Function in Phase 6** — there's no FR that requires server-side coordination beyond what SQL helpers can provide (unlike Phase 5's `request_password_reset` which needed Edge for account-enumeration resistance). Same Flutter + Dart base as Phases 1–5.

**Primary Dependencies**: `supabase_flutter` (already in `pubspec.yaml`), `flutter_bloc` (already in), `equatable` (already in), `get_it` (already in — used for DI registration of `PermissionChecker`), `go_router` (already in — the new admin route guard reads from `PermissionChecker.any(<admin-category-keys>)`). **No new runtime or dev packages.** **Tooling**: Supabase MCP server (`apply_migration`, `execute_sql`, `list_tables`, `list_migrations`, `get_advisors`) is the canonical migration-apply / inspection mechanism — same as Phases 4 and 5.

**Storage**: Remote Supabase Postgres project. Phase 6 adds:
- **Four new tables**: `roles`, `permissions`, `role_permissions`, `user_roles` (per FR-001/003/005/007 — full schemas in `data-model.md`).
- **One new SQL helper function**: `current_user_has_permission(perm_key TEXT) RETURNS BOOLEAN` (FR-008 — joins `user_roles → role_permissions → permissions` for `auth.uid()`; `SECURITY DEFINER STABLE SET search_path=public,auth`; returns `FALSE` for callers without `auth.uid()` via `COALESCE`).
- **One body-swapped SQL helper**: `current_user_is_admin()` rebodied from Phase 5's `SELECT is_admin FROM profiles WHERE user_id = auth.uid()` to a role-membership check `EXISTS (SELECT 1 FROM user_roles ur JOIN roles r ON r.id = ur.role_id WHERE ur.user_id = auth.uid() AND r.key IN ('admin', 'super_admin'))` (FR-012). The function name, signature, and qualifiers are unchanged; the body swap uses `CREATE OR REPLACE FUNCTION`.
- **Four new triggers**: (a) audit trigger `trg_user_roles_audit_granted` on `user_roles` AFTER INSERT calling `log_audit('user_role.granted', '*', 'user_id')` (FR-010); (b) audit trigger `trg_user_roles_audit_revoked` on `user_roles` AFTER DELETE calling `log_audit('user_role.revoked', '*', 'user_id')` (FR-010 — Phase 4's `log_audit()` takes the action string verbatim from `TG_ARGV[0]`, so Phase 6 attaches one trigger per legal mutation event per Phase 5 convention; no UPDATE trigger in v1); (c) `profiles AFTER INSERT` trigger auto-creating the default `user`-role assignment (FR-013); (d) `roles BEFORE UPDATE OR DELETE` trigger enforcing system-role immutability (FR-020).
- **One updated trigger function**: `enforce_profile_status_admin_only()` is rewritten in the same backfill migration as the `is_admin` column drop, so the trigger no longer references the dropped column (FR-011 step 5). The remaining responsibility (blocking non-privileged client mutations of `account_status` and `publisher_status`) is preserved.
- **One column drop**: `profiles.is_admin` is dropped after the backfill (FR-011 step 4). The Phase 5 schema is left with `profiles` minus this column.
- **One new policy on an existing table**: `profiles` gains a stacked cross-user read policy gated on `current_user_has_permission('users.view')` — added in a NEW policy file `supabase/policies/profiles_phase6_users_view.sql` (the Phase 4 `profiles_policies.sql` is NOT edited; R-05 central-helper invariant + the broader "no Phase 4/5 policy file edits" invariant is preserved).
- **Four new policy files** under `supabase/policies/`: `roles_policies.sql`, `permissions_policies.sql`, `role_permissions_policies.sql`, `user_roles_policies.sql` — each authoring the RLS posture per FR-009.
- **Seed content** for `roles` (7 system roles with bilingual `display_name` JSONB), `permissions` (24 keys from §9.1), `role_permissions` (the §9.1 default mappings — moderator 5 rows, admin 17 rows, super_admin all 24 rows; user/owner/agent/agency_admin 0 rows each in v1 — agency_admin's permissions land in Phase 19) — all `INSERT ... ON CONFLICT DO NOTHING` for idempotency. The seed lives inside the create-table migrations (one seed block per table, immediately after the `CREATE TABLE` + RLS enable) — research R-04 picks "inline in the migration" over "separate `supabase/seed/` files" for atomicity and re-apply safety.

**Testing**: **Manual SQL inspection against the remote Supabase project via Supabase MCP `execute_sql` + Supabase MCP `get_advisors` after each migration + manual UI verification on the reference Infinix Note 8 device.** Per the durable session feedback (`feedback_no_new_tests.md`) and the spec's assumptions, this phase introduces NO new automated tests of any kind. Build-time validation is preserved: Supabase's static SQL parser at `apply_migration` time catches syntax errors; Flutter's analyzer + the existing Phase 3 localization lint guard validate the new Dart files. Existing Phase 1/2/3/4/5 tests remain in source unchanged.

**Target Platform**: Android 7.0+ (API 24+) for the Flutter side (Constitution XI); Supabase remote Postgres for the backend side. iOS, Web, desktop NOT a target.

**Project Type**: Mobile app + backend. Phase 6 extends the Phase 5 features (`auth`, `profile`, `admin`) and adds two new files under `lib/core/security/`; it does NOT introduce any new feature-folder top-level (the `admin/` feature folder already exists from Phase 5's `admin/account_approvals/`; Phase 6 adds `admin/presentation/pages/admin_home_page.dart` as the new tile-listing entry and rehosts the Phase 5 queue route under it).

**Performance Goals**:
- Cold app launch + initial `PermissionChecker.load()` round-trip on the reference Infinix Note 8: under 4 seconds end-to-end (within the Constitution baseline of 3s plus an extra ~500-1000ms for the one extra Supabase round-trip — acceptable at MVP scale).
- `PermissionChecker.has(...)` is a synchronous in-memory `Set<String>` lookup — O(1), no measurable latency.
- `PermissionChecker.refresh()` on `didChangeAppLifecycleState(resumed)`: under 2 seconds against the remote project on a typical mobile connection.
- `current_user_has_permission(perm_key)` SQL call latency at MVP scale (tens of users, ~24 permissions, ~7 roles, single-digit `user_roles` rows per user): under 50ms end-to-end including round-trip — the join is over very small tables and `SECURITY DEFINER STABLE` lets Postgres cache the result within a transaction.
- Migration apply (eight migrations) against the remote project: under 30 seconds total.
- Admin home page initial render: under 2 seconds on the reference device (one read of `user_roles → role_permissions → permissions` for the signed-in user, already in the PermissionChecker cache by then).

**Structure Decision**: Phase 6's footprint is mostly backend (8 new migrations, 5 new policy files, 4 new doc files + 3 updated doc files) and a small but architecturally-significant Flutter addition (`lib/core/security/` — the first time the project introduces a `core/security/` subtree, alongside `core/network/` / `core/config/` / `core/di/` / `core/routing/`). The Flutter feature-folder layer extends the Phase 5 `lib/features/admin/` skeleton in place — Phase 6 adds an `AdminHomePage` as the tile-listing parent and the Phase 5 account-approvals page is rehosted as a child route. The existing Phase 5 `Profile` entity's `isAdmin` field is REMOVED as part of the column drop (Phase 6 deletes the field; no Phase 6 call site references it after the home-page admin tile is rewired to consume `PermissionChecker.any(...)`). No Phase 4 or Phase 5 policy file is edited — the central-helper invariant from Phase 4 R-05 / Phase 5 R-12 is preserved a second time. The eight migrations apply to the **remote** Supabase project via Supabase MCP `apply_migration` (Phase 4 R-01 carried forward). No Edge Function in Phase 6 (unlike Phase 5's `request_password_reset` which needed Edge for account-enumeration resistance — Phase 6 has no comparable requirement). Constitution IX is enforced by the directory layout: `lib/core/security/permission_checker.dart`, `permission_keys.dart`, and `permission_catalog_repository.dart` import nothing from `package:supabase_flutter`; only `permission_catalog_repository_impl.dart` does, and it is the single new file under `lib/core/security/` that touches Supabase.
