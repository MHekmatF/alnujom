# Contract: Flutter `PermissionChecker` Singleton

**Owner**: Phase 6 (`lib/core/security/permission_checker.dart`, registered via `get_it` in `lib/core/di/injection_container.dart`).
**Consumers**: every widget / BLoC / page in `lib/features/` from Phase 6 onward that needs to gate UI on a specific permission. Phase 6's only consumers: `lib/features/home/presentation/pages/home_page.dart` (the main-navigation admin tile visibility), `lib/features/admin/presentation/pages/admin_home_page.dart` (the per-tile visibility check), `lib/core/routing/auth_redirect.dart` (the `/admin` route guard). Phase 7+ adds many more.
**Stability**: API surface (`load`, `refresh`, `has`, `any`, `all`, `clear`) is stable for v1. Internal cache shape (`Set<String>`) may change without breaking callers.

---

## Purpose

A session-scoped synchronous cache of the signed-in user's effective permission key set. Lets widgets call `.has('users.approve')` synchronously from `build()` methods without async fetches on every rebuild. Decouples UI gating from database round-trips.

**NOT a security boundary.** Constitution III enforces security at the RLS layer. The `PermissionChecker` exists only to drive UX (hide buttons the user can't use anyway). A user who defeats the UI hiding hits the same RLS that would have rejected them.

## API

```dart
class PermissionChecker {
  PermissionChecker(this._repo);

  /// Fetches the signed-in user's effective permission set and populates the cache.
  /// Idempotent — calling twice in succession is safe.
  /// Throws nothing; on fetch failure, logs via the Phase 1 logger and keeps the cache empty.
  Future<void> load();

  /// Re-fetches and atomically replaces the cache. On fetch failure, retains the previous cache.
  /// Idempotent.
  Future<void> refresh();

  /// Synchronous lookup. Returns true iff [permKey] is in the cached set.
  bool has(String permKey);

  /// Synchronous lookup. Returns true iff ANY of [permKeys] is in the cached set.
  bool any(Iterable<String> permKeys);

  /// Synchronous lookup. Returns true iff EVERY of [permKeys] is in the cached set.
  bool all(Iterable<String> permKeys);

  /// Drops the cache. Called on sign-out.
  void clear();
}
```

## Lifecycle (FR-015) — wires into Phase 5's existing `AuthBloc`

The three observation points (per R-17 — Option A — locked Session 2026-05-15 Q2). All three live inside `lib/features/auth/presentation/bloc/auth_bloc.dart` — Phase 5's bloc IS the `WidgetsBindingObserver` (mixin: `class AuthBloc extends Bloc<…> with WidgetsBindingObserver`). There is no separate observer file.

1. **Auth-state listener** (existing Phase 5 path): the `_sessionSub` subscription on `_authRepository.sessionStream` fires `SessionRefreshed(session)` events. Phase 5's `_onSessionRefreshed` handler computes the new `AuthState`. Phase 6 extends this handler to:
   - When the new state would be `Authenticated` / `PendingApproval` / `Rejected` / `Suspended` (signed-in session): `await _permissionChecker.load()` BEFORE emitting (so the first UI render after sign-in sees a populated cache).
   - When transitioning to `Unauthenticated` (signed-out): `_permissionChecker.clear()`.

2. **Lifecycle resume** (existing Phase 5 path): Phase 5's `didChangeAppLifecycleState(AppLifecycleState.resumed)` (already overridden on the bloc) dispatches `AppResumedRefresh`. The handler `_onAppResumedRefresh` (already exists on the bloc) is extended in Phase 6 to also `await _permissionChecker.refresh()` alongside its existing `ProfileRefreshed` dispatch.

3. **Token refresh / session re-emit**: when `SessionRefreshed` fires for an already-authenticated session (a token refresh from `sessionStream`), the `_onSessionRefreshed` handler at point 1 also calls `_permissionChecker.refresh()` (not `load()`, since the cache may already be populated).

**Constructor change**: Phase 6 adds `PermissionChecker` as a third positional constructor argument: `AuthBloc(this._authRepository, this._profileRepository, this._permissionChecker)`. The `injection.config.dart` is auto-regenerated by `build_runner` so the registration picks up the new dependency automatically (run `flutter pub run build_runner build --delete-conflicting-outputs` after the source edit).

NO periodic timer. NO Supabase Realtime subscription on `user_roles`. Phase 22 is tagged to revisit (project memory `project_phase22_perm_cache_revisit.md`).

## Failure handling

- **Initial `load()` failure** (network error, transient Supabase error): the cache stays empty; the user is treated as having no admin permissions (the admin tile is hidden). The next observation point retries. SC-010 verifies the eventual-consistency property.
- **Subsequent `refresh()` failure**: the cache retains its previous value (do NOT clear). Clearing would falsely hide every admin tile from a signed-in admin during a transient blip.

## Constitution alignment

- **Constitution IV (Clean Architecture)**: the singleton consumes an abstract `PermissionCatalogRepository` (`lib/core/security/permission_catalog_repository.dart`). Only the impl (`permission_catalog_repository_impl.dart`) imports `package:supabase_flutter`. The `PermissionChecker` itself is Supabase-free.
- **Constitution IX (Future Backend Portability)**: same — the abstract repository is the only Supabase boundary.
- **Constitution VII (Dynamic Roles & Permissions)**: every UI gate in Phase 6 calls `permission_checker.has(<key>)` rather than reading `profile.role == 'admin'`. The hardcoded-role-check forbidden pattern (FR-019) is enforced by PR review.

## Verification

Manual UI walk on the reference Infinix Note 8 device, per `quickstart.md`:

1. Sign in as a regular user → confirm admin tile hidden.
2. Sign in as an admin → confirm admin tile visible.
3. While signed in as a regular user, background the app; from a desktop, INSERT an `admin`-role row for that user via Supabase MCP `execute_sql`; foreground the app → confirm admin tile appears within a few seconds (the lifecycle-resume refresh path).
4. Sign out → confirm admin tile remains hidden on the post-signout login screen (cache cleared).
