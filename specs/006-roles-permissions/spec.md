## Clarifications

### Session 2026-05-15

- Q: Does the Phase 6 backfill assign the `super_admin` role to a specific bootstrap user, or stay unassigned until a post-Phase-6 privileged SQL action creates the first one? → A: Backfill assigns nothing for super_admin; the first super_admin is created post-Phase-6 via `Supabase MCP execute_sql` running as `postgres`, mirroring the Phase 5 R-19 admin bootstrap pattern. Phase 7's super-admin UI requires this one-time privileged SQL action as an entry condition before it can function — that prerequisite is documented as a Phase 7 deploy step, not a Phase 6 gap. No user_id is hand-picked or hardcoded into any Phase 6 migration.
- Q: Is the proposed three-point set for PermissionChecker cache refresh (auth-state listener events, app foreground resume, the AuthBloc mid-session refresh path) complete for Phase 6, or should it be extended with a periodic timer / Realtime subscription? → A: Exactly the three points as proposed, mirroring Phase 5's R-21 lifecycle-resume pattern. The actual wiring (per the Phase 6 plan/research/contracts/tasks): the auth-state listener via `_onSessionRefreshed`; the foreground-resume path via the `_onAppResumedRefresh` event handler on `AuthBloc` (the bloc itself is the `WidgetsBindingObserver`, mixin-style); the third point folds into the second since the `_onAppResumedRefresh` handler is the canonical refresh path. No periodic timer and no Realtime subscription on `user_roles` in Phase 6 — Realtime stays deferred to Phase 22 per the implementation plan. **Phase 22 revisit note**: when Phase 22 ships push + Realtime, the spec for that phase MUST re-evaluate this decision and consider upgrading the PermissionChecker cache to also subscribe to `user_roles` changes via Realtime (the "Option C" alternative considered and rejected at Phase 6 time, or whatever pattern is best at Phase 22 time). The Phase 22 spec should treat this as a known follow-up, not as new work.
- Q: After Phase 6, which sessions can decrypt another user's Vault-stored PII (`legal_name`, `national_id`, `private_contact_methods`) via the Phase 5 `app_vault_secret_for_user(user_id, field_name)` helper? → A: Phase 6 keeps the existing `current_user_is_admin()` gate — only `admin` and `super_admin` decrypt other users' PII. Moderators gain `users.view` (cross-user `profiles` row read) but do NOT inherit cross-user PII decrypt access. No new permission key (`users.view_pii`) is carved out in Phase 6, and no cross-user PII write path is introduced (admins/super_admins decrypt but do not edit another user's PII). **Forward-extensibility**: the gate is future-mutable through Phase 7's super-admin UI — super_admin can reshape who has PII access by editing role-permission mappings (e.g., grant a future `users.view_pii` key to a custom role) or by changing role assignments via `user_roles`. Phase 6 ships the tightest sensible privacy boundary; later phases can broaden it through configuration without further code changes if a future spec carves out the permission key.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Seeded role and permission catalog goes live (Priority: P1)

When Phase 6 ships, the remote Supabase project carries a complete role/permission catalog: the seven system roles named in the implementation plan (`user`, `owner`, `agent`, `agency_admin`, `moderator`, `admin`, `super_admin`), every permission key from §9.1 (`users.view`, `users.approve`, `users.reject`, `users.suspend`, `listings.view_all`, `listings.approve`, `listings.reject`, `listings.edit_any`, `listings.delete_any`, `roles.view`, `roles.create`, `roles.update`, `roles.delete`, `permissions.manage`, `locations.manage`, `currencies.manage`, `ads.manage`, `reports.manage`, `agencies.view`, `agencies.approve`, `agencies.suspend`, `settings.manage`, `audit_logs.view`, `inquiries.view_all`), and the seeded default role-permission mappings from the same section. The catalog is the foundation every later phase reads — Phase 8 locations admin uses `locations.manage`, Phase 9 exchange-rate admin uses `currencies.manage`, Phase 12 listing approval uses `listings.approve`, Phase 16 cross-publisher inquiry view uses `inquiries.view_all`, Phase 18 reports moderation uses `reports.manage`, Phase 19 agency approval uses `agencies.approve`, Phase 21 ads admin uses `ads.manage`, Phase 23 settings admin uses `settings.manage`. Until this catalog exists, none of those phases can author their RLS policies.

**Why this priority**: This is the data foundation. Constitution VII (Dynamic Roles & Permissions) is the binding principle: the platform must be data-driven, not hardcoded-role-driven. Without the seeded catalog, every later admin-gated feature would have to invent its own predicate. Constitution III (Security-First Supabase) is enforced by RLS policies that join `user_roles → role_permissions → permissions` — those joins require the rows to exist. Constitution IX (Future Backend Portability) requires the permission keys to be string identifiers, not Supabase-specific objects, so the frontend can consume them through a domain-layer interface. This story is the MVP slice — it ships the four tables + the seed + the helper function and nothing else, but on its own it lets every later spec start authoring permission-keyed policies.

### User Story 2 - Interim `profiles.is_admin` is replaced cleanly (Priority: P1)

Every user who held `profiles.is_admin = true` at the moment Phase 6's backfill migration runs is converted into a row in `user_roles` referencing the seeded `admin` role. After the backfill runs, the `profiles.is_admin` column is dropped from the table in the same migration. The Phase 5 `current_user_is_admin()` helper function's body is swapped — without touching any Phase 4 or Phase 5 policy file — so it now resolves to "user has the `admin` or `super_admin` role" via the new `user_roles` table. Every Phase 5 policy that gated reads/writes on `current_user_is_admin()` (the account-approval-requests admin queue, the cross-user PII decrypt helper, the column-level write protection for `account_status` / `publisher_status`) continues to admit exactly the same users it admitted before Phase 6 ran. Phase 5's admin queue UI continues to work without code changes; an existing admin can still approve a pending registration; the four migrations and the one body-swap together produce zero observable behavior change for a user who was already an admin.

**Why this priority**: This is the highest-risk single migration of the phase. Dropping a column that is referenced (transitively) by every Phase 5 RLS policy means the change must land atomically with the helper-body swap or the project breaks. Constitution III is on the line — a misordered migration could leave the database in a state where no user has admin access, which immediately locks out every admin tool that Phase 5 shipped. The central-helper invariant from Phase 4 (the predicate body changes; no policy file is edited) is what makes this safe; Phase 6 must preserve it for Phase 5's policies. P1 because if this story fails the project's admin tooling is offline; everything else in Phase 6 is meaningless until this is right.

**Independent Test**: Before applying the Phase 6 migrations to the remote project, run `SELECT user_id FROM profiles WHERE is_admin = true ORDER BY user_id` and save the list (call it `L_pre`). Apply the Phase 6 migrations in order via Supabase MCP `apply_migration`. After apply, run `SELECT ur.user_id FROM user_roles ur JOIN roles r ON r.id = ur.role_id WHERE r.key = 'admin' ORDER BY ur.user_id` and confirm the result is a superset of `L_pre` (every prior admin still has the `admin` role). Run `SELECT column_name FROM information_schema.columns WHERE table_schema='public' AND table_name='profiles' AND column_name='is_admin'` — confirm zero rows (the column is gone). Run `SELECT current_user_is_admin()` from a privileged session and from a JWT-claims-simulated session for one of the users in `L_pre` — confirm the function does not error (the body no longer references the dropped column) and returns `true` for the simulated admin session. Sign in on the device as one of the users in `L_pre`, open the Phase 5 admin queue, approve a pending registration — confirm the action succeeds and the corresponding `audit_logs` row is emitted (the Phase 5 admin path still works).

**Acceptance Scenarios**:

1. **Given** the remote project has N users with `profiles.is_admin=true` before the Phase 6 migrations run, **When** the backfill migration completes, **Then** `SELECT count(DISTINCT ur.user_id) FROM user_roles ur JOIN roles r ON r.id = ur.role_id WHERE r.key = 'admin'` returns at least N, and every prior `user_id` from the pre-migration set is present in the new query's result.

### User Story 3 - User opens their profile and sees their assigned role(s) (Priority: P2)

After approval, an approved user opens their profile page. In addition to the Phase 5 fields (full name, username, phone, optional email, avatar, account/publisher status badges), the page now renders a read-only list of the role display names assigned to that user. A regular user sees a single entry showing the localized display name for the `user` role (e.g., "مستخدم" in Arabic, "User" in English). An admin sees two entries: the `user` role and the `admin` role. A super_admin sees the `user`, `admin`, and `super_admin` roles. The list cannot be edited from the user-facing profile page — role assignment is a privileged action that lands in Phase 7's super-admin UI. The display names come from the `roles.display_name` JSONB column whose keys are the supported locales (`ar`, `en`) per Phase 3's localization convention; missing translations fall back to the role's `key`.

**Why this priority**: P2 because the user-facing surface area for roles is small in v1 — most users will see only "User" on this list and the rest is opaque to them. But the surface establishes the first piece of user-visible role data in the app and exercises the cross-table join (`user_roles → roles`) that Phase 7's super-admin UI will lean on heavily. It is also the first place the new `roles` and `user_roles` tables are read from a Flutter feature folder, so the data-layer + repository shape is established here for Phase 7 to follow. Constitution V (Arabic-First Localization) is exercised: the role display names render in the active locale; falling back to the role `key` if the translation is missing is the documented fallback per Phase 3's runtime.

### User Story 4 - Admin-tile navigation visibility is permission-gated (Priority: P2)

The main navigation in the app surfaces an "Admin" tile (or section). Phase 5 currently shows or hides this tile based on the interim `profiles.is_admin` flag. Phase 6 replaces the visibility check with a permission-key check via the new `PermissionChecker`: the tile is visible iff the signed-in user holds **any** of the admin-category permissions (`users.approve`, `users.reject`, `users.suspend`, `users.view`, `listings.view_all`, `listings.approve`, `listings.reject`, `listings.edit_any`, `listings.delete_any`, `roles.view`, `permissions.manage`, `locations.manage`, `currencies.manage`, `ads.manage`, `reports.manage`, `agencies.view`, `agencies.approve`, `agencies.suspend`, `settings.manage`, `audit_logs.view`, `inquiries.view_all`). A regular user (only the `user` role) sees no admin tile. A moderator (with `users.view`, `listings.view_all`, `listings.approve`, `listings.reject`, `reports.manage`) sees the tile. An admin sees the tile. A super_admin sees the tile. The `PermissionChecker` is consulted as a UX layer only — the security boundary is the RLS policy on each admin-gated table, not the Flutter widget tree.

**Why this priority**: P2 because the navigation visibility change is a pure UX improvement — the same security is enforced by RLS regardless of whether the tile is visible. But this story is the only Phase 6 surface that exercises the Flutter `PermissionChecker` end-to-end: it caches the user's effective permission set on session start, it consults `has(...)` from widget code, and it refreshes the cache on the lifecycle events the spec defines. Establishing the pattern here is what makes Phase 7's super-admin UI, Phase 8 locations admin, Phase 9 exchange-rate admin, etc., trivial to author — they just call `PermissionChecker.has('locations.manage')` or whatever the relevant key is. Constitution VII (no hardcoded role checks) is enforced through this surface: the admin tile asks for the permission set, not for `user.role == 'admin'`.

**Independent Test**: Sign in as a regular user on the device. Confirm there is no "Admin" tile in the main navigation. Sign out. Sign in as the admin user from US2. Manually assign the `moderator` role to a test user via Supabase MCP `execute_sql` (replacing their `user`-only assignments — strictly an additive `INSERT INTO user_roles` with no DELETE in Phase 6). Sign in as that user. Confirm the "Admin" tile is visible (because moderator holds `users.view`, etc.) and tapping it lands on the admin home page. Confirm the admin home page shows the Phase 5 admin queue tile as inaccessible or hidden (the queue itself requires `users.approve`, which moderators do not have — moderator-visible admin tiles will appear in later phases as Phase 12 listings approval, Phase 18 reports moderation, etc., ship). Confirm that signing back in as the regular user removes the "Admin" tile from the navigation.

**Acceptance Scenarios**:

1. **Given** an authenticated session for a user with only the `user` role, **When** the main navigation renders, **Then** the "Admin" tile is not present in the tree (the widget is hidden, not just dimmed).
2. **Given** an authenticated session for a user with the `admin` role, **When** the main navigation renders, **Then** the "Admin" tile is present and tapping it lands on the admin home page.
3. **Given** an authenticated session for a user with the `moderator` role, **When** the main navigation renders, **Then** the "Admin" tile is present (because moderator holds at least one admin-category permission).
4. **Given** the admin home page renders for a moderator, **When** the page looks up the Phase 5 admin queue tile, **Then** the tile is hidden (the queue requires `users.approve`, which moderator does not have).
5. **Given** the admin home page renders for an admin, **When** the page looks up the Phase 5 admin queue tile, **Then** the tile is present and tapping it opens the Phase 5 queue (which still works exactly as Phase 5 shipped it).

### User Story 5 - Permission cache stays current as the session lives (Priority: P3)

When a user signs in, the Flutter app loads the user's effective permission set (the union of permission keys reachable via `user_roles → role_permissions → permissions`) and caches it in a `PermissionChecker` singleton. While the session is alive, the cache stays current through three observation points, mirroring the mid-session detection pattern Phase 5's R-21 established for `account_status`: (a) the auth-state listener stream fires on sign-in / sign-out / token-refresh, the cache reloads on each event; (b) `WidgetsBindingObserver.didChangeAppLifecycleState(resumed)` triggers a `PermissionChecker.refresh()` call so a user whose role changed while the app was backgrounded sees the new permissions on resume; (c) the AuthBloc's `refreshSession` flow (the same flow Phase 5 uses to refresh `account_status`) also refreshes the permission cache so the two observations happen atomically. A role change is not pushed in real-time — Phase 22 ships Realtime — but in practice every realistic role change happens while the affected user is signed out (Phase 7's super-admin UI in particular has no user-facing in-session mutation surface), so the foreground-resume detection is enough.

**Why this priority**: P3 because in v1 role changes are rare (the super-admin UI from Phase 7 is the only role-assignment surface, and it's used by humans, not by automated workflows) and the user almost always experiences the role change at sign-in time. But the cache-refresh wiring is what makes the permission model correct in edge cases — a moderator who is promoted to admin mid-session must see the new admin tiles on the next foreground resume, not have to sign out and back in. Phase 5's R-21 set the precedent that lifecycle-resume is the right observation point for session-level state changes; Phase 6 extends the same observer to also refresh the permission cache. The work is small (one new line in the existing lifecycle observer + one new method on `PermissionChecker`) but it is the difference between a permission system that drifts silently and one that converges within seconds.

**Independent Test**: Sign in as a regular user on the device. Confirm `PermissionChecker.has('users.approve')` returns `false` (no admin tile visible). Background the app (press the home button — do NOT force-quit; force-quit clears the session). On a desktop, run `INSERT INTO user_roles (user_id, role_id) VALUES (<this-user-id>, <admin-role-id>)` via Supabase MCP `execute_sql` running as `postgres`. Foreground the app on the device. Confirm — within one to two seconds — the admin tile appears in the navigation (the lifecycle-resume observer refreshes the permission cache; the navigation rebuilds against the new cache). Optionally: tap the admin tile, confirm the admin home loads, tap the admin queue tile, confirm the queue is now reachable (the user's session inherits the new role's permissions; the RLS policy that gates the queue accepts the new role's membership).

**Acceptance Scenarios**:

1. **Given** a signed-in session, **When** the auth-state listener emits a token-refresh or sign-out event, **Then** the `PermissionChecker` cache is invalidated and re-fetched (on sign-out the cache is cleared to empty).
2. **Given** a signed-in session backgrounded for some time, **When** the app comes back to the foreground (`didChangeAppLifecycleState(resumed)`), **Then** the `PermissionChecker` calls `refresh()` and the UI rebuilds against the (possibly changed) permission set.
3. **Given** a signed-in user whose role was changed via an out-of-band SQL action while the app was backgrounded, **When** they foreground the app, **Then** the navigation rebuilds within a small number of seconds to show or hide the appropriate admin tiles based on the new permission set.
4. **Given** a permission-cache fetch fails (network down, transient Supabase error), **When** the failure is observed, **Then** the cache retains its previous value (does NOT clear to empty — clearing would falsely hide every admin tile from a signed-in admin during a network blip) and a localized error is logged via Phase 1's logger; the next observation point retries the fetch.
5. **Given** any widget in the app, **When** it reads `PermissionChecker.has('listings.approve')`, **Then** the read is synchronous against the cached value — the widget does not perform a database round-trip on every rebuild.

### Edge Cases

- **System role immutability**: The seven seeded system roles (`user`, `owner`, `agent`, `agency_admin`, `moderator`, `admin`, `super_admin`) MUST be flagged `is_system=true` and protected from deletion in v1. Renaming the `key` column of a system role MUST also be forbidden. The `display_name` and `description` columns ARE editable so super admins can localize the labels. Phase 6 enforces this via a trigger or a column-level check; Phase 7's super-admin UI consumes the flag to hide delete/rename affordances.
- **Service-role caller without `auth.uid()`**: `current_user_has_permission(perm_key)` and the body-swapped `current_user_is_admin()` MUST return `FALSE` (not raise) when called without a JWT `auth.uid()` (e.g., from a service-role session or a migration's `DO $$` block). Wrap the body in `COALESCE` or check `auth.uid() IS NOT NULL` first.
- **No `auth.uid()` row in `user_roles`**: A signed-in user whose `auth.uid()` has no row in `user_roles` (e.g., the auto-provision trigger's brief window between `auth.users` insert and `user_roles` default-assignment, or — more realistically — every user who registered before Phase 6 shipped if no backfill assigns the implicit `user` role) MUST be treated as holding the `user` role's permissions by default. Phase 6's backfill migration inserts a `user`-role row for every existing profile that doesn't already have one (FR-011 step 3) so the invariant "every signed-in user has at least one `user_roles` row" is established immediately, and a Phase 6 INSERT trigger on `profiles` keeps the invariant for new signups (FR-013).
- **Duplicate role assignment**: `UNIQUE(user_id, role_id)` on `user_roles` MUST prevent the same user from holding the same role twice. INSERTs use `ON CONFLICT DO NOTHING` so re-running the backfill migration doesn't error.
- **Role assignment audit trail**: Every INSERT or DELETE on `user_roles` MUST emit one `audit_logs` row via Phase 4's reusable `log_audit()` trigger (Phase 5 FR-010 reusability invariant). Two triggers are attached — `trg_user_roles_audit_granted` (AFTER INSERT, emits `audit_logs.action = 'user_role.granted'`) and `trg_user_roles_audit_revoked` (AFTER DELETE, emits `audit_logs.action = 'user_role.revoked'`). No UPDATE trigger in v1 — `user_roles` rows are immutable post-insert. The `actor_user_id` column carries `auth.uid()` for in-app mutations from Phase 7 onward; for the Phase 6 FR-011 backfill migration itself, `actor_user_id` is NULL (the migration runs as `postgres` with no JWT), which makes backfill rows distinguishable from in-app assignments in the audit trail. The action string is taken verbatim from `TG_ARGV[0]` (Phase 4's `log_audit` does NOT append a TG_OP-derived verb — Phase 5 convention is to pass a full action key per trigger).
- **Audit triggers on `roles`, `permissions`, `role_permissions` are out of scope**: §9.4 of the implementation plan lists "Role / permission mutations" under Phase 7. Phase 6 does NOT attach `log_audit()` to these three tables; Phase 7 attaches them alongside its super-admin mutation UI. The single audit trigger Phase 6 ships is the one on `user_roles`.
- **Anonymous client sees nothing on Phase 6 tables**: An unauthenticated client MUST NOT be able to read `roles`, `permissions`, `role_permissions`, or `user_roles`. Phase 4's anon-blocked baseline is preserved. Authenticated read is allowed on `roles`, `permissions`, `role_permissions` (the profile page reads role display names; PermissionChecker reads the joins to compute the effective permission set); `user_roles` read is self-only (the user reads their own assignments) plus admin-cross-read via `users.view`.
- **Cross-user `profiles` read for moderators**: §9.1 grants `users.view` to moderators, admins, and super_admins. Phase 6 ADDS a new RLS policy on `profiles` granting cross-user read to sessions whose `current_user_has_permission('users.view')` returns `true`. The pre-Phase-6 self-only policy is preserved (a user can still read their own row); the new policy stacks on top. Phase 4's self-only invariant is upgraded — not replaced.
- **Phase 5 cross-user PII helper retains `current_user_is_admin()` gate**: The Phase 5 `app_vault_secret_for_user(user_id, field_name)` helper continues to check `current_user_is_admin()` (which now resolves to "user has admin or super_admin role"). Phase 6 does NOT refactor this helper to check `users.view` — granting moderators access to decrypted PII is a meaningful policy expansion, and the implementation plan does not specify it. Moderators retain `users.view` (cross-user `profiles` row read) but NOT cross-user PII read. The spec records this as a deliberate choice; a future spec may carve out a dedicated `users.view_pii` permission key.
- **`current_user_is_admin()` is retained, not deleted**: Phase 5 policies reference the helper by name. Phase 6 swaps the body; the function signature and name stay. The helper is retained as a documented alias for "has admin or super_admin role"; new policies added in Phase 6 (and later phases) MAY use it for the specific "any admin-tier user" semantics, but the preferred pattern for specific gates is `current_user_has_permission(<specific key>)`.
- **PermissionChecker cache lifetime**: The cache lives for the duration of the session. On sign-out, the cache clears. On sign-in, it loads. The mid-session refresh points are: auth state listener, app foreground resume, explicit `refresh()` call from AuthBloc.
- **Cache fetch failure falls back to last known value**: A network-down or transient Supabase error during a permission-cache refresh MUST leave the cache holding its previous value (not clear to empty). Clearing to empty would falsely hide every admin affordance from a signed-in admin during a transient blip. The next refresh point retries.
- **PermissionChecker is not a security boundary**: Constitution III is enforced at the database (RLS) layer. The `PermissionChecker` exists only to drive UX (hide buttons the user can't use anyway). A user who defeats the UI hiding hits the same RLS that would have rejected them via the admin queue test in US4 #6.
- **Hardcoded role checks are forbidden**: Per Constitution VII, no Phase 6 (or later) Flutter feature code MUST contain `if (user.role == 'admin')` or equivalent. Every gate goes through `PermissionChecker.has(...)`. The Phase 6 PR is reviewed against this rule; the project's existing lint setup (Phase 3's localization guard pattern) MAY be extended with a similar guard.
- **Idempotent migrations**: Every Phase 6 migration MUST be safe to re-apply against the remote Supabase project. The four create-table migrations use `CREATE TABLE IF NOT EXISTS`; the seed uses `INSERT ... ON CONFLICT DO NOTHING`; the helper functions use `CREATE OR REPLACE FUNCTION`; the trigger creates use `DROP TRIGGER IF EXISTS … CREATE TRIGGER`; the column drop uses `ALTER TABLE … DROP COLUMN IF EXISTS`. Supabase's migration tracker handles the normal flow; this defensive idempotency handles the project memory `project_supabase_mcp_apply_migration.md` (re-applying a migration name re-runs the SQL).
- **Domain layer stays Supabase-free**: New code in `lib/core/security/` and `lib/features/admin/` MUST follow Constitution IX — anything in `domain/` imports nothing from `package:supabase_flutter`. The `data/` layer of `lib/features/admin/` and the new `lib/features/admin/data/` repositories are the only places Supabase types appear.

      FROM public.user_roles ur
      JOIN public.role_permissions rp ON rp.role_id = ur.role_id
      JOIN public.permissions p ON p.id = rp.permission_id

  ), FALSE)

### Key Entities

- **Role**: A named bundle of permissions. Identified by an immutable string `key` (e.g., `admin`). Carries a localized `display_name` JSONB for the profile-page render. The seven seeded `is_system=true` rows cannot be deleted or renamed in v1; super_admin can edit their `display_name` / `description` and the permissions attached to them via Phase 7's super-admin UI.
- **Permission**: A fine-grained capability key (e.g., `listings.approve`). Identified by an immutable `key`. Grouped by `category` for the Phase 7 super-admin UI's grouping. The catalog is closed in v1 — Phase 7 may allow super_admin to add new keys post-v1, but Phase 6's seed is the canonical set.
- **RolePermission**: An (role, permission) tuple expressing "this role grants this permission". Many-to-many. Seeded per §9.1 defaults. Mutable in Phase 7 (super_admin can edit a role's permissions); read-only in Phase 6.
- **UserRole**: An (user, role) assignment. Records who granted it (`granted_by`, nullable for system grants) and when (`granted_at`). One row per user-per-role. The path the profile page uses to display a user's roles. Mutable in Phase 7 (super_admin assigns/revokes roles); read-only in Phase 6 except via the backfill migration and the auto-provision-of-`user`-role trigger.
- **PermissionChecker (frontend)**: A session-scoped singleton that caches the signed-in user's effective permission set. Refreshes on auth-state events (via `AuthBloc._onSessionRefreshed`) and app foreground resume (via `AuthBloc._onAppResumedRefresh` — the bloc itself is the `WidgetsBindingObserver` via mixin). UX layer only — not a security boundary.
- **AdminPredicate (Phase 6 form)**: The `current_user_is_admin()` SQL function whose body Phase 6 swaps a second time, from Phase 5's `(SELECT is_admin FROM profiles WHERE user_id = auth.uid())` to a role-membership check ("user holds `admin` or `super_admin`"). The function name and signature are unchanged; the body change is the only edit; every Phase 4 and Phase 5 policy that references the helper continues to work. Phase 6 is the LAST time this function's body changes — future phases use `current_user_has_permission(<key>)` directly.
- **PermissionPredicate (Phase 6 introduction)**: The `current_user_has_permission(perm_key TEXT)` SQL function joining `user_roles → role_permissions → permissions`. Every later phase's RLS policies use this for permission-keyed gating. The single helper definition every permission-keyed policy across the project depends on.

Migrations are authored as `.sql` files under `supabase/migrations/` and applied to the remote Supabase project via Supabase MCP `apply_migration`. Verification is manual SQL inspection via Supabase MCP `execute_sql` and manual UI verification on the reference Android device.
- **No new automated tests**: carried forward from the durable session feedback `feedback_no_new_tests.md`. This phase introduces no new automated tests of any kind. Existing Phase 1–5 tests remain in source unchanged. Verification is manual SQL inspection plus manual UI verification on the device.
- **Reference device**: Infinix Note 8 (Helio G80, 6 GB RAM, Android 10/11) per project memory `user_test_device.md` is the primary physical device for device-side acceptance scenarios.
- **First super_admin bootstrap**: The Phase 6 backfill does NOT assign the `super_admin` role to anyone — every prior `is_admin=true` user becomes `admin` only (per FR-011 step 2). The first `super_admin` in the project is created post-Phase-6 via privileged SQL (`Supabase MCP execute_sql` running as `postgres`) — the same pattern Phase 5 used for the first admin (spec 005 R-19). Phase 7's super-admin UI requires that one-time privileged SQL action as a deploy prerequisite before it can function; it is documented as a Phase 7 entry condition rather than a Phase 6 gap. No `user_id` is hand-picked or hardcoded into any Phase 6 migration. Resolved per Session 2026-05-15 Clarifications.
- **PermissionChecker cache refresh strategy**: Phase 6 uses exactly the observation points specified in FR-015 — auth-state listener events (via the bloc's `_onSessionRefreshed`) and app foreground resume (via the bloc's `_onAppResumedRefresh`, the Phase 5 R-21 lifecycle observer; the `AuthBloc` itself mixins `WidgetsBindingObserver`). No separate `refreshSession()` method exists on the bloc — the event-handled pattern (`SessionRefreshed`, `AppResumedRefresh`) is the canonical entry. No periodic timer; no Supabase Realtime subscription on `user_roles`. Realtime stays deferred to Phase 22 per the implementation plan. **Phase 22 follow-up**: the spec for Phase 22 (push notifications + Supabase Realtime signals) MUST re-evaluate this decision and consider extending the PermissionChecker to subscribe to `user_roles` changes via Realtime — the upgrade was considered and rejected at Phase 6 time to keep scope minimal and to avoid pulling Realtime in ahead of schedule. Track this as a known follow-up, not as new work. Resolved per Session 2026-05-15 Clarifications.
- **PII cross-user read predicate is unchanged in Phase 6**: the Phase 5 `app_vault_secret_for_user(user_id, field_name)` helper continues to check `current_user_is_admin()` (which Phase 6 re-bodies to "admin or super_admin role"). Phase 6 does NOT refactor this helper to gate by a specific permission key, and Phase 6 does NOT introduce any cross-user PII write path — admins and super_admins can decrypt another user's PII via the existing Phase 5 read helper, but neither admin nor super_admin can edit another user's PII in Phase 6. Moderators gain `users.view` (cross-user `profiles` row read) but do NOT inherit cross-user PII decrypt access. **Forward-extensibility**: super_admin can reshape who has PII access via Phase 7's super-admin UI by editing role-permission mappings or role assignments — if a future spec carves out a `users.view_pii` permission key (or similar) and refactors the helper to gate by it, super_admin can grant that key to a custom role without further code changes. Phase 6 ships the tightest sensible privacy boundary as the v1 default; the room to broaden it later via configuration is preserved. Resolved per Session 2026-05-15 Clarifications.
- **Audit triggers on `roles`, `permissions`, `role_permissions` are out of scope**: §9.4 of the implementation plan lists role/permission mutations under Phase 7. Phase 6 ships the trigger on `user_roles` only. Phase 7's super-admin mutation UI brings the triggers on the other three tables.
- **Realtime is out of scope**: the permission cache refreshes via the three documented observation points only; no Supabase Realtime subscription is opened on `user_roles` in v1. Phase 22 (push + Realtime) MAY layer real-time role-change notifications on top, but Phase 6 does not commit to that path.
- **System roles immutability is partial**: the `is_system=true` rows cannot be deleted in v1, and their `key` column is immutable. `display_name` and `description` are editable from Phase 7's super-admin UI so super_admin can localize the labels or refine the documentation. The set of permissions attached to a system role IS editable via Phase 7 (super_admin can grant or revoke a permission on the `moderator` role, for example) — only the role's identity is immutable.
- **Permission catalog is closed in v1**: the §9.1 catalog is the canonical set. Phase 7's super-admin UI does NOT ship a "create new permission key" affordance in v1 — the permission set is frozen at Phase 6's seed. Future specs MAY add new keys via migrations (Phase 19 agencies likely adds `agencies.assign_member` or similar; Phase 21 ads may add granular keys). Each future spec that adds a key authors its own migration that INSERTs into `permissions` and into `role_permissions` for the appropriate roles.
- **Permission keys are dot-namespaced strings, not Postgres enums**: §9.1's keys (`listings.approve`, `roles.update`, etc.) are `TEXT` values, NOT a Postgres enum. The flexibility (super_admin or future migrations can add keys without an `ALTER TYPE … ADD VALUE`) outweighs the compile-time safety loss. The frontend mirrors them as `const String` fields in `lib/core/security/permission_keys.dart` per FR-018.
- **Hardcoded role checks remain a code-review rule, not a lint rule, in v1**: extending Phase 3's lint guard to also flag `user.role == 'admin'` patterns is OPTIONAL in Phase 6 and ships only if the rule is cheap to author. The primary enforcement is the Phase 6 PR review against Constitution VII.
- **Domain layer stays Supabase-free**: new code in `lib/core/security/` and the new `lib/features/admin/domain/` (and the Phase 6 additions to `lib/features/profile/domain/`) MUST follow Constitution IX. The `data/` layer is the only place Supabase types appear.

The branch is `006-roles-permissions`; the merge target is `main`.
