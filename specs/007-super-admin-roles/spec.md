# Feature Specification: Super-Admin Role & Permission Management

**Feature Branch**: `007-super-admin-roles`
**Created**: 2026-05-15
**Status**: Draft
**Input**: User description: "Phase 7 — Super-admin role UI. Super admin can create roles, edit permissions on roles, and assign roles to users — fully in-app. Backend: Edge Function (or SECURITY DEFINER RPC) `mutate_role` wrapping role create/update/delete with permission re-check and audit-log emission; audit triggers on `roles`, `role_permissions`, `user_roles` (extending the Phase 6 `user_roles` triggers with parallel triggers on the other two tables); write-side RLS policies on the four Phase 6 catalog tables. Frontend: `lib/features/super_admin/` with `RolesListPage`, `RoleEditorPage` (toggle permissions per role + save name/description), `AssignRolePage` (search user → assign/remove roles); BLoCs and use cases in domain; confirmation dialogs on destructive actions (delete custom role, remove role from user). Acceptance: super_admin can create a custom `finance` role with `currencies.manage` only; assigning it to a user grants them the currency-management UI on next session refresh; a non-super-admin cannot reach the super-admin pages (route guard + RLS); every mutation writes an `audit_logs` row. Authored per docs/IMPLEMENTATION_PLAN.md §Phase 7 + §9.4 Audit triggers."

## Clarifications

### Session 2026-05-15

- **Q1.** Can `AssignRolePage` grant the `super_admin` role to another user from inside the app, or is `super_admin` strictly bootstrap-only? → A: **Allow with two-step confirmation.** `super_admin` appears in the role picker like any other role, but selecting it for a grant surfaces a heavier confirmation flow than a normal grant: the super_admin must (a) re-confirm via a dedicated dialog that lists the consequences ("this user will gain every permission in the catalog, including the ability to manage roles and permissions"), AND (b) type the target user's phone number (or username) into a confirmation field that must match exactly before the grant button enables. Both gates apply to the super_admin grant path only — every other role grant uses the standard single-step confirmation from US5. The first-super_admin bootstrap via privileged SQL remains an entry-condition for the very first super_admin (Phase 6 Q1, Option C); every subsequent super_admin in the project lifetime MAY follow either the in-app two-step path or the same privileged-SQL recipe.
- **Q2.** Should the UI / server block a super_admin from revoking their own `super_admin` role when they are the last remaining super_admin? → A: **Block all self-revocation.** A super_admin can NEVER revoke their own `super_admin` role via `AssignRolePage` — even if there are five other super_admins. The block is enforced in two places: the UI hides the remove-affordance on the super_admin's own `super_admin` row (and refuses the action if invoked through any other surface), AND the server-side `mutate_role` RPC (Q3) re-checks that `auth.uid() != target user_id` for any super_admin revocation. To leave the super_admin role, a super_admin must ask a different super_admin to revoke it. If the project ever ends up in a state with zero super_admins (e.g., the last super_admin's `auth.users` row is deleted), recovery follows the same Supabase MCP `execute_sql` running-as-`postgres` recipe as the original Phase 6 bootstrap. Rationale: the rule is the simplest mental model and the easiest server-side check (one equality check, no count query in the critical path).
- **Q3.** Should the atomic role+permissions mutation entry point ship as a Supabase Edge Function (`mutate_role`, the implementation plan's named choice) or as a SECURITY DEFINER SQL RPC? → A: **SECURITY DEFINER SQL RPC.** The entry point is a Postgres function (e.g., `public.mutate_role(op TEXT, role_id UUID, role_key TEXT, display_name JSONB, description TEXT, permission_keys TEXT[], expected_updated_at TIMESTAMPTZ) RETURNS JSONB`) defined `LANGUAGE plpgsql SECURITY DEFINER SET search_path = public, auth` and applied via Supabase MCP `apply_migration` — the same pipeline every prior phase used. The function (a) re-checks the caller's session permissions via `current_user_has_permission(...)`, (b) executes the `roles` row mutation AND the `role_permissions` delta in one implicit transaction, (c) relies on the Phase 7 audit triggers (FR-001, FR-002) to emit the audit-row sequence automatically. Rationale: matches the project's established "no local Supabase setup" constraint; transactional atomicity is native to Postgres; the permission re-check is a one-line SQL guard; the audit pattern is on-table-trigger (already in place from FR-001/FR-002); Edge Function deployment infrastructure (Supabase CLI deploy, service-role key handling, separate observability) is deferred to a later phase that genuinely needs an Edge Function for non-database reasons (e.g., the Phase 22 FCM fan-out, the Phase 12 listing-approval orchestration if it grows complex). The implementation plan explicitly admitted direct SQL is allowed; the Edge Function was named only because it would provide the atomicity guarantee — that guarantee is achieved here by the RPC.
- **Q4.** How should concurrent edits to the same role be handled when two super_admins open `RoleEditorPage` simultaneously and both tap Save? → A: **Optimistic locking via the existing `roles.updated_at` token.** The Flutter client captures `roles.updated_at` at the moment `RoleEditorPage` opens, passes it as `expected_updated_at` on the Save call into `mutate_role`, and the RPC compares the value against the current stored `roles.updated_at` before applying any mutation. If the values differ (someone else saved in the meantime), the RPC raises `SQLSTATE 40001` (serialization_failure) with a structured error code; the UI catches this and shows a localized "this role was changed by another super_admin — reload and re-apply your edits" message, drops the pending edits, and reloads the role. No schema change is required: Phase 6 FR-001 already created `roles.updated_at TIMESTAMPTZ` maintained by the Phase 4 `set_updated_at` trigger. This is the most security-sensitive in-app surface in v1; silent overwrite of a concurrent super_admin's edits would be unrecoverable absent audit-log archeology, and the cost of the guard is one extra RPC parameter plus one `IF` clause.
- **Q5.** Should the `super_admin` role's permission mapping be editable through `RoleEditorPage` like every other system role, given that emptying it would render every super_admin inert and require a privileged-SQL recovery? → A: **UI-level block on the `super_admin` row's permission checklist + server-side enforcement as defense-in-depth.** `RoleEditorPage` renders the permission checklist as read-only (disabled) when the active role's `key` is `super_admin`; the `display_name` and `description` fields remain editable so super_admin can localize labels (e.g., add a French translation). The `mutate_role` RPC additionally enforces the rule server-side: if `op='update'` and `role_id` references the `super_admin` row AND `permission_keys` differs from the role's current permission set, the RPC raises `42501` with a structured error code the UI maps to "the super_admin role's permission set is immutable". The DB-side `role_permissions` table is not trigger-locked at the table level (a future spec MAY carve out an exception via a SECURITY DEFINER helper if needed); the two-layer enforcement (UI hides the checklist; RPC rejects the write) is sufficient for v1. Rationale: super_admin's identity-as-superuser depends on holding the full catalog; permission emptying has no in-app recovery path and would require the same privileged-SQL bootstrap as the first-super_admin recipe — a footgun worth blocking with minimal infrastructure cost.
- **Q6.** How should the permission-category headings (`users`, `listings`, `roles`, `locations`, `currencies`, `ads`, `reports`, `agencies`, `settings`, `audit`, `inquiries`, `permissions`) be localized when `RoleEditorPage` groups the permission checklist by category? → A: **ARB-keyed app-side localization, no DB change.** Add `permissionCategory<Capitalized>` keys to both `lib/l10n/app_ar.arb` and `lib/l10n/app_en.arb` (e.g., `permissionCategoryUsers = "المستخدمون" / "Users"`, `permissionCategoryListings = "العقارات" / "Listings"`, …). The Phase 7 widget reads `permissions.category` (a stable TEXT identifier), normalizes it to the ARB key via a deterministic transform (e.g., `users` → `permissionCategoryUsers`), and looks up the localized string via `AppLocalizations.of(context)`. If a future spec adds a new category and the corresponding ARB key is missing, the widget falls back to displaying the raw `category` value (which is fine for short-lived dev gaps; the Phase 3 lint guard catches missing translations at PR review per FR-016). The `permissions.category TEXT` column from Phase 6 stays unchanged — no Phase 7 schema migration on `permissions`. This matches Constitution V (every user-visible string flows through `AppLocalizations`) and reuses the Phase 3 translation pipeline.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Super-admin entry tile and route guard are permission-gated (Priority: P1)

After Phase 7 ships, a logged-in user whose `user_roles` rows include `super_admin` sees a new "Super-admin" entry on the admin home page (the Phase 6 `AdminHomePage`). Tapping it opens the super-admin section, whose three top-level pages are `RolesListPage`, the in-list `RoleEditorPage` view, and `AssignRolePage`. A non-super-admin user (regular `user`, `moderator`, even `admin`) does NOT see the super-admin tile; if they hand-craft a deep link to `/admin/super-admin/...` the route guard refuses the navigation. Even if a non-super-admin defeats both layers, the underlying RLS policies introduced in this phase reject every write (role create / role update / role_permission INSERT-DELETE / user_role INSERT-DELETE), and the Edge Function (or SECURITY DEFINER RPC) `mutate_role` re-checks the caller's `permissions.manage` and `roles.*` keys server-side before performing any action. Phase 7's super-admin UI is also a deploy-prerequisite consumer: it cannot do anything useful until at least one `auth.users` row holds the `super_admin` role, and Phase 6 deliberately left the project with zero `super_admin` assignments (R-16, Option C). The Phase 7 entry condition is therefore "post-Phase-6 privileged SQL has inserted the first `super_admin` `user_roles` row" — that one-time bootstrap remains a privileged SQL action via Supabase MCP `execute_sql` running as `postgres`, with no in-app surface.

**Why this priority**: P1 because every later Phase 7 story rests on the entry gate. Constitution VII (Dynamic Roles & Permissions) is what made the gate possible in Phase 6; this story uses it to gate the most privileged in-app surface in v1. Constitution III (Security-First Supabase) requires the gate to be three-layer — UX hide via `PermissionChecker`, route guard at the Flutter router, RLS+RPC at the backend — and this story is the only Phase 7 surface that exercises all three layers. Without this story the project either exposes super-admin tools to the wrong users (security failure) or to nobody (the project is locked out and unusable). The "first super_admin bootstrap is privileged SQL" entry condition is the only operationally-load-bearing post-deploy step Phase 7 carries.

Sign out, sign in as the Phase 5 admin (holding only the `admin` role from the Phase 6 backfill) — confirm the admin home page renders, the existing Phase 5 admin queue tile is present, but the new "Super-admin" tile is absent (admin lacks `roles.view` / `permissions.manage`). Sign back in as the same account; confirm the "Super-admin" tile is now visible (the `PermissionChecker` reloaded the cache via the auth-state listener on sign-in); tap it; confirm `RolesListPage` opens.

**Acceptance Scenarios**:

1. **Given** a signed-in session for a user holding only `user`, `moderator`, or `admin` roles, **When** the admin home page renders, **Then** the "Super-admin" tile is absent (the widget is hidden, not just dimmed) — `PermissionChecker.any({rolesView, rolesCreate, rolesUpdate, rolesDelete, permissionsManage})` returns `false`.
2. **Given** the same non-super-admin session, **When** the user navigates directly via the deep link `/admin/super-admin/roles`, **Then** the route guard refuses the navigation and redirects to either the admin home or the access-denied screen used by the rest of the admin routes (the exact destination matches Phase 6's pattern for unauthorized admin routes).
3. **Given** the same non-super-admin session, **When** the user crafts a request that bypasses the UI entirely and POSTs to the `mutate_role` Edge Function (or the RPC), **Then** the function returns a 403 (or `RAISE`s `42501`) because its server-side permission re-check fails.
4. **Given** the same non-super-admin session, **When** the user crafts a direct SQL INSERT against `roles` / `role_permissions` / `user_roles`, **Then** the Phase 7 write-side RLS policy rejects the write (no rows affected, no error visible to the client beyond the standard RLS empty-result behavior).
5. **Given** a signed-in session for a user holding the `super_admin` role assigned via the post-Phase-6 privileged SQL bootstrap, **When** the admin home page renders, **Then** the "Super-admin" tile is present and tapping it opens `RolesListPage`.
6. **Given** the project has zero `super_admin` `user_roles` rows (a fresh post-Phase-6 deploy), **When** any user signs in, **Then** no user — including the prior-Phase-5 admin — sees the super-admin tile. The first super_admin must be created via the documented post-Phase-6 privileged-SQL bootstrap before the Phase 7 surface is reachable.

### User Story 2 - Roles list shows the full catalog with system-row protection (Priority: P1)

A signed-in super_admin taps the "Super-admin" tile, which opens `RolesListPage`. The page lists every row from `public.roles` — the seven seeded `is_system=true` rows from Phase 6 (`user`, `owner`, `agent`, `agency_admin`, `moderator`, `admin`, `super_admin`) plus any custom roles created via the Phase 7 surface, ordered alphabetically by `roles.key` (the same deterministic order Phase 6 uses on the profile page). Every row shows the role's localized `display_name` per the active locale (Arabic by default, English when toggled; falls back to `roles.key` if the active-locale value is missing — same fallback as Phase 6 US3), a short summary of how many permissions the role carries (e.g., "5 permissions" from `role_permissions` rolled up), and an `is_system` badge for the seven seeded rows. Tapping any row opens `RoleEditorPage` for that role. Custom (non-system) rows expose a delete affordance (long-press → confirm dialog, or a contextual menu); system rows do NOT expose a delete affordance and do NOT expose a `key`-rename affordance — Phase 6 FR-020 enforces this server-side via the `enforce_role_system_immutability` trigger, and Phase 7 honors it client-side so the user never sees an affordance that would error.

**Why this priority**: P1 because every later story navigates through this list. Constitution VII requires the UI to never expose a hardcoded role identity; the list is reading from the data table, not from a hardcoded enum. Constitution VI requires the list rendering to come straight from the Phase 2 design-token components (no inline colors, no inline paddings) and Constitution V requires every label to come from the ARB-driven localization. The system-row protection is the first place the Phase 6 `is_system` flag drives client-side UX, and it sets the pattern for every later "this row is protected" affordance the project ships.

### User Story 3 - Role editor changes a role's permission set and saves (Priority: P1)

The super_admin taps a role on `RolesListPage`, opening `RoleEditorPage` for that role. The page shows the role's editable `display_name` (one input per supported locale: `ar`, `en`) and `description` (single text area), plus the role's current permission set rendered as a list of checkable rows grouped by `permissions.category` (e.g., a "Listings" section listing `listings.view_all`, `listings.approve`, `listings.reject`, `listings.edit_any`, `listings.delete_any`; a "Users" section; etc.). Each permission row shows its `permissions.key` and the localized `permissions.description` from the catalog. The super_admin toggles permissions on or off and edits the `display_name` / `description` fields. Tapping "Save" produces ONE atomic mutation: the role's row in `public.roles` is updated (display_name JSONB, description), and the delta against `public.role_permissions` is applied — every newly-checked permission produces one INSERT row, every newly-unchecked permission produces one DELETE row. If the save fails (network down, RLS or DB-trigger violation, conflict), the editor restores the prior state and shows a localized error. On success, the editor returns to `RolesListPage`, which reflects the updated permission count.

**Why this priority**: P1 because this is the plan's centerpiece — "edit permissions on roles". The plan acceptance scenario "Assigning that role to a user grants them the currency-management UI on next session refresh" implicitly assumes role-permission edits work atomically. Constitution VII is enforced: every UI gate elsewhere in the project resolves to a `permissions.key` check, and this page is the only in-app surface that changes which keys a role grants. The atomicity is the safety property — if a half-applied save left a role in an intermediate state, a user's effective permission set could drift unpredictably. Constitution III is also enforced — the page does not call Supabase from the widget tree; the BLoC dispatches a single use-case which writes via the `data/` layer's atomic mutation path.

**Independent Test**: Sign in as the bootstrapped super_admin on the device, open `RolesListPage`, tap the `admin` role. Confirm the editor opens with `display_name` filled in (`{"ar": "مدير", "en": "Admin"}` from Phase 6 seed), `description` empty (the Phase 6 seed leaves this null), and 17 permission rows checked (the Phase 6 §9.1 admin mapping). Uncheck one permission (e.g., `ads.manage`). Tap Save. Confirm the editor returns to the list and the admin row now shows "16 permissions". Verify via Supabase MCP `execute_sql`: `SELECT count(*) FROM role_permissions rp JOIN roles r ON r.id=rp.role_id WHERE r.key='admin'` returns 16. Re-open the editor; re-check `ads.manage`; tap Save; confirm count returns to 17. Verify `audit_logs` carries one `role.updated` row (from the roles update) plus one `role_permission.revoked` row (from the original uncheck) and one `role_permission.granted` row (from the re-check). Verify the `display_name`/`description` text inputs persist edits: change the English label to "Administrator", save, refresh, confirm the new label is shown on `RolesListPage`. Revert.

**Acceptance Scenarios**:

1. **Given** `RoleEditorPage` opens for the `admin` role, **When** the page first renders, **Then** the `display_name` inputs are pre-filled from `roles.display_name->>ar` and `->>en`, the `description` field is pre-filled from `roles.description`, and the permission list shows exactly 17 checked rows (the §9.1 admin mapping) with the remaining permissions unchecked.
2. **Given** the super_admin checks a previously-unchecked permission and unchecks a previously-checked permission, **When** they tap Save, **Then** ONE atomic operation executes: `roles` UPDATE (display_name JSONB / description) AND `role_permissions` INSERT for the newly-checked row AND `role_permissions` DELETE for the newly-unchecked row. If any step would fail, the entire operation rolls back and the UI restores the prior state with a localized error.
3. **Given** the save succeeds, **When** the editor returns to `RolesListPage`, **Then** the row's permission count summary reflects the new total, and the localized `display_name` reflects the latest values from the same JSONB.
4. **Given** the super_admin edits the `moderator` (or any non-`super_admin` system role), **When** they Save, **Then** the save succeeds — non-`super_admin` system rows ARE editable on `display_name`, `description`, and on their permission mapping (only the `key` column and DELETE are blocked per Phase 6 FR-020). The Phase 7 audit triggers (US6) emit the corresponding `role.updated` / `role_permission.granted` / `role_permission.revoked` rows.
4a. **Given** the super_admin opens `RoleEditorPage` for the `super_admin` row, **When** the page renders, **Then** the permission checklist is read-only (disabled) per Clarifications Session 2026-05-15 Q5; the `display_name` and `description` fields ARE editable so super_admin can localize the role's label. Saving an edit to `display_name` and/or `description` only (no permission changes) succeeds; saving any payload that would mutate the `super_admin` permission set is rejected by `mutate_role` with `42501` and the UI surfaces "the super_admin role's permission set is immutable".
5. **Given** the super_admin attempts to save with both `display_name.ar` AND `display_name.en` cleared to empty strings, **When** they tap Save, **Then** the editor refuses to save and shows a localized validation error — `roles.display_name` is `NOT NULL` (Phase 6 FR-001) and must contain at least one non-empty locale value.
6. **Given** the editor renders for any role, **When** the super_admin scans for affordances that would expose creating new permission keys (NOT permissions on roles, but the catalog itself), **Then** none exist — the v1 permission catalog is closed (Phase 6 assumption); the editor only toggles existing rows.
7. **Given** super_admin A and super_admin B both have `RoleEditorPage` open for the `admin` role at the same moment, **When** A taps Save and the mutation completes, **Then** A's `mutate_role` call succeeds (their captured `expected_updated_at` matched `roles.updated_at` at the moment of the call). **When** B subsequently taps Save without reloading the editor, **Then** B's call raises `SQLSTATE 40001` because the `set_updated_at` trigger advanced `roles.updated_at` during A's transaction; the UI shows a localized "this role was changed by another super_admin — reload and re-apply your edits" message and reloads the role. No partial write happens for B; A's edits are preserved verbatim (Clarifications Session 2026-05-15 Q4).

### User Story 4 - Custom non-system roles can be created and deleted (Priority: P2)

The super_admin taps a "Create role" affordance on `RolesListPage`, opening a creation form. The form requires a unique lowercase `key` (TEXT, dot-namespace-friendly but not enforced; e.g., `finance`), a non-empty `display_name` JSONB (input per locale), an optional `description`, and an initial permission set (the same category-grouped checklist used by `RoleEditorPage`). The form refuses to save if the `key` collides with an existing row (the `UNIQUE(roles.key)` constraint would error; the form catches this and shows a localized "this key is already used" message). On save, the new row is inserted into `public.roles` with `is_system=false`, and the selected permissions are written to `public.role_permissions` in the same atomic operation. The new row appears on `RolesListPage` at the alphabetically-correct position, carries no `is_system` badge, and exposes a "Delete" affordance. Tapping "Delete" prompts a confirmation dialog ("Are you sure you want to delete this role? All users currently holding this role will lose its permissions on their next session refresh.") and lists the count of users currently affected (via `SELECT count(*) FROM user_roles WHERE role_id=<id>`). Confirming the dialog deletes the role; the `ON DELETE CASCADE` on `role_permissions.role_id` removes its permission mappings; the `ON DELETE RESTRICT` on `user_roles.role_id` (Phase 6 FR-007) means the delete fails if any user still holds the role — the dialog therefore offers an option to revoke the role from all affected users first (which produces N `user_role.revoked` audit rows) and only then completes the delete.

**Why this priority**: P2 because the project ships fine at Phase 7 without it — every later phase that needs a permission gate references existing catalog keys, and the seven seeded system roles cover every v1 admin-tier need. Custom roles are an extensibility surface for the project's future: a "finance" role with `currencies.manage` only is the plan's acceptance criterion; a "QA" role with `listings.view_all` + `reports.manage` is a plausible v1+1 use. The story is independently shippable — Phase 7 could deploy with `RoleEditorPage` working but with the "Create" / "Delete" affordances disabled in v1, and add them in a v1.1 spec without touching the other stories. The DB schema, RLS, and audit triggers from US6 already cover this story end-to-end (the same INSERT/DELETE policies on `roles` apply); only the UI surface is the incremental work.

**Independent Test**: Sign in as the bootstrapped super_admin on the device. Open `RolesListPage`. Tap "Create role". Fill in `key = finance`, `display_name = {"ar": "محاسبة", "en": "Finance"}`, no description, check `currencies.manage` only in the permission list. Tap Save. Confirm the list now shows 8 rows including a `finance` row at the right alphabetical position with no `is_system` badge. Verify via Supabase MCP `execute_sql`: `SELECT key, is_system FROM roles WHERE key='finance'` returns `finance, false`; `SELECT p.key FROM role_permissions rp JOIN roles r ON r.id=rp.role_id JOIN permissions p ON p.id=rp.permission_id WHERE r.key='finance'` returns exactly `currencies.manage`. From the list, long-press the `finance` row, confirm a "Delete" affordance is present (unlike system rows), tap it. Confirm a confirmation dialog appears, lists "0 users currently affected", and explains the consequences. Confirm. Confirm the row disappears from the list. Verify via Supabase MCP `execute_sql`: `SELECT count(*) FROM roles WHERE key='finance'` returns 0, and `SELECT count(*) FROM role_permissions WHERE role_id=<old finance id>` returns 0 (cascade fired). Verify `audit_logs` shows one `role.created` row (for the create) followed by one `role.deleted` row (for the delete) and one `role_permission.revoked` row (for the cascaded permission delete).

**Acceptance Scenarios**:

1. **Given** the super_admin opens the creation form, **When** they enter `key = admin` (a system role already exists with this key), **Then** the form refuses to save and shows a localized "this key is already used" error.
2. **Given** the super_admin enters a valid new `key`, a `display_name` with both locale values populated, and selects one or more permissions, **When** they tap Save, **Then** the operation atomically inserts ONE row into `roles` (with `is_system=false`) and N rows into `role_permissions`. The new role appears in `RolesListPage` immediately on return.
3. **Given** a custom role with zero users currently holding it, **When** the super_admin taps Delete and confirms, **Then** the row is deleted from `roles`, the cascade removes its `role_permissions` rows, and the row disappears from `RolesListPage`. Audit logs show `role.deleted` plus the cascaded `role_permission.revoked` rows.
4. **Given** a custom role with N users currently holding it, **When** the super_admin taps Delete, **Then** the confirmation dialog states "this role is currently assigned to N users" and offers a "Revoke and delete" option that first emits N `user_role.revoked` audit rows (one per affected user) then deletes the role; OR "Cancel" which aborts. If the super_admin somehow attempts a raw DELETE on `roles` without first revoking, the `ON DELETE RESTRICT` foreign key on `user_roles.role_id` causes the DB to reject with `23503 foreign_key_violation`; the UI maps this back to a localized error.
5. **Given** the super_admin attempts to create a role with `is_system=true` set somehow (e.g., direct SQL via the Edge Function), **When** the request reaches the server, **Then** the function refuses — `is_system` is reserved for the seed and cannot be set by an in-app create. The check lives in the `mutate_role` Edge Function (or RPC) since RLS alone cannot constrain a single column's value at INSERT time without a column-level CHECK; the `is_system` default is FALSE and the function does not pass through user-supplied values for that column.

### User Story 5 - Assign or revoke a role on a user, with mid-session propagation (Priority: P1)

The super_admin taps an "Assign roles" affordance from the admin home (or a sub-navigation within the super-admin section), opening `AssignRolePage`. Constitution VII enforces that role assignment is data-driven; this story is the only in-app surface that mutates the data. Constitution III enforces that the surface is RLS-gated AND server-validated; this story is also where the `users.view` permission gets exercised by a non-admin admin (a moderator can search users for context but not grant — the grant affordance is super_admin-only).

### User Story 6 - Every mutation through Phase 7 emits an audit-log row (Priority: P1)

The implementation plan §9.4 lists "Role / permission mutations (Phase 7)" as the audit-trigger expansion item. Phase 6 left `user_roles` covered (the only mutation source then was the backfill migration); Phase 7 extends coverage to `roles`, `role_permissions`, and `permissions`. Three INSERT/UPDATE/DELETE trigger pairs attach to these three tables via Phase 4's reusable `log_audit()` function (the Phase 4 R-05 invariant — `log_audit` is unchanged a third time). The action keys are `role.created` / `role.updated` / `role.deleted` (one per `roles` mutation), `role_permission.granted` / `role_permission.revoked` (one per `role_permissions` INSERT/DELETE; no UPDATE because rows are immutable post-insert), and `permission.created` / `permission.updated` / `permission.deleted` (defensive — the v1 catalog is closed but the triggers fire for any future direct-SQL or post-v1 spec). The audit row's `actor_user_id` carries `auth.uid()` for in-app mutations (the super_admin performing the action) and NULL for system mutations (e.g., a future migration that adds a new permission key — the migration runs as `postgres`). The action name is taken verbatim from the trigger's `TG_ARGV[0]` per Phase 5's convention (Phase 4's `log_audit` does NOT append a TG_OP-derived verb — one trigger per legal mutation event with a full action key passed as the first argument).

**Why this priority**: P1 because every mutation surface introduced in US3, US4, US5 depends on this story for compliance with Constitution VII (Dynamic Roles & Permissions audit requirement) and Constitution III (the audit trail IS the after-the-fact security verification). The implementation plan §9.4 lists the audit-trigger expansion under Phase 7 specifically; without this story, the project's audit coverage has gaps. The story is independently testable — the triggers can be installed and tested via direct-SQL mutations (Supabase MCP `execute_sql` simulating the super_admin) before any of the UI stories ship.

### Edge Cases

- **First super_admin is a deploy prerequisite**: The Phase 7 super-admin UI requires at least one `user_roles` row pointing at the `super_admin` role to be useful. Phase 6 deliberately left this state empty (R-16 — Option C). The Phase 7 deploy step documents the one-time SQL: `INSERT INTO public.user_roles (user_id, role_id, granted_by, granted_at) SELECT '<chosen-uuid>', id, NULL, now() FROM public.roles WHERE key='super_admin'`, run via Supabase MCP `execute_sql` running as `postgres`. The chosen UUID is the project owner's `auth.users.id`. This bootstrap is a one-time action, not a recurring operation; once the first super_admin exists, every subsequent super_admin assignment happens through Phase 7's `AssignRolePage` (subject to whatever clarification the user provides on whether super_admin grants are allowed via UI).
- **Super_admin in-app grants require two-step confirmation**: Per Clarifications Session 2026-05-15 Q1, granting `super_admin` via `AssignRolePage` is allowed but gated by a dedicated consequences-dialog AND a typed-phone-match confirmation step before the grant button enables. The two-step gate applies to the `super_admin` grant path only; every other role grant uses the standard single-step confirmation. The first-super_admin bootstrap remains the privileged-SQL recipe (an entry-condition for the very first super_admin); every subsequent super_admin in the project lifetime MAY follow either the in-app two-step path or the same privileged-SQL recipe.
- **Self-revocation of `super_admin` is blocked unconditionally**: Per Clarifications Session 2026-05-15 Q2, a super_admin can NEVER revoke their own `super_admin` role via `AssignRolePage` — regardless of how many other super_admins exist. The block is enforced UI-side (the remove affordance is absent on the super_admin's own `super_admin` row) AND server-side (the `mutate_role` RPC re-checks `auth.uid() != target_user_id` for any super_admin revocation). To leave the super_admin role, a super_admin asks a different super_admin to revoke it. If the project ever ends up with zero super_admins, recovery is the privileged-SQL bootstrap.
- **System role permission edit removing critical access**: A super_admin can revoke `users.approve` from the `admin` role via `RoleEditorPage`. After save, every admin loses the ability to approve accounts. The UI MAY show a confirmation step warning about high-impact edits to system roles, but does NOT block — Constitution III is enforced at the DB layer (RLS still gates correctly), and the super_admin is trusted. The audit trail records the edit so accidental damage is traceable and reversible.
- **Super_admin role permission set is immutable**: Per Clarifications Session 2026-05-15 Q5, the `super_admin` row's permission mapping is locked to the canonical full-catalog set (FR-006 seed). `RoleEditorPage` renders the permission checklist as read-only when the active role's `key` is `super_admin`; the `mutate_role` RPC additionally rejects any update that would change the super_admin permission set with `42501`. The `display_name` and `description` columns on the `super_admin` row ARE editable so super_admin can add localized labels. The rule's purpose: super_admin's identity-as-superuser depends on holding the full catalog; emptying the permission set has no in-app recovery path. Future specs that add new permission keys are responsible for INSERTing the new key into `role_permissions` for the `super_admin` role in the same migration (Phase 6 assumption) — at that point the "canonical full-catalog set" expands and the immutability check compares against the new canonical set.
- **Mutation entry point is a SECURITY DEFINER SQL RPC**: Per Clarifications Session 2026-05-15 Q3, the atomic role+permissions mutation entry point is a Postgres function (`public.mutate_role(...)`) applied via Supabase MCP `apply_migration`, NOT a Supabase Edge Function. The function re-checks `current_user_has_permission('roles.create')` / `roles.update` / `roles.delete` / `permissions.manage` server-side; the audit-row sequence is emitted automatically by FR-001/FR-002/FR-003 triggers firing inside the function's implicit transaction. The Edge Function path is deferred to a later phase that needs an Edge Function for a non-database reason. The companion user-role assignment RPCs (`assign_role_to_user`, `revoke_role_from_user`) follow the same pattern and also re-check `permissions.manage` plus the FR-009-Q2 self-revocation guard.
- **Permission delta atomicity**: Saving a role's permission edits via two separate SQL transactions (one INSERT per added permission, one DELETE per removed permission) could leave a role in an intermediate state if the second transaction fails. The Phase 7 mutation surface MUST execute the entire delta in one transaction (whether via the Edge Function, RPC, or a single multi-statement SQL block from the Flutter data layer). Per-row INSERT/DELETE on `role_permissions` outside an atomic envelope is forbidden in Phase 7.
- **Concurrent edits to the same role**: If two super_admins open `RoleEditorPage` for the same role and both save, optimistic locking via `roles.updated_at` prevents silent overwrite per Clarifications Session 2026-05-15 Q4. Whoever saves first wins (their `updated_at` matched the stored value); whoever saves second receives a `40001 serialization_failure` from `mutate_role`, sees a localized "this role was changed by another super_admin — reload and re-apply your edits" message, and the editor reloads the role's current state. The losing super_admin's pending edits are dropped (no draft persistence in v1; if useful, a future spec can add it). Concurrent edits on `role_permissions` alone (without a `roles` row update) are similarly guarded because every `mutate_role` `op='update'` rev's `roles.updated_at` via the `set_updated_at` trigger. Concurrent edits on `user_roles` (assign/revoke) are NOT subject to optimistic locking: the operations are single-row INSERTs/DELETEs gated by `UNIQUE(user_id, role_id)`, and the audit trail records every grant/revoke independently — a race between two super_admins granting then revoking the same role to the same user produces a coherent audit story regardless of ordering.
- **Cascade delete on `roles`**: `role_permissions.role_id ON DELETE CASCADE` (Phase 6 FR-005) means deleting a role automatically removes its permission mappings. The cascade INSERTs N `role_permission.revoked` audit rows (one per cascaded delete, via the new Phase 7 trigger). `user_roles.role_id ON DELETE RESTRICT` (Phase 6 FR-007) means a role with users still holding it CANNOT be deleted; the UI mediates this by either (a) refusing delete and listing affected users, or (b) revoking first then deleting (US4 acceptance scenario 4).
- **Anon client sees nothing on Phase 7 mutation surfaces**: Anon clients cannot invoke the `mutate_role` Edge Function (or RPC) — both gate on `auth.uid()`. The RLS write policies introduced in Phase 7 also reject anon writes. The Phase 4 RLS-default-block invariant is preserved.
- **Hardcoded role checks remain forbidden**: Per Constitution VII and Phase 6 FR-019, no Phase 7 feature code MUST contain `user.role == 'super_admin'` or similar. Every gate goes through `PermissionChecker.has(<key>)` referencing `PermissionKeys` constants. The new super-admin tile visibility uses `PermissionChecker.any({rolesView, rolesCreate, rolesUpdate, rolesDelete, permissionsManage})` or a `PermissionKeys.superAdminCategoryKeys` constant added to Phase 6's `permission_keys.dart`.
- **`PermissionChecker` cache propagation latency**: Per Phase 6 FR-015, the affected user's cache refreshes on auth-state token-refresh OR foreground resume. There is no real-time push. In practice the latency is "next foreground resume" for a backgrounded app, "immediately" for a session that triggers a token refresh, and "never until sign-in" for a fully signed-out session. Phase 22 (push + Realtime) MAY add a fourth observation point that subscribes to `user_roles` changes for the affected user (project memory `project_phase22_perm_cache_revisit.md` tracks the revisit).
- **Domain layer stays Supabase-free**: New code in `lib/features/super_admin/` MUST follow Constitution IX — anything in `domain/` imports nothing from `package:supabase_flutter`. The `data/` layer of `lib/features/super_admin/` is the only place Supabase types appear.
- **Localization for new strings**: Every user-visible string introduced in Phase 7 (page titles, button labels, validation errors, confirmation dialogs, audit-action descriptions if surfaced) MUST exist in both `app_ar.arb` and `app_en.arb` per Constitution V. Phase 3's localization gate is binding. The category headings on `RoleEditorPage` use the `permissionCategory<Capitalized>` ARB key set per Clarifications Session 2026-05-15 Q6 (12 keys for Phase 6's seeded categories: `permissionCategoryUsers`, `permissionCategoryListings`, `permissionCategoryRoles`, `permissionCategoryLocations`, `permissionCategoryCurrencies`, `permissionCategoryAds`, `permissionCategoryReports`, `permissionCategoryAgencies`, `permissionCategorySettings`, `permissionCategoryAudit`, `permissionCategoryInquiries`, `permissionCategoryPermissions`). Future specs that introduce new permission categories add the corresponding ARB key in the same PR.
- **Theme tokens for new widgets**: Every color, font size, spacing, radius used by the new pages MUST come from `Theme.of(context)` or the project's design-token API per Constitution VI. No inline hex literals, no raw `TextStyle(...)`.
- **Idempotent migrations**: Every Phase 7 migration MUST be safe to re-apply against the remote Supabase project per the project memory `project_supabase_mcp_apply_migration.md`. Triggers use `DROP TRIGGER IF EXISTS … CREATE TRIGGER`; new policies use `CREATE POLICY IF NOT EXISTS` where supported (Postgres 15+) or are gated by an `EXISTS` check; the audit-trigger functions use `CREATE OR REPLACE FUNCTION`. Edge Function deploy via Supabase CLI is similarly idempotent (re-deploy replaces).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST add audit triggers on `public.roles` covering INSERT, UPDATE, DELETE, reusing Phase 4's `log_audit()` function. Trigger names: `trg_roles_audit_created`, `trg_roles_audit_updated`, `trg_roles_audit_deleted`. Action keys: `role.created`, `role.updated`, `role.deleted`. Each trigger passes `TG_ARGV = (<action key>, '*', 'id')` per Phase 5 / Phase 6 convention — the action key is the full string, all columns captured into `before_state`/`after_state`, and the target id is the role's own `id`.
- **FR-002**: System MUST add audit triggers on `public.role_permissions` covering INSERT and DELETE (no UPDATE — Phase 6 FR-005 makes rows effectively immutable). Trigger names: `trg_role_permissions_audit_granted`, `trg_role_permissions_audit_revoked`. Action keys: `role_permission.granted`, `role_permission.revoked`. Trigger arguments: `(<action key>, '*', 'role_id')` — `target_id` references the role (the operationally-meaningful target; the permission_id can be derived from `before_state`/`after_state` if needed).
- **FR-003**: System MUST add audit triggers on `public.permissions` covering INSERT, UPDATE, DELETE — defensive coverage for any future migration that mutates the catalog (the v1 catalog is closed but the triggers fire for direct-SQL or post-v1 spec changes). Trigger names: `trg_permissions_audit_created`, `trg_permissions_audit_updated`, `trg_permissions_audit_deleted`. Action keys: `permission.created`, `permission.updated`, `permission.deleted`. Trigger arguments: `(<action key>, '*', 'id')`.
- **FR-004**: System MUST add INSERT, UPDATE, DELETE RLS policies on `public.roles` gating the writes by `current_user_has_permission(<appropriate key>)`. Specifically: INSERT requires `roles.create`; UPDATE requires `roles.update`; DELETE requires `roles.delete`. The `enforce_role_system_immutability` trigger (Phase 6 FR-020) continues to fire and provides the defense-in-depth that blocks DELETE-on-system-row even if a permission-holder is somehow granted `roles.delete`.
- **FR-005**: System MUST add INSERT and DELETE RLS policies on `public.role_permissions` gating writes by `current_user_has_permission('permissions.manage')`. No UPDATE policy — rows are immutable.
- **FR-006**: System MUST add INSERT and DELETE RLS policies on `public.user_roles` gating writes by `current_user_has_permission('permissions.manage')`. The DB-side RLS policy is the authoritative gate; the Phase 7 `assign_role_to_user` / `revoke_role_from_user` RPCs (FR-009) additionally re-check the same key inside their bodies as defense-in-depth and to enable structured error-code emission. No UPDATE policy on `user_roles` — rows are immutable post-insert (Phase 6 R-15 invariant preserved).
- **FR-007**: System MUST keep the four catalog tables' READ posture from Phase 6 (FR-009) intact. Authenticated-read on `roles`, `permissions`, `role_permissions`; self-read + `users.view`-gated cross-user read on `user_roles`. No Phase 7 migration edits a Phase 6 policy file; new write policies live in new files (`supabase/policies/roles_phase7_write.sql`, `role_permissions_phase7_write.sql`, `user_roles_phase7_write.sql`).
- **FR-008**: System MUST ship a server-side atomic mutation entry point for role + role_permissions bundle edits as a **SECURITY DEFINER SQL RPC** named `public.mutate_role` (Clarifications Session 2026-05-15 Q3). Signature: `public.mutate_role(op TEXT, role_id UUID, role_key TEXT, display_name JSONB, description TEXT, permission_keys TEXT[], expected_updated_at TIMESTAMPTZ) RETURNS JSONB` — applied via Supabase MCP `apply_migration`, `LANGUAGE plpgsql SECURITY DEFINER SET search_path = public, auth`. The function:
  - Accepts arguments equivalent to: `op` (`'create' | 'update' | 'delete'`), `role_id` (for update/delete; NULL for create), `role_key` (for create; the column-level enforcement that `is_system=false` is hard-coded inside the function, NOT client-supplied), `display_name` (JSONB, both locales required for create / update where display_name is being changed), `description` (text, nullable), `permission_keys` (the full target set of permission keys the role should grant after the operation — the function computes the delta against the current `role_permissions` rows), `expected_updated_at` (the `roles.updated_at` value the client captured when `RoleEditorPage` opened; required for `op='update'` and `op='delete'`, ignored for `op='create'`).
  - Re-checks server-side: caller's session holds `roles.create` (for `op='create'`), `roles.update` (for `op='update'`), `roles.delete` (for `op='delete'`), AND `permissions.manage` (for any permission-set delta on create or update) — via `current_user_has_permission(<key>)`. Re-check failure raises `42501`.
  - Super_admin permission-set immutability check (Clarifications Session 2026-05-15 Q5): for `op='update'` where `role_id` references the row with `key='super_admin'`, the function compares the supplied `permission_keys` array against the role's current permission set (via `SELECT array_agg(p.key) FROM role_permissions rp JOIN permissions p ON p.id=rp.permission_id WHERE rp.role_id = role_id`). If the two sets differ in any element, the function raises `42501` with a structured error code mapped to the localized "the super_admin role's permission set is immutable" message. `display_name` and `description` edits on the `super_admin` row are allowed. For `op='delete'` where `role_id` references `super_admin`, the existing system-role-immutability trigger (Phase 6 FR-020) already raises `42501` before the function's check fires. For `op='create'` with `role_key='super_admin'`, the `UNIQUE(roles.key)` constraint already blocks the duplicate.
  - Optimistic-locking check (Clarifications Session 2026-05-15 Q4): for `op='update'` and `op='delete'`, the function compares the current `SELECT updated_at FROM roles WHERE id = role_id` against the caller's `expected_updated_at` argument. If the two values differ, the function raises `SQLSTATE 40001` (`serialization_failure`) with a structured error message the Flutter client maps to the localized "this role was changed by another super_admin — reload and re-apply your edits" message. No partial work is committed (the check fires before any write). For `op='create'`, the check is skipped because no existing row exists.
  - Executes ONE implicit transaction (Postgres functions run in a transaction by default): the `roles` row mutation AND the `role_permissions` delta (INSERTs for newly-included keys, DELETEs for newly-excluded keys, plus the row-level INSERT/UPDATE/DELETE on the `roles` row itself). The Phase 4 `set_updated_at` trigger fires on the `roles` UPDATE, advancing `updated_at` — which any concurrent caller's `expected_updated_at` will now mismatch.
  - On failure (RLS rejection, trigger violation, unique-key conflict, system-role-immutability, optimistic-locking conflict), the entire transaction rolls back and the function raises with a structured `SQLSTATE` the Flutter client can pattern-match.
  - Audit-trail behavior: the FR-001 / FR-002 / FR-003 triggers fire automatically for each mutation in the transaction, producing the correct sequence of `role.*` / `role_permission.*` rows. The function does NOT call `log_audit` directly; it relies on the table triggers.
  - The Edge Function path named in `docs/IMPLEMENTATION_PLAN.md §Phase 7` is **deferred** to a later phase that needs Edge-Function infrastructure for a non-database reason. This spec records the deviation per Constitution XII (No Hidden Product Decisions); the implementation plan's "Direct SQL also allowed via roles.create RLS" sentence acknowledges this path.
- **FR-009**: System MUST ship two SECURITY DEFINER SQL RPCs for the user-role assignment surface: `public.assign_role_to_user(target_user_id UUID, target_role_id UUID, confirmation_token TEXT) RETURNS JSONB` and `public.revoke_role_from_user(target_user_id UUID, target_role_id UUID) RETURNS JSONB`. Both functions:
  - Re-check `current_user_has_permission('permissions.manage')` server-side; raise `42501` on failure.
  - **`assign_role_to_user` only** — apply the Clarifications Q1 two-step-confirmation server-side enforcement: when `target_role_id` references the `super_admin` role, the function additionally requires a non-NULL `confirmation_token` argument carrying the typed-confirmation value; the function compares it against the target user's `profiles.phone` OR `profiles.username` and rejects with `42501` + a structured error code if mismatched (or NULL). For non-`super_admin` role grants, `confirmation_token` is ignored. (The UI gates this client-side; the server gate is defense-in-depth so a crafted client cannot bypass the two-step.)

  - Execute ONE atomic operation: the `user_roles` INSERT (assign) or DELETE (revoke), gated by the RLS write policies from FR-006. Phase 6's `trg_user_roles_audit_granted` / `trg_user_roles_audit_revoked` triggers emit the audit rows automatically.

### Key Entities

- **Super-admin entry point**: The `RolesListPage` is the entry into the Phase 7 surface, gated by the union of the five `roles.*` and `permissions.manage` permission keys. Reached from the Phase 6 admin home page via a new tile.
- **Role row mutation event**: An INSERT/UPDATE/DELETE on `public.roles`. Each event produces exactly one `audit_logs` row via the new Phase 7 trigger.
- **Role-permission mapping event**: An INSERT/DELETE on `public.role_permissions`. Each event produces exactly one `audit_logs` row via the new Phase 7 trigger. UPDATEs are not produced — the row is composite-keyed and immutable.
- **User-role assignment event**: An INSERT/DELETE on `public.user_roles` from the in-app surface. Phase 6's existing triggers cover the audit. Phase 7 adds the in-app mutation surface but does NOT add or modify the audit triggers — the existing trigger names and action keys are preserved (`user_role.granted`, `user_role.revoked`).
- **Atomic role mutation entry point**: The Edge Function `mutate_role` (or the SECURITY DEFINER RPC equivalent). Bundles role row mutation + role-permissions delta into one transaction; re-checks permissions server-side; produces the correct audit-row sequence.
- **Mid-session propagation event**: The `PermissionChecker.refresh()` call triggered on a lifecycle observation point (auth-state listener event OR foreground resume) for an affected user. Inherited from Phase 6 FR-015 — Phase 7 introduces no new observation point.
