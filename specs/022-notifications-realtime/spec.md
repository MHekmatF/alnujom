# Feature Specification: Push Notifications + Supabase Realtime Signals

**Feature Branch**: `022-notifications-realtime`
**Created**: 2026-06-02
**Status**: Draft
**Input**: Phase 22 — Push notifications + Supabase Realtime signals, from `docs/IMPLEMENTATION_PLAN.md` (§ "Phase 22 — Push notifications + Supabase Realtime signals", plus the schema in §6.2, RLS posture in §6.4, the auth/transition flows in §6.6–§6.7, the permission model in §9, and cross-cutting [ADR-0001 — Secrets & PII storage](../../docs/decisions/0001-secrets-and-pii-storage.md))

> **Scope note**: Phase 22 introduces the **notification and live-signal layer** that sits on top of every flow already built — it tells a user, on their phone, that something happened to them (their account was approved or rejected, a listing of theirs was approved or rejected, someone inquired about one of their listings, or they were invited to an agency), and it makes the admin dashboard's live counters move on their own. The phase ships exactly: **(a) a notification fan-out path** hung off the existing server-side transitions (the Phase 5 account-approval decision, the Phase 12 listing approve/reject, the Phase 16 inquiry record, and the Phase 19 agency-invitation RPC) that resolves the correct recipient from the underlying row, writes one history record, and dispatches device push to that recipient's registered devices — emitting exactly once per qualifying transition and never on a non-qualifying write; **(b) a provider-agnostic notification core** in which in-app delivery, the notification center, and Realtime ALWAYS work, and device push is delivered through a **pluggable push provider** whose v1 adapter is Firebase Cloud Messaging (FCM) — so that if the Firebase project proves unreachable or unacceptable from Syria (the plan's flagged sanction risk), the app **degrades gracefully** to in-app + Realtime + foreground refresh with **no user-visible error and no code change**, only configuration (the user-resolved "provider-agnostic core, FCM pluggable" decision — see Clarifications); **(c) device push-token registration** on login (and token-refresh) with deregistration on logout, associating tokens with the user so fan-out targets the right devices (a user may have several); **(d) a server-side per-user notifications history store** backing an **in-app notification center** — newest-first list, unread badge/count, mark-read (single + all), deep-link-on-tap, history persisting across sessions / devices / reinstall (the user-resolved "server-side notifications table" decision — see Clarifications; this adds a `notifications` table beyond the plan's §6.2 list, which named only `notification_tokens`); **(e) localized notification content** — the in-app center renders copy in the viewer's *active* locale (from a notification type + structured params), while OS-tray push text is rendered server-side in the **recipient's stored preferred language** (Arabic-first default), so notifications honor Principle V on both surfaces; **(f) Supabase Realtime for admin counters** — the admin dashboard's pending-listing counter (driven by `listings` status changes) and reports counters (new + resolved on `reports`) update in near-real-time with no manual refresh, gated to admins and reconciling correct counts on reconnect; **(g) a Realtime permission-refresh signal** — a subscription on the signed-in user's own `user_roles` rows that calls `PermissionChecker.refresh()` on change, adding the fourth observation point that Phase 6 explicitly deferred to Phase 22 (so a granted/revoked role re-shapes the user's UI without re-login); **(h) security at both ends** — the FCM service-account JSON is a single Supabase Vault secret (`fcm_service_account`) read only server-side by the fan-out path (never committed, never shipped to the client; per ADR-0001), the `notification_tokens` and `notifications` tables are **self-only RLS** (a user reads/writes only their own rows), fan-out (which reads many users' tokens and writes many users' history) runs through a controlled elevated-privilege server path rather than client writes, and a client cannot forge a notification to another user, read/write another user's tokens, or read another user's notifications at the wire level; **(i) preference honoring** — the existing per-user global `user_preferences.notifications_enabled` flag is respected (when off, the user is not actively pushed/alerted), reusing the Phase 5/Phase 9 preference rather than inventing per-category preferences; **(j) the localization + theming layer** — the notification center and every affordance (list, unread badge, empty / loading / error states, a single item) flow through `AppLocalizations` with `ar` + `en` entries and render correctly in all four (light / dark) × (Arabic RTL / English LTR) combinations using Phase 2 tokens. Phase 22 honors Principle I (this spec precedes implementation), Principle III (Vault secret; self-only RLS on both new tables; fan-out through a controlled server path; checks at both ends; admin Realtime gated server-side), Principle V (all UI strings + notification copy localized `ar` / `en`, push text in the recipient's preferred language), Principle VI (themed via Phase 2 tokens, four-combination correct), Principle IX (the domain layer stays provider-agnostic — no push-SDK import in `domain/`; the FCM adapter lives only in the data layer), and Principle XI (Android-only; any manifest / Google-services configuration is Android-only and the app still builds and runs with push disabled). Phase 22 does **NOT** add user-facing live data beyond the admin counters + permission refresh (a publisher's My Listings does not stream status live in this phase — it keeps the established read/refresh posture); does **NOT** add Realtime-driven ad liveness (Phase 21 ads remain read/refresh; the Phase 21 spec's "Phase 22 owns Realtime" note refers to this layer existing, not to ads becoming live this phase); does **NOT** introduce per-category notification preferences, delivery/read analytics, notification grouping/digests, web push, or iOS push; does **NOT** change the §9.1 permission catalog or add a new permission key (the notification center is available to every signed-in user; admin counters reuse existing admin permissions); does **NOT** add a new audited admin action (the underlying transitions are already audit-logged in their own phases — §9.4 does not list notification fan-out); and does **NOT** alter any existing business-data table beyond enabling Realtime on `listings` / `reports` / `user_roles`.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — A user is told, in-app, what happened to them (Priority: P1)

A signed-in user goes about their life in the app. When an admin approves or rejects their account, when one of their listings is approved or rejected, when someone sends an inquiry about one of their listings, or when they are invited to join an agency, a notification appears for them: a new entry lands in their notification center and the unread badge increments. They open the notification center, see their notifications newest-first with clear read/unread state, and tap one to be taken straight to the relevant screen — the approved listing's details, the rejected listing in My Listings (with its reason and a resubmit affordance), the inquiry, the agency invitation's accept/decline screen, or home for an approved account. Tapping marks the item read and the badge drops. This works whether or not device push is available.

**Why this priority**: P1 because the in-app notification + history center is the foundation that delivers value with **zero dependency on the sanctions-risky push channel** — it is the slice that always works. The plan's first two acceptance criteria ("Approving a user sends them 'Account approved'… tapping opens the home screen"; "Approving a listing sends the publisher 'Listing approved'; opens listing details") describe exactly this recipient-resolution + deep-link behavior, and the plan's frontend deliverable centers on `lib/features/notifications/` with "deep links to the relevant page" and an "in-app notification center (history of received notifications)." Nothing about push (US2) or live counters (US3) is required before a user can be told something happened to them and be routed to it.

**Independent Test**: Sign in as a regular user on the reference device. From a second (admin) session, approve the user's account → confirm a notification appears in the user's center and the unread badge increments; tap it → confirm it opens home and marks read. Submit + have the admin approve one of the user's listings → confirm a "listing approved" notification deep-links to that listing's details. Have the admin reject another listing with a reason → confirm the notification deep-links to My Listings showing the reason + resubmit. From a third account, send an inquiry on the user's listing → confirm the publisher gets an "inquiry received" notification deep-linking to the inquiry. From an agency admin, invite the user to an agency → confirm an "agency invitation" notification deep-links to the accept/decline screen. Confirm history persists after logout/login and on a fresh install of the same account; confirm mark-all-read clears the badge.

**Acceptance Scenarios**:

1. **Given** a signed-in user whose account an admin approves, **When** the approval completes, **Then** exactly one "account approved" notification is recorded for that user, the unread count increments, and tapping it opens home and marks it read.
2. **Given** a signed-in user whose account an admin rejects, **When** the rejection completes, **Then** an "account rejected" notification is recorded and tapping it opens the rejection screen (with the reason surfaced where the existing screen shows it).
3. **Given** a publisher whose listing an admin approves, **When** the approval completes, **Then** a "listing approved" notification is recorded and tapping it opens that listing's details.
4. **Given** a publisher whose listing an admin rejects with a reason, **When** the rejection completes, **Then** a "listing rejected" notification is recorded and tapping it opens My Listings at that listing with its rejection reason and a resubmit affordance.
5. **Given** a publisher whose listing receives an inquiry, **When** the inquiry is submitted (by an anonymous or signed-in sender), **Then** an "inquiry received" notification is recorded for the publisher and tapping it opens the relevant inquiry.
6. **Given** a user invited to an agency, **When** the invitation is created, **Then** an "agency invitation" notification is recorded for the invitee and tapping it opens the agency accept/decline screen.
7. **Given** any notification, **When** the user opens the notification center, **Then** notifications are listed newest-first with read/unread state and an unread count; **and When** the user marks one (or all) read, **Then** the unread count updates accordingly.
8. **Given** a user with notifications in history, **When** they log out and back in (or reinstall and sign in on a new device), **Then** their notification history is present (server-side persistence), not lost.

### User Story 2 — Notifications reach the phone even when the app is closed (Priority: P1)

A user who isn't currently in the app still finds out when something happens. After they log in, their device is registered to receive push. When one of the qualifying events fires, a system push notification arrives on their phone — even if the app is backgrounded or fully closed — and tapping it opens the app at the same destination the in-app item would (the approved listing, the rejected listing in My Listings, the inquiry, the invitation, or home). The push text appears in the language the user prefers. Crucially, push is a **pluggable** channel: if the push provider isn't configured or is unreachable (the Firebase-from-Syria sanction risk the plan flags), the user experiences no error and no broken screen — they simply get their notifications in-app the next time they open the app, and live counters/Realtime still work. When the user logs out, that device stops receiving push.

**Why this priority**: P1 because background/closed-app reach is the headline capability of the phase ("FCM push for status changes") and the plan's manual verification is explicitly a two-device push test ("approve on B → push received on A"). It builds on US1's recipient resolution + deep-link map. It is co-equal P1 with US1 because the plan treats push as a primary deliverable — but the **provider-agnostic** decision (see Clarifications) makes US1 viable on its own if push must be deferred, which is why US1, not US2, is the always-on foundation.

**Independent Test**: On device A signed in as a user with push enabled, confirm a push token is registered after login (inspect the token store). Background the app. From device B (admin), approve device A's account → confirm a system push arrives on A with localized text; tap it → confirm the app opens to home. Fully close the app on A and repeat with a listing approval → confirm the cold-start tap deep-links to the listing. Switch A's preferred language and confirm subsequent push text language follows it. Log out on A → confirm A's token is removed and A stops receiving push while a second still-logged-in device keeps receiving it. Then **disable/unconfigure the push provider** and repeat US1's flows → confirm every notification still arrives in-app with no error, no crash, and no broken UI (the documented sanctions fallback).

**Acceptance Scenarios**:

1. **Given** a user who logs in on a device with push enabled, **When** login completes, **Then** the device's push token is registered against that user; **and When** the push token later refreshes, **Then** the registration is updated.
2. **Given** a registered device that is backgrounded or fully closed, **When** a qualifying event fires for that user, **Then** a system push notification is delivered to the device with content in the user's preferred language.
3. **Given** a delivered push, **When** the user taps it (app backgrounded OR cold-started from closed), **Then** the app opens and deep-links to the same destination as the corresponding in-app notification (FR-007's map).
4. **Given** the push provider is NOT configured or is unreachable, **When** qualifying events fire, **Then** the app continues to deliver notifications in-app and via the notification center with NO user-visible error, NO crash, and NO broken state — push is simply skipped (the sanctions fallback), and enabling the provider later requires only configuration, not a client code change.
5. **Given** a user logs out on one device, **When** logout completes, **Then** that device's push token is deregistered and it stops receiving push, while the user's other still-logged-in devices keep receiving push.
6. **Given** a foreground app receiving a push, **When** it arrives, **Then** it surfaces in-app (the center/badge updates) without a jarring duplicate system banner; **and Given** a background/closed app, **Then** it surfaces as a system notification.

### User Story 3 — Admin counters move on their own (Priority: P1)

An admin watching the dashboard sees the live operational numbers change without pressing refresh. When a publisher submits a listing for review, the pending-listing counter ticks up; when a listing is approved or rejected, it ticks down. When a new report is filed, the reports counter increments; when a report is resolved, it updates. If the admin's connection drops and recovers, the counters reconcile to the correct values rather than drifting. Only admins receive these live signals.

**Why this priority**: P1 because "Supabase Realtime for admin counters" is half the phase's stated goal and the subject of the plan's first verification ("submit on A, observe Realtime counter bump on B (admin)"). The plan scopes Realtime explicitly to `listings` (status changes) and `reports` (new + resolved) "for admin clients." It is independent of the notification stories — counters can go live with or without push.

**Independent Test**: Open the admin dashboard on device B as an admin. From device A, submit a listing for review → confirm B's pending-listing counter increments within a couple of seconds with no manual refresh; approve it on B (or another admin) → confirm it decrements. File a report from device A → confirm B's reports counter increments; resolve it → confirm it updates. Kill B's network briefly and restore it → confirm the counters reconcile to correct values. Confirm a non-admin client does not receive these admin counter signals.

**Acceptance Scenarios**:

1. **Given** an admin viewing the dashboard, **When** a publisher submits a listing for review, **Then** the pending-listing counter increments in near-real-time without manual refresh.
2. **Given** an admin viewing the dashboard, **When** a pending listing is approved or rejected, **Then** the pending-listing counter decrements accordingly.
3. **Given** an admin viewing the dashboard, **When** a new report is filed, **Then** the reports counter increments; **and When** a report is resolved, **Then** the reports counter updates.
4. **Given** an admin whose Realtime connection drops and reconnects, **When** it recovers, **Then** the counters reconcile to the correct current values (no missed-event drift).
5. **Given** a non-admin client, **When** these admin counter changes occur, **Then** it does not receive or act on the admin counter signals (the live admin channel is gated to admins; RLS still governs what any channel can carry).

### User Story 4 — A user's permissions refresh live when their roles change (Priority: P2)

A signed-in user whose roles a super-admin changes sees their in-app capabilities update without having to log out and back in. If they are granted a role that carries a new permission, the gated UI for that permission becomes available; if a role is revoked, the gated UI disappears — on the next live refresh, not only at the next cold login.

**Why this priority**: P2 because it is the Phase 6 follow-up that was explicitly deferred to Phase 22 (the PermissionChecker cache-refresh strategy was chosen at Phase 6 time as a three-observation-point model precisely *because* Realtime was deferred to this phase). It is a real correctness/freshness improvement layered on the Realtime capability US3 introduces, but it is not required for the notification or counter stories to deliver value, so it sits below them.

**Independent Test**: Sign in as a test user on device A and confirm a permission-gated surface (e.g., an admin section) is hidden. From a super-admin on device B, grant device A's user a role carrying that permission → confirm the gated surface becomes reachable on A on the next live refresh without A logging out. Revoke the role → confirm the surface disappears on A's next live refresh. Confirm this rides the Phase 6 `PermissionChecker.refresh()` path (now with a fourth, Realtime-driven observation point) and that the existing three observation points still function.

**Acceptance Scenarios**:

1. **Given** a signed-in user, **When** a super-admin grants them a role carrying a new permission, **Then** the user's effective permissions refresh and the permission-gated UI becomes available without requiring re-login.
2. **Given** a signed-in user, **When** a super-admin revokes a role, **Then** the permission-gated UI is removed on the next live refresh.
3. **Given** the live permission refresh, **When** it is implemented, **Then** it adds a fourth observation point (a subscription on the user's own role rows) to the Phase 6 three-point strategy — it does not remove or break the existing auth-state-listener, app-foreground-resume, or explicit-`refreshSession()` points.

### User Story 5 — Notifications and live signals are enforced at the data layer, not just the UI (Priority: P2)

The product MUST guarantee that notifications cannot be forged or read across users, that push tokens are owned by their user, and that the push-provider credential never leaks. A user can read and write only their own push tokens and only their own notifications; a user cannot create a notification for someone else; the fan-out that reads many users' tokens and writes many users' history runs only through a controlled server-side path with elevated privilege; the FCM service-account credential lives only in Supabase Vault and is read only server-side, never committed to the repo and never shipped to the client; and the admin live-counter signals are gated to admins.

**Why this priority**: P2 because Constitution Principle III ("checks at both ends") and ADR-0001 (the FCM service account is a Vault secret) make a UI-only or trust-the-client posture insufficient, and the §6.4 matrix mandates self-only access to user-private tables. It is a hard correctness/security requirement layered over the P1 delivery behaviors.

**Independent Test**: From user X's session, attempt at the wire level to: read user Y's notifications, insert a notification for user Y, read or write user Y's push token. Confirm each is denied. Confirm a client cannot perform the cross-user fan-out write directly (it goes only through the controlled server path). Confirm the FCM service-account JSON is absent from the repository and from the built client bundle (grep / artifact inspection) and exists only as a Vault secret read server-side. Confirm a non-admin does not receive the admin counter channel.

**Acceptance Scenarios**:

1. **Given** user X, **When** X attempts to read or write user Y's `notifications` or `notification_tokens` rows at the wire level, **Then** every such attempt is denied by RLS (self-only access).
2. **Given** user X, **When** X attempts to insert a notification targeting user Y directly, **Then** it is denied — notification rows are written only by the controlled fan-out path (elevated-privilege server side), not by arbitrary client inserts.
3. **Given** the FCM service-account credential, **When** the repository and the built client artifact are inspected, **Then** the credential is NOT present in either — it exists only as the Vault secret `fcm_service_account`, read only server-side by the fan-out path (ADR-0001).
4. **Given** the admin live-counter signals, **When** a non-admin client connects, **Then** it does not receive admin counter data (the admin Realtime surface is gated server-side; RLS governs what any subscription can read).

### User Story 6 — The notification surface is fully localized and themed in every combination (Priority: P3)

Every user reading notifications gets a correct, readable experience whether the app is in Arabic (RTL) or English (LTR), in light or dark theme: a localized notification center (list, unread badge, empty / loading / error states, a single item), localized notification copy, direction-aware layout, and design-token styling — and the OS-tray push text appears in the language the user prefers.

**Why this priority**: P3 because localization and theming are cross-cutting quality gates the plan calls out for every phase (Principles V and VI); they refine the experience delivered by the P1/P2 stories rather than being a standalone capability. Notification *content* localization is called out specifically because, unlike most UI, push text is rendered server-side and so must be localized to the recipient's stored language at send time.

**Independent Test**: Open the notification center with several notifications of different types and cycle the four combinations — (light, ar), (dark, ar), (light, en), (dark, en) — on the reference Infinix Note 8 and a 412 dp emulator profile; confirm every string is localized (no raw literals), the list / badge / empty / error states lay out correctly RTL and LTR, and colors/typography/spacing come from Phase 2 tokens (no clipped text, no mis-mirrored icons, no inline hex). Set a user's preferred language to Arabic and trigger a push → confirm the tray text is Arabic; switch to English and confirm the tray text is English.

**Acceptance Scenarios**:

1. **Given** the app locale is Arabic, **When** the notification center and any notification affordance render, **Then** all strings appear in Arabic and the layout is RTL-correct (list rows, badge, directional icons mirror appropriately).
2. **Given** the app locale is English, **When** the same surfaces render, **Then** all strings appear in English and the layout is LTR-correct.
3. **Given** light and dark themes, **When** the surfaces render in each, **Then** all colors, typography, spacing, and elevation come from the Phase 2 design tokens with no inline hex / raw font size / ad-hoc padding.
4. **Given** a recipient whose preferred language is Arabic (or English), **When** a push notification is sent, **Then** its tray title/body are rendered in that language; **and Given** the in-app center, **Then** its copy follows the viewer's *active* locale (re-rendering when the user toggles locale), defaulting to Arabic when no preference is set.

### Edge Cases

- **No registered token / push disabled / provider unreachable**: the user still receives every notification in-app (center + badge); push is skipped silently — no error, no crash, no broken UI. This is the plan's documented sanctions fallback and MUST hold even when the app ships with no Firebase configuration at all.
- **Multiple devices for one user**: all the user's registered devices receive push; logging out on one device removes only that device's token, leaving the others registered.
- **Push token refresh**: when the OS rotates the device push token, the app re-registers the new token (and the stale one is superseded), so delivery keeps working.
- **App fully closed at delivery time**: tapping the push cold-starts the app and still deep-links to the correct destination (the deep link survives a cold start).
- **Deep-link target no longer resolves** (e.g., the linked listing was deleted or is no longer public, the inquiry was removed, the agency was deleted): tapping the notification MUST fail gracefully — a localized "content unavailable" message or a safe fallback screen — never a crash or a broken page; the notification is still marked read.
- **Recipient offline when the event fires**: the push provider queues delivery per its own semantics; regardless, the in-app history record is present the next time the user opens the app, and Realtime counters reconcile on reconnect — no event is silently lost from the user's history.
- **Duplicate / retried transition**: a single qualifying transition produces exactly one notification (and at most one push per registered device); retries or non-qualifying writes (e.g., editing a listing that is already approved) MUST NOT generate spurious notifications.
- **`notifications_enabled` is off**: the user is not pushed or actively alerted, but the notification history row is **still written silently** — so the user sees what happened (as unread) when they next open the center; the flag governs active *interruption*, not historical *visibility*. There is no new per-category preference UI in this phase.
- **Recipient has no preferred language set**: push text defaults to Arabic (Arabic-first, Principle V); the in-app center always follows the device's active locale.
- **Admin Realtime connection drop**: on reconnect the counters reconcile to correct current values from a fresh read — they do not drift from missed events.
- **Permission revoked mid-session**: the gated UI is removed on the next live refresh (the new fourth observation point) or, failing the live signal, at the next existing observation point (foreground resume / explicit refresh / next login) — access never silently persists past a cold restart.
- **Agency invitation to a user who later declines or is removed**: the invitation notification still records the invite event; subsequent state is reflected when the user opens the agency hub (this phase notifies the invite; it does not add new agency-state notifications beyond the invitation).
- **Anonymous inquiry sender**: the notification recipient is always the listing's publisher; the anonymous sender receives nothing (they have no account to notify).
- **Self-acting admin**: if the same person is both the actor and the recipient of an event (rare — e.g., an admin approving their own pending account in a test), a notification is still recorded for the recipient identity; no special suppression is required in v1.
- **Very large notification history**: the notification center read MUST be bounded/paginated — the client MUST NOT fetch a user's entire notification history at once as it grows.
- **Firebase project blocked by sanctions at release**: the phase ships with push behind the pluggable provider; if blocked, the documented fallback (in-app + Realtime + foreground refresh) is the shipping behavior and the spec/release notes record it (the plan's explicit instruction).

## Requirements *(mandatory)*

### Functional Requirements

#### Notification events, recipients & content

- **FR-001**: The system MUST generate a notification for each of these events, to the relevant recipient: **account approved**, **account rejected**, **listing approved**, **listing rejected**, **inquiry received** (on the recipient's listing), and **agency invitation**. Each notification MUST carry a notification **type**, the **recipient identity**, a **deep-link target**, and the structured **parameters** needed to render localized copy and resolve the target. (User-resolved event-catalog decision — see Clarifications.)
- **FR-002**: The recipient MUST be resolved **server-side** from the triggering domain row (account events → the account's user; listing approval/rejection → the listing's publisher; inquiry → the listing's publisher; agency invitation → the invited user) and MUST NOT be client-supplied.
- **FR-003**: Notification generation MUST hang off the **existing server-side transition paths** (the Phase 5 account-approval decision, the Phase 12 listing approve/reject, the Phase 16 inquiry record, the Phase 19 agency-invitation creation) such that exactly **one** notification is emitted per qualifying transition — never duplicated on retries and never emitted on a non-qualifying write (e.g., re-saving an already-approved listing).
- **FR-004**: Notification content MUST be localizable to **Arabic and English** (Principle V). In-app center copy MUST render in the **viewer's active locale** (derived from the notification type + parameters, so it re-renders on a locale toggle); OS-tray push text MUST be rendered **server-side in the recipient's stored preferred language**, defaulting to Arabic when no preference is set. The OS-tray title/body MUST stay **generic** and MUST NOT carry free-text moderator/rejection reasons or other sensitive detail (push renders on the device lock screen); the full rejection reason is revealed **only in-app behind the deep link** (FR-007), and the tray body conveys only that a decision occurred plus a "tap for details" affordance.

#### In-app delivery & notification center

- **FR-005**: Every generated notification MUST be persisted to a **per-user server-side store** (history) carrying the type, the parameters/deep-link target, a **read/unread** state, and a creation timestamp, so history survives across sessions, devices, and reinstall. (User-resolved "server-side notifications table" decision — see Clarifications.)
- **FR-006**: A signed-in user MUST be able to open a **notification center** — reached from a **bell icon carrying an unread-count badge in the home/primary app bar** (routing to a `/notifications` route; not a Profile-only tile) — that lists their notifications **newest-first** with read/unread state and surfaces the **unread count**. The list read MUST be bounded/paginated (the client MUST NOT fetch the entire history at once).
- **FR-007**: Tapping a notification MUST **deep-link** to the relevant screen and **mark it read**: account approved → home; account rejected → the rejection screen; listing approved → that listing's details; listing rejected → My Listings at that listing (showing its rejection reason and a resubmit affordance); inquiry received → the relevant inquiry; agency invitation → the agency accept/decline screen. A target that no longer resolves MUST fail gracefully (localized "content unavailable" / safe fallback), never crash.
- **FR-008**: A user MUST be able to **mark notifications read** individually and **mark all read**, and the unread count MUST update accordingly.
- **FR-009**: A user MUST be able to read and modify (mark-read) **only their own** notifications; a user MUST NOT read another user's notifications.

#### Push delivery (provider-agnostic, pluggable FCM)

- **FR-010**: The system MUST be able to deliver the same notifications as **device push** so a user is reachable when the app is **backgrounded or fully closed**, through a **pluggable push provider** (the v1 adapter is FCM). The notification **core** (in-app delivery, center, Realtime) MUST NOT depend on the push provider. (User-resolved "provider-agnostic core, FCM pluggable" decision — see Clarifications.)
- **FR-011**: The app MUST **register** the device's push token on **successful authentication regardless of `account_status`** (pending / approved — so a not-yet-approved user sitting on the pending-approval screen can still receive the "account approved" / "account rejected" push), **re-register** on token refresh, and **deregister** it on logout, associating tokens with the user so fan-out targets the correct devices; a user MAY have **multiple** registered devices, each independently registered/deregistered.
- **FR-012**: Tapping a push notification MUST open the app and deep-link to the **same destination** as the corresponding in-app notification (FR-007), whether the app was backgrounded or **cold-started from fully closed**. The app MUST subscribe to the push provider's *notification-opened* signal (including the launch/initial message that cold-starts the app from a terminated state) and route every opened push through the **same deep-link resolver** the in-app center uses (FR-007) — so push-tap and in-app-tap navigation can never diverge, and the tapped notification is marked read on navigation.
- **FR-013**: The app MUST function **fully** when **no push provider is configured or available** — in-app delivery, the notification center, and Realtime continue to work; push is skipped with **no user-visible error, no crash, and no broken state** (the plan's documented sanctions fallback). Enabling or disabling the push provider MUST require only **configuration**, not client code changes.
- **FR-014**: The app MUST subscribe to the push provider's *foreground-message* signal. A **foreground** push MUST surface in-app by refreshing the unread badge / notification center (and MAY show a lightweight in-app affordance such as a snackbar) — it MUST NOT raise a duplicate system-tray banner while the app is foregrounded; a **background or fully-closed** push MUST surface as a system notification rendered by the OS. The foreground and notification-opened handlers (FR-012) are a single app-level push listener that consumes the pluggable provider's streams.

#### Realtime admin counters

- **FR-015**: The admin dashboard counters the plan scopes to Realtime — the **pending-listing** count (from `listings` status changes) and the **reports** counts (**new + resolved** on `reports`) — MUST update in **near-real-time** without manual refresh as the underlying rows change.
- **FR-016**: The admin Realtime counter signals MUST be **gated to admins** (a non-admin client MUST NOT receive or act on them; RLS still governs what any subscription can read), and the counters MUST **reconcile** to correct current values on reconnect after a dropped connection (no missed-event drift).

#### Realtime permission refresh

- **FR-017**: A signed-in user's effective permissions MUST **refresh live** when their role assignments change — via a subscription on the user's **own** role-assignment rows that triggers the Phase 6 `PermissionChecker` refresh — so a granted or revoked role re-shapes the user's UI **without re-login**. This MUST be implemented as a **fourth observation point** added to the Phase 6 three-point cache-refresh strategy, leaving the existing three points intact.

#### Security & enforcement (checks at both ends)

- **FR-018**: The push-provider service credential (the **FCM service-account JSON**) MUST be stored as a **Supabase Vault** secret (`fcm_service_account`) and read **only server-side** by the dispatch path; it MUST NOT be committed to the repository and MUST NOT be shipped to the Flutter client (ADR-0001). The server→dispatch wiring's own credentials — the dispatch endpoint URL (`push_dispatch_url`) and the shared authorization token (`push_dispatch_token`) the trigger uses to call the dispatch function — MUST likewise be Vault secrets read **only server-side**, never committed and never shipped to the client.
- **FR-019**: The `notification_tokens` and `notifications` tables MUST have **self-only read RLS** (a user can SELECT only their own rows) and MUST **REVOKE all direct client writes** — every mutation goes through a **self-scoped RPC** (token register/deregister, mark-read / mark-all-read), so a user can only ever affect their own rows. The cross-user **fan-out** (which reads many users' tokens and writes many users' history) MUST run through a **controlled server-side path with elevated privilege** (the internal `enqueue_notification` definer writer plus the dispatch path), never via client writes.
- **FR-020**: A client MUST NOT be able, at the wire level, to **forge** a notification to another user, **write** another user's push token, or **read** another user's notifications or tokens — these are all denied (Principle III).

#### Preferences

- **FR-021**: The system MUST respect the existing per-user global setting `user_preferences.notifications_enabled`: when it is off, the user is **not pushed and not actively alerted** (no device push, no badge/banner interruption), but the notification **history row is still written** so the in-app notification center stays complete — events that occurred while the flag was off appear as **unread** when the user next opens the center (the off state means "don't interrupt me," not "hide what happened"). This phase MUST NOT introduce new per-category notification-preference UI (reuse the existing global flag; per-category preferences are future work).

#### Localization, theming & dependency / scope constraints

- **FR-022**: Every user-visible string in the notification center and any in-app notification affordance MUST flow through `AppLocalizations` with both `ar` and `en` entries, and notification **copy templates** MUST exist in both languages (Principle V).
- **FR-023**: The notification center and all its states (list, unread badge, empty, loading, error, single item) MUST render correctly in all four combinations of (light / dark theme) × (Arabic RTL / English LTR), using logical/direction-aware insets and Phase 2 design tokens — no inline hex literals, no raw font sizes, no ad-hoc paddings (Principle VI).
- **FR-024**: The **domain layer MUST remain provider-agnostic** — no push-provider SDK import under any feature's `domain/` (Principle IX); the FCM adapter MUST live only in the data layer behind the notification abstraction. This phase MAY introduce the push-provider client SDK (the one phase where a new client dependency is justified by the feature), and any Android manifest / Google-services configuration it adds MUST be **Android-only** (no iOS/Web code; Principle XI). The app MUST **build and run with push disabled**.
- **FR-025**: The new backend surface MUST be limited to: the **`notification_tokens`** store and the **`notifications`** history store (RLS on + client writes REVOKEd); the internal **`enqueue_notification`** writer plus the client RPCs (register/deregister token, mark-read / mark-all-read, unread count); the **CREATE-OR-REPLACE amendments** to the four existing transition functions (account decision, `submit_inquiry`, `invite_agency_member`, listing-decision internals) that hang the fan-out off them; the **`fcm_service_account`** + **`push_dispatch_url`** + **`push_dispatch_token`** Vault secrets; the **`pg_net`** extension + the `notifications`-insert **dispatch trigger** + the **`dispatch_push`** Edge Function (the controlled push-dispatch path); and **Realtime enablement** on `listings` / `reports` / `user_roles` — plus their RLS policies. Phase 22 MUST NOT add a new permission key or change the §9.1 catalog (the notification center is available to every signed-in user; admin counters reuse existing admin permissions), MUST NOT add a new audited admin action (the underlying transitions are already audit-logged in their own phases per §9.4), and MUST NOT alter any existing business-data table beyond enabling Realtime on the three named tables — the four transition functions are amended **additively** (same params / returns / grants), not behaviorally changed.

### Key Entities

- **Notification (history record)**: A per-user record of something that happened to that user. Attributes: recipient user, notification **type** (account_approved / account_rejected / listing_approved / listing_rejected / inquiry_received / agency_invitation), structured **parameters** (the IDs/values needed to render localized copy and resolve the deep link), **deep-link target**, **read/unread** state, creation timestamp. Owned by and readable only by its recipient (self-only RLS). Written only by the controlled fan-out path. Backs the notification center. Adds a `notifications` table beyond the plan's §6.2 list (which named only `notification_tokens`).
- **Notification Type / Event**: The catalog of qualifying events, each mapping to a recipient-resolution rule, a deep-link target, and a bilingual copy template. The closed set for this phase is the six events in FR-001.
- **Push Token (device registration)**: A registration of one device's push token to one user (with platform + freshness metadata). Self-owned (a user reads/writes only their own tokens); a user may have several. Targeted by fan-out to dispatch push. Corresponds to the plan's `notification_tokens` table.
- **Push Provider (pluggable sender)**: The abstraction the fan-out path dispatches through; the v1 adapter is FCM. Its credential is the Vault secret `fcm_service_account`, read only server-side. The provider may be **absent/unconfigured**, in which case the system runs in degraded (in-app + Realtime) mode with no error.
- **Fan-out Path**: The controlled, elevated-privilege server-side process invoked by existing transitions that resolves the recipient, writes exactly one notification history row, and dispatches push to the recipient's registered tokens (when a provider is configured). Never invoked by direct client writes.
- **Realtime Admin Signal**: The live stream feeding the admin dashboard's pending-listing and reports counters (from `listings` / `reports` changes), gated to admins and reconciling on reconnect.
- **Permission-Refresh Signal**: The live stream on the signed-in user's own role-assignment rows that triggers the Phase 6 `PermissionChecker.refresh()` — the fourth observation point.
- **Notification Center**: The signed-in user's screen listing their notification history newest-first with read/unread state, an unread count, mark-read (single + all), and deep-link-on-tap.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Each of the six events (account approved, account rejected, listing approved, listing rejected, inquiry received, agency invitation) generates **exactly one** notification to the **correct** recipient, visible in that recipient's notification center within **5 seconds** of the triggering action, with a working deep link — verified per event type on the reference Infinix Note 8 (two sessions/devices).
- **SC-002**: With push enabled and a device registered, approving an account or listing, sending an inquiry, or inviting to an agency results in a **system push** arriving on the recipient's second device within **~10 seconds**, and tapping it opens the correct destination — verified two-device (action on B, push on A), including a cold-start (app fully closed) tap.
- **SC-003**: With the push provider **disabled/unconfigured**, the app **builds, runs, and delivers all six notifications in-app** (center + badge) with **no error, no crash, and no broken UI** — the sanctions fallback verified on-device and at build time.
- **SC-004**: The admin dashboard's **pending-listing** counter changes within **~5 seconds** of a publisher submitting / a listing being approved-or-rejected, and the **reports** counter within **~5 seconds** of a report being filed / resolved — on a second admin device with **no manual refresh** — and both counters **reconcile** to correct values after a forced connection drop (the plan's two-device counter test).
- **SC-005**: A super-admin granting a role carrying a new permission to a signed-in user makes that user's permission-gated UI **reachable without re-login** on the next live refresh, and revoking it makes the UI disappear on the next live refresh — verified two-device.
- **SC-006**: The notification center and all its states render correctly in all four (light/dark) × (Arabic RTL / English LTR) combinations on the reference Infinix Note 8 (≈480 dp) and a 412 dp emulator profile — all strings localized, layout direction-correct, styling from Phase 2 tokens — **and** push-tray text appears in the recipient's preferred language (Arabic when unset).
- **SC-007**: From a session lacking access, a direct wire-level attempt to read/write another user's `notifications` or `notification_tokens`, or to insert a notification targeting another user, is **DENIED**; the `fcm_service_account` credential is **absent** from the repository and the built client artifact (grep / artifact inspection) and present only as a Vault secret; a non-admin does not receive the admin counter channel — all checks pass.
- **SC-008**: The unread **badge count matches** the number of unread rows; marking read (single and all) updates it; notification **history persists** across logout/login and on a fresh install of the same account on a different device — verified on-device.
- **SC-009**: A **single** qualifying transition produces **exactly one** notification (no duplicates on retries; none on non-qualifying writes) — verified by counting notification rows for the recipient before/after a transition and after a deliberate retry.
- **SC-010**: A repository-wide check confirms: **no push-provider SDK import** under any `domain/` (Principle IX); any Firebase/manifest/Google-services configuration is **Android-only** (no iOS/Web); the app **runs with push disabled**; **no new permission key** is added; and the new backend surface is exactly the enumerated set — the `notification_tokens` + `notifications` tables, the `enqueue_notification` writer + the token/read-state client RPCs, the four additive transition-function amendments, the `fcm_service_account` + `push_dispatch_url` + `push_dispatch_token` Vault secrets, the `pg_net` extension + the dispatch trigger + the `dispatch_push` Edge Function, Realtime on `listings`/`reports`/`user_roles`, and their RLS policies — with no other table / enum / permission / audit change.
- **SC-011**: A device's push token is **registered on login** and **removed on logout** (verified by inspecting the token store before/after); with two devices logged into one account, both receive push, and logging out one leaves the other receiving push.

## Assumptions

- **Phase 22 is the notifications + Realtime layer** (`specs/022-notifications-realtime/`), distinct from Phase 21 (Ads & banners) and Phase 23 (App settings). This spec covers only push notifications and Supabase Realtime signals.
- **Four decisions were resolved with the user on 2026-06-02** (folded in here — see Clarifications): (1) push delivery uses a **provider-agnostic core with FCM as a pluggable sender** (in-app + Realtime always work; push degrades gracefully when Firebase is unavailable — the plan's flagged sanction risk); (2) the **event catalog** is the full set — account approved/rejected, listing approved/rejected, inquiry received, agency invitation; (3) the in-app notification center is backed by a **server-side `notifications` table** (cross-device, survives reinstall, read/unread); (4) **Realtime scope** is admin counters (`listings` + `reports`) **plus** the signed-in user's `user_roles` permission-refresh subscription.
- **Cross-cutting [ADR-0001](../../docs/decisions/0001-secrets-and-pii-storage.md)**: the FCM service-account JSON is the Vault secret `fcm_service_account`, read only server-side by the dispatch path; the dispatch wiring's `push_dispatch_url` + `push_dispatch_token` are likewise Vault secrets. None are committed or shipped to the client. Server→push dispatch is an async `pg_net` trigger on the `notifications` insert calling the `dispatch_push` Edge Function — part of the controlled fan-out path, and the **one new Postgres extension** this phase introduces (justified in the plan's Complexity Tracking alongside the one new client dependency `firebase_core`/`firebase_messaging`).
- **The sanctions fallback is a first-class shipping mode.** If the Firebase project proves unreachable/unacceptable from Syria, the documented fallback (in-app delivery + notification center + Realtime + foreground refresh) is what ships, with no functional break and no user-visible error — exactly as the plan's Phase 22 acceptance criterion instructs ("if blocked, document fallback (in-app polling only) in the spec").
- **`notification_tokens` is the plan's named table; `notifications` is added by decision (3).** The plan's §6.2 schema list names only `notification_tokens` for Phase 22; the server-side-history decision adds a `notifications` table — recorded here per Principle XII (no hidden product decisions).
- **Recipients are existing registered users.** The agency-invitation notification targets an already-registered invitee (Phase 19's invite + in-app-accept model invites an existing user); anonymous inquiry senders have no account and receive nothing — the inquiry notification goes to the listing's publisher.
- **Notification fan-out attaches to already-built transitions.** It reuses the Phase 5 account-approval decision path, the Phase 12 listing approve/reject path, the Phase 16 inquiry record path, and the Phase 19 agency-invitation creation path; this phase adds the fan-out hook, not new transition logic, and emits exactly once per qualifying transition.
- **Notification copy is localized on both surfaces.** In-app copy is rendered client-side from the type + parameters in the viewer's active locale; push-tray text is rendered server-side in the recipient's `profiles.preferred_language`, defaulting to Arabic (Arabic-first) when unset.
- **The global `user_preferences.notifications_enabled` flag governs active *interruption*, not historical *visibility*** (resolved 2026-06-02 — see Clarifications): when off, the user is not pushed or actively alerted, but the notification history row is still written so it appears (as unread) when they next open the center. No new per-category preferences UI in this phase.
- **Realtime scope is admin counters + permission refresh only.** User-facing live data beyond that — a publisher's My Listings streaming status live, a live notification badge driven by Realtime rather than fetch-on-open, etc. — is **out of scope** this phase and keeps the established read/refresh posture. The likely Phase 22 permission-refresh change is a subscription on `user_roles` rows where `user_id = auth.uid()` that calls `PermissionChecker.refresh()` on INSERT/UPDATE/DELETE (the Phase 6 deferred follow-up).
- **Realtime-driven ad liveness is NOT in this phase.** Phase 21 ads keep their server-side-eligibility read/refresh model; the Phase 21 note that "Phase 22 owns Realtime" means this layer now exists, not that ads become Realtime-driven here.
- **No new audit events and no new permission key.** The triggering transitions are already audit-logged in their originating phases (§9.4 does not list notification fan-out); the notification center is available to every signed-in user, and admin counters reuse the existing admin permissions — so the §9.1 catalog is unchanged.
- **A new client dependency is expected this phase, unlike Phases 19/21.** The push-provider (Firebase) Flutter SDK is permitted, but only in the data-layer adapter behind the notification abstraction (domain stays provider-agnostic, Principle IX), and the app must build/run with push unconfigured. Any Android manifest / `google-services` configuration is Android-only (Principle XI). This is the deliberate, documented exception to the project's recent "zero new deps" pattern, justified by the feature.
- **Push delivery semantics follow the provider.** Offline/queued delivery, delivery receipts, and retry are the provider's responsibility; this phase does not build a custom delivery-guarantee layer. The in-app history record is the durable record of "this happened to you."
- **No new automated tests** are added, per the project's MVP manual-verification convention; verification is by manual on-device walks (two-device for push and counters) plus direct wire-level/SQL inspection against fixtures, recorded against the Success Criteria.
- **Backend backed by Supabase** with RLS on both new tables, the Vault secret per ADR-0001, the fan-out through a controlled elevated-privilege server path, and Realtime enabled on the three named tables. The repository remains the source of truth (migrations, policies, function, Vault-secret registration, and Realtime enablement all checked in — Principle II).

## Clarifications

### Session 2026-06-02

- Q: The plan flags a Firebase/FCM sanction risk from Syria and says to document a fallback if blocked — how should the phase treat push delivery? → A: **Provider-agnostic core with FCM as a pluggable sender.** In-app delivery + the notification center + Realtime always work; device push is a pluggable provider (FCM v1 adapter) that degrades gracefully — when unavailable, push is skipped with no user-visible error and enabling it later is configuration-only, not a code change (FR-010, FR-013).
- Q: Which events should generate a notification to the relevant user this phase? → A: **All four families** — account approved/rejected, listing approved/rejected, inquiry received, and agency invitation (the plan's three named events plus their symmetric reject cases and the Phase 19-deferred agency invite) (FR-001).
- Q: The plan requires an in-app notification center (history) but lists no notifications table — how is that history stored? → A: **A server-side `notifications` table** (per-user, type + params/deep-link + read/unread + created_at) so history syncs across devices and survives reinstall; this adds a table beyond the plan's §6.2 list (FR-005).
- Q: The plan scopes Realtime to "admin counters" on listings + reports — how wide should Realtime go this phase? → A: **Admin counters (`listings` + `reports`) plus a `user_roles` permission-refresh subscription** for the signed-in user (the Phase 6 deferred follow-up); no other user-facing live data this phase (FR-015, FR-017).
- Q: When `user_preferences.notifications_enabled` is off, what does it suppress? → A: **Push + active in-app alerts only** — the notification is still written to history and appears (as unread) in the center when the user next opens it; the flag means "don't interrupt me," not "hide what happened" (FR-021).
- Q: Where does the user reach the notification center from? → A: **A bell icon with an unread-count badge in the home/primary app bar**, routing to `/notifications` (not a Profile-only tile) (FR-006).
- Q: Is the push token registered for not-yet-approved (pending) users? → A: **Yes — register on successful auth regardless of `account_status`**, so the flagship "account approved / rejected" push can reach a user on the pending-approval screen (FR-011).
- Q: Does the push (OS-tray) body include the rejection reason? → A: **No — generic tray body, full reason in-app only.** The lock-screen push conveys only that a decision occurred + "tap for details"; the free-text moderator reason is revealed only after the in-app deep link (FR-004, FR-007).
