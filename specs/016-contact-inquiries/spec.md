# Feature Specification: Contact, Inquiries & Lead Events

**Feature Branch**: `016-contact-inquiries`
**Created**: 2026-05-25
**Status**: Draft
**Input**: Phase 16 — Contact, inquiries & lead events, from `docs/IMPLEMENTATION_PLAN.md`

> **Scope note**: Phase 16 introduces the *publisher-to-visitor contact pipeline* — the working implementation of the three contact CTAs that Phase 13's `ListingDetailsPage` ships as Coming-soon stubs (Call / WhatsApp / Send inquiry, in the `ContactBlock` widget per `lib/features/listing_details/presentation/widgets/contact_block.dart`), plus the publisher-side inbox where written inquiries land and are worked through a status workflow, plus the lead-event telemetry that captures every engagement signal a publisher (or admin) needs to understand who reached out and how. It does NOT introduce a calling or VoIP capability inside the app (the Call CTA delegates to the Android system dialer via `tel:`), does NOT introduce a chat surface inside the app (the WhatsApp CTA delegates to the WhatsApp app via `wa.me/`), does NOT introduce real-time chat between the inquirer and the publisher (Phase 22 owns Realtime; Phase 16 ships a one-way "send and the publisher responds via phone/WhatsApp" model), does NOT introduce an in-app message thread or reply UI for the publisher (status updates only — the publisher's actual reply happens out-of-band via the call/WhatsApp/contact the inquirer left), does NOT introduce favorites (Phase 17 owns the `favorite_added` lead event), does NOT introduce reports (Phase 18 owns the `Report` button on the listing details page and the reporter→admin workflow), does NOT introduce push notifications when a new inquiry arrives (Phase 22 owns FCM fan-out; Phase 16 ships inbox polling on inbox open + pull-to-refresh per the Phase 13 freshness model), does NOT introduce sender-side "my inquiries" tracking for signed-in users (the inquirer's view of their own outbound submissions is out of scope; the captured callback phone is the channel), does NOT modify Phase 13's `PerListingActionBlock` (Favorite/Share/Report stubs remain Coming-soon — those belong to Phases 17, 18, and a future share-wiring phase respectively). The Phase 16 PR ships exactly: (a) two new tables — `inquiries` for the publisher-targeted written submissions (with the inquirer's callback phone stored via Supabase Vault per ADR-0001 so a leaked DB dump never exposes it as plaintext) and `lead_events` for the high-volume tap-tracking stream (phone-reveal taps, WhatsApp-click taps, inquiry-submission taps, plus forward-stated `favorite_added` for Phase 17 — the enum is defined here so Phase 17 does not need a schema migration); (b) a single server-side write surface that atomically inserts an `inquiries` row plus its companion `inquiry_sent` lead event in one transaction when the inquiry form is submitted, plus a lighter write surface that records a single lead event when the user taps Call or WhatsApp; (c) RLS on `inquiries` that strictly partitions visibility — the sender (when signed in) can read their own outbound submission, the listing's publisher can read every inquiry on every listing they own, admins with `inquiries.view_all` can read every inquiry across the platform, no other reader path exists, and the Vault-decrypted `inquirer_phone` is exposed ONLY through a privileged decrypt view that the same three reader classes can reach; (d) replacement of the Phase 13 `ContactBlock` Coming-soon stubs with the working CTAs — Call opens the Android system dialer via `tel:` after recording a `phone_revealed` lead event, WhatsApp opens WhatsApp via `https://wa.me/<E.164-without-plus>` after recording a `whatsapp_clicked` lead event, "Send inquiry" opens an inquiry form (name + phone + message, anonymous-allowed) that records an `inquiry_sent` lead event on submit; (e) a new publisher inbox at `lib/features/inquiries/` listing every inquiry on every listing the publisher owns, sortable/filterable by status, with the four-state workflow `new → seen → responded → closed` (plus the `spam` side-branch state from the IMPLEMENTATION_PLAN §6.3 enum surfaced through a "Mark as spam" affordance per Q3=A) where status transitions are publisher-driven and forward-progressive (a `seen` inquiry can become `responded`, `closed`, or `spam`; it cannot regress to `new`); (f) two new pubspec packages added for the first time: `url_launcher` (the Flutter-team-maintained launcher for `tel:` and `https:` schemes — already locked in Phase 15's research as the preferred non-commercial-map launcher) and one phone-validation utility if the existing Phase 5 `PhoneNumber` value object's E.164 normalization needs the inquirer-side string-input coverage extended; (g) the localization layer gains the inquiry form chrome strings, the inbox status labels, the empty-state strings, the spam-confirmation dialog strings, and the launcher-failure error messages — all flowing through `AppLocalizations` per Phase 3 conventions. Phase 16 makes the three Phase 13 CTAs working, makes the publisher inbox real, and lays the lead-event substrate that Phases 17, 18, 22, and the eventual analytics surface all consume. It honors ADR-0001 (inquirer phones in Vault, never plaintext columns); it honors the Phase 7 audit-log discipline (status changes are publisher-driven CRM operations, NOT admin moderation, so they are NOT audit-logged per §6.4 — the `inquiries` row is the log of itself); it honors the Phase 6 permission system (the admin oversight surface is gated by `inquiries.view_all` per §9.1).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Visitor places a direct call from a listing details page (Priority: P1)

A visitor (signed-in or anonymous) browsing a listing's details page decides the listing is worth a callback. They tap the "Call" CTA in the contact block. The app records a `phone_revealed` lead event server-side (so the publisher can later see in their analytics that someone tapped Call on this listing), then hands off to the Android system dialer pre-populated with the publisher's phone number. From there the visitor confirms or cancels the call in the dialer; the app's responsibility ends at handoff.

**Why this priority**: P1 because a direct phone call is the single highest-conversion contact channel in Syrian real-estate behavior — the buyer expects to call, the publisher expects calls, and the rest of the marketplace's UX is only as valuable as it ends in a call. Without a working Call CTA, the listing page is a dead-end. Without the lead event, the publisher has no signal that their listing is generating interest. The Phase 13 Coming-soon stub is the placeholder this story replaces.

**Independent Test**: Apply the Phase 16 migrations. With ≥ 3 approved listings whose `phone` field is non-empty (and at least one approved listing whose `phone` field is empty), launch the app on the reference Infinix Note 8. From the home feed, tap any approved listing whose `phone` is set; on the details page, tap the Call CTA. Confirm: (a) a `lead_events` row exists with `event_type = 'phone_revealed'`, `listing_id` matching the listing, `user_id` set if the visitor is signed in or null if anonymous, `created_at` within the last 5 seconds, (b) the Android system dialer opens pre-populated with the listing's `phone` value, (c) tapping Back from the dialer returns to the listing details page (the app was not killed). Tap Call on the listing whose `phone` is empty; confirm the Call CTA is not visible (or is visibly disabled). Re-tap Call on the first listing two more times; confirm three `lead_events` rows now exist for the same listing — each tap is its own event, no deduplication.

**Acceptance Scenarios**:

1. **Given** a visitor is on the listing details page for an approved listing whose `phone` field is non-empty, **When** the visitor taps the Call CTA, **Then** the app inserts one `lead_events` row with `event_type = 'phone_revealed'` AND `listing_id` set to the listing AND `user_id` set to the signed-in visitor (or null for anonymous), AND the Android system dialer opens pre-populated with the listing's `phone` value.
2. **Given** the Call CTA tap recorded a `phone_revealed` lead event, **When** the dialer hand-off succeeds, **Then** the event row remains in `lead_events` even if the visitor cancels the call before dialing — the event captures intent-to-call, not call-completion.
3. **Given** an approved listing whose `phone` field is empty (null or empty string), **When** the visitor reaches the listing details page, **Then** the Call CTA is hidden (or visibly disabled with a localized hint) AND tapping it is impossible AND no `lead_events` row can be created for this listing's phone-reveal action.
4. **Given** the Android system has no dialer available (e.g., a tablet build with the dialer disabled), **When** the visitor taps Call, **Then** a localized error message explains that no dialer is available AND the `phone_revealed` lead event was still recorded (the tap-intent is captured regardless of launcher success).
5. **Given** an anonymous visitor taps Call, **When** the event is recorded, **Then** the `user_id` column on the `lead_events` row is null AND the row is still inserted (anonymous taps count as engagement signals).
6. **Given** the visitor taps Call rapidly (e.g., three taps within 1 second), **When** each tap is processed, **Then** each tap inserts its own `lead_events` row — no client-side deduplication is applied (the publisher's analytics may post-process duplicates if desired).

### User Story 2 — Visitor opens WhatsApp from a listing details page (Priority: P1)

A visitor browsing a listing's details page decides they would rather chat than call. They tap the "WhatsApp" CTA. The app records a `whatsapp_clicked` lead event, then hands off to WhatsApp via the standard `wa.me/<phone>` URL so the conversation opens pre-populated to the publisher's contact. The visitor types whatever they want and sends it through WhatsApp; the app's responsibility ends at handoff.

**Why this priority**: P1 because WhatsApp is the de-facto messaging channel in Syria — for a non-trivial fraction of users it is preferred over a voice call (cheaper, can include photos, can be answered async). A real-estate marketplace that ships without a WhatsApp CTA loses those conversions to competitor channels (Facebook Marketplace, direct word-of-mouth). The Phase 13 Coming-soon stub is the placeholder this story replaces.

**Independent Test**: With ≥ 3 approved listings whose `whatsapp` field is non-empty (and at least one approved listing whose `whatsapp` field is empty — see Clarification Q1 for the fallback policy when `phone` is set but `whatsapp` is not), open the listing details page for an approved listing whose `whatsapp` is set. Tap the WhatsApp CTA. Confirm: (a) a `lead_events` row exists with `event_type = 'whatsapp_clicked'`, (b) the WhatsApp app opens to the publisher's contact (or, if WhatsApp is not installed, the system's web browser opens the `wa.me/...` URL which prompts to install WhatsApp). Re-test on a listing where `whatsapp` is empty and `phone` is set; confirm the WhatsApp CTA behavior matches the resolution of Q1.

**Acceptance Scenarios**:

1. **Given** a visitor is on the listing details page for an approved listing whose `whatsapp` field is non-empty AND validates as a callable phone number, **When** the visitor taps the WhatsApp CTA, **Then** the app inserts one `lead_events` row with `event_type = 'whatsapp_clicked'` AND the WhatsApp app opens to a chat with the publisher (or the web `wa.me/` URL opens if WhatsApp is not installed on the device).
2. **Given** an approved listing whose `whatsapp` is non-empty but is malformed (contains letters, fewer than the E.164 minimum digits, etc.), **When** the page renders, **Then** the WhatsApp CTA is hidden (or visibly disabled) AND tapping it is impossible — malformed numbers cannot be silently launched.
3. **Given** WhatsApp is not installed on the device, **When** the visitor taps the WhatsApp CTA, **Then** the lead event is still recorded AND the system browser opens the `wa.me/...` URL which presents WhatsApp's standard "install WhatsApp" landing page.
4. **Given** an anonymous visitor taps WhatsApp, **When** the event is recorded, **Then** the `user_id` column on the `lead_events` row is null AND the row is still inserted.
5. **Given** the `phone` field is set on the listing AND the `whatsapp` field is empty, **When** the page renders, **Then** the WhatsApp CTA is rendered AND visibly disabled (greyed out, non-tappable) with a localized hint explaining that the publisher did not register a WhatsApp number — the CTA is NOT silently hidden (so the visitor sees the channel exists but is not available for this listing) AND tapping it is impossible AND no `whatsapp_clicked` lead event can be recorded.
6. **Given** the visitor taps WhatsApp, **When** the event row is inserted, **Then** the row is inserted BEFORE the launcher hand-off begins — if the launcher fails (e.g., the `intent` is rejected by the OS), the event is still durable.

### User Story 3 — Visitor sends a written inquiry to a publisher (Priority: P1)

A visitor browsing a listing's details page wants to ask a specific question (price negotiation, viewing schedule, availability date) and prefers a written record over a phone call. They tap the "Send inquiry" CTA. A form opens with three fields: a name field (so the publisher knows who's contacting), a phone field (so the publisher has a callback channel — the platform does NOT operate an in-app reply UI in v1), and a free-form message field. The visitor fills the form; if they're signed in their profile name and phone pre-populate the fields. They submit. The app atomically writes one `inquiries` row (with the phone stored encrypted via Supabase Vault per ADR-0001 so a leaked DB dump never exposes it as plaintext) and one `inquiry_sent` lead event. The visitor sees a localized success confirmation and returns to the listing details page. The visitor does NOT get an in-app thread to track the inquiry — the captured phone is the channel for the publisher's reply, and that reply happens out-of-band.

**Why this priority**: P1 because not every contact intent fits a voice call or a WhatsApp message — some buyers need to put a specific written question in front of a publisher (e.g., "Is this furnished?", "Is the bathroom remodeled?", "When can I view this Friday afternoon?") and want a written record. Without an inquiry channel, the marketplace pushes those buyers into competitor channels. The Phase 13 Coming-soon stub is the placeholder this story replaces. Anonymous submission is explicitly supported per the IMPLEMENTATION_PLAN; many Syrian visitors prefer not to sign up before a single inquiry.

**Independent Test**: From an approved listing details page (anonymous session), tap "Send inquiry." Fill the form with a test name, a valid E.164 Syrian phone (`+963991234567`), and a 50-character message. Submit. Confirm: (a) one `inquiries` row exists with `listing_id` matching the listing, `sender_user_id` null (anonymous), `sender_name` matching the typed name, the encrypted `inquirer_phone` Vault field non-null AND not equal to the plaintext phone the visitor typed (verify by reading the table directly — a raw SELECT must not return the plaintext), `message` matching the typed text, `status = 'new'`, `created_at` within the last 5 seconds; (b) one `lead_events` row exists with `event_type = 'inquiry_sent'` linked to the same listing; (c) the success confirmation appears in the localized language; (d) the visitor is returned to the listing details page; (e) the visitor has no in-app entry point to a "my inquiries" view (send-and-forget by design). Sign in as a different test account, browse to the same listing, tap "Send inquiry"; confirm the form pre-populates the name and phone from the signed-in profile AND that the resulting `inquiries` row has `sender_user_id` set to the signed-in user.

**Acceptance Scenarios**:

1. **Given** a visitor is on an approved listing's details page, **When** they tap "Send inquiry," **Then** a form opens with three fields — name (required), phone (required, validated as E.164), message (required, non-empty after trim).
2. **Given** a signed-in visitor opens the inquiry form, **When** the form renders, **Then** the name and phone fields pre-populate from the signed-in user's profile (`profiles.full_name`, `profiles.phone`) — the visitor MAY override either field before submitting.
3. **Given** an anonymous visitor opens the inquiry form, **When** the form renders, **Then** the name and phone fields render empty AND the visitor types both manually.
4. **Given** a visitor submits a completed inquiry form, **When** the submission succeeds, **Then** exactly one `inquiries` row is inserted AND exactly one `inquiry_sent` lead event is inserted AND the inquirer's phone is stored via Supabase Vault per ADR-0001 (not as a plaintext column).
5. **Given** a visitor submits an inquiry form with an invalid phone (malformed E.164), **When** validation runs, **Then** the form rejects the submission with a localized "Invalid phone number" message AND neither an `inquiries` row nor a `lead_events` row is inserted.
6. **Given** the inquiry form atomically writes the `inquiries` row AND the `inquiry_sent` lead event, **When** either insert would fail, **Then** the entire transaction rolls back — there must NEVER be an `inquiries` row without its companion `lead_events` row OR vice versa.
7. **Given** an inquiry has been successfully submitted, **When** the success state renders, **Then** a localized confirmation message displays AND the visitor returns to the listing details page AND no in-app "my inquiries" surface is offered to the visitor.
8. **Given** an anonymous visitor's `sender_user_id` is null on the `inquiries` row, **When** the row is read later by the listing's publisher, **Then** the publisher sees a localized "Anonymous inquirer" label AND the decrypted `inquirer_phone` AND the typed `sender_name` (so the publisher can still call back).
9. **Given** the visitor is the listing's own publisher AND they reach the listing's details page, **When** the page renders, **Then** all three contact CTAs (Call / WhatsApp / Send inquiry) are hidden — a publisher inquiring on their own listing is meaningless engagement noise AND lead events for self-contact would pollute the publisher's own analytics.

### User Story 4 — Publisher reads inquiries inbox and updates status (Priority: P1)

A publisher (an approved user who has published at least one listing) opens the new "Inquiries" surface in the app. They see a single chronological feed of every inquiry on every listing they own, newest first. Each row shows the inquirer's name and (decrypted) callback phone, the listing the inquiry was about, a snippet of the message, the inquiry's current status, and the submission timestamp. The publisher reads an inquiry; tapping it auto-marks it as `seen` (the auto-mark is one-way — the inquiry cannot regress to `new` once seen). When the publisher has called/WhatsApp'd the inquirer, they flip the inquiry to `responded`. When the matter is fully resolved (deal closed, lost, or otherwise no longer actionable), they flip the inquiry to `closed`. A `closed` inquiry MAY be reopened to `seen` or `responded` if the matter resurfaces, but MAY NOT regress to `new` (the soft-terminal rule per Q2=B). Phase 16 does NOT surface a publisher-side "Mark as spam" affordance per Q3=B — the `spam` enum value is reserved in the schema for forward admin-side use; a publisher who receives junk uses `closed`. All status changes persist immediately.

**Why this priority**: P1 because without an inbox the inquiries land in a black hole — they accumulate in the database but the publisher has no way to read them, respond to them, or know they exist at all. The inbox is the publisher's view of the inquiry pipeline; without it, US3 (inquiry submission) is functionally a write-only sinkhole. The full state machine (new → seen → responded → closed, plus spam side-branch) is part of v1 because publishers need to track which inquiries they've actioned across multiple listings and visits over time.

**Independent Test**: With ≥ 2 publisher accounts each owning ≥ 1 approved listing, and with ≥ 5 inquiries pre-seeded (some on publisher-A's listings, some on publisher-B's listings, some anonymous, some signed-in), sign in as publisher-A. Navigate to the new "Inquiries" surface. Confirm: (a) the feed shows ONLY inquiries on publisher-A's listings — none on publisher-B's listings, (b) the feed is ordered newest-first, (c) each row shows the inquirer's name, decrypted phone (for the publisher and admins only), listing reference, message snippet, status, timestamp. Tap an inquiry to read; confirm its status flips from `new` to `seen` and persists across app restart. Manually set an inquiry to `responded`, then to `closed`, then reopen it back to `seen` and confirm the transition succeeds; attempt the forbidden `closed → new` transition and confirm the UI offers no affordance for it AND a direct SQL attempt is rejected by the UPDATE policy. Confirm the inbox surfaces no publisher-side "Mark as spam" affordance per Q3=B (the `spam` enum exists for forward admin use). Sign out and sign in as publisher-B; confirm publisher-B sees only their inquiries — publisher-A's inquiries are entirely absent (not merely hidden, but absent from the response payload).

**Acceptance Scenarios**:

1. **Given** a signed-in publisher with at least one inquiry on a listing they own, **When** they open the Inquiries surface, **Then** they see a list of every inquiry on every listing they own, sorted newest-first, with status, inquirer name, decrypted callback phone, message snippet, and submission timestamp visible.
2. **Given** a publisher viewing an inquiry whose status is `new`, **When** they tap to read the full inquiry, **Then** the status auto-transitions to `seen` AND persists across app restart AND the change does NOT affect the inquiry's timestamp (the `created_at` stays as the original submission time).
3. **Given** a publisher has called or WhatsApp'd the inquirer using the captured callback phone, **When** they tap "Mark as responded," **Then** the inquiry's status becomes `responded` AND persists across app restart.
4. **Given** an inquiry whose status is `responded`, **When** the publisher taps "Mark as closed," **Then** the status becomes `closed` AND the inquiry moves to (or is filterable from) the closed-inquiries view; the inquiry remains readable for the publisher's records.
5. **Given** an inquiry has been delivered AND the publisher decides it is junk, **When** they look for a "Mark as spam" affordance in the inbox UX, **Then** none is offered (per Q3=B) AND the publisher uses `closed` as the disposal status — the `spam` enum value exists in the schema for forward admin-side use only; Phase 16 ships no publisher-write path to it.
6. **Given** the publisher's inbox is non-empty AND the publisher has multiple listings, **When** they apply a per-listing filter, **Then** the feed shows only inquiries on the selected listing.
7. **Given** the publisher's inbox is non-empty, **When** they apply a per-status filter (e.g., show only `new`), **Then** the feed shows only matching inquiries.
8. **Given** a publisher has zero inquiries on any of their listings, **When** they open the Inquiries surface, **Then** a localized empty-state message renders (the surface does not crash, blank, or show another publisher's data).
9. **Given** an inquiry's status is `closed`, **When** the publisher attempts to flip the status back to a non-terminal state, **Then** the publisher MAY reopen the inquiry to `seen` or `responded` (the soft-terminal rule per Q2=B) but MAY NOT reopen it back to `new` — the `new` state's "never been opened" semantics are preserved by forbidding regression into it; a UI affordance for `closed → seen` and `closed → responded` is offered, but no `closed → new` affordance exists.
10. **Given** the publisher has an inquiry that came from a listing they OWN AT THE TIME OF THE INQUIRY but the listing has since been deleted (Phase 18 future delete flow) or transitioned to terminal status (sold/rented/expired), **When** they open the Inquiries surface, **Then** the inquiry remains visible in the inbox AND the row shows a localized "Listing closed" or "Listing deleted" affordance so the publisher can still see and act on the inquiry history.

### User Story 5 — Cross-publisher RLS isolation is strictly enforced (Priority: P1)

The product handles inquiries that carry the inquirer's callback phone (a PII field stored via Supabase Vault per ADR-0001). A leak — publisher B reading publisher A's inquiries, an anonymous visitor enumerating other people's inquiries, an admin without `inquiries.view_all` seeing inquiries they shouldn't, the public client seeing the decrypted phone of any inquiry — would be a catastrophic privacy breach. The RLS posture and the Vault decrypt boundary together enforce strict three-tier visibility: the sender (when signed-in) reads their own outbound inquiry, the listing's publisher reads every inquiry on every listing they own, admins holding the `inquiries.view_all` permission read every inquiry across the platform, and no other reader path exists. The decrypted `inquirer_phone` is reachable ONLY through a privileged decrypt view whose RLS gate is the same three-tier rule.

**Why this priority**: P1 because publisher trust and inquirer trust are both at stake. Constitution Principle III (Security-First Supabase) and ADR-0001 jointly require defense-in-depth on PII; this is the load-bearing check. A single high-profile leak — an inquirer's phone appearing in another publisher's inbox, or a public network capture showing a decrypted phone — destroys trust permanently.

**Independent Test**: Seed two publisher accounts (publisher-A, publisher-B) each with ≥ 1 approved listing. Seed inquiries — some on A's listings (from various senders, both signed-in and anonymous), some on B's listings. Capture the wire-level response when publisher-A queries the inquiries surface. Confirm: (a) the response contains ONLY rows whose `listing_id` belongs to publisher-A's listings — none of publisher-B's, (b) for each row, the response contains the decrypted `inquirer_phone` field (publisher-A's privileged-decrypt path is the reason), (c) the same query executed from publisher-B's session returns ONLY rows whose `listing_id` belongs to publisher-B's listings, (d) the same query executed from an anonymous client returns zero rows AND/OR is rejected by RLS — anonymous reads on the inquiries table are not permitted, (e) the privileged decrypt view, when read from an anonymous client or a non-owner authenticated client, returns no rows for inquiries that client does not own (the row-level gate matches the table-level gate). Repeat for a third user with the `inquiries.view_all` permission; confirm they read every inquiry from every publisher with the decrypted phone visible.

**Acceptance Scenarios**:

1. **Given** publisher-A is signed in AND has inquiries on listings they own, **When** publisher-A queries the inquiries surface, **Then** the response contains every inquiry whose listing's `publisher_user_id` equals publisher-A's user-id AND zero inquiries on any listing publisher-A does not own.
2. **Given** publisher-B is signed in AND has zero inquiries on publisher-A's listings (publisher-B does not own those listings), **When** publisher-B queries the inquiries surface, **Then** zero inquiries on publisher-A's listings appear in the response — they are absent from the wire-level payload, not merely hidden in the UI.
3. **Given** an anonymous client, **When** the client queries the inquiries table, **Then** RLS denies the read AND no rows are returned regardless of the client's query parameters.
4. **Given** an admin holds the `inquiries.view_all` permission, **When** they query the inquiries surface, **Then** they see every inquiry across every publisher (with decrypted callback phone visible — admins are authorized to decrypt per the three-tier rule).
5. **Given** a signed-in inquirer who previously submitted an inquiry, **When** they query the inquiries table for their own outbound submission, **Then** they see only their own submission row AND no other inquirer's rows AND no other publisher's rows — the visibility is symmetric on the sender side too.
6. **Given** an anonymous inquirer who submitted with `sender_user_id = null`, **When** they (or anyone else) later attempts to read that inquiry, **Then** only the listing's publisher and admins with `inquiries.view_all` can read it — the anonymous sender has no authenticated identity by which to re-read their submission, which is consistent with the send-and-forget design.
7. **Given** the `inquirer_phone` field is stored via Supabase Vault per ADR-0001, **When** a non-authorized reader (anonymous, non-owner publisher, non-admin user) reads the inquiries table through any path including direct SQL, **Then** the encrypted Vault column is returned but never decrypts AND the privileged decrypt view returns zero rows for them.
8. **Given** a developer runs `pg_dump` or any standard database backup, **When** the dump is inspected, **Then** the `inquirer_phone` values are encrypted ciphertext (or absent from the dump entirely, per Vault's storage model) AND no plaintext phone numbers from inquiries appear in the dump.

### User Story 6 — Lead event telemetry accumulates engagement signals (Priority: P2)

Every contact tap — Call, WhatsApp, inquiry submission — records a `lead_events` row tagged with the listing, the event type, the user (or null for anonymous), and the timestamp. The publisher can read their own listings' lead events (via the same listing-ownership RLS rule), and admins with `inquiries.view_all` can read all of them. While Phase 16 does not ship a publisher-facing analytics dashboard (that surfaces later when Phase 19's agency analytics page lands and Phase 20's admin dashboard consolidates counters), the lead-event table is the substrate every future analytics screen reads from. The `favorite_added` event type is also reserved in the enum so Phase 17 can begin writing favorites events without needing a fresh schema migration.

**Why this priority**: P2 because the marketplace operates without lead-event analytics in v1 (publishers do not yet have a "how is my listing performing" dashboard), but the underlying data must be captured from day one so the eventual analytics surface has a meaningful historical record to render. Capturing without surfacing is the correct order — building the surface before the data exists would render a blank screen for months.

**Independent Test**: Perform 5 Call taps, 3 WhatsApp taps, and 2 inquiry submissions across 3 different listings in 3 different publisher accounts. Query the `lead_events` table directly. Confirm: (a) 10 rows total exist with matching event types, listing_ids, and timestamps, (b) for each row the `user_id` is null if the action was anonymous or set if the action was signed-in, (c) rapid repeat taps from the same user on the same listing each get their own row (no client-side dedup). Sign in as publisher-A and query the lead events surface (if the spec exposes one — it is not user-facing in Phase 16, but a privileged-read SQL path or a future admin tool must work); confirm publisher-A sees only their listings' events. Sign in as an admin with `inquiries.view_all`; confirm they see every event across every publisher.

**Acceptance Scenarios**:

1. **Given** any of the three contact actions (Call, WhatsApp, inquiry submit) occurs on an approved listing, **When** the action is processed, **Then** exactly one `lead_events` row is inserted with the correct `event_type` (`phone_revealed`, `whatsapp_clicked`, or `inquiry_sent`), the correct `listing_id`, the visitor's `user_id` (or null), and a server-generated `created_at` timestamp.
2. **Given** a visitor performs the same action multiple times within a short window, **When** each action is processed, **Then** each action inserts its own row — no client-side or server-side deduplication is applied at the row level.
3. **Given** the IMPLEMENTATION_PLAN §6.3 inquiry-status enum reserves `favorite_added` for Phase 17, **When** Phase 16's `lead_events` table is created, **Then** the `event_type` CHECK constraint (or enum) allows at least `phone_revealed`, `whatsapp_clicked`, `inquiry_sent`, AND `favorite_added` so Phase 17 can write events without schema modification.
4. **Given** the lead-event write path is invoked, **When** the request is processed, **Then** the row is inserted whether the corresponding launcher (dialer, WhatsApp, browser) ultimately succeeds or fails — the event captures intent, not completion.
5. **Given** publisher-A signed in queries the lead events surface, **When** the response is computed, **Then** it contains every lead event on every listing publisher-A owns AND zero events on listings publisher-A does not own.
6. **Given** an admin with `inquiries.view_all` queries the lead events surface, **When** the response is computed, **Then** it contains every event across every publisher.
7. **Given** the `lead_events` table accumulates many rows in a v1-scale catalog, **When** publisher-A queries their own listings' events with a reasonable date filter, **Then** the response is computed efficiently (indexes on `(listing_id, created_at)` exist).
8. **Given** the lead events are written from a privileged server-side path, **When** an anonymous user fires a contact tap, **Then** the write succeeds despite the user having no authenticated identity AND no public client-side INSERT permission is granted on `lead_events` (the write goes through a privileged Edge Function or RPC).

### User Story 7 — Admin oversight of inquiries across the platform (Priority: P3)

An admin holding the `inquiries.view_all` permission per the Phase 6/9 catalog has a cross-publisher view of every inquiry submitted on the platform — for support cases ("Publisher X reports a missing inquiry"), for moderation cases ("Inquirer Y is spamming dozens of listings"), and for general platform-health observability. The view is read-only in v1 (admins do not write inquiry-status changes on behalf of a publisher in Phase 16; the publisher remains the sole writer of their own inbox's status workflow).

**Why this priority**: P3 because admin oversight is operational rather than user-facing — it is essential for the team running the marketplace but is not a hot-path conversion driver. Shipping with the read path in place from day one (gated by `inquiries.view_all`) is cheaper than adding it later and ensures the platform team has visibility into the inquiry pipeline as soon as it goes live.

**Independent Test**: Sign in as an admin account holding `inquiries.view_all`. Open the admin inquiries surface (Phase 16 ships the read-only listing; an admin-side UI page MAY be a thin reuse of the publisher inbox styled differently, or a separate panel — implementation detail). Confirm: (a) the admin sees every inquiry across every publisher with the decrypted callback phone visible, (b) the admin can filter by status, by listing, by publisher, by date, (c) the admin can mark an inquiry as `spam` on a publisher's behalf only if the team's operational policy permits (Phase 16 ships the data path; the operational policy is decided by the team). Sign in as a regular admin WITHOUT `inquiries.view_all` (e.g., a moderator role per §9.1 default mapping); confirm they cannot reach the admin inquiries surface AND the RLS denies any cross-publisher read.

**Acceptance Scenarios**:

1. **Given** an admin holds the `inquiries.view_all` permission, **When** they sign in, **Then** the admin-side inquiries surface is reachable via the existing admin dashboard navigation (or a new tile per Phase 20's dashboard composition).
2. **Given** an admin without `inquiries.view_all` (e.g., the default `moderator` role per §9.1), **When** they attempt to reach the admin inquiries surface, **Then** the navigation tile is hidden AND the route guard denies the request AND the RLS rejects any cross-publisher inquiries read.
3. **Given** an authorized admin queries the admin inquiries surface, **When** the response is computed, **Then** it contains every inquiry across every publisher with the decrypted callback phone visible AND the inquiry status reflects the publisher's current state (admin reads are real-time, not cached).
4. **Given** the admin marks an inquiry as `spam` on a publisher's behalf (only when operational policy permits), **When** the change persists, **Then** the publisher's own inbox reflects the change on next refresh AND the change is auditable through the standard moderation channel only if Phase 18's audit pattern is applied; Phase 16 does NOT add a new audit category for status changes per §6.4's "high volume" rule.

### Edge Cases

- **Listing has `phone` empty and `whatsapp` empty AND visitor submits the inquiry form**: The inquiry-submission path remains functional — the inquirer's typed phone is the publisher's only callback channel; the publisher's own contact fields being empty does not block inquiries. The publisher will receive the inquiry in their inbox and is responsible for using the captured callback phone.
- **Listing's `phone` and `whatsapp` are identical**: Both CTAs render normally; each tap records its own event type; no special handling.
- **The listing's `phone` value is a non-Syrian E.164 (e.g., a publisher who lives abroad uses their international number)**: The Call CTA still works (the system dialer accepts any E.164); the WhatsApp CTA also works (WhatsApp accepts any country code). No country-specific gate is imposed in v1.
- **The listing's `phone` value contains non-digit characters (spaces, dashes, parentheses)**: The Call CTA strips or accepts per the system dialer's tolerance — the `tel:` URI accepts `+`, digits, and a small set of allowed characters; the WhatsApp launcher requires strict E.164 without `+`. The Phase 10 listing form was responsible for validating and normalizing on write; Phase 16 trusts the stored value but defensively re-strips for the WhatsApp URL.
- **An inquirer submits the same message twice in rapid succession (network retry or impatient double-tap)**: Two `inquiries` rows are inserted; two `inquiry_sent` lead events are inserted. The publisher's inbox shows two duplicate rows. The publisher can mark either as `closed` to remove from the active list. Server-side dedup is NOT applied in v1.
- **An inquirer fills the form, taps submit, and the network drops mid-write**: The atomic transaction either fully commits (visible to the publisher) or fully rolls back (the visitor sees a localized error and may retry). There is NEVER a partial state where an `inquiries` row exists without its companion `lead_events` row, OR vice versa.
- **An inquirer is signed-in but their `profiles.phone` is malformed (data drift from before Phase 5 normalization)**: The inquiry form pre-populates with the stored value AND the form-level validator catches the malformation AND requires the visitor to type a corrected E.164 before submit succeeds.
- **A signed-in inquirer submits an inquiry on a listing whose publisher they have blocked, or that has blocked them**: Phase 16 does NOT introduce a publisher-block or inquirer-block feature in v1. The inquiry submission proceeds; future moderation phases may revisit.
- **A listing is approved when the inquiry is submitted, but is then `rejected`, `paused`, `sold`, `rented`, `expired`, or `deleted` afterwards**: The inquiry remains in the publisher's inbox indefinitely. The inquirer's view of the listing details page is governed by the visibility rules of those terminal states (e.g., a `deleted` listing returns a 404-equivalent — Phase 13's `_NotFoundView`). No retroactive deletion of inquiries on terminal-state listings occurs.
- **The Vault decrypt operation fails for an inquiry row (corrupt encrypted ciphertext, missing decrypt key)**: The inbox row renders with a localized "Phone unavailable" placeholder in place of the decrypted phone AND the listing's publisher (or the admin) can still see the inquirer's typed name and message AND a server-side error is logged for operations to investigate. The inbox does NOT crash or 500 on a single corrupted row.
- **The inquirer enters a phone number that is the SAME as the listing's `phone` (someone trying to contact themselves)**: The inquiry submission proceeds. The publisher will receive an inquiry whose callback phone is their own number; they will recognize this and may use `closed` to dismiss. No special self-detection is implemented (cost outweighs benefit).
- **An inquirer types a message that exceeds the 2000-character cap** (per FR-006 / Q7=B): The form's submit affordance is disabled while the typed length is over the cap AND a localized "Message too long — max 2000 characters" error renders next to the field; defense-in-depth, the server-side write path also rejects an over-cap submission with a structured error (no client-side check is ever the only check). The same cap applies to a re-submission attempt after backgrounding the app.
- **Two devices/sessions of the same publisher account flip the same inquiry's status concurrently** (e.g., publisher's phone marks `responded` while their tablet marks `closed` within the same second): Per Q8=A, last-write-wins applies — both writes succeed in the order they reach the server, the later one's value persists, the earlier one's value is overwritten. No "another session changed this" dialog is surfaced. The server-side transition CHECK from FR-021a still validates each write against the current row state (so a transition that would have been valid against the stale read but is now invalid against the current state is rejected by the CHECK, not silently clobbered). Acceptable because inquiries are personal CRM data; the publisher can re-flip if a teammate clobbered their intent.
- **The publisher has ≥ 50 inquiries on a single listing**: The inbox renders with cursor-based pagination (matching Phase 13's home-feed cursor pattern); status filters and per-listing filters help the publisher navigate.
- **The publisher tries to manipulate the status of an inquiry on a listing they no longer own (e.g., the listing was transferred to another publisher — not a v1 feature, but the RLS gate must hold)**: The RLS gate is computed on the listing's CURRENT `publisher_user_id`; if ownership changes, the prior publisher loses access to the inquiry instantly. Phase 16 does NOT add listing-transfer mechanics; this is a forward-stated constraint.
- **A junk inquiry contains a malicious URL or shell-injection-like content in the `message` field**: The `message` is stored as text and rendered as text-only (no HTML, no markdown, no link auto-detection in v1); the spec's localization-and-text-only rendering rule prevents render-time injection. The publisher uses `closed` to remove from active view per Q3=B (no Phase 16 publisher-side spam-flagging).
- **Network failure during inquiry submission**: The transactional write either fully succeeds or fully fails; the visitor sees a localized "Send failed, retry?" message and the form's state is preserved so they can re-submit without re-typing.
- **The Android system dialer (Call CTA) or WhatsApp app (WhatsApp CTA) is intentionally disabled or uninstalled**: The lead event is still recorded (per the "intent-to-call, not call-completion" rule). The launcher hand-off surfaces a localized fallback message; the visitor's recourse is to manually note the number and call from a different device.
- **A signed-in admin holding `inquiries.view_all` is also a publisher with their own listings**: They see the union of (their own listings' inquiries) and (every inquiry across the platform) through their admin lens — no special filtering is needed; the RLS gate evaluates ownership OR admin-permission as an OR, not as a conflict.

## Requirements *(mandatory)*

### Functional Requirements

#### Listing-details contact CTAs

- **FR-001**: System MUST replace the Phase 13 `ContactBlock` Coming-soon stubs (Call / WhatsApp / Send inquiry) with three working CTAs that operate on the listing's stored `phone`, `whatsapp`, and an inquiry form respectively. The Phase 13 widget surface MUST be modified only to swap the Coming-soon snackbar handlers for the working handlers; the surrounding widget tree (listing details page composition, button styles, icons, ordering) MUST NOT be reflowed by this PR.
- **FR-001a**: The Call CTA MUST be visible on the listing details page when the listing's `phone` field is non-empty AND validates as a callable phone number. When the `phone` field is empty or malformed, the Call CTA MUST be hidden (or visibly disabled with a localized hint) so that an unworkable launcher is never offered.
- **FR-001b**: The WhatsApp CTA MUST be rendered on the listing details page for every approved listing, AND its enabled-state MUST depend strictly on the listing's `whatsapp` field per Q1=B-refined: when `whatsapp` is non-empty AND validates as a callable phone number for the WhatsApp `wa.me/` URL scheme, the CTA is enabled and tappable; when `whatsapp` is empty (regardless of whether `phone` is set) OR is malformed, the CTA is visibly disabled (greyed out, non-tappable) with a localized hint explaining that the publisher did not register a WhatsApp number — the CTA is NEVER silently hidden when the rest of the contact block is rendered. The strict source-of-truth rule (no `phone → whatsapp` fallback) was chosen so that the displayed channel matches the publisher's explicit choice; the "render but disable" treatment was chosen so that the visitor sees the channel exists but is not available for this listing rather than wondering why a WhatsApp button is missing.
- **FR-001c**: The "Send inquiry" CTA MUST be visible on the listing details page for every approved listing AND regardless of whether the listing has `phone` or `whatsapp` set — the inquiry channel does NOT depend on the publisher having pre-populated contact fields, because the inquirer's typed callback phone becomes the channel.
- **FR-001d**: When the signed-in visitor is the listing's own publisher (`auth.uid() = listings.publisher_user_id`), all three CTAs MUST be hidden — a publisher inquiring on their own listing is meaningless engagement noise AND lead events for self-contact would pollute the publisher's own analytics.
- **FR-002**: Tapping the Call CTA MUST insert exactly one `lead_events` row with `event_type = 'phone_revealed'` AND `listing_id` set to the listing AND `user_id` set to the signed-in visitor (or null for anonymous) AND a server-generated `created_at`. The row MUST be inserted BEFORE the launcher hand-off begins so that the event is durable even if the launcher fails or the user backgrounds the app mid-handoff.
- **FR-003**: Tapping the Call CTA MUST then hand off to the Android system dialer pre-populated with the listing's `phone` value via the `tel:` URI scheme. The Phase 16 PR MUST NOT introduce any in-app calling, VoIP, or audio capability — the dialer is the OS's responsibility.
- **FR-004**: Tapping the WhatsApp CTA MUST insert exactly one `lead_events` row with `event_type = 'whatsapp_clicked'` AND the same column semantics as FR-002. The row MUST be inserted BEFORE the launcher hand-off begins.
- **FR-005**: Tapping the WhatsApp CTA MUST then hand off to WhatsApp via `https://wa.me/<E.164-without-plus>` so the WhatsApp app opens (or the web URL prompts to install WhatsApp if not installed). The hand-off MUST handle launcher failure gracefully — a localized "WhatsApp unavailable" or "Open URL failed" message surfaces if the OS rejects the intent.

#### Inquiry form

- **FR-006**: Tapping the "Send inquiry" CTA MUST open an inquiry form with exactly three input fields — name (required, non-empty after trim, max 100 chars), phone (required, validates as E.164 per the Phase 5 `PhoneNumber` value object), and message (required, non-empty after trim, max **2000 chars** per Q7=B) — plus a submit affordance. The message field MUST display a live character counter (e.g., "1842 / 2000") **when the typed length reaches ≥ 80% of the cap (≥ 1600 chars per research.md R-108)** so the visitor knows they are approaching the cap; below that threshold the counter MUST stay hidden to keep the form chrome uncluttered for the common case (~50–300 char messages). Submission MUST be blocked client-side when the typed length exceeds 2000 chars AND the server-side write path MUST enforce the same cap as a defense-in-depth check.
- **FR-007**: When the visitor is signed-in, the inquiry form MUST pre-populate the name field from `profiles.full_name` AND pre-populate the phone field from `profiles.phone`. The visitor MAY override either field before submitting.
- **FR-008**: When the visitor is anonymous (no Supabase Auth session), the form fields MUST render empty AND the visitor MUST type both name and phone manually AND the submission MUST proceed with `sender_user_id = null`.
- **FR-009**: Submitting the inquiry form MUST atomically (in one server-side transaction) insert exactly one `inquiries` row AND exactly one `lead_events` row with `event_type = 'inquiry_sent'`. If either insert would fail, the entire transaction MUST roll back — there MUST NEVER be an `inquiries` row without its companion `lead_events` row OR vice versa.
- **FR-010**: The `inquiries` row MUST persist the inquirer's typed phone via Supabase Vault per ADR-0001 — the column MUST be encrypted at rest AND MUST NOT be exposed via a standard `SELECT inquirer_phone FROM inquiries` query path AND MUST be reachable in decrypted form only through a privileged decrypt view whose RLS gate matches FR-022 below.
- **FR-011**: Submitting the inquiry form MUST surface a localized success confirmation to the visitor AND return them to the listing details page. The visitor MUST NOT be offered an in-app "my inquiries" tracking view in v1 — the captured callback phone is the publisher's response channel and is sufficient.
- **FR-012**: Validation failures on the inquiry form (malformed phone, empty fields) MUST surface localized field-level error messages AND prevent submission AND MUST NOT insert any `inquiries` or `lead_events` rows.

#### Tables, indices, and the server-side write path

- **FR-013**: System MUST create a new `public.inquiries` table with at minimum the columns: `id` (UUID primary key, server-generated default), `listing_id` (UUID, foreign key to `public.listings(id)` with `ON DELETE RESTRICT` per Q4=C — listings use soft-delete via `status='deleted'` per Phase 10's enum, so the FK defends against accidental hard-deletes and preserves inquiry history for the "Listing deleted" inbox affordance), `sender_user_id` (UUID nullable, foreign key to `auth.users(id)` with `ON DELETE SET NULL`), `sender_name` (TEXT, CHECK `length(trim(sender_name)) BETWEEN 1 AND 100`), `inquirer_phone` (Vault-backed encrypted column per ADR-0001), `message` (TEXT, CHECK `length(trim(message)) BETWEEN 1 AND 2000` per Q7=B), `status` (TEXT with CHECK constraint allowing exactly `new`, `seen`, `responded`, `closed`, `spam` per IMPLEMENTATION_PLAN §6.3), `created_at` (TIMESTAMPTZ, server default `now()`), `updated_at` (TIMESTAMPTZ, server default `now()`, refreshed by a trigger on every status mutation).
- **FR-014**: System MUST create a new `public.lead_events` table with at minimum the columns: `id` (UUID primary key, server-generated default), `listing_id` (UUID, foreign key to `public.listings(id)` with `ON DELETE RESTRICT` per Q4=C — same rationale as FR-013), `user_id` (UUID nullable, foreign key to `auth.users(id)` with `ON DELETE SET NULL`), `event_type` (TEXT with CHECK constraint allowing exactly `phone_revealed`, `whatsapp_clicked`, `inquiry_sent`, `favorite_added` — the last is reserved for Phase 17 and is part of this migration so Phase 17 does NOT need a schema change), `metadata` (JSONB nullable, populated by the server-side write path with `{ip, user_agent}` per Q5=B for forensic / abuse-investigation use — the column MUST NOT be selectable by anonymous or non-admin authenticated clients), `created_at` (TIMESTAMPTZ, server default `now()`).
- **FR-014a**: The server-side write path for lead events (per FR-016) MUST capture the requesting client's IP address and user-agent string from the incoming request and persist them into `lead_events.metadata` as `{ip: "<v4/v6>", user_agent: "<string>"}` per Q5=B. The capture MUST happen on every lead-event insert — `phone_revealed`, `whatsapp_clicked`, and `inquiry_sent` — regardless of whether the visitor is signed in or anonymous. The Edge Function or RPC reads the IP from the trusted server-side request context (NOT from a client-supplied header), so a malicious client cannot spoof the captured IP.
- **FR-014b**: The RLS posture on `lead_events` MUST gate the `metadata` column's visibility per Q5=B: the listing's publisher (when reading their own listings' events) MUST see every column EXCEPT `metadata` — the publisher receives `id`, `listing_id`, `user_id`, `event_type`, `created_at` but not the IP or user-agent. Admins holding `inquiries.view_all` MUST see every column INCLUDING `metadata`. Anonymous clients MUST NOT read `lead_events` at all (no public read policy). The masking MUST be enforced at the data layer — either by exposing the publisher-readable subset through a view that omits `metadata`, or by a column-level GRANT, or by a SECURITY DEFINER reader RPC. An application-layer "just don't show it" filter is NOT sufficient per Constitution Principle III.
- **FR-015**: System MUST create indexes that support the publisher inbox's primary access pattern — at minimum an index on `inquiries(listing_id, created_at DESC)` for per-listing chronological reads AND an index on `lead_events(listing_id, created_at DESC)` for per-listing lead-event reads. A status-filter index on `inquiries(listing_id, status, created_at DESC)` MAY be added if EXPLAIN analysis at plan time confirms it pays off at v1-scale.
- **FR-016**: Inserting an `inquiries` row OR a `lead_events` row from the Flutter client MUST go through a privileged server-side write path (an Edge Function or SECURITY DEFINER RPC) that performs input validation (E.164 phone validity, non-empty fields, listing existence and approved-status, ownership-self-check per FR-001d) AND inserts the row(s) atomically AND returns either a success confirmation or a structured error code. No direct table INSERT permission MUST be granted to `anon` or `authenticated` clients on either `inquiries` or `lead_events`.
- **FR-017**: The atomic write for an inquiry submission MUST insert the `inquiries` row first, then the companion `inquiry_sent` `lead_events` row, in the same transaction. If either insert fails, the transaction MUST roll back; the client MUST receive a structured error indicating which validation failed.
- **FR-018**: The write path MUST validate that the target `listing_id` references an existing listing whose `status = 'approved'` AND whose `phone` is non-empty for `phone_revealed` events, whose `whatsapp` (or `phone` per Q1) is non-empty for `whatsapp_clicked` events, with no field constraint for `inquiry_sent` events. Writes for `favorite_added` are deferred to Phase 17 (the enum value is reserved here but Phase 16 ships no write path for it).

#### Publisher inbox

- **FR-019**: System MUST ship a new feature folder at `lib/features/inquiries/` containing the publisher-facing inbox page, its BLoC, repository, and data source. Per Q6=B, the page MUST be reachable via a **top-level navigation entry** ("Inquiries") that is visible ONLY to users who own at least one approved listing (i.e., a user whose `listings` rows include at least one with `status = 'approved'`). The entry MUST NOT be a profile-page tile (Option A rejected: too buried) and MUST NOT require navigating through the publisher dashboard first. Exact placement on the navigation surface (drawer item, app-bar action, dedicated tab, or home-shell entry alongside the Phase 15 map tile) is plan-time, but the entry MUST satisfy these properties: (a) reachable from the home shell in at most one tap, (b) consistently positioned across app launches, (c) styled per Phase 2 design tokens. The entry MUST be hidden from users who own zero approved listings (anonymous visitors, browser-only accounts, publishers whose first listing is still in `pending_review`, etc.) so it does not clutter non-publisher UI.
- **FR-019a**: The top-level Inquiries entry per FR-019 MUST display an **unread-count badge** showing the number of inquiries whose `status = 'new'` across every listing the signed-in publisher owns. The badge MUST update on (a) every fresh app foreground-resume, (b) every pull-to-refresh / re-open of any surface that hosts the entry, and (c) immediately after the publisher reads an inquiry (which auto-transitions `new → seen` per FR-021 and therefore decrements the badge by 1). The badge MUST be hidden (or render as zero) when there are no `new` inquiries; it MUST NOT show stale counts after a status change. The badge is the day-one push-equivalent affordance until Phase 22 ships FCM push notifications for new-inquiry events.
- **FR-020**: The publisher inbox MUST display every inquiry on every listing the signed-in publisher owns, sorted by `created_at DESC` (newest first), with each row showing: the inquirer's `sender_name`, the decrypted `inquirer_phone`, a snippet of the `message` (truncated to a localizable maximum length), the listing's title (so the publisher knows which listing the inquiry is about — a publisher with multiple listings needs this orientation), the inquiry's current `status`, and the `created_at` timestamp formatted per Phase 9's locale rules.
- **FR-021**: Tapping a row in the inbox MUST navigate to (or expand into) a per-inquiry detail view showing the full message body, the listing reference (tappable, navigating to the Phase 13 listing details page), the decrypted callback phone, the inquirer's name, and a status-mutation control. Opening this view MUST auto-transition the inquiry's status from `new` to `seen` (if currently `new`) so the publisher sees a clean "what's new since I last checked" feed on return.
- **FR-021a**: The status-mutation control on the per-inquiry view MUST allow the publisher to advance an inquiry through the forward path per Q2=B (soft-terminal): `new → seen` (auto on read, per FR-021), `seen → responded` (explicit), `responded → closed` (explicit), `closed → seen` (explicit reopen), AND `closed → responded` (explicit reopen). The transition `closed → new` MUST NOT be permitted — the `new` state's "never been opened" semantics are preserved by forbidding regression into it AND no UI affordance for `closed → new` MUST exist. All other regressions (e.g., `responded → seen`, `seen → new`) MUST also be forbidden — forward progression and `closed`-reopen are the only allowed direction set. The state-machine rules MUST be enforced server-side by an UPDATE policy CHECK or trigger on `inquiries`, not merely by hiding UI affordances.
- **FR-021b**: Per Q3=B, Phase 16 MUST NOT surface a "Mark as spam" affordance in the publisher inbox UX — the `spam` enum value exists in the `status` CHECK constraint for forward use (admin moderation in a later phase, or Phase 18's report-and-resolve flow may set it) but no Phase 16 UI MUST write `spam`. A publisher who receives junk inquiries MUST use the `closed` status (which is reversible per FR-021a if needed) or report them via the forward-stated Phase 18 report mechanism when it lands. The `spam` filter view in the inbox (FR-025) MAY exist as a read-only section so that admin-set or future-set spam rows are still discoverable to the publisher; the inbox MUST NOT crash if a `spam` row appears even though Phase 16 ships no write path to that state from the publisher side.
- **FR-022**: The publisher inbox's data read MUST enforce strict RLS: the SELECT policy on `inquiries` MUST permit a row IF AND ONLY IF the requesting user (a) is the signed-in publisher whose `auth.uid()` equals the row's `listing.publisher_user_id`, OR (b) is the signed-in original sender whose `auth.uid()` equals the row's `sender_user_id` (when non-null), OR (c) holds the `inquiries.view_all` permission. No other reader path MUST exist. Anonymous reads MUST be denied entirely.
- **FR-023**: The privileged decrypt view for `inquirer_phone` MUST apply the same three-tier rule as FR-022 — only the listing's publisher, the original sender (when signed-in), and admins with `inquiries.view_all` MUST decrypt. Any other reader MUST see the encrypted Vault column without a viable decryption path.
- **FR-024**: Publisher status mutations (`new → seen`, `seen → responded`, `responded → closed`, `closed → seen`, `closed → responded`) MUST go through an UPDATE policy on `inquiries` gated by the publisher-ownership rule (the requesting user's `auth.uid()` matches `listing.publisher_user_id`). Sender-side updates MUST NOT be permitted (the sender cannot modify their own inquiry's status — they have no inbox-equivalent). The transition allowlist is enforced server-side per FR-021a (UPDATE policy CHECK or row trigger); the publisher's UI is one consumer of the same rule, not the only enforcer.
- **FR-024a**: Per Q8=A, concurrent status mutations on the same inquiry from two devices/sessions of the same publisher account (or two members of a shared-account agency setup) MUST follow **last-write-wins** semantics — the spec MUST NOT introduce optimistic concurrency control (no `WHERE updated_at = <client-read-timestamp>` predicate) and MUST NOT introduce a row-level lock or `SELECT FOR UPDATE` serialize. The server-side transition CHECK from FR-021a still rejects invalid transitions regardless of which write wins (e.g., if Device-1 wins the race to set `closed` and then Device-2 tries to write `responded` from a stale `seen` read, the CHECK validates the new transition against the current row's status — `closed → responded` is allowed per Q2=B, so the late write wins cleanly; if a write would violate the transition allowlist, it is rejected by the CHECK rather than by an optimistic version check). The trade-off is intentional: inquiries are personal CRM data, not financial transactions; the occasional clobbered status update is cheap to re-flip; the conflict-detection UX cost is high relative to the value.
- **FR-025**: The publisher inbox MUST support filtering by inquiry status (e.g., show only `new`, only `seen`, only `responded`, only `closed`) AND filtering by listing (when the publisher owns more than one listing) AND sorted-by-newest by default. A read-only `spam` filter MAY exist for forward-state admin-set rows per FR-021b, but the inbox MUST function correctly whether or not the `spam` filter is exposed in v1.
- **FR-026**: The publisher inbox MUST handle a corrupted Vault decrypt on a single row by rendering a localized "Phone unavailable" placeholder in that row's phone slot — the row MUST still render (with name, message, status, timestamp) AND the inbox MUST NOT crash, blank, or 500 on a single corrupted row.

### Key Entities

- **Inquiry**: A written contact submission from a visitor (signed-in or anonymous) to a listing's publisher. Carries the inquirer's name, encrypted callback phone, and free-form message, plus the inquiry's current `status` in the four-state workflow (`new → seen → responded → closed`) plus the `spam` side-branch. The inquiry is owned by the listing's publisher; the signed-in inquirer can read their own outbound submission; admins with `inquiries.view_all` can read all inquiries.
- **Lead Event**: A lightweight engagement signal tagged with the listing, the event type (`phone_revealed`, `whatsapp_clicked`, `inquiry_sent`, plus the reserved-for-Phase-17 `favorite_added`), the visitor's user-id (or null for anonymous), and the server-generated timestamp. Lead events accumulate engagement data for the publisher's eventual analytics surface; Phase 16 ships the data substrate but no analytics dashboard.
- **Inquiry Status**: A finite-state enumeration drawn from IMPLEMENTATION_PLAN §6.3 — `new`, `seen`, `responded`, `closed`, `spam`. The publisher-driven path in Phase 16 is `new → seen → responded → closed` (forward-only on the way out); `closed` is a soft terminal state — it MAY be reopened to `seen` or `responded` per Q2=B but MAY NOT regress to `new`. `spam` is reserved for forward admin-side use per Q3=B; no Phase 16 publisher-write path to `spam` exists.
- **Publisher Inbox**: The publisher-facing surface that lists every inquiry on every listing they own, with status filters, per-listing filters, and per-inquiry status-mutation controls. The inbox is the publisher's view of the inquiry pipeline; v1 ships no inquirer-side equivalent.
- **Vault-Decrypted Inquirer Phone**: The plaintext callback phone reachable only through the privileged decrypt view, gated by the same three-tier rule as the `inquiries` table SELECT policy — listing publisher, signed-in original sender, admin with `inquiries.view_all`.

> **Terminology clarification**: This spec uses three closely-related terms for the same field at different layers. They are intentional cross-layer naming, not drift:
> - **"inquirer phone"** — the spec-level user-domain name (the phone number the inquirer typed in the form).
> - **"callback phone"** — the publisher-UX-level name (what a publisher sees in the inbox as "the number to call back").
> - **"decrypted phone"** — the data-layer entity field name (`Inquiry.decryptedPhone`, populated by the `decrypt_inquirer_phone(uuid)` function).
>
> All three refer to the same Vault-encrypted column `public.inquiries.inquirer_phone_encrypted`, surfaced via the `v_inquiries_inbox.inquirer_phone_decrypted` view projection. The encryption-at-rest and three-tier-decrypt contract is identical regardless of which name the reader encounters.

## Clarifications

### Resolved — Session 2026-05-25

Three plan-shaping decisions resolved during `/speckit-specify` before validation. Answers are folded into the spec's Functional Requirements (FR-001b, FR-021a, FR-021b, FR-025), User Stories (US2 acceptance scenario 5, US4 narrative + Independent Test + acceptance scenarios 5 and 9), Edge Cases, and Key Entities.

- **Q1 — WhatsApp CTA visibility when only `phone` is set**: When the listing's `whatsapp` field is empty but `phone` is set, should the WhatsApp CTA fall back to `phone` (assuming most Syrian numbers are WhatsApp-reachable), or hide the CTA entirely (treating `whatsapp` as the strict source of truth)? → **B-refined: Strict source-of-truth, with "render but disable" treatment instead of hiding.** The WhatsApp CTA is rendered on every approved listing's details page but is enabled only when the listing's `whatsapp` field is non-empty AND validates. When `whatsapp` is empty or malformed, the CTA is visibly disabled (greyed out, non-tappable) with a localized hint explaining that the publisher did not register a WhatsApp number. The strict source-of-truth rule (no `phone → whatsapp` fallback) was chosen so the displayed channel matches the publisher's explicit choice; the "render but disable" treatment was chosen so the visitor sees the channel exists rather than wondering why a WhatsApp button is missing on some listings but not others. See FR-001b and US2 acceptance scenario 5.
- **Q2 — `closed` status reopen rule**: Should the `closed` status be a hard terminal state (no reopening), a soft terminal state (publisher can reopen back to `seen` or `responded`), or fully reversible across all transitions including `closed → new`? → **B: Soft terminal — reopen to `seen` or `responded` only.** The publisher MAY reopen a `closed` inquiry to `seen` (e.g., "actually I want to revisit this") or to `responded` (e.g., "I already responded but the matter resurfaced") but MAY NOT regress it to `new`. The "never been opened" semantics of `new` are preserved by forbidding any path into it from a non-fresh state. All other regressions (`responded → seen`, `seen → new`) are also forbidden. Server-side UPDATE policy CHECK/trigger enforces the rule, not merely UI hiding. See FR-021a and US4 acceptance scenario 9.
- **Q3 — Publisher-self-service spam-flagging**: Should the publisher inbox surface a "Mark as spam" affordance in Phase 16, or should the `spam` enum value exist in the schema for forward use without UX in Phase 16 (admin-only deferral)? → **B: Reserved for forward use only — no Phase 16 publisher-side UX.** The `spam` enum value exists in the `status` CHECK constraint so admin-side moderation in a later phase (or Phase 18's report-and-resolve flow) can set it without a schema change, but Phase 16 ships no publisher-side affordance to write `spam`. Publishers who receive junk inquiries use `closed` (which is reversible per Q2=B if needed) or report via the forward-stated Phase 18 report mechanism when it lands. The inbox MUST still render rows whose status is `spam` (set by admin or a future flow) without crashing, but a `spam` filter view in the inbox is OPTIONAL in v1. See FR-021b, FR-025, US4 narrative + acceptance scenario 5, and Edge Cases (junk-inquiry handling).

### Session 2026-05-25 (clarification pass)

- Q: What `ON DELETE` behavior should `inquiries.listing_id` and `lead_events.listing_id` foreign keys carry? → A (Q4=C): `ON DELETE RESTRICT`. AlNujom uses soft-delete via `status='deleted'` (Phase 10's enum), so listing rows are never hard-deleted in normal operation; the FK `ON DELETE RESTRICT` defends against accidental hard-deletes (e.g., a future admin tool or migration mistake) and preserves inquiry history needed for the "Listing deleted" inbox affordance per the Edge Cases. CASCADE was rejected because it would wipe valuable inquiry history; SET NULL was rejected because orphaning `listing_id` would break the inbox row's listing-title display. See FR-013 and FR-014.
- Q: What IP / user-agent capture posture should `record_lead_event` carry per IMPLEMENTATION_PLAN §6.7? → A (Q5=B): Capture IP and user-agent into `lead_events.metadata` JSONB on every event, **visible to admins only** via `inquiries.view_all`. The listing's publisher reads every column EXCEPT `metadata` (no IP, no UA in their response); admins read every column INCLUDING `metadata`; anonymous clients read nothing. The masking is enforced at the data layer (column-restricted view, column GRANT, or SECURITY DEFINER reader RPC) — not in application code. Rationale: marketplace publishers don't operationally need raw IPs (they consume aggregate engagement signals — "100 phone reveals this month"); admins do need them for abuse investigation; capturing now preserves forensic utility without leaking identifying data into every publisher's inbox. Matches Aqarmap / Bayut / Property Finder convention. See FR-014, FR-014a, FR-014b, SC-016.
- Q: What UX shape should the publisher inbox's entry point take? → A (Q6=B): A **top-level navigation entry** ("Inquiries") with an **unread-count badge** showing the count of `status='new'` inquiries, visible ONLY to users who own ≥ 1 approved listing. The entry MUST be reachable from the home shell in at most one tap and consistently positioned across launches; the badge MUST update on app foreground-resume, on pull-to-refresh, AND immediately after the auto `new → seen` transition (decrementing in real time). Exact placement (drawer item / app-bar action / dedicated tab / home-shell tile alongside Phase 15's map tile) is plan-time; the requirement is prominence + count-badge + visibility-gate. The badge is the day-one push-equivalent affordance until Phase 22 ships FCM push notifications. Profile-page-tile (A), publisher-dashboard-tile (D), and both-A-and-B (C) were rejected as either too buried (A, D) or unnecessary UI clutter (C). Matches the Phase 15 Q8=B precedent of "prominent first-class entry, not buried." See FR-019, FR-019a, SC-017.
- Q: What should the maximum length of the inquiry `message` field be? → A (Q7=B): **2000 chars**. Bounded `CHECK (length(trim(message)) BETWEEN 1 AND 2000)` on the column, mirrored by client-side validation with a live counter when typing approaches the cap, mirrored by server-side defense-in-depth in the write path. 2000 chars accommodates serious multi-question real-estate inquiries (Arabic in particular has higher information density per character than English) without admitting junk blobs; matches Aqarmap / Property Finder convention. Inbox `message`-snippet truncation logic can size against a known upper bound. The `sender_name` field is also bounded at 100 chars on the same defense-in-depth principle. 500 (A) was rejected as cramped for multi-question Arabic inquiries; 5000 (C) was rejected as unnecessarily generous; unbounded (D) was rejected as vulnerable to junk-blob abuse. See FR-006, FR-013, and Edge Cases (message-too-long).
- Q: How should the spec handle concurrent inbox status mutations from two devices/sessions of the same publisher account? → A (Q8=A): **Last-write-wins** with no optimistic concurrency control and no row-level serialize. The server-side transition CHECK from FR-021a still validates each write against the current row state, so an invalid transition is rejected by the CHECK rather than silently clobbered. The trade-off is intentional: inquiries are personal CRM data (not financial), the cost of an occasional clobbered status update is cheap to re-flip, and the conflict-detection UX cost (a "someone else changed this — refresh?" dialog) is high relative to the value. Optimistic concurrency (B) and row-lock serialize (C) were both rejected as overkill for the data class. See FR-024, FR-024a, and Edge Cases (concurrent status mutations).
