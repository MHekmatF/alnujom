# Feature Specification: Listing Approval Workflow

**Feature Branch**: `012-listing-approval`
**Created**: 2026-05-23
**Status**: Draft (clarifications resolved 2026-05-23)
**Input**: User description: "Phase 12 — Listing approval workflow. Goal: Admins with `listings.approve` review pending listings, approve or reject with reason; approved listings become public. Backend: Edge Functions `approve_listing`, `reject_listing` (permission check + transition + audit + status_history + optional notification stub); RLS update — public read where `status = 'approved'`. Frontend: `lib/features/admin/listing_review/` — pending queue, listing preview (full-fidelity render), approve / reject buttons, reject-reason dialog (with localized reason presets + free text). Publisher dashboard shows rejection reason on rejected cards with a 'Resubmit' button. Acceptance: admin approves a pending listing → it appears in any anonymous client's home feed; admin rejects with reason → publisher sees reason in My Listings; both transitions write audit logs. Authored per docs/IMPLEMENTATION_PLAN.md §Phase 12."

> **Status**: Draft (clarifications resolved 2026-05-23 — see `Clarifications` section)
>
> **Scope note**: Phase 12 introduces the *moderation surface* that flips a listing from `pending_review` to either `approved` (public) or `rejected` (returned to the publisher with a reason). It does NOT change Phase 10's listings schema (Phase 10 owns the five listings tables + the status-transition trigger + the `submit_listing` RPC); it does NOT change Phase 11's media schema or bucket policies (Phase 11 owns `public.listing_media` + the two storage buckets + their RLS); it does NOT render the public home feed or details page (Phase 13 owns the home + listing-details surfaces); it does NOT ship search or map (Phases 14 / 15); it does NOT ship contact / inquiry surfaces (Phase 16); it does NOT ship push or Realtime notification fan-out (Phase 22 owns push, Phase 17 owns in-app notifications if any). Phase 12 ships exactly: (a) two new server-side mutators (`approve_listing` and `reject_listing` — RPC vs Edge Function is Q1) that gate on `listings.approve` / `listings.reject` permissions, flip `public.listings.status`, set `published_at` on approve and persist a rejection reason on reject, write a `listing_status_history` row, and emit an `audit_logs` row; (b) the public-read-when-approved RLS amendment on `public.listings` (Phase 10's existing public-read policy is verified end-to-end against real `approved` rows; Phase 11's `listing_media` and storage policies already read `public.listings.status` at request time so they immediately reflect the new flag without an additional edit); (c) the admin "Pending review" queue page with full-fidelity listing preview (consumes Phase 10's listing entities + Phase 11's `listing_media` rows), approve / reject buttons, and a reject-reason dialog with localized presets + free text; (d) the publisher dashboard amendment showing the rejection reason on rejected cards (Phase 10's `MyListingsPage` Rejected filter already renders rejected cards — Phase 12 adds the reason text + a "Resubmit" button that deep-links to the Phase 10 form for the rejected listing per Phase 11 Q3=A edit-in-place semantics).

## Clarifications

### Session 2026-05-23

The three questions below were resolved in-session before `/speckit-plan`. They pin the mutator architecture (Q1 ends the RPC-precedent streak — Phase 12 ships the project's first Edge Functions following IMPLEMENTATION_PLAN §6.7 verbatim), the approved-listing lifecycle (Q2 sets `expires_at` to NULL so approved listings stay public indefinitely), and the reject-reason taxonomy (Q3 picks the publisher-actionable Minimal-5 set rather than the broader report-reason mirror). Answers are folded into the "Functional Requirements", "Success Criteria", "Edge Cases", and "Assumptions" sections below.

- **Q1 — Server-side mutator pattern: SECURITY DEFINER RPC vs Edge Function**: The IMPLEMENTATION_PLAN §6.7 names `approve_listing` and `reject_listing` as Edge Functions; the project's actual precedent across Phases 7 / 9 / 10 / 11 has uniformly chosen SECURITY DEFINER RPCs. → **B: Edge Function (follow IMPLEMENTATION_PLAN §6.7 verbatim).** Phase 12 ships the project's FIRST two Edge Functions under `supabase/functions/approve_listing/index.ts` and `supabase/functions/reject_listing/index.ts` (Deno + TypeScript runtime). Each function: (a) extracts the caller's JWT from the request `Authorization` header; (b) creates a Supabase client bound to that JWT (`createClient(SUPABASE_URL, SUPABASE_ANON_KEY, { global: { headers: { Authorization } } })`); (c) calls Phase 6's `current_user_has_permission('listings.approve' | 'listings.reject')` RPC to verify permission (the JWT-bound client makes the permission check honor the user's actual roles); (d) on permission success, creates a separate service-role-bound Supabase client (`SUPABASE_SERVICE_ROLE_KEY`) to perform the privileged UPDATE on `public.listings` and the `log_audit()` call (the service-role client bypasses RLS; the permission check above is the authoritative gate); (e) returns a structured JSON payload with success state or a typed error. This is a hard reversal of Phase 11's R-36 invariant ("zero new Edge Functions"); the reversal is justified by IMPLEMENTATION_PLAN §6.7's explicit naming AND the future-spec Phase 17 / Phase 22 expectation that notification fan-out will hang off the same Edge Function entry points (an RPC cannot trivially call external Push services; an Edge Function can). The plan-time research file documents the new precedent + the deployment story (Supabase CLI `supabase functions deploy approve_listing` / `reject_listing`; secrets `SUPABASE_SERVICE_ROLE_KEY` already provisioned per ADR-0001 prep in Phase 4). Future phases MAY revert to RPCs for non-notification-bearing mutators (the Edge Function pattern is not retroactive to Phases 7-11; their RPCs remain). The R-05 invariant (`log_audit()` reuse unchanged) is preserved — the Edge Functions invoke `log_audit()` via the service-role client; the function body itself is untouched.
- **Q2 — Default publish-window on approval**: When `approve_listing` flips `status='approved'`, what does it set `expires_at` to? → **A: NULL — no automatic expiry.** The `approve_listing` Edge Function sets `published_at = now()` AND leaves `expires_at = NULL` (the column's default). Approved listings remain publicly visible indefinitely until a publisher / admin explicitly transitions them out of `approved` (e.g., to `paused`, `sold`, `rented`, or `deleted` via future-spec moderation actions). The Phase 10 public-read RLS already encodes the `expires_at IS NULL OR expires_at > now()` predicate, so the NULL value naturally satisfies the publish-window-open clause. The Syrian real-estate market context informs this choice — listings often persist for months (matches Aqarmap-style markets), and a 30/60/90-day forced-expiry would create publisher renewal friction without a corresponding business-rule justification in v1. Phase 23 (admin settings) MAY introduce an `app_settings.default_listing_expiry` row + a corresponding mutator amendment if the team later wants per-deploy configurable expiry; Phase 12 itself does not write to `app_settings`. The "expired listings" UX (renewal CTA, expiration warnings) is consequently OUT of Phase 12 scope — no listing ever auto-expires under Q2=A. The Phase 14 search filter "exclude expired" is a no-op until a future spec introduces auto-expiry.
- **Q3 — Rejection-reason preset taxonomy**: The reject-reason dialog surfaces localized presets + a free-text fallback. What are the v1 presets? → **A: Minimal (5 specific presets + Other).** The Phase 12 reject-reason dialog exposes EXACTLY six preset keys, each with a paired ARB label in `ar` AND `en`: (1) `missing_or_low_quality_photos` ("Photos missing or low quality"), (2) `incorrect_location` ("Location is incorrect or imprecise"), (3) `unrealistic_price` ("Price appears unrealistic"), (4) `incomplete_description` ("Description is incomplete or unclear"), (5) `duplicate_listing` ("Duplicate of an existing listing"), (6) `other` ("Other — please provide details"). When `reason_preset='other'` is selected, the free-text "Additional details" field is treated as effectively required at the UX layer (a localized hint nudges the admin to provide context); the server-side validator in `reject_listing` does NOT enforce this — even when `reason_preset='other' AND reason_detail IS NULL`, the call succeeds (Q3 explicitly chose Minimal-5+Other over the more constraining Industry-aligned-10 because the publisher-actionable presets are the primary value; broader admin vocabulary lives in the free-text). The choice deliberately diverges from the §6.3 `report_reason` enum (`fake_listing` / `wrong_price` / `already_sold_or_rented` / `duplicate` / `spam` / `wrong_location` / `inappropriate_content` / `other` — eight values) because user-report reasons and admin-reject reasons serve different audiences: report reasons categorize *user complaints* (so the admin can route them), while reject reasons categorize *what the publisher needs to fix* (so the publisher can correct and resubmit). A future spec MAY align them if cross-surface consistency becomes a stronger requirement than publisher-clarity.
- **Q4 — Rejection-reason storage representation in `listing_status_history.reason`**: Phase 10 introduced the column as TEXT; the spec captures the requirement (queryable per-listing + machine-parseable on the preset key for future-spec notification routing) but deferred the encoding choice. → **A: JSON-encoded TEXT in the existing Phase 10 column.** Phase 12 persists the rejection reason as a JSON object literal serialized to TEXT in `public.listing_status_history.reason`, with shape `{"preset":"<preset_key>","detail":"<free_text or null>"}`. The reject_listing Edge Function builds the JSON string via `JSON.stringify({preset, detail: detail ?? null})` before the UPDATE that triggers the status-history INSERT (via session-variable handoff to the Phase 10 trigger). The publisher banner + moderation-history page consume the value via `jsonb_extract_path_text(reason::jsonb, 'preset')` AND `..., 'detail')` from the client query. NO schema migration is added in Phase 12 — Phase 10's TEXT column is reused as-is, preserving Phase 11 R-35 immutability. A future spec MAY convert the column to JSONB if cross-row analytic queries on the preset key become hot (the JSON-encoded TEXT is forward-compatible — a `ALTER TABLE ALTER COLUMN reason TYPE JSONB USING reason::jsonb` migration converts the data in place without rewriting history). Sidecar table (option C) and delimited TEXT (option D) were rejected: sidecar adds a join hop on every publisher-dashboard render for no analytic benefit in v1; delimited TEXT is fragile against newlines in preset keys or detail bodies.
- **Q5 — "Other" preset UX required-ness**: When the admin selects `reason_preset='other'` in the reject-reason dialog, must the free-text "Additional details" field be non-empty before Confirm enables? FR-013(f) currently only nudges via a hint; FR-002(g) keeps the server permissive. → **A: UX-required when `preset='other'`; server stays permissive.** The reject-reason dialog MUST disable Confirm whenever (`preset='other' AND detail.trim().length === 0`) — the admin cannot submit an "Other" rejection without providing free-text context. The localized hint from FR-013(f) ("Please describe the issue so the publisher can fix it") remains as a guidance surface above the field; the disabled-Confirm gate is the structural enforcement. The Edge Function `reject_listing` validator does NOT add a server-side check for "Other-with-no-detail" — it accepts the call (matches Q3=A's "server permissive, broader admin vocabulary lives in the free-text"); this preserves the future-spec / direct-SQL admin escape hatch AND keeps the Edge Function's input-validation surface focused on enum membership + length cap. Publisher experience benefit: every "Other" rejection in v1 carries meaningful free-text the publisher can act on (no empty-detail "Other" cards). A future spec MAY tighten the server contract if direct-SQL bypass becomes a real concern.
- **Q6 — Edge Function per-action latency target**: SC-001 sets the end-to-end admin journey at 2 minutes but no per-mutator latency budget is stated; Edge Functions have a documented cold-start window (~500ms–2s on the free tier). → **A: ≤ 2 seconds p95 per `approve_listing` / `reject_listing` invocation.** The latency budget covers the full client-to-client round-trip: client request → Edge Function cold-start (if any) → JWT validation → `current_user_has_permission` RPC call → service-role-client UPDATE on `public.listings` → status-transition trigger + `log_audit()` → JSON response back. The 2-second target is intentionally generous to accommodate Edge Function cold starts on the Supabase free tier (which is the project's deployment surface in v1) WITHOUT engineering a keep-warm cron pinger or migrating to a dedicated tier in Phase 12 — both deferred to a future spec (Phase 24 observability) if latency budgets tighten. The target is measured at the admin device (not at the Edge Function's own logs) so it includes the network leg from the Syrian publisher mobile network → Supabase region (Frankfurt or US-East per project research); typical sustained admin sessions over Syrian 4G should warm the function after the first call, so the second+ call lands well under the budget. The target is verifiable from the Supabase Edge Function logs' `duration_ms` field AND from a manual stopwatch session on the Infinix Note 8 over Syrian-realistic network conditions. Phase 22 (push + Realtime) MAY revisit this budget if Realtime fan-out adds latency overhead to the Edge Function body.
- **Q7 — Status-transition trigger `changed_by` source from Edge Function context**: Phase 10's status-transition trigger writes `listing_status_history.changed_by` AND the audit-log's `actor_user_id`; FR-001/FR-002 hedged whether the Edge Function passes the admin UID via `auth.uid()` (which is NULL under the service-role client) or via a session variable or via an explicit column. → **A: Session variable + amend Phase 10's status-transition trigger.** Phase 12 ships a NEW migration that AMENDs Phase 10's status-transition trigger function (Phase 10's migration file remains unedited per Phase 11 R-35) so the trigger sources `changed_by` via `coalesce(nullif(current_setting('app.current_user_id', true), '')::uuid, auth.uid())` — the COALESCE prefers the session-variable path (used by Edge Functions running under the service-role client) AND falls back to `auth.uid()` for direct user-JWT writes (preserving Phase 10's original semantics for non-Edge-Function callers). Both Edge Functions call `set_config('app.current_user_id', '<uid extracted from JWT>', true)` immediately BEFORE the UPDATE — the third argument `true` scopes the session variable to the current transaction only, so leak-across-requests is impossible. The same pattern applies to `log_audit()`'s `actor_user_id` (Phase 4's function already reads from `auth.uid()` per its v1 signature; Phase 4's function is amended in the same Phase 12 migration to use the same COALESCE — this is the FIRST edit to `log_audit()` since Phase 4 shipped, narrowly relaxing the R-05 invariant from "byte-identical" to "byte-identical except for the COALESCE actor-source amendment"; the amendment is a single-line change that adds session-variable fallback without breaking any existing call site). Plan-time research codifies the exact migration filename + the SQL diff (a `CREATE OR REPLACE FUNCTION` for both Phase 10's trigger AND Phase 4's `log_audit()`, leaving Phase 10's and Phase 4's original migration files unedited).
- **Q8 — Listing-preview shared-widget location (Phase 12 vs Phase 13)**: FR-011 hedged whether the gallery / price / location / amenities / description widgets live in `lib/shared/presentation/widgets/listing_display/` (Phase 12-owned, Phase 13 imports) OR `lib/features/listing_details/presentation/widgets/` (Phase 13's natural home, Phase 12 imports its export). → **A: Phase 12 builds under `lib/shared/presentation/widgets/listing_display/`.** Phase 12 ships the shared display widgets — `ListingGallery` (consumes Phase 11 `listing_media` rows ordered by `ordering ASC` with `is_main=true` first), `ListingPriceBlock` (consumes Phase 9 `listing_prices` via `MoneyFormatter`), `ListingLocationBlock` (consumes Phase 8 governorate/city/area names), `ListingAmenitiesBlock` (consumes Phase 10 `listing_details.amenities` jsonb), `ListingDescriptionBlock` (consumes Phase 10 `listing_details.description`) — all under `lib/shared/presentation/widgets/listing_display/`. The Phase 12 admin preview page composes these widgets. Phase 13's public listing-details page MUST import the same widgets — no second implementation, no drift. Matches the existing project convention from Phase 2 (design tokens + shared widgets live in `lib/shared/presentation/` and `lib/core/widgets/`). The widgets MUST be Constitution IX-clean (no `package:supabase_flutter` imports) AND Constitution V-clean (every user-visible string via `AppLocalizations`) AND Constitution VI-clean (Phase 2 design tokens only — no inline magic numbers). The widgets accept domain entities as constructor inputs (e.g., `ListingGallery({required List<ListingMedia> media})`), so the BLoC layer responsible for fetching the underlying rows is owned by the consumer (Phase 12 BLoC for the preview surface; Phase 13 BLoC for the public surface) — no shared BLoC ships in Phase 12.

> **Folded default — concurrent-admin lock semantics** (last-writer-wins with status-guard vs optimistic version column vs pessimistic row lock) is folded into Edge Cases below; the default is **last-writer-wins with a status-guard predicate** (the Edge Function's UPDATE includes `AND status='pending_review'` so a second admin acting after the first sees zero rows affected and receives a structured "already_acted_on" error). This is the industry-standard pattern for low-contention admin queues and matches Phase 10's submit_listing concurrency model.
>
> **Folded default — notification stub scope** is folded into FR-019 below; the default is **no Phase 12 notification subsystem** — the publisher sees state changes on next `MyListingsPage` refresh. The IMPLEMENTATION_PLAN's "optional notification stub" phrasing is honored by deferring fan-out to Phase 17 (in-app notifications) and Phase 22 (push + Realtime). The Edge Function entry points from Q1=B are the natural future-spec attachment site for notification emission, which is why Q1=B over the RPC alternative. A `notifications_outbox` table or similar is NOT introduced in Phase 12.
>
> **Folded default — admin re-edit of an approved listing** (whether an admin holding `listings.edit_any` can mutate listing fields after approval) is **already covered by Phase 10's write-policy composite** (`auth.uid() = parent.publisher_user_id` OR `listings.edit_any`) and does not require new Phase 12 surface. The admin UI for editing arbitrary listings is a future-spec extension.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Admin reviews pending queue, opens a listing preview, approves it → listing becomes public (Priority: P1)

An admin user whose role grants `listings.approve` (per Phase 6's seeded role mappings — `moderator`, `admin`, `super_admin` all carry this permission) signs in and lands on the admin home (Phase 6 / Phase 7 admin tile is visible). The admin taps the new "Pending review" tile, which routes to a queue page rendering every `public.listings` row with `status='pending_review'`, ordered oldest-first by `submitted_at` (the `listing_status_history` row that transitioned the listing into `pending_review` carries the timestamp; the queue surface joins for it). Each queue card surfaces a thumbnail of the listing's main image (consumed from `public.listing_media` where `is_main=true AND kind='image'`), the title, the property type and purpose, the location (governorate / city / area names), the primary price, the publisher's display name, and the time-since-submit. The admin taps any card, which routes to a **full-fidelity preview page** that re-renders the listing exactly as Phase 13's public listing-details page will render it — same gallery widget consuming the `listing_media` rows by `ordering ASC` with `is_main=true` first, same price block, same location block, same amenities, same description — so the admin sees what the public will see. The admin scrolls through the preview, confirms the photos are watermarked (Phase 11) and the content is acceptable, taps the floating **Approve** button at the bottom of the preview. A confirmation dialog appears ("Approve this listing? It will become publicly visible.") with localized labels. The admin confirms. The form invokes the `approve_listing` mutator (Q1 — RPC or Edge Function), which: (a) re-checks the caller's `listings.approve` permission server-side; (b) re-checks the listing's current status is `pending_review` (status-guard predicate prevents the second-admin race); (c) UPDATEs `public.listings` setting `status='approved'`, `published_at=now()`, and `expires_at` per Q2's resolved default; (d) INSERTs a `listing_status_history` row with `previous_status='pending_review'`, `new_status='approved'`, `changed_by=auth.uid()`, `changed_at=now()`, `reason=NULL`; (e) emits an `audit_logs` row via the existing trigger with `action='listing.approved'`. The admin returns to the queue, which now omits that listing. From any anonymous (not-signed-in) device, opening the home feed shows the just-approved listing in the latest-listings shelf — Phase 11's storage RLS immediately permits anonymous read on the listing's media (the policy reads `public.listings.status` at request time per Phase 11 SC-025).

**Why this priority**: P1 because the marketplace cannot launch without a working approval flow — Phase 10 publishers can submit drafts to `pending_review`, but without Phase 12 those listings never become public, and the anonymous home feed (Phase 13) has zero content to render. Constitution VIII (Approval Workflow & Publisher Identity) explicitly names this as the v1 admin gate.

**Acceptance Scenarios**:

1. **Given** an admin holding `listings.approve` AND a listing in `status='pending_review'`, **When** the admin invokes `approve_listing(listing_id)`, **Then** the listing's `status` flips to `approved`, `published_at` is set to the transaction `now()`, `expires_at` is set per Q2's resolution, exactly one `listing_status_history` row is inserted for the transition, exactly one `audit_logs` row with `action='listing.approved'` is emitted, and the call returns success.
2. **Given** the approved listing, **When** an anonymous Supabase client requests it via the public-read RLS path, **Then** the row is returned; Phase 11's `listing_media` RLS AND storage-bucket RLS immediately permit anonymous SELECT on the listing's media (no additional policy edit is needed in Phase 12 — Phase 11's policies join through `public.listings.status` at request time).
3. **Given** the approved listing, **When** an anonymous Supabase Storage client fetches a media path under `<that-listing-id>/*`, **Then** Supabase Storage returns the object bytes (Phase 11 FR-007 + Phase 12 RLS combined).
4. **Given** a non-admin user (no `listings.approve` permission), **When** they attempt to invoke `approve_listing(listing_id)`, **Then** the mutator's permission re-check rejects with a structured error; the listing's status is unchanged; no `audit_logs` or `listing_status_history` row is written.
5. **Given** a listing in any status OTHER than `pending_review` (e.g., `draft`, `approved`, `rejected`, `paused`, `sold`, `rented`, `expired`, `deleted`), **When** an admin invokes `approve_listing(listing_id)`, **Then** the status-guard predicate fires (zero rows affected by the UPDATE) AND the mutator returns a structured "invalid_status_transition" error including the current status; no state change occurs; no audit row is written.
6. **Given** two admins acting simultaneously on the same `pending_review` listing, **When** both invoke `approve_listing` within the same transaction window, **Then** exactly one call succeeds (the first to commit) AND the second sees zero rows affected by the UPDATE's status-guard and receives a structured "already_acted_on" error including the new (now-approved) status.
7. **Given** the admin queue page, **When** it loads, **Then** only listings in `status='pending_review'` are visible AND they are ordered oldest-first by the `submitted_at` derived from `listing_status_history.changed_at` for the row that transitioned the listing INTO `pending_review`.

### User Story 2 — Admin rejects a pending listing with reason; publisher sees reason on rejected card and can resubmit (Priority: P1)

An admin opens a pending listing's preview page and finds the listing unacceptable — perhaps the main photo is a watermarked stock image, or the price is unrealistic, or the location is wrong. The admin taps the **Reject** button next to Approve. A modal dialog appears titled "Reject this listing — please tell the publisher why". The dialog renders Q3's resolved preset list as selectable chips / radio options, each localized via Phase 3 ARB keys; below the chips, a multi-line free-text field labeled "Additional details (optional)" allows the admin to add context. A preset MUST be selected before the Confirm button enables; the free-text field is optional and capped at 500 characters. The admin selects "Misleading or low-quality photos" + types "The main photo appears to be a stock image; please re-upload from the actual property." and taps Confirm. The form invokes `reject_listing(listing_id, reason_preset, reason_detail)` which: (a) re-checks the caller's `listings.reject` permission (note: per Phase 6's seeded mappings, `listings.reject` is paired with `listings.approve` on the same roles — `moderator`, `admin`, `super_admin`); (b) re-checks current status is `pending_review`; (c) UPDATEs `public.listings` setting `status='rejected'`; (d) INSERTs a `listing_status_history` row with `previous_status='pending_review'`, `new_status='rejected'`, `changed_by=auth.uid()`, `reason=<concatenated preset key + detail>` (the persistence format is plan-time decided); (e) emits an `audit_logs` row with `action='listing.rejected'` and a `after_state` JSONB carrying the preset key + detail. The admin returns to the queue, which now omits the rejected listing. From the publisher's `MyListingsPage` (Phase 10) under the Rejected filter, the rejected listing now renders with a **rejection-reason card** at the top: a translated label for the preset ("Misleading or low-quality photos") + the free-text detail rendered in a quoted block + a **Resubmit** button that opens the Phase 10 form pre-populated for the rejected listing (Phase 10 already established edit-in-place semantics for rejected listings; Phase 11 Q3=A established that `listing_media` rows survive the resubmit unchanged).

**Why this priority**: P1 because rejection without a reason is a closed-loop dead-end for the publisher (they cannot fix the listing); Constitution XII (No Hidden Product Decisions) AND VIII (Approval Workflow & Publisher Identity) both require the rejection to be actionable. Without a reason flow, the publisher's only recourse is to message support — friction that loses publishers on the v1 launch.

**Independent Test**: Same setup as US1. Sign in as admin, open a `pending_review` listing preview, tap Reject. Confirm the reject-reason dialog opens. Confirm the Q3-resolved presets render as localized chips / radio options. Confirm the Confirm button is disabled until a preset is selected. Select "Misleading or low-quality photos", optionally type free-text detail, tap Confirm. Verify the listing's `status='rejected'` AND `SELECT reason FROM public.listing_status_history WHERE listing_id='<that-id>' AND new_status='rejected' ORDER BY changed_at DESC LIMIT 1` returns the persisted reason (preset + detail per the plan-time decided format). Verify `SELECT * FROM public.audit_logs WHERE action='listing.rejected' AND target_id='<that-id>'` returns exactly one row with the preset + detail in `after_state`. Sign out, sign in as the listing's owning publisher, open `MyListingsPage` → Rejected filter. Confirm the listing renders with a rejection-reason card showing the localized preset label + the free-text detail. Tap the Resubmit button; confirm the Phase 10 listing form opens at step 1, pre-populated with the rejected listing's data. Edit one field, advance through steps, reach the Review step, tap Submit; confirm `submit_listing` succeeds and the listing flips to `pending_review` again. Verify `listing_status_history` now shows `pending_review → rejected → pending_review` chain.

**Acceptance Scenarios**:

1. **Given** an admin holding `listings.reject` AND a listing in `status='pending_review'`, **When** the admin invokes `reject_listing(listing_id, reason_preset, reason_detail)` with a valid preset key, **Then** the listing's `status` flips to `rejected`, exactly one `listing_status_history` row is inserted with the persisted reason, exactly one `audit_logs` row with `action='listing.rejected'` is emitted carrying the preset + detail.
2. **Given** the reject-reason dialog, **When** it renders, **Then** Q3's resolved presets appear as localized selectable chips / radio options AND a free-text field accepts up to 500 characters AND the Confirm button is disabled until a preset is selected.
3. **Given** the admin calls `reject_listing` with `reason_preset=NULL` OR a `reason_preset` value outside the Q3-resolved enum, **When** the mutator validates the input, **Then** the call is rejected with a structured "invalid_reason_preset" error; the listing's status is unchanged; no audit / status-history row is written.
4. **Given** a listing in any status other than `pending_review`, **When** an admin invokes `reject_listing`, **Then** the status-guard predicate fires AND a structured "invalid_status_transition" error is returned (matches the US1 symmetric error for approve).

### User Story 3 — Public read RLS: only approved listings appear in anonymous home feed; reverting status removes visibility immediately (Priority: P1)

Phase 10 shipped a Phase-10-scoped public-read RLS on `public.listings` that permitted anonymous SELECT only when `status='approved'` (and the publish window is open). Phase 12's `approve_listing` is the first writer that actually FLIPS a listing INTO `approved`, so until Phase 12 lands the public read path has zero rows to return. Phase 12 explicitly verifies the end-to-end policy: an anonymous Supabase client SELECTing `public.listings` returns only rows where `status='approved'` AND `published_at IS NULL OR published_at <= now()` AND `expires_at IS NULL OR expires_at > now()`. Listings in `draft`, `pending_review`, `rejected`, `paused`, `sold`, `rented`, `expired`, `deleted` are invisible to anonymous callers — verified by attempting an anonymous SELECT against a listing of each status. The owning publisher continues to see their own listings in any status (Phase 10 RLS owner-read policy). Admins with `listings.view_all` continue to see all listings in all statuses (Phase 6 / Phase 10 RLS admin-read policy). Critically, when an admin (or a future-spec admin flow) flips a listing OUT OF `approved` (e.g., back to `paused` or `rejected` via a future-spec moderation action), the listing becomes anonymous-invisible IMMEDIATELY on the next request — the policy reads `public.listings.status` at request time, not at upload time. Phase 11's `listing_media` RLS and storage-bucket RLS inherit the same property (Phase 11 SC-025), so media becomes 403 to anonymous callers at the same instant.

**Why this priority**: P1 because Constitution III (Security-First Supabase) requires the public-read predicate to be enforced at the RLS layer (not the application layer) AND verified end-to-end before launch. A leak — e.g., a draft listing's media visible to anonymous callers — is a launch-blocking defect. Phase 12 is the first phase where the public-read path is exercised against real `approved` rows.

### Edge Cases

- **Two admins both tap Approve / Reject within the same second**: Last-writer-wins with a status-guard predicate. The mutator's UPDATE includes `AND status='pending_review'`; the first commit changes status; the second's UPDATE sees zero rows affected and returns a structured "already_acted_on" error including the listing's now-current status (which the client can render as "Already approved by another admin moments ago — refresh the queue").
- **Admin approves a listing whose owning publisher was suspended since submit**: The approve succeeds at the schema layer — `approve_listing` does not re-check the publisher's status (the listing was valid at submit time). The listing's public-read RLS will surface it. A future-spec admin flow can sweep `approved` listings whose owners are now suspended and pause / hide them. Phase 12 does not auto-pause on publisher suspension; that linkage is deferred.
- **Admin rejects with no preset selected**: The reject-reason dialog's Confirm button is disabled until a preset is selected (UX gate). If a malicious caller bypasses the UX and invokes `reject_listing(reason_preset=NULL)`, the mutator's input validator rejects with a structured "invalid_reason_preset" error.
- **Admin enters free-text detail exceeding 500 characters**: The dialog's text field caps input at 500 characters at the UX layer; the mutator additionally validates server-side and rejects with "reason_detail_too_long" if bypassed.
- **Listing has zero `listing_media` rows somehow (defense-in-depth — Phase 11 FR-022 prevents this)**: The preview page renders a placeholder where the gallery would be. The admin can still approve / reject — but the SC-018 invariant would have prevented the listing from reaching `pending_review` in the first place. No new Phase 12 gate is added; Phase 11's `submit_listing` amendment is the authoritative gate.
- **Listing's `listing_media` bucket objects are missing (admin used Studio to delete a media bucket object out-of-band)**: The preview page's gallery shows a broken-image placeholder per Phase 11 edge case. The admin can still approve / reject — the schema row is what Phase 12 acts on, not the bucket object presence.
- **Publisher resubmits a rejected listing without changing anything**: The Phase 10 form's Submit button does not enforce a "must change something" check; the resubmit succeeds and the listing re-enters `pending_review`. The admin queue surfaces the listing again; the admin can re-reject (with a fresh reason).
- **Publisher tries to approve / reject their own listing via direct mutator call**: The mutator's permission re-check requires `listings.approve` (or `listings.reject`). A publisher whose role is `user` / `owner` / `agent` / `agency_admin` does NOT carry these permissions per Phase 6's seeded mappings. The call is denied with `permission_denied`.
- **Admin who has been demoted (role removed) mid-session attempts to approve / reject**: The mutator re-checks the permission against the user's current `user_roles` rows; demoted-admin's call is denied. The frontend `PermissionChecker` would also hide the approve / reject buttons if the demotion is reflected in the cached permission set (Phase 6 three-point cache refresh).
- **Approve action runs but the audit-trigger fails for some reason (e.g., `audit_logs` table is locked)**: The entire transaction rolls back — no status change, no status-history row, no audit row. Phase 4's `log_audit()` is part of the same transaction; a failure is atomic across all three writes.
- **Notification fan-out IS desired in Phase 12** (per Q5 default = NO): not in scope. The publisher sees the new status on next `MyListingsPage` refresh. Phase 17 / Phase 22 will add notifications.
- **Approved listing whose `expires_at` is set to a non-NULL value silently expires**: not applicable in Phase 12 per Q2=A — the `approve_listing` Edge Function never writes a non-NULL `expires_at`. Any expired listings in the database were transitioned to `status='expired'` manually (or via a future spec) — Phase 12 does NOT auto-expire. The Phase 10 RLS predicate `(expires_at IS NULL OR expires_at > now())` is preserved unchanged so future-spec auto-expiry can layer in without further Phase 12 changes.
- **A Phase 10 listing was submitted before Phase 12 ships but never approved (because no admin was available)**: When Phase 12 ships, the listing surfaces in the queue normally. No migration is needed; the data was already in `pending_review`.
- **Constitution III RLS amendment**: Phase 10 shipped a public-read RLS on `public.listings` with a placeholder `status='approved'` predicate. Phase 12's migration **does not introduce a new policy** if Phase 10's policy already names `status='approved'` AND `published_at IS NULL OR published_at <= now()` AND `expires_at IS NULL OR expires_at > now()`. Phase 12 verifies the policy works end-to-end against real `approved` rows. If Phase 10's policy text needs amendment (e.g., to add a tighter publish-window check), Phase 12 amends via a new migration per Phase 11 R-35 (Phase 10's migration file remains unedited).
- **Audit-log retention**: Phase 12 does not introduce audit-log retention / purge logic. Phase 23 (admin settings) may introduce retention controls. Phase 12's `audit_logs` rows persist indefinitely.
- **Trigger-before-seed audit ordering**: Following Phase 8 / 9 / 10 / 11 R-08, the migration MUST attach audit triggers BEFORE any seeded fixture rows. Phase 12 seeds zero rows (rejection-reason presets MAY ship as a seed if FR-003 / Key Entities pick a sidecar-table representation per Q3 plan-time refinement); the trigger-before-seed invariant is preserved.

#### Server-side mutators (Edge Functions per Q1=B)

- **FR-001**: System MUST ship the `approve_listing` Edge Function at `supabase/functions/approve_listing/index.ts` (Deno + TypeScript). - **Migration naming follows project convention**: Phase 12 migrations (if any beyond the optional FR-003 reason-column schema-evolution AND the optional FR-004 missing-permission seed) use the date-prefixed names established in Phase 8 R-01. The plan-time research file codifies exact filenames. SQL is idempotent via `CREATE OR REPLACE` / `ON CONFLICT DO NOTHING`.
- **Edge Function deployment story** *(new per Q1=B)*: The two new Edge Functions are deployed via Supabase CLI (`supabase functions deploy approve_listing` and `supabase functions deploy reject_listing`). Both functions read `SUPABASE_URL`, `SUPABASE_ANON_KEY`, AND `SUPABASE_SERVICE_ROLE_KEY` from the Supabase Edge runtime's secret store; the service-role key was already provisioned during Phase 4's Vault scaffolding per ADR-0001. No new repository secrets are added; the CI / deployment pipeline gains two new `supabase functions deploy` steps. The plan-time research file codifies the exact deployment flow + any local-development invocation pattern (`supabase functions serve approve_listing --env-file .env.local`).
- **R-36 reversal acknowledged** *(new per Q1=B)*: Phase 11's R-36 invariant ("zero new Edge Functions") is explicitly OVERRIDDEN in Phase 12. This is a hard reversal documented in the spec's Q1 resolution; future phases MAY revert to RPCs for non-notification-bearing mutators (the Edge Function pattern is not retroactive). The reversal is justified by IMPLEMENTATION_PLAN §6.7's explicit naming of `approve_listing` and `reject_listing` as Edge Functions AND the future-spec Phase 17 / Phase 22 expectation that the same entry points will fan out notifications (which an RPC cannot trivially do).
- **No `expires_at` autopopulation** *(new per Q2=A)*: The `approve_listing` Edge Function does NOT write to `expires_at`. The column stays NULL for every Phase-12-approved listing. The "expired listings" UX surface (renewal CTA, expiration warnings on the publisher dashboard, Phase 14's "exclude expired" filter at search-result time) is consequently a no-op in v1 — there are no expired listings until a future spec introduces auto-expiry. The Phase 10 RLS `expires_at IS NULL OR expires_at > now()` clause is preserved unchanged; the NULL path is the always-taken branch in v1.

The "Skip new tests until MVP" directive applies for the ninth time across Phases 5–12.

- **No Realtime / push in Phase 12**: Per FR-019, the publisher sees state changes on next `MyListingsPage` refresh. Realtime subscriptions on `listings` + push notifications are Phase 22's scope. The admin queue's "on-pop refresh" (US5 acceptance 5) is a pull-based refresh, not a push.

Phase 12 does NOT add a publisher-side "edit approved listing" surface; that is a future-spec extension.
