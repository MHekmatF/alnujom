# Feature Specification: Supabase Foundation

**Feature Branch**: `004-supabase-foundation`
**Created**: 2026-05-06
**Status**: Draft
**Input**: User description: "Phase 4 — Supabase base schema + RLS scaffolding. A source-controlled Supabase project with the skeleton tables every later phase depends on (profiles, user_preferences, audit_logs), RLS enabled by default, the reusable audit-trigger function in place, and the Vault scaffolding ready for later phases to encrypt secrets and admin-only PII per ADR-0001."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Remote Supabase project mirrors the version-controlled migrations (Priority: P1)

A developer (human or AI agent) writes the Phase 4 migrations as SQL files in `supabase/migrations/` and applies them to the remote Supabase project via the Supabase MCP server. The remote project's schema — every table, enum, trigger, helper function, RLS toggle, policy, and the Vault scaffolding — matches the checked-in `.sql` files exactly. There are no hand-applied changes living only inside the remote Supabase Studio session that aren't traceable to a checked-in file. If the team ever needs to swap to a different Supabase project (different region, different organization, eventually the Phase-IX custom backend), the entire Phase-4 schema is recoverable by re-applying the same migration files. The repository — not the live database — is the source of truth, even when the live database is the only environment that actually runs.

**Why this priority**: Constitution Principle II (Source-Controlled Backend) is a non-negotiable foundation. Phase 4 has no local Supabase setup — every migration lands directly on the remote project — which makes "the repo mirrors the live database" the only line of defense against drift. If a column or policy ever exists only in Studio, the next time the project is rebuilt elsewhere it disappears. Every later phase adds migrations on top of this base, and Phase 5's auth flow runs against the same remote project, depending on the auto-provision trigger and RLS being already applied — so Phase 4's migrations being correctly applied to the remote is the prerequisite for Phase 5 even starting.

**Independent Test**: From a fresh checkout, apply each Phase 4 migration to the remote Supabase project via the Supabase MCP `apply_migration` tool. Inspect the remote schema (via MCP `list_tables`, `execute_sql`, or Supabase Studio) and confirm that the three Phase 4 tables exist, every Phase 4 enum is defined, every Phase 4 RLS toggle is on, every Phase 4 policy is attached, the audit-trigger function exists, and the Vault scaffolding is enabled — all of them, and nothing more. Then attempt to re-apply the same migrations: confirm Supabase's migration tracker reports them as already applied (no duplicate objects). Walk every artifact in the remote project and confirm each one has a matching `.sql` file in the repo — any artifact that does not is a defect.

**Acceptance Scenarios**:

1. **Given** the Phase 4 migration files are checked into `supabase/migrations/` and the remote Supabase project has no Phase 4 artifacts yet, **When** each migration is applied via Supabase MCP `apply_migration`, **Then** the remote project ends up with the three Phase 4 tables (`profiles`, `user_preferences`, `audit_logs`), the §6.3 enum definitions from `20260506120001_init_enums.sql`, the audit-trigger function and the concrete trigger on `profiles`, the Vault scaffolding (`pgsodium` + `vault` schema + `app_vault_secret` helper), RLS enabled on every Phase 4 table, and every Phase 4 policy attached.
2. **Given** the migrations have been applied once, **When** the same migrations are re-applied (or the apply step is retried), **Then** Supabase's migration tracker treats them as already applied and the remote schema is unchanged — no duplicate objects, no doubled policies, no orphaned rows.
3. **Given** every migration file is checked into the repo at this commit, **When** a reviewer enumerates the Phase 4 artifacts on the remote project (tables, enums, triggers, functions, policies, extension enables, Vault scaffolding), **Then** each one is traceable to a checked-in `.sql` file with the same definition — there is no schema object whose definition exists only on the remote.
4. **Given** a developer makes a one-off hand edit in remote Supabase Studio (e.g., adds an ad-hoc column or alters a policy without writing a migration), **When** that edit is detected during review, **Then** it is treated as a defect and reverted — the corrective action is to either author a proper migration in the repo or undo the change. The repo is authoritative; the remote follows.
5. **Given** the team ever needs to migrate to a different Supabase project, **When** the same migration files are applied to the new project in order, **Then** the new project ends up with the identical Phase 4 schema — no manual reconstruction is needed, and nothing was lost to the abandoned project.

### User Story 2 - A signed-up user has a server-side profile and isolated data by default (Priority: P1)

A new user finishes the platform's authentication signup (Phase 5 will wire the UI; Phase 4 just guarantees the backend behavior). The instant their `auth.users` row appears, a matching `profiles` row appears too — pre-populated with the defaults the rest of the product expects. The user's preferences row, when written, is invisible to every other user; an anonymous client and any other authenticated client both fail to read it. The same is true of the user's profile: only the user themselves (and, eventually, an admin via the placeholder admin predicate) can read or modify it. There is no public-by-default surface; access has to be explicitly granted by a policy. The user's data exists, has the right shape, and is locked down from the moment it is created.

**Why this priority**: Constitution Principle III (Security-First Supabase, NON-NEGOTIABLE) requires RLS on every table from day one. If the default in Phase 4 is "permissive until Phase 5 tightens it," every later phase ships against an unsafe baseline and the burden shifts to per-feature policy reviews. Auto-provisioning the profile on `auth.users` insert is also load-bearing for Phase 5 — without it, the auth flow has to do client-side profile creation, which is racy and opens a window where an authenticated user has no profile row. Both halves of this story (auto-provision + locked-down RLS) ship together because they are the minimum useful baseline; you cannot validate one without the other.

**Independent Test**: Insert a row into `auth.users` via a privileged session (test fixture). Confirm a `profiles` row appears with the expected default values (status `pending`) AND a matching `user_preferences` row appears with the FR-019 defaults (locale `ar`, theme `system`, currency `SYP`, notifications enabled) — both produced atomically by the same trigger. From an anonymous Supabase client, attempt to read either row — the read returns zero rows. From a *second* authenticated user's client, attempt to read the first user's profile or preferences — also zero rows. From the user's own client, reading their own `profiles` and `user_preferences` rows returns exactly one row each.

**Acceptance Scenarios**:

1. **Given** a row is inserted into `auth.users`, **When** the database trigger fires, **Then** exactly one `profiles` row exists for that `auth.users.id` (populated with `account_status = 'pending'`, `publisher_status = 'pending'`, timestamps) AND exactly one `user_preferences` row exists for the same `user_id` (populated with the FR-019 defaults). Both rows are produced by the same trigger and arrive atomically — downstream code can assume that for any `auth.users.id` either both rows exist or neither does.
2. **Given** two authenticated users (A and B), **When** user B issues a `SELECT` against `profiles` filtered to user A's id, **Then** the result is empty — RLS suppresses the row regardless of any join, view, or filter combination.
3. **Given** an anonymous (unauthenticated) Supabase client, **When** it issues a `SELECT *` against `profiles`, `user_preferences`, or `audit_logs`, **Then** every result set is empty — no row leaks via the anonymous role.
4. **Given** user A is authenticated, **When** they read their own `profiles` and `user_preferences` rows, **Then** the read succeeds and returns exactly their own data.
5. **Given** user A is authenticated, **When** they attempt to update or delete user B's `profiles` row, **Then** the operation affects zero rows (RLS write policy enforced).
6. **Given** every Phase 4 table is in place, **When** a reviewer inspects the migrations, **Then** RLS is enabled on every Phase 4 table and no table is documented as opt-out.

### User Story 3 - Sensitive changes leave an admin-readable audit trail (Priority: P2)

When an admin-relevant field changes — for Phase 4 specifically, that means a `profiles` row's `account_status` or `publisher_status` flipping from one allowed value to another — a row appears in `audit_logs` capturing who acted, what changed, when, and the before/after state of the affected fields. The audit trail is admin-readable only: a normal user cannot read `audit_logs`, even of their own profile. No client can write to `audit_logs` directly; rows arrive there only via server-side triggers. The audit-trigger function itself is reusable — every later phase that adds a new audit-worthy table reuses the same function instead of reinventing the pattern.

**Why this priority**: Constitution Principle VII requires every sensitive admin action to be audit-logged with actor, action, target, timestamp, and before/after state. Phase 4 cannot make every later phase's audit triggers concrete (those land per-feature, in the phase that owns each table), but it MUST ship the **reusable trigger function** plus at least one **concrete trigger** so the pattern is verifiable end-to-end before Phase 5 layers more on top. This is P2 because it is not on the critical path for Phase 4 to be usable — Phase 5 still gates publishing if audit triggers are missing — but if the function is not in place by the end of Phase 4, every subsequent phase has to either define its own audit pattern (drift) or back-fill Phase 4 (rework).

**Independent Test**: Against the remote Supabase project, as a privileged session (e.g., via Supabase MCP `execute_sql`), update a profile's `account_status` from `pending` to `approved`. Query `audit_logs`. Confirm a single row exists with the actor (the privileged session's user id), the action (e.g., `profile.status_changed`), the target (the profile's user id), a `before_state` JSON containing `{"account_status":"pending"}`, an `after_state` JSON containing `{"account_status":"approved"}`, and a timestamp. From a normal authenticated user's client, attempt to `SELECT * FROM audit_logs` — zero rows. From any client, attempt to `INSERT INTO audit_logs` — the insert is rejected.

**Acceptance Scenarios**:

1. **Given** the `log_audit()` trigger function is installed and a concrete trigger is attached to `profiles` covering status field changes, **When** an `account_status` or `publisher_status` value changes, **Then** exactly one `audit_logs` row is inserted whose `actor_user_id`, `action`, `target_type`, `target_id`, `before_state`, `after_state`, and `created_at` reflect the change.
2. **Given** any client (anonymous, authenticated user, or admin), **When** it attempts to `INSERT`, `UPDATE`, or `DELETE` on `audit_logs`, **Then** the operation fails or affects zero rows — `audit_logs` is append-only via the trigger function.
3. **Given** a normal authenticated user, **When** they `SELECT` from `audit_logs`, **Then** the result is empty — `audit_logs` is admin-readable only (admin readability is gated by the placeholder admin predicate that Phase 5/6 replace; in Phase 4 the placeholder evaluates to `false` for every caller, so the table is effectively read-blocked until Phase 5 ships the interim `is_admin` flag).
4. **Given** a later phase needs to make a new table audit-logged, **When** that phase's spec is written, **Then** it can reuse the `log_audit()` trigger function unchanged; no Phase 4 work is duplicated.

### User Story 4 - Vault scaffolding ready for later-phase secrets and PII (Priority: P2)

The database has the `pgsodium` extension enabled and the Supabase Vault scaffolding (the `vault` schema and supporting machinery) in place. A thin SQL helper, `app_vault_secret(name)`, exists and is the canonical way an Edge Function or server-side SQL function will read a Vault secret in later phases. No actual secrets are stored yet — Phase 4 is forward-prep. When a later phase (auth/profile in Phase 5; inquiries in Phase 16; agencies in Phase 19; ad-network keys in Phase 21; FCM service-account JSON in Phase 22) needs to add an encrypted column or a stored secret, it does so by writing a migration that uses the already-enabled extension and the already-defined helper — no Phase 4 redo, no extension-enable migration showing up in a later phase.

**Why this priority**: ADR-0001 commits the project to Supabase Vault as the canonical store for backend secrets and admin-only per-user PII. The ADR's own verification clause requires Phase 4 to ship the extension and Vault scaffolding "as a forward-prep step (no secrets stored yet)" so that the very next phase (Auth & Profile) can store `legal_name`, `national_id`, and `private_contact_methods` via Vault without having to first re-architect Phase 4. This is P2 because no end-user behavior depends on it in Phase 4 — it is invisible until Phase 5 — but landing it any later than Phase 4 stalls Phase 5.

**Independent Test**: Against the remote Supabase project, inspect the schema to confirm `pgsodium` is enabled (via `SELECT * FROM pg_extension WHERE extname = 'pgsodium'`), the Vault schema exists, and the `app_vault_secret(name)` helper is defined. From a privileged session (Supabase MCP `execute_sql`), call `app_vault_secret('does_not_exist')` and confirm it returns `NULL` (or the documented "not present" response) without crashing. Confirm via inspection that no application-level secret is yet stored in the Vault — the count is zero by construction in Phase 4. Read the migration's comments in the repo to confirm the forward-prep intent is documented in-place.

**Acceptance Scenarios**:

1. **Given** Phase 4's migrations have been applied to the remote Supabase project, **When** a reviewer queries `pg_extension WHERE extname = 'pgsodium'` via Supabase MCP `execute_sql`, **Then** the row exists.
2. **Given** the same remote project, **When** the reviewer queries the `vault` schema's expected objects, **Then** the Supabase Vault scaffolding is in place per the platform's documented baseline.
3. **Given** the helper `app_vault_secret(name TEXT)` is defined on the remote, **When** an Edge Function or SQL function calls it with a name that does not exist, **Then** it returns the documented "not present" response (e.g., `NULL`) and does not raise an error to the caller.
4. **Given** Phase 4 is complete, **When** the remote project's Vault contents are inspected, **Then** no application-level secret has been stored (count is zero by construction — Phase 4 stores none).
5. **Given** Phase 5's spec is being authored, **When** it adds Vault-backed columns for `legal_name`, `national_id`, and `private_contact_methods`, **Then** it does so on top of Phase 4's scaffolding without re-enabling the extension, redefining the schema, or rewriting `app_vault_secret`.

## Clarifications

### Session 2026-05-06

- Q: When does a user's `user_preferences` row come into existence? → A: It is auto-created in the same trigger that creates the profile (a single `auth.users` insert produces both rows atomically). Reads from `user_preferences` for any signed-up user can therefore assume the row exists; client code never has to handle "preferences row missing."
- Q: Where do locale and display-currency preferences live — on `profiles`, on `user_preferences`, or both? → A: `user_preferences` is the single source of truth. `profiles` does NOT carry `preferred_language` or `preferred_currency`; those columns from the implementation-plan §6.3 sketch are dropped at Phase 4 in favor of `user_preferences.locale` and `user_preferences.display_currency`, which already exist for exactly this purpose. Every later phase reads/writes locale and display-currency through `user_preferences` only.
- Q: Does Phase 4 pre-declare every §6.3 status enum, or only the ones whose tables land in this phase? → A: Pre-declare every §6.3 enum (account/publisher, listing, inquiry, report, listing-purpose, property-type, location-visibility, report-reason) in `20260506120001_init_enums.sql`. Later phases reference the already-defined enum types; no later migration adds a new top-level enum unless the spec for that phase explicitly extends §6.3. The Dart enum mirror in `lib/shared/domain/` ships in lockstep with the database enum.
- Q: How should `profiles.username` and `profiles.phone` uniqueness handle the NULL state that the auto-provision trigger leaves them in? → A: Plain `UNIQUE` constraint on both columns, using Postgres's default NULL semantics (multiple NULLs coexist as distinct). Uniqueness kicks in only after Phase 5's auth flow writes real values. No partial index, no `NULLS NOT DISTINCT`, no ordering dependency on Phase 5.
- Q: Where does Phase 4 actually apply its migrations — to a local Supabase project, to the remote project, or both? → A: **Remote project only.** Phase 4 has no local Supabase setup. Migrations are authored as SQL files checked into `supabase/migrations/` (source of truth per Constitution II) and applied directly to the remote Supabase project via the Supabase MCP server (`apply_migration`). The repo preserves the SQL so that if the Supabase project ever needs to be swapped or rebuilt elsewhere — different organization, different region, or eventually the Phase-IX custom backend — the schema is fully recoverable from the repository alone. Verification is manual SQL inspection against the remote project (via MCP `execute_sql` or Supabase Studio); there is no `supabase db reset` workflow in Phase 4.

### Edge Cases

- **Auth signup race**: Two near-simultaneous `auth.users` inserts for the same id (e.g., a retried signup) MUST NOT produce two `profiles` rows OR two `user_preferences` rows. The trigger MUST be idempotent for both side-effects — second inserts are absorbed (`ON CONFLICT DO NOTHING` shape on each target table) so that the one-profile-per-user and one-preferences-per-user invariants both hold under retry.
- **Concurrent signups with NULL `username` / `phone`**: When N new users sign up before any of them complete the Phase 5 profile-fill step, all N profile rows have `username IS NULL` and `phone IS NULL`. This MUST be allowed — Postgres's default `UNIQUE` semantics treat NULLs as distinct, so the unique constraints do not collide on NULL. Once a user provides a username or phone, the same constraint enforces uniqueness against every other non-NULL row.
- **Manually-inserted auth user**: When a developer or admin inserts an `auth.users` row outside the normal signup path (e.g., a SQL fixture), the trigger MUST still fire and create the matching profile. The trigger is unconditional on the source of the insert.
- **Profile-without-auth-user is impossible**: Direct `INSERT` into `profiles` for a `user_id` that has no `auth.users` row MUST fail (foreign key). Profiles are derived from auth, never primary.
- **`user_preferences` self-only on insert too**: A user MUST NOT be able to insert a `user_preferences` row whose `user_id` is not their own; only the row matching the authenticated `auth.uid()` is writable.
- **Cross-user read attempted via JOIN**: A user MUST NOT be able to bypass RLS on `profiles` by joining through another table whose policy is laxer. RLS is checked on every row read, and Phase 4 ships no laxer-than-self table on which a join could leak.
- **Anonymous client read**: An unauthenticated session MUST receive zero rows from any of the three Phase 4 tables. There is no public-read column in Phase 4.
- **`audit_logs` write attempt by client**: Any direct INSERT/UPDATE/DELETE on `audit_logs` from any client role (anon, authenticated, or service-role-via-misconfigured-client) MUST fail or affect zero rows. The only writer is the `log_audit()` trigger function executing in the database.
- **`audit_logs` read by self**: Even the user whose status changed MUST NOT be able to read their own row in `audit_logs` from a normal authenticated client. The `audit_logs` table is admin-only by design; the user's status itself is visible to them via `profiles`.
- **Trigger function is reusable as-is**: The `log_audit()` trigger function MUST accept the table name and the changed columns generically (or via a documented `TG_OP` / `OLD` / `NEW` convention) so that later phases attach it to new tables without rewriting it.
- **Idempotent migration apply**: Each migration file MUST be safe to re-apply against the remote Supabase project. Supabase's migration tracker (`supabase_migrations.schema_migrations`) handles this for normal flows by skipping already-applied filenames; the migration body itself SHOULD also use idempotent constructs where reasonable (`CREATE … IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`) so a forced re-apply does not error. Partial application that leaves the remote DB in a half-state is a defect.
- **Status enum exhaustiveness**: When a Phase 4 status enum is referenced by a column with a `CHECK` constraint, an attempt to set a value outside the enum MUST be rejected at the database level — domain code does not protect the database; the database protects itself.
- **Admin predicate placeholder is forward-compatible**: The "admin-read-all" placeholder used by Phase 4 policies MUST be expressible as a single helper (e.g., a function whose body Phase 5 swaps to read the interim `is_admin` flag and Phase 6 swaps again to call `current_user_has_permission(...)`). Replacing the placeholder MUST NOT require touching every Phase 4 policy file.
- **Vault helper failure isolation**: If `app_vault_secret(name)` is called for a name that does not exist, it MUST NOT raise an exception that propagates to the caller's error path. A caller treats a missing secret the same as an empty result — this is what later phases will rely on.
- **No secret stored yet**: Phase 4 MUST NOT store any actual Vault secret. Anything that *uses* a secret (Phase 22's FCM key, Phase 21's ad-network keys, etc.) lands in its own phase's migration. Phase 4 ships only the empty cabinet.
- **Domain layer does not import Supabase types**: The `Profile` and `UserPreferences` entities introduced in this phase MUST NOT expose `package:supabase_flutter` types in their public API (Constitution Principle IX). The data layer maps from Supabase rows to domain entities; the domain layer is provider-agnostic.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST define a `profiles` table whose primary key is the `auth.users.id` foreign key, with the columns required by the v1 product: full name, username (unique, nullable), phone (unique, nullable), email (nullable), avatar URL, account status, publisher status, created/updated timestamps. The uniqueness constraint on `username` and `phone` MUST use Postgres's default `UNIQUE` semantics — multiple NULLs coexist as distinct, so the auto-provision trigger (which leaves both columns NULL) is unaffected; uniqueness applies once Phase 5's auth flow writes real values. Locale and display-currency preferences are NOT on `profiles` — they live on `user_preferences` per the Session 2026-05-06 clarification, which is the single source of truth. Enums are constrained per §6.3 of the implementation plan, and RLS is enabled.
- **FR-002**: System MUST define a `user_preferences` table keyed by `user_id` (FK to `auth.users`), containing at minimum `display_currency`, `locale`, `theme_mode`, and `notifications_enabled`, with RLS enabled and self-only read/write policies.
- **FR-003**: System MUST define an `audit_logs` table containing `id`, `actor_user_id` (nullable for system actions), `action` (text key), `target_type`, `target_id`, `before_state` (JSON), `after_state` (JSON), `ip` (nullable), `user_agent` (nullable), and `created_at`, with RLS enabled, no client write policies, and a placeholder-admin-only read policy.
- **FR-004**: System MUST automatically insert exactly one `profiles` row AND exactly one matching `user_preferences` row whenever an `auth.users` row is inserted, regardless of how the `auth.users` insert originated (signup flow, fixture, admin import). Both side-effects MUST be produced by a single trigger so they arrive atomically — there is never a window in which a user has a profile but no preferences row, or vice versa. The trigger MUST be idempotent on both target tables so that retried signups do not produce duplicate rows.
- **FR-005**: All three Phase 4 tables (`profiles`, `user_preferences`, `audit_logs`) MUST have RLS enabled. No Phase 4 table opts out of RLS. The migration files MUST contain explicit `ENABLE ROW LEVEL SECURITY` statements.
- **FR-006**: `profiles` policies MUST allow self-read and self-write of all non-status fields, and MUST allow admin-read and admin-write of status fields, where "admin" is determined by a single placeholder predicate that Phase 5 (interim `is_admin` flag) and Phase 6 (role/permission system) replace without amending Phase 4 policy files.
- **FR-007**: `user_preferences` policies MUST be self-only — a user can read and write their own preferences row and no other user's. There is no admin policy on `user_preferences` in Phase 4.
- **FR-008**: `audit_logs` policies MUST forbid all client-initiated writes (no `INSERT`, `UPDATE`, or `DELETE` policy is granted to any role). Reads MUST be gated by the same placeholder admin predicate used by `profiles`.
- **FR-009**: System MUST define a reusable trigger function `log_audit()` that, when attached to a target table via `AFTER INSERT/UPDATE/DELETE`, writes one `audit_logs` row capturing `actor_user_id` (from the database session's authenticated user), the configured action key, the target table and id, a `before_state` JSON of the changed columns' OLD values, and an `after_state` JSON of the NEW values. The function MUST be reusable by later phases without modification.
- **FR-010**: System MUST attach a concrete audit trigger to `profiles` for changes to `account_status` and `publisher_status` so that User Story 3 is end-to-end verifiable in Phase 4.
- **FR-011**: System MUST define every status enum from §6.3 of the implementation plan in Phase 4 — even those whose owning tables land in later phases. The full set is: account/publisher (`pending`, `approved`, `rejected`, `suspended`, `deleted`); listing (`draft`, `pending_review`, `approved`, `rejected`, `paused`, `sold`, `rented`, `expired`, `deleted`); inquiry (`new`, `seen`, `responded`, `closed`, `spam`); report (`new`, `reviewing`, `resolved`, `dismissed`); listing-purpose (`sale`, `rent`, `daily_rent`, `investment`); property-type (`apartment`, `villa`, `land`, `shop`, `office`, `farm`, `warehouse`, `other`); location-visibility (`hidden`, `approximate`, `exact`, `admin_only`); report-reason (`fake_listing`, `wrong_price`, `already_sold_or_rented`, `duplicate`, `spam`, `wrong_location`, `inappropriate_content`, `other`). Each enum MUST be enforced at the database level via native enum types or `CHECK` constraints, and ships in a single migration `20260506120001_init_enums.sql`. Later phases that introduce the owning tables reference these enum types directly without redefining them; no later migration adds a new top-level enum unless its spec explicitly extends §6.3.
- **FR-012**: System MUST enable the `pgsodium` extension and the Supabase Vault scaffolding (the `vault` schema and the platform's standard machinery), and MUST define a thin SQL helper `app_vault_secret(name TEXT) RETURNS TEXT` (or the documented Supabase return type) that an Edge Function or server-side SQL function uses to read a Vault secret by name.
- **FR-013**: Phase 4 MUST NOT store any actual Vault secret. The Vault scaffolding is forward-prep for Phases 5, 16, 19, 21, and 22 per ADR-0001; any phase that introduces a Vault-backed column or stored secret MUST do so in its own migration, not retroactively in Phase 4.
- **FR-014**: Every backend artifact in Phase 4 (table, enum, trigger, function, policy, extension enable, Vault scaffolding, helper) MUST live as a checked-in `.sql` file under `supabase/migrations/` (or a sibling tree the implementation plan specifies). No artifact MUST be defined only in the remote Supabase project. Constitution Principle II is the binding rule: if a hand edit is made in Studio, it is a defect, not a feature.
- **FR-015**: The Phase 4 migrations MUST be applied to the remote Supabase project via the Supabase MCP `apply_migration` tool. No local Supabase setup is required or expected in Phase 4. Re-applying the same migrations to the same remote project MUST be safe — Supabase's migration tracker skips already-applied filenames, and migration bodies SHOULD additionally use idempotent constructs (`CREATE … IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION`) so manual re-application does not error. Applying the same migrations to a freshly-created Supabase project MUST produce an identical schema, preserving the "swap-the-project" recoverability property.
- **FR-016**: The Flutter `data/` layer's Supabase client wrapper MUST expose an auth-state listener (a stream or callback) that publishes session changes (signed-in, signed-out, refreshed) to consumers. Phase 4 introduces the listener; Phase 5 consumes it. The listener MUST NOT leak `package:supabase_flutter` types into the `domain/` layer (Constitution Principle IX).
- **FR-017**: The Flutter `domain/` layer MUST gain provider-agnostic entities `Profile` and `UserPreferences` (in `lib/shared/domain/entities/`) that mirror the Phase 4 columns relevant to consumers. The entities MUST NOT import from `package:supabase_flutter`.
- **FR-018**: Backend documentation MUST exist for the new tables — at minimum `supabase/docs/profiles.md` and `supabase/docs/audit_logs.md` — describing the table's purpose, columns, default values, RLS posture, and the audit fields covered. Documentation MUST be human-readable and reviewable in PR.
- **FR-019**: The default `user_preferences` values written by the auto-provision trigger MUST be: `locale = 'ar'` (Phase 3 default), `theme_mode = 'system'`, `display_currency = 'SYP'`, `notifications_enabled = true`. The row is created at the same moment as the profile (per FR-004); reads of `user_preferences` for any signed-up user MUST be able to assume the row exists. Phase 4 MUST document these defaults; later phases MAY refine them with their own migrations.
- **FR-020**: The default `profiles` values written by the auto-provision trigger MUST set `account_status = 'pending'` and `publisher_status = 'pending'`, leaving every other column at its column-level default or `NULL` (the `auth.users` insert payload does not yet carry full-name / phone / email — Phase 5's auth flow updates the profile after signup). Phase 4 MUST document these provisioning defaults.

### Key Entities

- **Profile**: A user's server-side identity and operational-status record. Keyed by `auth.users.id`. Holds public-ish identity (full name, username, phone, email, avatar) and operational status (`account_status`, `publisher_status`). Does NOT hold locale or display-currency preferences — those live on `UserPreferences`. Self-readable and self-writable for non-status fields; admin-managed for status. Auto-provisioned on auth signup. Vault-backed columns for `legal_name`, `national_id`, `private_contact_methods` are introduced by Phase 5 per ADR-0001 — Phase 4 ships only the plaintext identity/status columns.
- **UserPreferences**: A user's account-level preferences — `locale`, `display_currency`, `theme_mode`, `notifications_enabled`. The single source of truth for locale and display currency across the app. Self-only RLS. Auto-provisioned in the same trigger as the profile, so for every signed-up user the row exists at first read. Phase 3's locale persistence migrates from device-local secure storage into this row once Phase 5 ships authenticated profiles.
- **AuditLog**: Append-only record of admin-relevant changes. Captures actor, action key, target table+id, before/after JSON, IP, user-agent, timestamp. Written only by the `log_audit()` trigger function; never by client code. Admin-readable only.
- **Status Enum (account/publisher)**: The bounded set `{pending, approved, rejected, suspended, deleted}` enforced at the database level. Domain code mirrors the same enum so the data and domain layers cannot disagree.
- **Audit Trigger Function (`log_audit`)**: A reusable database function that any later phase can attach to a new audit-worthy table without rewriting. The contract: it reads `TG_OP`, `OLD`, `NEW`, and a configured action key, and inserts the matching `audit_logs` row.
- **Vault Scaffolding**: The `pgsodium` extension and the Supabase `vault` schema, enabled and ready. The thin helper `app_vault_secret(name)` is the canonical read path. No secrets are stored in Phase 4 — the cabinet is empty by design.
- **Admin Predicate Placeholder**: The single helper expression that the Phase 4 admin-gated policies depend on. It evaluates to `false` for every caller in Phase 4, becomes the interim `is_admin` flag in Phase 5, and becomes the role/permission system in Phase 6. Centralizing the predicate behind a single helper means Phase 5 and Phase 6 swap the implementation without touching the policy files Phase 4 wrote.

## Assumptions

- **Phases 1–3 foundations are in place**: the Flutter app shell, the design tokens, the bilingual font stack, the `LocaleCubit`, the localization runtime, and the literal-string lint guard from `specs/001-project-foundation/`, `specs/002-design-system/`, and `specs/003-localization/` are already shipped. Phase 4 adds backend skeleton tables and the matching data-layer scaffolding on top of that base.
- **No local Supabase setup**: Phase 4 has no local Supabase project, no `supabase start` workflow, and no `supabase db reset` flow. The remote Supabase project is the only environment where the schema actually runs. Migrations are authored as SQL files in `supabase/migrations/`, applied to the remote via Supabase MCP `apply_migration`, and verified via Supabase MCP `execute_sql` / `list_tables` (or Studio). This is a deliberate simplification for the solo-developer / Windows-host workflow; if a future contributor wants local iteration, they MAY add a local Supabase setup in a separate spec without changing the migrations.
- **Repository = source of truth even with no local environment**: Constitution Principle II is binding. The repo holds every Phase 4 SQL artifact; the remote project is one applied instance of the repo. If the project ever needs to be swapped (different region, different organization, eventually the Phase-IX custom backend), re-applying the same migrations to the new target reproduces the schema exactly. Hand edits in Studio that are not backed by a checked-in migration are defects, not features.
- **Verification posture is manual SQL inspection against the remote project**: per the project's no-new-tests stance carried forward from Phase 3, Phase 4 introduces no automated database tests (no `supabase test db` suite), no widget tests, no integration tests. Verification is performed by running SQL queries against the remote Supabase project via Supabase MCP `execute_sql` (or Supabase Studio) and confirming the documented results. Supabase's static SQL parser used at `apply_migration` time is in scope as build-time validation. Existing Phase 1/2/3 tests remain in source unchanged.
- **Auth is provided by the Supabase platform**: `auth.users` and `auth.uid()` are platform primitives. Phase 4 does not redefine them; it adds the trigger that creates a `profiles` row whenever an `auth.users` row is inserted.
- **The audit-trigger function is generic, the Phase 4 trigger is concrete**: Phase 4 ships the reusable `log_audit()` function (so later phases attach it to new tables without rewriting) AND attaches one concrete trigger to `profiles` for `account_status` / `publisher_status` changes (so User Story 3 is end-to-end verifiable in this phase). Subsequent phases attach more triggers as their tables land.
- **The "admin" predicate is a placeholder**: Phase 4 has no real admin role yet. The admin-gated policies use a single helper expression that evaluates to `false` for every caller. Phase 5 swaps the helper to read the interim `is_admin` boolean it introduces on `profiles`. Phase 6 swaps the helper again to call `current_user_has_permission(...)`. Centralizing the predicate behind a single helper means the Phase 5/6 swap touches one file, not every Phase 4 policy file.
- **Default `user_preferences`**: `locale = 'ar'` (Phase 3 default), `theme_mode = 'system'`, `display_currency = 'SYP'`, `notifications_enabled = true`. These defaults are documented in the data-model and may be refined by later phases via their own migrations.
- **Default `profiles` provisioning**: `account_status = 'pending'`, `publisher_status = 'pending'`. Other identity columns (full name, username, phone, email, avatar) are left at their column-level defaults or NULL; Phase 5's auth flow fills them in after signup.
- **`profiles` does not carry locale or display-currency**: the implementation plan's §6.3 sketch lists `preferred_language` and `preferred_currency` on `profiles`, but Phase 4 deliberately drops those columns and treats `user_preferences.locale` and `user_preferences.display_currency` as canonical (Session 2026-05-06 clarification). This is a documented divergence from the §6.3 column list; downstream phases that read locale or display-currency MUST query `user_preferences`, never `profiles`.
- **Status enums for tables not yet introduced**: Phase 4 pre-declares **every** §6.3 enum in `20260506120001_init_enums.sql`, including those whose owning tables (listings, inquiries, reports, ads, etc.) land in later phases. Per the Session 2026-05-06 clarification, this matches the implementation plan's literal wording, gives every later migration a stable enum to reference at insert time, and keeps the Dart-side enum mirror in `lib/shared/domain/` synchronized with the database from day one. Later phases MUST NOT redefine any §6.3 enum; if a later spec needs to extend an enum's value set, that extension is itself a new migration whose spec calls it out explicitly.
- **Vault scaffolding is forward-prep, not a feature in itself**: Phase 4 enables `pgsodium`, lays down the `vault` schema, and ships the `app_vault_secret(name)` helper. Phase 4 stores no actual secret. The first real use lands in Phase 5 (`profiles.legal_name`, `profiles.national_id`, `profiles.private_contact_methods`).
- **No Vault-backed columns on `profiles` yet**: ADR-0001 lists `legal_name`, `national_id`, `private_contact_methods` as Vault-backed, but those columns are introduced by Phase 5's `0008_profiles_vault_columns.sql` migration. Phase 4's `profiles` table does not include them.
- **Admin-readable does not mean readable in Phase 4**: Because the admin predicate is a placeholder that evaluates to `false`, the `audit_logs` table and the `profiles` admin-only fields are effectively read-blocked for every caller until Phase 5 ships the interim `is_admin` flag. This is correct behavior — it means the data is locked down by default; permissions are granted by later phases.
- **Domain layer stays Supabase-free**: The `Profile` and `UserPreferences` entities (in `lib/shared/domain/entities/`) MUST NOT import from `package:supabase_flutter`. The `data/` layer maps Supabase rows into these domain entities. Constitution Principle IX is the binding rule.
- **Reference device for the Flutter wiring check**: Infinix Note 8 (Helio G80, 6 GB RAM, Android 10/11) per project memory. The Flutter side's Phase 4 additions (auth-state listener, domain entities) are verified by a clean build and launch on the device against the remote Supabase project.
- **No real-time, no Edge Functions, no Storage in Phase 4**: realtime channels, Edge Functions, and Storage buckets are introduced by the phases that own their use cases (e.g., realtime in Phase 22, ad storage in Phase 21, listing-image storage in Phase 11). Phase 4 ships SQL only.
- **No app-icon, splash, or marketing changes**: Phase 4 is backend + data-layer. The user-visible app surface does not change in Phase 4; the auth-state listener is wired but its consumers (Phase 5's auth flow, Phase 5's pending-approval screen) are not yet present.
