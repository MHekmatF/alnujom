# Feature Specification: Reports & Moderation

**Feature Branch**: `018-reports-moderation`
**Created**: 2026-05-29
**Status**: Draft
**Input**: Phase 18 — Reports & moderation, from `docs/IMPLEMENTATION_PLAN.md` (§ "Phase 18 — Reports & moderation")

> **Scope note**: Phase 18 introduces the *community-moderation capability* — the working implementation of the Report control that Phase 13 ships as a Coming-soon stub (the rightmost CTA in `PerListingActionBlock` per `lib/features/listing_details/presentation/widgets/per_listing_action_block.dart`, `Icons.flag_outlined` / `l10n.cta_report`, currently calling `_showComingSoon`), plus a privileged admin resolution flow where a moderator/admin reviews a queue of reports and resolves each one with a moderation action that may change the reported listing's status — and every resolution writes a paired `moderation_actions` row and an `audit_logs` row. It is the first phase to consume the `reports.manage` permission key that Phase 6 seeded onto the `moderator` and `admin` roles. Phase 18 ships exactly: (a) two new tables — `public.reports` (a user-submitted complaint about a single listing, keyed to a reporter and a reason) and `public.moderation_actions` (an append-only record of the admin action taken when a report is resolved, with before/after listing state); (b) a privileged submit path — a `submit_report(listing_id, reason, note)` SECURITY DEFINER RPC that requires an authenticated session, validates the target listing exists, idempotently creates an *open* report (one open report per reporter+listing — re-submitting while a prior report is still open is a no-op rather than a duplicate), and captures the reporter, reason, optional note, IP, and user-agent (mirroring the Phase 16 `record_lead_event` capture posture); (c) a privileged resolution path — a `resolve_report` Edge Function that gates on the caller's `reports.manage` permission (JWT-bound, via `current_user_has_permission`) and then invokes a SECURITY DEFINER `resolve_report_internal` RPC (service-role only) that, in a single transaction, sets the report's terminal status + resolution + resolver + timestamp, inserts the paired `moderation_actions` row, applies the chosen listing-status transition when the action requires one, and lets the existing Phase 4 / Phase 10 audit triggers (plus an explicit moderation audit entry) fire — exactly mirroring the Phase 12 `approve_listing` / `reject_listing` Edge-Function-plus-`*_internal`-RPC pattern; (d) the four moderation actions from the plan goal — **dismiss** (the report is invalid; the listing is unchanged), **hide** (take the listing off the public surface by transitioning it to `paused`), **mark_duplicate** (transition the listing to `rejected` with reason "duplicate"), and **delete** (soft-delete the listing via `status='deleted'`) — all expressed through the *existing* Phase 10 listings status enum and Phase 12 status-transition machinery, so Phase 18 adds NO new listings status value (per Q1=A); (e) the report-submission UI — the Phase 13 `PerListingActionBlock` Report CTA rewired from the Coming-soon snackbar to a real report sheet (reason dropdown over the eight canonical report reasons + an optional free-text note), leaving the Share CTA an untouched Phase 13 stub and not reflowing the surrounding widget tree (mirroring how Phase 17 surgically rewired only the Favorite CTA); (f) the admin moderation surface at `lib/features/admin/reports/` — a reports queue (filterable by status and reason) and a resolve flow (open a report, view the reported listing context, pick an action, confirm), gated behind `reports.manage` and reached from the Phase 6 admin home, following the same Clean-Architecture shape as the Phase 12 `listing_review` feature; (g) the reporter-facing visibility surfaces (per Q3=Both) — a "My Reports" list reached from a Phase 5 Profile tile via a new `/reports` route (the reporter's own submitted reports with their current status and resolution) AND an inline banner on the Phase 13 listing details page that tells a signed-in reporter who re-opens a listing they reported its current report status; (h) the localization layer gains the reports & moderation strings — the Report CTA label and report sheet (reason labels, note hint, submit/cancel), the "Sign in to report" prompt, the duplicate-report acknowledgement, the admin queue labels and action labels, the resolve confirmation copy, the "My Reports" page title / empty-state / status labels, the details-page reporter banner, and the Profile tile label — all flowing through `AppLocalizations` with `ar` and `en` entries per Phase 3. Per Q2=A, reporting is an **authenticated-only** capability: the Report CTA renders for everyone (so the feature is discoverable) but tapping it while signed-out surfaces a localized "Sign in to report" prompt and routes into the existing Phase 5 login flow — no report row is written for an anonymous tap (mirroring the Phase 17 anonymous-heart posture). It does NOT introduce reporting of anything other than listings (no reporting of users, agencies, inquiries, or reviews in v1); it does NOT introduce automatic duplicate detection (manual admin `mark_duplicate` only, per the IMPLEMENTATION_PLAN non-goal); it does NOT introduce report-reason-specific automation, report quotas/rate-limit tuning beyond the open-report dedup, reporter reputation scoring, or any reporter↔publisher messaging; it does NOT add any new third-party dependency. Phase 18 honors Principle III (RLS on both new tables, reporter-self + `reports.manage`-admin read posture, no service-role key on the client, the resolution mutation gated server-side at both the Edge-Function permission check AND the RLS/RPC layer per Principle "checks at both ends"), Principle VII (the admin surface is gated by the data-driven `reports.manage` permission, never a hardcoded role check), and Principle I (this spec precedes any implementation).

## User Scenarios & Testing *(mandatory)*

### User Story 1 — A signed-in user reports a problematic listing (Priority: P1)

A signed-in user viewing a listing's details page notices something wrong — a fake listing, a wrong price, a listing that is already sold, a duplicate, spam, a wrong location, or inappropriate content. They tap the Report control, choose a reason from a short list, optionally add a note, and submit. The app confirms the report was received. Their report enters the moderation queue with status "new." If they tap Report again on the same listing while their prior report is still open, the app tells them they have already reported this listing rather than creating a duplicate.

**Why this priority**: P1 because the report submission IS the entry point of the feature — without a working report there is nothing in the admin queue to resolve and no moderation action to take. The Phase 13 Coming-soon stub (a snackbar on tap) is the placeholder this story replaces. Reporting is the community's only mechanism to flag bad listings between admin reviews.

**Independent Test**: Apply the Phase 18 migrations. Sign in as a test user. Open an approved listing's details page; confirm the Report CTA is present and tappable. Tap it; confirm a sheet appears offering the eight canonical reasons and an optional note field. Pick "fake_listing," add a note, submit; confirm (a) a localized success confirmation appears, (b) exactly one `public.reports` row exists with `listing_id` = the listing, `reporter_user_id` = the signed-in user, `reason = 'fake_listing'`, `note` = the entered text, `status = 'new'`, `created_at` recent. Tap Report again on the same listing while the report is still open; confirm NO second `reports` row is created and a localized "already reported" acknowledgement appears.

**Acceptance Scenarios**:

1. **Given** a signed-in user on an approved listing's details page, **When** they tap the Report CTA, **Then** a localized report sheet opens offering the eight canonical reasons (`fake_listing`, `wrong_price`, `already_sold_or_rented`, `duplicate`, `spam`, `wrong_location`, `inappropriate_content`, `other`) and an optional free-text note field.
2. **Given** the report sheet is open, **When** the user selects a reason and submits, **Then** exactly one `public.reports` row is inserted with `listing_id` = the listing, `reporter_user_id = auth.uid()`, the chosen `reason`, the optional `note`, `status = 'new'`, and a server-generated `created_at`, AND a localized success confirmation surfaces.
3. **Given** a user has an already-open report (`status` ∈ {`new`, `reviewing`}) on a listing, **When** they submit another report for the same listing, **Then** NO second `reports` row is created (idempotent per reporter+listing while open) AND a localized "you have already reported this listing" acknowledgement surfaces.
4. **Given** a user whose prior report on a listing was already resolved or dismissed, **When** they report the same listing again, **Then** a NEW `public.reports` row IS created (the dedup applies only to currently-open reports), so a recurrence after resolution can be re-flagged.
5. **Given** the report submission issues a server write, **When** the write fails (network drop, RPC error), **Then** a localized retryable error surfaces AND no partial `reports` row is committed.
6. **Given** a signed-in user submits a report with no note, **When** the write completes, **Then** the report is stored with a null/empty note and `reason` only — the note is optional.

### User Story 2 — An admin reviews and resolves reports from a moderation queue (Priority: P1)

A moderator or admin (any user holding the `reports.manage` permission) opens the Reports queue from the admin home. They see open reports, newest first, each showing the reported listing, the reason, the reporter, and the note. They can filter by status and by reason. They open a report, review the reported listing's context, and resolve it by choosing one of four actions — **dismiss** (the report is invalid; the listing is untouched), **hide** (take the listing off the public surface), **mark duplicate** (flag the listing as a duplicate), or **delete** (remove the listing) — confirming the destructive ones. Resolving a report sets its terminal status, records the action taken, applies any required listing-status change, and writes an audit trail.

**Why this priority**: P1 because a queue of reports with no resolution path is a dead-end — the entire value of reporting is that an authorized human acts on it. This story delivers the admin half of the loop and the moderation-action + audit record the IMPLEMENTATION_PLAN's acceptance criteria require.

**Independent Test**: Seed ≥ 3 open reports across ≥ 2 listings and ≥ 2 reasons. Sign in as a user holding `reports.manage`; confirm the Reports tile is visible on the admin home and a user WITHOUT the permission does NOT see it. Open the queue; confirm reports list newest-first with listing/reason/reporter/note, and the status and reason filters narrow the list correctly. Open one report, choose **hide**, confirm; verify (a) the `reports` row moves to a terminal status with `resolved_by` = the admin, `resolved_at` recent, and a `resolution` recording "hide," (b) exactly one `public.moderation_actions` row is inserted with the action, the target listing, the resolver, and before/after listing state, (c) the listing's status transitions to `paused` and it no longer appears in the public/anonymous home feed, (d) an `audit_logs` row records the moderation action. Repeat with **dismiss** (listing unchanged), **mark_duplicate** (listing → `rejected`, reason duplicate), and **delete** (listing → `deleted`); confirm each writes its paired `moderation_actions` + `audit_logs` rows and applies the correct listing transition.

**Acceptance Scenarios**:

1. **Given** a user holding `reports.manage`, **When** they open the admin home, **Then** a "Reports" entry is visible and routes to the reports queue; **And given** a user WITHOUT `reports.manage`, **When** they open the admin home, **Then** no Reports entry is shown (frontend hide) AND the queue data is denied at the RLS layer (backend gate).
2. **Given** the reports queue is open, **When** it loads, **Then** reports are listed ordered by `created_at DESC` (newest first), each showing the reported listing, the reason, the reporter, and the note, AND the list paginates rather than issuing an unbounded query.
3. **Given** the reports queue is open, **When** the admin applies a status filter (e.g., `new`) or a reason filter (e.g., `spam`), **Then** only matching reports remain visible.
4. **Given** an admin opens a report and chooses **dismiss**, **When** they confirm, **Then** the report's status becomes terminal (`dismissed`) with `resolved_by`/`resolved_at`/`resolution` set, a `moderation_actions` row records the `dismiss` action with before/after listing state, an `audit_logs` row is written, AND the listing's status is UNCHANGED.
5. **Given** an admin opens a report and chooses **hide**, **When** they confirm, **Then** the listing transitions to `paused` (off the public feed), a `moderation_actions` row + `audit_logs` row are written, and the report becomes terminal (`resolved`).
6. **Given** an admin opens a report and chooses **mark duplicate**, **When** they confirm, **Then** the listing transitions to `rejected` with a "duplicate" reason recorded in `listing_status_history`, a `moderation_actions` row + `audit_logs` row are written, and the report becomes terminal (`resolved`).
7. **Given** an admin opens a report and chooses **delete**, **When** they confirm via the destructive-action confirmation dialog, **Then** the listing transitions to `deleted` (soft-delete), a `moderation_actions` row + `audit_logs` row are written, and the report becomes terminal (`resolved`).
8. **Given** any report resolution, **When** it commits, **Then** the report-status update, the `moderation_actions` insert, the listing-status transition (if any), and the audit entry are written in a SINGLE transaction — there is never a resolved report without its paired moderation action, nor a listing change without its report resolution.
9. **Given** a listing has multiple open reports, **When** an admin resolves one of them with a listing-affecting action (hide/mark_duplicate/delete), **Then** the listing transition applies exactly once AND every other open report on that listing is auto-resolved in the same transaction (each moved to `resolved` with its own `moderation_actions` row referencing the triggering resolution); **And** a **dismiss** resolution affects only the dismissed report and leaves siblings open.
10. **Given** an admin taps "Start review" on a `new` report, **When** the action commits, **Then** the report moves to `reviewing` and records the claiming admin (`reviewing_by`) and claim time; **And given** a report already `reviewing` under another admin, **When** a second `reports.manage` holder opens it, **Then** the current reviewer is surfaced but the second admin may still take over or resolve it (the claim is an advisory soft lock, not a hard block).

### User Story 3 — Reporters see what happened to their report (Priority: P2)

A signed-in user who has reported listings wants to know the outcome. They open a "My Reports" tile in their Profile and land on a page listing every report they have submitted, newest first, each showing the listing they reported, the reason, and the current status (new / reviewing / resolved / dismissed) plus the resolution where one exists. Separately, when they re-open a listing they have an open or recently-resolved report on, the listing details page shows an inline banner with that report's current status, so they get feedback in context without hunting for it.

**Why this priority**: P2 because the IMPLEMENTATION_PLAN explicitly requires "Reporters see the resolution status on their report," and a report that disappears into a void erodes trust in the reporting mechanism — but the visibility surfaces sit on top of the P1 submit + resolve loop rather than being a prerequisite for it.

**Independent Test**: Sign in as a user with ≥ 2 submitted reports in different states (one `new`, one resolved by an admin). Open Profile → "My Reports"; confirm (a) the page lists both reports newest-first with the reported listing, reason, status, and resolution where present, (b) a user with zero reports sees a localized empty-state. Open the details page of a listing the user has an open report on; confirm a localized inline banner shows "You reported this — status: new/reviewing." Have an admin resolve that report; reload the details page and confirm the banner reflects the new terminal status/resolution. Confirm the "My Reports" page and banner show ONLY the signed-in user's own reports (never another user's).

**Acceptance Scenarios**:

1. **Given** a signed-in user with ≥ 1 submitted report, **When** they open the "My Reports" page from the Profile tile, **Then** every report THEY submitted appears, ordered by `created_at DESC`, each showing the reported listing, reason, current status, and resolution where one exists, AND no report submitted by any other user appears.
2. **Given** a signed-in user with zero submitted reports, **When** they open "My Reports," **Then** a localized empty-state renders (not a crash, not a blank screen).
3. **Given** a signed-in user has an open report on a listing, **When** they open that listing's Phase 13 details page, **Then** a localized inline banner shows their report's current status; **And** the banner appears only for the reporter (other users and anonymous visitors never see it).
4. **Given** an admin resolves a report the user submitted, **When** the user reloads the "My Reports" page or the listing details page, **Then** the displayed status reflects the new terminal status (`resolved` / `dismissed`) and the resolution.
5. **Given** the "My Reports" page is open and the user has many reports, **When** the list renders, **Then** it paginates (matching the Phase 13 home-feed cursor pattern) rather than issuing an unbounded query.

### User Story 4 — Reports & moderation data are protected by RLS (cross-user isolation) (Priority: P1)

A report reveals who flagged what and why — sensitive moderation data. The product MUST guarantee that a reporter can read only their OWN reports, that only users holding `reports.manage` can read the full reports queue and the moderation-action log, and that no anonymous client can read either table or submit a resolution. Submitting a report is authenticated-only; resolving a report is gated at BOTH the Edge-Function permission check AND the database layer (Principle "checks at both ends").

**Why this priority**: P1 because Constitution Principle III makes an unprotected moderation table a breach, and exposing who reported whom (or letting a non-admin resolve a report) would undermine the entire moderation system. The reporter-self + admin-only read posture and the no-anonymous-write posture are load-bearing.

**Independent Test**: Seed reports from user-A and user-B, plus moderation actions from an admin. From user-A's session, query the reports surface; confirm ONLY user-A's reports return at the wire level — none of user-B's. From an anonymous client, confirm zero reports return and any resolve attempt is rejected. From a non-admin authenticated session, confirm the full reports queue and the `moderation_actions` table are NOT readable and a resolve call is rejected (both at the Edge Function and, if bypassed, at the RPC/RLS layer). From a `reports.manage` session, confirm the full queue and the moderation-action log ARE readable. Attempt to INSERT a report row with `reporter_user_id` set to another user's id from user-A's session; confirm it is rejected (the submit path ties `reporter_user_id` to `auth.uid()`).

**Acceptance Scenarios**:

1. **Given** user-A is signed in, **When** they query the reports surface, **Then** the response contains every report whose `reporter_user_id = auth.uid()` AND zero reports submitted by any other user.
2. **Given** a user holding `reports.manage`, **When** they query the reports queue and the `moderation_actions` log, **Then** they can read ALL reports and ALL moderation actions (the moderation-team view).
3. **Given** an authenticated user WITHOUT `reports.manage`, **When** they attempt to read another user's report, the full queue, or the `moderation_actions` table, **Then** RLS denies the read (only their own reports are visible; moderation actions are admin-only).
4. **Given** an anonymous client, **When** it attempts to read reports or moderation actions, or to submit/resolve, **Then** RLS denies all of it and no rows are returned or written.
5. **Given** user-A is signed in, **When** they attempt to create a `reports` row whose `reporter_user_id` is NOT their own `auth.uid()`, **Then** the write is rejected (the submit path sets `reporter_user_id = auth.uid()`; no client INSERT bypass exists).
6. **Given** an authenticated user without `reports.manage`, **When** they call the `resolve_report` Edge Function (or attempt the underlying mutation directly), **Then** it is rejected — the Edge Function rejects on the permission check AND the service-role `resolve_report_internal` RPC is not client-callable, so no resolution path exists for an unauthorized caller.
7. **Given** any report resolution by an authorized admin, **When** it commits, **Then** an `audit_logs` row records the actor, action, target, and before/after state (the resolution is audit-logged per the §6.4 matrix).

### User Story 5 — Anonymous visitor is invited to sign in when they tap Report (Priority: P3)

An anonymous (signed-out) visitor browsing a listing's details page sees the same Report control that signed-in users see — reporting is advertised to everyone so it is discoverable. When the anonymous visitor taps Report, instead of silently failing or opening a sheet that cannot submit, the app surfaces a localized "Sign in to report" prompt and routes them into the existing login flow. After signing in, they can report normally.

**Why this priority**: P3 because anonymous browsing is a first-class path (Phases 13–15), but the conversion nudge ("sign in to report") is a refinement on top of the core authenticated report flow rather than a prerequisite. The chosen behavior mirrors the Phase 17 anonymous-heart posture exactly.

**Independent Test**: Without signing in, open a listing's details page; confirm the Report CTA renders (it is NOT hidden). Tap it; confirm (a) NO `reports` row is written, (b) a localized "Sign in to report" prompt appears and routing into the login page occurs. Complete sign-in; confirm the user can now report normally and the listing is NOT auto-reported (the pre-auth tap has no hidden side effect — the user re-taps Report and fills the sheet explicitly).

**Acceptance Scenarios**:

1. **Given** an anonymous visitor on a listing details page, **When** the surface renders, **Then** the Report CTA is visible (not hidden, not greyed).
2. **Given** an anonymous visitor taps Report, **When** the tap is handled, **Then** NO `reports` row is written AND a localized "Sign in to report" prompt surfaces AND the app routes into the existing Phase 5 login flow.
3. **Given** an anonymous visitor who tapped Report and signed in, **When** sign-in completes, **Then** the listing is NOT auto-reported — the user makes an explicit re-tap and fills the report sheet (no hidden side effect from the pre-auth tap).
4. **Given** an anonymous visitor declines to sign in (dismisses the prompt / backs out of login), **When** they return to browsing, **Then** no report was created.

### Edge Cases

- **Anonymous user taps Report**: Per US5 / Q2=A — the CTA renders for everyone; the tap routes to the sign-in flow with a localized prompt; no row is written. The pre-auth tap does not silently persist after login.
- **A user reports a listing that is later soft-deleted (status = `deleted`)**: The `reports.listing_id` FK uses `ON DELETE RESTRICT` (matching the Phase 16 `lead_events` and Phase 17 `favorites` precedent); listings soft-delete via `status='deleted'` rather than hard-deleting, so the FK is never exercised. The report remains in the queue and on the reporter's "My Reports" page; the admin can still resolve it (e.g., `delete` on an already-deleted listing is idempotent or surfaces as a no-op transition).
- **A user reports the same listing twice while their first report is still open**: The second submission is a no-op (one open report per reporter+listing); a localized "already reported" acknowledgement surfaces. After the first report is resolved/dismissed, a fresh report MAY be created (re-flagging a recurrence).
- **Multiple users report the same listing**: Each user's report is an independent `reports` row. The admin queue shows all of them; resolving one with a listing-affecting action (hide/mark_duplicate/delete) applies the listing transition once AND auto-resolves the other open reports on that listing in the same transaction (FR-016), so the queue self-cleans. A `dismiss` resolution affects only the dismissed report.
- **An admin chooses an action whose listing transition is invalid for the listing's current status** (e.g., `hide` (→ `paused`) a listing that is already `deleted`, or `delete` an already-deleted listing): The resolution still records the `moderation_actions` row and resolves the report, but the listing transition is a guarded no-op (the existing Phase 12 transition machinery / status guards govern legality); the resolution MUST NOT leave the report unresolved because the listing was already in a terminal state.
- **A reporter's account is later deleted**: The `reports.reporter_user_id` FK uses `ON DELETE CASCADE` (the `favorites`/`user_preferences` precedent) OR `ON DELETE SET NULL` (the `lead_events.user_id` precedent) — the spec mandates that a deleted user leaves no orphaned reporter identity; the chosen behavior is plan-time (see Assumptions). The `moderation_actions.performed_by` (an admin) uses `ON DELETE SET NULL` so the moderation log survives the admin's account deletion (the action history must not vanish).
- **A report references a listing the reporter could not normally see** (e.g., a crafted `submit_report` call targeting a `draft`, terminal, or non-existent listing): The `submit_report` RPC validates the target listing exists AND is currently `approved` (per Q6=A), rejecting anything else with a structured error — reporting is constrained to the listings a user can legitimately surface, consistent with the `record_lead_event` / `add_favorite` gate. The `already_sold_or_rented` reason is not blocked by this: such a report is filed while the listing is still shown as `approved` but sold in reality.
- **An admin resolves a report that another admin resolved a moment earlier** (concurrent resolution): The first resolution moves the report to a terminal status; the second resolution targets an already-terminal report and is rejected or is a guarded no-op (the RPC checks the report is still open before resolving), so a report is resolved exactly once and produces exactly one `moderation_actions` row.
- **The reports queue grows large**: The admin queue and the "My Reports" page both paginate (no unbounded query per the Constitution performance baseline).
- **Network failure during report submission or resolution**: A localized retryable error surfaces AND the database has no partial state (no half-written report; no resolved report without its moderation action).
- **A user enters an over-long note**: The note field enforces a reasonable maximum length (plan-time) and the server stores within a bounded column; over-long input is truncated or rejected with a localized validation message, never silently corrupting the row.

## Requirements *(mandatory)*

### Functional Requirements

#### Report submission (listing details)

- **FR-001**: System MUST replace the Phase 13 `PerListingActionBlock` Report CTA's Coming-soon snackbar handler (per `lib/features/listing_details/presentation/widgets/per_listing_action_block.dart`) with a working report flow. Only the Report CTA's handler and label MUST change; the Share CTA in the same block MUST remain a Phase 13 Coming-soon stub, the Favorite CTA's Phase 17 toggle MUST be untouched, and the surrounding widget tree (layout, icons, ordering, button styles) MUST NOT be reflowed.
- **FR-002**: Tapping Report as a signed-in user MUST open a localized report sheet offering exactly the eight canonical report reasons — `fake_listing`, `wrong_price`, `already_sold_or_rented`, `duplicate`, `spam`, `wrong_location`, `inappropriate_content`, `other` (per IMPLEMENTATION_PLAN §6.3) — and an OPTIONAL free-text note field.
- **FR-003**: Submitting the report sheet MUST create exactly one `public.reports` row with `listing_id` = the listing, `reporter_user_id = auth.uid()`, the chosen `reason`, the optional `note`, `status = 'new'`, and a server-generated `created_at`, via the privileged submit path (FR-010), AND surface a localized success confirmation.
- **FR-004**: The report submission MUST be idempotent per (reporter, listing) WHILE a prior report is open — if the signed-in user already has a report with `status` ∈ {`new`, `reviewing`} on the target listing, the submit path MUST NOT create a second row and the app MUST surface a localized "already reported" acknowledgement. Once the prior report reaches a terminal status (`resolved` / `dismissed`), a new report MAY be created.
- **FR-005**: When report submission fails (network or server error), the system MUST surface a localized, retryable error AND leave the database with no partial report row.

#### Anonymous behavior

- **FR-006**: The Report CTA MUST render for anonymous (signed-out) visitors on the listing details page — it MUST NOT be hidden or greyed-out (per Q2=A).
- **FR-007**: When an anonymous visitor taps Report, the system MUST NOT write any `reports` row AND MUST surface a localized "Sign in to report" prompt AND route into the existing Phase 5 login flow. The pre-authentication tap MUST NOT auto-submit a report after the user signs in — reporting requires an explicit post-login action.

#### Tables, indices, and the server-side submit path

- **FR-008**: System MUST create a new `public.reports` table with at minimum: `id` (UUID PK), `listing_id` (UUID, NOT NULL, FK to `public.listings(id)` with `ON DELETE RESTRICT` per the Phase 16/17 precedent), `reporter_user_id` (UUID, NOT NULL, FK to `auth.users(id)`), `reason` (TEXT, NOT NULL, CHECK over the eight canonical reasons), `note` (TEXT, NULL, length-bounded), `status` (TEXT, NOT NULL, DEFAULT `'new'`, CHECK over `new` / `reviewing` / `resolved` / `dismissed` per §6.3), `reviewing_by` (UUID, NULL, FK to `auth.users(id)` — the admin who claimed the report for review, per FR-036), `reviewing_started_at` (TIMESTAMPTZ, NULL), `resolved_by` (UUID, NULL, FK to `auth.users(id)`), `resolved_at` (TIMESTAMPTZ, NULL), `resolution` (TEXT/JSONB, NULL — what action was taken), and `created_at` (TIMESTAMPTZ, NOT NULL, DEFAULT `now()`).
- **FR-009**: System MUST create a new `public.moderation_actions` table with at minimum: `id` (UUID PK), `target_type` (TEXT, NOT NULL — `'listing'` in v1), `target_id` (UUID/TEXT, NOT NULL — the reported listing), `report_id` (UUID, NULL/NOT NULL — the report being resolved, FK to `public.reports(id)`), `action` (TEXT, NOT NULL, CHECK over `dismiss` / `hide` / `mark_duplicate` / `delete`), `performed_by` (UUID, NULL, FK to `auth.users(id)` with `ON DELETE SET NULL` so the log survives the admin's deletion), `performed_at` (TIMESTAMPTZ, NOT NULL, DEFAULT `now()`), `reason` (TEXT, NULL — optional moderator note), `before_state` (JSONB, NULL), and `after_state` (JSONB, NULL). The table is append-only (no client UPDATE/DELETE; written only by the resolution path).
- **FR-010**: Submitting a report from the client MUST go through a privileged server-side write path — a `submit_report(listing_id, reason, note)` SECURITY DEFINER RPC — that (a) requires an authenticated session (rejects anonymous callers with a structured error, mirroring the Phase 17 `auth_required` posture), (b) validates the target listing exists AND is currently `status = 'approved'` (mirroring `record_lead_event` / `add_favorite`), rejecting non-approved or non-existent targets with a structured error (per Q6=A), (c) enforces the open-report dedup (FR-004), (d) inserts the `reports` row with `reporter_user_id = auth.uid()` and `status = 'new'`, and (e) MAY capture the reporter IP and user-agent (mirroring the Phase 16 `record_lead_event` capture). No direct client INSERT grant on `public.reports` is given, so a client cannot forge a report with a foreign `reporter_user_id`.
- **FR-011**: System MUST create indices supporting the primary access patterns — at minimum an index for the admin queue (`reports(status, created_at DESC)`) and an index for the reporter's "My Reports" / per-listing-reporter lookups (`reports(reporter_user_id, created_at DESC)`), plus support for the open-report dedup lookup by `(reporter_user_id, listing_id, status)`.

#### Report resolution (admin)

- **FR-012**: Resolving a report MUST go through a privileged path mirroring the Phase 12 `approve_listing` / `reject_listing` pattern: a `resolve_report` Edge Function that (a) extracts the caller's JWT, (b) gates on the caller holding `reports.manage` (via `current_user_has_permission('reports.manage')`), and (c) on success invokes a SECURITY DEFINER `resolve_report_internal` RPC granted to `service_role` only. The RPC MUST NOT be client-callable. An unauthorized caller MUST be rejected at the Edge-Function permission check.
- **FR-013**: The `resolve_report_internal` RPC MUST, in a SINGLE transaction: (a) verify the report is still open (`status` ∈ {`new`, `reviewing`}) and reject/no-op a double-resolution; (b) set the report's terminal status, `resolved_by` = the acting admin, `resolved_at = now()`, and a `resolution` recording the chosen action; (c) insert one `public.moderation_actions` row per resolved report — the triggering report plus any auto-resolved siblings on the same listing for a listing-affecting action (FR-016) — each capturing the action, target listing, resolver, and before/after listing state; (d) apply the listing-status transition required by the action (FR-014) using the existing Phase 12 transition machinery so `listing_status_history` and the listing audit triggers fire; and (e) ensure the resolution is audit-logged (an `audit_logs` row recording actor, action, target, and before/after).
- **FR-014**: The four moderation actions MUST map to the EXISTING Phase 10 listings status enum (no new status value is introduced, per Q1=A): **dismiss** → the listing status is UNCHANGED and the report becomes `dismissed`; **hide** → the listing transitions to `paused` and the report becomes `resolved`; **mark_duplicate** → the listing transitions to `rejected` with a "duplicate" reason recorded, and the report becomes `resolved`; **delete** → the listing transitions to `deleted` (soft-delete) and the report becomes `resolved`.
- **FR-015**: A listing-affecting moderation action (hide / mark_duplicate / delete) MUST take the listing off the public surface immediately — because public/anonymous read is gated to `status = 'approved'`, transitioning to `paused` / `rejected` / `deleted` removes it from the home feed, search, and map without any further code change.
- **FR-016**: When a report is resolved with a **listing-affecting** action (hide / mark_duplicate / delete), the resolution path MUST, in the SAME transaction, auto-resolve every OTHER currently-open report on the same listing — moving each to a terminal `resolved` status and writing each its own `public.moderation_actions` row that references the triggering resolution (via the moderator-note/`reason` field and/or `before_state`/`after_state`) using the same `action` value (no new action enum value is introduced). The listing-status transition itself applies exactly once. A **dismiss** action (no listing change) MUST NOT auto-resolve sibling reports — only the dismissed report is affected, because a dismissal makes no statement about the other reports' validity. This keeps the queue self-cleaning: a hidden/duplicated/deleted listing leaves no stale open reports, while every report still carries its own auditable disposition.
- **FR-017**: Destructive moderation actions (delete; and any action that takes a listing down — hide / mark_duplicate) MUST require an explicit confirmation step in the admin UI before the resolution is submitted (matching the Phase 7/12 destructive-action confirmation convention).

#### Admin moderation surface

- **FR-019**: The reports queue MUST be reachable from the Phase 6 admin home via an entry gated on the `reports.manage` permission (using the frontend `PermissionChecker`, exactly as `listing_review` gates on `listings.approve` / `listings.reject`), and MUST be denied at the RLS layer for callers without `reports.manage` (Principle "checks at both ends").
- **FR-020**: The reports queue MUST list reports ordered by `created_at DESC` (newest first), each showing the reported listing, the reason, the reporter, and the note, MUST be filterable by status and by reason, and MUST paginate (cursor- or page-based, matching the Phase 13 home-feed pattern) rather than issuing an unbounded query.
- **FR-021**: Opening a report in the admin surface MUST present enough listing context to make a resolution decision and MUST offer the four moderation actions (dismiss / hide / mark_duplicate / delete) with the destructive-action confirmation per FR-017.
- **FR-036**: The admin surface MUST offer an explicit "Start review" action (separate from resolving) that transitions an open report from `new` to `reviewing` and records the claiming admin in `reports.reviewing_by` and the claim time in `reviewing_started_at` (per Q4=B). ### Key Entities

- **Report**: A signed-in user's complaint about a single listing, carrying the reporter, the chosen reason (one of the eight canonical reasons), an optional note, a lifecycle status (`new` → optionally `reviewing` → terminal `resolved`/`dismissed`), and, once resolved, the resolving admin, the resolution timestamp, and the recorded resolution. An admin may claim a report for review via an explicit "Start review" action (an advisory, overridable soft lock recorded in `reviewing_by` / `reviewing_started_at` per FR-036); the claim is optional signposting and resolution is valid from either `new` or `reviewing`. Readable by its own reporter and by `reports.manage` holders only. At most one OPEN report exists per (reporter, listing); a fresh report may follow a terminal one.
- **Moderation Action**: An append-only record of the action an admin took when resolving a report — one of `dismiss` / `hide` / `mark_duplicate` / `delete` — tagged with the target listing, the originating report, the performing admin, an optional moderator note, and the listing's before/after state. Readable by `reports.manage` holders only; never written by a client directly (only by the resolution path). Survives the performing admin's account deletion.
- **Report Submission**: The user-facing action of flagging a listing from the Phase 13 details page — auth-gated (anonymous tap prompts sign-in), reason-driven, idempotent per open (reporter, listing), durable server-side via the `submit_report` SECURITY DEFINER RPC.
- **Report Resolution**: The privileged admin action of disposing of a report — gated at both the Edge-Function permission check and the service-role RPC, atomic (report status + moderation action + listing transition + audit in one transaction), and audit-logged. The listing transition (if any) reuses the existing Phase 12 status machinery.
- **Reports Queue**: The `reports.manage`-gated, paginated, newest-first admin list of reports, filterable by status and reason, from which each report is opened and resolved.
- **My Reports**: The signed-in user's private, paginated, newest-first list of their own submitted reports with status and resolution, reached from a Profile tile; complemented by an inline reporter-only status banner on the listing details page.

## Assumptions

- **Reporting is an authenticated-only capability** (Q2=A): submitting a report requires a Supabase Auth session because `reports.reporter_user_id` foreign-keys `auth.users(id)` NOT NULL and the acceptance criterion "reporters see the resolution status on their report" requires an identifiable reporter. Anonymous users see the Report CTA and are prompted to sign in — mirroring the Phase 17 anonymous-heart posture exactly. This is a deliberate narrowing of the IMPLEMENTATION_PLAN §6.4 "Anyone (insert)" wording, chosen because anonymous reports cannot be shown a resolution status and are higher-abuse; recorded here per Principle XII (no hidden product decisions).
- **The four moderation actions reuse the existing listings status enum** (Q1=A): `dismiss` (no listing change), `hide` → `paused`, `mark_duplicate` → `rejected` (reason "duplicate"), `delete` → `deleted`. Phase 18 adds NO new value to the Phase 10 `listings.status` CHECK and reuses the Phase 12 status-transition + `listing_status_history` + audit machinery. Because public/anonymous read is already gated to `status = 'approved'`, any non-approved transition removes the listing from public surfaces with no further code change. A dedicated moderation `hidden` status was rejected as unnecessary schema churn for v1; a minimal dismiss+delete-only set was rejected as narrower than the plan's stated action list.
- **Reporters see resolution status on BOTH a "My Reports" page and an inline details-page banner** (Q3=Both): a Profile-tile "My Reports" list (mirroring the Phase 17 "My Favorites" tile + `/favorites` route, here `/reports`) AND a reporter-only banner on the Phase 13 listing details page. Both surfaces are driven by the reporter-self RLS read policy, never an application-layer trust.
- **Resolution follows the Phase 12 Edge-Function-plus-`*_internal`-RPC pattern**, NOT a pure client RPC. The repo's established posture for permission-gated admin mutations (`approve_listing` / `reject_listing` in `supabase/functions/`, each calling a service-role-only `approve_listing_internal` / `reject_listing_internal` SECURITY DEFINER RPC) is mirrored by `resolve_report` (Edge Function, gates on `reports.manage`) + `resolve_report_internal` (service-role RPC, atomic mutation). Report *submission* follows the lighter Phase 16/17 SECURITY DEFINER RPC pattern (`submit_report`, like `record_lead_event` / `add_favorite`), granted to `authenticated` only, because submission needs no cross-permission gate beyond an authenticated session.
- **Reports are NOT lead events.** The `lead_events` table (Phase 16) is high-volume engagement telemetry with its own four `event_type` values; reports are a distinct moderation entity in their own `public.reports` table. Phase 18 does NOT add a `report_submitted` value to `lead_events.event_type`, and does not write to `lead_events` at all.
- **The open-report dedup key is (reporter_user_id, listing_id, status ∈ {new, reviewing}).** A partial unique index (or an in-RPC existence check) enforces "at most one open report per reporter per listing"; a terminal report does not block a fresh report, so a recurrence after resolution can be re-flagged. The exact enforcement mechanism (partial unique index vs. RPC `EXISTS` guard) is plan-time; the spec mandates the behavior (FR-004).
- **The `submit_report` RPC requires the target listing exist AND be currently `approved`** (Q6=A), mirroring the `record_lead_event` / `add_favorite` gate — a crafted call against a `draft`, terminal, or non-existent listing is rejected with a structured error. This does not block the `already_sold_or_rented` reason, which is filed while the listing is still shown as `approved` but sold in reality.
- **FK delete behaviors**: `reports.listing_id` uses `ON DELETE RESTRICT` (Phase 16 `lead_events` / Phase 17 `favorites` precedent — listings soft-delete via `status='deleted'`, so the FK is never exercised). `moderation_actions.performed_by` uses `ON DELETE SET NULL` (the moderation log must survive the admin's deletion). `reports.reporter_user_id` delete behavior (`CASCADE` like `favorites` vs. `SET NULL` like `lead_events`) is plan-time; the spec mandates only that a deleted user leaves no orphaned reporter identity and no dangling FK.
- **The `reports.manage` permission already exists** and is seeded onto the `moderator` and `admin` roles (per `supabase/migrations/20260515120003_create_role_permissions.sql`); Phase 18 introduces NO new permission key and is the first consumer of `reports.manage`. The frontend `PermissionChecker.any([...])` / `.has('reports.manage')` API (Phase 6) gates the admin surface exactly as `listing_review` does.
- **Audit logging reuses the Phase 4 `audit_logs` table.** The resolution writes a moderation `audit_logs` entry through the established pattern (the listing-status transition fires the existing Phase 10/12 listing audit triggers; the moderation action itself is audit-logged with actor/action/target/before/after). No parallel audit mechanism is introduced.
- **The Phase 13 `PerListingActionBlock` already renders a Report CTA wired to a Coming-soon snackbar** (`_showComingSoon`, `l10n.action_report_coming_soon`, `Icons.flag_outlined`, `l10n.cta_report`). Phase 18 surgically rewires only the Report CTA's handler + label, leaving the Share stub and the Phase 17 Favorite toggle untouched and not reflowing the surrounding widget tree — exactly as Phase 17 surgically rewired only the Favorite CTA.
- **The new `/reports` route is added to the Phase 1 `go_router` surface** (`AppRoutes`/`AppRouteNames` in `lib/core/routing/app_router.dart`) alongside the existing routes; its entry point is the authenticated-only Profile tile, mirroring the Phase 17 `/favorites` entry. The admin queue route lives under the `/admin/...` namespace consistent with `/admin/listing-review/pending`.
- **No automatic duplicate detection** (IMPLEMENTATION_PLAN §1 non-goal): `mark_duplicate` is a purely manual admin action; Phase 18 ships no heuristic or automated duplicate matching.
- **No reporter↔publisher messaging, reporter reputation scoring, report-reason-specific automation, or report rate-limiting beyond the open-report dedup** is introduced — each is a separate future spec. Publishers are NOT notified of reports against their listings in Phase 18 (notifications are Phase 22's concern); a publisher learns of a moderation outcome only through the listing's resulting status change and `listing_status_history`.
