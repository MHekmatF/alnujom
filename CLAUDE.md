Cross-cutting:
- [docs/decisions/0001-secrets-and-pii-storage.md](docs/decisions/0001-secrets-and-pii-storage.md) — the FCM service-account JSON is the single Vault secret `fcm_service_account` (+ `push_dispatch_url`/`push_dispatch_token`), registered from env (no plaintext), read only server-side by `dispatch_push`/`notify_push_dispatch`; NEVER committed, NEVER shipped to the client. `notifications`/`notification_tokens` are self-only RLS, all client writes REVOKEd; fan-out writes only via the `enqueue_notification` definer path — checks-at-both-ends (Principle III).
- DEPARTURE from the recent zero-new-deps/zero-extension pattern (Phases 19/21), feature-justified + recorded in plan Complexity Tracking: ONE new client dep (`firebase_core`+`firebase_messaging`, data-layer only behind `PushMessagingService`, app builds with push disabled — Principle IX/XI) + ONE new Postgres extension (`pg_net`, for the source-controlled push-dispatch trigger). NO new permission key, NO §9.1 change, NO new audited action, NO existing-table change beyond the 3 Realtime publication adds.
- Provider-agnostic core / sanctions fallback: in-app delivery + the notification center + Realtime ALWAYS work; device push is pluggable and degrades **silently** (no user-visible error, no build break) when Firebase/Vault-secret is absent — `notify_push_dispatch` skips when the dispatch secret is null and `NoopPushMessagingService` stands in when Firebase is unconfigured (FR-013, the plan's flagged Syria sanction risk).
- Localization on both surfaces: in-app copy follows the viewer's active locale (rendered client-side from `type`+`params`); OS-tray push copy is server-rendered by `dispatch_push` in the recipient's preferred language (default Arabic) and stays GENERIC — the full rejection reason is shown only in-app behind the deep link, never on the lock screen (FR-004).
