Cross-cutting:
- Zero-new-deps / zero-new-extension posture (back to the Phase 19/21 pattern, unlike Phase 22): Phase 23 adds ONE table (`app_settings`), ONE definer RPC (`set_app_setting`), ONE audit trigger — NO new dependency, NO new Postgres extension, NO new permission key, NO §9.1 change, NO change to any existing table.
- Security at both ends (Principle III): `app_settings` RLS with per-key public/sensitive read (`is_public OR current_user_has_permission('settings.manage')`); ALL client writes REVOKEd; the only mutation path is `set_app_setting`, which re-checks `settings.manage` server-side and is audited via `trg_app_settings_audit` (the §9.4 Phase 23 action).
- Maintenance mode: fetch-on-load + foreground-resume (NOT Realtime — Phase 22's Realtime scope is unchanged); the gate sends everyone to `MaintenanceScreen` EXCEPT `settings.manage` holders (so the operator who flips it on is never locked out); a failed settings fetch is fail-open (safe defaults, NOT maintenance-on, never a crash).
- Forward-only defaults: default language/currency seed NEW users at registration (client-side); publisher-name/location-visibility defaults pre-select NEW listings; existing users/listings are never retroactively rewritten.
- Forward-stated future work (OUT of Phase 23): per-user settings beyond `user_preferences`, sensitive (`is_public=false`) settings keys (the column exists, none seeded in v1), Realtime-driven settings, a curated supported-currencies allow-list — each a separate future spec.
